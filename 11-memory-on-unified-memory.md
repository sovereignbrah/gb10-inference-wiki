# Memory management on a unified-memory GB10

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 128 GB LPDDR5X shared by CPU and GPU, about 119.6-121.7 GiB visible to the OS and to CUDA), one to three nodes (node-1, node-2, node-3). Pairs are node-1 (head) + node-2 unless a row says otherwise; the three-node DeepSeek V4.1 SGLang lane used node-3 as head, the three-node GLM lane uses node-1. Code is quoted at these pins: vLLM `34b069080d9f`, SGLang `2909f84e3b2f`, llama.cpp `6e60f35608ec`, ExLlamaV3 `6b84a21b6f1e`, antirez/ds4 `0aaea5a238fb`. The own lanes run older or forked builds, so a code line says what upstream does now, not what a given lane runs. Vocabulary: "available" is Linux `MemAvailable` (includes reclaimable page cache), "free" is `MemFree`. SGLang prints "GB" in its memory lines but divides by 2^30, so every SGLang figure on this page is GiB (logged as GB).

## 1. What it is

A GB10 has one pool of memory, 128 GB of LPDDR5X, and the CPU, the operating system, the desktop, the network stack and the GPU all draw from it; there is no separate graphics memory to fill. Inference engines were written for cards with their own memory, so each needs a rule for how much of the shared pool it may take. On GB10 they all start from MemAvailable (the kernel's reclaimable-memory estimate) and then take a share of the total or hold back a slack. The biggest single allocation is the KV cache (the conversation's per-token memory), sized once at start-up. Around it sit fixed costs (weights, CUDA graphs (pre-recorded GPU launch sequences), network buffers, compile caches) and transients (scratch buffers that swell during a long prompt and are not always given back). Three facts turn this from a capacity question into a speed-and-uptime question. First, "available" is not "allocatable": the GPU driver needs truly free pages, and reclaiming page cache (file data kept in RAM) takes time, so an allocation can fail while the box still reports gigabytes available. Second, memory the driver pins (locks in place for the GPU) is invisible to the Linux out-of-memory killer, to cgroups and to swap, so when the pool runs dry the kernel kills the wrong process, or the whole node stops answering and needs a power cycle. Third, the numbers do not repeat exactly: page cache, uptime and boot order change what an identical configuration gets. Every speed lever that spends memory (a bigger KV pool, a larger prefill chunk, a speculative drafter) is paid from the same few gigabytes of headroom that keep the node alive. That is why this page is a budget and a protocol, not a single setting. Related pages: [Prefill optimization on GB10](04-prefill-optimization.md), [KV cache and prefix caching on GB10](10-kv-cache-and-prefix-caching.md), [Inter-Spark communication](03-inter-spark-communication.md), [SM121 hardware facts](17-sm121-hardware-facts.md).

## 2. How each engine does it

### vLLM

- Free memory on GB10. `MemorySnapshot.measure()` takes the total from `torch.accelerator.get_memory_info` and, when `current_platform.is_integrated_gpu()` is true, replaces free with `psutil.virtual_memory().available`, which is MemAvailable (vllm/utils/mem_utils.py:143-151). [Code-verified] PR #35356 (merged, 995e9a20) introduced the `is_integrated` detection; an older compute-capability tuple already included (12,1), so GB10 took the psutil path before that PR too. [Code-verified] The PR author measured, at one instant on one GB10, CUDA free 39.21 GiB against psutil available 113.06 GiB, total 119.70 GiB. [Community-measured]
- Budget. `requested_memory = ceil(total x gpu_memory_utilization)`, and start-up raises a ValueError if free (psutil) is smaller (v1/worker/utils.py:533-552). KV = requested - non-KV - CUDA-graph estimate (v1/worker/gpu_worker.py:660-664); non-KV = the drop in free memory from engine creation to the end of profiling plus (torch peak - torch allocated) (mem_utils.py:309-321). [Code-verified] Consequence: utilization is a share of the whole shared pool. The OS, desktop, containers, non-reclaimable cache and every transient vLLM does not profile must fit inside (1 - util) x total. At a 121.7 GiB total each 0.01 of utilization is about 1.2 GiB, and the default 0.9 leaves about 12 GiB for everything else. [Interpretation] The MiaAI-Lab GLM EXL3 2x kit README states the same rule ("each 0.01 is 1.2 GiB of host headroom"). [Community-measured]
- Explicit KV bytes. With `--kv-cache-memory-bytes`, vLLM still runs `profile_run()`, then returns the pin and logs "... skipped memory profiling. This does not respect the gpu_memory_utilization config" (gpu_worker.py:581-603). [Code-verified] A pinned KV size removes vLLM's only computed margin; the own launches that died this way are in §4.
- Pressure release. `release_device_memory_under_pressure` empties the caching allocator on integrated GPUs when at least 512 MiB is releasable and psutil available is at or below 20% of total (mem_utils.py:46-79; PR #45179, merged 2026-06-11, 5edf7ff4). It has one call site, in the weight-loader loop. Nothing equivalent runs while serving at this pin. [Code-verified]
- Profiling is not capped by utilization. Issue #46307 (open): Gemma-4 26B-A4B bf16 (48.54 GiB of weights) at util 0.70; during `profile_run` MemAvailable fell 14,228 to 7,352 MiB, about 112 GiB in use against about 83 GiB implied, and unwatched runs needed a power cycle. The same settings served on a discrete 96 GB card. [Community-measured] PR #49760 (open, head 51e122a1) would cap the budget at min(util x total, available - max(8 GiB, 5%)) and set `torch.cuda.set_per_process_memory_fraction` before profiling so an oversized transient raises a clean OOM. Reviewers found two gaps (explicit-KV runs get a ceiling below their own KV size; weights load before the cap). A follow-up that installs the cap in `init_device()` passed 30 native tests on GB10; the original wedge was not reproduced under the fix. [Proposed]
- The batch budget is charged at profile time. On a single-node DeepSeek-V4-Flash, changing only `MAX_NUM_BATCHED_TOKENS` (MNBT) from 8224 to 2048 cut the profiled activation peak 5.30 to 1.39 GiB and grew the pool 290,632 to 1,262,567 tokens; the profiled peak also grows with `max_model_len` (1.39 to 2.23 GiB from 262K to 1M). [Community-measured] (MiaAI-Lab/DeepSeek-v4-Flash-One-DGX-Spark issue #4) The same issue records the catch in §7. PR #48322 (open, docs only) would document the trade-off.
- GLM-5.3-Flash sparse-indexer workspace. Stock vLLM reserves `max_model_len x 40` entries, 5,036.40 MiB at 1M, locked for the life of the process and subtracted from KV. The kit's `rightsize` mode bounds it to min(max_num_seqs, MNBT) x cdiv(max_model_len + k, compress_ratio). [Code-verified] (MiaAI-Lab GLM EXL3 2x kit, docs/DESIGN-indexer-workspace.md at 71962cd) Per-step indexer logits are capped by `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB`; see [Prefill optimization](04-prefill-optimization.md).
- Boot lines. vLLM prints `Available KV cache memory: X GiB` (requested - non-KV - graph estimate). With a pin it prints the "reserved ... as specified by kv_cache_memory_bytes" message above. With CUDA-graph memory profiling on (default since v0.21.0 per the log text) it also prints the utilization equivalent and a suggested value. [Code-verified] `GPU KV cache size: N tokens` is max_concurrency x max_model_len, with the per-request block demand summed over KV groups (seven on the GLM kit); it is not a prefix-cache capacity. [Code-verified] (MiaAI-Lab GLM kit, docs/DESIGN-kv-capacity-log.md at 71962cd)
- Feature interactions on GB10. `--enable-cumem-allocator` routed about 84 GB of weights through `cuMemCreate`, the driver ran out in `nv_alloc_system_pages`, and both nodes hard-froze (issue #48242). PR #40812 (merged) switches `expandable_segments` off around the CuMem pool, and vLLM rejects KV connectors when that flag is set. Sleep/wake killed EngineCore on GB10 (issue #50011). [Community-measured]
- Env vars and flags seen in GB10 recipes: `PYTORCH_CUDA_ALLOC_CONF`, `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB`, `LONG_PREFILL_TOKEN_THRESHOLD`, `--skip-mm-profiling`, `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS`, `--kv-cache-memory-bytes`, `--gpu-memory-utilization`.

### SGLang

- Free memory on GB10. `get_available_gpu_memory` empties the device cache, then returns `psutil.virtual_memory().available` when `props.is_integrated` (python/sglang/srt/utils/common.py:442-450). [Code-verified]
- Budget. `rest = available_after_load - pre_model_load_memory x (1 - mem_fraction_static) - mm_reservation`, with a floor on the slack for Mamba models (srt/mem_cache/kv_cache_configurator.py:2238-2252). If `rest <= 0` it raises "Loaded weights leave no GPU memory for the KV cache" and suggests a minimum fraction of `1 - available/pre` (2257-2272). [Code-verified]
- What the fraction means. The fraction sets how much is held back as slack: (1 - f) x MemAvailable at launch. On a lane where weights dominate, lowering f raises that slack above what weights leave behind, so the KV budget goes to zero or below and the boot fails or the pool starves. Lowering f frees RAM only when the budget has room to spare. [Interpretation] Own inputs (2026-09-16 DeepSeek V4.1 TP3 memory-ceiling record): 108.90 GiB before load, 7.41 GiB after weights and draft. At f = 0.90 the slack is 10.89 GiB > 7.41, so no pool. The same arithmetic gives a minimum viable f of about 0.932 (rest > 0) and about 0.947 to fit a 750K-token pin (1.59 GiB with SWA), which agrees with the upstream README's "at least 0.944". "0.95 is the only bootable value" is overstated; "at least about 0.945 at these inputs" is the supported form. [Measured] inputs, [Interpretation] arithmetic
- Upstream main versus the lane's fork. At 2909f84e there is no fixed "- 0.1 GB" term (a multimodal reservation takes its place, zero for text-only models), and a `--max-total-tokens` above profiled capacity is not clamped silently: it logs "max_total_tokens=... is larger than the profiled value ... Use the profiled value instead." (kv_cache_configurator.py:2313-2325). [Code-verified] The MiaAI-Lab DeepSeek V4.1 README wording (with - 0.1 GB, "silently clamped") describes its fork build, which the own lane ran.
- Page cache moves the base. On one idle GB10 in an SGLang container: CUDA free 80.75 GiB, psutil available 115.52 GiB, MemAvailable 116.03 GiB, Cached 30.53 GiB; at 0.85 the two bases give 68.64 vs 98.19 GiB. [Community-measured] (NVIDIA forum 383859) The same thread's pool recovery (75,520 to 432,640 tokens) changed three knobs at once (fraction 0.80 to 0.85, running requests 8 to 4, Mamba cache 40 to 20), so it is not a single-lever result.
- Boot lines. `Load weight begin ... avail mem=` and `Load weight end ... avail mem=` (srt/model_executor/model_runner.py:1206, 1298-1302), `Memory pool end avail mem=` (kv_cache_configurator.py:388), and on DeepSeek-V4 `DSV4 memory calculation: ... bytes_per_full_token=... available_bytes=... full_token=...` (srt/model_executor/pool_configurator.py:1516-1527). All in GiB. [Code-verified]
- Prefill transients. GLM-5.3-Flash kpool indexer: `_fp8_mqa_logits` builds a dense fp32 block of about chunk rows x total prompt tokens bytes, so it grows with both chunk and total length; `_should_chunk_mqa_logits` is defined (srt/layers/attention/dsa_indexer_kpool.py:1010) with no call site on that path. [Code-verified] (issue #36941 reporter's reading, confirmed at 2909f84e) DeepSeek-V4 low-ratio indexer: about 14 B x T x L (T = chunk, L = prefix), with the empirical bound T x L below about 2.0e8 token^2, per an "analysis only" design note whose constants come from a report that is not published. [Community-measured] (MiaAI-Lab/DeepSeek-v4.1-Flash-DGX-Sparks docs/chunked-prefill-memory.md at 25379c22) Per-sequence Mamba or linear-attention state is sized by `--max-running-requests` and `--max-mamba-cache-size`. FlashInfer autotune and graph capture allocate outside the tracked pool: one recipe measured 21.30 GiB free after capture at 0.76 and a crash at 0.80 under three concurrent requests. [Community-measured] (hasso5703/dgx-spark-qwen38 docs/gb10-memory.md at 54bb2c3)
- Empty-cache hook. The MiaAI-Lab DeepSeek V4.1 adapter frees cached blocks after each chunk of a sequence at least `DSV41_PREFILL_EMPTY_CACHE_TOKENS` long (default 8192), so the peak is "one chunk's live set instead of the sum over chunks". [Code-verified] (adapter/prefill_empty_cache.py at 25379c22) It is not in upstream SGLang.
- Vendor guidance. The SGLang docs say to lower the fraction to 0.8 or 0.7 on OOM and to lower `--chunked-prefill-size` to 4096 or 2048 for prefill OOM (docs hyperparameter_tuning.mdx at 2909f84e). NVIDIA's playbook says start at 0.85 and go toward 0.70-0.75 on unified memory (dgx-spark-playbooks at 3410c65). [Interpretation] (vendor doc) Correct only when the budget has room (above).

### llama.cpp and forks

- llama.cpp mainline. When `prop.integrated` is set, or `GGML_CUDA_ENABLE_UNIFIED_MEMORY` is set, device free is read from `/proc/meminfo` MemAvailable; SwapFree is not added (under hugetlb, available is free hugepages and SwapFree is zeroed) (ggml/src/ggml-cuda/ggml-cuda.cu:5050-5070; PR #17368 "DGX Spark: UMA support", merged 2025-11-20). There is no fraction knob. `--fit` is on by default with a 1024 MiB target margin per device, and `--cache-ram` defaults to an 8192 MiB host prompt cache, which on GB10 comes out of the same pool (common/common.h, common/arg.cpp). The per-device `integrated` flag is hard-set to false because of corrupted output (ggml-cuda.cu:307, issue #15034), so there is no zero-copy host-buffer path. The env var switches allocations to `cudaMallocManaged`. [Code-verified] Compute buffers are sized at context build from `--ubatch-size`; the documented ubatch failure (#17578, filed on AMD gfx1151, GB10 repro only in one blog) is a ggml graph-pool assertion, not unified-memory exhaustion. [Community-measured] No GB10 long-prefill memory measurement for mainline was found. One forum reply says `--cache-ram` "does not make sense on Spark" (forum 357012). [Community-measured]
- antirez/ds4 (the lineage behind the Entrpi fork). Non-movable memory is `MemAvailable - CmaFree`, commented "CMA pages can back movable allocations, but not ordinary pinned GPU pages" (ds4_linux_memory.h). On integrated CUDA devices that figure minus an 8 GiB reserve sizes the streaming expert cache (ds4_cuda.cu:3152-3177). The KV cache switches to `cudaMallocManaged` when it is at least 8 GiB, or when context buffers crowd free memory, "to keep oversized contexts from turning memory pressure into a machine-wide lockup" (ds4.c:19195-19215); that decision uses `cudaMemGetInfo`, not MemAvailable. The process sets its own `oom_score_adj` to 1000. It logs `memory: KV ... + buffers ... + resident model ... = ... planned` (ds4.c:42459-42477) and `using managed KV cache` (19210). The `MemAvailable - CmaFree` baseline in the GLM graph guard is compiled only into the ROCm build (45405-45440). [Code-verified]
- ds4 arena waste. A fixed 1792 MiB weight-arena chunk wasted 35.7% on 1152 MiB spans (12.25 GiB of arenas for 7.88 GiB of spans) and caused a start-up OOM at any context size; one commenter's workaround, `DS4_CUDA_WEIGHT_ARENA_CHUNK_MB=2304`, loads and serves (not a merged fix). A smaller `--prefill-chunk` let the regressed build start but it OOM'd on the first prompt. [Community-measured] (antirez/ds4 issue #585)
- Entrpi/ds4 (b0a147a). The README documents an automatic cache budget of "80% of the backend's recommended working set" for SSD streaming. [Community-measured] The own single-node row in §4 shows its governor admitting 4 of 32 requested banks.
- Anemll/dspark-vllm-gx10 (081fda9) is a vLLM fork, so vLLM's accounting applies. Its README says a 155.43 GiB FP8 checkpoint is not runnable on one node, and a TP=1 launch hit `NV_ERR_NO_MEMORY` before the API was ready. [Community-measured]

### ExLlamaV3 in vLLM

- Inside vLLM, EXL3 is a quantization method and vLLM's budget governs (§2 vLLM). [Code-verified]
- EXL3-specific memory. `EXL3_TEMP_ROWS_FUSED` is the number of fused `exl3_moe` rows per expert; experts above it are "fat". The kit says to keep it at or above `MAX_NUM_SEQS x (DFLASH_TOKENS + 1)` so decode stays one graph-safe launch (defaults 32 with E3, 256 with E2). A 1024-row temp lost the A/B (commit c9f731f). The E3 fat-row scratch is 560 MiB and is charged to the KV budget by vLLM's profile run. [Community-measured] (MiaAI-Lab GLM EXL3 2x kit at 71962cd) The kit's "never MNBT 8192" limit (docs/improve-prefill.md and start.sh: "oversubscribes GB10 persistent_topk smem") is an on-chip shared-memory limit, not a unified-memory one. No per-byte measurement of temp-row scratch beyond the 560 MiB was found.
- Loader and allocator defaults. The GLM kit sets `expandable_segments:True` when `PYTORCH_CUDA_ALLOC_CONF` is unset (PR #175, merged, only made it overridable). With the InstantTensor loader the kit left 12.4-12.5 GiB of available KV at 850K context against 17-18 GiB with it off (three boots each), and `GPU_MEM_UTIL=0.85` no longer booted without an explicit 14 GiB pin. [Community-measured]
- Host-side tables. On DeepSeek V4.1 EXL3 the Engram row store never pins host memory; vLLM `cpu_offload` would `cudaHostAlloc` about 47 GiB per layer for those tables. [Community-measured] (MiaAI-Lab/DeepSeek-v4.1-Flash-EXL3-2x-DGX-Sparks README at 6f7d159)
- ExLlamaV3 standalone budgets with `torch.cuda.mem_get_info` only, with no integrated-GPU branch (exllamav3/util/memory.py at 6b84a21), so on GB10 it counts page cache as used and errs conservative. [Code-verified] Not GPU-validated on GB10 here; no GB10 report found.

## 3. What is different on GB10 / SM121

- [Interpretation] (vendor doc) One pool. NVIDIA says `cudaMemGetInfo` on DGX Spark under-reports allocatable memory because it ignores what the CPU could free by swapping, gives sample code that reads MemAvailable and SwapFree, and says `nvidia-smi` shows "Memory-Usage: Not Supported" by design. The CUDA-for-Tegra app note (section 3.3) gives the formula: host allocated = used - device allocated, allocatable = total - (host used - free swap) when host use exceeds free swap.
- [Code-verified] vLLM, SGLang and llama.cpp all treat MemAvailable as GPU free on GB10 (§2). MemAvailable counts reclaimable page cache, so a fresh model download or a large file copy moves the KV budget.
- [Community-measured] Available is not allocatable. A six-boot ladder on a GLM-5.3-Flash TP2 pair: vLLM's suggested 4.14 GiB KV worked 3 of 3; 5.5 GiB and up never survived (0 of 5), with NVRM OOM in dmesg, while MemFree sat at 0.7-4.4 GiB during the shard load and the rest was page cache. `drop_caches`, a fresh reboot and a 112 GiB cgroup cap did not move the ceiling. (tonyd2wild ladder at 9fea48c) One maintainer reports the driver refusing allocations near MemFree of about 3 GiB, and gates on MemFree only while MemAvailable is below 10 GiB because MemFree legitimately sits near zero during loading (0.9 GiB MemFree, 32 GiB MemAvailable, zero driver errors). (MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark README at 6b50864)
- [Interpretation] `NV_ERR_NO_MEMORY (0x51)` from the driver's own allocation path can fire below the CUDA runtime, so the application may never see `cudaErrorMemoryAllocation`, and it can fire while MemAvailable is large because reclaim has to finish first. (forum 353752 post 16; forum 363989 post 3, "descriptor allocations can fail if system RAM or page file is depleted or heavily fragmented")
- [Community-measured] Nothing in the Linux accounting sees driver allocations. 10.7 GB allocated on the GPU raised the cgroup's `memory.current` by 377 MB, and a Docker container escaped a `systemd-run --scope MemoryMax` wrapper (forum 353752 post 17); a container cgroup showed 9.6 GiB while the host had 118 GB in use (lrozewicz/vLLM-Moet-GB10 at 8da6cf9). The OOM killer scores by RSS, so in one 2x EXL3 incident it killed desktop daemons while the engine held the memory (MiaAI-Lab DS V4.1 EXL3 2x README). Own 2026-09-16 record: the OOM killer took a small desktop daemon twice and never the engine. [Historical diagnostic]
- [Community-measured] vLLM's "non-torch" line absorbs host activity: same image and model (Qwen3-0.6B-FP8), non-torch forward increase 3.55 GiB on GB10 vs 0.01 GiB on an x86 host with an RTX 5090 (forum 353523).
- [Interpretation] (vendor forum) No GPUDirect RDMA: iGPU `cudaMalloc` memory is not coherently reachable by PCIe devices, so NCCL stages through host buffers from the same pool and logs `GDR 0` (forum 352051 post 2; camerono/gb10-nccl-recipe at f235d6d). NCCL connection buffers therefore land in pinned, unreclaimable `Shmem`; see [Inter-Spark communication](03-inter-spark-communication.md).
- [Community-measured] Kernel 7.0.0-1019-nvidia broke multi-node registration through pinning capacity, not bytes: default-on kexec handover marks 4,761 pageblocks (about 9.30 GiB) as `MIGRATE_CMA` without counting them in `CmaTotal`, and `ibv_reg_mr` long-term pins fail at 108 GiB of committed CUDA pressure; `kho=off` fixes it (NVIDIA/NV-Kernels PR #590, open). NVIDIA advised multi-node users to hold that kernel and later said a hotfix adding `kho=off` was rolling out (forum 383254). [Interpretation] (vendor forum) for the advisory.
- [Community-measured] The firmware reserves about 2 GiB for display scanout that CUDA never sees, even headless; with `nvidia_drm modeset=1 fbdev=0` and no desktop, up to 2032 MiB can be carved from it as KV backing, at about 69% of normal read bandwidth (MiaAI-Lab GLM PR #234, open). No NVIDIA document on this reservation was found.
- [Community-measured] Driver versions change the failure clock. On 2-node GB10 the first idle `NV_ERR_NO_MEMORY` came 2 min 24 s after boot on driver 580.142 and 67-72 min after boot on 580.159.03; under load 580.142 escalated to a host wedge (forum 363989 post 4). Driver 590.48.01 did not release unified memory after the CUDA process exited; 580.126.09 did (forum 359969).
- [Community-measured] Swap can page out cold host memory to make room, never pinned device memory: "swap does not touch" `Shmem`-backed GPU allocations (lrozewicz README item 2). Both halves show in own records (§4).
- [Community-measured] Builds and JIT exhaust the same pool. FlashInfer CUTLASS MoE JIT with default ninja parallelism hit the OOM killer (exit 137) on a 4x GB10 SGLang deployment, fixed by `MAX_JOBS=1 NVCC_THREADS=1` at +10-15 min first start (forum 373676); a single-node build fanned out to 38 `nvcc` jobs and passed 121 GB, and `MAX_JOBS=4` held it near 33 GB (vcruz305/Ornith-1.5-35B-A3B-DGX-Spark at 6f0ff0a).
- [Community-measured] Wedged-host signature: ping and L2 answer, TCP 22 accepts, then either no SSH banner or a banner with no login; only a power cycle recovers (NNNtrance/GLM-5.3-Flash-EXL3-DGX-Spark docs at 7f1bd29 section 9.1; lrozewicz item 7; own 2026-08-29 and 2026-09-03 records).
- [Community-measured] `/health` is not liveness: it returned 200 during UVM livelock (MiaAI-Lab GLM kit docs/uvm-livelock-gb10.md), while the kernel was already logging driver OOM (dgx-spark-playbooks issue #97), and up to the fatal request (vLLM issue #54629).
- [Community-measured] Some "memory" wedges are power or thermal events. A vendor-affiliated forum account separates a unit that powers off from one that freezes and recommends capping GPU clocks for power-offs (forum 363989 posts 13 and 15); see [Clocks, thermal, and power](13-clocks-thermal-power.md).

## 5. Levers, ranked

Ranked by evidence strength times headroom recovered on the lanes this fleet runs. A gain here is headroom (GiB of MemAvailable at the warm floor) unless stated.

1. **Cap the token pool on SGLang below the measured slack** (`--max-total-tokens`). Applies to: SGLang x any model x 1, 2 or 3 nodes. Gain: +15-17 GiB per node (TP2, 3.2M cap) and 6.7 -> 29 GiB (single node, 1.64M -> 1.05M tokens), at -1.5% on a 486K prefill [Measured]. Cost: logical pool capacity (pool sizing on [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md)), which is rarely filled: one own 1M request used 52% of the GLM TP3 pool, and a community 600K prompt used 76% of its pool. Risk: a cap above profiled capacity is ignored with a warning at upstream main (§2), so read the log. Smallest falsifying experiment: one boot with the cap at the measured peak live-token count plus 10%; if warm available rises by less than the pool bytes removed, the cap is not the binding term.
2. **On vLLM, lower utilization and let auto-KV size the pool; do not pin KV to force a length.** Applies to: vLLM (incl. EXL3) x any family x 1-3 nodes. Gain: each 0.01 is about 1.2 GiB [Interpretation]; 0.87 -> 0.84 gave a qualified lane with 4.3-7.2 GiB headroom; 0.835 -> 0.73 with FP8 KV kept about 2.27M tokens and 16-20 GiB available [Measured]. Cost: pool tokens. Risk: an explicit pin is the only way past some kit defaults (InstantTensor), and it removes the profiled margin (five failed launches, §4). Smallest falsifying experiment: two boots, util U and U - 0.02, same pull; if warm available at the floor point moves by less than 2 GiB, something outside utilization is binding.
3. **Right-size fixed costs and bank the bytes as headroom before spending them.** Applies to: vLLM GLM-5.3 (indexer `rightsize`: 5,036 MiB workspace at 1M bounded to the request shape [Code-verified]), GLM dense FP8 weights (82.01 -> 79.61 GiB/rank, head warm 5.3-5.5 -> 9.7 GiB [Measured]), drafter grouping fixes (pool 501K -> 907K tokens at equal memory [Measured]), lower-bpw weights (a 2.9 bpw DeepSeek V4.1 EXL3 port runs about 64.6 GiB/rank vs about 101 native [Measured], experimental). Cost: engineering or a quality check for format changes (formats: [GEMM backends and quant formats](09-gemm-backends-and-quant-formats.md); gates: [Quality and correctness gates](21-quality-and-correctness-gates.md)); dense FP8 prefill was −18 to −21% in the own A/B (BF16 is 22-26% faster), with decode +7-14% at short depth (+1% at 120K). Risk: spending the freed bytes in the same boot (see §7, the wedge that lasted until a power cycle). Smallest falsifying experiment: one boot with only the right-sizing change, pin unchanged; the warm floor should rise by at least 80% of the predicted bytes.
4. **Prefill chunk size as the transient lever** (vLLM MNBT and long-prefill threshold, SGLang `--chunked-prefill-size`, ds4 `--prefill-chunk`). Applies to: every engine on long-context lanes; biggest on sparse-indexer models (GLM-5.3, DeepSeek V4/V4.1). Gain: 8192 -> 1024 recovered about 4 GiB at the minima on DS V4.1 EXL3 TP3 [Measured]; 7168 -> 2048 grew the GLM TP3 pool 2.58M -> 3.37M from the same pin [Measured]; 8192 -> 2048 turned a 300 s timeout into a 65.5 s pass on a SGLang kpool pair [Community-measured]. Cost: prefill rate (+26% at 32K for 8192 on DS V4.1 EXL3; halved at chunk 256 on DS V4.1 SGLang). Risk: direction depends on where you measure: on one DS V4.1 EXL3 pair 1536 left more boot headroom than 1024 (0.09 vs 3.50 GiB) [Community-measured], and where a workspace is locked after warm-up a smaller MNBT boots but asserts later (§7). Chunk and context must agree (1024 with at most 131K on the SGLang DS V4.1 profile). Smallest falsifying experiment: two boots, chunk C and C/2, same unique cold prompt at the lane's longest qualified length; compare per-rank minimum MemAvailable sampled at 1-2 s. See [Prefill optimization](04-prefill-optimization.md).
5. **Bound allocator transients** (empty-cache after each long-prefill chunk; `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB`). Applies to: SGLang DeepSeek-V4 stacks (hook), vLLM sparse-indexer models (logits cap). Gain: indexer replay 32.26 -> 1.04 GiB reserved at 262K [Community-measured]; hook reduces the peak to one chunk's live set [Code-verified]. Cost: 7-10 ms per `empty_cache()` call [Community-measured]. Risk: releasing allocator reserve does not promptly raise MemAvailable (+88-96 MiB per 6.68 GiB released), and the own hook was installed byte-identical and was still insufficient at about 200K x chunk 1024 [Measured]. Smallest falsifying experiment: hook on vs off, one boot each, same 131K unique cold prompt; count NV_ERR and record the head minimum.
6. **`expandable_segments`: decide per stack by A/B, never by rule.** Applies to: any PyTorch engine. Gain or loss: on made the fix on a GLM EXL3 vLLM indexer ratchet (32.26 -> 1.49 GiB) [Community-measured]; on cost 59% of the pool on a 4-node vLLM DeepSeek V4.1 (616,678 vs 1,511,623 tokens) [Community-measured]; on plus autotune gave RM 0x51 errors on a vLLM DeepSeek-V4 TP2 lane [Community-measured]; one SGLang DeepSeek-V4 stack reports NaN logits above 64 query tokens with it on (unpublished, §8). Cost: one boot per arm plus a logit-sum check. Risk: correctness, not only memory. Smallest falsifying experiment: flag on vs off, one boot each, same pull; record the pool, the warm floor, and a greedy logit sum at 64 / 65 / 512 / 4000 tokens.
7. **Small NCCL connection buffers on multi-node lanes.** Applies to: SGLang or vLLM x TP2/TP3. Gain: about 4.6 GiB -> 0.14 GiB of pinned `Shmem` per node [Community-measured, single source]; the own lanes inherited these settings and never measured with and without. Cost: possible collective-latency change (see [Inter-Spark communication](03-inter-spark-communication.md)); `NCCL_LL128_BUFFSIZE` is not in the current NCCL documentation. Risk: low. Smallest falsifying experiment: read `Shmem` and `Mlocked` from /proc/meminfo before and after NCCL init, default vs small-buffer env, one boot each.
8. **Make the kernel kill the engine, not the node.** `--oom-score-adj 1000` on engine containers (ds4 sets it on itself), a resident guard that kills its container without forking, raised `vm.min_free_kbytes` with lower dirty ratios. Applies to: every lane. Gain: failure mode changes from wedge to worker death; one 2x GB10 kit reports large-checkpoint loads went from flaky to 100% [Community-measured]. Cost: raising watermarks lowers reported MemAvailable by roughly 11-15 GiB for the same physical state (computed from the watermark formula, not measured) [Interpretation], so every floor must be re-derived. Risk: masking a real overrun. Smallest falsifying experiment: on a scratch node, a deliberate over-pin with and without the settings; record whether the node stays reachable.
9. **Reclaim the display scanout reservation as KV** (open PR #234). Applies to: headless nodes that can run `nvidia_drm modeset=1 fbdev=0`. Gain: head KV 13.7 -> 16.52 GiB [Community-measured]; about 1.75-2.03 GiB per rank. Cost: the region reads at about 69% of normal bandwidth; loses local display. Risk: unmerged, bare-metal prerequisite. Smallest falsifying experiment: one boot with the carve-out, same pin; compare pool and decode rate at a context that lands KV in the region. [Proposed] for the own lanes.
10. **Swap as a valve for cold host pages only.** Applies to: every node. Gain: KV reservation pushed 1.5-2.8 GiB of cold host pages to swap per rank on the GLM TP3 lane [Measured]; a host-only valve (model cgroups excluded) held 1.4 GiB / 956 MiB after a 1M activation [Measured]. It never creates room for pinned GPU memory (0 MiB swapped during 104 NV_ERR, with swappiness 0) [Measured]. Cost: disk; with a model cgroup that cannot swap, the host swapped out `sshd` in the own 2026-09-03 wedge [Measured]. Risk: UVM livelock if pages swapped out long ago are touched by a long prefill [Community-measured, one incident]. Smallest falsifying experiment: two boots, swappiness 60 vs 0 with the same swap, same 131K unique cold prompt; compare NV_ERR count and swap-in during the prompt.

## 6. Protocol

This is the memory protocol an agent runs before any change that moves memory: a KV size, a fraction or utilization, a chunk, a context length, a drafter setting, an allocator flag, a loader, NCCL buffers, or weights. It generalizes the incidents in §4 and §7. See also [Profiling protocol](14-profiling-protocol.md).

**Preconditions (fleet rules, all mandatory).**
- All index rules apply (see [the entry page](README.md)), in particular: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor measured after the longest qualified prefill, and traffic stopped below 4 GiB; a greedy logprob probe after every relaunch; discard the first request and warm every serving shape before timing; a unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection or configuration line read on every rank; at least 3 repetitions with a closing baseline (A/B/A); MemAvailable sampled every 1-2 s with zero NV_ERR_NO_MEMORY or Xid lines; no reboot or power cycle without per-node permission; correctness gates from [Quality and correctness gates](21-quality-and-correctness-gates.md) before any speed number. For this page: warm every serving shape before reading a warm floor.
- No memory overcommit. At least 8 GiB MemAvailable on every rank before a start. A warm floor of at least 5 GiB on every rank, measured after the multimodal warmup and after the longest qualified prefill, not at boot.
- One memory variable per boot. KV pin raises are at most 1.5 GiB per boot, and stop at the first boot that lands under 5 GiB warm or shows swap growth for model processes. Never spend freed memory in the same step: a change that frees memory and a change that uses it are two boots.
- Traffic stop: stop benchmark traffic when MemAvailable falls below 4 GiB on any rank. Preserve the engines; no automatic engine teardown.
- Clean window: no co-tenant GPU processes, no builds or JIT compiles running (cap `MAX_JOBS` if one must run), no other benchmark, the lane's owner has agreed to the downtime.
- Restart A/Bs with the image and recipe pull skipped, so both arms run identical bits.
- Never restart a serving gateway or front-end as part of the experiment. If the change needs one, stop and hand that step to the operator.
- Never `pkill -f` a pattern that also matches your own shell.
- Record the baseline count of `NV_ERR_NO_MEMORY` and Xid lines from `journalctl -k` on every rank. Use the journal, not `dmesg`, which rotates within about an hour under these errors.

**The change.** Exactly one variable. Size it with the lane's own numbers, never another operator's: absolute floors do not port between fleets (one operator saw 10.3 GiB after a full 1M request on a 4-node fleet and 1.1-2.4 GiB while serving on a 2-node pair, different workloads), and the same configuration gave different results on two fleets (own DS V4.1 head idled near 2.9 GiB where the upstream README reports about 6 GB while serving) [Community-measured], [Measured]. What does port is the delta a change produces. Sizing rules:
- Bytes per token per rank are model-specific: DeepSeek V4.1 MLA latent FP8 1,670.75 B/token plus a fixed 0.34 GiB SWA pool (README at 25379c22) [Community-measured]; GLM 5.3 EXL3 on the own TP2 lane about 0.72 GiB per 100K tokens [Measured]; Qwen3.8-Flash-Next full attention 12,288 B/token at FP8 plus about 54 MiB of linear state per sequence (config arithmetic, not measured) [Interpretation]. On a DeepSeek V4.1 EXL3 pair, +0.5 GiB of pool cost about 1 GiB of head margin at the end of a long prefill (chunk not stated; the 601K floor of 2.1 GiB was measured at chunk 1024) [Community-measured].
- Context does not buy pool: raising `max_model_len` grows the profiled activation peak, and lowering it did not free pool on the own GLM TP2 lane [Measured].
- Concurrency follows the pool, not `max_model_len`. One operator's untested arithmetic: c2 needs the sum of live contexts within the pool. A 599,840-token prompt used about 76% of a 785,676-token pool and could not stay cached for reuse [Community-measured].
- Chunk and context must agree; client context must match served context; client retries against a slow long prefill multiply the load (8 resends in the own 2026-09-16 wedge) [Historical diagnostic].

**Read the boot line** (all SGLang figures GiB):
- vLLM: `Available KV cache memory: X GiB`; with a pin, the "skipped memory profiling" message (then no margin exists); `GPU KV cache size: N tokens` is logical concurrency x length, not prefix capacity.
- SGLang: the `avail mem=` ladder (load begin, load end, pool end, after graphs); on DeepSeek-V4 the `DSV4 memory calculation` line (`available_bytes`, `full_token`); a warning if `--max-total-tokens` exceeds profiled capacity.
- ds4: `memory: KV ... + buffers ... + resident model ... = ... planned` and `using managed KV cache`.
- For SGLang, compute the slack yourself: (1 - f) x "Load weight begin" avail, and compare with "Load weight end" avail. If slack is not well below it, lowering f will starve KV.

**Record (packet fields).** Engine, version and pin; the one-line recipe diff; per-rank `/proc/meminfo` at pre-start (MemAvailable, MemFree, Cached, Shmem, Mlocked, SwapFree, CmaFree); the boot line(s) above; pool tokens; graph-capture size; warm available after the multimodal warmup; MemAvailable and MemFree sampled every 1-2 s per rank for the whole run, with each rank's minimum and when it happened; `journalctl -k` NV_ERR and Xid counts split into startup and serving; swap used delta; oom_kill count; workload (unique prompts, prefix cache flushed for cold runs); longest prefill length, TTFT and prefill rate; soak length; number of trials per arm.

**Pass gate.**
- Zero `NV_ERR_NO_MEMORY` during the gated workload. A pass with driver allocation errors is a fail. Startup-only bursts are recorded separately and never summarized as warning-free.
- Warm floor at least 5 GiB on every rank after the longest qualified prefill; no swap growth for model processes; no oom_kill.
- Liveness by progress counters (prompt plus generation tokens advancing while requests are open), not `/health` and not container status.
- If boot-to-boot variance matters to the decision (own pool noise about ±0.6 GiB between boots on one TP2 lane; 6.60 vs 4.1-4.2 GiB after KV on DS V4.1), repeat the boot before concluding.
- Record `Cached`, `MemFree` and whether page cache was dropped (`drop_caches`) before every launch, and compare the engine's KV-capacity boot line across two boots before attributing a capacity change to the variable; identical boots can differ in KV capacity.

**Rollback.** Revert the one changed line, boot, and confirm the floor is back to the recorded baseline. If a rank dies, remove every rank of that TP group before relaunching: a surviving rank keeps its allocations [Community-measured]. Capture container logs before teardown. A wedged node (ping answers, TCP 22 accepts, no usable SSH) needs a power cycle, and that needs the operator's explicit permission; before any reboot, check that the next-launch recipe on disk is not the one that wedged. Low-power stalls (tokens frozen, requests held, GPU power well below a healthy long prefill's draw) point to a livelock or NCCL hang rather than a memory overrun [Community-measured].

**Threshold set** [Proposed] (derived, not tested as a set): pre-start at least 8 GiB on every rank (agrees with the vLLM PR #49760 reserve and the ds4 reserve); warm floor at least 5 GiB after the longest qualified prefill; traffic stop below 4 GiB, engines preserved; single-node lanes keep a larger cushion (10-15 GiB or more; community single-node recipes run 10-30 GiB) because compile workers, desktop and host tools share the node; replace any percentage guideline with absolute per-fleet figures; add a MemFree gate near 2-3 GiB applied only while MemAvailable is below 10 GiB. Lane-specific guards above the fleet floor stay lane-specific.

## 7. Anti-patterns and known-bad

- [Measured] Lowering the SGLang static fraction "to free RAM" on a weight-dominated lane. At the own DS V4.1 inputs, 0.90 gives a KV budget of 7.41 - 10.89 < 0: the boot fails or the pool starves. The same wrong advice appears in generic vendor guidance (§2). The opposite overstatement, "0.95 is the only bootable value", is also wrong; at those inputs the floor is about 0.945 [Interpretation].
- [Measured] Pinning vLLM KV bytes to force a context length. Five launches at 900K (15 and 14 GiB) and 800K (12.5 GiB) died at the multimodal warmup from a kernel OOM with no Python traceback. Read the kernel log, not the engine log.
- [Measured] Skipping the multimodal warmup to survive boot. Max-size multimodal profiling must be skipped on this memory, but the read-only warmup is what proves vision fits; skipping it defers the OOM to the first image.
- [Measured] Two memory knobs in one boot. The indexer right-sizing and a +4.0 GiB pin raise, applied together with 4.4 GiB host free, took node-1 off the network until a power cycle; the model cgroup could not swap, so the host swapped out `sshd`. This produced the one-variable and never-spend-freed-memory rules.
- [Measured] Calling a run a pass with `NV_ERR_NO_MEMORY` in the log. A 131K retrieval "passed" with 104 driver errors on the DS V4.1 SGLang lane; the next ~200K real turn wedged all three nodes (the incident record is titled a head-wedge record, and whether only the head or all three nodes wedged is recorded differently across pages and unresolved).
- [Historical diagnostic] Trusting configured limits to bound a long prefill. In the 2026-09-16 wedge the pool was 25-28% full and every configured limit was honored; the uncapped per-rank prefill working set overran the last GiB or so. The settings matched the upstream TP3 profile exactly; lower host headroom is the leading explanation [Interpretation].
- [Measured] Lowering `max_model_len` to buy pool. On the own GLM TP2 lane the pool followed the KV bytes, not the context ceiling (907,024 vs 906,181 tokens).
- [Community-measured] Lowering MNBT to recover KV where a workspace is locked after warm-up. On a single-node DeepSeek-V4-Flash vLLM, MNBT 2048 profiled smaller and booted a larger pool, then crashed under real traffic: `AssertionError: Workspace is locked ... requires 1949.52 MB, current size is 1157.00 MB` (b12x MLA workspace, wide attend on a warm prefix). The maintainer added a README warning. (MiaAI-Lab/DeepSeek-v4-Flash-One-DGX-Spark issue #4)
- [Community-measured] Copying another fleet's pin, fraction or floor. Host baselines differ (desktop, page cache, driver, kernel), and absolute floors differ by several GiB for the same quantity (§6).
- [Community-measured] Treating `nvidia-smi`, `cudaMemGetInfo`, `docker --memory` or a `systemd-run` scope as a memory guard for GPU allocations (§3).
- [Measured] Trusting container status. A dead TP group showed both containers "Up" while a surviving rank held its memory.
- [Measured] Counting swap as GPU headroom. Swap never engaged during 104 driver errors or the three-node wedge on the DS V4.1 lane (with swappiness 0, which also suppresses swap-out).
- [Community-measured] `--enable-cumem-allocator` on GB10: about 84 GB of weights through `cuMemCreate`, driver exhaustion, both nodes frozen (vLLM #48242).
- [Community-measured] Switching to a direct-I/O loader to gain KV. It let a 7.5 GiB slab allocate on one kit, but ranks then died silently 60-90 s after load, even at the proven size; on another kit it cost about 5 GiB of available KV (tonyd2wild ladder; MiaAI-Lab GLM kit).
- [Community-measured] Treating `empty_cache()` as headroom by itself. It stops a reserve staircase, but MemAvailable rose only about 90 MiB per 6.68 GiB released, and after a server stop the nodes stayed near 38-40 GiB available until a reboot (bjk110 section 30).
- [Community-measured] Blaming the driver or kernel first. A "driver 580.178.04 OOM" was withdrawn by its poster: the cause was a systemd restart race during model load (forum 383859 post 8). A "kernel 7.0 regression" NV_ERR was CUDA-graph capture on a b12x MoE path (forum 383023 post 76). Another operator reported `kho=off` alone did not work for them and reverted to `cma=128M`, outcome not reported (post 46).
- [Community-measured] Long-prefill memory ladders with reused prompts or a cold JIT cache. The #36941 claim that prompts "above 40k kill the worker" was retracted: first-request JIT and radix-cache reuse contaminated it. Use unique prompts and flush the prefix cache.
- [Community-measured] Reading every long-prefill hang as memory. On 4x GB10 TP4+EP, repeated prompts above about 74-78K tokens (at mamba block 1600) kill a worker stream; a smaller mamba block moves the wall; prefix caching, MTP, graphs, `expandable_segments` and a `drop_caches` loop were eliminated (vLLM #54629, open). Some wedges are power-offs, not overruns (forum 363989).
- [Code-verified] Quoting vLLM's `GPU KV cache size: N tokens` as prefix-cache capacity. It is max concurrency x max_model_len summed over KV groups.
- [Community-measured] Running a FlashInfer or CUTLASS JIT build at default ninja parallelism on a serving node: 38 jobs passed 121 GB (Ornith README), and 5-8 GB per `nvcc` kernel is one operator's estimate without a protocol (forum 373676).

## 8. Open questions

- Does the `expandable_segments:True` NaN (every prefill above 64 query tokens) reproduce outside the one SGLang DeepSeek-V4 stack that reports it? Its evidence is an unpublished report, and 64 tokens is that stack's own dispatch boundary to FlashInfer's sparse-prefill path, so it is likely stack-specific [Interpretation]. The own lane runs the flag off because upstream said so; there is no own A/B either way. Settle with a greedy logit-sum check at 64 / 65 / 512 / 4000 tokens, flag on vs off, one boot each.
- How many bytes do NCCL connection buffers really pin on a loaded multi-node node? The 4.6 GiB -> 0.14 GiB figure has one source and its ~6 GB head gain is not isolated. Settle with `Shmem` and `Mlocked` before and after NCCL init, default vs small-buffer env, one boot each.
- Does page-cache state at load explain boot-to-boot KV variance (6.60 vs 4.19 / 4.07 GiB after KV on identical knobs)? Settle with `drop_caches` or `posix_fadvise(DONTNEED)` right before launch vs none, logging Cached, MemFree and the resulting KV line, three boots per arm.
- Do the DeepSeek-V4 low-ratio indexer constants (about 14 B x T x L; T x L below about 2.0e8) hold? They trace to the same unpublished report. Settle with a per-tensor peak trace (`torch.cuda.memory_stats`) across T in {512, 1024, 2048} and L in {64K, 128K, 256K}.
- Does cycling swap before start prevent UVM livelock, and which swap policy is safest? Swappiness 0 (UVM doc), 60 (one operator after an unproven incident), swap off, and keep-swap all have advocates; no controlled A/B exists. Also unreconciled: one recipe says the unit "ships with zero swap", while the own factory audit found a 16 GB swap image in use (OS image versions may differ). Settle with swappiness 0 vs 60, same swap, same 131K cold prompt, and a long-uptime run that touches old pages.
- Is there UVM livelock during builds specifically? Every build failure found is host exhaustion ending in the OOM killer or a freeze; no source ties builds to UVM livelock. Settle by sampling SM utilization and power during a deliberate over-parallel JIT on a scratch node.
- What are the speculative-decoding verify-buffer peaks on GB10? The only byte figure is the own drafter's padded reserve (about 3.3 GiB at MNBT 2048, about 7.4 GiB at 7168). Settle with `torch.cuda.memory_stats` around verify steps at k = 3 / 5 / 7. See [Speculative decoding](02-speculative-decoding.md).
- What do llama.cpp mainline and ExLlamaV3 standalone do under long prefill on GB10? No measurement found. Settle with a 32K / 131K / 262K cold ladder per engine with 1-s MemAvailable and MemFree sampling.
- What happens when a pool is actually full, not just logically sized? Every own and community test found used one request at 52-76% of the pool. Settle with concurrent unique long requests that sum to at least 95% of the pool, with the floor sampled.
- What headroom and chunk does NVIDIA recommend for long context? Playbooks issue #97 asks exactly this and has no vendor answer; the NVIDIA knowledge-base articles 5776 and 5728 cited by one community doc returned HTTP 403 on 2026-09-23.
- Why do startup-only `NV_ERR_NO_MEMORY` bursts appear (72 / 172, 109 / 170, 1-3 per rank on own lanes) with no serving failure? One maintainer describes them as the two large startup bursts while MemFree dips to about 1 GiB under page cache [Interpretation]. Settle by sampling MemFree at 100 ms through boot and correlating with journal timestamps.
- How much does the FlashInfer autotuner plus graph capture allocate outside SGLang's accounting? One recipe says 25-40 GB with no stated protocol. Settle by sampling MemAvailable across capture and autotune with each switched off in turn.
- Is the vLLM TP4 hang at about 74-78K tokens (vLLM #54629) a memory failure at all? Currently it looks like mamba or GDN state-cache indexing. Settle by the issue's own mamba-block sweep with MemAvailable sampled.
- Why did identical DS V4.1 TP3 settings survive upstream and wedge here? Desktop vs headless moved the floor only about 0.3 GB in one community report. Settle with a side-by-side boot line and a slabtop/smaps inventory of the head's host memory.
