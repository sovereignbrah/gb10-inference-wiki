# Profiling protocol: classify a bottleneck on a live GB10 lane

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 128 GB unified LPDDR5X, 273 GB/s nominal, which is a denominator and never an achieved figure), one to three nodes (node-1, node-2, node-3) on a direct-cabled ConnectX-7 RoCE triangle. Code is quoted at these pins, all fetched 2026-09-23: vLLM `34b069080d9f`, SGLang `2909f84e3b2f`, llama.cpp `6e60f35608ec`, ExLlamaV3 `6b84a21b6f1e`, antirez/ds4 `0aaea5a238fb`, Triton `2cfa16702a3a`. NVIDIA tool statements come from the current online documentation fetched 2026-09-23 (Nsight Systems User Guide, Nsight Compute CLI and Profiling Guide v2026.3.1, CUDA Binary Utilities 13.4); they are marked "[Code-verified] (vendor doc)" and none of them was validated on a GB10 unless a row says so. Staff answers on the NVIDIA forum are vendor statements, not measurements.

State of the evidence in one line: as of 2026-09-23 no Nsight Systems or Nsight Compute capture has been taken on the own fleet; the only own GPU profile is one all-rank torch-profiler prefill capture, and everything else is component timing, build logs, sanitizer gates and end-to-end benchmarks. [Measured, absence established by a search of all retained evidence]

## 1. What it is

Profiling is how you find out where the time goes inside one step of a running model, so that the next change goes after the real wall and not a guessed one. A "step" is either one prefill chunk (a slice of the prompt being read) or one decode step (one round of producing the next token or tokens). On a GB10 a slow step usually has one of five causes: the chip is waiting on memory (bandwidth-bound), the math units are full (compute-bound), too few threads are running to hide delays (latency-bound), the host cannot hand out small pieces of work fast enough (launch-bound), or one node is waiting for another over the cable (communication-bound, or simply waiting on a slower rank). Three tools see different parts of the picture: a timeline tracer (Nsight Systems) shows what ran when on every node; a per-kernel counter tool (Nsight Compute) shows why one kernel is slow; and the engines' built-in PyTorch profiler ties GPU work back to model code. Every one of them slows the thing it measures, sometimes a lot (one own capture added about half again to the time to first token), and some of them change the behaviour they are measuring, so a profile can tell you where to look but never whether a fix worked. That decision always comes from an unprofiled before-after-before comparison run under strict rules: fresh prompts that cannot hit the prompt cache, pinned output length, warm-up discarded, one change per engine restart, and a clean window with no other traffic. This page is the procedure an agent follows, the metrics that separate the five classes on this chip, the places where the GB10 differs from a datacenter GPU, and the table that routes each finding to the page that owns the fix. See also [SM121 hardware facts](17-sm121-hardware-facts.md), [Clocks, thermal, and power](13-clocks-thermal-power.md) and [Quality and correctness gates](21-quality-and-correctness-gates.md).

## 2. How each engine does it

### vLLM

Mechanism. One interface selects the profiler: `--profiler-config` with `profiler` in {`torch`, `cuda`, `proton`} (vllm/config/profiler.py:16). The older environment-variable path, including `VLLM_TORCH_PROFILER_DIR`, `VLLM_TORCH_CUDA_PROFILE`, `VLLM_PROFILER_DELAY_ITERS` and `VLLM_PROFILER_MAX_ITERS` (eleven variables in all), was removed by PR 33536 (merged 2026-02-03, `ef248ff7`), which is an ancestor of the pin. Any recipe that still sets `VLLM_TORCH_PROFILER_DIR` does nothing on a current build. [Code-verified]

- Windows. `POST /start_profile` and `/stop_profile`, or `vllm bench serve --profile`. `delay_iterations` and `max_iterations` count worker steps after start, in the base `WorkerProfiler`, so they bound the `cuda` profiler as well as torch (vllm/profiler/wrapper.py:29-160). Torch also has a schedule: `wait_iterations`, `warmup_iterations`, `active_iterations` (default 5) (config/profiler.py:43-158). [Code-verified] Because tensor-parallel ranks step in lockstep, a step-bounded window captures the same engine steps on every rank. [Interpretation]
- Torch defaults at the pin: `torch_profiler_with_stack=True`; shapes, memory and FLOPs off; gzip on; CUDA-time table dump on; activities `["CPU","CUDA"]` on NVIDIA. `["CUDA"]` alone "omits CPU annotations and the AsyncLLM CPU trace to reduce profiling overhead and trace size" (config/profiler.py:43-158; docs/contributing/profiling.md:17-28). [Code-verified]
- Frontend trace. With `profiler=torch`, `ignore_frontend=False` and CPU activity, the API process writes its own CPU-only trace named `<host>_<pid>.async_llm` (v1/engine/async_llm.py:211-229). It never records CUDA, which explains an own trace file with zero kernel events. [Code-verified]
- Overhead warning in code: torch with `delay_iterations` / `max_iterations` while `ignore_frontend=False` "may result in high overhead" because the frontend profiler "does not track iterations and will capture the entire range" (config/profiler.py:122-127, 191-201). [Code-verified]
- Frontend-profiler bug. In builds before PR 55237 (merged 2026-09-07, `c3ec0d29`), `ignore_frontend=True` (and every other case where the frontend profiler is not built) left `AsyncLLM.profiler` unset, so `/start_profile` raised. The fix is the one line `self.profiler = profiler`. [Code-verified] An own lane build predates it (§4, §7).
- `cuda` kind for Nsight Systems: `torch.cuda.profiler.start()/stop()` plus `torch.cuda.nvtx.range` annotations (profiler/wrapper.py:607-625). The documented recipe is `nsys profile --trace-fork-before-exec=true --cuda-graph-trace=node --capture-range=cudaProfilerApi --capture-range-end repeat <vllm serve ...> --profiler-config.profiler cuda` (docs/contributing/profiling.md:219-226). The doc says it is "advisable" (not required) to set `VLLM_WORKER_MULTIPROC_METHOD=spawn` under nsys (line 190), and quotes a flush of about 10 minutes for about 100 requests of a 70B model on an H100 (line 41; not a GB10 figure). [Code-verified]
- NVTX. `VLLM_NVTX_SCOPES_FOR_PROFILING=1` routes internal profiling scopes to NVTX; `VLLM_CUSTOM_SCOPES_FOR_PROFILING` takes precedence (v1/utils.py:784-793). `enable_layerwise_nvtx_tracing` adds per-module ranges with shapes but "doesn't work with CUDA graphs enabled" (config/observability.py:72-75). Stage-level NVTX (`prefill_batch`, `decode_batch`, `sampling`) is PR 37095, open, not merged (head `cfe25cff`). [Code-verified]
- Under CUDA graphs. A replayed-graph torch trace has GPU kernels but "no CPU-side call stack and no input shapes" (RFC issue 45069, open). The pin ships `capture_torch_profiler` (a trace of graph capture, rank 0 only) and `detailed_trace_annotation` (per-step `sq`, `sk`, `sqsq`, `sqsk` aggregates) (config/profiler.py:111-120). Proton with `proton_graph_attribution` (Triton 3.7 or newer, `proton_data: "tree"`) attributes replayed kernels; Proton pcsampling and Chrome traces need `--enforce-eager` (docs lines 91-160). No cross-node merge is documented. [Code-verified]
- Startup memory profiler (the other thing vLLM calls "profiling"). On a GB10, `profile_run` at `gpu_memory_utilization=0.70` drove available memory to about 7 GiB and un-watched runs hung until a power cycle, while the same model and settings served fine on a 96 GB discrete card (vLLM issue 46307, open). [Community-measured] `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` is the community fix for an over-reserving graph estimate (§4). See [Memory management on a unified-memory GB10](11-memory-on-unified-memory.md).
- Benchmark client. `vllm bench serve` has `--ignore-eos`, `--num-warmups` (default 0), `--percentile-metrics` and `--metric-percentiles` (default only `99`) (vllm/benchmarks/serve.py:1752-1836). Per-request `cache_salt` is "injected into the hash of the first block, ensuring that only requests with the same salt can reuse cached KV blocks" (docs/design/prefix_caching.md:86-100). `POST /reset_prefix_cache` (dev router) fails while blocks are held. [Code-verified]
- Defaults on CC 12.1. The `cuda` platform accepts all three profiler kinds (profiler/wrapper.py:632-722). No SM121-specific profiling path or default was found at the pin. [Code-verified]

### SGLang

- `/start_profile` fields (python/sglang/srt/managers/scheduler_components/profiler_manager.py:86-156, 233-276): `output_dir` (else `SGLANG_TORCH_PROFILER_DIR`, else `/tmp`), `num_steps`, `start_step`, `activities` (default `["CPU","GPU"]`; also `MEM`, `CUDA_PROFILER`, `RPD`), `merge_profiles` (default false), `detailed_annotations` (default false), `with_stack` (default true), `record_shapes` (default false). `CUDA_PROFILER` calls `cudaProfilerStart()` only when `gpu_id == base_gpu_id` (lines 274-276); with one GPU per node on GB10 that is every rank. Detailed annotations emit per-step `sq`, `sqsq`, `sqsk`, `sk` and are "identical in eager and CUDA graph modes". [Code-verified]
- Multi-node. Automatic merge needs shared storage for `output_dir`: "If there is no shared storage accessible across nodes, automatic merging ... is not supported". Per-rank files are `{profile_id}-TP-{tp}-DP-{dp}-PP-{pp}-EP-{ep}.trace.json.gz` (docs/docs/developer_guide/benchmark_and_profiling.mdx). A collaborator adds: send the request only to the leading node of each instance, capture about 5 steps for prefill and 25 for decode, and expect stop to stick "for seconds or even minutes" (issue 9638). [Code-verified]
- Graph visibility. `--enable-layerwise-nvtx-marker`: "NVTX markers are not emitted for kernel launches captured by CUDA graphs. Use `--disable-cuda-graph`". Python source under kernels also needs graphs off. `--enable-profile-cuda-graph` profiles only decode-graph capture (Chrome traces through `SGLANG_ENABLE_CUDA_GRAPH_CAPTURE_TRACE=1` or `SGLANG_GRAPH_BATCH_CAPTURE=1`). The nsys option `--python-backtrace=cuda` "can cause inaccurately long kernel runtimes for CUDA event based timing" (same doc). [Code-verified]
- Reading method. The in-repo analysis skill prescribes two traces: a "mapping" trace with graphs off or lower fusion to recover kernel to Python scope, and a "formal" trace with production settings for shares and overlap ("Do not call the mapping pass a fast profile"); warm 10 steps, capture 5; prefer one-rank traces over merged ones; and an off-by-one: `forward_ct` increments before the stop check, so a `num_steps=1` prefill capture "can stop just before the actual prefill forward" (.claude/skills/llm-torch-profiler-analysis/SKILL.md:128-136, 490-518; validated on H100, not GB10). Its heuristics define "hidden" kernels and warn "A trace shows what overlapped, not what could legally overlap" (references/heuristics.md:116, 119). [Code-verified]
- nsys post-processing. `gputrc2graph.py` takes the unprofiled elapsed time of the same run, so non-GPU time is computed against the unprofiled wall clock (examples/profiler/nsys_profile_tools/README.md). [Code-verified] That is the right denominator for any share table. [Interpretation]
- Benchmark client. `bench_one_batch_server` forces EOS off by default (`--disable-ignore-eos` for real prompts) and warns a single batch "is never in a steady-state"; `bench_serving` needs `num-prompts` at least 5x `max-concurrency` (benchmark_and_profiling.mdx:49-62). Per-request `cache_salt` exists: `GenerateReqInput.cache_salt`, "Cache namespace used to isolate otherwise-identical prefixes" (srt/managers/io_struct.py:352-353), carried in the OpenAI protocol (srt/entrypoints/openai/protocol.py:403, 962, 1674), and the radix cache refuses to match across salts (srt/mem_cache/radix_cache.py:62-77, 172-175). `flush_cache` clears the tree. [Code-verified]
- Defaults on CC 12.1. No SM121-specific profiling path was found at the pin. All SGLang profiling evidence on GB10 is community-measured (§4). FlashInfer autotune re-picks kernels per boot unless `--disable-flashinfer-autotune` is set (§4). [Community-measured]

### llama.cpp and forks

- llama.cpp @ 6e60f35: no built-in NVTX, CUPTI or `cudaProfilerStart` hooks were found; profile with external nsys or ncu. CUDA graphs are on for Volta and newer unless `GGML_CUDA_DISABLE_GRAPHS` is set (ggml/src/ggml-cuda/common.cuh:1298; ggml/src/ggml-cuda/ggml-cuda.cu:4409-4413). Other environment switches change the kernel path and belong in every A/B record: `GGML_CUDA_ENABLE_UNIFIED_MEMORY`, `GGML_CUDA_DISABLE_FUSION`, `GGML_CUDA_GRAPH_OPT`, `GGML_CUDA_NO_PINNED`, `GGML_CUDA_P2P`, `GGML_CUDA_ALLREDUCE` (getenv calls in ggml-cuda.cu). [Code-verified]
- Measurement. `llama-bench` repeats each test `-r 5` by default with warm-up on (`--no-warmup` to disable), reports mean and standard deviation, and writes per-repetition `samples_ns` / `samples_ts` in JSON (tools/llama-bench/README.md). `llama-server` caches prompts by default (`cache_prompt: true`; send `false` for a cold prompt) and returns `timings` with `cache_n`, `prompt_ms`, `predicted_per_second` (tools/server/README.md). [Code-verified] The community `llama-benchy` pins output with `--exact-tg` (`min_tokens` plus `ignore_eos`), 3 runs, 1 discarded warm-up (eugr/llama-benchy README @ e9be3445). [Code-verified]
- antirez/ds4 @ 0aaea5a: no nsys or NVTX hooks. Attribution comes from timing environment variables that synchronize (`DS4_QWEN4_TIMING=2`, `DS4_QWEN4_MOE_PROFILE=1`, and `DS4_DSPARK_STATS=1` per PR 772): "use uninstrumented alternating runs for throughput claims" (speed-bench/README.md). docs/PERFORMANCE.md: "repeat in alternating order: one favorable run is not a speed result". The documented A/B harnesses (ABBA/BAAB blocks, both variants warmed, abort unless full-vocabulary logits are bit-identical, only dispatch-time environment variables comparable because one engine stays alive) are the Apple Metal decode and prefill benches and the session-concurrency bench; the discipline transfers to GB10, the tools as documented do not. `serve_concurrency_bench.py` uses fresh nonces, `--ignore-eos` and `--shared-prefix` for cache tests. The QA procedure asks for CUDA 12.8+ and `sm_121` builds and has no resource-usage make target (QA_BEFORE_RELEASES.md). [Code-verified] One nsys capture on a DGX Spark changed a ds4 design decision (PR 772, §4). [Community-measured]
- Entrpi/ds4 @ b0a147a7 and Entrpi/ds4-on-spark @ 99fb7b17 carry `ds4_bench.c`, speed-bench and a `bench/bw_bench.cu` bandwidth probe (file listing only; contents not audited). Anemll/dspark-vllm-gx10 @ 081fda97 is a vLLM image with prefill benchmark scripts; it profiles through vLLM's mechanism. No fork-specific profiling procedure was found. [Code-verified]
- Defaults on CC 12.1. CUDA graphs are on (12.1 is above the Volta gate), and no profiling hook or SM121-specific profiling default exists in llama.cpp or the forks listed. [Code-verified]
- Resource reports. These engines compile their own CUDA with nvcc, so `-Xptxas -v` or `--resource-usage` in the build flags gives the per-kernel register, stack and spill report; no pinned make target for it was found. [Interpretation]

### ExLlamaV3 in vLLM

- ExLlamaV3 @ 6b84a21 has no profiler integration. `eval/perf.py` times prefill and generation with warm-up passes and `torch.cuda.synchronize()`; `exllamav3/util/profile_opt.py` only makes `@profile` a no-op unless line-profiler injects it (CPU). [Code-verified]
- Build flags that matter for profiling: the extension builds with `-lineinfo -O3 --use_fast_math` (exllamav3/ext.py:92), so Nsight Compute source view works; `--ptxas-options=-v` is added only when the module-level `verbose`, hard-coded `False`, is flipped (ext.py:11, 121-122). [Code-verified]
- Architecture clamp. exllamav3/util/arch_list.py:10-11 returns immediately if `TORCH_CUDA_ARCH_LIST` is set; otherwise it clamps the device capability to the highest SM in the torch wheel and appends `+PTX`. If the variable is unset and the wheel tops out at sm_120, the JIT build emits sm_120 SASS plus PTX, not sm_121 SASS. [Code-verified] Defaults on CC 12.1: no ptxas report, and an arch list of the lower of 12.1 and the torch wheel's highest SM, plus PTX, unless `TORCH_CUDA_ARCH_LIST` is set. Whether a given lane image hits the clamp is unverified (§8).
- Inside vLLM, EXL3 is profiled with vLLM's `--profiler-config` (own 2026-09-16 capture) and with component harnesses: CUDA-graph replay, CUDA events and compute-sanitizer (§4). A community two-node EXL3 capture used delay 2 / max 3 engine steps (§4). Nothing EXL3-specific in the profiler path was found; the vLLM items above apply unchanged. [Measured] for the own capture; [Code-verified] for the rest.
- Triton kernels on the EXL3 path (KDA/GDN) expose `n_regs` and `n_spills` on the compiled kernel after load (python/triton/compiler/compiler.py:482-483 @ 2cfa167, with a code comment noting they should come from ptxas); `TRITON_CACHE_DIR`, `TRITON_KERNEL_DUMP` and `TRITON_DUMP_DIR` keep cubins and IR for cuobjdump (python/triton/knobs.py:346-359). [Code-verified]

## 3. What is different on GB10 / SM121

Tool support and permissions
- [Community-measured] Nsight Systems works on DGX Spark for LLM inference but Unified Memory trace is rejected ("not supported by the current driver version or configuration"), unchanged by the UM page-fault flags; NVIDIA staff: "UVM profiling is not supported on Spark but is currently being worked on" (forum 357848; driver 580.95.05, CUDA 13.1, Nsight Systems 2026.1.1). The same page-fault collection costs "up to 70%" elsewhere per the User Guide. [Code-verified] (vendor doc)
- [Community-measured] Inside a container, nsys produced CPU and OS rows only ("No CUDA events collected") until the container had `SYS_PTRACE`; `nsys status --environment` showed `SYS_PTRACE: Fail`. The working setup added `cap_add: [SYS_PTRACE]`, `ipc: host`, `memlock -1`, and moved from a pinned nsys 2024.2.3 to the current package (forum 371190, poster nvidia3453). NVIDIA's container section names only the CPU-sampling needs (`--privileged=true`, `--cap-add=SYS_ADMIN` or a seccomp profile allowing `perf_event_open`) and recommends the CLI inside the container. [Code-verified] (vendor doc)
- [Community-measured] Host nsys 2025.3.2 on a DGX Spark produced a CUDA HW row for a vecAdd with `nsys profile --trace=cuda --sample=none --cpuctxsw=none` (note.com, incolorcat). An earlier empty-GPU-lane report with a wider trace list was acknowledged by NVIDIA and not resolved in-thread (forum 352250). Remote GUI profiling over SSH needs passwordless sudo on the node (forum 376266, unanswered); CLI capture on the node avoids it. [Interpretation]
- [Community-measured] Nsight Compute runs on DGX Spark: stock ncu 2025.3.1 ran `--set basic` on a vecAdd in 9 replay passes per launch, and needed sudo until `options nvidia NVreg_RestrictProfilingToAdminUsers=0` plus a reboot (then `RmProfilingAdminOnly: 0`) (note.com, incolorcat). That reboot needs explicit operator permission on a fleet node (§6). No posted ncu report of any vLLM, SGLang, llama.cpp or ExLlamaV3 kernel on GB10 was found.
- [Community-measured] DCGM profiling is not available: NVIDIA staff, "Since the Spark is not a datacenter, there are no plans to support DCGM on Spark" (forum 351926). Vendor statement.
- [Community-measured] A CUPTI activity-kind sweep on one GB10 (CUDA 13.0, driver 580.142) failed three kinds: `UNIFIED_MEMORY_COUNTER` (`NOT_READY`), `CONCURRENT_KERNEL` (`NOT_COMPATIBLE`), `INSTRUCTION_EXECUTION` (`LEGACY_PROFILER_NOT_SUPPORTED`); a second unit running the derived collector skipped the same three (forum 367851; parallelArchitect/cupti-activity-collector @ b21fa816). [Interpretation] `CONCURRENT_KERNEL` works when it is the kernel kind enabled: torch.profiler's backend enables it (pytorch/kineto @ fcda4416, libkineto/src/CuptiActivityApi.cpp:134) and own torch traces on GB10 carry kernel events; the sweep's error most likely follows from enabling `KERNEL` first. The current CUPTI docs say `KERNEL` serializes kernels and `CONCURRENT_KERNEL` does not; they do not state an exclusivity rule.
- [Community-measured] In-kernel `%clock64` timing read valid on CUDA 13.0, overflowed on 13.1 and returned 0 on 13.2 with driver 580.142 (forum 367851, one tester, three toolkits; the PTX cause is the tool author's reading). This concerns in-kernel cycle counters, not CUDA events or nsys timestamps. Any cycle-count instrumentation should record the toolkit and cross-check with CUDA events. [Interpretation]
- [Code-verified] (vendor doc) From Blackwell on, nsys uses CUDA hardware trace by default ("usually lower overhead ... especially for workloads that launch many short kernels"), falls back to software trace when it cannot collect it, and records the method on the report's diagnostics page; `--trace=cuda-sw` forces software trace. Whether hardware trace engages on SM121 was not found in any GB10 post (§8).
- [Code-verified] (vendor doc) The Nsight Systems guide names GB10 ("for example, NVIDIA DGX Spark") as supported for `--cpu-metrics` and ships a Grace / DGX Spark CPU top-down script. This is the only GB10-specific statement found in that guide.

Chip naming and metrics
- [Code-verified] (vendor doc) In NVIDIA tool tables "GB10x" means the GB100 datacenter family, not DGX Spark's GB10: the ncu 2025.3.1 support table lists GB10x, GB11x, GB20x; the `gb10x` GPU-metrics config declares `chips: [GB100]` (Hugging Face CUDA 12.8 mirror @ 9b8e89d7); the ncu known issue about `--clock-control` names "GB10b (Thor)", a different part. `ncu --list-chips` (2025.3.1, forum 348711) lists gb10b and gb20b among others. [Interpretation] DGX Spark probably reports a GB20x-family identifier (ncu 2026.3 Update 1 "added limited support for C2C metrics for GB20B and GB20C"); `ncu --query-metrics --devices 0` on a node settles it (§8).
- [Community-measured] Pipe metrics on consumer Blackwell, from an NVIDIA engineer's forum answer (vendor statement): the `tc` pipe (`sm__pipe_tc_cycles_active`) counts UTCMMA work on SM10x "and future chips capable of executing UTCMMA"; the `tensor` pipe (`sm__pipe_tensor_cycles_active`) is the warp-level MMA pipe, "SM 7.0 - 12.0"; SM12x has an SM-level FP64 pipe and a new ALU pipe sharing fmaheavy dispatch; prefer `sm[sp]__pipe_{pipe}_cycles_active` over `inst_executed_pipe_*` (forums 345730, 355164). [Interpretation] On SM121 a zero `tc` pipe does not mean idle tensor cores; read `tensor`.
- [Community-measured] SM12x has no tcgen05, TMEM or wgmma: ptxas rejects `wgmma.fence` for sm_120 (Backend.AI, "Is DGX Spark actually a Blackwell", 2026-02) and `tcgen05.alloc` for sm_120, and RTX 5090 SASS shows HMMA/IMMA (fengwang/ncu-report-skill-rtx-5090 @ d6f15d2d). Both are sm_120, not sm_121. [Interpretation] A SASS audit on SM121 should expect warp-level MMA (HMMA/IMMA/QMMA class). Kernel names are not proof of the architecture: the one posted GB10 serving profile saw `sm120` and `cutlass_80_wmma_*` names on sm_121 and could not tell SASS from PTX fallback (forum 374382); `cuobjdump -lelf` answers that.
- [Community-measured] NVML does not expose the GB10 memory clock: a bandwidth probe prints "Peak BW not reported (memory clock N/A on this platform)" and `cudaDeviceGetAttribute` returns 0 (forum 367851). [Interpretation] What peak ncu uses for `dram__*.pct_of_peak_*` on LPDDR5X GB10 is unknown; quote DRAM bytes per second against a measured ceiling, never a percent of peak (§7, §8).
- [Community-measured] Achieved-bandwidth ceilings disagree by method and none was measured on own nodes: 161.31 GB/s GPU read (`ld.global.cg`, 4 GB buffer, 2 warm-up + 5 runs, CUDA 13.0, driver 580.142) with a vLLM process resident but idle, 90.49 GB/s during inference (-44%), and a second tester at 165.68 GB/s (forum 367851); 216-235 GB/s p50 for a decode-shaped bf16 GEMV (a weight-bytes-only rate) and 220-234 GB/s device copy on eight clock-locked nodes, driver 580.173.02 (tonyd2wild issue 1). [Interpretation] The GEMV figure is the best-evidenced ceiling proxy.

Clocks
- [Code-verified] (vendor doc) ncu locks SM clocks by default and flushes caches between replay passes. The default `--clock-control` is `base` in the 2025.3.1 CLI docs and `boost` in the 2026.3.1 docs, so the behaviour depends on the ncu build installed. `--clock-control` is documented as unsupported on aarch64 SBSA only for GA10b (Orin) and GB10b (Thor); DGX Spark is not named, and nobody has reported trying it on a Spark.
- [Community-measured] `nvidia-smi -lgc 0,2200` takes effect on driver 580.173.02 even though `applications_clocks_setting` reads "Not Active": on one node, locked vs unlocked, SM clock 2,190 vs about 2,490 MHz median (2,554 max) (im0xMagnus, in tonyd2wild issue 1). Own locks were verified the same way, by median graphics clock under load (§4). [Measured] [Interpretation] The only evidenced clock-control path for profiling on GB10 is an external `nvidia-smi` lock plus `ncu --clock-control none`.
- [Community-measured] Thermal throttling "always overrides" any tool setting (ncu Profiling Guide). A GB10 "hidden slow state" at a constant reported 2.16-2.19 GHz read GEMV 66-80 vs 224-233 GB/s with 7-32 s dwell; it was not seen on eight newer-firmware nodes (0 slow seconds in about 540 s) or after a power cycle. A separate latched-low state (721 MHz, visible in `nvidia-smi`) is not cleared by a reboot; removing AC power 30-60 s usually clears a latch, but one 721 MHz unit did not clear after 8 h unplugged (forum 376039; see [Clocks, thermal, power](13-clocks-thermal-power.md) §7). A clock lock therefore does not guarantee a stable denominator; read clocks and power beside every capture.

Unified memory and co-residency
- [Code-verified] (vendor doc) ncu kernel replay saves all device memory the kernel can reach on the first pass and restores the written subset before later passes, falling back to host memory; single-pass metric sets skip the save and restore. [Interpretation] On a unified-memory node already near the 5 GiB warm floor (traffic stops at 4 GiB), that save area competes with the serving pool and the operating system.
- [Community-measured] A second CUDA context cannot be created on a node while its serving rank is up (`cudaMemGetInfo` fails); analyse traces on another node (MiaAI-Lab DeepSeek-V4.1-Flash three-node README @ 68b34cf). Neighbouring containers made one rank 5-8% slower on identical GEMMs (same source). [Interpretation] Nsight Compute belongs on a component harness or a dedicated profiling boot, never beside serving.
- [Code-verified] (vendor doc) ncu graph profiling of device-launched graphs and conditional nodes needs driver 590+; nodes that launch device graphs, 580+. The fleet driver is in the 580 series.

CUDA graphs and multi-node
- [Community-measured] Graphs matter too much on SM121 to profile eager and call it the lane: eager vs graphs about 26 vs 59 tok/s (Conselara note, vLLM 0.19.0, two DGX Sparks, model and batch not given) and about 42 vs 66-67 tok/s (Hugging Face nologik/vllm-dgx-spark README @ 82d28eb3, Nemotron-3-Nano NVFP4, protocol not given); graphs about 2x at low concurrency (luisefigueroa/pulsar-gb10-vllm-stack @ 8d5d8fbe). Protocols are partial; read these as a range, not a figure.
- [Community-measured] Cross-node graphs are not uniformly stable: cross-node TP=2 with graphs on the official vLLM image needs `--enforce-eager` (pulsar); an SGLang cluster script attributes `CUDART error: invalid device context` to FlashInfer AllReduce Fusion using CUDA IPC across nodes, fixes it with `--enable-dp-attention`, and disables graphs only when TP across nodes triggers IPC-incompatible kernels (mark-ramsey-ri/sglang-dgx-spark @ b58fe777); one operator reports full graphs with FlashInfer fine on sm_121 and piecewise graphs crashing (forum 373677).
- [Community-measured] On two DGX Sparks over ConnectX-7, an SGLang decode-graph hang (both ranks stuck in `cudaGraphLaunch`) was delayed or hidden by `CUDA_LAUNCH_BLOCKING=1` and by Nsight Systems profiling (SGLang issue 29548; not reproduced on 2x H200 at a newer main). [Interpretation] A clean profile does not prove a graph-mode lane is healthy.

## 5. Levers, ranked

Here a lever is a measurement tool or discipline; its "gain" is how much decision quality it buys per unit of lane time and risk. Ranking puts cheap, non-perturbing, well-evidenced tools first.

1. **Unprofiled A/B/A with a closing baseline as the only decider** — applies to: every engine x every model family x every topology. Gain: decisive; own and community evidence both show profile-driven fixes losing or vanishing end to end (own cache 10-40x local, +0.4 / +0.5 / -2.1% end to end; ds4 probe -98% local, +2.1-2.2% end to end; community row tiling and temp rows lost 13-61%; a hidden n=1 prefill win reversed at n=3) [Measured] [Community-measured]. Cost: one boot per arm plus a closing baseline. Risk: none beyond lane time. Smallest falsifying experiment: find one profile-suggested change whose sign flips between the profiled estimate and an A/B/A; the existing record already contains three.
2. **Engine-native counters and zero-overhead log lines first** — applies to: all engines (vLLM `/metrics` and usage, llama-server `timings`, ds4 stats, SGLang logs) x all families x all topologies. Gain: unmeasured on this fleet; the planned per-step tuple (proposed, verified, accepted, rows, graph bucket, kernel path, step ms), per-step scheduled tokens, and a device-side routed-row histogram would answer questions no profiler window can (acceptance vs depth, routing concentration) [Proposed]. Cost: small patches, one boot. Risk: a log line that synchronizes the host is not zero-overhead. Falsify: add the lines, run A/B/A, and check step time moves less than the A0-to-A1 drift.
3. **Unprofiled component timing per rank (CUDA events, CUDA-graph replay)** — applies to: any kernel or host region x any family x TP lanes especially. Gain: precise and cheap; it overturned a trace-level rank imbalance (35.90 / 35.65 / 36.11 ms) and exposed a ceil(rows/16) step function and a 0.107 ms host-path gap [Measured]. Cost: a harness per region; idle GPU. Risk: a decision rule finer than inter-rank noise (up to 15% at 25 samples) [Measured]. Falsify: re-measure the threshold rows with identical locked clocks and at least 200 samples on every rank; if p10-p90 envelopes still overlap, the rule is noise.
4. **Clock sensitivity as a free classifier** — applies to: all engines x all families x all topologies. Gain: cheap separation of compute-bound from memory- or wait-bound phases: prefill slowed -3.0 / -4.9 / -9.1% at 2200 / 2100 / 1900 MHz while C1 decode means were 5-6% lower, inside rep spread (own TP3, n=5); community controlled runs ±2% [Measured]; GEMV unchanged and matmul -10% under a 2200 lock on one node [Community-measured]. Cost: one lock per arm, no restart. Risk: first request after a new lock reads low; the two own decode results (TP2 −6.8%, n=3; TP3 means −5.8%, n=5) are the same size and neither settles it. Falsify: a decode-only 10-rep stock vs capped A/B/A; decode moving beyond the A0-A1 drift would make decode clock-sensitive on that lane. See [Clocks, thermal, power](13-clocks-thermal-power.md) §5 lever 1.
5. **Nsight Systems, relaunched under the tool with an engine-driven capture range** — applies to: vLLM (`cuda` profiler kind) and SGLang (`CUDA_PROFILER` activity) x all families x one node or all ranks; llama.cpp and ds4 with `--delay/--duration`. Gain: the only tool that shows every kernel with hardware timestamps, graph nodes, host API gaps and NCCL phases; one GB10 nsys capture found a blocking device-to-host copy that a code read had missed [Community-measured]. No own capture exists. Cost: an engine restart into and out of a profiling boot; overhead on GB10 unmeasured (§8); `--cuda-graph-trace=node` (the engines' recommendation) "may cause significant runtime overhead" vs the default `graph` [Code-verified] (vendor doc). Risk: attach to a running engine is not supported (§7); the tool can hide a graph-mode hang (issue 29548). Falsify: capture one fixed request under `graph` and `node` granularity and unprofiled, 5 reps each; if step-time shares differ by more than the overhead, the capture is not usable for shares.
6. **Torch profiler through the engine (vLLM `torch`, SGLang `/start_profile`)** — applies to: vLLM and SGLang x all families x all ranks. Gain: ties kernels to Python scope and ranks shares; own capture ranked categories across three ranks [Measured]. Cost: large overhead on CPU-heavy prefill (+51% TTFT own; 324 vs 893 tok/s community with debug syncs also on); trace flush can take minutes. Risk: frontend-profiler bug in older vLLM builds; eager mapping traces are not the production schedule. Falsify: re-run the own capture with activities `["CUDA"]` and `ignore_frontend=true` on a build that has PR 55237; if TTFT overhead stays near +51%, the frontend profiler was not the cost.
7. **Nsight Compute on a component harness, off traffic** — applies to: any single kernel x any family x one GPU; NCCL kernels only with `--communicator tcp --lockstep-kernel-launch` across all ranks. Gain: the only source of DRAM bytes, L2 hit, local-memory (spill) traffic, occupancy, eligible warps and stall reasons; nothing measured on a GB10 serving kernel yet [Proposed]; vecAdd works [Community-measured]. Cost: a harness, a profiler permission change that needs a reboot (operator permission), replay passes. Risk: replay save area on unified memory; clock and cache behaviour differ from serving (ncu durations run front-end semaphore to semaphore and read longer than nsys). Falsify: run one component kernel under `--clock-control none` and default; if `gpc__cycles_elapsed.avg.per_second` or duration differs beyond sample spread, the external lock is being overridden.
8. **SASS and resource audit** — applies to: any compiled extension x any family. Gain: static proof of spills and residency cliffs: own ptxas 63 registers, 0 spills, two blocks per SM [Measured]; community SASS audit fast 127 regs / 16 B frame / 6 STL / 0 LDL vs stock 128 / 88 B / 37 STL / 39 LDL [Community-measured, as recorded in the 2026-09-20 GLM 5.3 Flash TP3 frontier dossier v2]. Cost: minutes, no GPU. Risk: `ptxas -v` describes a rebuild, not the deployed binary; the deployed binary may carry sm_120 SASS or PTX (ExLlamaV3 clamp). Falsify: `cuobjdump -lelf` and `-res-usage` on the deployed extension; if the embedded arch or register count differs from the rebuild, the rebuild audit does not apply.
9. **On-node ceilings (GEMV or STREAM-style bandwidth, nccl-tests, ib_write_bw)** — applies to: every node x every topology. Gain: turns "bandwidth-bound" and "comm-bound" from guesses into ratios; none measured on own nodes; community GEMV 216-235 GB/s, NVIDIA two-Spark `ib_write_bw` 92.57 + 97.28 = 189.85 Gb/s at 65,536 B [Community-measured] [Code-verified] (vendor doc). Cost: a maintenance window with engines stopped. Risk: low. Falsify: if the own GEMV ceiling lands far from 216-235 GB/s on driver 580.173.02, community denominators do not transfer. The wiki's bandwidth ruler (about 215-245 GB/s depending on the probe) is stated once on [SM121 hardware facts](17-sm121-hardware-facts.md) §3; fabric ceilings belong to [Inter-Spark communication](03-inter-spark-communication.md).
10. **Advanced NCCL tracing with vClock alignment** — applies to: multi-node TP lanes with NCCL 2.28 or newer and Nsight Systems 2025.6.1 or newer. Gain: per-operation GPU timestamps correlated across ranks; could show when each rank entered a collective [Proposed]. Cost: a profiling boot; vClock is experimental and needs a provider on every host plus UDP reachability. Risk: symmetric-memory collectives record only API calls as of NCCL 2.28; proxy-step recording "can have a significant performance impact". Falsify: on a three-rank ring, check whether per-rank entry times for one collective explain the own 15.5 s vs 2.7 s collective skew; if not, it does not separate wait from wire. See [Inter-Spark communication](03-inter-spark-communication.md).
11. **Boot identity as a variable (autotune off, host settings pinned)** — applies to: SGLang with FlashInfer autotune (isolated cause); vLLM multi-node (host compaction suspected, contested). Gain: C8 spread ±1.6% instead of 92-111 tok/s, at ~2% throughput cost [Community-measured]. Cost: a flag or sysctl. Risk: the compaction cause is contested in its own source. Falsify: three boots per arm with autotune on vs off on an own SGLang lane; if boot-to-boot spread is unchanged, autotune is not the cause there.

## 6. Protocol

This is the procedure an agent runs to classify a bottleneck on a live lane and route it to the page that owns the fix. It follows the fleet rules on the entry page and the incidents in §4 and §7.

Preconditions.
- No memory overcommit: at least 8 GiB MemAvailable on every node before any engine start, at least 5 GiB warm while serving, and stop all benchmark or profiling traffic at 4 GiB MemAvailable on any node (engines preserved). Sample MemAvailable continuously during every capture, not only before it. Nsight Compute replay and trace buffers come out of the same unified pool.
- One variable per boot. A profiling boot is itself a variable: the tool, its flags and its trace mode are the change; nothing else moves in that boot.
- Restart A/Bs with the image pull skipped, so a restart cannot silently replace the image under test. Read the running engine's identity on the node; never copy it from an old packet.
- Clean window: no outside traffic. Before and during each pass, compare the server's running-request count with what the harness sent; discard any overlapped pass. Contended runs never become evidence by subtracting a guessed load.
- Never restart a client gateway; restarting the lane's engine into or out of a profiling boot is an operator step, and a gateway restart is the operator's decision.
- Never reboot a node without explicit per-node permission. The Nsight Compute permission change (`NVreg_RestrictProfilingToAdminUsers=0`) needs a reboot; ask first, or run ncu with sudo.
- Never `pkill -f` a pattern that also matches your own shell; a killed client can leave its request running server-side, so confirm the engine is idle.
- All [entry-page](README.md) rules apply, in particular: greedy logprob probe after every relaunch; discard the first request and warm every shape; unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection line on every rank; ≥3 reps with a closing A/B/A; MemAvailable every 1-2 s and zero NV_ERR_NO_MEMORY/Xid; no reboot without per-node permission. For this page that means in particular at least 3 reps per arm for every decision and a greedy logprob probe after every relaunch into or out of a profiling boot.
- Check clocks and power before starting: all ranks at the same lock, median `clocks.gr` under load matching it, no latched-low clock, power plausible for the load ([Clocks, thermal, power](13-clocks-thermal-power.md) §6). Record the driver, CUDA toolkit, nsys and ncu versions (the ncu `--clock-control` default changed between versions).

Change. Exactly one of: a profiling mode (nsys, torch, ncu on a harness), a capture window, or the one lane change being evaluated. Never profile and A/B in the same boot.

Run, in this order; stop at the first step that answers the question.
1. Name the question and the ruler. Which phase (cold prefill chunk at a stated depth, or decode step at a stated concurrency), which metric (TTFT, per-step ms, tok/s from usage), and which owning page is suspected. Two rulers are both honest if labelled (peak protocol vs mixed-corpus median; sparklab).
2. Zero-overhead signals. Engine counters and logs: scheduled tokens per step, acceptance, graph bucket, cache hits (`cached_tokens`, `timings.cache_n`), running requests. Tokens always from `usage`, never from SSE chunks (whole speculative blocks arrive in one chunk: 3-5x under-report, 0xBakeer). Recognise both `delta.reasoning` and `reasoning_content`.
3. Unprofiled component timing. CUDA events or CUDA-graph replay around the suspect region, per rank, alternating variant order, idle GPU, identical locked clocks. At least 25 samples per cell for a ranking; at least 200 near any dispatch threshold, and hold the decision when p10-p90 envelopes overlap. Never mix ranks in one curve.
4. Timeline (Nsight Systems) in a dedicated profiling boot. Relaunch the engine under nsys; do not attach. On each rank, wrap the engine command:
   `nsys profile --trace=cuda,nvtx --sample=none --cpuctxsw=none --trace-fork-before-exec=true --cuda-graph-trace=graph --capture-range=cudaProfilerApi --capture-range-end=repeat -o <one file per rank> <engine command>`
   with vLLM `--profiler-config.profiler cuda` plus `delay_iterations` / `max_iterations`, or SGLang `/start_profile` with `activities: ["CUDA_PROFILER"]`, `start_step`, `num_steps` (5 for prefill, 25 for decode; never `num_steps=1` for prefill). Use `--cuda-graph-trace=node` only when per-node timing inside graphs is needed, and record it. Add `-t nccl --nccl-trace=all` when Nsight Systems is 2025.6.1 or newer and NCCL 2.28 or newer. In a container add `SYS_PTRACE`, `ipc: host`, unlimited memlock, and run `nsys status --environment` first. Read the report's diagnostics page for hardware vs software CUDA trace. Align cross-node timelines with the vClock plugin or on a collective boundary (UTC alignment error is "one to tens of milliseconds", the size of a whole decode step). [Proposed on GB10; mechanism Code-verified]
5. Engine torch profiler, only if Python or module attribution is needed. vLLM `--profiler-config` with `profiler=torch`, activities `["CUDA"]` where CPU is not needed, `delay_iterations` / `max_iterations`, `ignore_frontend=true` only on builds that include PR 55237. SGLang `/start_profile` with `output_dir` on every node, request sent to the leader node only. Take a mapping trace with graphs off and a formal trace with production graphs; label which is which. Analyse traces on a node that does not host a serving rank.
6. Counters (Nsight Compute) on a component harness, never beside serving. Lock clocks externally and pass `--clock-control none`. Start with `ncu --list-chips`, `ncu --query-metrics --devices 0 --query-metrics-mode suffix`, `ncu --list-sets` and record which names return `n/a`. Then collect SpeedOfLight, MemoryWorkloadAnalysis, LaunchStats, Occupancy, SchedulerStats and WarpStateStats, plus `dram__bytes_read.sum`, `dram__bytes_write.sum`, `lts__t_sector_hit_rate.pct`, local-memory load and store bytes, `launch__registers_per_thread`, `launch__shared_mem_per_block_dynamic`, `sm__warps_active.avg.pct_of_peak_sustained_active`, `smsp__average_warps_eligible_per_active_cycle`, `sm__pipe_tensor_cycles_active` and `sm__pipe_fmaheavy_cycles_active`, `sm__cycles_active.avg.pct_of_peak_sustained_elapsed` (check every name on the node first). Kernels shorter than about 20 µs give unreliable multi-pass hit rates; memory throughput can print above 100% for multi-pass metrics. For NCCL kernels on a TP lane use `--communicator tcp --communicator-tcp-num-peers <ranks> --communicator-tcp-hostname <rank-0 address> --lockstep-kernel-launch` on every rank, or application replay; ncu on one rank alone stalls at the first collective. [Proposed on GB10; flags Code-verified (vendor doc)]
7. SASS and resources, no GPU needed. On the deployed extension: `cuobjdump -lelf` (which `sm_` cubins are embedded, and whether only PTX is), `cuobjdump -res-usage` (REG count; STACK, SHARED, LOCAL in bytes), `cuobjdump -sass -arch sm_121` and count `STL` / `LDL` in the target kernel, `nvdisasm --print-life-ranges` for live registers. For Triton kernels read `n_regs` / `n_spills`. `ptxas -v` describes a rebuild, not the deployed binary. [Code-verified] (vendor doc)
8. Ceilings, in a maintenance window with engines stopped: a GEMV or STREAM-style bandwidth probe per node on the current driver, `nccl-tests all_reduce_perf` from 8 KiB to 32 MiB across the triangle, `ib_write_bw` / `ib_write_lat` per link, and one boot with `NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET` for communicator, channel and protocol choices.
9. Classify with the table below, then decide any fix only by step 10.
10. Unprofiled A/B/A: opening baseline, candidate, closing baseline, each in its own boot with the pull skipped; unique salt (`cache_salt` in vLLM and SGLang, `cache_prompt: false` in llama-server) or a fresh nonce at token 0 with `cached_tokens == 0` recorded; pinned output (`ignore_eos` or `min_tokens`); one discarded warm-up request that is not the measured prompt, after every boot, clock change or idle period; medians plus every per-run value; FlashInfer autotune disabled or boot recorded as a variable.

Reading a profile into a topic. Vendor thresholds from the NVIDIA TensorRT-LLM ncu sections guide (tag v1.3.0rc12): memory throughput above 60% suggests memory-bound, compute above 60% compute-bound, both below 40% latency-bound, then read LaunchStats and Occupancy. They are not validated on SM121. [Code-verified] The table is [Interpretation] built on §3 and §4.

Record (packet fields): engine commit and image digest read on the node; driver, CUDA toolkit, nsys and ncu versions; profiler kind and every flag (trace list, graph-trace granularity, capture range and step window, activities, `ignore_frontend`); hardware vs software CUDA trace from the diagnostics page; ranks captured and how timelines were aligned; clock lock and median `clocks.gr` and power per rank during the capture; minimum MemAvailable per rank; the unprofiled elapsed time of the same request; a flag that profiled requests are excluded from scores; per request: salt or nonce, `cached_tokens`, prompt and completion tokens from usage, output-length pin, content kind, temperature, acceptance; per-run values, not only medians; boot identifier and autotune setting; outside-traffic check per pass; discarded passes and why.

Pass gate. A profile is usable when: the unprofiled elapsed for the same work is recorded; every rank captured the requested steps; no MemAvailable breach; clocks matched the lock on every rank; and its classification is confirmed by a second, independent method (unprofiled component timing, clock sensitivity or an on-node ceiling). A fix passes only by unprofiled A/B/A: the effect exceeds the lane's A0-to-A1 drift (own decode drift about -1% / +4%), a decode effect below ~8% needs repeated boots per arm before it is called (community boot-to-boot spread), every per-run value is kept, and the change passes [Quality and correctness gates](21-quality-and-correctness-gates.md).

Rollback. Restart the engine without the profiler wrapper or profiler config, with the pull skipped; confirm tracing is off on every rank and the configuration line matches the serving baseline; restore the fleet clock lock if it was changed and verify `clocks.gr` under load; move trace files off the node and delete them there; if the ncu permission option was changed, revert it only in a reboot the operator has approved. Then run one cold request and its exact repeat and compare with the baseline before the lane serves again.

## 7. Anti-patterns and known-bad

Tooling
- [Code-verified] (vendor doc) "Attach nsys to the live container." Neither Nsight tool can attach CUDA tracing to an engine that was not started under it: nsys traces the launched process tree, or with `--cuda-trace-scope=system-wide` only same-user processes launched after collection starts (one system-wide session per machine); ncu attach reaches only a target started by ncu or `ncu --mode=launch`. A profiling plan written as "attach to the live container" does not work as written.
- [Measured] Scoring profiled throughput. The own torch capture added about +51% TTFT; a community capture ran 324 vs 893 tok/s with extra debug syncs also on. Profiled requests are never scores.
- [Measured] Reading a collective kernel's duration as network cost. Two ranks showed ~15.5 s in the all-reduce kernel because they were waiting for the third; an unprofiled component timing showed no persistent imbalance.
- [Code-verified] `VLLM_TORCH_PROFILER_DIR` and its sibling variables. Removed on 2026-02-03 (PR 33536); setting them on a current build silently does nothing.
- [Measured] `ignore_frontend=True` on a vLLM build older than PR 55237: `/start_profile` raised because `AsyncLLM.profiler` was missing. The workaround (frontend on plus `max_iterations`) is the configuration vLLM warns may be high overhead.
- [Code-verified] Layerwise NVTX, Python stacks, Proton pcsampling and Chrome traces with CUDA graphs on: none of them see inside replayed graphs. A graphs-off trace is a mapping trace, not the lane.
- [Code-verified] `--python-backtrace=cuda` in SGLang nsys runs inflates CUDA-event kernel times; `num_steps=1` for an SGLang prefill capture can stop just before the prefill forward.
- [Community-measured] `TORCH_DISTRIBUTED_DEBUG=DETAIL` or `TORCH_NCCL_BLOCKING_WAIT=1` for multi-node SGLang over RoCE produced false collective-mismatch errors; use `NCCL_DEBUG=INFO` (forum 373677, four DGX Sparks).
- [Community-measured] Treating a clean profile as proof a graph lane is healthy: a two-GB10 SGLang decode-graph hang was delayed or hidden by Nsight profiling and `CUDA_LAUNCH_BLOCKING=1` (issue 29548).
- [Code-verified] (vendor doc) Nsight Compute beside serving traffic or on one TP rank alone: it serializes launches across processes on the device, flushes caches, saves and restores device memory, and NCCL kernels "may be unable to make forward progress" without lockstep across all ranks.
- [Community-measured] UM page-fault tracing on GB10: unsupported (forum 357848), and elsewhere it costs up to 70% (vendor doc).
- [Community-measured] Trusting in-kernel `%clock64` on CUDA 13.1 or 13.2 (overflow, zero) (forum 367851).
- [Code-verified] (vendor doc) Leaving ncu's default clock control on while the fleet holds an external lock: depending on the ncu version it locks to base or boost and fights the external setting. Pass `--clock-control none`.

Reading
- [Measured] Percent-of-ceiling from a byte model, or from mixed ranks. A per-rank implied bandwidth above nominal (351 vs 273 GB/s) refuted the byte model; the earlier "66-92% of nominal, 10-30% headroom" came from mixing ranks and was withdrawn. No GB10 "X% of peak DRAM" statement is defensible until the ncu denominator is known and an on-node ceiling exists.
- [Community-measured] Reading "Memory Throughput" as DRAM: it is the maximum over memory units; a kernel can read ~91% memory throughput at ~12% DRAM with L1 hot (forum 290438, GPU unknown). Expand with `breakdown:`.
- [Community-measured] Reading SM utilisation as busy: a prefill graph starving memory cut 96K prefill 893 -> 202 tok/s with utilisation at 100% and power 40-57 W vs 150-204 W at genuine load (SGLang issue 40094, two small discrete cards). Read power beside utilisation.
- [Measured] A local speedup taken as an end-to-end win: own lookup cache 10-40x local, +0.41 / +0.45 / -2.08% end to end. [Community-measured] ds4 probe -98% local, +2.1-2.2% alone end to end (PR 772); five kernels fused to one per layer changed throughput 0% because ~590 µs idle per graph break dominated (SGLang issue 35851, one H200); community trace-suggested fixes lost 13-61%.
- [Community-measured] A long "send" read as communication: a ~100 ms pipeline-parallel token send with decode graphs turned out to be a device-to-host copy plus `cudaStreamSynchronize` while the last stage waited for the first, still in a longer prefill (SGLang issue 10865, off-platform). It is rank waiting and schedule imbalance, not wire time.
- [Measured] A dispatch rule finer than its noise: a worst-of-six 0.97 gate against up to 15% inter-rank spread at 25 samples; 39 of 64 row counts never measured.
- [Measured] Bundle results used for attribution: kernel, prefill path, FP8 scope, slot count and loader changed together, with no closing baseline.
- [Historical diagnostic] Changing the adaptive speculation set without re-profiling dispatch: it changes captured rows and the cooperative / stock kernel mix, confounding the A/B (2026-09-20 GLM 5.3 Flash TP3 frontier dossier v2).

Benchmark discipline
- [Measured] Measuring in a contaminated window: one base pass overlapped ~90 outside requests and was discarded; counter deltas and acceptance probes read wrong under live traffic.
- [Measured] Probes standing in for traffic: idle nonce probes read acceptance 3.0 of 3 at short depth while real deep traffic read 0.00.
- [Measured] [Community-measured] Prompt-cache contamination: one unrelated request wiped a warm chain (66% -> 0%); nested prompts overstated cold prefill ~50x (hasso5703); `vllm bench` walking ShareGPT sequentially produced cache hits even at one request until fixed upstream (forum 343318); warm-up with the measured prompt made a later "cold" prompt take 148 ms for 4 tokens (llmkube). Enabling the prefix cache also changed agent trajectories on 36.2% of episodes at 16-bit and 75.0% at 4-bit weights with greedy decoding, while cache-off repeats were bit-identical (arXiv:2609.04748, single-author preprint, two engines, not GB10). [Community-measured]
- [Measured] Comparing across protocols: the same lane read 45-51 or 31-44 tok/s depending on temperature and content; structured counting vs prose read 101.7 vs 44.2 tok/s on the same weights.
- [Community-measured] Counting SSE chunks as tokens (3-5x under-report with speculative blocks, 0xBakeer); recognising only one reasoning field (97 vs 19.9 tok/s, hasso5703); taking the first HTTP byte as TTFT.
- [Measured] [Community-measured] Scoring the first request after a boot, clock change or idle: 813 vs 1,375 tok/s (own cold 8K); 24.6 vs ~34 tok/s after a new lock (own); 23.8 vs ~40 tok/s after boot (hasso5703).
- [Community-measured] Calling an n=1 or single-boot result: an 8192-token budget "win" reversed at n=3 (jschmied); two ~16%-looking single-stream gains each cost ~16% of C8 under a boot-lottery control (hasso5703); identical configs differed +11% across boots (neko-legends).
- [Measured] Stacking memory changes in one boot, or running load generators and trace analysis on a head node: a long prefill at a high static memory fraction wedged a head node under synchronous tensor parallelism; two memory knobs in one boot left a node unreachable until a power cycle.
- [Measured] Restarting an A/B arm without skipping the pull (silently reverts a local image); reading container "Up" as health (a dead TP pair can leave both up; poll the health endpoint); `pkill -f` on a pattern in your own command line; a 10.5 s dashboard sampler read as proof of no clamps (it is blind to millisecond power clamps); a control arm never gated for correctness (it produced corrupted logits mid-campaign); harness assertion stops read as engine crashes; outputs compared after a precision cast; a sanitizer run that instrumented unchanged stock code.
- [Community-measured] Assuming a reboot clears a latched clock. A latch is usually cleared by removing AC power 30-60 s; one 721 MHz unit did not clear after 8 h (see [Clocks, thermal, power](13-clocks-thermal-power.md) §7); a drain is a power cycle and needs per-node permission. Check clocks before every profiling session.
