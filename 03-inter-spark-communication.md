# Inter-Spark communication over DAC: NCCL, RoCE, and the TP tax

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 128 GB unified memory). Two nodes (node-1 + node-2) joined by one QSFP direct-attach copper cable (DAC), later three nodes in a triangle (one DAC per node pair). Code lines are quoted at these pins: NCCL `v2.30.7-1` (73cf112), vLLM 34b0690, SGLang 2909f84, llama.cpp 6e60f35, antirez/ds4 0aaea5a, Entrpi/ds4 b0a147a, ExLlamaV3 6b84a21, nccl-tests b4d5bee, NVIDIA dgx-spark-playbooks 3410c65. The own lanes run older or forked builds, so a code line says what upstream does at the pin, not what a given lane runs. Units: Gb/s is gigabits, GB/s is gigabytes; NCCL "bus bandwidth" (busbw) is the nccl-tests normalisation, not wire rate.

## 1. What it is

When one model is too big or too slow for one GB10, engines split every layer across several boxes (tensor parallelism, "TP": each box holds a slice of every weight matrix). After almost every layer the boxes must add their partial results together over the cable (an all-reduce, one "collective"), and every box waits until the slowest one has finished. A decode step of a modern model needs about 90 to 120 of these collectives, whatever the TP width, and each costs a fixed round-trip time no matter how few bytes it carries. That fixed cost is the "TP tax": on the two independent three-node stacks that have profiled it, NCCL (NVIDIA's collective library) takes about 13-16 ms of each single-user decode step, about 14-20% of the step. The link itself is rarely full during decode (one TP2 pair used 0.3% of it); what matters is latency per collective, how many collectives each step issues, and whether each box runs at the same speed. Bandwidth matters for prefill (long prompts), where each collective carries megabytes. On GB10 the cable is a ConnectX-7 (the network chip) port rated "up to 200 Gb/s", but each port is really two independent PCIe halves of about 100 Gb/s each, there is no GPUDirect RDMA (the NIC cannot read GPU memory directly), and none of the NVLink-era tricks that fuse or hide collectives are enabled on this chip. Getting the fabric right is therefore mostly about correctness and avoiding silent slow paths; making it faster is mostly about issuing fewer, larger collectives per generated token. See also [SM121 hardware facts](17-sm121-hardware-facts.md), [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md), [Speculative decoding](02-speculative-decoding.md) and [MoE dispatch](08-moe-dispatch.md).

## 2. How each engine does it

Shared layer: NCCL. vLLM, SGLang, ExLlamaV3-in-vLLM and llama.cpp's experimental tensor mode all hand cross-node collectives to NCCL; antirez/ds4 is the only engine found with its own RoCE transport. What NCCL does on this fabric, at `v2.30.7-1` unless stated:

- Protocols. LL moves 8-byte words of 4 B data plus a 4 B flag (device.h:75-86); LL128 uses 128-byte lines with one 8-byte flag (device.h:110-112); Simple moves bulk data with separate synchronisation. With `NCCL_LL128_C2C=1` (default) and compute capability at least 9.0, LL128 stays enabled only when the graph's inter-node path type is at most `PATH_PXN` (tuning.cc:514-534). A ring graph file that declares `typeinter="PHB"` therefore already excludes LL128, with or without `NCCL_PROTO=^LL128`. [Code-verified] The env reference warns that LL128 "on platforms that don't support it can lead to data corruption" (NCCL env page, fetched 2026-09-23). [Code-verified]
- Protocol efficiency, from the literature. A paper on NCCL internals cites LL at 25-50% and LL128 at about 95% of peak bandwidth (values it takes from a reference, not its own measurement) and measures that LL and LL128 win below about 64 KiB inter-node on a 16-node GH200 + Slingshot system (arXiv 2507.04786v3, §V-F). Not GB10. [Community-measured]
- Buffers. Default per-connection buffers: LL 512 KiB, LL128 4.69 MiB, Simple 4 MiB, 9.19 MiB in all (init.cc:810-826; device.h:26, 97-115). On GB10 pinned host memory is the same pool as GPU memory. [Code-verified]
- Latency model. With one GPU per node the tuner uses the NET latencies for each inter-node hop: Ring all-reduce = base + 2(n-1) x inter, Tree = base + 2 x floor(log2 n) x inter; Simple adds the graph's `latencyInter` a second time for the flush (tuning.cc:146-176, 376-412). Predicted LL floors: 2 nodes Ring 16.6 µs, Tree 16.8 µs; 3 nodes Ring 26.6 µs, Tree 16.8 µs. The tuner's modelled bus bandwidth is channels x per-channel inter bandwidth (tuning.cc:306, :324). [Code-verified] Measured GB10 floors run 2-5x this model (§4). [Interpretation]
- RoCE defaults. `NCCL_IB_GID_INDEX=-1` (auto: picks an IPv4 RoCE v2 GID per device), `NCCL_IB_ROCE_VERSION_NUM=2`, `NCCL_IB_TIMEOUT=20`, `NCCL_IB_RETRY_CNT=7`, `NCCL_IB_TC` unset, `NCCL_IB_QPS_PER_CONNECTION=1`, `NCCL_IB_SPLIT_DATA_ON_QPS=0`, `NCCL_IB_MERGE_NICS=1`, `NCCL_IB_PCI_RELAXED_ORDERING=2` (net_ib/connect.cc:12-22, 60-62, 101-116, 298-330; net_ib/init.cc:11-30; common.cc:22). [Code-verified]
- Subnet-aware routing. `NCCL_IB_SUBNET_AWARE_ROUTING` (default 0) and `NCCL_IB_SUBNET_PREFIX_LEN` (default 24) exist at `v2.30.7-1` (net_ib/connect.cc:61-62) and are absent from `v2.30.4-1`, `v2.30.3-1`, `v2.29.7-1`, `v2.28.9-1` and `v2.28.3-1`. NVIDIA's three-node ring fork (zyang-dev/nccl @ fab1850, which reports itself as 2.29.7) already carried both, so a log that says "2.29.7" can still have live subnet routing. Mechanism: the listener advertises up to two GIDs in its handle; the connector keeps its default device only if that device shares a subnet with a remote GID, otherwise it switches and logs `Subnet-aware routing: overriding dev X with dev Y` (connect.cc:518-596, 610-625, 798-804, 1470-1476). [Code-verified]
- NIC merging. `NCCL_IB_MERGE_NICS=1` fuses only NICs within `NCCL_NET_MERGE_LEVEL` (default `PATH_PORT`), and a NIC is multi-port only when bus IDs match except the final function digit (topo.cc:1160-1185, 1392-1415, 1738-1748). The two cages' functions on the same PCIe domain (`...f0` + `...f1`) merge at the default; the domain-0 and domain-2 "twins" of one cage never do. [Code-verified] A two-cable pair log shows exactly that merge (`Made virtual device ... rocep1s0f0+rocep1s0f1 speed=400000`, forum 352051 #1). [Community-measured] On a triangle, where the two cages face different peers, the default merge is wrong, which is why ring recipes set `NCCL_IB_MERGE_NICS=0` and/or `NCCL_NET_MERGE_LEVEL=LOC`. [Interpretation]
- Graph files. `NCCL_GRAPH_FILE` attributes are parsed straight into the graph (search.cc:928-957). A graph with `crossnic=1` is silently skipped when `NCCL_CROSS_NIC=0` (search.cc:936). With one GPU per node, `ncclTopoGetNetDev` always takes index 0, so only the first `<net>` of each channel is used for both send and receive (search.cc:1400-1417); a second `<net>` entry is inert. [Code-verified]
- GPUDirect RDMA. NCCL disables GDR when neither a peer-memory module nor dma-buf registration works, even though `NCCL_NET_GDR_C2C` defaults to 1 (paths.cc:465-520). [Code-verified]
- Documentation gaps. The NCCL env page as fetched 2026-09-23 (labelled NCCL 2.32.3) has no entry for `NCCL_IB_SUBNET_AWARE_ROUTING`, `NCCL_IB_SUBNET_PREFIX_LEN` or `NCCL_GRAPH_FILE`; `NCCL_NET_MERGE_LEVEL` is only referenced inside the `NCCL_NET_MERGE_POLICY` entry. [Code-verified] Undocumented variables are silently ignored on builds that lack them; the INFO log line `<VAR> set by environment to ...` is the only proof a variable was read. [Interpretation]
- TensorRT-LLM is out of scope here. NVIDIA publishes one multi-node GB10 result (§4) without fabric settings; its fusion kernels share the NVLink/multicast requirements below. [Interpretation]

### vLLM

Mechanism. The TP all-reduce dispatcher tries, in order, NCCL symmetric memory, quick all-reduce, FlashInfer PCIe IPC, FlashInfer all-reduce, AITER, custom all-reduce, torch symmetric memory, then PyNCCL (distributed/device_communicators/cuda_communicator.py:335-410). [Code-verified]

- Defaults on CC 12.1, multi-node. Every path before PyNCCL is off: FlashInfer all-reduce disables itself when its size table has no entry for this capability and world size (flashinfer_all_reduce.py:351-388); custom all-reduce needs one node or NVLink multicast (custom_all_reduce.py:196-206, 306-320); torch symmetric memory needs `multicast_ptr != 0` (symm_mem.py:100-118). `VLLM_ALLREDUCE_USE_SYMM_MEM=1` and `VLLM_ALLREDUCE_USE_FLASHINFER=1` (envs.py:268-270) do not change this. [Code-verified] A two-node GB10 user on a GLM EXL3 fork logged `Custom collectives are disabled because this multi-node group does not support MNNVL multicast` and `Using ['PYNCCL'] all-reduce backends` (MiaAI-Lab GLM-5.3-Flash-EXL3-2x issue #163, open, no maintainer reply as of 2026-09-19). [Community-measured]
- All-reduce + RMSNorm fusion. Auto-enabled only for capability family 10.x or exactly 9.0 (config/vllm.py:177-201). With no explicit `fi_allreduce_fusion_max_size_mb` the SM121 size lookup is empty and the pass disables itself (compilation.py:194-208; allreduce_rms_fusion.py:102-127, 1008-1016); an explicit value bypasses the table, but `FI_SUPPORTED_WORLD_SIZES = [2, 4, 8, 16]` excludes TP3 and multi-node fusion needs the `mnnvl` backend, which needs NVSwitch multicast (flashinfer_all_reduce.py:146-160; PR #38136 merged 2026-03-26; FlashInfer issue #2006). [Code-verified]
- Sequence parallelism (SP) and async TP. SP thresholds have entries for capability 90 and 100 only, so SP is never auto-applied on SM121 (compilation/passes/fusion/sequence_parallelism.py:38-94); it can be forced by setting `PassConfig.sp_min_token_num`. The docs say: "Sequence Parallelism itself does not directly improve performance; it is a prerequisite for the AsyncTP pass" (docs.vllm.ai design/fusions, fetched 2026-09-23). Async TP uses `torch.ops.symm_mem`, which needs multicast. [Code-verified] SP replaces each all-reduce with a reduce-scatter plus an all-gather (arXiv 2205.05198), so on GB10 it would double the op count at flat bytes. [Interpretation]
- Expert parallelism. All-to-all kernels are used only when EP is on and data parallel > 1, prefill context parallel > 1, or sequence-parallel MoE is on (model_executor/layers/fused_moe/config.py:1028-1031); the default `all2all_backend` is `allgather_reducescatter` (config/parallel.py:202-213). "TP + EP" with one data-parallel rank keeps the TP all-reduce pattern and only changes the weight layout. [Code-verified]
- Logits. The target's logits are gathered with a full-vocabulary all-gather (`use_all_gather()` True by default, logits_processor.py:86-134). A vocab-parallel local-argmax path that gathers only `[batch, 2]` is opt-in (`speculative_config.use_local_argmax_reduction`, default False), "Only applies to greedy draft selection in non-tree speculation" (speculative.py:458-462), and is rejected together with adaptive verification except for the `dspark` method (speculative.py:1580-1590). [Code-verified] See [Sampling and the lm_head](12-sampling-and-lm-head.md).
- Community-known bad defaults on GB10: NGC containers with NCCL 2.27.7 predate SM121 and hang (route179 blog, 2026-07-21); the NGC-bundled AWS OFI network plugin fails dma-buf registration and falls back to TCP sockets unless `NCCL_NET_PLUGIN=none` (forum 366266); Ray is absent from aarch64 images, so `--distributed-executor-backend mp` with `--nnodes/--node-rank` is used; six ranks exceed Docker's default `nofile=1024` (capetron gb10-cluster-guide docs/05). [Community-measured]
- GB10 forks. Anemll/dspark-vllm-gx10 @ 081fda9 (a vLLM 0.25.1 fork, TP2) and the DSpark-style recipes use the same PyNCCL path; none adds a non-NCCL transport. [Code-verified] for the Anemll README; [Interpretation] for the rest.

### SGLang

- All-reduce fusion. `flashinfer_comm_fusion.py:36-85` raises unless SM90 or SM100; `trtllm` is single-node and `mnnvl` multi-node needs SM100. Auto-enable was restricted to SM90/SM100 after SM120 graph-capture crashes (issue #15650; PR #16283 merged 2026-01-03); an SM12x enable PR (#18758) was closed unmerged; the MNNVL all-reduce backend (PR #30700, merged 2026-08-11) is NVLink-only. [Code-verified]
- Custom all-reduce is disabled when the group spans nodes (distributed/device_communicators/custom_all_reduce_utils.py:455-470), so collectives run on NCCL. [Code-verified]
- MoE all-to-all backends are enumerated (`deepep`, `deepep_v2`, `mooncake`, `nixl`, `mori`, `flashinfer`, `megamoe`, `pplx` and others; layers/moe/utils.py:34-48). DeepEP's internode mode requires GPUDirect RDMA and IBGDA (DeepEP docs/nvshmem.md @ a56d6156, lines 11-15), and GB10 has no GPUDirect RDMA (§3). No GB10 run of any internode all-to-all backend was found. [Code-verified] list; [Interpretation] applicability.
- Sequence parallelism for dense layers was only a proposal (issue #10519, closed); the TP-overlap PR #9058 closed unmerged; the H100 NVLink fusion win in PR #22664 (5.49 -> 9.41 req/s) does not transfer. [Code-verified] status.
- On GB10. A DeepSeek V4.1 Flash TP3 triangle profile reports 104 collectives per decode step taking about 13-16 ms of an ~82 ms step, LL for the 61 KB decode all-reduces and Simple for prefill (MiaAI-Lab DeepSeek V4.1 README, snapshot kept in the own 2026-09-13 DeepSeek V4.1 Flash TP3 qualification packet). A four-node switched cluster found EP=4 "consistently loses 3-7%" against EP=1 for Qwen3.5-397B at TP4 (ht12, forum 366325 #3, logs in the linked repo). [Community-measured]

### llama.cpp and forks

- llama.cpp @ 6e60f35. Multi-node is the RPC backend (`ggml-rpc-server`): TCP by default, with an RDMA transport negotiated at handshake when both peers are built with libibverbs (RoCEv2 on ConnectX); `GGML_RPC_NO_RDMA=1` forces TCP; the README calls RPC proof-of-concept and insecure (tools/rpc/README.md). `--split-mode layer` (pipeline) is the default; `--split-mode tensor` is experimental, uses NCCL (build flag `GGML_CUDA_NCCL=ON`) for cross-GPU reductions, needs flash attention and unquantized KV, and is not implemented for DeepSeek2, GLM-DSA, Minimax-M2 and other MoE architectures (docs/multi-gpu.md). [Code-verified] No source shows tensor mode across RPC nodes, and no GB10 multi-node llama.cpp measurement was found. [Code-verified] negative.
- antirez/ds4 @ 0aaea5a. Two-Spark tensor parallelism exists for DeepSeek V4.1 Flash Q2 text only: one GPU per rank, 50/50 expert split, `--transport rdma` (ibverbs, RoCEv2, device and GID picked from the link address) or TCP; "The transport stages CUDA results through host memory; this is RoCE, not GPUDirect"; no NCCL; vision and DSpark unsupported in CUDA network TP; layer splits use pipeline parallelism over TCP (docs/DISTRIBUTED.md:100-135). No throughput is published for the Spark TP mode. [Code-verified]
- Entrpi/ds4 @ b0a147a: "Spark-to-Spark RDMA tensor parallelism is not implemented" (README:309); its TP section documents two-Mac RDMA only; pipeline parallelism is TCP only. Entrpi/ds4-on-spark @ 99fb7b1 is single-Spark serving. [Code-verified] No SM121 multi-node path found as of b0a147a.
- Anemll: the GB10 artifact is the vLLM fork above; no llama.cpp-family multi-node path found. [Code-verified]

### ExLlamaV3 in vLLM

- EXL3 as a vLLM quantization method inherits vLLM's PyNCCL path. For GLM-5.3-Flash at TP3 with EP3 and EXL3 experts, each rank runs its 96 local experts on the whole token batch and the routed and shared-expert partials are summed in one all-reduce per MoE layer; there is no all-to-all. Per target forward: 45 attention output all-reduces + 3 dense-MLP all-reduces + 42 MoE all-reduces + 1 lm_head all-gather = 91; the TP-sharded draft model adds about 11 more per decode step, so about 102 per decode step and 91 per prefill chunk. [Code-verified] at the own lane's fork commit (2026-09-20 GLM 5.3 Flash TP3 frontier dossier v2).
- Ring bytes per rank for that lane: at 8 rows 7.5 MiB of all-reduce plus the lm_head all-gather (3.15 MiB if fp32, half that with 16-bit logits); at 64 rows 60 MiB plus 12.6 MiB with 16-bit logits (≈17% of decode ring bytes; ≤30%, 25.2 MiB, only if fp32; no fp32 cast before the gather was found, see [Sampling and the lm_head](12-sampling-and-lm-head.md)); at 2,048 rows about 1.9 GiB per chunk. [Interpretation] from code-verified shapes.
- Enabling sequence-parallel MoE for this quant method turns each MoE all-reduce into dispatch + combine and each attention all-reduce into all-gather + reduce-scatter: op count doubles at flat ring bytes. [Code-verified] Predicted neutral to negative at decode. [Interpretation]
- Standalone ExLlamaV3 @ 6b84a21 has its own TP with `native` (default) and `nccl` backends; the NCCL backend joins a torch.distributed NCCL group for barriers and all-reduce but builds a POSIX shared-memory fallback for broadcast and gather (model_tp_backend.py:74-120, 221-280), which is single-host. `EXL3_TP_NCCL_FP32` selects an fp32 or bf16 wire (doc/env_vars.md). [Code-verified] Standalone ExLlamaV3 TP across Sparks is therefore not supported as written. [Interpretation]
- The only other multi-Spark EXL3 comm data point is a two-node user reporting about 2x the lab's per-step time, attributed to the PyNCCL path (issue #163, unresolved). [Community-measured]

## 3. What is different on GB10 / SM121

- [Code-verified] Each node has two QSFP cages, Ethernet only, each "up to 200 Gb/s"; a faster cable does not raise the cap. The ConnectX-7 reaches the SoC over two independent PCIe Gen5 x4 links, so each cage appears as two network interfaces and two RoCE devices, one in PCIe domain 0 and one in domain 2 (left cage `rocep1s0f0` + `roceP2p1s0f0`, right cage `rocep1s0f1` + `roceP2p1s0f1`). Approved cables are QSFP112 DACs. NVIDIA's cluster assistant supports up to three nodes direct and four through a switch. (DGX Spark User Guide, ConnectX-7 networking, fetched 2026-09-23; vendor documentation, a nominal cap, not an achieved rate.)
- [Community-measured] The kernel reports each function at `126.028 Gb/s available PCIe bandwidth (32.0 GT/s PCIe x4 link)` (Sangiorgi blog; forum 360591 #42). One half delivers about 109-112 Gb/s of RDMA; both halves of one cable together about 196 Gb/s per direction (§4). "200 Gb/s" is per direction per cage and needs both halves busy.
- [Community-measured] A second cable to the same peer adds no bandwidth; NVIDIA staff call it "mostly just for redundancy, or if you want to connect to a third system" (forum 366266 #7), and with the two-node playbook it can cap at 100 Gb/s (forum 362403 #3).
- [Code-verified] InfiniBand mode is unsupported; the ports are Ethernet/RoCE only (NVIDIA moderator, forum 355444 #4).
- [Code-verified] No GPUDirect RDMA. NVIDIA staff: memory from the pinned device allocators "cannot be coherently accessed by the CPU complex nor by I/O peripherals"; `nvidia-peermem`, dma-buf and GDRCopy do not work; use `cudaHostAlloc` + `ibv_reg_mr` (forum 352051 #2). [Measured] Own init log on the triangle: `GPU Direct RDMA Disabled`, `GDR 0`, `dlvsym failed on mlx5dv_reg_dmabuf_mr`, `cuMemGdrSupport 0` (2026-09-14 GLM-5.3-Flash EXL3 TP3 triangle qualification).
- [Community-measured] Large messages do not need GDR here: a custom two-node benchmark that writes GPU buffers and lets the NIC read the same unified-memory pointers (transport unstated) measured 20.39 GB/s at 8 MB to 22.31 GB/s at 64 MB, one direction (alan.dang, forum 352051 #12). Whether host staging inflates small-message latency is unmeasured (§8).
- [Community-measured] The GPU reports PCIe Gen1 x1 to NCCL because it reaches the CPU over C2C; NVIDIA staff confirm this is expected. A topology file forcing 32 GT/s raised NCCL's planned bandwidth (`totalBw 3.0` -> `48.0`) but not the measurement (forum 366266).
- [Code-verified] No NVLink and no multicast, so every collective-fusion, custom all-reduce and symmetric-memory path in vLLM and SGLang is off across nodes, and capability tables keyed on 9.0/10.x exclude 12.1 (§2). Every cross-node collective is a plain NCCL call over RoCE.
- [Community-measured] Pinned host memory is GPU memory: default NCCL buffers on a three-node DeepSeek V4.1 SGLang deployment came to 512 connections x 9.19 MiB = 4.7 GiB per node of unreclaimable `Shmem` (MiaAI-Lab DeepSeek V4.1 README). NCCL buffers compete with KV cache. See [Memory on unified memory](11-memory-on-unified-memory.md).
- [Code-verified] A triangle has one cable per pair, so each node's two cages face different peers on different subnets; NCCL's default device choice and NIC merging assume otherwise. Subnet-aware routing (NCCL `v2.30.7-1` or NVIDIA's ring fork), `NCCL_IB_MERGE_NICS=0`, and on the own fleet a per-rank ring graph plus `NCCL_CUMEM_ENABLE=1` were each needed to pass init (§4).
- [Community-measured] Link and firmware states unique to this box: a "200G link, ~13 Gb/s RDMA" state cleared by OS and firmware updates (capetron docs/04: 12.74 -> 111.86 Gb/s; chronara.io: ~13 -> 196 Gb/s); a February 2026 firmware regression that cut two-node all_gather from ~24 to ~16 GB/s, fixed first on the Founders Edition and later on OEM units (forums 360591, 366457, 366055); a link bounce that leaves the CX-7 degraded until reboot or AC drain (forum 371031; itadmin.blog); a `cx7-pcie-hotplug` driver that logs `Cable removal` and drops CX-7 devices after boot on some kernels (forum 374275). The `Detected insufficient power on the PCIe slot (27W)` line appears on healthy systems too and is not diagnostic (itadmin.blog).
- [Community-measured] TP is lockstep, so the slowest rank sets the pace. One four-node cluster saw a GPU "fast/slow" state invisible to `nvidia-smi` move TP4 decode between 63 and 94 ms per step (single-GPU GEMV probe 224-233 vs 66-80 GB/s) on older BIOS, driver and kernel; it did not reproduce on BIOS 0ACUM027 + driver 580.173.02 + kernel 1032 across 8 nodes and about 540 probe-seconds (tonyd2wild DeepSeek V4.1 issue #1). See [Clocks, thermal, and power](13-clocks-thermal-power.md).

How to read the TP tax numbers together. The standalone floor for one small collective is about 40-86 µs (two nodes 41-43 µs; four nodes 60 µs graph-captured; three nodes 72-86 µs; own eager 80 µs as an upper bound). Inside an engine, one C1 decode step spends about 13-16 ms in NCCL across 104-108 collectives, about 130-150 µs each, because rank skew and waits are included. Multiplying the floor by the count (for example 80 µs x 102 ≈ 8 ms) underestimates the in-engine cost by about half. [Interpretation] The own GLM TP3 dossier's 4-10 ms per step band is below both in-engine profiles and should be read as a lower bound until an own per-rank timeline exists. [Interpretation]

## 5. Levers, ranked

Ranked by expected value on a working fabric. The first lever is a precondition; skip it only when an INFO boot already proves it.

1. **Prove the transport and the link before tuning anything** — applies to: every engine x every model x every topology. Gain: 1.88x serving throughput and 2.12 -> 9.78 GB/s busbw going from TCP sockets to RoCE (forum 366325); 1.19 -> 13-20 GB/s by turning off a broken network plugin (forum 366266); ~13 -> 196 Gb/s after a firmware/OS update (chronara.io) [Community-measured]. Cost: one INFO boot and a counter read. Risk: none. Smallest falsifying experiment: one boot with `NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH,TUNING,ENV`; if it already shows `NET/IB` with the expected HCA list, `GDR 0` and the expected channel count, and per-cable counters move, this lever is spent.

2. **Pick the TP width by what the model needs, not by how many nodes exist** — applies to: all engines x model family x 1, 2, 3, 4 nodes. Gain: dense models that fit gain from TP2 (+60-73% decode, own 2026-08-17 [Measured]; 1.79x, community); small-active MoE gains little or loses from wider TP (Qwen3.6-35B-A3B TP2 99.0 -> TP4 89.2; Flash Next pair vs single mixed, own 2026-09-05); large MoE gains per stream from TP4 (+9 to +37%) because each rank streams fewer weight bytes; TP3 at the same image buys capacity (KV 2x) with +5-9% single stream and +22-23% worse long-prompt TTFT (MiaAI-Lab, FlyCockpit) [Community-measured]; for aggregate throughput, independent pairs beat one wide group (2.2x, capetron) [Community-measured]. The own GLM TP2 -> TP3 +29-45% is confounded with recipe (slots, k, kit): a recipe change, not a TP-width effect [Measured] (confounded). Model-level TP fit is on [Model architecture cards](20-model-architecture-cards.md); EP versus TP on [MoE dispatch](08-moe-dispatch.md). Cost: a redeploy. Risk: padding waste when heads do not divide (§7), and every extra rank is one more place to be slowest. Smallest falsifying experiment: a same-recipe TP2 vs TP3 A/B on one model (not yet run on the own fleet).

3. **Issue fewer engine steps per generated token** — applies to: all engines with speculative decoding x any model x TP2/TP3. Gain: collective cost is fixed per engine step, not per token ("fixed per engine step, not per token", danielgbates, forum 375607), so each extra accepted draft token divides the ~13-16 ms step tax [Interpretation]; no isolated GB10 measurement of the comm share versus acceptance length exists. Cost: a drafter, which itself adds collectives when TP-sharded (about 11 more per step on the own GLM lane [Code-verified]). Risk: the drafter's own collectives. Smallest falsifying experiment: per-rank step timeline at two draft lengths; the NCCL time per step should stay flat while tokens per step rise. See [Speculative decoding](02-speculative-decoding.md).

4. **Capture collectives in CUDA graphs** — applies to: vLLM and SGLang decode x all models x all TP. Gain: a graph-captured standalone small all-reduce ran 60 µs p50 on four switched nodes (tonyd2wild) against the own eager 80 µs on three direct nodes; different topologies, so the gap is suggestive only [Interpretation]. Cost: none where the engine already captures decode. Risk: capture-time shape limits. Smallest falsifying experiment: nccl-tests `all_reduce_perf -b 8 -e 1M` once eager and once with `-G 100` on the same fabric and library. See [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md).

5. **Use both PCIe halves of each cable (the "twins")** — applies to: vLLM/SGLang x prefill-heavy lanes x pair and triangle. Gain: prefill single digits, decode flat or negative: pair ~+5.0% prefill, decode flat (upstream maintainer); switched TP4 +9% prefill, decode -5 to -9%, aggregate -11% (capetron); triangle via a patched plugin, 64 MB all-reduce 12.0 -> 20.8 GB/s, prefill +5.5%, decode flat (NNNtrance) [Community-measured]. The own triangle runs one half per hop (12.9 GB/s busbw [Interpretation]); the NCCL-IB version of this lever (addressing the domain-2 functions on their own per-leg subnets, listing them in `NCCL_IB_HCA`, and a graph whose channels start on alternating devices, since only the first `<net>` is used) is [Proposed]. On the own pair, both halves were enabled on three lanes and never A/B-measured. Cost: new addresses, a new HCA list, a new graph file; a maintenance window. Risk: decode loss on latency-bound lanes; changing addresses on a live shared port can flap the serving link. Smallest falsifying experiment: nccl-tests all-reduce at 16 and 64 MiB with and without the twins; if busbw does not rise well above ~13 GB/s, stop before any serving A/B.

6. **NCCL channel count** — applies to: NCCL on triangles x MoE TP3 x concurrency 4-8. Gain: `NCCL_MAX_NCHANNELS=8` vs default +7.7% at C4 and +9.7% at C6 on re-test, C1 flat, one arm contradictory (NNNtrance, raw not published) [Community-measured]; no effect on a TP2 decode (ai-muninn) [Community-measured]; all_gather 32 vs 64 channels 21.19 vs 19.36 GB/s (karol.spark) [Community-measured]. The own lanes already pin 8 through the graph file and `MAX_NCHANNELS`. Cost: an env line. Risk: noise misread as signal. Smallest falsifying experiment: ABBA channel A/B at C4 with at least 10 decode reps per arm.

7. **Shrink NCCL buffers** — applies to: triangles and wider groups with many connections x any engine. Gain: memory, not speed: 4.7 GiB -> 139 MB pinned host memory per node (MiaAI-Lab) [Community-measured]; own saving never isolated. No source measured a latency or bandwidth effect of `NCCL_BUFFSIZE` on GB10. Cost: an env block (`NCCL_BUFFSIZE=1 MiB`, `NCCL_LL128_BUFFSIZE=256 KiB`, `NCCL_PROTO=^LL128`, `NCCL_MAX_NCHANNELS=8`). Risk: unknown latency effect at prefill sizes. Smallest falsifying experiment: `Shmem` in `/proc/meminfo` before and after init, plus a 4 MiB and 32 MiB all-reduce at each setting.

8. **Let NCCL choose protocol and algorithm with correct numbers (Tree on three nodes; real per-channel bandwidth in the graph file)** — applies to: NCCL on the triangle x all models. Gain: [Proposed]. The model predicts a three-node LL floor of 16.8 µs for Tree against 26.6 µs for Ring [Code-verified]; the own ring graph declares 12 GB/s per channel x 8 channels = 96 GB/s modelled against 12.9 GB/s measured, which biases the LL/Simple switch points [Interpretation]. Cost: a graph edit or a no-graph boot with subnet-aware routing. Risk: the ring graph file was needed to pass init on the own fleet; Tree has never been tried there. Smallest falsifying experiment: a `NCCL_DEBUG_SUBSYS=TUNING` dump of the chosen protocol per size, then nccl-tests 8 B-1 MiB with `NCCL_ALGO=Ring` vs `Tree`.

9. **Shrink the lm_head gather** — applies to: vLLM x large-vocabulary models x TP. Gain: [Proposed]; the target's full-vocabulary all-gather is 12.6 MiB with 16-bit logits (≈17% of the own GLM lane's decode ring bytes at 64 rows; ≤30% only if fp32) [Interpretation]. The upstream local-argmax path covers greedy non-tree draft proposers only and is rejected with adaptive verification except for `dspark` [Code-verified]. Cost: fork work. Risk: sampling correctness. Smallest falsifying experiment: measure the all-gather's share in a per-rank timeline at C1 and C8 before writing code. See [Sampling and the lm_head](12-sampling-and-lm-head.md).

10. **`NCCL_PROTO=LL` with `NCCL_MAX_NCHANNELS=2` for eager decode** — applies to: two-node eager-mode recipes. Gain: none demonstrated; two recipes adopt it with no isolated A/B, and the one attempted channel trial was confounded by this setting (danielgbates forum 375607; tonyd2wild MiMo-V2.5 @ cfd8267; NNNtrance docs/10) [Community-measured]. Forcing LL also forces it onto prefill-size all-reduces, where the literature puts LL at 25-50% of bandwidth [Interpretation]. Cost: an env line. Risk: prefill regression. Smallest falsifying experiment: A/B on a battery that includes a 32K+ prefill, not decode only.

11. **Jumbo MTU 9000** — applies to: all. Gain: TCP +24% and zero retransmits on the own pair [Historical diagnostic]; upstream prefill +2.4% [Community-measured]; RDMA reaches line rate at RoCE MTU 1024 in NVIDIA's own example [Community-measured]. No RoCE MTU 1024 vs 4096 NCCL A/B exists. Keep it as harmless and TCP-positive, not as an NCCL speed lever. Cost: interface profiles on every node. Risk: a mismatched MTU on one side. Smallest falsifying experiment: `ping -M do -s 8972` both ways, then the same nccl-tests sweep at IB MTU 1024 and 4096.

Unavailable on GB10 multi-node, so not ranked: all-reduce + RMSNorm fusion, custom all-reduce, symmetric memory, async TP, NVLink-class overlap (§7).

## 6. Protocol

This is the protocol for measuring the collective floor and for A/B testing any NCCL or fabric change on a serving lane. It follows the fleet rules on the entry page and the incidents in §4 and §7. For kernel attribution see [Profiling protocol](14-profiling-protocol.md).

Preconditions.
- All index rules apply (see [the entry page](README.md)), in particular: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor measured after the longest qualified prefill, and traffic stopped below 4 GiB; a greedy logprob probe after every relaunch; discard the first request and warm every serving shape before timing; a unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection or configuration line read on every rank; at least 3 repetitions with a closing baseline (A/B/A); MemAvailable sampled every 1-2 s with zero NV_ERR_NO_MEMORY or Xid lines; no reboot or power cycle without per-node permission; correctness gates from [Quality and correctness gates](21-quality-and-correctness-gates.md) before any speed number. For this page: a fabric or protocol change (LL128 in particular, which NCCL warns can corrupt data) runs the greedy probe and the correctness gate before any speed arm; link bounces and firmware states that suggest a reboot or AC drain still need per-node permission.
- Clean window: no outside traffic, and the fabric is not shared with another job. nccl-tests owns the fabric while it runs; it needs a maintenance window, not a slot beside serving.
- No memory overcommit: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor while serving, and stop all test traffic when any node falls to 4 GiB MemAvailable. Memory on any one rank is a liveness condition for the whole group: a TP group is synchronous, and a triangle wedged when workers ran out of memory while the head waited in collectives (own 2026-09-16 DeepSeek V4.1 wedge).
- One variable per boot. NCCL reads its environment and binds devices at communicator init, so every arm is a restart. A restart for an A/B skips the image pull.
- Never restart a client gateway; restarting the lane's engine is the operator's step, and a gateway restart is the operator's decision. Never `pkill -f` a pattern that also matches your own shell.
- Same NCCL library on every node, and know which one the engine loads (a container's `NCCL_VERSION` can differ from the library actually preloaded; a pip install can silently downgrade NCCL, as when a FlashInfer nightly pulled 2.30.7 back to 2.29.7 and init failed on RoCE, capetron docs/05; mismatched libraries fail with `Message truncated: received 176 bytes instead of 172`).
- Launch all ranks from one command concurrently (a harness that launched ranks one after another produced false fabric failures, own 2026-09-14).
- Never use `echo 1 > /sys/bus/pci/rescan` as a probe (it hard-crashed a GB10, forum 374275 #2). Never bring an interface profile up with a connection manager on a port that is serving; add addresses with `ip addr add` and let the next engine start pick them up.

Link layer first (once per fabric change).
1. `ethtool` shows 200000Mb/s; `ibv_devinfo` shows `PORT_ACTIVE` and the expected `active_mtu`; every RDMA device you will name has a RoCE v2 IPv4 GID (a device with only IPv6 link-local GIDs is silently unusable, own 2026-08-30).
2. `ping -M do -s 8972` across every leg.
3. `ib_write_bw` per half and both halves concurrently (`-q 8 -s 1M -D 10`), and `ib_write_lat`. Expect ~109-112 Gb/s per half, ~196 Gb/s for both halves of one cable, ~2 µs write latency (§4). About 13 Gb/s on a 200G link means firmware or power state, not cabling.

NCCL floor.
4. One boot with `NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH,TUNING,ENV`: confirm `NET/IB` (not `NET/Socket`), the device list, `GDR 0`, the channel count, the protocol table, every non-default variable echoed as `set by environment`, and on a triangle the `Subnet-aware routing: overriding` lines. Warn-level logging hides the transport line (own 2026-08-20).
5. `all_reduce_perf -b 8 -e 64M -f 2 -g 1 -n 200 -w 50` with the exact serving environment and library, once eager and once with `-G 100`; add `all_gather_perf` and `sendrecv_perf`; write JSON with `-J`. nccl-tests reports all-reduce busbw = algbw x 2(n-1)/n and all-gather busbw = algbw x (n-1)/n (doc/PERFORMANCE.md @ b4d5bee). Vendor pass bars on `all_gather_perf -b 16G -e 16G`: 21.875 GB/s for a pair or switch, 10 GB/s for a three-node ring (spark_cluster_setup.py:53-54, 293 @ 3410c65; the pair bar was set on an NCCL 2.28.9 build).
6. Read the per-cable RDMA counters on every node after the run: bytes must appear on the cabled functions you expect and nowhere else (kernel IP forwarding can otherwise hide a wrong-NIC path).

Change. Exactly one of: one NCCL variable, the HCA list, the graph file, an address plan, MTU, or TP width. Keep the graph file consistent with `NCCL_CROSS_NIC` (a `crossnic=1` graph is silently dropped when `NCCL_CROSS_NIC=0`). On a triangle copy the whole proven NCCL block (ring graph per rank, `NCCL_ALGO=Ring`, `NCCL_CROSS_NIC=1`, `NCCL_IB_SUBNET_AWARE_ROUTING=1`, `NCCL_IB_MERGE_NICS=0`, `NCCL_NET_MERGE_LEVEL=LOC`, `NCCL_CUMEM_ENABLE=1`) and change one line; a subset fails init (own 2026-09-16). Pin RoCE GIDs per rank and check each is populated after every reboot, or leave `NCCL_IB_GID_INDEX` unset and let the auto path pick the IPv4 RoCE v2 entry.

Serving A/B.
7. Arms in ABBA order. Per arm: at least 10 decode-only reps at C1, the concurrency the lane serves (C4 or C8), and one cold 32K+ prefill. Identical clock settings on every rank. Record a per-rank single-GPU probe (a GEMV bandwidth check) before each arm to exclude a slow-rank state.
8. Profiled runs are for attribution only and are never scored (profiling moved TTFT 23.8 -> 35.96 s, own 2026-09-16).

Record (packet fields): NCCL library version as logged, engine commit and image, the one variable and both values, full NCCL env, HCA list, graph file hash, topology and address plan, MTU, firmware and kernel per node, the INFO excerpt (transport, devices, GDR, channels, protocol table, env echo), link-layer numbers, nccl-tests JSON per size (eager and graph), per-cable counters, per-rank probe results, serving numbers per arm with rep spread, minimum MemAvailable per node, NCCL `Shmem` per node, and any discarded arm with its reason.

Pass gate. Init passes on every rank; the INFO log shows the variable took effect; nccl-tests is at or better than baseline at the sizes the change targets and not worse elsewhere beyond run-to-run spread; decode at C1 inside the baseline spread or better; prefill at or above baseline; no new NCCL warnings; minimum MemAvailable at or above the 5 GiB warm floor on every node; counters show traffic on the intended functions.

Rollback. Restore the previous environment file (keep a dated backup beside it), restart with the pull skipped, confirm the INFO excerpt matches the baseline boot, and run one nccl-tests small-size check plus one cold decode fixture; both must match the baseline before the lane serves again. If a rank dies mid-flight, poll the engine's health endpoint rather than container status (a dead rank can leave containers "up"), and expect NCCL abort timeouts to be long.

## 7. Anti-patterns and known-bad

- [Code-verified] Collective fusion and hiding on GB10 multi-node. All-reduce + RMSNorm fusion, FlashInfer all-reduce, custom all-reduce, torch symmetric memory, NCCL symmetric kernels and async TP are disabled by capability tables or by the lack of NVLink multicast in vLLM and SGLang; SP is not auto-applied on SM121 and doubles op count if forced (§2). Overlap work is NVLink-era: TokenWeave reports ~20% TP overhead even on NVLink and notes overlap is off by default in vLLM, SGLang and TRT-LLM (arXiv 2505.11329); Flux evaluates 8-GPU nodes only (arXiv 2406.06858); Ladder-residual needs a retrained model (arXiv 2501.06589).
- [Community-measured] `NCCL_TOPO_FILE` to lift the "PCIe Gen1 x1" cap: the plan changed, the measurement did not (1.19 -> 1.29 GB/s); the real fault was the bundled network plugin falling back to TCP (forum 366266).
- [Community-measured] A second cable to the same peer for bandwidth: no gain; can cap at 100 Gb/s with the two-node playbook (forums 366266 #7, 362403 #3).
- [Community-measured] NCCL over TCP or the management network: 1.88x slower serving (forum 366325), 1.19 GB/s all_gather (forum 366266), a dense 27B at TP4 over 10 GbE slower than one node (capetron docs/02). A container without `/dev/infiniband` silently falls back to `NET/Socket` (forum 377290).
- [Community-measured] QSFP addresses in the mpirun host list: 2.86 GB/s all_gather instead of ~20 (forum 365160 #7). Bootstrap belongs on the management NIC; NVIDIA staff say the socket variables are bootstrap only (forum 365160 #2).
- [Measured] Half a port for weeks: the pair named one of the two controllers behind the port; the other had only IPv6 link-local GIDs, so NCCL never used it and nothing warned (own 2026-08-30 dual-HCA fabric enablement).
- [Historical diagnostic] Counting network interfaces as cables: one cable was recorded as two, and "the second rail needs a cable" was concluded; both wrong. Map controllers to cables by traffic counters.
- [Measured] One shared GID index across ranks: a reboot renumbered RoCE GIDs, and the old shared index pointed at an all-zero entry that would kill a rank about 60 s into load.
- [Measured] Triangle legs without the full routing fix: `ibv_modify_qp` error 110 at init on a leg whose same-index peer port has no cable; NCCL's automatic device selection tried unreachable subnet pairs. Any `ibv_modify_qp ... 110` at init is a stop (own 2026-09-14, 2026-09-16).
- [Historical diagnostic] Warn-level NCCL logging on a fabric change: the transport line was suppressed, so RoCE vs sockets could not be proven afterwards.
- [Measured] "Containers up" as health: a mid-flight rank death left every container running with the engine dead; poll the API.
- [Measured] Reading a mixed-collective preflight bundle as per-op latency: the three sizes do not fit one latency-plus-bandwidth line.
- [Interpretation] Multiplying the standalone collective floor by the count to get the step tax: it gives about half the in-engine figure (§4).
- [Code-verified] Trusting recipe comments on where the draft model runs: a comment said "rank 0 only"; the source builds the drafter TP-sharded on every rank, adding about 11 collectives per step and no draft broadcast. A per-rank shape dump is still owed to confirm it at run time (see [Speculative decoding](02-speculative-decoding.md)).
- [Measured] Scoring profiled runs (TTFT 23.8 -> 35.96 s under the profiler); a rank skew seen in the trace did not persist unprofiled.
- [Measured] A TP comparison without a validated control: an early "one node 49% faster than TP2" was withdrawn after the control arm's lm_head scale was found dropped (own 2026-08-19).
- [Community-measured] Plain TP3 without EP on DeepSeek V4 Flash: ~11 tok/s and ~2.1M KV against ~81 tok/s at TP2 (FlyCockpit); that arm ran socket transport with MTP 0, and with the mesh fabric and MTP 5 no-EP matched EP on speed, so it is not a verdict on TP3 without EP (see the ledger's anti-pattern 187). Wider TP on a small-active MoE that fits: 99.0 -> 89.2 tok/s (forum 377871). TP6 on Qwen3.8 Flash Next: "16 is not divisible by 6" even with EP (capetron docs/05).
- [Community-measured] Padding when heads do not divide by three: DeepSeek V4 Flash TP3 pads 8 -> 9 attention output groups (heads 64 -> 72, +12.5%), keeping 8 heads per group because padding inside a group breaks the output-projection contract DeepGEMM checks, and pad lanes need `-inf` sinks (localaiguyy @ 496c6a1; MiaAI-Lab TP3.md); MiniMax-M3 TP3 uses a vLLM commit described secondhand as padding heads 64 -> 96 and KV heads 4 -> 6 (forum 372123; commit not opened). No source timed the pad cost.
- [Community-measured] EP=4 against EP=1 at TP4 in SGLang: EP loses 3-7% (ht12, forum 366325 #3). "EP beats TP" is not a default on Sparks.
- [Community-measured] Reboot recipes that tell you to rescan the PCIe bus: `echo 1 > /sys/bus/pci/rescan` hard-crashed a GB10 (forum 374275 #2). The NVIDIA staff workaround for the hotplug driver dropping CX-7 devices is to remove `/etc/nvidia/cx7-hotplug-enabled` and reboot (forum 362667 #9, quoted in 371031 #7).
- [Code-verified] Contested advice where source wins: `NCCL_IB_MERGE_NICS=1` called "critical" for a one-cable pair is the default and does not merge the twins (topo.cc multi-port rule); the effective change in those threads was listing and addressing both twins. `NCCL_IB_QPS_PER_CONNECTION` "defaults to 4" (karol.spark) is 1 in every checked tag. `NCCL_IB_SUBNET_PREFIX_LEN` "defaults to /16" (MiaAI-Lab TP3.md) is 24 in source. "The f0 functions are the ASIC's unconnected second port" (neko-legends FABRIC @ b46eabc) contradicts NVIDIA's port map and every concurrent both-halves measurement; that note's "rail A vs rail B" A/B compared the two twins of one cage, and its "~104 Gb/s is a single-QP artifact" is contradicted by 111.86 Gb/s on one half with `-q 8`. "TP=3 is impossible on DeepSeek V4 Flash" (tonyd2wild TP4 README) is stale; group padding works.
- [Community-measured] "DMA-BUF GDR works on DGX Spark OS 7.5+" (ArgentAIOS docs/04 @ ee11bb3) shows a "look for this in the output" template with a generic HCA, not a captured GB10 log; NVIDIA staff and every captured log say GDR is off.
- [Community-measured] camerono's "an sm_121 rebuild is required for correctness": their own table shows 11.5 -> 11.5 GB/s from the rebuild alone at 1 GB; the rebuild is still NVIDIA's documented procedure (NCCL `v2.30.7-1` with `compute_121`).

## 8. Open questions

- Ring vs Tree on three nodes for small messages (the model predicts Tree lower) — nccl-tests `all_reduce_perf -b 8 -e 1M` with `NCCL_ALGO=Ring` vs `Tree` on the triangle, eager and `-G`, same library.
- LL vs LL128 vs Simple on GB10, including whether LL128 is numerically safe over the host-staged C2C path — `NCCL_PROTO` A/B across 8 B-64 MiB plus a checksum pass; no GB10 A/B exists.
- Latency effect of `NCCL_BUFFSIZE` and `NCCL_LL128_BUFFSIZE` — the same sweep at default and shrunk buffers, with `Shmem` recorded.
- RoCE MTU 1024 vs 4096 for NCCL — nccl-tests sweep at each IB MTU; only TCP and ib_write_bw evidence exists.
- Both cages active at once on a triangle node (NVIDIA: "each CX7 port provides full 200GbE"; users: each drops to 100 Gb/s, unmeasured; a reseller's four-path ~196 Gb/s total is secondhand, the original returned HTTP 403) — `ib_write_bw -b` on both legs of one node concurrently, then a triangle all-reduce.
- Simultaneous bidirectional NCCL throughput on GB10 — nccl-tests `sendrecv_perf` in both directions at once with per-direction counters.
- The twins on triangle legs through NCCL's own IB path (the community result used a patched plugin) — address the domain-2 functions per leg, list all HCAs, graph channels alternating start devices; nccl-tests at 16/64 MiB, then a serving A/B.
- The true NCCL share of a decode step on the own lanes (dossier band 4-10 ms vs community 13-16 ms) — a per-rank step timeline with collective start and end times at C1 and C8, unprofiled wall time alongside.
- Whether the inflated per-channel bandwidth in the own ring graph changes protocol choice at 61 KB-class and MiB-class sizes — `NCCL_DEBUG_SUBSYS=TUNING` dump, then the graph's `speedinter` set to the measured value.
- Cost of host staging (no GDR) inside the small-message latency — compare `ib_write_lat` (2 µs) and nccl-tests 8 B latency on the same pair with a host-buffer NCCL microbenchmark; none found.
- Whether `NCCL_NET=Mesh` (plugin) and built-in subnet-aware routing differ on the same triangle — nccl-tests sweep with each, same HCA set.
- Whether a lane's forked vLLM commit changes upstream behaviour for logits gather, fusion gates or the `dspark` exemption — read the fork at its commit; the upstream lines in §2 may not apply.
- Why a two-node EXL3 user sees about 2x the lab's per-step time (issue #163) — per-rank timeline and INFO log from that setup; no reply yet.
- llama.cpp `--split-mode tensor` across RPC nodes, and ds4 two-Spark TP throughput — any measured tok/s with a stated protocol; none published.
- Any internode all-to-all EP backend on GB10 (DeepEP, NVSHMEM, NIXL, Mooncake) — a first functional run; DeepEP's internode mode requires GPUDirect RDMA and IBGDA, so a host-staged backend is the likely candidate.
- A second rail on one own node reported dark with no explanation (the hotplug driver is a candidate on the same kernel) — `dmesg` for `Cable removal` and device removal within a minute of boot, and presence of the hotplug marker file, in a window where a reboot is permitted.
- Whether decode on the own TP lanes is clock-sensitive (TP2 read -6.8% as real; TP3 read -5.8% of means as inside spread; see [Clocks, thermal, and power](13-clocks-thermal-power.md)) — a 10-rep decode-only ABBA A/B at stock vs the capped clock on all ranks.
- Pad cost on TP3 (head and KV-head padding) — a timed per-layer attention component with and without padding; no source timed it.
- The single-source community notes kept out of §4 — a "~1 MB and ~2 ms per step" TP4 decode estimate and a "second IPv4 on the NCCL interface cost ~30% of C1 decode (103.4 -> 136.25 tok/s after cleanup)" finding (neko-legends FABRIC, method unstated), and a "22 µs RoCE vs 424 µs TCP" pair with no message size (r0b0tlab) — each needs a stated protocol to use.
- The fleet firmware update that promised to fix "~35% lower NCCL bandwidth" was never re-measured against the pre-update 110 Gbit/s TCP figure — repeat the iperf3 and ib_write_bw checks at the current firmware.
