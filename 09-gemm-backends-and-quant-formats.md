# GEMM backends and quantization formats on SM121

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 48 SMs, 128 GB unified LPDDR5x, 273 GB/s nominal), one to three nodes (node-1, node-2, node-3) over direct-cabled ConnectX-7 RoCE. Since the 2026-09-21 clock-cap change all three nodes run a 2,100 MHz GPU clock cap, for heat and throttling, not speed (about 5% cold prefill; C1 decode means 5-6% lower, inside rep spread, on the own TP3 lane; the owner statement and per-lane qualification rule are on [Clocks, thermal, and power](13-clocks-thermal-power.md)); earlier packets ran at stock clocks, so GEMM rates are not comparable across that date without saying so. Own measurements are cited by evidence-packet date and title. Code lines are quoted at these pins: vLLM `711fc55c`, SGLang `2909f84e` (main) and `da64c5cb` (the build a DeepSeek V4.1 lane ran), FlashInfer `06aa49c1`, CUTLASS `0b55a2f6`, DeepGEMM `78b69000` (main) and `a23e1f08` (`nv_dev`), llama.cpp `6e60f356`, ExLlamaV3 `6b84a21b`, b12x `2fca4df8`, and the DeepSeek-V4 C/CUDA engine (antirez/ds4) at the commits named in §2. The own lanes run older builds (a GLM 5.3 Flash lane on vLLM `487ecf187`, a Qwen 3.8 Flash Next lane on vLLM `8e685d198`), so a code line says what upstream does now, not what a given lane runs. Formats in scope: block FP8 (128×128 or 32×32 blocks, FP32 or UE8M0 scales), per-tensor and per-channel FP8, MXFP8, NVFP4 (W4A4 and weight-only W4A16), MXFP4, EXL3 trellis codes, and GGUF K-, I- and legacy quants.

## 1. What it is

A GEMM (general matrix multiply) is the weight-times-activation math that takes most of a language model's GPU time, and on a GB10 the format the weights are stored in decides which GEMM program runs. The GB10's tensor cores multiply FP8 and 4-bit floats natively through warp-level `mma.sync` instructions (per-warp tensor-core ops), but the chip has no `tcgen05` path (datacenter Blackwell tensor instructions), only 99 KB of shared memory per block, and a memory bus that, not the math units, limits speed when only a few tokens are in flight. Each engine therefore walks an ordered list of candidate kernels per format and takes the first whose compute-capability and shape checks pass. Small differences in those checks send the same checkpoint to a fast native kernel, to Marlin (unpack-weights-on-the-fly kernel), to a slow Triton (Python GPU compiler) fallback, or to a path that returns wrong answers without any error. Two regimes decide the right choice. At decode, with 1 to about 64 rows per step, fewer weight bytes win, so weight-only kernels such as Marlin match or beat native FP4 and FP8 math. At prefill, with hundreds to thousands of rows, arithmetic wins, and a plain BF16 GEMM or a native low-precision kernel can be two to three times faster than Marlin on the same layer. Format is also a quality choice: the fastest format measured on this fleet (2-bit EXL3 experts) failed agent-loop and retrieval gates, and several community lanes on this chip shipped kernels that were fast and wrong. This page records which kernel each engine picks on SM121, what has been measured, and how to change a format or backend safely. See also [Engine dispatch maps](16-engine-dispatch-maps.md), [MoE dispatch](08-moe-dispatch.md), [SM121 hardware facts](17-sm121-hardware-facts.md) and [Quality and correctness gates](21-quality-and-correctness-gates.md).

## 2. How each engine does it

Shared kernel libraries (used by several engines; grades apply per line).

- CUTLASS warp-level atoms for SM120/121 (`include/cute/arch/mma_sm120.hpp` @ `0b55a2f6`): FP8/FP6/FP4 without block scale `mma.sync.aligned.kind::f8f6f4.m16n8k32` (lines 45-70, 670-690); MXFP8/MXFP6 and byte-padded FP4 with UE8M0 scales per 32 `kind::mxf8f6f4.block_scale.scale_vec::1X.m16n8k32` (1761-1809); MXFP4, UE8M0 per 32, `kind::mxf4nvf4.block_scale.scale_vec::2X.m16n8k64` (3107-3159); NVFP4, UE4M3 per 16, `scale_vec::4X.m16n8k64` (3187-3216); plus a 4X UE8M0 variant (3137). [Code-verified] NVFP4 and MXFP4 use the same packed m16n8k64 instruction and differ in scale type and scale-vector width; NVFP4 also carries a per-tensor FP32 global scale that kernels fold into alpha. [Interpretation]
- Issue rate. A register-resident probe on GB10 (`sm_121a`, CUDA 13.0) measured packed `kind::mxf4nvf4` at about 511 TFLOPS dense (102% of the 500 spec), about 1,014-1,022 TFLOPS 2:4-sparse, and FP4 fed through the byte-padded `kind::mxf8f6f4` atom at about 256 TFLOPS (NVIDIA developer forum thread 373618, adg1). [Community-measured] These are instruction issue rates with no memory traffic, not GEMM throughput. A kernel that feeds FP4 through the f8f6f4 atom gives up half the FP4 issue rate, so which atom a kernel uses matters more than the format label. [Interpretation]
- Architecture enables. CUTLASS defines `tcgen05` enables only for SM100/101/103/107/110; SM121 gets `SM121_ENABLED`/`SM121A_ENABLED` for the warp-level atoms, and the MXF4NVF4 4X-UE8M0 variant needs nvcc 13.1+ (`include/cute/arch/config.hpp:162-180`). [Code-verified] Dense `mxf4nvf4`/`mxf4` are in the `120f` family target; only sparse `mma.sp` FP4 needs `sm_120a`/`sm_121a` (FlashInfer issue #3170, corrected 2026-06-12). [Community-measured]
- Shared memory. `sm120_smem_capacity_bytes = 101376` (`include/cutlass/arch/arch.h:47`) and CuTe-DSL maps both `sm_120` and `sm_121` to 99 KiB (`python/CuTeDSL/cutlass/cutlass_dsl/cutlass.py:170-172`). [Code-verified] A CUTLASS contributor states SM120 and SM121 both have 99 KiB and that the FP4 MoE tile carve-out fix is in CUTLASS 4.4.2 (CUTLASS issue #3144, closed; the issue title's "SM120 228 KiB" is wrong). [Community-measured]
- CuTe-DSL arch whitelist (the "CUTLASS SM121 MMA guard"). This was the Python whitelist, not the C++ atoms: vLLM PR #40082 (merged 2026-05-20) patched `cute/nvgpu/warp/mma.py` to accept `sm_121a` and pinned `nvidia-cutlass-dsl==4.4.2` because "4.5.0 generates bad PTX for SM121"; at `0b55a2f6` the warp block-scaled ops list `sm_120a, sm_120f, sm_121a, sm_121f` as admissible (`python/CuTeDSL/cutlass/cute/nvgpu/warp/mma.py:445-450`). [Code-verified] cutlass-dsl 4.5.1 fixed the 4.5.0 PTX bug (CUTLASS #3227, per ai-muninn, 2026-05-30). [Community-measured]
- FlashInfer. `mm_fp4` auto on SM 12.0 with CUDA ≥ 12.9 prefers b12x → cutlass → cuDNN; "SM121 (GB10) is intentionally excluded from automatic selection because cutlass/cudnn are faster in most cases; b12x remains explicitly selectable" (`flashinfer/gemm/gemm_base.py:8446-8465`); `_b12x_gemm_fp4_requirement` needs K % 32 == 0 and the 128×4 scale layout (`:7435-7470`). A maintainer confirmed in PR #3113 (merged 2026-04-20) that leaving SM121 out of auto was intentional. [Code-verified] JIT: SM 12.1 keeps its minor on CUDA ≥ 12.9 and builds `compute_121a` (`flashinfer/compilation_context.py:85-110`). A dedicated `sm121a` FP4-quantization module exists (`jit/fp4_quantization.py:97-98`), but `get_fp4_quantization_module` remaps backend 121 to the `120f` family module whenever torch CUDA ≥ 12.9 (`quantization/fp4_quantization.py:248-256`), so the module GB10 runs is the `120f` build. [Code-verified]
- b12x. A separate CuTe-DSL and Triton kernel library "for SM120/SM121" (PyPI `b12x` 1.3.0, "DGX Spark and RTX 6000-focused"; source @ `2fca4df8`), with warp-level MMA and 16- or 32-row tiles. [Code-verified] It is reached through vLLM kernel classes, FlashInfer's `mm_fp4`/MXFP8 paths, and recipe adapters (below). No public kernel-level b12x vs CUTLASS vs Triton timing on GB10 exists beyond one author's step profile (§4). [Interpretation]
- DeepGEMM. `main` @ `78b69000` has no `arch_major == 12` branch in `csrc/`; `nv_dev` @ `a23e1f08` has about 40 in 7 files (dense FP8/FP4, M-grouped, K-grouped, einsum, MQA logits, scale layouts), e.g. `csrc/apis/gemm.hpp:290-300` sends SM12x grouped FP8/FP4 to `sm120_m_grouped_fp8_fp4_gemm_contiguous_1d1d`. The SM120 kernels entered `nv_dev` through PR #324 (merged 2026-06-24) and were rebased by PR #447 (merged 2026-09-23), whose validation section says it is "not … a SM121 … claim". PR #318 is open and unmerged. [Code-verified]
- cuBLAS and cuBLASLt. Tensor Core "most performance" conditions are 16-byte multiples for leading dimensions, `m * CtypeSize`, `ld × typeSize` and every pointer; outside FP8 alignment is a performance condition, not a requirement. Tensor- or block-scaled FP8 kernels require those alignments and the TN layout on "Blackwell GeForce (compute capability 12.x)". `CUBLASLT_LOG_LEVEL=4` or the Info bit (8) of `CUBLASLT_LOG_MASK` logs heuristic status (cuBLAS docs §2.1.11, §3.1.3, fetched 2026-09-23). [Code-verified] The CUDA 13.x release notes name DGX Spark in four cuBLAS items: 13.0 Update 2 "improved performance on NVIDIA DGX Spark for FP16/BF16 and FP8 GEMMs"; 13.1 CFP32; 13.2 "up to 3× performance improvement for selected matrix shapes" for MXFP8 and NVFP4 at large M and N, plus a fixed illegal access in BF16/FP16 GEMM on DGX Spark; and 13.2 Update 2 known issues (out-of-bounds reads for small broadcast operands on sm_120/121; alpha/beta read before `cudaGridDependencySynchronize()`). Experimental cuBLASLt grouped GEMM (MXFP8, NVFP4) is listed only for CC 10.x and 11.0. No before/after TFLOPS are published (CUDA 13.2 Update 2 release-notes archive, fetched 2026-09-23). The cuBLAS inside an engine's PyTorch wheel, not the host toolkit, decides which of these a lane has. [Interpretation]
- TensorRT-LLM (status only). SM121 routes with SM120 in the FP4 GEMM template; SM120 tiles overflowed 99 KiB until the CUTLASS 4.4.2 carve-out fixes (TensorRT-LLM #11368, closed; CUTLASS #3144, closed); a 1.3.0rc5 image failed with `ptxas fatal: Value 'sm_121a' is not defined` (forum 366006, April 2026). No current GB10 TensorRT-LLM GEMM benchmark was found. [Community-measured]

### vLLM

Selection mechanism. Dense linears walk a per-method kernel list; each kernel has `is_supported(capability)` and `can_implement(config)`, and the first that passes both wins. Overrides are `VLLM_DISABLED_KERNELS`, `--linear-backend` and `linear_backend_per_quant` (`vllm/model_executor/kernels/linear/__init__.py:357-403, 606-690`). Every choice is logged as `Selected <Kernel> for <method>` (dense, `:727`) or `Using '<BACKEND>' … MoE backend out of potential backends: [...]` (MoE). The old `VLLM_NVFP4_GEMM_BACKEND` is gone; vLLM 0.24.0 warns "Unknown vLLM environment variable" and ignores it (issue #43507 comment). [Code-verified]

Block FP8, dense.
- A checkpoint with `weight_block_size = [bn, bk]` builds an activation key of group shape `(1, bn)` and a weight key `(bn, bk)` (`quantization/fp8.py:278-284`). The CUDA list is FlashInfer-plus-DeepGEMM dynamic, DeepGEMM, CUTLASS blockwise, B12X, Marlin FP8 (weight-only), Humming, Triton, torch blockwise (`kernels/linear/__init__.py:455-475`). [Code-verified]
- DeepGEMM passes on GB10: `support_deep_gemm()` accepts the whole 120 family (`vllm/platforms/cuda.py:719-725`), `VLLM_USE_DEEP_GEMM` defaults to 1, and the `deep_gemm` package must be installed (`vllm/utils/deep_gemm.py:110-116`); it needs `(1,128)` activation groups. [Code-verified] Default on CC 12.1: DeepGEMM if the package is installed; see the known-bad items in §7.
- CUTLASS blockwise: `cutlass_scaled_mm_supports_block_fp8` is true for capability ≥ 100 with CUDA ≥ 12.8 (`csrc/libtorch_stable/quantization/w8a8/cutlass/scaled_mm_entry.cu:161-173`). The SM120 kernel hard-codes a (1, 128, 128) scale granularity and picks its tile by M: M ≤ 64 swaps A/B and runs 128×32×128, 64 < M ≤ 256 a 64×128×128 ping-pong tile, above that 128×128×128 (`c3x/scaled_mm_blockwise_sm120_fp8_dispatch.cuh:139-172, 255-280`); the wrapper's `enable_sm120_family` (`__CUDA_ARCH__` 1200-1299) admits 12.1 (`cutlass_extensions/common.hpp:130-142`). [Code-verified] Default on CC 12.1 with `VLLM_USE_DEEP_GEMM=0`: CUTLASS SM120 blockwise.
- B12X block FP8: 120 family, the `b12x` package (optional extra `b12x==1.3.0`, `setup.py:1550`), `(1,128)` activations, exactly 128×128 blocks, N and K multiples of 128 (`scaled_mm/b12x.py:49-98`). [Code-verified]
- Non-128 blocks. DeepGEMM, CUTLASS and B12X test the activation group `(1, block_n)`, so they reject a block whose N side is not 128 (for square 32×32 or 64×64 blocks the same as block_k). Marlin's `can_implement` accepts every config and sits ahead of Triton, so a non-128 block lands on weight-only Marlin, not Triton, unless Marlin is disabled (`VLLM_DISABLED_KERNELS=MarlinFP8ScaledMMLinearKernel`, `--linear-backend triton`, or batch-invariant mode). Marlin treats only `kFp8Static128BlockSym` as block layout; for any other block shape it skips block processing and sets `size_k_first=True` under the comment "Non-block: callers must pass weight in (K, N) layout" (`scaled_mm/marlin.py:56-73`). [Code-verified] A non-128-block checkpoint that reaches Marlin is a correctness risk until tested (§8). [Interpretation] The rule "non-128 blocks go to Triton" is true of SGLang, not of current vLLM.
- Per-tensor and per-channel FP8, dense: FlashInfer FP8 (needs ≥ 100) → CUTLASS FP8 → B12X tensor FP8 → torch → Marlin (`__init__.py:420-431`). [Code-verified]

FP8 MoE. List: AITER, FLASHINFER_TRTLLM, FLASHINFER_CUTLASS, DEEPGEMM, VLLM_CUTLASS, TRITON, MARLIN, … (`fused_moe/oracle/fp8.py:84-100`). VLLM_CUTLASS cannot be chosen on 12.x: the Python gate is false for capability ≥ 110 (`vllm/_custom_ops.py:851-858`), `cutlass_group_gemm_supported` reports only SM90 and SM100-119 (`scaled_mm_entry.cu:176-195`), and there is no `grouped_mm_c3x_sm120.cu`. DeepGEMM MoE experts accept families 100 and 120. [Code-verified] Default on CC 12.1: DeepGEMM for 128-block FP8 when installed, otherwise Triton; tensor/token-scaled FP8 MoE logs `Using TRITON Fp8 MoE backend` (issue #43507, open). [Community-measured] Open PR #43814 adds an SM120 grouped path (§4) and needs CUTLASS PR #3280, not yet in a CUTLASS release. [Code-verified]

MXFP8. Dense: FlashInfer CUTLASS MXFP8 (capability ≥ 100) → Marlin → B12X (`__init__.py:529-538`); small or unaligned shapes are asserts, not gates, which open PR #54223 would turn into `can_implement` checks (N ≥ 128, K ≥ 128, K % 32 == 0, N % 32 == 0 on SM12x). MoE: the oracle lists TRTLLM (100 family), DeepGEMM and Marlin (`oracle/mxfp8.py:18-31`), so GB10 lands on Marlin W8A16 (issue #43906, open) unless open FlashInfer PR #3463's native grouped kernel is present. [Code-verified]

NVFP4, dense. CUDA order: FlashInfer CuTe-DSL (100 family only) → FlashInfer CUTLASS → FlashInfer b12x (needs `has_flashinfer_b12x_gemm`) → vLLM CUTLASS → FlashInfer CuTe-DSL W4A16 (accepts sm_12x) → Marlin → … (`__init__.py:551-571`). FlashInfer CUTLASS needs `cutlass_fp4_supported()` (the SM12x NVFP4 kernel compiled in, CUDA runtime ≥ 12.8; `nvfp4_scaled_mm_entry.cu:71-85`), capability ≥ 100 and FlashInfer (`nvfp4/flashinfer.py:184-197`). A `W4A16_NVFP4` (weight-only) checkpoint lands on Marlin for linear because `init_nvfp4_linear_kernel` forces `MarlinNvFp4LinearKernel` on any device other than SM100/103 (`__init__.py:1115-1126`). A W4A4 checkpoint reaches Marlin only if FlashInfer CUTLASS, FlashInfer b12x, vLLM CUTLASS and CuTe-DSL W4A16 all fail their gates (for example a build without `ENABLE_NVFP4_SM120` and an older FlashInfer). [Code-verified] Default on CC 12.1 for W4A4: FlashInfer CUTLASS, if the build carries SM12x NVFP4 kernels.

NVFP4 MoE. Auto order: FLASHINFER_TRTLLM, FLASHINFER_CUTEDSL, FLASHINFER_CUTEDSL_BATCHED, FLASHINFER_CUTLASS, VLLM_CUTLASS, MARLIN, HUMMING, EMULATION. FLASHINFER_B12X is excluded from auto "until the upstream CUTLASS SM121 MMA op guard is resolved"; `moe_backend="flashinfer_b12x"` opts in (`fused_moe/oracle/nvfp4.py:188-201`). The newer direct `B12X` backend is also not in auto; open PRs #54669 (39/39 SM121 selection and correctness tests, a 100-file, 524-tool-call stress with no illegal-memory access) and #54719 would add it. W4A4 MoE backends reject a missing activation key, so a W4A16 checkpoint's MoE also goes to Marlin (`quantization/modelopt.py:836-846`). [Code-verified] Default on CC 12.1: FlashInfer CUTLASS for W4A4.

MXFP4 MoE. For GPT-OSS, `_get_priority_backends_for_gpt_oss` includes Triton and FlashInfer CUTLASS before Marlin (`oracle/mxfp4.py:345-363`). For DeepSeek-V4 and generic models the CUDA auto order is FLASHINFER_TRTLLM_MXFP4_MXFP8 → DEEPGEMM_MXFP4 → MARLIN → BATCHED_MARLIN (`:367-390`; `select_deepseek_v4_mxfp4_moe_backend`, `:657-727`), so GB10 selects DeepGEMM MXFP4 when DeepGEMM is installed. First-class `B12X_MXFP4_*` backends are upstream and opt-in with `moe_backend="b12x"`. [Code-verified]

Marlin FP8 is weight-only. `apply_fp8_marlin_linear` raises for FP8 activations ("Marlin W8A8 is not supported") and runs `marlin_gemm` with BF16/FP16 activations (`quantization/utils/marlin_utils_fp8.py:60-100`). Marlin's FP8 `mma.sync … m16n8k32 … e4m3` code generation is only for its FP8-activation W4A8 variants on SM89 and SM12x (`csrc/libtorch_stable/quantization/marlin/generate_kernels.py:11-27`). Padded N is un-padded with a real slice copy; a code comment proposes writing unpadded columns directly instead (`marlin_utils.py:293-305`). FlashInfer CUTLASS NVFP4 pads weights to 32 (`pad_nvfp4_weight_for_cutlass(alignment=32)`, `nvfp4_utils.py:61-63`). [Code-verified] Marlin prints "GPU does not have native support for FP4/FP8" on GB10; open PR #48199 says the message is misleading on SM100/SM12x. [Code-verified]

Build targets. NVFP4 SM12x kernels build for `12.0f` on CUDA ≥ 13 and `12.0a;12.1a` below, defining `ENABLE_NVFP4_SM120` and `ENABLE_CUTLASS_MOE_SM120` (`CMakeLists.txt:988-1012`); Marlin builds `8.0+PTX;12.0f` (CUDA ≥ 13) or `…;12.0a;12.1a` (`:610-636`); SM120 scaled-mm `12.0f` or `12.0a;12.1a` (`:816-822`). [Code-verified] Open PR #38484 says published wheels never passed 12.1 in the arch list; a maintainer replied that on CUDA 13 a 12.0 target becomes a `12.0f` family cubin that runs natively on 12.1, and a GB10 A/B in the same thread (vLLM 0.27.1, Qwen3.5-122B-A10B-NVFP4, FlashInfer CUTLASS MoE) measured 16.4 vs 16.3 tok/s for the published image vs an sm_121 build. [Community-measured] The native target matters for the CUTLASS FP8 block path built for `120a` under CUDA 12.9 (§7). Vendored Marlin before PR #40923 (native SM12x Marlin cubins) ran JIT from `8.0+PTX`, which "produces silently-wrong outputs on Marlin-MoE" per a GB10 user in the #40082 thread. [Community-measured]

DeepGEMM in vLLM on GB10. Three separable upstream facts explain why one build refuses DeepGEMM and another uses it. [Community-measured] (1) vLLM issue #54125 (GB10, the `8e685d198` preview build): DeepGEMM was selected for a block-FP8 linear and crashed in `profile_run`; a second GB10 user traced it to an attribute-name mismatch that skipped UE8M0 repacking, fixed by commit `f8e0602713` (2026-08-21); the reporter then showed DeepGEMM's E8M0 variant is selected on SM121 for checkpoints with plain FP32 scales. (2) Same thread: DeepGEMM block-FP8 silently corrupts at K = 2560 (§4). (3) DeepGEMM issue #417 (open): `nv_dev` `8b1392b` routed FP8×FP8 through the FP4 kernel on SM12x; a vLLM PR to pin `a6b593d` (#53680) was closed unmerged and one community image froze `a6b593d`; on `vllm-project/DeepGEMM@ad1f1726` the dtype-driven dispatch (described as the #447 design) gave exact FP8 results at 1×128×256 and 7×512×4096, an FP32 scale with `disable_ue8m0_cast=True` was misread as UE8M0 there, and a later guard (`f9d0e2361`) rejects it; whether #447 carries that guard is unconfirmed. DeepGEMM issue #372 (NVFP4 expert-scale layout without an arch-12 branch) is fixed on `nv_dev` per the #447 author; issue #425 (`paged_mqa_logits` varlen illegal access on sm121a) is open. Open vLLM PRs at 2026-09-23: #54600 (head `7cecd54e`, titled "Exclude SM121 from DeepGEMM support", filed as a fix for #54125 before the reporter's retraction; the thread also reports unmodified DeepGEMM passing all 984 warm-up kernels and that excluding sm_121 breaks `profile_run`, see [SM121 hardware facts](17-sm121-hardware-facts.md)), #57512 (do not select DeepGEMM with FP32 scales on SM12x), #58157 (warn on FP32→UE8M0 requantization). [Code-verified] The DeepGEMM "unsafe" message in an own vLLM 0.24.0 log was the model-type auto-disable for that Qwen architecture plus a JIT recipe miss, not a GPU-arch statement. [Historical diagnostic]

Community forks. The Anemll DeepSeek V4 Flash port (`Anemll/dspark-vllm-gx10` @ `081fda97`) is a vLLM 0.25 DSpark port for two GB10s, not a llama.cpp fork; it adds a b12x native-MXFP4 MoE backend (b12x pinned `7dc6fb8f`) and serves FP8 weights with UE8M0 scales in 128×128 blocks. This matches an own boot line selecting `B12X_MXFP4` (fork-local `VLLM_USE_B12X_MOE=1`). [Code-verified]

Env and flags that matter on CC 12.1: `VLLM_USE_DEEP_GEMM` (default 1), `VLLM_USE_DEEP_GEMM_E8M0`, `VLLM_BLOCKSCALE_FP8_GEMM_FLASHINFER` (default 1), `VLLM_DISABLED_KERNELS`, `VLLM_MARLIN_USE_ATOMIC_ADD` (default 0), `VLLM_B12X_MOE_FP4_FORCE_A16`, `--linear-backend`, `--moe-backend`. [Code-verified]

### SGLang

- Block FP8 dense checks the block shape before the backend flag. At main any `weight_block_size[1] != 128` goes to `triton_w8a8_block_fp8_linear` (`python/sglang/srt/layers/quantization/fp8_utils.py:590-591`); at `da64c5cb` the test is `weight_block_size != [128, 128]` (`:567-573`). The one exception: with an explicit `--fp8-gemm-backend flashinfer_cutlass` or `flashinfer_cutedsl`, a 32-wide-K block with UE8M0 scales on Blackwell is served as MXFP8 on FlashInfer's dense kernel (`can_serve_block_fp8_as_mxfp8`, main `:721-743`; `da64c5cb` `:668-682`). [Code-verified]
- For 128×128 blocks the `is_sm120` platform flag (`is_sm120_supported`: major 12, CUDA ≥ 12.8; set at `runtime_context.py:1955`) is true on GB10, and `initialize_fp8_gemm_config` turns `auto` into `cutlass` (`fp8_utils.py:956-966`). The CUTLASS wrapper falls back to Triton when N or K is not a multiple of 128 instead of padding (`fp8_utils.py:1126-1160`). DeepGEMM runs only with an explicit `--fp8-gemm-backend deep_gemm`. [Code-verified] Default on CC 12.1: CUTLASS for 128×128 blocks, Triton for everything else.
- b12x. SGLang main has no b12x code path (tree and code search at `2909f84e`). b12x lives in open upstream PRs (#34878 b12x MXFP4 MoE W4A8, #35899 b12x compressed-MLA attention, #34018 FP8 `wo_a` on sm120/121) and in a DGX-Spark-only preview image (branch `b12x-vision` @ `452239a74f`) documented in the SGLang DeepSeek-V4 cookbook. ### llama.cpp and forks

- Kernel choice for quantized weights: MMVQ (dequantize-in-dot-product vector kernel) for batch ≤ 8 (`MMVQ_MAX_BATCH_SIZE`, `ggml/src/ggml-cuda/mmvq.cuh:3`); above that MMQ whenever the type is supported (legacy, K- and I-quants, MXFP4, NVFP4), per-block shared memory ≥ 48 KiB and Turing-class MMA exist, which is always true on GB10 (`mmq.cu:266-330`). `GGML_CUDA_FORCE_CUBLAS` switches MMQ off. [Code-verified]
- DGX Spark has its own constant `GGML_CUDA_CC_DGX_SPARK = 1210` (`common.cuh:60`), its own MMVQ parameter table (`mmvq.cu:135-145`), a prefetch set keyed at compile time on `__CUDA_ARCH__ == 1210` (`mmvq.cu:9-25`), and a runtime batch cap in `ggml_cuda_should_use_mmvq` (Q2_K uses MMVQ only up to 6 rows, other types 8; `mmvq.cu:348-352`), which ordinary quantized `mul_mat` uses (`ggml-cuda.cu:1868`). The nwarps table keys on the highest compiled arch. [Code-verified]
- On Blackwell (compiled arch ≥ 1200 and < 1300) MMQ uses native block-scaled FP4 MMA for MXFP4 (`kind::mxf4 … scale_vec::2X.m16n8k64 … ue8m0`) and NVFP4 (`kind::mxf4nvf4 … scale_vec::4X.m16n8k64 … ue4m3`), and int8 MMA for K/I-quants (`mma.cuh:1185-1210`). The CUDA CMake default adds `120a-real` for CUDA ≥ 12.8 and `121a-real` for CUDA ≥ 12.9, and rewrites a `native` build's `12X` to `12Xa` (`ggml/src/ggml-cuda/CMakeLists.txt:40-55, 94-99`). [Code-verified] A llama.cpp image built with CUDA < 12.9, or with an arch list that omits 121, runs the generic MMVQ table and no DGX Spark prefetch on GB10. [Interpretation]
- imatrix. The pinned `tools/quantize/README.md` says quantization loss "can be minimized by using a suitable imatrix file". [Code-verified] No GB10-specific imatrix comparison exists (§8).
- The DeepSeek-V4 C/CUDA engine (antirez/ds4). Entrpi's CUDA work is upstream: the fork's `main` is 0 commits ahead (GitHub compare, merge base `b0a147a7`, fetched 2026-09-23). `0f62c620e` vendors llama.cpp MMQ and wires dense Q8_0 GEMMs and the IQ2_XXS gate/up + Q2_K down routed-MoE pipeline for n_tok ≥ 2 (decode, n_tok = 1, untouched; FP32 reduction order changes, so prefill logits drift at ULP scale; `DS4_CUDA_MMQ=0` restores the cuBLAS + dequant path). `6f087f425` "cuda-spark uses native arch": an empty `CUDA_ARCH` compiled the MMQ tensor-core paths out ("measured 39 vs 423 prefill tok/s on GB10", commit message, workload unstated). `56ec89260` builds `-gencode arch=compute_121a,code=sm_121a -DDS4_CUDA_HAVE_MXF4=1` only when `CUDA_ARCH=sm_121` exactly and uses `kind::mxf4 … scale_vec::2X` MMA for the sparse-attention indexer, not for weight GEMMs. [Code-verified] The ds4 engine's prefill speed comes from MMQ tensor-core kernels that exist only when the arch flag is set. [Interpretation]
- The Anemll GB10 work is a vLLM fork, covered under vLLM above.

### ExLlamaV3 in vLLM

- vLLM main has no EXL3 support: no `exl3`/`exllamav3` symbol under `vllm/` at `711fc55c` (only the GPTQ `mixed_precision/exllama.py`). Every "EXL3 in vLLM" lane, own and community, runs a community overlay around the ExLlamaV3 extension. [Code-verified]
- Dequant-then-GEMM crossover is fixed in code, not tuned per device: a linear with ≤ 144 rows (`AUTO_RECONSTRUCT_THRESHOLD`) runs the fused trellis GEMM; above that it reconstructs the FP16 weight and runs a dense GEMM (`exllamav3/modules/quant/exl3.py:10, 136-144`). From 1,024 rows, with 128-divisible dimensions, a fused reconstruct folds both Hadamard transforms in; the code comment puts break-even at 400-900 rows and says the standalone Hadamard launches were about 14% of long-chunk prefill GPU time (`exl3.py:176-190`; device unstated). [Code-verified]
- Tile shapes: `select_gemm_shape(cc, …)` maps any major ≥ 10, including 12.1, to `CC_BLACKWELL`, which shares the Hopper table (`exl3_devctx.cu:39`, `exl3_kernel_map.cu:23-75`; K-tile 16/32, N-tile 128-512). No SM121-specific tuning exists. The dense reconstruct GEMM first tries an FP16-accumulate `mma.sync` kernel that flushes to FP32 every 32 K-elements, enabled only if a runtime probe finds FP16 accumulate ≥ 1.5× faster ("GeForce: 2.0x; workstation / datacenter parts: 1.0x"), else cuBLAS (`hgemm_f16acc.cu:1-12, 376-392`). [Code-verified] The probe's result on GB10 has not been observed (§8).
- Build: when `TORCH_CUDA_ARCH_LIST` is unset, the extension's arch list is clamped to the highest SM the installed PyTorch lists and gets `+PTX`, so a torch wheel that only knows `sm_120` makes GB10 compile `12.0+PTX` (`exllamav3/util/arch_list.py:8-40`). [Code-verified] Whether an EXL3 lane runs a native 12.1 cubin depends on the torch build. [Interpretation]
- Stock fused MoE re-streams the 4-bit B matrix every 16 rows; the grouped prefill kernel every 64 rows (64-row tile, 32 KiB shared memory, 4-stage cp.async, FP16 MMA after in-register trellis decode) (`exl3_moe_kernel.cuh:104-143` @ `c5d9c657`). [Code-verified]
- Recipe overlays on EXL3 lanes also change the non-EXL3 GEMMs: dense projections can be converted at load to per-output-channel FP8 weight-only and run through Marlin, and a KDA input projection can switch to a BF16 GEMM over a load-time BF16 copy above M = 512 (MiaAI-Lab GLM EXL3 PR #233, merged 2026-09-20, merge `d4bd9eb4`; PR #237 extended it to three-way tensor parallelism: 34/34 KDA layers at [8726 × 4096], +68.2 MiB per layer per rank). [Code-verified] Two independent GLM EXL3 recipes say `--moe-backend marlin` corrupts EXL3 serving (MiaAI-Lab README; tonyd2wild README). [Community-measured]
- At three-way tensor parallelism two small KDA projections stay BF16 because their merged view is not 16-byte aligned for Marlin (22 local heads; row offset 16,940 bytes, 16,940 mod 16 = 12). [Code-verified]

## 3. What is different on GB10 / SM121

- [Code-verified] No `tcgen05`/TMEM and no `wgmma`. Low-precision math is warp-level `mma.sync`: `kind::f8f6f4` m16n8k32, block-scaled `kind::mxf8f6f4` m16n8k32 and `kind::mxf4nvf4` m16n8k64. Kernels gated to the SM100 family (TRTLLM MoE, FlashInfer CuTe-DSL NVFP4) and cuBLASLt grouped MXFP8/NVFP4 (listed for CC 10.x and 11.0 only) are unavailable, and the "SM120 family" kernels are what run.
- [Code-verified] 99 KiB (101,376 bytes) shared memory per block, identical on 12.0 and 12.1. Tile configs sized for datacenter parts fail at compile or launch (CUTLASS FP4 MoE tile asking 102,400 bytes, fixed in CUTLASS 4.4.2; SGLang Triton MoE configs asking 147,456 bytes). [Community-measured]
- [Code-verified] Family flags cut both ways. Code keyed on "major == 12" or "family 120" includes GB10 automatically (vLLM DeepGEMM, CUTLASS SM120 blockwise, SGLang `is_sm120`); code keyed on exact (12, 0) excludes it (FlashInfer b12x auto, `is_sm120()` in SGLang). GB10 therefore inherits RTX PRO 6000 defaults it was never validated on (DeepGEMM with FP32 scales; §7) and misses some it would benefit from.
- [Code-verified] Build targets decide native code. vLLM builds `12.0f` on CUDA ≥ 13; FlashInfer JIT builds `compute_121a` on CUDA ≥ 12.9 but runs the `120f` FP4-quantize module; llama.cpp needs CUDA ≥ 12.9 for `121a-real` and its DGX Spark tables; ExLlamaV3 inherits torch's list. A CUTLASS FP8 block kernel compiled for `120a` under CUDA 12.9 passed `can_implement()` and failed at launch with `kErrorInternal` on GB10; rebuilding for `121a` fixed it, and CUDA 13 builds do not need the workaround (vLLM issue #43367, closed). [Community-measured]
- [Measured] Decode is weight-bandwidth-bound. Own step-time data on a dense 27B (decode step 138 ± 3 ms [Measured]) imply weight streaming of 185.2 GB/s over the packet's 130.8 ms KV-excluded base step for 24.22 GB; the 206.5 GB/s variant has no stated step time [Interpretation] (bytes model: [Decode optimization](05-decode-optimization.md)); a community device-to-device copy ceiling is 245.9 GB/s (NNNtrance, [Community-measured]); achievable bandwidth is about 215-245 GB/s depending on the probe (contested; single-probe figures per tool family: saturating read 227-235, rotating-buffer read 238.6-245.9, copy 215-229, STREAM triad 200-214 GB/s [Community-measured]), see [Decode optimization](05-decode-optimization.md) §3. Marlin runs NVFP4 MoE at 227-236 GB/s (91-96% of that ceiling) for M ≤ 256 (same source). This is why weight-only kernels tie or beat native FP4 at decode sizes.
- [Community-measured] Chip state can move a large-M BF16 GEMM by about 40% at the same reported SM clock (FP16 2048³ 53-55 vs 76-84 TFLOPS; decode-shaped BF16 GEMV 66-80 vs 224-233 GB/s, one node of a four-node cluster; tonyd2wild DeepSeek-V4.1 repo issue #1, open). Component A/Bs must interleave arms. See [Clocks, thermal, and power](13-clocks-thermal-power.md).
- [Community-measured] cuBLAS picks SM80-generation `cutlass_80_*` kernels for BF16 on SM12x (two-GB10 DeepSeek-V4-Flash profile: 25.6% of GPU time in `cutlass_80_wmma_*`; RTX-class sm_120 GEMM at 8192³ likewise); the author notes kernel names alone do not prove Ampere code paths. Whether a better SM12x BF16 kernel exists in cuBLAS's GB10 heuristics is not shown.
- [Code-verified] GB10-specific code exists in a few places only: llama.cpp's `GGML_CUDA_CC_DGX_SPARK = 1210` tables, b12x, FlashInfer's `sm121a` module (remapped at runtime), and the cuBLAS DGX Spark release-note items.
- [Historical diagnostic] Marlin prints "GPU does not have native support for FP4/FP8" on GB10 in every Marlin FP4/FP8 path. It is a code-path message; the same builds dispatch FlashInfer CUTLASS NVFP4 elsewhere, and the ISA lists FP8 and block-scaled FP4 `mma.sync` for 12.x.

## 5. Levers, ranked

1. **BF16 GEMM over a load-time BF16 copy of an FP8 weight for large-M prefill, Marlin below the boundary** — applies to: vLLM (EXL3 overlay or any lane running FP8 weight-only dense projections) × hybrid or dense models with large prefill projections × TP2 and TP3. Gain: 2.17-2.34× on the own TP3 KDA input projection at M ≥ 513 on all three ranks and +7.20% / +7.93% cold prefill at ~7.6K / ~95K as part of a four-change group [Measured]; 3.1-3.7× at M ≥ 768 on the TP2 shape and -11 to -12% cold TTFT (MiaAI-Lab PR #233) [Community-measured]. Do not average the two: different shard shape. This is the same KDA-projection lever as [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md) lever 4. Cost: +2.264 GiB per rank for 34 retained layers; a boundary in the M range. Risk: an inherited boundary (512 was placed in an empty M band of the TP2 workload, not measured as a crossover [Interpretation]); keep the boundary above the largest captured graph size so capture and replay agree. Smallest falsifying experiment: time BF16 and Marlin on the real weight at M ∈ {64, 128, 256, 511, 512, 513} at N = 8,726; if BF16 does not win above the chosen boundary, or wins well below it, the boundary is wrong.
2. **FP8 weight-only (Marlin W8A16) dense projections for decode-heavy agent turns** — applies to: vLLM × models whose dense or shared projections are BF16 on disk (GLM 5.3 Flash EXL3 lanes) × TP2 and TP3. Gain: decode +7-14% at short depth (+1% at 120K) and 2.4 GiB smaller weights per node, at an 18-21% long-prompt prefill cost (BF16 is 22-26% faster) [Measured]; a recipe author reports about 11 ms less per decode step [Community-measured]. The turn arithmetic favours FP8 for typical agent turns (2-5K new prompt tokens, 300-2,000 output) [Interpretation]. Cost: prefill; lever 1 recovers part of it. Risk: the numerics are provisional (author KL proxy 0.002-0.013 nats per position, which cannot be placed above noise without a replay-matched panel; §8); widening FP8 scope arrived inside a bundle with an unexplained -8.92% short-prefill result. Smallest falsifying experiment: one boot per arm, BF16 vs FP8 dense on the same image, decode fixtures × 5 plus a replay-matched KLD panel; FP8 fails if decode gain is inside repetition spread or KLD exceeds the cross-launch floor by more than the pre-set margin.
3. **NVFP4 instead of block FP8 for dense or hybrid models when decode dominates** — applies to: vLLM and SGLang × dense 27B-class and hybrid MoE × one node. Gain: fewer bytes per step (block FP8 30.77 GB vs NVFP4 20.09-24.22 GB per verify step; [Measured] step time, [Interpretation] byte model, see [Decode optimization](05-decode-optimization.md)); +29-33% output at 16 concurrent prompts without speculation (forum 380258) [Community-measured]; with a k = 7 drafter +27% at c1 falling to +0.2% at c16, and 7-9% slower prefill (0xBakeer) [Community-measured]. Contested at high concurrency with speculation. Cost: re-quantized checkpoint; export choice matters more than the label (§4 export screen). Risk: 2-6 points lower on 50-item math sets (flash7777, ai-muninn) [Community-measured]; strict-JSON rate varied 0/4 to 3/4 across NVFP4 exports [Measured]. Smallest falsifying experiment: same engine, same drafter, same harness, NVFP4 vs block FP8 at c1/c4/c8 plus the quality gates in §6; NVFP4 loses if its c1 gain is inside spread or any gate regresses.
4. **Keep Marlin at decode sizes; use native FP4/FP8 grouped kernels only where M per expert group is large** — applies to: vLLM × NVFP4/MXFP8 MoE × all topologies. Gain: native FP4 MoE beats Marlin by >5% only from M ≈ 1,024 all-local (1,792-4,096 in the expert-parallel form) (NNNtrance sweep) [Community-measured]; native MXFP8 grouped 0.95× at c = 1 but 1.28-1.34× at c = 16-32 (FlashInfer PR #3463) [Community-measured]; b12x/b12x within 0.6% of INT4 Marlin at batch 1 (vLLM #40082) [Community-measured]. A hybrid (Marlin below an M threshold, native above) is [Proposed]. MoE backends are on [MoE dispatch](08-moe-dispatch.md). Cost: backend flags per format; open PRs. Risk: known-bad native paths (§7). Smallest falsifying experiment: on the lane's real MoE shape, time Marlin vs FlashInfer CUTLASS vs b12x at M ∈ {8, 64, 256, 512, 1,024, 2,048} with interleaved arms; the lever fails if native wins at M ≤ 256.
5. **`VLLM_USE_DEEP_GEMM=0` for block FP8 on GB10 unless a pinned build proves DeepGEMM** — applies to: vLLM × 128-block FP8 dense and MoE × all topologies. Gain: safety, not speed: avoids the FP32-scale mis-selection, the K = 2560 silent-corruption window and the FP4-kernel routing regression; CUTLASS SM120 blockwise then serves (23.7-26.1 tok/s single stream, NLL 0.7610 vs 0.7748 dense, #54125) [Community-measured]; own vLLM 0.24.0 boot failed until DeepGEMM was disabled [Historical diagnostic]. Cost: may give up DeepGEMM MoE speed on builds where it works (own 2026-09-05 lane qualified with DeepGEMM FP8 MoE) [Historical diagnostic]. Risk: low. Smallest falsifying experiment: on the pinned build, a K-sweep (1,024-10,240, including 2,560) of DeepGEMM vs CUTLASS vs a BF16 dequant reference at M ∈ {1, 17, 64, 128}; if DeepGEMM is clean and faster, keep it for that build only.
6. **b12x warp-level MMA for small-M block FP8 with 32×32 UE8M0 blocks** — applies to: SGLang (recipe adapter or preview image) and vLLM `B12xMxfp8LinearKernel` × DeepSeek V4.x-style checkpoints × TP3. Gain: about 17 vs 50-52 ms per decode step for the dense FP8 projections (author profile) [Community-measured]; no own A/B [Historical diagnostic]. Cost: out-of-tree adapter or open PRs. Risk: padded shards with uninitialized scales silently fall back (86 layers in the author's run). Smallest falsifying experiment: component timing of b12x vs CUTLASS vs Triton on the real 32×32 weights at M ∈ {1, 2, 4, 6, 8, 16, 32, 64} with FP32-reference numerics, plus a per-layer count of fallback lines at boot.
7. **EXL3 cooperative decode MoE kernel** — applies to: vLLM + EXL3 overlay × MoE models with 2-3 bpw experts × TP3. Gain: 1.23-1.94× on the decode MoE component [Measured] (see [MoE dispatch](08-moe-dispatch.md)). Cost: overlay kernel build. Risk: bundle adoption hides its whole-model share. Smallest falsifying experiment: one-variable boot swapping the stock fused MoE back in, decode fixtures × 5; the lever fails if whole-model decode moves less than repetition spread.
8. **Triton small-M specialization where the Triton block-FP8 fallback runs** — applies to: vLLM × block FP8 with no tuned JSON for the (N, K, device) tuple × any. Gain: +23% median decode on a two-GB10 DeepSeek-V4-Flash run (PR #40925, open) [Community-measured]. Cost: patch or tuned JSON. Risk: a config above 101,376 B drops out only while two or more configs are benchmarked; a sole, default or pinned config launches and crashes (see [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md) §2). Smallest falsifying experiment: add BLOCK_SIZE_M = 16 configs for M ≤ 8 on the lane's shapes and compare decode × 5 A-B-A.
9. **Native 12.1 builds for llama.cpp and the ds4 engine** — applies to: llama.cpp and ds4 × GGUF × one node. Gain: MMVQ nwarps = 8 gives +1.6-6.3% at batch 1 on dense models [Community-measured]; an empty-arch ds4 build lost the MMQ tensor-core paths ("39 vs 423 prefill tok/s", commit message) [Community-measured]. Cost: rebuild with CUDA ≥ 12.9 and `121a-real` or `CUDA_ARCH=sm_121`. Risk: low. Smallest falsifying experiment: `llama-bench -p 512 -n 128` on the same GGUF with a generic vs a native 12.1 build.
10. **Selective NVFP4 W4A16 for dense projections instead of FP8** — applies to: vLLM × GLM 5.3 Flash-class lanes × TP3/TP4. Gain: +12.4% coding and +27.3% prose on a four-node community lane vs that author's BF16 projections, with no closing BF16 arm (own re-computation of committed data) [Community-measured]; about 44% fewer bytes than FP8 on the overlapping tensors (storage only) [Interpretation]. Cost: new checkpoint from the BF16 source, not a cascaded FP8 -> FP4 conversion. Risk: W4A16 runs Marlin (dequant), so prefill cost resembles lever 2; stale duplicate tensors after re-quantization broke one load. [Proposed] for own lanes. Smallest falsifying experiment: one arm vs the current FP8 dense scope, decode × 5, prefill at 8K and 95K, KLD panel and the gates in §6.
11. **Pad N to a Marlin-aligned width and re-derive M boundaries per shape** — applies to: vLLM Marlin paths × TP3 shards with odd N (8,726 -> 8,768). Gain: removes a per-call unpad copy, about 1% cold prefill by arithmetic [Interpretation]; also meets cuBLAS's 16-byte rule (8,726 × 2 bytes mod 16 = 12). [Proposed] Cost: overlay change. Risk: low. Smallest falsifying experiment: `CUBLASLT_LOG_LEVEL=4` plus timings at N ∈ {8,726, 8,768}, M ∈ {64, 128, 256, 511, 512, 513, 2,048}.

## 6. Protocol

This is the protocol for changing a weight format, a GEMM backend, a kernel build or a dispatch boundary on a GB10 lane. It follows the fleet rules on the entry page and the incidents in §4 and §7. See [Profiling protocol](14-profiling-protocol.md) for kernel attribution and [Quality and correctness gates](21-quality-and-correctness-gates.md) for output gates.

Preconditions.
- All index rules apply (see [the entry page](README.md)), in particular: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor measured after the longest qualified prefill, and traffic stopped below 4 GiB; a greedy logprob probe after every relaunch; discard the first request and warm every serving shape before timing; a unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection or configuration line read on every rank; at least 3 repetitions with a closing baseline (A/B/A); MemAvailable sampled every 1-2 s with zero NV_ERR_NO_MEMORY or Xid lines; no reboot or power cycle without per-node permission; correctness gates from [Quality and correctness gates](21-quality-and-correctness-gates.md) before any speed number. For this page: check every rank for a latched low clock (see [Clocks, thermal, and power](13-clocks-thermal-power.md)), warm every GEMM shape before timing, and run the quality gates before any speed number.
- No memory overcommit: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor while serving, KV pin raises of no more than 1.5 GiB per boot, and memory freed by one change (for example FP8 weights 2.4 GiB smaller) never spent in the same boot. Stop all benchmark traffic at 4 GiB MemAvailable on any node. Retained BF16 copies (+2.264 GiB per rank in §4) are a memory change and count as one.
- Clean window: no outside traffic; poll running requests before each pass and discard any pass that overlaps outside traffic.
- One variable per boot. A restart for an A/B skips the image pull, so the only difference is the variable under test. A format change is one variable only if engine, image, drafter and flags are held fixed; otherwise label the result engine-confounded, as every format row in §4 is.
- Never restart a client gateway; restarting the lane's engine is the operator's step, and a gateway restart is the operator's decision.
- Record the GPU clock state (the 2,100 MHz cap or stock) and interleave arms; chip state alone can move a large-M GEMM by about 40% (§3).
- Build receipt: engine commit; CUDA version of the build; the arch list actually compiled (`12.0f`, `12.1a`, or `12.0a` only) for the engine, Marlin, FlashInfer and the extension; FlashInfer, cutlass-dsl, b12x and DeepGEMM versions (DeepGEMM branch and commit); whether `VLLM_USE_DEEP_GEMM` is set; the cuBLAS version inside the PyTorch wheel.
- Checkpoint receipt before GPU boot: per-layer `quant_algo` or `quantization_config`, weight block size and scale dtype (FP32 vs UE8M0), whether activations are quantized (W4A4 vs W4A16), a unique tensor-name inventory (no stale duplicates), and both `weight` and `weight_packed` field names when auditing packed tensors.

Change. Exactly one of: the checkpoint's format or export; `--linear-backend`, `--moe-backend`, `--fp8-gemm-backend` or `--fp4-gemm-backend`; `VLLM_USE_DEEP_GEMM`, `VLLM_DISABLED_KERNELS` or `VLLM_MARLIN_USE_ATOMIC_ADD`; a kernel build or library version; a dispatch boundary (M threshold); the precision scope of dense projections.

Run.
1. Component test before the serving engine sees the change: real weights from the checkpoint, seeded BF16 activations, M ∈ {1, 8, 64, 128, 256, 511, 512, 513, 1,024, 2,048, the lane's max chunk}, median of 20, arms interleaved; numerics against an FP32 reference of the same logical weight (relative RMSE and relative max, gate fixed in advance; the own gate was 0.004 / 0.008), plus changed-input graph replay at one small and one large M. Also report relative error, not only cosine: a 25× magnitude error kept cosine at 0.996 (§4). Keep any dispatch boundary above the largest captured graph size.
2. Boot one arm and grep, on every rank, the dense `Selected <Kernel> for <method>` lines and the MoE `Using '<BACKEND>' … MoE backend` lines, and count every "falling back", "BF16 emulation", "Skipped N unsupported tactic(s)", "Unknown recipe" and Marlin FP4/FP8 warning line per layer shape. A boot whose selection lines do not show the intended kernel is a boot where the change did not run.
3. Greedy logprob sanity check after every relaunch: top-1 logprobs of a fixed prompt in the healthy O(-1) to O(-20) range; fail closed if a quantized head or KV scale exists on disk but is not bound; treat unusually high speculative acceptance on prose as a red flag (§7).
4. Serving A-B-A through the frozen harness: cold-nonce prompts at 8K, 32K and 95-100K × 3-5 with short outputs; decode fixtures (structured, coding, prose) × 5; C4/C8 aggregate if the lane serves concurrency.
5. Quality gates per format, not per kernel: functional checks, executed code, strict unfenced JSON, a strict multi-call tool loop, retrieval at 20K-30K and near the lane's maximum context, and a KLD panel against BF16 or official FP8 where one exists. Place a KLD difference against the panel's measured noise floor (cross-launch replay about 1e-3 nats, live-vs-replay about 1.5e-2 on the community suite), not against zero.
6. Watch MemAvailable at 1 s resolution on every node through the longest prompt; record Xid and allocation-error counts.

Record (packet fields): build, checkpoint and clock receipts; the one variable and its two values; topology and shard shapes; per-rank selection and fallback lines; component timings per M with spread and numerics; per depth prompt tokens, TTFT and effective prefill; decode tok/s per fixture with spread; concurrency aggregates; every gate result with its protocol; KLD with noise floor where run; weights and KV capacity; minimum MemAvailable per node; discarded passes and why.

Pass gate. Component numerics inside the pre-set gate on every rank and no new fallback lines; the intended kernel selected on every rank; the target metric (decode or prefill) better than baseline beyond repetition spread and the other metric not worse than the accepted trade (for example lever 2 accepts a prefill loss for a decode gain, stated in advance); every quality gate at or above baseline, including strict JSON and the tool loop; greedy logprobs healthy; minimum MemAvailable at or above the 5 GiB warm floor; zero Xid and allocation errors.

Rollback. Revert the one variable (checkpoint path, backend flag, env var, build or boundary), restart with the pull skipped, confirm from the selection lines on every rank that the old kernel runs, and run one cold 8K prompt, one decode fixture and the greedy logprob check; all must match the baseline within repetition spread before the lane serves again.

## 7. Anti-patterns and known-bad

- [Measured] The fastest format was the least reliable. On one node, 2-bit EXL3 experts gave the fastest DeepSeek V4 Flash decode (54 tok/s code) but scored 28/40 on the shared battery, 0/7 on a strict seven-call agent loop and 4/8 on 20K retrieval, while the slower full-expert GGUF scored 36/40 and 7/7 (2026-08-22 packets). The community KLD for 2-bit EXL3 (about 10× official FP8's divergence) is the mechanism. [Community-measured]
- [Measured] A quantized lm_head whose scale failed to bind (a key-path mismatch) produced logprobs near 0 / -30,000, dead sampling and inflated speculative acceptance, because draft and verifier shared the broken head; the same bug dropped calibrated FP8 KV scales to 1.0. Several speed and quality results were withdrawn. Check greedy top-1 logprobs after every relaunch. See [Sampling and the lm_head](12-sampling-and-lm-head.md).
- [Historical diagnostic] A quantization audit read the wrong field (`weight` instead of `weight_packed` for compressed-tensors FP4) and stopped a valid arm before timing. A failed audit is not an "unquantized load" finding.
- [Historical diagnostic] Reading Marlin's "GPU does not have native support for FP4/FP8" warning as a hardware fact. It is a code-path message; grep the selection line.
- [Code-verified] "SM121 has no native FP4 compute" and "FP4 is dequantized on SM12x". Contradicted by CUTLASS's `mxf4nvf4`/`mxf4` m16n8k64 atoms for SM120/121, a ~511 TFLOPS dense issue-rate probe on GB10, and llama.cpp MMQ using the same instructions. What is absent is `tcgen05`/TMEM (CUTLASS `config.hpp`). Sources repeating the stronger claim include an early forum 360142 post, an April ai-muninn post (since retracted by its author: the `cvt…e2m1x2` conversion exists but needs the `sm_121a` target) and an X article that also misstates NVFP4 scales as E8M0 (they are UE4M3 per 16) and calls MXFP4 "emulation" on Blackwell. [Community-measured]
- [Code-verified] "SM121 has 99 KiB but SM120 has 228 KiB" (CUTLASS #3144 title). Both are 101,376 bytes.
- [Code-verified] "`tcgen05.mma` MX tensor cores on SM12x" (vLLM #43906 and FlashInfer #3463 bodies). SM12x uses warp-level `mma.sync` block-scaled atoms; the throughput numbers in those threads stand, the mechanism described does not.
- [Code-verified] Carrying SGLang's "non-128 blocks go to Triton" rule over to vLLM. In vLLM, Marlin precedes Triton and treats non-128 blocks as non-block K-first weights, which mispredicts both the kernel and the correctness risk.
- [Community-measured] DeepGEMM on GB10 by default: FP32-scale checkpoints get the E8M0 variant (vLLM #54125), block-FP8 GEMM corrupts silently at K = 2560 for small N, `nv_dev` `8b1392b` routed FP8×FP8 through the FP4 kernel (garbled output, 25.8 -> 4.4 tok/s; DeepGEMM #417), `DEEPGEMM_MXFP4` hit `CUDA_ERROR_INVALID_IMAGE` on `nv_dev` `2073ddb` (vllm-gb10 issue #27; workaround `VLLM_USE_DEEP_GEMM=0 VLLM_USE_DEEP_GEMM_E8M0=0` booted Triton FP8 linear plus Marlin MXFP4 MoE). The vLLM #54125 title's framing ("reported supported but faults") was corrected by its own reporter: the crash itself was a skipped post-processing step, fixed upstream.
- [Community-measured] Block-FP8 Triton at 0% math with good speed (60 tok/s on SGLang 0.5.8, forum 360142): a speed number without a numerics gate.
- [Community-measured] A weight-only NVFP4 checkpoint (scales for weights only, no `input_scale`) driven on vLLM's W4A4 NVFP4 MoE path computed a global activation scale from an unfilled parameter and produced "lock lock lock"; Marlin "fixed" it only because it never needs that scale. Cosine similarity hid a 25× magnitude error (Libertai probe).
- [Community-measured] Output collapse with no CUDA error: all-`!` output (token id 0) from CUTLASS FP4 on SM121, found by dumping the pre-lm_head tensor; a wrong environment-variable name silently re-enabled the bad backend (ai-muninn part 1; forum 364009). Every completion returned null content because the Marlin MXFP4 path produced a wrong first Harmony token, found with `return_token_ids` (vLLM #37030, open). `foss foss foss` output from Marlin WNA16 MoE on a large GB10 cluster despite `--moe-backend triton` (a vLLM draft filed on the SGLang tracker, #23264, closed). Garbled output from a stale Triton cache on `sm_121` JIT, fixed by wiping the cache (vLLM #41871, closed).
- [Community-measured] Copying MoE backend flags across formats. `--moe-backend marlin` corrupts EXL3 serving in two GLM EXL3 recipes, was required for one NVFP4 GLM lane, and was unnecessary for another NVFP4 lane that ran FlashInfer CUTLASS cleanly. [Historical diagnostic]
- [Community-measured] Zero-padded tensor-parallel shards with uninitialized (denormal) block scales made 86 layers silently fall back to Triton until scales on all-zero blocks were set to 1.0 (DeepSeek-V4.1 recipe). Initialize scales when padding; count fallback lines per layer.
- [Community-measured] Stale duplicate tensors survived an index rewrite after re-quantization (412 superseded BF16 tensors in mixed shards); loads failed. Inventory unique tensor names before boot.
- [Historical diagnostic] An MXFP8 layer below FlashInfer's shape limits ([N = 96, K = 2560]) falls back to BF16 emulation with one log line; upstream it is an assert, not a gate (vLLM PR #54223 open).
- [Interpretation] An M threshold inherited from a different tensor-parallel shape was shipped without re-measurement (512 from the TP2 workload used at TP3). Re-derive boundaries per shard shape.
- [Measured] A precision-scope change inside a multi-change bundle left an unexplained -8.92% short-prefill result that could not be attributed. One precision change per arm.
- [Measured] "FP8 is safer than NVFP4 on this chip" advice for a dense 27B was wrong for speed here: block FP8 needs 30.77 GB per verify step vs 20-24 GB for NVFP4, and SGLang's FP8 CUTLASS path falls back on non-128 shapes. Quality is model- and export-dependent (§4). [Interpretation]
- [Community-measured] Serving-flag bundles presented as backend results: a tool benchmark moved 91 -> 88 when eight flags changed together, including the tool-call parser (MichaelGannotti).
- [Community-measured] Marlin atomic-add (`VLLM_MARLIN_USE_ATOMIC_ADD=1`): one GB10 deployer found the gain "too small and inconsistent" (forum 364842); a forced no-split-K Marlin W4A16 MoE path hits an illegal memory access at M = 256 on a patched build (vLLM #56064, open; the stock op cannot reach that state per the thread), a hazard for anyone re-tuning Marlin, not a stock-serving bug.
- [Measured] Rejected on this fleet: EXL3 grouped-prefill tile variants (stock 64-row/4-stage won 8/8), ExLlamaV3 approximate INT8 GEMV mode 2 (failed numerics), a fused decoder-staging kernel (component gains, whole-model C8 -5.51%), the W8A8 FP8-activation path for the KDA projection (upstream evidence: slower than BF16 and 23 argmax flips at its boundary [Community-measured]), and a llama.cpp GGUF Q3 lane for Qwen 27B (1.9× slower agent loop, 2.3× slower decode near 500K, strict JSON fail).

## 8. Open questions

- Is b12x MXFP8 faster than CUTLASS SM120 blockwise and Triton for block FP8 at M = 1-64 on GB10 outside one author's step profile? — Component timing on real 32×32-UE8M0 and 128×128 weights at M ∈ {1, 2, 4, 6, 8, 16, 32, 64, 128, 512}, each backend forced by flag, arms interleaved, numerics against FP32.
- Does vLLM's Marlin path load non-128 FP8 block shapes correctly, given it treats them as non-block K-first weights? — A tiny block-FP8 checkpoint with [64, 64] and [32, 32] blocks, Marlin output vs a dequantized reference.
- Is `has_flashinfer_fp8_blockscale_gemm()` true on a GB10 FlashInfer build, which would make the FlashInfer-plus-DeepGEMM dynamic kernel the first block-FP8 choice? — Call it on the lane image and read the `Selected` line with and without DeepGEMM installed.
- Why did the own Flash Next build select `MarlinNvFp4LinearKernel`: a build without `ENABLE_NVFP4_SM120`, or W4A16-declared linears? NVIDIA-published Qwen3.6 NVFP4 exports are W4A16 per Unsloth, which makes the declaration route plausible. — On that image call `cutlass_scaled_mm_supports_fp4(121)` and read each layer's `quant_algo`; then a same-model Marlin-NVFP4 vs FlashInfer-CUTLASS-NVFP4 dense A/B.
- How does MXFP4 compare with NVFP4 on the same weights on GB10? The atoms suggest equal math throughput with different scale overhead. — The lossless MXFP4 -> NVFP4 cast (ModelOpt `--cast_mxfp4_to_nvfp4`) on one MoE, timed per backend.
- What is the SM121 trellis-decode tactic latency for EXL3 (fused GEMM per K and shape index, M = 1-144), and what does ExLlamaV3's FP16-accumulate rate probe return on GB10? — Run the kernel-lab sweep (auto dispatch plus four compiled tile shapes × SM quotas) and log the probe ratio at extension load.
- Does imatrix help GGUF quality on the formats the own lanes use? — KLD against a BF16 reference for the same GGUF type with and without imatrix, plus the strict tool loop.
- How do llama.cpp MMQ, MMVQ and cuBLAS compare on GB10 at batch 1-16 for Q3_K_XL, IQ2_XXS and Q8_0? — `llama-bench` with and without `GGML_CUDA_FORCE_CUBLAS`, native 12.1 build, batch 1/2/4/8/16.
- Does cuBLASLt pick a slower kernel at N = 8,726 than at 8,768, and where does BF16 overtake Marlin between M = 65 and 512? — `CUBLASLT_LOG_LEVEL=4` (or `CUBLASLT_LOG_MASK=8`) around the component probe at N ∈ {8,726, 8,768}, M ∈ {64, 128, 256, 511, 512, 513, 2,048}.
- Which cuBLAS is inside each lane's PyTorch wheel, and so which of the CUDA 13.0 Update 2 to 13.2 DGX Spark fixes each lane has? — Read `torch.backends.cuda` / the bundled `libcublasLt` version on each image and record it in the packet.
- Is dense FP8 (weight-only) above the output-divergence noise floor? The author's proxy (0.002-0.013 nats) sits between the community cross-launch floor (~1e-3) and live-vs-replay capture noise (~1.5e-2). — A replay-matched KLD panel at three prefix lengths and at least 33K positions for FP8 dense, the KDA BF16 path, and EXL3 vs NVFP4.
- Do deployed libraries carry `12.0f` or `12.1a` cubins, and does it matter? PR #38484's claim that wheels ran SM120 PTX JIT is contested; one GB10 A/B saw 16.4 vs 16.3 tok/s. — `cuobjdump --list-elf` on the engine, Marlin, FlashInfer and extension `.so` files, then a native-vs-published A/B on the lane's own model.
- Does DeepGEMM `nv_dev` after #447 carry the FP32-scale guard (`f9d0e2361`), and is the K = 2560 corruption window gone? — The K-sweep in lever 5 on the pinned commit, with an FP32-scale checkpoint.
- Should B12X or FLASHINFER_B12X NVFP4 MoE enter auto on SM121 (open vLLM PRs #54669 and #54719; FlashInfer excludes SM121 from b12x auto on purpose)? — The lever 4 sweep on the lane's own MoE shape plus the §6 gates, on a build carrying #54669.
- Does B12X_MXFP4 MoE beat Marlin MXFP4 on the own DeepSeek V4 Flash TP2 lane, and does Marlin MoE on the Nemotron NVFP4 lane beat FlashInfer CUTLASS? Both were selected without an A/B. — One boot per MoE backend, decode fixtures × 5, C8 aggregate, quality gates.
- Does the Marlin atomic-add flag help on GB10? — `VLLM_MARLIN_USE_ATOMIC_ADD` 0 vs 1, decode × 5 A-B-A on one NVFP4 lane, with a numerics check.
