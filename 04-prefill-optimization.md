# Prefill optimization on GB10

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 128 GB unified memory), one to three nodes (node-1, node-2, node-3), 200 Gb/s RoCE between nodes. "Effective prefill" means prompt tokens divided by streamed time to first token (TTFT), request overhead included, unless a row says otherwise. Code lines are quoted at these pins: vLLM `711fc55c10a2`, SGLang `2909f84e3b2f`, llama.cpp `6e60f35608ec`, ExLlamaV3 `6b84a21b6f1e` (release tag v1.5.0 = `0740edc2`). The own lanes run older builds, so a code line says what upstream does now, not what a given lane runs.

## 1. What it is

Prefill is the phase in which the engine reads the whole prompt before it writes the first word of the answer. On a GB10 it decides how long an agent waits after pasting a long file or resuming a long conversation: at 1,500 tokens per second a 100K-token prompt takes about a minute, and a 1M-token prompt about twelve. Engines do not read the prompt in one piece; they cut it into chunks (fixed-size prompt slices) and run one chunk per scheduler step, so the chunk size sets how big each matrix multiply is, how much scratch memory each step needs, and how long a user who is already receiving an answer has to wait while someone else's prompt is processed. Three costs make up each step: a fixed cost per step and per request, a cost that grows with the chunk (mostly the big matrix multiplies, including the mixture-of-experts layers, where many small expert networks each take a share of the tokens), and a cost that grows with how much prompt is already behind the chunk (attention and the sparse "indexer" that picks which earlier tokens to attend to). The GB10 is different from a datacenter card in three ways that matter here: its tensor-core peak is BF16 ≈123 or ≈213 TFLOPS, FP8 ≈214-256, FP4 ≈427-511 (contested; single-probe evidence), its memory bandwidth is about 215-245 GB/s depending on the probe (contested; single-probe figures per tool family: saturating read 227-235, rotating-buffer read 238.6-245.9, copy 215-229, STREAM triad 200-214 GB/s [Community-measured]); see [Decode optimization](05-decode-optimization.md), and its 128 GB is shared with the operating system, so the temporary buffers a large chunk needs come out of the same pool that keeps the machine alive. The fastest chunk on paper can therefore be the one that stalls other users, shrinks the cache, or freezes the node. Warm prefill, where most of the prompt is already cached from an earlier turn, is a separate and often larger win: it turns minutes into seconds, but only if nothing near the start of the prompt changes. See also [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md), [Memory management on a unified-memory GB10](11-memory-on-unified-memory.md) and [Serving agent workloads](22-serving-agent-workloads.md).

## 2. How each engine does it

### vLLM

Mechanism. The V1 scheduler fills each step with running decodes first, then spends the leftover token budget (`--max-num-batched-tokens`, MNBT) on prefill chunks. Chunked prefill is on by default in V1 (`enable_chunked_prefill = True`, config/scheduler.py:129). `--long-prefill-token-threshold` (LPT) caps how many tokens one request may take per step; it defaults to 0, meaning off (config/scheduler.py:80-86). [Code-verified]

- Default budget on CC 12.1. The OpenAI server picks MNBT by device memory: 160 GiB or more gives 16,384; 70 GiB or more (and not A100) gives 8,192 with `max_num_seqs` 1,024; anything else gives 2,048 with 256 (engine/arg_utils.py:2779-2807). On the NVML platform vLLM reads memory with `nvmlDeviceGetMemoryInfo` (platforms/cuda.py:831-834), and on GB10 that call returns "Not Supported" (NVIDIA DRA driver issue #1073; `nvidia-smi` prints "Memory-Usage: Not Supported" in the llama.cpp GB10 bench's system info). The try/except then sets device memory to 0. [Code-verified] path; [Interpretation] result: an unconfigured vLLM server on GB10 most likely gets the fallback tier, MNBT 2,048 and 256 sequences, not 8,192. Confirm from the boot line "Chunked prefill is enabled with max_num_batched_tokens=%d" (config/scheduler.py:301-305).
- Solo requests. Since PR #57951 (merged 2026-09-22, c64b15cd) the scheduler ignores LPT whenever it holds only one request (running + waiting + skipped at most 1) (v1/core/sched/scheduler.py:602-608). `_mamba_block_aligned_split` (line 466) still reads the raw LPT for its alignment decision. [Code-verified] [Interpretation] Before this change a solo cold prefill was capped at LPT even when MNBT was larger. Any lane rebuilt past 2026-09-22 changes solo cold-ladder behaviour whenever LPT < MNBT; re-baseline after such an upgrade.
- Concurrent partial prefills. V1 has no `max_num_partial_prefills` field at the pin; PRs #49075 and #57427, which would add one, are open. [Code-verified] Recipes patch in their own admission cap (§4).
- Hybrid (attention plus Mamba/KDA recurrent layers) alignment. For hybrids the attention block is set to the alignment times ceil(recurrent page / (alignment x per-token page)), at least 128 for MLA hybrids, and the recurrent page is padded to match; in `align` mode `mamba_block_size = block_size` (platforms/interface.py:762-945). In `align` mode chunk ends fall on block multiples, and when a block is larger than the chunk limit, intermediate chunks advance by less than a block and realign at the next boundary (v1/core/sched/scheduler.py:405-470). The engine logs "Setting attention block size to %d tokens". [Code-verified]
- Sparse-indexer transient. Sparse-indexer prefill builds an fp32 logits tensor of shape [M, N]; its size is capped by `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` (default 512, "Bounds the [M, N] float32 logits"; envs.py:1085-1090) and larger batches are sub-chunked on M (v1/attention/backends/mla/indexer.py:1345, `_split_indexer_prefill_chunks`). The GLM-5.3 indexer reserves max(worst-case decode logits, prefill cap) at profile time (models/glm5next/nvidia/sparse_indexer.py:140-166). No SM12x row cap exists in the vLLM indexer files; the SM12x checks in indexer_topk.py gate only the cooperative decode top-k. [Code-verified] The cap bounds memory, not compute. [Interpretation]
- Short-context DeepSeek V4 top-k skip. PR #49486 (merged b0cb1da1) skips top-k and routing when not needed; it needed a CUDA-graph capture guard, PR #52492 (merged 2026-08-17), after silent corruption under MTP plus prefix caching plus graphs. Carry both or neither. [Code-verified]
- MoE on SM12x. NVFP4 MoE auto order: FLASHINFER_TRTLLM, FLASHINFER_CUTEDSL, FLASHINFER_CUTEDSL_BATCHED, FLASHINFER_CUTLASS, VLLM_CUTLASS, MARLIN, HUMMING, EMULATION. FLASHINFER_B12X, the SM12x kernel that fuses dispatch, both GEMMs, SwiGLU and the top-k reduction, is kept out of auto selection "until the upstream CUTLASS SM121 MMA op guard is resolved" (fused_moe/oracle/nvfp4.py:188-203; experts/flashinfer_b12x_moe.py:30-45). Only two GB10-tuned Triton fused-MoE configs ship (E=256 and E=512, N=512, fp8_w8a8, block [128,128]); any other shape logs "Using default MoE config. Performance might be sub-optimal!" (fused_moe.py:1164). The Triton `tile::gather4` (TD) gather path compiles on SM12x but is opt-in "pending validation" and falls back to pointer loads under any quantization, so it is moot for quantized MoE (fused_moe/utils.py:604-633). [Code-verified]
- Dense GEMM. No M-dependent switch from weight-only Marlin/FP8 GEMMs to a dequantized BF16 GEMM exists in the linear-kernel tree at the pin; the only M tiers there are kernel-config choices and one RDNA hybrid path. Marlin W4A8-FP8 activations are allowed on SM12x (`VLLM_MARLIN_INPUT_DTYPE=fp8`; quantization/utils/marlin_utils.py:720-736). [Code-verified]
- Warm path. `prefix_match_unit` (equal to `hash_block_size`) sets "the finest token boundary a prefix-cache hit can land on" and can be finer than the physical hybrid block (config/cache.py:91-102; PR #46384, merged 481e481b). With partial hits on an `align`-mode hybrid, the scheduler adds a stop at the prompt's last hash boundary (`mamba_partial_cache_hit`, scheduler.py:363-369), costing one extra step. Internal prefill checkpoints remove that extra forward: PR #52789 (merged 9eb9d9d3) and PR #53614 (Kimi K3, merged 144e79c8); GLM-5.3-Flash KDA checkpoints are still open (PR #56960, head 7565389f). `prefix_cache_retention_interval` defaults to 0: keep only semantic checkpoints (config/cache.py:160-166). [Code-verified]
- Observability. `--enable-mfu-metrics` logs "MFU: %.1f TF/s/device %.1f GB/s/device" from analytic FLOP and byte estimates and exports `vllm:estimated_flops_per_gpu_total` (config/observability.py:77-78; v1/metrics/perf.py:1706-1731). It reports achieved TFLOPS, not a percentage; the operator supplies the peak. Perf metrics are built only when stats logging is on. [Code-verified]
- Speculation and the step budget. With speculative decoding on, `max_num_scheduled_tokens` defaults to MNBT, and the engine logs a warning whenever it is below 8,192 (config/vllm.py:2287-2316). The warning echoes the configured value; it is not a clamp, although one GB10 recipe reads it as "MTP clamps max_num_scheduled_tokens to 2048". [Code-verified]
- MNBT also sizes workspaces on some sparse-MLA builds. On a DeepSeek V4 DSpark-class build an MNBT-proportional prefill workspace shares the pinned KV region, so a smaller MNBT with LPT 2,048 grew the KV pool 40% (dkmode22). On a b12x build, warm-up sizes the compressed-MLA scratch from MNBT and then locks it, so MNBT 2,048 later crashed on a warm-prefix turn that needed 1,949.52 MB against a locked 1,157 MB (single-node DeepSeek V4 recipe, issue #4). [Community-measured] The same knob moves memory in opposite directions on different builds (§4, §7).
- Per-step logging. `--enable-logging-iteration-details` (`enable_logging_iteration_details`, default False; config/observability.py:85-89) logs per-iteration request and token counts. The docstring says "elapsed cpu time", but `step()` in v1/engine/core.py times `time.monotonic()` around the blocking wait for the model output, so the figure is host wall time that includes the GPU step (it starts after the non-blocking dispatch and the grammar bitmask). It logs only when stats logging is on. [Code-verified] A forum reply recommends it, with the `request_prefill_time_seconds` and `request_queue_time_seconds` histograms, over `vllm:iteration_tokens_total`, which records a whole chunked prefill as one observation (NVIDIA forum thread 382099). [Community-measured]
- Hybrid prefix-caching defaults. Generative hybrids support prefix caching and get it by default: `default_prefix_caching = model_config.is_prefix_caching_supported` (engine/arg_utils.py:2847, applied at 2878), and `is_prefix_caching_supported` is True for `attn_type == "hybrid"` (config/model.py:2211-2213). Prefix caching on forces `mamba_cache_mode` "align"; off forces "none" (model_executor/models/config.py:626-655). A community README from 2026-08 that quotes an `… and not is_hybrid` opt-in rule is stale at this pin. [Code-verified]
- Hybrid page arithmetic. The attention block follows the recurrent-state page and moves with every term in it. On one GB10 with Qwen3.8-Flash-Next the engine logged 1,568 tokens with no speculation, 1,600 at MTP 3 and 1,616 at k = 4; FP8 KV doubles the block (it halves the per-token bytes in the denominator), and `--mamba-ssm-cache-dtype bfloat16` halves it (1,600 to 832, predicted before the run) (jschmied). [Community-measured] Read the "Setting attention block size" line; do not derive it (§7).
- Trailing-block drop under speculation. `disable_eagle_block_drop` (PR #53388, merged 481839ad on 2026-09-01, an ancestor of the pin) stops speculative decoding from giving up one full hybrid block of cacheable prefix on every turn. [Code-verified] Measured effect in §4.
- SM12x blockwise-FP8 GEMM fixes. PR #52775 (merged 2b7fcbf5, 2026-08-19) changed the swap-AB dispatch from `(M <= 64) || (M % 4 != 0)` to `(M <= 64)`, so chunks with M not a multiple of 4 no longer fall to the small-M tile. PR #55180 (merged 4df80187, 2026-09-07) swizzles the CTA raster when the weight exceeds the 24 MiB L2. Both are ancestors of the pin and apply to blockwise-FP8 CUTLASS linears only. Builds older than those dates lack them, including the vLLM development base (dated 2026-08-25) that the own GLM lanes build on, which also lacks #53388. [Code-verified] Effects in §3 and §4.
- FP8 MoE on SM12x. `cutlass_group_gemm_supported` returns False for capability 110 and above (_custom_ops.py:851-853). [Code-verified] Issue #43507 (open, reproduced on DGX Spark 2026-05-23) traces this to a missing CUTLASS CollectiveBuilder specialisation for tensor- or token-scaled grouped FP8, so that FP8 MoE falls through to Triton. [Community-measured] [Interpretation] With only two GB10-tuned Triton configs shipped, tensor- or token-scaled FP8 MoE on GB10 most likely runs default-config Triton; this is not shown for block-scaled FP8 or other backends.
- DeepSeek V4 MoE in practice. Community DeepSeek V4 recipes force the b12x fused MoE and describe builds without it as "2x slower prefill" or "silently falls back to a ~2x-slower MoE path" (qualitative, no workload stated; NVIDIA forum thread 372268, dkmode22). Because vLLM keeps B12X out of auto selection on SM121, an unconfigured upstream serve does not get that path. [Community-measured] [Interpretation] DeepGEMM's `nv_dev` SM120 support (DeepGEMM #324, merged 2073ddb2) did not boot DeepSeek-V4-Flash on a dual-GB10 pair running a PR #41834 preview build of vLLM (`CUDA_ERROR_INVALID_IMAGE` in weight post-processing); the maintainer pointed to mainline vLLM, and no mainline GB10 result was found. Its published peaks are RTX PRO 6000 numbers. [Community-measured]
- Indexer top-k and shared memory. FlashInfer 0.6.18 `CanImplementFilteredTopK()` needs 131,072 B of shared memory per SM; GB10 reports 102,400 B (101,376 B per-block opt-in), so FilteredTopK is unavailable for every k, and the opt-in deterministic FlashInfer top-k dies in warm-up with `TopKRaggedTransform failed … operation not supported`. Separately, at indexer compress ratio 4 an `indexer_budget` of 8,196 or more exceeds the 2,048 filtered top-k limit on any GPU (PR #55872, open, head bccc06c5; comments from three GB10 units). The deterministic `persistent_topk` single-CTA path caches the row at 4 B per element, is bounded by `4,256 + 4n <= 101,376`, and sets `RADIX_THRESHOLD` to 22,016 (PR #55122, open, head b2312b2d). A commenter's own out-of-tree deterministic wrapper, which did not clamp, failed near 100K context with `dynamic smem 98080 exceeds 97120`. [Community-measured] [Interpretation] These walls are keyed to sequence length and top-k geometry, not to chunk size. The top-k kernel choice moves prefill (§4).
- Indexer logits cap in practice. Community GB10 builds set `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` to 128 (indexer logits "had been eating unified memory (and the drafter was amplifying it)", nacyot) or to 256 (a two-node DeepSeek V4.1 EXL3 recipe, sfxnz, reporting 21.6 / 23.2 GiB free per node after a 32K prefill and zero OOMs in ~30 boots). [Community-measured] Whether the cap can stand in for a smaller chunk is untested (§8).
- GLM indexer prefill workspace, in a recipe's vLLM tree (not upstream). `get_max_prefill_buffer_size` sizes the glm5next sparse-MLA indexer prefill workspace at `max_model_len x 40` entries, 5,036.40 MiB at 1M, requested at profile time and locked; the DeepSeek V4 call site divides by `compress_ratio` and the glm5next site does not (GLM EXL3 recipe PR #86, merged 36cedcbe). [Community-measured] Right-sizing it is measured in §4; spending the reclaim is in §7.

### SGLang

- Chunk and budget. `chunked_prefill_size` defaults by memory tier; the 90-160 GB tier gets 8,192 and the activation reserve is modelled as proportional to chunk size (arg_groups/memory_hook.py). SGLang reads capacity with `nvidia-smi --query-gpu=memory.total` and falls back to `torch.cuda.mem_get_info` when the output is unparseable (srt/utils/common.py:709-772); on GB10 that fallback yields about 119.7 GiB and the 8,192 tier. `max_prefill_tokens` defaults to 16,384, and its help text says the real bound is max(this, model context). `enable_mixed_chunk` defaults to False, so prefill batches do not carry decodes (arg_groups/fields/schedule.py:59-84, 209-212). [Code-verified]
- DeepSeek V4 indexer. fp32 logits are [rows, compressed columns]; rows per call = min(`_SM120_INDEXER_M_CHUNK` = 4,096, rows the memory budget allows), with the comment "DeepGEMM's paged-MQA metadata kernel cannot schedule more rows than this on SM120 (shared-memory cap)" (layers/attention/dsv4/metadata.py:66-108). The budget is free memory x `SGLANG_DSA_MQA_LOGITS_FREE_MEM_FRACTION` (default 0.2, environ.py:1640); reading free memory synchronizes the host, so it is skipped under CUDA-graph capture (metadata.py:297-318). [Code-verified]
- DSA backend (GLM-5 and DeepSeek V3.2). KV lengths up to `SGLANG_DSA_PREFILL_DENSE_ATTN_KV_LEN_THRESHOLD` (2,048) take a dense-attention path (used by dsa_backend.py and model_hook.py). This threshold belongs to the DSA backend, not to the DeepSeek V4 path. [Code-verified]
- GLM-5.3-Flash kpool indexer. `dsa_indexer_kpool.py` defines `_should_chunk_mqa_logits` (line 1010) with no call site; the CUDA branch of `_fp8_mqa_logits` calls `deep_gemm.fp8_mqa_logits` on the whole ragged batch, and row chunking exists only in the ROCm branch. The logits block therefore grows with chunk x total prompt length. [Code-verified] at 2909f84. This is the mechanism behind the GB10 chunk-size failure in §4.
- Block-FP8 linear on SM12x. `_dispatch_auto_backend` orders DeepGEMM, FlashInfer, CUTLASS, but `initialize_fp8_gemm_config` rewrites "auto" to CUTLASS on SM120-family GPUs, so the auto order is never reached there. DeepGEMM is enabled on 120/121 only when the installed build exposes the SM120 APIs (DeepGEMM#324, `mma.sync` block-scale) and is reached only through an explicit `--fp8-gemm-backend deep_gemm` or its own call sites (layers/quantization/fp8_utils.py:924-965; layers/deep_gemm_wrapper/configurer.py:35-48). [Code-verified]
- Mamba radix cache with an extra buffer. A `chunked_prefill_size` below `mamba_cache_chunk_size` "can make mamba_track_mask false for unfinished chunked-prefill handoff and skip Mamba state checkpoints"; `mamba_track_interval` must be at least the draft-token count and a multiple of `page_size` (arg_groups/mamba_hook.py:117-138). Radix is disabled only for specific models and modes, not because speculation is on. [Code-verified]
- Tuning guidance. The "5-8 GB available is good" rule sits in docs/docs/advanced_features/hyperparameter_tuning.mdx:45-53. It is a discrete-GPU rule; see §7. [Code-verified]
- Default MoE Triton configs. On GLM-4.7-FP8 across four GB10s, default configs requested 147,456 B of shared memory against GB10's 101,376 B limit and raised `OutOfResources`, but only with EAGLE on; tuned configs gave +6.3% decode with EAGLE off (15.77 to 16.77 tok/s, SGLang v0.5.4, TP4). No prefill was measured. [Community-measured] (BTankut, dgx-spark-sglang-moe-configs @ 5d4f546b)
- Hybrid radix reuse. At 2909f84, `mamba_radix_cache_strategy` (auto / no_buffer / extra_buffer / extra_buffer_lazy) and `mamba_track_interval` (default 256) exist, with validation hooks in arg_groups/mamba_hook.py; no rule disables radix reuse for hybrids in general. [Code-verified] A one-GB10 Qwen3.8-Flash-Next SGLang deployment reports ~99% prefix hits over a 120-turn tool-calling session (§4). The NVIDIA DGX Spark SGLang playbook (@ 3410c65f) states that cross-request reuse is skipped for hybrid Mamba/SSM models and `cached_tokens` stay 0; that note is tied to a floating image tag and shown on a ~150-token exchange, below the tracking granularity. [Interpretation] Treat it as unverified for its image and not as a statement about SGLang at 2909f84.
- Decoder SWA bounded replay. `--enable-decoder-swa-bounded-replay` exists for DeepSeek V4.1 (default False; srt/arg_groups/fields/exec_.py:104-107): "after the last kv_source layer, run the remaining layers over only the last window_size tokens of a prefill. Main and indexer KV stay exact". [Code-verified] Its only reported gain comes from eight GB10 nodes with an unstated prefill-timing method, outside this page's one-to-three-node scope (§8).
- Indexer metadata on SM120, per PR text. PR #29927 (merged 19c30dff, 2026-09-02; tested on RTX PRO 6000) describes the same 4,096-row metadata chunking ("the DeepGEMM row cap is SKU-dependent") and a paged-MQA metadata kernel that sizes its shared-memory request from the device budget instead of a fixed 128 KB. This is PR text, consistent with the code read above, not a separate read at the pin. [Interpretation] Its TTFT table comes from indexer, sparse-MLA and prefill-path changes with Marlin MoE in both arms, so it is not a MoE result, and it is not GB10.
- Chunk defaults in GB10 recipes. A Qwen3.8-27B SGLang recipe ships `CHUNKED_PREFILL=8192` with the note that "2048 gives smoother decode inter-token latency / better single-wave TTFT under mixed load, at some prefill-throughput cost" (@ 9fb18edf); a one-GB10 Qwen3.8-Flash-Next SGLang recipe defaults to 4,096 (shantanugoel @ 1a335740). Guidance, not ladders. [Community-measured]
- MoE fixes that never landed. PR #28038 (clamp default fused-MoE Triton configs to the 101,376 B limit) was closed unmerged by the stale bot on 2026-09-16; PR #17421 (add SM121 to the NVFP4 MoE SM check) was closed unmerged, and the file it patched no longer exists at 2909f84, where NVFP4 MoE runs through FlashInfer backends. [Code-verified] [Interpretation] The default-config shared-memory failure above is a Triton fused-MoE concern, not a general SGLang MoE one.
- Background, not GB10. PR #30272 (merged faf68940) makes FlashInfer MXFP4 x MXFP8 the SM120 MoE default for DeepSeek V4 with no dequantized weight copy; its numbers are RTX PRO 6000.

### llama.cpp and forks

- llama.cpp. `n_batch` 2,048 and `n_ubatch` 512 by default (common/common.h:451-452). A `GGML_CUDA_CC_DGX_SPARK` (1210) constant is used in decode (mmvq) and flash-attention dispatch (ggml-cuda/common.cuh:61). Quantized prompt processing uses MMQ on every Turing-or-newer part, including native FP4 MMQ for MXFP4/NVFP4, and MMQ needs at least 48 KiB of shared memory per block (ggml-cuda/mmq.cu:266-336). [Code-verified] The maintainers' GB10 benches run `-ub 2048 -fa 1` with no mmap (benches/dgx-spark/dgx-spark.md, build b7941). No `ubatch` ladder above 2,048 on GB10 was found.
- antirez/ds4 @ 0aaea5a2. Metal is the first target; the CUDA backend states "DGX Spark is our main goal" and supports multi-GPU and a multi-session server for DeepSeek V4 / V4.1 Flash, V4 PRO and Qwen3.8 Flash Next. It exposes `--prefill-chunk`. [Code-verified] (README)
- Entrpi/ds4 fork @ b0a147a7 and ds4-on-spark @ 99fb7b17. "Dequant-to-register" MoE GEMMs dequantize expert weights straight into MMA fragments with an expert-major CTA schedule for L2 reuse. The continuous-batching server ingests long prompts in `DS4_CONT_PREFILL_CHUNK` / `DS4_CONT_PREFILL_CHUNK_LIVE` steps (4,096 / 4,096; "smaller keeps live decode smoother, larger ingests faster"). `--cuda-tensor-parallel` mode uses 2,048-token chunks by default (to fit 16 sessions x 100K resident KV); the distributed layer-split mode's `--dist-prefill-chunk` defaults to 4,096. No chunk ladder is published. [Code-verified] (README)
- Anemll/dspark-vllm-gx10 @ 081fda97. Not a llama.cpp fork: a public two-node GB10 / SM121 port of vLLM 0.25.1 for DeepSeek V4 Flash DSpark, with a FlashInfer SM120/SM121 sparse-MLA bridge, a b12x MXFP4 MoE backend with GB10 small-M tuning, and a server-side prefill harness (ladder in §4). [Community-measured] The same organization publishes GB10 agent operating rules.
- Mainline llama.cpp on DeepSeek V4 Flash. Build b10235 (`221f0f635`) runs DeepSeek-V4-Flash-0731 UD-IQ2_M at pp2048 459-462 tok/s at depth 0 with `-b 2048 -ub 1024` (§4); the thread reports 200-370 tok/s in serving "depending on request shape". [Community-measured] [Interpretation] That is about 2.2-2.5x below single-GB10 vLLM and ds4-family rates on the same model family.
- Other ds4-family engines on one GB10. The xangel82 DS4-GB10 fork rebuilt its prefill pipeline: aligned in-place SoA MoE weights, D2R/MMQ prefill tiers, token-tile HMMA attention, a 68-byte MXFP4 indexer cache on native SM121a block-scaled MMA, and an exact top-512 radix select for large prefill batches. DwarfStar (ds4-dfm-rs) removed escapes from the tensor-core path: a K = 640 expert-down tail fused into MMQ, the shared expert moved from DP4A to MMQ, and a counting-sort routing map. A third engine, Athena Engine, publishes a server-timed depth ladder. Results in §4. [Community-measured]

### ExLlamaV3 in vLLM

- Upstream MoE prefill tiers (modules/block_sparse_mlp.py:25-43, 1098-1126; modules/moe_batch_recon.py @ 6b84a21). [Code-verified]
  1. Fused kernel for experts with at most `EXL3_MOE_FUSED_ROWS` rows (128, or 256 with wide tiles), launched as 16/32/64-row tiles. The docs state the cost directly: "The kernel dequantizes each expert's weights once per 16-row tile, so an expert holding 100 rows re-runs the whole B pipeline seven times" (doc/env_vars.md, `EXL3_MOE_MTILE`).
  2. Batched reconstruct: groups of up to 16 experts sorted by row count, padding at most 1.1x, at most 16,384 rows, 256 MB weight scratch; each group is dequantized to FP16 once and run as one strided-batched GEMM per projection. `RECON_TILES` 64 keeps large experts per-expert.
  3. Per-expert reconstruct above that.
- Host sync. `expert_count.tolist()` is skipped only when `num_tokens * top_k <= fused_rows`, so the per-layer host sync fires on every prefill chunk whose assignments exceed the fused-row capacity, which is effectively all prefill. [Code-verified]
- Dating. The tiers landed 2026-09-11 and 2026-09-12 (commits 893199c1, d5d56bdc, 1c8aff47, 2b3cc4ef), after the ExLlamaV3 extension pin the own GLM kit declares (c5d9c657, dated 2026-06-14). No GB10 measurement of the upstream tiers exists. [Code-verified]
- Upstream-reported gains, not GB10 (RTX PRO 6000, 4090 + 3090): wide tiles cut fused-kernel time 30-47% at 24-128 rows per expert "on every GPU generation"; model level with 4K chunks Qwen3.8 +10% (PRO 6000), +3% (4090 + 3090), gemma4-26B +1-4%, Qwen3-30B neutral; fused rows 128 to 256 took 6.87k to 7.06k tok/s; batched reconstruct +16% prefill on a 512-expert model at 8K; deterministic accumulation "costs nothing measurable". [Community-measured] (doc/env_vars.md @ 6b84a21) Background only.
- `SMEM_MAX` is a 90 KiB `#ifndef` default, commented as the CC 8.6 maximum (exllamav3_ext/quant/exl3_moe_common.cuh:21-23). [Code-verified]
- Release. Tag v1.5.0 (`0740edc2`, published 2026-09-13) contains 893199c1 and 2b3cc4ef (GitHub compare API). [Code-verified]
- Fat-expert paths measured on GB10 through vLLM overlays. The two-node GLM-5.3-Flash EXL3 recipe added E2 (sorted routing, batched fat experts, direct and scatter CUDA kernels for "fat" experts) and then E3 (`EXL3_FAT_GROUPED=1`): three GPU launches per MoE layer (gather, gate/up + SwiGLU, down + scatter), built from device-side segment tables with no host sync. An independent two-GB10 kit (Reederey87) adds a fat GEMM that dequantizes the packed trellis inside a warp `mma.m16n8k16` with fused Hadamard and scatter, and a 3-stage `cp.async` k-loop that took the kernel from 52 to ~73.5 TFLOP/s, bit-exact over 56 comparisons; its grouped kernels run at 33.0-33.2% of a 33.33% theoretical occupancy ("no gap to close"). Gains in §4. [Community-measured] The own GLM lanes run the grouped path; its gate/up and down kernels appear in the §4 profile. [Measured]
- The fused-row cap moves in opposite directions for a reason. [Interpretation] Without a fast fat-expert path, a higher cap keeps experts off the slow whole-expert reconstruct (vllm-exl3 raised 128 to 2,048 to fix a >163K stall); with E3, a lower cap sends more rows to the grouped path (128 to 32 gained 13-16%, §4); the recipe author's pre-E2 raise to 1,024 lost 13-24% (§4). The best cap depends on which fat path exists.
- vllm-exl3, a separate public vLLM plugin (@ 78e17279). When a prefill call has more tokens than `TEMP_ROWS_FUSED` (default 2,048) and any expert count exceeds it, the fused path re-runs per slice of at most `TEMP_ROWS_FUSED` tokens, so each token adds at most one row per expert (src/vllm_exl3/exl3.py lines 2042-2060). The `(counts > TEMP_ROWS_FUSED).any().item()` host sync is guarded by `tokens > TEMP_ROWS_FUSED` and never runs at MNBT <= 2,048; a second sync, `fat.any().item()`, runs when tokens exceed `FAT_EXPERT_THRESHOLD`. [Code-verified] Release 0.4.2 fixed a fat-path correctness bug and a short-prefill wedge (§7). Its README states that the K2/K3 grouped-prefill planner has "no grouped CUDA executor; `execution_available` is false". [Code-verified]
- Native ExLlamaV3 1.5.0 on GB10. On one GB10 with Qwen3.8-Flash-Next, native 1.5.0 (extension JIT-built for sm_121) matched the vLLM + EXL3 plugin at 24K and had a slower cold 3K TTFT (§4). Inside the plugin, 1.5.0 vs 1.4.7 left prefill unchanged because the plugin passes the 1.4.x all-fused arguments, so the new tiers were not engaged. No arm isolates the upstream tiers; they remain unmeasured on GB10 (§8). [Community-measured]
- The vLLM + EXL3 integration the GLM and DeepSeek V4.1 lanes use is an out-of-tree overlay with its own grouped fat-expert kernel on top of the ExLlamaV3 `exl3_moe` extension. Large-M BF16 reconstruction of weight-only FP8 projections exists in that kit, not upstream (§4, §5). [Measured]

## 3. What is different on GB10 / SM121

- [Community-measured] Tensor-core ceilings. Register-resident MMA peaks on one GB10 (mmapeak, CUDA 13.0.2, clock not stated): BF16 or FP16 with FP32 accumulate 212.9-213.1 TFLOPS, FP8 with FP32 accumulate 213.7, MXFP4/NVFP4 427.3, INT8 215.1, TF32 53.3 (NVIDIA developer forum thread 351993). Packed `mxf4nvf4` dense reached 486-511 TFLOPS at about 2.6 GHz and byte-padded `mxf8f6f4` 243-256 across three units (nvfp4bench). These are ceilings, not achieved serving rates. The same mmapeak probe measured FP8 with FP16 accumulate at 213.8 TFLOPS. Tensor-core peak is contested, on single-probe evidence: mmapeak (NVIDIA forum 351993, clock not stated) reads BF16 ≈213 and FP8 ≈214 TFLOPS [Community-measured]; a hand-PTX probe (getpoppy) reads BF16 123.3 / FP8 246.5 / NVFP4 493 TFLOPS, an exact 1:2:4 ladder that matches nvfp4bench's `mxf8f6f4` 243-256 and the 500 TFLOPS dense-FP4 figure [Community-measured]. Until an own register-resident probe at a recorded clock settles it, assume neither 'FP8 = BF16 rate' nor 'FP8 = 2x BF16'.
- [Community-measured] A CUTLASS NVFP4 GEMM peaks at about 375 TFLOPS at 4,096 x 14,336 x 4,096, which its author calls the memory ceiling, not the compute ceiling; shapes of 8,192 cubed and above throttle thermally. The block-scaled FP4 MMA needs `-gencode=arch=compute_121a,code=sm_121a`; the `-arch=sm_121a` shorthand silently yields plain `sm_121` (nvfp4bench @ df8e8f46).
- [Community-measured] Bandwidth. STREAM triad 205-207 GB/s (nvfp4bench) and kernel-effective ~215 GB/s copy / ~227 GB/s read-only (Entrpi ds4-on-spark `bench/bw_bench.cu`), against 273 GB/s nominal. Achievable bandwidth is about 215-245 GB/s depending on the probe (contested; single-probe figures per tool family: saturating read 227-235, rotating-buffer read 238.6-245.9, copy 215-229, STREAM triad 200-214 GB/s [Community-measured]); the enumeration is on [Decode optimization](05-decode-optimization.md) §3. [Interpretation] Any prefill step that re-streams expert weights (thin kernels, small chunks) is bounded by that probe-dependent range.
- [Interpretation] Prefill is clock-sensitive but only partly compute-bound. A -12.5% nominal clock cap cost -4.9% prefill and -21% cost -9.1% (elasticity about 0.4) while C1 decode means were 5-6% lower, inside rep spread (2026-09-21 GPU clock-cap sweep, GLM 5.3 Flash EXL3 TP3; see [Clocks, thermal, and power](13-clocks-thermal-power.md)). A recipe author's analysis puts expert streaming at chunk 1,024 near 112 FLOP/B, below the ridge. Under a 2,100 MHz cap, whichever BF16/FP8 ceiling holds is roughly 0.8x its ~2.6 GHz figure.
- [Interpretation] Unified memory. Activation, attention and indexer workspaces sit outside the GPU-memory fraction the engine reserves, so the prefill working set competes with the operating system, not with a separate VRAM pool. Community sizings are all linear in chunk x prefix: about 9.32 bytes per (token x batch-token), 11.45 GiB at 600K x 2,048, not sharded by decode context parallelism (0xdfi, GLM-5.2 on four GB10s); about q_rows x total_tokens bytes, 328 MB at 40K and 1.07 GB at 131K with chunk 8,192, against 2.98 GB available after graph capture (SGLang #36941); about 14 B x chunk x prefix, ~15 GB at chunk 1,024 x 1M (DeepSeek V4.1 TP3 recipe README). [Community-measured]
- [Code-verified] Memory probes misread the device. `nvmlDeviceGetMemoryInfo` is unsupported on GB10, so vLLM's MNBT tier logic falls to its smallest tier; SGLang falls back to `torch.cuda.mem_get_info` (~119.7 GiB) and picks the 8,192 tier. Two engines, two different defaults on the same box.
- [Community-measured] Shared memory is 102,400 B per SM and 101,376 B per block (opt-in). It rules out FlashInfer FilteredTopK, which needs 131,072 B per SM, and bounds the deterministic `persistent_topk` path (vLLM PRs #55872, #55122; §2). Default SGLang MoE Triton configs asking for 147,456 B fail (EAGLE on, BTankut); SGLang caps its DeepSeek V4 indexer at 4,096 rows per call on SM120 for the same reason [Code-verified]. [Interpretation] No equivalent cap exists in vLLM's indexer; a GLM recipe's "8,192 unsafe (indexer smem)" note has no upstream vLLM counterpart and was never tested (§8).
- [Community-measured] Formats. "On SM12x NVFP4 is not a memory or throughput win versus MXFP4": about 4 GiB per GPU larger, single-stream prefill marginally faster, decode marginally slower (vLLM PR #41834 author, two GB10s). vLLM keeps its SM12x-specific FP4 MoE kernel (B12X) out of auto selection [Code-verified]. The earlier claim that SM121 lacks an FP4 conversion instruction was retracted by its author (ai-muninn, update 2026-08-23): the MMA fires on the W4A4 path, and the measured slowdown came from software picking the wrong kernel path.
- [Community-measured] Chunk steps below GEMM saturation are expensive only for MoE. On one GB10 (llama.cpp b7941, `llama-batched-bench -ub 2048 -fa 1`, batch 1), the 512-token rate was 45-55% of the 4,096-token rate for four MoE models, while dense Qwen2.5-Coder-7B was faster at 512 (2,420 vs 2,237 tok/s) and Gemma-3-4B was 5,567 vs 6,080. [Interpretation] The short-step penalty tracks per-expert GEMM size, not a general per-step fixed cost.
- [Community-measured] L2 is 24 MiB (`l2CacheSize` 25,165,824 B), and blockwise-FP8 CUTLASS throughput falls with M once the weight exceeds it: 10240 x 2560 (25 MiB) ran 173 / 90 / 64 TFLOPS at M = 4K / 8K / 16K, and 12288 x 2560, 16384 x 2560 and 5120 x 5120 behaved alike. A tile-scheduler swizzle of 8 restores 148-168 TFLOPS at every M, bit-identical, at a 5-9% cost at M = 4K when the weight already fits in L2 (jschmied, standalone single-launch benchmarks, two starts each; upstream as vLLM PR #55180). [Interpretation] On pre-fix builds a larger chunk lowers per-token GEMM efficiency for these projections: a second mechanism, independent of indexer memory, by which a bigger chunk fails to help on GB10. It concerns blockwise-FP8 checkpoints, not Marlin, EXL3 or BF16 paths.
- [Community-measured] M alignment. Before vLLM PR #52775, blockwise-FP8 chunks whose M was not a multiple of 4 ran the small-M tile. Padding to a multiple of 4 cut 8K TTFT from 4.52-4.57 s to 2.86 s (-37%) and 30K from 12.6 to 11.5 s (-9%) on a preview build (jschmied, batch 8,192). A profile of the same build put 48.1% of an 8K prefill in FP8 blockwise projections, all on the swap-AB tile.
- [Community-measured] Achieved kernel throughput on GB10, each at its source's shape and none an end-to-end MFU: CUTLASS NVFP4 dense 356 TFLOPS at 4096 x 14336 x 4096 (~71% of the 500 TFLOPS dense-FP4 figure) and NVFP4 MoE grouped GEMM 120-154 TFLOPS (8 and 64 experts, N = 256) (baristankut, NVIDIA forum thread 359960, CUDA 13.1, CUTLASS 4.4.0, who calls the 101 KB shared-memory limit "the main constraint, not compute"); blockwise FP8 CUTLASS 150-173 TFLOPS in L2 or swizzled and 52-97 past L2 without the swizzle; Triton FP8 `tl.dot` mainloop ~100 and `dot_scaled` 66 TFLOPS (jschmied finding 99); the EXL3 trellis-dequant fat GEMM ~73.5 TFLOP/s (Reederey87). The same forum post's 188 TFLOPS FP8 figure states no shape and is not used here.
- [Community-measured] Unified-memory accounting. Docker `--memory` does not bound GPU allocations on GB10 (NVIDIA forum thread 371180). A default utilisation of 0.9 pre-allocated ~89 GB of KV for a single-user Nemotron Nano (thread 364886). MemAvailable is a per-fleet floor, not a gauge: 10.3 GiB after a full 1M request on a four-node fleet against 1.1-2.4 GiB in normal serving on a two-node pair with zero OOM kills (DeepSeek V4.1 EXL3 recipe issue #19), so the useful number is the change a chunk arm produces. Allocators add their own growth: a native DeepGEMM logits allocator ratcheted reserved memory +1.89 GB per 15 minutes under mixed-length prefills until bounded bucket reuse fixed it, and fragmented UVM stalled an 18 GiB KV allocation for 20+ minutes until `compact_memory` cleared it (nacyot).

## 5. Levers, ranked

1. **Size the chunk budget per model, indexer path, memory headroom and build, not by "bigger is faster"** — applies to: every engine x every model family x every topology. Gain: from -4% per halving (GLM 5.3 Flash EXL3 TP3, vLLM, 8K-524K) through +7.8% (Qwen3.8 Flash Next, 2,048 to 4,096 at 500K) to +26% (DeepSeek V4.1 EXL3 TP3, 1,024 to 8,192 at 32K) [Measured]; community GB10 results run the other way where the indexer transient is unbounded: SGLang GLM-5.3 kpool at 102K times out at 8,192 and is fastest at 2,048, TRT-LLM gpt-oss-20b improves P95 TTFT as the budget falls from 8,192 to 2,048 under C4 load, Hy3 buys only ~+3% for 16,384 [Community-measured]. Contested on one model family, so do not average: on GLM-5.3-Flash EXL3 over two GB10s an independent repeated ladder (5 cold reps per rung, anchor boot) is flat within ~2% from 2,048 to 7,168 and -6% at 1,024, while a maintainer one-shot put 7,168 about 6-10% above 2,048 at 100K-256K [Community-measured]; the repeated ladder has the strongest protocol, and the own TP3 result (~4% per doubling) differs in topology, fat-expert tier and engine settings, so all three can hold and none transfers without a matched run [Interpretation]. On DeepSeek V4.1 EXL3 the single-variable evidence (own +26% at 32K; +23% at 2K-64K for 1,024 to 3,072 on a community pair) favours a bigger chunk until end-of-prefill headroom runs out; the one negative report (-5% at 12.7K) changed two things at once and was +11% at 3.2K [Community-measured]. Cost: KV capacity (3.37M to 2.58M tokens from the same 32 GiB/rank on the GLM TP3 lane; -306K on DeepSeek V4.1 EXL3; -29% at 7,168 on the external GLM ladder), draft-model reservations that scale with the budget (-640K context on GLM TP2), longer decoder stalls (1.02 s to 2.37 s), and host memory (~4 GiB at 8,192 on DeepSeek V4.1 EXL3). Risk: a silent wedge at depth (MNBT 3,072 stopped a DeepSeek V4.1 EXL3 prefill at ~140K with no error), a later crash after lowering MNBT on a build that locks warm-up workspaces [Community-measured], and the head-node wedge in §7 [Historical diagnostic]; headroom is not monotone in chunk size (1,024 to 1,536 raised boot headroom 0.09 to 3.50 GiB on the same pair). On blockwise-FP8 checkpoints, builds older than vLLM PR #55180 also lose GEMM efficiency above 4K chunks (§3). Smallest falsifying experiment: one arm per boot at the current value and one rung either side, cold 8K and 100K x 3 plus one memory-watched probe past 128K and the short-decode fixture; if no rung beats the current value by more than the measured noise floor without losing capacity or decode, the lever is exhausted for that lane.
2. **Scheduling for mixed prefill and decode: fair interleave, LPT, a cap on concurrent partial prefills** — applies to: vLLM (any family, any topology; V1 has no upstream partial-prefill cap), ds4 continuous batching (`DS4_CONT_PREFILL_CHUNK_LIVE`). Mechanism: decode tokens produced during a long prefill ≈ (prefill tokens / chunk) x accepted tokens per decode step, so a smaller budget gives incumbents more steps, while LPT, not the budget, is what lets a newcomer in [Community-measured] [Interpretation]. Gain: 2K newcomer TTFT 130 s to 5.9 s and 8-stream aggregate +12.6% from fair vs skip (GLM TP3) [Measured]; first-token spread -39% from two in-flight prefills (DeepSeek V4 TP2) [Measured]; worst decode 0.36 to ~15 tok/s from an admission cap plus LPT 1,024 [Community-measured]. MNBT 8,192 to 2,048 raised decode share during a 262K prefill from 1.7% to 5.0% and cut the p95 output gap 6.10 to 1.64 s but admitted a newcomer no faster (~145 vs ~159 s); MNBT 2,560 + LPT 2,048 admitted short requests beside a deep prefill; MNBT 8,192 to 4,096 cut short-request TTFT during a long prefill by 30% on GLM TP2; a fork's mixed-prefill cap raised decode during a 76K prefill from 2.24 to 12.44 tok/s [Community-measured]. Cost: incumbents slow ~30% while newcomer chunks run; a cold prefill beside a decoder under LPT 1,024 drops ~890 to ~245 tok/s (GLM TP2) [Measured]; prefill -7.7% at MNBT 2,048 and -5 to -8% with MNBT 2,560 + LPT 2,048 (DeepSeek V4 TP2), ~6% worse solo TTFT at 4,096 (GLM TP2) [Community-measured]. Risk: LPT 0 raises the working set (warm headroom 5.6 to 4.0 GiB on DeepSeek V4 TP2) [Measured]; after vLLM PR #57951 solo requests ignore LPT. Smallest falsifying experiment: incumbent decoder plus a 2K and a 30K newcomer, and 4 x 8K cold, with the cap at 1 and 2 on the same build, decode counted from streamed token ids matched to usage (never from SSE events); the lever fails if the spread and worst-stream TTFT do not improve beyond trial spread.
3. **Protect the warm path: stable prompt head, block alignment, cache-safe directive placement, correct cache accounting, correct hits** — applies to: all engines with prefix caching; largest on hybrid-attention models in vLLM. Gain: the largest recorded wins, in TTFT rather than tok/s: 300K second turn 345.5 s to 10.0 s after a draft-model block-id fix; a per-turn directive moved before the last user message keeps 14,336 of 16,579 tokens cached (14.9 s to ~2.5 s) [Measured]; 53.9 s to 0.69 s at 29K in the ds4 fork; a changing field at the start instead of the end costs 13.7-39.6x per turn; `disable_eagle_block_drop` -26% per warm turn under MTP; a block-aligned prefix hit plus 1 token 0.61-0.84 s to 0.153 s; retention interval 0 on a kit that extends it to Mamba groups 0% to 95-98% round-2 hits; a coordinator patch took a drafter recipe from zero hits to 0.986; an SSD tier restores a 493K session in 7.8 s against 392 s cold [Community-measured]. Cost: template discipline; for hybrids a trailing partial page still costs ~6 s per turn until internal checkpoints land (vLLM PR #56960 open for GLM KDA) [Measured]; a bf16 SSM state halves the block and the cached-prefix intercept but moved 5.1% of top-1 predictions, a tail lever rather than a free one [Community-measured]. Before citing the retention-interval result for a lane, check that its build carries the Mamba-group extension. Cache mechanics are on [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md); hybrid state on [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md). Risk: on GB10 hybrids a hit can be wrong, not only slow (§7). Smallest falsifying experiment: two-turn fixture at 16K and 100K with a varying per-turn field; record cached tokens, TTFT and output equality against a cache-off run; the lever fails if cached tokens fall below the same-prompt control's ceiling (to the page grain) or any output differs.
4. **MoE prefill kernels: grouped fat-expert paths, dequantization inside the MMA, slow-path removal** — applies to: vLLM + EXL3 MoE lanes (measured on GB10 externally), ds4-family engines (measured), DeepSeek V4 on vLLM (b12x MoE, qualitative only), Triton fused-MoE shapes outside the two shipped GB10 configs. Gain: E2 fat-expert kernels +20-21% at 8K-300K with complete separation, reproduced on a second deployment; E3 grouped dispatch +37-45% over E2 (32K and 64K E2 values interpolated, 128K against a 100K run) and +19.6% over a pipelined E2 in an independent kit; temp-row cap 128 to 32 with E3 +13-16% on TP2 with no measured decode loss; a trellis-dequant fat GEMM +11-18% at 178K-254K; 2.43-3.30x over upstream ds4; 350-400 to 854 tok/s on a ds4-family fork [Community-measured]. The own GLM lanes already run the grouped path [Measured]. Upstream ExLlamaV3 batched reconstruct +16% on non-GB10 hardware; on GB10 no arm isolates it [Proposed]. Cost: kernel work or an image rebase ([Kernel authoring on SM121](15-kernel-authoring-sm121.md)); scratch charged to KV (560 MiB for E3). MoE backends are on [MoE dispatch](08-moe-dispatch.md). Risk: the best fused-row cap depends on which fat path exists (a 1,024 cap lost 13-24% on a pre-E2 build); row tiling (-18% to -61%), a fused gather (-10.7%) and own geometry variants (4-219% slower) lost [Community-measured] [Measured]; a pre-0.4.2 vllm-exl3 fat path was numerically wrong for distinct-`suh` packs (§7); on TP3 a temp-row cap of 32 is estimated, never measured, to cost 5-7% decode [Interpretation]. Smallest falsifying experiment: component A/B of the candidate kernel at the lane's expert shapes and chunk, then one cold 8K/100K ladder on/off/on with 5 salted samples per rung plus short decode, only if the component wins by more than 10%.
5. **Large-M BF16 reconstruction for weight-only-quantized projections** — applies to: vLLM + EXL3/Marlin weight-only FP8 or INT4 projections (the KDA input projection on GLM 5.3 Flash measured); no upstream vLLM switch exists. Gain: +7.20% at 7.6K and +7.93% at 95K as part of a group; component 2.17-2.25x at M = 2,048 [Measured]; a recipe author's TP2 port reports TTFT -11.4% at 16K and -12.3% at 100K (median of 20, A/B/A) [Community-measured]. Cost: +2.264 GiB per rank for the retained BF16 copy (formats: [GEMM backends and quant formats](09-gemm-backends-and-quant-formats.md)). Risk: numerics (rel-RMSE <= 0.004 measured), boundary choice (M > 512 is the only qualified value). Smallest falsifying experiment: boundary sweep at M = 128 / 512 / 1,024 on the lane shape with 5 matched cold samples at 7.6K and 95K.
6. **Choose dense-projection precision by workload: BF16 for prefill-heavy, FP8 weight-only for decode-heavy** — applies to: GLM 5.3 Flash EXL3 (measured), any weight-only FP8 dense path on SM121 (whether FP8 MMA runs at the BF16 rate or at 2x is contested, §3; precision choices are on [GEMM backends and quant formats](09-gemm-backends-and-quant-formats.md)). Gain: FP8 decode +7-14% at short depth (+1% at 120K) and more context headroom; FP8 prefill −18 to −21% (BF16 is 22-26% faster) [Measured]. Cost: memory. Risk: low. Smallest falsifying experiment: the same two arms on real traffic with the ratio of new prompt tokens to output tokens recorded; the recorded break-even was about 1K output per 27K new prompt tokens.

## 6. Protocol

This is the cold-ladder protocol for any prefill change. It follows the fleet rules on the entry page and the incidents in §4 and §7. See [Profiling protocol](14-profiling-protocol.md) for kernel attribution.

Preconditions.
- Clean window: no outside traffic. Poll running requests and any client shim's in-flight count before each pass; discard any pass that overlaps outside traffic.
- No memory overcommit: at least 8 GiB MemAvailable on every node before a start, 5 GiB warm floor while serving, and stop all benchmark traffic at 4 GiB MemAvailable on any node. Swap is not headroom. KV pin raises no more than 1.5 GiB per boot, and memory freed by one change is never spent in the same boot. MemAvailable floors differ by fleet, so judge an arm by the change it produces against its own baseline, not by another fleet's absolute number.
- One variable per boot. A restart for an A/B skips the image pull, so the only difference is the variable under test.
- Restart between arms on speculative hybrid lanes, and record cumulative `vllm:prompt_tokens_total` with every number: a long-running engine has moved a 24K prefill by +86% until restart (§4).
- One compile cache per arm: a torch.compile cache shared across arms contaminates A/Bs because its key omits env-gated branches. Confirm from a log line or profile that the arm runs the kernel under test; an arm can fall back to the stock kernel behind a layout guard.
- Never restart a client gateway; restarting the lane's engine is the operator's step, and a gateway restart is the operator's decision.
- Never `pkill -f` a pattern that also matches your own shell.
- Record the build: engine commit, and whether it includes vLLM PR #57951 (solo LPT bypass), PR #52789 / #56960 (internal checkpoints), PR #52492 (capture guard for #49486), PR #53388 (`disable_eagle_block_drop`), and, for blockwise-FP8 checkpoints, PR #52775 (M alignment) and PR #55180 (L2 swizzle).

Change. Exactly one of: MNBT or chunk size, LPT, in-flight prefill cap, mixed-prefill policy, a kernel or backend switch, a precision change, the fused-row cap, the indexer logits cap or top-k kernel. Chunk rungs are multiples of 512. On a hybrid, rungs relate to the scheduler block only if the logged scheduler block equals the hybrid page; read it, do not derive it (§7).

Run.
1. Boot. Record the resolved configuration line (vLLM: "Chunked prefill is enabled with max_num_batched_tokens=...", "Setting attention block size to ... tokens", block size, hash block size, `mamba_cache_mode`, partial-cache-hit; SGLang: `max_total_num_tokens / chunked_prefill_size / max_prefill_tokens / available_gpu_mem`), the KV capacity log, and MemAvailable per node. Size the pool from the boot line, never from bytes-per-token arithmetic.
2. Warm-up: one discarded request per shape, logged separately (first requests after boot ran 813 vs 1,375 tok/s and 11.8 vs 5.3 s in own §4 packets, and 999 vs ~1,500 and 418 vs 1,112 tok/s on a community GLM EXL3 recipe; a first-request JIT compile caused a retracted "40K kills the worker" report in SGLang #36941).
3. Cold ladder, one request at a time: unique salt or nonce at token 0, 8-token output, prompt tokens from the usage block. Accept a row as cold only when all of these hold where the engine exposes them: `cached_tokens == 0`, a zero delta in `prefix_cache_hits_total`, a zero delta in local cache hits, and locally computed tokens equal to prompt tokens; a missing field fails the row. Depths 8K, 32K, 100K and 250K, then 524K and 1M where the lane serves them. Three repetitions up to 131K; n=1 above 131K may be reported as a labelled probe but never promotes a change; decide on at least 3 repetitions with a closing baseline (A/B/A).
4. Exact repeat after each cold request: cached tokens and TTFT (a miss where the baseline hit is a failure, as at 524K under MNBT 7,168). On a hybrid, also compare the output of the hit with a cache-off run of the same prompt.
5. Short decode fixtures, 3 repetitions, on every chunk or budget arm (a "kept" budget once hid a 16% decode loss). Count decode tokens from streamed token ids or `usage.completion_tokens`, never from SSE events.
6. Concurrency probe: an incumbent decoder plus a 2K and a 30K newcomer (record the incumbent's longest inter-token gap, its decode share during the newcomer's prefill, and newcomer TTFT), and 4 x 8K cold (first-token spread and worst stream).
7. Long-prompt memory probe: on every chunk arm, one request past 128K under a memory watch at 1 s resolution (the failure mode is a silent wedge at ~140K, §7); record minimum MemAvailable per node and the NVIDIA allocation-error count.
8. Optional profiler run at one depth. Never score it (profiler on: 32K TTFT 23.8 to 35.96 s). For per-step timing without the profiler, `--enable-logging-iteration-details` gives scheduled tokens per step and host wall time around the GPU wait; pair it with a GPU-side timer.

Record (packet fields): engine and image commit and the PRs above, the resolved configuration line, the one variable and its two values, topology and slots, KV capacity, per depth: prompt tokens, TTFT, effective prefill, repetition spread, cached tokens on repeat; next-chunk-at-depth and whole-context rates kept separate where the harness reports both, with the metric named (prompt / TTFT, server-timed prefill, local compute / TTFT, or prompt / total client wall); short-decode tok/s; incumbent gap and decode share; C4 spread; minimum MemAvailable per node; allocation-error count; `vllm:estimated_flops_per_gpu_total` or the MFU log line with the peak assumed, naming which candidate (BF16 ≈123 or ≈213 TFLOPS, FP8 ≈214-256, FP4 ≈427-511 (contested; single-probe evidence), §3) and the lane's clock; cumulative prompt tokens since boot; for EXL3 lanes the fused-row cap and the fat-expert path (E2, E3 or none); for sparse-indexer models the indexer logits cap and top-k kernel (stock, exact or deterministic), because the kernel alone moves prefill by 0-40%; contention flag per pass; discarded passes and why. For long prefills use per-request prefill duration or TTFT with usage counts, not interval counters (vLLM credits prompt tokens only when a prefill completes).

Pass gate. Every depth at or above baseline beyond the noise floor, or a stated trade accepted in advance. The floor is ±2% for whole-context prefill on repeated runs within one boot; measure start-to-start spread on the lane, and where it is larger (one community stack measured ±20% start to start for prefill and 6.9% for decode) use two or three server starts per arm and gate on that spread. Treat build-to-build differences under ~15% on decode as unresolved without a blocked design. Short decode within repetition spread; exact repeats hit wherever the baseline hit, with outputs equal to cache-off; incumbent longest gap not worse; zero NVIDIA allocation errors through the past-128K probe; minimum MemAvailable at or above the 5 GiB warm floor on every node; KV capacity change recorded and accepted.

Rollback. Revert the one variable, restart with the pull skipped, confirm the configuration line matches the baseline, and run one cold 8K plus its exact repeat; both must match the baseline within repetition spread before the lane serves again.

## 7. Anti-patterns and known-bad

- [Historical diagnostic] A ~200K-token agent turn on a three-node DeepSeek V4.1 SGLang lane (chunk 1,024, static memory fraction 0.95) exhausted per-rank host memory during prefill while the KV pool was only 25-28% full. The prefill working set (indexer transient ~14 B x chunk x prefix, about 2.9 GB at 1,024 x 200K, plus allocator growth) is not bounded by any KV or context setting. Chunks took 2-3 minutes, the client retried eight times on 60 s timeouts, and the head node became unreachable (the incident record is titled a head-wedge record, and whether only the head or all three nodes wedged is recorded differently across pages and unresolved). Rule: cap the request or the chunk, require zero allocation errors at 131K before serving (2026-09-16 head-wedge incident record, DeepSeek V4.1 Flash SGLang TP3).
- [Measured] Nonfatal NVIDIA allocation errors during 32K (6) and 131K (104) prefills preceded that incident and were read as harmless. Treat any allocation error during prefill as a failed memory gate (2026-09-15 fast-profile scorecards).
- [Measured] Swap is not prefill headroom: 16 GB of swap was enabled and 0 MiB used while 104 allocation errors fired (same packets). [Community-measured] Host sysctl hardening (`vm.min_free_kbytes`, cache pressure, dirty ratios) turned node freezes into clean worker deaths on a two-node GB10 SGLang pair but did not stop the worker dying (SGLang #36941).
- [Historical diagnostic] Spending memory freed by one change in the same boot (an indexer-workspace resize plus a +4 GiB KV pin raise with 4.4 GiB host free) left a head node unreachable until a power cycle. One memory variable per boot.
- [Measured] Transplanting community prefill knobs without the host-memory budget: LPT 0 cost 1.6-1.9 GiB of warm headroom on a DeepSeek V4 TP2 lane, because activation, attention and indexer workspaces live outside the engine's memory fraction (2026-09-03 threshold-0 rejection).
- [Measured] A larger budget that hid a decode loss: MNBT 10,240 was "kept" until short decode was re-run (50.6 to 42.5 tok/s) (2026-08-20 speed-headroom packet). Every budget arm re-runs short decode.
- [Measured] Modelling the chunk sequence from the recurrent-state page instead of the logged scheduler config: a predicted 2,048/512 alternation from a 2,560-token page did not exist, because the running scheduler used block 64 and hash block 64 (2026-09-20 startup and prefill optimization). The page-grown block applies only where the logged scheduler block equals the hybrid page (the 1,664-token Flash Next and 3,584-token GLM TP2 cases).
- [Measured] Reading the headline KV pool as the shareable prefix cache: a 501,152-token pool had ~6,960 tokens of shareable cache because of a draft-model block-id bug, and an interleaved request of ~2,540+ tokens wiped it (2026-08-28 500K stabilization). Read the engine's cache-config metric.
- [Measured] Anything that varies near token 0 (thinking or effort toggles, dates, directives) re-prefills the whole prompt: ~84 s at median depth and ~157 s at p90 per toggle on real traffic (2026-08-30 metered traffic).
- [Measured] Two long sessions evict each other: two ~275K sessions on a 896K pool dropped from 97.7% to 0% cached (8.3 s to 319 s). Keep one long thread hot per lane.
- [Measured] Scoring profiler-on or first-after-boot runs (§4, DeepSeek V4.1 EXL3 rows). [Community-measured] Reused filler served from the radix cache inflated one reported rate from 494 to 2,914 tok/s before the reporter retracted it (SGLang #36941).
- [Community-measured] Treating flat engine counters as a hung engine: vLLM credits prompt tokens only when a prefill completes, so an 870 s window with every counter flat was a long chunked prefill (vLLM #54919). Conversely, logger interval rates are bursty for long prefills, so "trust the engine logger" (0xdfi) holds for totals, not for per-interval rates. [Historical diagnostic] A hung-step watchdog does not catch a slow but progressing prefill.
- [Code-verified] One engine's dashboard "prefill rate" is uncached compute throughput, not cold full-prompt throughput (2026-08-29 throughput-semantics audit). [Community-measured] llama-benchy falls back to the gpt2 tokenizer when the served model name does not resolve, so depth labels become approximate, and its throughput is invalid under speculative decoding (fankserver).
- [Community-measured] The SGLang "5-8 GB available is good" guidance is a discrete-GPU rule; a GB10 run with 2.98 GB after graph capture timed out at 8,192-token chunks at 102K (SGLang #36941).
- [Community-measured] Row-tiling the fat experts (-18% to -61%) and raising the fused temp-row cap to 1,024 (-13% to -24%) both lost on a two-node GB10 GLM 5.3 Flash EXL3 lane (recipe author's notes @ 0c098aa6). [Measured] Three grouped fat-expert kernel geometries were 4-219% slower than stock at 1,024-8,192 rows; a hashed-embedding row cache cut lookups 338 ms to 8-30 ms but moved end-to-end by +0.4% / -2.1% (2026-09-16 prefill profiling and tuning).
- [Measured] Chunk 7,168 on the GLM TP2 lane bought +4-12% prefill and cost ~640K of context through the draft model's budget-scaled reservation (2026-09-08 E4 candidate A/B).
- [Interpretation] Stale guidance: a 2026-07-09 blog says LPT defaults to "about 4% of context length" and that `max_long_partial_prefills` / `max_num_partial_prefills` cap long prefills; at vLLM 711fc55 LPT defaults to 0 and V1 has no partial-prefill cap (dreaming.press, fetched 2026-09-23).
- [Interpretation] Two vendor rows are not cold compute measurements: Qwen3 235B on two nodes at 23,477 tok/s implies about 1.03 PFLOPS (the combined dense-FP4 peak of two GB10s), and Qwen2.5-VL-7B at 65,832 tok/s implies about 1.0 PFLOPS on one node, twice its dense-FP4 peak (NVIDIA technical blog 2025-10-24). Do not use them as roofline anchors.
- [Interpretation] A recipe roofline that assumed ~125 TFLOPS BF16 per GB10 put a lane at ~14% of peak; against the ≈213 TFLOPS mmapeak reading the same 17 TFLOPS per node would be about 8%. Neither figure is a verdict: Tensor-core peak is contested, on single-probe evidence: mmapeak (NVIDIA forum 351993, clock not stated) reads BF16 ≈213 and FP8 ≈214 TFLOPS [Community-measured]; a hand-PTX probe (getpoppy) reads BF16 123.3 / FP8 246.5 / NVFP4 493 TFLOPS, an exact 1:2:4 ladder that matches nvfp4bench's `mxf8f6f4` 243-256 and the 500 TFLOPS dense-FP4 figure [Community-measured]. Until an own register-resident probe at a recorded clock settles it, assume neither 'FP8 = BF16 rate' nor 'FP8 = 2x BF16'. State which peak an MFU figure assumes, at the lane's clock.
- [Code-verified] A community write-up credits a prefix-cache host-RSS leak fix to vLLM PR #44237; that PR is closed and unmerged (it targeted host-RSS growth under a classification workload). [Interpretation] The fix lives only in that community image; no upstream equivalent was checked.
- [Code-verified] vLLM PR #49486 (short-context DeepSeek V4 top-k skip) caused silent corruption under MTP plus prefix caching plus CUDA graphs until the capture guard in PR #52492 (graph capture: [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md)). Backport both or neither.
- [Community-measured] A bigger chunk can exhaust end-of-prefill headroom without an error. On a two-node DeepSeek V4.1 EXL3 pair, MNBT 3,072 wedged a prefill at ~140K while MNBT 1,024 completed 1.03M tokens; a client abort cleared it (recipe issue #19). This is the only case found that isolates the chunk. A 16,384 boot refusal at util 0.80 (Qwen3.8-Flash-Next EXL3) is a loud start-up failure, and a head reset at MNBT 8,192 (NVIDIA playbooks issue #97) was attributed by its reporter to allocation churn from `expandable_segments:True` plus FlashInfer autotune, with a mitigation that changed four settings at once.
- [Community-measured] Lowering MNBT to free memory crashed a b12x sparse-MLA build: warm-up sized and locked the compressed-MLA scratch from MNBT 2,048, and a later warm-prefix turn needed 1,949.52 MB against the locked 1,157 MB (single-node DeepSeek V4 recipe issue #4). The same knob grew the pool safely on another build (§4). Whether prefill activation memory follows MNBT only, or also max-model-len (1.39 to 2.23 GiB at fixed MNBT on the issue #4 build), differs by build (§8).
- [Community-measured] Build-level backend traps change what a ladder measures: one published image auto-enables `VLLM_USE_BREAKABLE_CUDAGRAPH`, which made single-stream decode 22% slower than regular graphs (regular graphs are +28.6% over breakable; see [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md)), and `VLLM_USE_B12X_FP8_GEMM` hit a DeepGEMM layout assert on that build (dkmode22). Record which backend each arm actually ran.
- [Community-measured] `expandable_segments` cuts both ways: `True` stopped an allocator ratchet that had wedged a 258K prefill on one GB10 (vllm-exl3 K2 build), while `True` plus FlashInfer autotune coincided with RM allocation failures and a head reset on a two-node DeepSeek V4 pair where `False` without autotune ran clean. Different builds and models; test per lane.
- [Community-measured] On GB10 hybrids a prefix-cache hit can be wrong, not only slow. An engine core overwrote `cache_config.block_size` with the smallest KV group (8 tokens with MTP 2) while the Mamba block was 1,600, so the state slot came out as `(3200-1)//8 = 399` and hits restored an all-zero Mamba state (lancelind); drafter groups flagged as EAGLE groups zeroed every hit until a coordinator patch (tonyd2wild); one missing KDA checkpoint silently vetoes every attention hit, and page-granular accounting inflates `vllm:kv_cache_usage_perc` about 2.4x, which also counts only running requests (Reederey87). Separately, with prefix caching on, a ~60-token probe diverged 3/3 at a logged 0.0% hit rate: run-to-run nondeterminism with the align machinery active, not a wrong restore (jschmied). One align-mode completion that ignored its prompt did not reproduce (pangoleen). Gate on output equality as well as hit counters.
- [Community-measured] vllm-exl3 before 0.4.2 computed fat-expert prefill wrongly for packs whose gate and up projections carry distinct `suh` rotations, whenever more than 256 tokens routed to one expert: NLL 4.21 against the ExLlamaV3 reference's 0.94 and top-1 agreement 30.8% against 74.7% on a 6K corpus; after the fix 0.9436 against 0.9422. Workaround on older builds: `VLLM_EXL3_FAT_THRESHOLD=1000000000`. The same release fixed a cooperative-GEMM wedge on 33-144-token prefills under the V2 model runner. GLM packs share `suh` (boots log "shared SUH 42/42") and are not exposed to the first bug (vllm-exl3 release v0.4.2). Numerics gates for such kernels are on [Quality and correctness gates](21-quality-and-correctness-gates.md).
- [Community-measured] Counting SSE events as tokens. Under speculative decoding one event carries several tokens, so event counts measure steps and under-read throughput 2.5-3x (dkmode22); one benchmark release was superseded after it counted events as tokens (95 events for 200 tokens, 2.11x, on its server; svangenstudios).
- [Community-measured] Engine-state drift between arms: a long-running speculative hybrid engine moved a 24K prefill +86% until restart, with GPU power falling to ~28 W at 96% reported utilisation (forum 382099); a shared torch.compile cache contaminated A/Bs, and an arm silently fell back to the stock kernel behind a layout guard (jschmied findings 135 and 114).
- [Community-measured] A smaller hash block lowered the cached-prefix intercept (485 to 265 ms) but not real-turn medians (0.592 / 0.547 / 0.631 s at 1,600 / 1,024 / 512) on one GB10 (jschmied). The intercept is not the turn.
- [Community-measured] Variants rejected with numbers in an independent two-GB10 GLM kit: a fused gather (-10.7% at 60K), a persistent A-cache, dual-rail NCCL, FlashInfer radix top-k, and KV offload to a bounded filesystem (Reederey87 @ 8e443d6b).
- [Interpretation] A recipe plan's premise that "GB10 FP8 tensor rate is 2x BF16" is unsettled, not false: mmapeak measured FP8 with FP32 accumulate at 213.7 TFLOPS, FP8 with FP16 accumulate at 213.8 and BF16 at 212.9 on one device, while a hand-PTX probe reads a 1:2:4 ladder (§3). Until an own probe settles it, do not carry the plan's "+25%" ceiling for FP8 non-routed GEMMs forward as established, and do not treat it as refuted either (GLM EXL3 recipe docs/improve-prefill.md §P6 @ 71962cd1).
- [Code-verified] Closed-unmerged pull requests are not fixes: SGLang #28038 (Triton fused-MoE shared-memory clamp) and #17421 (SM121 in the NVFP4 MoE check) never landed.
- [Interpretation] Unusable or out-of-scope numbers, kept so they are not reused: The Register's GB10 TensorRT-LLM claim that gpt-oss-120B TTFT exceeds 200 ms at 65,536 tokens implies ~330K tok/s, about 140x the maintainers' measured ~2.4K tok/s (article 2025-10-14); the SGLang #29927 TTFT table is RTX PRO 6000 and indexer or sparse-MLA work with Marlin MoE in both arms, not a MoE or GB10 result; a Grok-quoted per-length TTFT table attributed to #29927 is absent from the PR and its comments; the vllm-exl3 v0.3.0 "7.85 TFLOPS" prefill GEMM claim states no shape; DeepGEMM #324's grouped-GEMM peaks are RTX PRO 6000 numbers.
- Claims that did not survive verification, kept so they are not repeated: "tile-width gains do not transfer across GPUs" (the upstream wide tiles and the own geometry test concern different kernels and row regimes; nothing is shown either way); "no public SM121 path from Anemll" (a public GB10 vLLM port exists, §2); "no TensorRT-LLM chunk ladder on GB10" (one exists, §4); "vLLM auto-selects MNBT 8,192 on GB10" (the NVML probe fails, §2). From the second pass: "the rate peaks between 100K and 250K" on a DeepSeek V4 pair (no rung lies between 0 and 240K); "-79% at 500K" on Qwen3.5-35B (it mixed two users; the same-user drop is -77%); "chunk size leaves prefill speed unchanged" (both arms of that test prefilled in steps of at most 1,024 tokens under LPT 1,024); "a misrouted tile ran at 14 TFLOPS against 94" (those were two projections on the same misrouted kernel); "the upstream ExLlamaV3 tiers are partly measured on GB10" (no arm isolates them); "the iteration log records CPU time" (it records host wall time around the GPU wait); "GB10 MoE on SGLang still relies on tuned config files" (shown only for the Triton fused-MoE path); "a separate deployment did not reproduce the 2,048 chunk gain" (that sentence referred to the E2 kernel gain, which a second deployment later reproduced); "the whole-context llama-benchy rows are cold" (their author does not say so); "DeepGEMM SM120 support does not boot on GB10" (it failed on a vLLM PR preview build; mainline is untested); "the -27% from 450K to 989K is a depth term" (five settings changed between those rows).

## 8. Open questions

Cost model and depth
- What MNBT does an unconfigured vLLM server actually pick on GB10? — boot one stock server with no MNBT flag and read the "Chunked prefill is enabled with max_num_batched_tokens" line and `max_num_seqs`.
- The per-step cost model `t_step(M, P) ≈ t_fixed + a(M, W, L2, M mod 4)·M + b·M·P + c_sync` is an [Interpretation]. The W / L2 and M mod 4 terms are shown only for blockwise-FP8 CUTLASS linears on builds older than vLLM PRs #52775 and #55180 (§3); they are unmeasured for the Marlin, EXL3 and BF16 paths that dominate the GLM lanes. The depth term was single-digit through ~300K on two GLM lanes (author TP2 947 to 928 tok/s from 100K to 300K; own TP3 -3.4% at 250K, -8% at 524K) and reaches -16.5% near 1M; external DeepSeek V4 terms are larger (about -19% per doubling from 297K to 992K; -42% from 240K to 980K). — profiler-off wall time per step with scheduled tokens per step (the iteration-details log gives host wall time around the GPU wait) plus a GPU-side timer at 8K, 100K and 300K, and one profiler-on run per depth for the kernel split.
- What causes the 131K to 1M drop (1,692 to 1,412 tok/s) on the GLM TP3 lane: indexer, attention, or something else? — per-step timing at 131K, 524K and 1M with the indexer kernel isolated in a profiler run.
- How much of a short prompt's TTFT is host overhead and how much GPU work on each lane? On one GB10 stack host, HTTP and chat template cost ~40 ms and the rest of a ~0.5-0.6 s intercept was GPU work (unhit hybrid tail, small-M MoE); the vLLM blog's ~0.2-0.4 s intercept on Nemotron-3-Super was not decomposed. — server-side prefill duration next to TTFT at 1K-32K, plus one profiled 58-token request, per lane.
- What MFU do the MoE lanes reach against a stated peak? Arithmetic only so far: the recipe author's ~36 GFLOP/token estimate gives ~11-14% per node for the two-node GLM EXL3 recipe after E3 and ~9-10% for the own TP3 lane at 95K, against a 213-256 TFLOPS MMA ceiling; against the contested alternative (BF16 ≈123 or ≈213 TFLOPS, FP8 ≈214-256, FP4 ≈427-511 (contested; single-probe evidence), §3) the percentages change [Interpretation]. — `--enable-mfu-metrics` or analytic FLOPs over a cold ladder, divided by the ceiling at the lane's clock.

The recipe restates it in a later pull request without data; the shared-memory walls measured on SM121 sit in top-k selection and metadata and are keyed to sequence length. — one memory-guarded 8,192 arm at 100K+, off the production lane.
