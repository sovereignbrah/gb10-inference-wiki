# Model architecture cards: what each model family demands of the kernels on GB10

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 128 GB unified memory, about 121 GiB usable per node), one to three nodes (node-1, node-2, node-3) on 200 Gb/s RoCE. Community rows run on the same GB10 class unless a row says otherwise. Engine source is quoted at vLLM main `8b660ce96bc2e7ef164e7c9c26b969495a88f82c` (flashinfer-python 0.6.18.post1), SGLang main `f2a1366584e1ca152fa7afce719e9254e06e0f8b`, llama.cpp master `d2e54583c7452353eb35d40431281f6ee984332f` and ExLlamaV3 `6b84a21b6f1e5da3f291b9e1019061f0de788279`. The own lanes run forks and overlay kits, so a code line says what that commit does, not what a given lane dispatched.

Model checkpoints are pinned at their Hugging Face revisions: GLM-5.3-Flash `eb9eb20`, DeepSeek V4 Flash 0731 `7872f01` (Vision-Exp `6821d6a`), DeepSeek V4.1 Flash `dba1be0`, Qwen 3.8 27B `1d4bf0f`, Qwen 3.8 Flash-Next `de4b8e4`, MiniMax M3 `f0e1c1e`, Kimi K3 `f831ab6`; quantized exports nvidia GLM-5.3-Flash-NVFP4 `09b04e5`, nvidia DeepSeek-V4-Flash-0731-NVFP4 `f1caa71`, RadixArk Qwen3.8-Flash-Next-NVFP4 `7b71922`, RadixArk Qwen3.8-27B-NVFP4 `319f741`, nvidia MiniMax-M3-NVFP4 `9014640`, Mia-AiLab DeepSeek-V4.1-Flash-EXL3-2.9bpw `64ba41b`.

Vocabulary used on this page. **Checkpoint-verified**: read from every safetensors header of the checkpoint at the pinned revision (tensor names, dtypes, shapes, byte ranges), graded [Code-verified]; a verifier re-pulled the headers independently and reproduced every derived figure. **Active parameters**: every matmul weight one token touches in the language model (attention, linear attention, shared experts, dense MLP, routers, indexers, hyper-connection projections, `lm_head`) plus routed experts × top-k / n_experts; input embeddings, n-gram tables (lookups, not GEMMs), vision towers and drafter layers are excluded. **Weight bytes per token**: the bytes a batch-1 decode step must stream for those active parameters, with no speculation; this is the number the bandwidth ruler divides. **Ruler**: achieved read bandwidth on GB10; this page divides by NNNtrance's rotating-buffer read rulers, 238.6 to 245.9 GB/s, not the 273 GB/s datasheet figure. Other probes read lower (saturating read 227-235, copy 215-229, STREAM triad 200-214, decode ruler 230-245); the figures are contested and each is a single-author probe, and the wiki's single statement of the range is on [SM121 hardware facts](17-sm121-hardware-facts.md) §3. **KV bytes per token**: per rank, for the record format the engine actually stores on SM12x, not the model card's figure. **Effective prefill**: prompt tokens divided by time to first streamed token, request overhead included. **Code / prose / structured**: the author's own fixtures; numbers are comparable only within one row or one author.

## 1. What it is

Every model family asks a GB10 for a different mix of work, and that mix decides which kernels matter, which settings help, and how many nodes it needs. A card lists the facts that set the mix: how many layers use full attention versus a cheaper "linear attention" (fixed-size memory instead of a growing cache), how many "experts" (sub-networks, only a few run per token) each layer has, how many bytes of weights each generated token must read from memory, how many bytes of attention cache (KV, the per-token memory of the prompt) each token adds, and quirks such as attention without rotary position slices (NoPE), sparse "indexers" that pick which past tokens to attend to, and giant lookup tables that cannot sit in GPU memory. Those facts matter more on a GB10 than on a datacenter GPU for three reasons: generation speed at one request is set by bytes per token divided by about 240 GB/s of achievable bandwidth; the GPU has about 100 KB of fast on-chip memory per block and 48 compute units, so kernels written for datacenter Blackwell or Hopper often refuse to run or fall back to slow paths; and all 128 GB is shared with the operating system, so weights, cache and temporary buffers compete for the same headroom. This page gives one card per family run or considered on the own fleet (GLM-5.3-Flash, DeepSeek V4 Flash 0731, DeepSeek V4.1 Flash, Qwen 3.8 27B, Qwen 3.8 Flash-Next, with MiniMax M3 and Kimi K3 as fit references), the best measured recipes per node count, a fit table, and which topic page to open first for each family. Related pages: [SM121 hardware facts](17-sm121-hardware-facts.md), [Engine dispatch maps](16-engine-dispatch-maps.md), [Decode optimization](05-decode-optimization.md), [Prefill optimization](04-prefill-optimization.md), [MoE dispatch](08-moe-dispatch.md), [Attention backends on SM121](06-attention-backends-sm121.md), [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md), [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md), [Memory on unified memory](11-memory-on-unified-memory.md), [Speculative decoding](02-speculative-decoding.md), [Sampling and the lm_head](12-sampling-and-lm-head.md), [Quality and correctness gates](21-quality-and-correctness-gates.md).

## 2. How each engine does it

What each engine dispatches for each family on compute capability 12.1 at the pins above. Topology rule common to vLLM and SGLang: tensor parallelism (TP) must divide the query-head count, and for GQA models the KV-head count too.

### vLLM

- **Layout.** All seven architectures are registered; new families live in `vllm/models/<family>/{common,nvidia,amd}` (DeepseekV4, DeepseekV41, Glm5Next, Qwen4Exp, KimiK3, MiniMaxM3) [Code-verified, `registry.py:97-703` @ `8b660ce`]. TP must divide the query heads (`vllm/config/model.py:1501-1506`), so TP3 is unavailable for GLM, DeepSeek V4/V4.1 and MiniMax (64 heads) without forks; Qwen 3.8 27B (4 KV heads) and Flash-Next (2 KV heads) fail at `QKVParallelLinear` `divide(total_num_kv_heads, tp_size)` (`linear.py:1053-1057`) [Code-verified].
- **DeepSeek V4 Flash.** The FlashMLA sparse backend supports compute capability major 9 and 10 only (`vllm/models/deepseek_v4/sparse_mla.py:96`). On SM12x the path is `FLASHINFER_MLA_SPARSE_DSV4` -> `DeepseekV4FlashInferSM120Attention` (`deepseek_v4/nvidia/flashinfer_sparse.py:133-170`): KV dtype must be `fp8`, `fp8_e4m3` or `fp8_ds_mla` (no BF16 KV on SM12x), block 256, head size 512, FlashInfer's sparse-MLA decode API required; per-rank query heads are padded up to `_SPARSE_MLA_SUPPORTED_Q_HEADS` {8, 16, 32, 64, 128} (`:72`); adaptive-width ratio-128 decode is disabled on the SM120 family (a source comment marks SM120 adaptive-width decode as not yet supported, `sparse_mla.py:332-333`). The stored record is 584 bytes: "448B NoPE + 128B RoPE + 8B fp8 scale" (`deepseek_v4/attention.py:858-859`) [Code-verified]. Before this path reached mainline, working GB10 boots ran forks; one build note states stock vLLM did not serve V4 Flash on SM120/121 as of early August [Community-measured, hazyumps `docs/BUILD.md` @ `8d8e031`].
- **DeepSeek V4.1 Flash.** `_select_dsv4_attn_cls` sends major 12 to the same SM120 FlashInfer class (`deepseek_v41/nvidia/model.py:136-173`). FlashMLA mega-attention (`flash_mla_mega_attn.py:94`), V4.1's MXFP8 528-byte KV record (`deepseek_v41/attention.py:118-125`), the 288-byte FP4 record ("nvfp4_ds_mla needs the V4.1 KV records, which FlashMLA decodes only on SM100", `:504-518`) and the mHC overlap (`nvidia/ops/mhc.py:37`) are all SM100-family only, so SM12x stores the V4 584-byte record. Indexer rows are 132 B FP8 or 68 B MXFP4 (`attention.py:89-97`); `compress_ratios` semantics "0 = pure sliding window, 1 = full-length compressed cache, 2 = ratio-2 compressed" (`:295`) [Code-verified]. Community: at `e77daef` the model could not serve on SM12x (sliding-window block 32 vs the SM120 decode page 64; ratio-1 indexer `block_kv` 128 vs DeepGEMM's SM120 64-only; vLLM #56461), and with CUDA graphs on SM120/121 it produced NaN from dummy-capture writes into the null KV block (vLLM #57156) [Community-measured].
- **GLM-5.3-Flash.** Generic `FLASHINFER_MLA_SPARSE_SM120`: the base class lists head sizes [512, 576], 512 being the no-rope layout (`vllm/v1/attention/backends/mla/flashinfer_mla_sparse.py:58-62`), requires `index_topk` == 2048 (`:230-233`) and a FlashInfer build exposing `trtllm_batch_decode_sparse_mla_dsv4` (pinned flashinfer-python 0.6.18.post1). The kpool indexer needs the cache block to be a multiple of `index_kpool` × 32 (`glm5next/common/attention.py:95-140`). FlashKDA is used on SM90/SM10x/SM12x only for BF16, head dim 128 and a bounded gate; otherwise Triton (`glm5next/common/kda.py:128-150`) [Code-verified]. vLLM #45317 (open) reported every MLA backend rejecting `use_sparse=True` on SM121 on a June nightly (0.22.1rc1); main at the pin routes major-12 GPUs to `FLASHINFER_MLA_SPARSE_SM120` [Code-verified]. Community on GB10: the auto-selected FlashInfer CUTLASS NVFP4 MoE backend gave silent repeated-token output until `--moe-backend marlin` (forum 381433); the day-0 fix dressed GLM as DeepSeek's 576-wide layout with zero-padded rope (`VLLM_MLA_NOPE_PAD_ROPE=1`; "zeros are rotation-invariant and add exactly 0 to every logit") and compacted a 2,176-wide top-k table to 2,048 [Community-measured, forum 381433; kingjones30 @ `48a2f32`]. The vLLM GLM recipe states FlashInfer >= 0.6.17 is required for NoPE sparse MLA and validates only datacenter GPUs (recipes.vllm.ai, fetched 2026-09-23). A FlashKDA port (vLLM PR #55737, merged) replacing the ten-kernel Triton KDA chunked-prefill chain measured +6.5% sustained prefill at 3 nodes [Community-measured, NNNtrance EXL3 README @ `7f1bd29`].
- **Qwen 3.8 Flash-Next.** QSA (the model's sparse attention) runs the Triton backend `QWEN4_EXP_QSA_TRITON` (`qwen4_exp/nvidia/qsa.py:103`), which dequantizes FP8 KV itself (`:147-155`) because flash-attn's quantized-KV probe raises on sm120. Tile tables exist for GB300 (default), SM90 and exactly (12, 0); GB10 (12, 1) falls through to the GB300-tuned default (`qwen4_exp/nvidia/ops/qsa.py:20-22, 552-566`). The QSA indexer uses `persistent_topk`, never `cooperative_topk`, on the 120 family (`ops/qsa_indexer.py:481-486`) [Code-verified]. PLE (the per-layer n-gram embedding table) can be mmapped (`VLLM_PLE_MMAP=1`, Spark Arena sub1788296210046 recipe) or offloaded (`VLLM_PLE_CPU_OFFLOAD=1`, which "currently only runs on Nvidia devices", recipes.vllm.ai) [Community-measured]. TP4 needs `--enable-expert-parallel` because FlashInfer CUTLASS NVFP4 cannot pad the 640-wide MoE intermediate four ways; with torch.compile on, 2-node decode fell to 8 to 15 tok/s at 4,096-token chunks, so the speed profile runs compile off with decode-only CUDA graphs [Community-measured, forum 382476]. The QSA ring asserts `block_size % capacity == 0` with capacity 4·ceil((4+k)/4), 12 for MTP k = 5 to 8 (vLLM #54552).
- **Qwen 3.8 27B.** Registered as a Gated DeltaNet plus full-attention hybrid; its SM121 attention and GDN dispatch was not examined at the pin (open question in §8). The vLLM PR #52816 line plus a packed-head patch served the own two-node DFlash2 lane [Measured, 2026-08-20 two-node packed-head qualification].
- **Kimi K3 and MiniMax M3.** KDA uses family binaries on SM10x/SM12x (`kimi_k3/nvidia/kda.py:181-185`); MiniMax M3's CUTLASS sparse decode and index scoring are SM100-gated (`minimax_m3/nvidia/msa_cutlass_sparse_decode.py:220`; `common/indexer.py:512-514`); a `b12x` paged-attention backend explicitly accepts (12, 0) and (12, 1) (`v1/attention/backends/b12x.py:212-215`) [Code-verified]. Community MiniMax TP4 runs `B12X_ATTN` plus b12x NVFP4 MoE (forum 373927).
- **Top-k kernels.** FlashInfer's FilteredTopK needs >= 131,072 B shared memory per SM and GB10 reports 102,400, so the deterministic top-k returns `cudaErrorNotSupported` at TP1 and TP2 across three drivers (vLLM PR #55872, open). `persistent_topk` drops true candidates when more than 16,384 elements share the k-th value's coarse histogram bin (vLLM #51782, boundary test: 16,384 clean, 16,385 drops) [Community-measured].
- **KV-dtype naming.** In one pre-0.27.1 runtime the name `nvfp4_ds_mla` was routed to the same 584-byte FP8 record and kernel; on 0.27.1 that repo normalizes the alias to `fp8_ds_mla`, with no packed NVFP4 V4 reader on SM121 at that tag [Community-measured, nepenth `docs/NVFP4_DS_MLA.md` @ `e82bab4`]. Pool sizes quoted under that name need checking against the record actually allocated.

### SGLang

- **Arch detection.** `get_platform().is_sm120` maps to `is_sm120_supported` = any major 12, GB10 included (`runtime_context.py:1762`; `python/sglang/srt/utils/common.py:293`), while `is_sm120()` means exactly (12, 0) and `is_sm121()` exactly (12, 1) (`common.py:326-336`): two meanings of "SM120" in one codebase [Code-verified]. Model files exist for `deepseek_v4` (covers V4.1), `glm5_next`, `qwen3_5`, `qwen4_exp` (+MTP), `kimi_k3`, `minimax_m3`.
- **DeepSeek V4 and V4.1 on SM12x.** No FlashMLA metadata (`layers/attention/deepseek_v4_backend.py:199-200`); FlashMLA's `sparse_prefill_fwd` is skipped on SM12x (`:3803-3813`), and prefill runs FlashInfer's SM120 sparse paged kernel via `flash_mla_sm120` (index-sparse; only the late-layer tail stays dense). Decode goes through `flash_mla_sm120` with `SGLANG_SM120_FLASHMLA_BACKEND` defaulting to `flashinfer` (`environ.py:1073`; Triton and PyTorch alternatives), at most 64 tokens per decode call (`kernels/ops/attention/flash_mla_sm120.py:212`); indexer metadata is split into 4,096-row chunks because DeepGEMM's paged-MQA metadata kernel cannot schedule more rows on SM120 (`dsv4/metadata.py:70`, `_SM120_INDEXER_M_CHUNK = 4096`) [Code-verified]. SGLang pads DeepSeek V4 decode queries to 64 heads on SM12x for an SM90 FlashMLA constraint; removing the pad saves 0.50% of a TP4 step but changes greedy output (SGLang #39235, open). Community: DSpark on 2 nodes failed on a runtime-clamped top-k 192 not in the SM120 kernel buckets 128/512/1024/2048 (SGLang #33134); the V4.1 FP8 `wo_a` absorb GEMM is silently about 25% wrong on SM121 when UE8M0 scales are off (SGLang #39193); `deep_gemm` MoE runner is accepted for MXFP4 experts then fails at graph capture (SGLang #39226) [Community-measured]. The DeepSeek V4 prefix cache is a ShadowRadix with per-pool shadows for sliding-window, C4 and C128 plus nested compressor rings (LMSYS DeepSeek V4 blog, fetched 2026-09-23).
- **GLM-5.3-Flash.** In SGLang v0.5.20 every DSA backend fails for Glm5Next on SM121: the TRT-LLM-gen kernel is SM100-only ("Unsupported architecture"), TileLang needs 169,984 B of dynamic shared memory, the Triton path is ROCm-only, and `flashinfer_sparse_mla` is gated to GlmMoeDsa architectures (SGLang #40286). FP8 KV is closed because `index_kpool` 4 excludes `flashmla_kv` (SGLang #36830, reproduced on H20 and GB10); a community five-file TileLang raw-FP8 patch in that thread runs on sm_121 at decode parity (29.2 vs 29.8 tok/s, 16K warm TTFT 6.6 vs 7.9 s) and is unmerged. MTP MoE weights fail to load at TP > 1 (SGLang #36653) [Community-measured]. The cookbook keeps a paged DSA KV pool and a separate KDA state pool; the state pool clamps `max_running_requests` before the KV pool fills (`--mamba-full-memory-ratio`, default 0.9; `--max-mamba-cache-size`); prefill CUDA graphs are off for the KDA hybrid (`--disable-prefill-cuda-graph` in generated commands); speculative decoding does not start under PD disaggregation (SGLang GLM-5.3-Flash cookbook, fetched 2026-09-23). On GB10 the TileLang DSA kernel dies at warmup ("Failed to set the allowed dynamic shared memory size to 151552") until single-buffered, and decode graphs needed the then-open mHC capture fix PR #36755 [Community-measured, joesinvestments @ `880efbc`]. SGLang DFlash on hybrid-KDA models consumes 1 + D state slots per request and silently clamps `max_running_requests` to pool/(1 + D) (SGLang #36889).
- **Qwen 3.8 Flash-Next.** FlashInfer's TRT-LLM-gen paged sparse decode "silently corrupts long-context decode on SM121/GB10" (120K/190K/210K reproductions returned token 0 for all 32 tokens with HTTP 200), so SM121 routes to a dedicated Triton kernel `qwen38_qsa_sm121_varlen` (BF16, D = 256, 12:1 GQA, TP1 or TP2, <= 2,055 selected KV, batch <= 128), 1.41 to 5.09× over the earlier correct Triton kernel, 64/64 + 42/42 GB10 cases passed (PR #36845, merged at `78c5024`; `layers/attention/qwen_sparse_attn_backend.py:46-76`) [Code-verified + Community-measured]. Remaining SM121 reports: QSA + NEXTN decode graphs silently corrupt on TP2 (SGLang #37111), NEXTN acceptance decays to about 0 over uptime (#37326), a chunked-prefill + radix race corrupts KV pages (#38319), Triton `load_binary` failure during graph replay cascading to a driver lockup (#40948). PLE can be served from a sparse NVMe file (`--ple-offload-backend file`) [Community-measured, hasso5703 @ `81ae2bf`].
- **Qwen 3.8 27B.** The cookbook (@ `81cb895`) lists DGX Spark as a supported single-GPU target and makes `--mamba-full-memory-ratio` the throughput-sizing flag. Its float32 SSM-state default cost about 40% prefill and 16 GB of KV pool on GB10 with no acceptance gain (vitorallo post, fetched 2026-09-23) [Community-measured]. SGLang drops a packed-FP4 `lm_head.weight_scale` and the calibrated `k/v_scale` of the 16 attention layers [Measured, 2026-08-19 single-node DFlash2 audit]; an Unsloth NVFP4 export with an FP8 `lm_head` does not load, RadixArk's does (TysAIs @ `2d8d8c1`).
- **MiniMax M3 and Kimi K3.** MiniMax M3 W4A16 on 2× GB10 emits token 0 for every position on the Triton MiniMaxSparse path while the same weights are correct on vLLM (SGLang #38143); NVFP4 CUTLASS GEMM intermittent "Error Internal" on 4× GB10 (SGLang #32021, closed). Kimi K3: long-context [PAD] storms and DSpark NaN asserts on a released branch image (SGLang #32968, not GB10-specific) [Community-measured].

### llama.cpp and forks

- **Registry.** `qwen35`, `qwen4exp`, `deepseek4` (+ DSpark conversion), `minimax-m3`, `kimi-k3`, `kimi-linear`, `glm-dsa` are registered (`src/llama-arch.cpp:41-43, 83-87, 140, 155` @ `d2e5458`); GLM-5.3-Flash only via open PR #27754 (head `86ebfef`, used by Unsloth GGUFs); DeepSeek V4.1 only via open PR #28696 [Code-verified]. No SM121-specific code paths for these models were found at the pin.
- **Forks.** `ds4` (antirez; C/CUDA/Metal engine for DeepSeek V4 Flash; the V4.1 branch reads Engram rows from SSD and is Metal-only) and the Entrpi GB10 fork (continuous batching, DSpark, tensor-core MoE GEMMs) [Community-measured]. A Flash-Next fork replaces the `[n_kv, n_tokens]` QSA score table with block-level top-k (flattening the prefill curve), requires F16 KV because quantizing raw index keys changes which blocks survive the discrete top-k, and serves the PLE table mmap-only (mihailescu2m `docs/Qwen3.8-Flash-Next.md` @ `1a3bb34`). Upstream-branch recipes stream the PLE with `-ot per_layer_token_embd.weight=CPU` or keep an IQ4_XS build fully resident (ncmalan @ `ddd6ef4`).
- **GB10 bugs.** DeepSeek V4 Flash deterministic character-level corruption on sm_121, quant- and build-independent (llama.cpp #28132, open); REAP-pruned V4 race fixed only by `CUDA_LAUNCH_BLOCKING=1` (#26588, closed); `qwen4exp` aborts at native 262,144 depth (#27871); data-dependent cuBLAS failure avoided by `-ub 256` (#28377, closed); host RSS plus swap growth on 128 GB unified memory (#28933) [Community-measured]. Kimi K3 serves across 4 nodes over RPC (0xTank card @ `6b12997`).

### ExLlamaV3 in vLLM

- **Registry and arch.** The mainline registry includes `DeepseekV4Model`, `Glm5NextModel`, `Qwen3_5` (dense, MoE, VL), `Qwen4ExpModel`, `KimiLinearModel`, `MiniMaxM2Model`; no DeepseekV41, KimiK3 or MiniMaxM3 (`exllamav3/architecture/architectures.py` @ `6b84a21`). Kernels JIT-compile for the detected capability clamped to torch's arch list (`util/arch_list.py`), so SM121 builds natively with no arch gating [Code-verified].
- **How it is served on GB10.** Every GB10 EXL3 deployment found runs through vLLM overlay kits: MiaAI-Lab GLM 2×, MiaAI-Lab DeepSeek V4.1 2× (on a DeepseekV41 vLLM base with ExLlamaV3 v1.4.5), the own GLM TP3 and DeepSeek V4.1 TP3 ports, tonyd2wild DeepSeek V4.1 EXL3 TP3/TP4, punkjazz-labs GLM TP4, NNNtrance GLM TP3 (`cuda-exl3` vLLM fork, TP3 + EP, pre-sliced per-rank sidecars of about 79 GB, 280 s fast-load boot) [Community-measured]. The EXL3 attention backend refuses dense MLA (`index_topk` null) and `index_topk` >= 16,384 (NNNtrance EXL3 README @ `7f1bd29`).
- **Recipe-reported EXL3 wins on GB10.** MiaAI-Lab PR77 "E2 fat-expert prefill" (direct/scatter kernels) +20.33 / +21.36 / +20.70%; E3 grouped MoE prefill 1,428 to 1,587 tok/s on 2 nodes from 8K to 256K (MiaAI-Lab GLM kit @ `71962cd`) [Community-measured]; cooperative decode MoE kernel 1.23 to 1.94× kernel-only at H5120/I768/top-6 [Measured, kernel only: 2026-09-16 V4.1 EXL3 component gates]. ExLlamaV3's own engine (a GB10-tuned fork at `329e051`) beat vLLM plus an EXL3 plugin on one node for Flash-Next: 79 vs 52 tok/s on code, 47 s vs 9.5 min cold load [Community-measured, vcruz305 @ `e0ebee8`].

### TensorRT-LLM (status)

No TensorRT-LLM engine run of these models on GB10 was found. Separately, FlashInfer's TRT-LLM-gen attention kernels, used as backends inside SGLang and vLLM, corrupt Flash-Next long-context decode on SM121 (SGLang PR #36845; own rejection of that path for coding corruption [Measured, 2026-08-26/28 Flash-Next two-node SGLang screens]) and are unsupported for GLM DSA on SM121 (SGLang #40286) [Community-measured].

## 3. What is different on GB10 / SM121

- [Community-measured] **Shared memory is about 100 KB, not about 228 KB.** Opt-in dynamic shared memory is 101,376 B per block; kernels sized for Hopper or datacenter Blackwell fail: Triton MLA decode (vLLM #53748, 102,400 > 101,376), TileLang DSA (169,984 B, SGLang #40286; a 148 KB double-buffered tile, joesinvestments @ `880efbc`), the `persistent_topk` fallback needing 128 KB on 48 SMs (tonyd2wild V4.1 notes), FlashInfer FilteredTopK (131,072 B per SM vs 102,400, vLLM PR #55872), the FA2 FP8 CTA tile (forum 381429, fixed by capping the tile). Two community texts give "NVIDIA GB10, sm_121, 48 SMs / shared memory per SM: 102400 bytes" (vLLM PR #55872 comment) and "24 MiB L2, 99 KiB smem/block" (vLLM RFC #55394); an own device query is still owed. See [SM121 hardware facts](17-sm121-hardware-facts.md).
- [Community-measured, contested; single-author probes] **The read ruler used on this page is about 240 GB/s** (the full probe range, about 200-246 GB/s, is on [SM121 hardware facts](17-sm121-hardware-facts.md) §3). Three NNNtrance read rulers 238.6 / 245.9 / 239.5 GB/s (about 90% of 273 GB/s), raw `cudaMemcpyD2D` 123.0 GB/s, BF16 matmul ceiling 97 TFLOPS, best FP4 MoE GEMM 76.1 TFLOPS at M = 1,792 (NNNtrance `results/kernels` @ `eb11cef`). Marlin W4A16 MoE at decode shapes (M <= 64) already reads 91 to 96% of a three-way-confirmed 245.9 GB/s ceiling, so FP4 tensor-core MoE has no idle arithmetic to sell at decode; the FP4 crossover sits at M ≈ 1,024 (same source, superseding its earlier "94–99% of 240.5"). [Interpretation] Against a 240 GB/s ruler the own implied 185 to 206 GB/s for the Qwen 3.8 27B DFlash2 verify step is 77 to 86% of achievable, not 68 to 75% of nominal.
- [Community-measured] **A hidden slow state and a clock latch.** A decode-shaped BF16 GEMV runs 224 to 233 GB/s and FP16 matmul 76 to 84 TFLOPS in a "fast" state, but 66 to 80 GB/s and 53 to 55 TFLOPS in an undiagnosed "slow" state that nvidia-smi does not show (tonyd2wild DeepSeek-V4.1 recipe issue #1); a separate latch holds GPUs at 630 to 950 MHz until an AC power cycle (a reboot does not clear it) and was worth 41 -> 77.2 tok/s peak on one 4-node V4.1 lane (forum 382897). Every per-model number needs a clock-state check first; see [Clocks, thermal, and power](13-clocks-thermal-power.md).
- [Code-verified] **Datacenter-only attention paths.** FlashMLA sparse decode and prefill for V3.2/V4/V4.1 are SM90 and SM100 only, and "Sparse Decoding for DeepSeek V4.1 is only available on SM100" (FlashMLA README @ `ba89a34`); V4.1's 528-byte and 288-byte KV records are therefore unavailable and SM12x stores the V4 584-byte record (vLLM `deepseek_v41/attention.py:118-125, 504-518`). MiniMax M3's CUTLASS sparse decode is SM100-gated. FlashInfer's TRT-LLM-gen attention is unsupported for GLM DSA and corrupts Flash-Next long decode on SM121.
- [Code-verified] **"SM120" is ambiguous in the engines.** vLLM's Flash-Next QSA tile tables key on exactly (12, 0), so GB10 gets the GB300 default table (`qwen4_exp/nvidia/ops/qsa.py:20-22`); SGLang's `is_sm120()` means (12, 0) while `is_sm120_supported` means any major 12. GB10 silently gets untuned defaults or is excluded depending on which helper a file uses. See [Engine dispatch maps](16-engine-dispatch-maps.md).
- [Code-verified] **NoPE is a kernel contract, not a flag.** GLM has `qk_rope_head_dim` 0. Packed MLA kernels that assume a 64-dim rope slice crash on it; vLLM main's SM120 sparse-MLA path needs `index_topk` 2048 and a FlashInfer API; community boots either zero-pad into DeepSeek's 576-wide record, extend the SM90 plain-cache NoPE sparse-MLA backend to capability 12 on the FA2 path with `fp8_e4m3` KV and a capped CTA tile (a tonyd2wild layered image, as documented in Wpnx330 `docs/DESIGN.md` @ `bde0848`; about 0.005 relative error vs FP32 per forum 381429), or hand-write a NoPE sparse-MLA kernel sized for 101,376 B with no tcgen05/TMA/wgmma (before it, stock vLLM emitted "locklocklock…" for every prompt; Libertai @ `617d0cc`) [Community-measured]. On ROCm a 512-wide entry under 576-assuming decode kernels kept prefill correct (cosine >= 0.9997) while decode GSM8K fell to 0.0099 (ROCm ATOM recipe @ `23a99bc`) [Community-measured].
- [Community-measured] **TP3 on 64-head models means padded heads, and the pad differs by kit.** GLM 64 -> 66 (22 per rank; b12x kernels pad again 22 -> 24; the own adapter pads 22 -> 32 and 512 -> 576 query width on every call because 22-head prefill crashed [Code-verified, 2026-09-20 GLM TP3 frontier dossier v2]); DeepSeek V4 64 -> 72 (MiaAI-Lab V4 kit); DeepSeek V4.1 64 -> 96 with 8 -> 12 output groups (MiaAI-Lab SGLang, "rank 2 all padding") or 64 -> 72 (tonyd2wild V4.1 vLLM TP3). TP4 is exact for 64-head models. Stock engines reject TP3 outright. GLM also pads vocabulary 154,880 -> 154,944 and its BF16 shared expert to 2,112 at TP3; DeepSeek vocab 129,280 pads to 129,408 at TP3 [Code-verified, own ports; NNNtrance `docs/02-image-build.md` @ `eb11cef`].
- [Community-measured] **Unified memory makes transients the ceiling, not KV.** vLLM's free-memory estimate on integrated GPUs is MemAvailable, which counts reclaimable page cache (forum 381429); the driver fails `NV_ERR_NO_MEMORY` while the page cache shows memory available; FlashInfer autotune and graph capture allocate outside SGLang's accounting and froze one machine (SGLang #35860). Indexer-logit workspaces scale with chunk × prefix: a ~230K GLM prompt killed a 2-node engine (vLLM #55569), Flash-Next's QSA indexer buffer grows with `max_seq` (vLLM #56457), and a DeepSeek V4.1 TP3 head wedged a node on a ~200K prefill with the KV pool 25 to 28% full [Historical diagnostic, 2026-09-16 V4.1 TP3 wedge record]. See [Memory on unified memory](11-memory-on-unified-memory.md).
- [Interpretation] **Huge lookup tables must live off-GPU.** DeepSeek V4.1's Engram (188.8 GiB) and Flash-Next's PLE (95.4 GiB BF16, about 48 GiB FP8) do not fit beside the model on 1 to 3 nodes, so NVMe or mmap placement, not a kernel, decides whether those models run at all on small topologies.
- [Community-measured] **Silent corruption is the dominant failure class.** HTTP 200 with wrong tokens: Flash-Next token 0 on FlashInfer TRT-LLM-gen decode (SGLang PR #36845), QSA + NEXTN graphs (#37111), MiniMax M3 W4A16 token 0 on SGLang Triton (#38143), GLM FlashInfer CUTLASS NVFP4 MoE loops (forum 381433), FlashInfer 0.6.17 FA2 MLA NaN on 64 to 256-row batches (forum 381429), DeepSeek V4 `fuse_norm_quant`/`fuse_act_quant` garbling (vLLM #50773), V4.1 NaN under CUDA graphs (#57156), V4 character corruption in llama.cpp (#28132), GLM non-ASCII corruption under concurrency on NVFP4 TP2 (#57087), Flash-Next greedy non-determinism from `persistent_topk` above the indexer budget (#54521). See [Quality and correctness gates](21-quality-and-correctness-gates.md).

## 5. Levers, ranked

Ranked by evidenced gain per unit of risk for the families on this page. Each lever names where it applies (engine × family × topology), the gain band with its grade, cost, risk and the smallest experiment that would falsify it.

1. **Choose the topology from the fit table and the head divisibility before tuning anything.** Applies to: all engines × all families × 1 to 4 nodes. Gain: Qwen 3.8 27B TP1 -> TP2 +60 to 73% decode [Measured, 2026-08-17 TP1 vs TP2 identical battery]; GLM TP2 -> TP3/EP3 +29 to 45% decode and +48% prefill at 95K, confounded by slots, k and kit [Measured, 2026-09-14 GLM TP3 triangle qualification]; DeepSeek V4.1 3 -> 4 nodes 1.2 to 1.3× decode and ≈2× prefill on one author's kit [Community-measured, MiaAI-Lab @ `25379c2`]; DeepSeek V4 TP2 -> TP3 only +4 to 13% per stream with 4 to 22% slower prefill because attention does not shrink [Community-measured, MiaAI-Lab @ `97e8733`]. Cost: nodes, and a fork for TP3 on 64-head models. Risk: TP3 pads heads (DeepSeek V4.1 rank 2 is all padding at 64 -> 96), GQA families with 2 or 4 KV heads cannot run TP3, and a node that joins a TP3 group takes its single-node lane offline. Smallest falsifying experiment: same kit, same fixtures, one topology change per boot, code/prose/C4/cold 32K prefill at both topologies. Owner: [Inter-Spark communication](03-inter-spark-communication.md).
2. **Tune speculation per family: depth, drafter and draft vocabulary.** Applies to: vLLM and SGLang × GLM (DFlash2), Qwen 27B (DFlash2), Flash-Next (MTP), DeepSeek V4/V4.1 (DSpark) × any topology. ## 6. Protocol

Use this to qualify a new model family, a new quant of a known family, or a new recipe on GB10. It builds on [Profiling protocol](14-profiling-protocol.md), [Memory on unified memory](11-memory-on-unified-memory.md) and [Quality and correctness gates](21-quality-and-correctness-gates.md).

**Preconditions.**
- All [entry-page](README.md) rules apply, in particular: greedy logprob probe after every relaunch; discard the first request and warm every shape; unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection line on every rank; ≥3 reps with a closing A/B/A; MemAvailable every 1-2 s and zero NV_ERR_NO_MEMORY/Xid; no reboot without per-node permission. Clearing a latch is a power cycle and needs the operator's explicit per-node permission.
- Fleet rules from the [entry page](README.md): never overcommit memory (keep the 5 GiB warm floor on every node, measured after the longest qualified prefill, 8 GiB before a start, raise a KV pin by at most 1.5 GiB per boot); one variable per boot (a node wedged when an indexer-workspace change and a 4 GiB KV-pin raise went into one boot with 4.4 GiB host free [Historical diagnostic]); stop benchmark traffic when any node's MemAvailable drops below 4 GiB and keep the engines up for diagnosis; clean window with no outside requests; restart-based A/Bs skip the image pull so arms stay identical; never restart an agent gateway to test an engine change.
- Clock and state check ([Clocks, thermal, power](13-clocks-thermal-power.md)): confirm the clock cap and no latch (a 4-node lane went 41 -> 77.2 tok/s peak after clearing two GPUs stuck below 1 GHz [Community-measured]); run a short GEMV read ruler and reject the window if it reads far below ≈220 GB/s, because a slow state reads 66 to 80 GB/s and nvidia-smi does not show it [Proposed threshold; Community-measured states].
- Pins recorded: image digest, engine commit, overlay kit commit, checkpoint revision, FlashInfer version.

**Step A: architecture read.** Pull `config.json` and every safetensors header at the pinned revision. Compute active parameters, weight bytes per token for the exact quant (which layers the export keeps in BF16), KV bytes per token for the record the engine will store on SM12x (not the card's), fixed per-request state, and the bytes-bound ceiling at the target topology. Flag: NoPE (`qk_rope_head_dim` 0), query-head and KV-head counts vs the TP size, vocabulary divisibility, indexers and their `index_topk`, hybrid layers, n-gram or Engram tables, drafter shape (tokens per pass).

**Step B: fit.** Per rank: weights + KV pin + drafter weights and KV + CUDA graphs + the largest prefill transient (indexer logits scale with chunk × prefix; QSA workspace with chunk × history) + the warm floor. Treat vendor footprints as weights only.

**Step C: boot receipts.** From the boot log record the selected attention backend per layer type, MoE backend, KV dtype and record bytes, hybrid page size, head padding, vocabulary padding, graph capture sizes, allocated KV tokens; check allocated bytes per token against Step A. A mismatch is a finding, not noise (the GLM drafter page padding and the `nvfp4_ds_mla` alias were both found this way).

**Step D: correctness before speed.** Needle or echo at three depths, including past 120K for hybrid-state families; a fixed-seed greedy set at the target concurrency (silent corruption often appears only at C > 1); a `max_tokens=1` isolation run; a tool-call battery; for indexer families, a multi-turn agentic replay past 32K scored on tool-call arguments.

**Change.** Exactly one of: topology, quant, speculation depth or draft vocabulary, KV dtype, chunk or MNBT, `index_topk`, a kernel path, table placement, slot count. Bundles are allowed for promotion only after each part has its own arm, and are labelled as bundles.

**Record (packet fields).** Pins; Step A figures and Step C receipts side by side; per node MemAvailable before, at peak and after; frozen-harness code / prose / structured at three depths with n and spread; C1 / C4 / C8 aggregate and per stream; warm acceptance; cold prefill ladder with a fresh nonce at 8K, 32K, 95K and the longest supported depth; clock state; every NV memory message.

**Pass gate.** Correctness gates unchanged or better; the targeted metric improves beyond rep spread over at least 3 reps with a closing baseline arm (A/B/A); no other frozen-harness cell regresses beyond spread; every node above the warm floor throughout and never below 4 GiB; zero NV_ERR_NO_MEMORY or Xid lines during the gated workload. A quick probe of a few reps never promotes: a 3-rep probe once claimed +38% decode after a GLM change that the frozen harness showed as zero [Measured, 2026-09-23 V3.2 verification].

**Rollback.** Keep the previous recipe as the rollback target and restore it with the same one-variable boot. If a candidate wedges a node or drops MemAvailable below the stop line, stop traffic, keep engines up for diagnosis, log the incident, then restore.

## 7. Anti-patterns and known-bad

Owner pages for the items below: sizing and fit [Memory on unified memory](11-memory-on-unified-memory.md); KV records [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md); attention and sparse-MLA paths [Attention backends on SM121](06-attention-backends-sm121.md); MoE backends and FP4 decode [MoE dispatch](08-moe-dispatch.md) and [GEMM backends](09-gemm-backends-and-quant-formats.md); chunking and prefill [Prefill optimization](04-prefill-optimization.md); speculation [Speculative decoding](02-speculative-decoding.md); GDN and KDA state [Linear attention](07-linear-attention-and-hybrid-layers.md); quick probes and quality [Quality and correctness gates](21-quality-and-correctness-gates.md).

- [Interpretation] **Sizing from the model card.** Cards omit KV, runtime, transients, PLE and Engram: GLM's "18B active" includes embedding and vision; Flash-Next "125B" excludes the 51.20B PLE; DeepSeek V4.1 "~522B / ~280 GB 4-bit" vs 552B backbone and ≈286 to 305 GiB GPU-resident natively. Earlier fit tables built from cards were wrong in these three cells.
- [Interpretation] **Reusing the card's KV bytes.** DeepSeek V4.1's 890 B per token needs the SM100 FP4 record; SM12x stores ≈2.3 KB. A vLLM blog figure of 9.62 GiB per sequence at 1M was computed for a 61-layer stack (30 c4a + 31 c128a), not for V4 Flash; it must not be used as a Flash figure (refuted in verification).
- [Community-measured] **Assuming SGLang prefill runs dense for DeepSeek V4 on SM12x.** It runs FlashInfer's SM120 sparse paged kernel via `flash_mla_sm120`; only the late-layer tail stays dense (code at `f2a1366`).
- [Code-verified] **Trusting the `nvfp4_ds_mla` name.** One pre-0.27.1 runtime stored the 584-byte FP8 record under that name; pool sizes quoted under it may not be 4-bit.
- [Community-measured] **Reading an NVFP4 profile label as a layer attribution.** On Flash-Next the 34% "NVFP4 GEMM" kernel cannot be the dense layers, which are BF16 in that export.
- [Community-measured] **FP4 tensor-core MoE for decode.** Marlin W4A16 already reads 91 to 96% of the 245.9 GB/s ceiling at M <= 64; FP4 wins only from M ≈ 1,024.
- [Community-measured] **Auto-selected MoE and attention backends on SM121.** FlashInfer CUTLASS NVFP4 MoE looped GLM output until marlin (forum 381433) and OOM'd a second node on another recipe (sfxnz @ `e25f4b4`); FlashInfer TRT-LLM-gen attention corrupts Flash-Next long decode (token 0, HTTP 200); SGLang Triton MiniMaxSparse emits token 0 on W4A16; the NVFP4-Marlin MoE path dropped MiniMax M3's SwiGLU-OAI `gemm1_alpha` 1.702 and `gemm1_beta` 1.0 (arriving as 1.0 / 0.0) so all 57 MoE layers computed the wrong activation (forum 376979); an AWQ fused path quantized the BF16 MSA indexer and bled context on long prompts (CosmicRaisins @ `08b3ea4`); a bare top-level `lm_head.weight` not mapped to `language_model.lm_head.weight` gave garbage logits (forum 373819).
- [Code-verified] **Running 22-head sparse-MLA prefill at TP3.** It killed the engine on the first real prompt; the head count must land on the kernel grid {8, 16, 32, 64, 128} (own adapter pads 22 -> 32) [2026-09-20 GLM TP3 frontier dossier v2].
- [Historical diagnostic] **Changing two memory variables in one boot.** A GLM indexer-workspace change plus a KV-pin raise wedged a node; DeepSeek V4.1 native TP3 wedged on a ≈200K prefill with the pool 25 to 28% full because the indexer transient, not KV, was the ceiling; `expandable_segments:True` gave NaN logits on V4.1 prefills over 64 query tokens (MiaAI-Lab README).
- [Measured] **Rejected levers, kept for the record.** A DeepSeek V4.1 profile including chunk 256 (with 8 slots and a 2M pool, not isolated; cold prefill halved); V4.1 DSpark k=3 (code −11.0%, same-day A/B); V4.1 Engram RAM row cache (no repeatable gain, decode down); V4.1 grouped-kernel variants (slower); DeepSeek V4 zero long-prefill threshold (warm headroom 4.0 GiB); Qwen 27B SGLang TP2 over vLLM TP2 (C1 −20%); Flash-Next MTP6 (prose and C5 down), MTP5 (no boot), NVFP4 KV (−29% decode), speculative-attention decode mode (coding 20.97 vs 62); GLM early row-tile, temp-rows and MNBT 3,584 to 4,096 variants on the two-node kit. Sources: chunk 256, 2026-09-14 V4.1 TP3 optimization and quick scorecard; k=3, 2026-09-15 V4.1 TP3 k=3 scorecard; Engram cache, 2026-09-16 V4.1 prefill tuning; zero long-prefill threshold, 2026-09-03 DeepSeek V4 Flash TP2 long-prefill-threshold-off qualification; Flash-Next MTP depth, 2026-08-31 dual-node MTP depth A/B; NVFP4 KV and speculative-attention decode mode, 2026-08-26/28 Flash-Next two-node SGLang screens (§4); GLM row-tile, temp-rows and MNBT variants, the MiaAI-Lab two-node kit's own records (community; see [MiaAI-Lab recipes](18-case-study-miaai-lab-recipes.md) §4). The V4.1 grouped-kernel variants and the Qwen 27B SGLang-vs-vLLM TP2 comparison have no row on this page and their packets are not named here.
- [Community-measured] **Deeper drafts for prose.** GLM prose acceptance is ≈13% at k=7 on every public stack read; deeper k does not help prose.
- [Community-measured] **The SGLang float32 GDN state default for Qwen 27B on GB10.** ≈40% prefill and 16 GB of pool for no acceptance gain.
- [Measured] **Quick probes.** A 3-rep probe reported +38% GLM decode that the frozen harness did not reproduce.
- [Community-measured] **Extreme pruning or 1-bit builds as "the model".** A 4-node Kimi K3 IQ1_S build decodes 2.65 tok/s on a single probe and a 154-of-384-expert DeepSeek V4.1 build has no independent quality gate; neither is evidence about the full model.
- [Community-measured] **Quoting unit-less or protocol-less figures.** An 8-node DeepSeek V4.1 forum post (92.7 code, 256 at C6) and a 16-node Kimi K3 "20 to 30 t/s" lead carry no engine, quant or protocol and are excluded from §4.
- [Community-measured] **Source errors not to reuse.** "8/256 experts fire per token" and "~27 KB/token" KV for DeepSeek V4 (config: top-6; record arithmetic ≈3.85 KB) (iggerask @ `abdfcce`); "3 dense + 21 c4 + 20 c128" layers (= 44; the config gives 2 sliding-window-only + 21 + 20) (libertywing @ `d23db37`); Qwen 3.8 vocabulary "≈151 to 152K" (it is 248,320, so head-byte arithmetic from those posts is ≈1.6× low) (fattchris, vitorallo); a "measured within 1.6%" Qwen 27B KV check that is an RTX 5090 llama.cpp measurement with no 1.6% figure (kgptalkie); "Flash: 10% FLOPs, 7% KV vs V3.2" (the V4 paper abstract, arXiv 2606.19348, states 27% FLOPs and 10% KV for V4-Pro).
