# Engine dispatch maps: which kernel actually runs on GB10 per engine, and every switch

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 128 GB unified memory), node-1, node-2 and node-3; two- and three-node lanes use direct-cabled ConnectX-7 RoCE. Code is quoted at these pins, all re-read from fresh tarballs on 2026-09-23: vLLM `487ecf187d3d` (the build the own GLM lanes run) and `711fc55c10a2` (main); SGLang `da64c5cbb8cf` (an own lane pin) and `2909f84e3b2f` (main); llama.cpp `6e60f35608ec` (main) and `1deefcca3957` (DFlash2 branch); exllamav3 `c5d9c657966f` (v0.0.43), `58d4d7322a1b` and `6b84a21b6f1e`; Entrpi/ds4 `d92d93ad21c2` (v0.6.3); MiaAI-Lab GLM-5.3-Flash EXL3 kit `71962cd19e51`; Anemll DSpark vLLM port `081fda975417`; TensorRT-LLM `f5ca10543fc4` (main) and tag `v1.3.0rc13`; NVIDIA dgx-spark-playbooks `3410c65fbf4b`. A code line says what that pin does. It does not say what a given image runs; only the engine's own selection log line says that.

## 1. What it is

An inference engine does not run "a model"; it runs a few dozen separate GPU programs (kernels): one for attention (the step that looks back over the conversation), one for each matrix multiply, one for the mixture-of-experts layer (the part that routes each token to a few specialist sub-networks), one for picking the next token, and so on. For each of those jobs the engine keeps a ranked list of candidate kernels and, at start-up, takes the first one whose checks pass on the current GPU. Those checks ask questions like "is this GPU at least version 10.0?", "is it exactly 12.0?" or "is it in the 10.x family?", and GB10 answers them in surprising ways: it reports version 12.1, which is "at least 10.0" but not "in the 10.x family" and not "exactly 12.0". So the same flag can land GB10 on a fast kernel, a slow fallback, or a kernel that runs and silently produces garbage. That is why the kernel that actually runs decides speed and correctness on this machine more than any headline setting does. This page lists, per engine, what gets picked on GB10 by default, the flag or environment variable that changes each choice, the known-bad defaults and their fixes, and the status of NVIDIA's own TensorRT-LLM on the chip. Companion pages go deeper on single components: [Attention backends on SM121](06-attention-backends-sm121.md), [MoE dispatch on GB10](08-moe-dispatch.md), [GEMM backends and quantization formats on SM121](09-gemm-backends-and-quant-formats.md), [CUDA graphs and launch overhead on GB10](01-cuda-graphs-and-launch-overhead.md), [Sampling and the lm_head on GB10](12-sampling-and-lm-head.md) and [SM121 hardware facts card](17-sm121-hardware-facts.md).

## 2. How each engine does it

Reading rule for every gate below [Code-verified]. GB10 reports capability (12, 1), and each gate is one of four shapes:
- "at least X" (`has_device_capability(100)`, `cc >= 100`): GB10 passes, including gates written with SM100 in mind.
- "same major" (`is_device_capability_family(120)`, `is_sm120_supported()`, `major == 12`, `enable_sm120_family`): GB10 passes.
- "exactly 12.0" (`== 120`, `is_sm120()`, `enable_sm120_only`, `__CUDA_ARCH__ == 1200`): GB10 is excluded.
- "family 10.x" (`is_device_capability_family(100)`, `is_sm100_supported()`): GB10 is excluded.

Most GB10 dispatch bugs on this page are one of these shapes used where another was meant. [Interpretation]

### vLLM

Mechanism [Code-verified]. Every layer asks an "oracle" for a backend. The oracle walks a fixed priority list and takes the first class whose `_supports_current_device()`, quant-scheme, activation and parallel-config checks all pass, then logs `Using '<X>' ... backend out of potential backends: [...]`. A user flag (`--moe-backend`, `--linear-backend`, `--attention-backend`) skips the walk and raises if the named backend cannot serve the layer. A kernel can pass the Python gate and still be missing from the build, which is why `cutlass_*_supported()` asks the compiled C++ entry points. Capability helpers: `has_device_capability(x)` is `>=`, `is_device_capability(x)` is `==`, and `is_device_capability_family(x)` compares `to_int() // 10` (`vllm/platforms/interface.py:431-491` @ 487ecf187).

The lane pin is not a main-branch commit [Code-verified]: GitHub compare shows `487ecf187` diverged from main at `b908a21f9a44` (2026-08-13), 142 commits ahead and 1,930 behind; 135 of the 142 are by a single contributor on a GLM-5-Next branch. Pin and main behaviour are therefore quoted separately. Example: main removed `VLLM_TEST_FORCE_FP8_MARLIN` (commit `bca7bea240`, PR #52182, 2026-08-18); the pin still defines it (`envs.py:1094`).

SM12x family gating [Code-verified]. `enable_sm120_family` guards 1200 ≤ `__CUDA_ARCH__` < 1300 with the comment "SM12x family includes SM120 (RTX 5090) and SM121 (DGX Spark GB10)". `enable_sm120_only` (the `== 1200` trap that prints "This kernel only supports sm120a") is still defined but has no users at the pin (`csrc/libtorch_stable/cutlass_extensions/common.hpp:113-142`). The family fix landed in PR #35568 (merged 2026-05-15, merge `06d020bb6ef7`): Marlin codegen `arch == 89 or arch // 10 == 12`, runtime `major_capability == 12`, and the CUTLASS FP8 wrapper on `enable_sm120_family`. The CUTLASS FP8 dispatcher sends every `version_num >= 120` to `cutlass_scaled_mm_sm120` (`scaled_mm_entry.cu:220-226`).

The Marlin warning "Your GPU does not have native support for FP4 computation but FP4 quantization is being used" is printed by `MarlinNvFp4LinearKernel.process_weights_after_loading` (`kernels/linear/nvfp4/marlin.py:33-36`) and by the MoE path (`marlin_utils_fp4.py:355`) whenever Marlin is chosen, on any GPU. It is a code-path message, not a hardware probe. [Code-verified]

Legacy environment variables do nothing [Code-verified]. `VLLM_NVFP4_GEMM_BACKEND`, `VLLM_USE_FLASHINFER_MOE_FP4`, `VLLM_FLASHINFER_MOE_BACKEND`, `VLLM_ATTENTION_BACKEND` and `VLLM_MXFP4_BACKEND` are defined nowhere in `vllm/` at the pin or on main; an unknown `VLLM_*` variable is a warning, or an error under hard-fail (`envs.py:2179-2186`; main `platforms/interface.py:1271-1275`). NVIDIA's Nemotron playbook @ 3410c65 still exports the first two with `vllm/vllm-openai:cu130-nightly`; its `--moe-backend marlin` is what actually selects Marlin. A community write-up (vlaicu.io, fetched 2026-09-23) independently says these variables stopped working on 0.23+ images and still work on the NGC 0.19 image, which gives the version boundary. [Community-measured]

`VLLM_MARLIN_USE_ATOMIC_ADD` at the pin enables atomic-add reduction only for shapes with n < 2048 and k ≥ 2048, framed as a performance option (`model_executor/layers/quantization/utils/marlin_utils.py:633-653`). [Code-verified] A community note on vLLM 0.19 in an NGC 26.04 image says it is required for correct Marlin output on SM121. Contested; see §8.

Draft tensor parallelism [Code-verified]. `speculative_config.draft_tensor_parallel_size` accepts 1 or the target TP (`config/speculative.py:1296-1330`), but at the pin the resulting `draft_parallel_config` is read only by `v1/spec_decode/draft_model.py:63-89`, which requires draft TP == target TP. The DFlash/EAGLE proposer (`llm_base_proposer.py:1285-1336`) builds the drafter from the target config and never reads it. So "draft TP = 1" is not applied to a DFlash drafter at 487ecf187; the drafter is built at world TP, which is why the EXL3 kit pads the draft heads to 36/9. The kit's README and the header of its TP3 launcher say "rank 0 only", which contradicts the upstream code and the launcher's own comment at `start-tp3.sh:881-885`. See [Speculative decoding](02-speculative-decoding.md) §2 for drafter sharding and [Inter-Spark communication](03-inter-spark-communication.md) for the extra collectives it costs.

### llama.cpp and forks

Mechanism [Code-verified]. There is no runtime switch for the matrix-multiply kernel. `ggml_cuda_mul_mat` picks by tensor type and batch width in this order (`ggml/src/ggml-cuda/ggml-cuda.cu:1823-1870` @ 6e60f35): cuBLAS if src1 or dst is not F32 (or for a padded view); MMVF; MMF; MMVQ for quantized weights with at most 8 columns (`MMVQ_MAX_BATCH_SIZE 8`); MMQ; cuBLAS. `ggml_cuda_should_use_mmq` returns true for every supported quant type on Turing-or-newer GPUs with at least 48 KiB opt-in shared memory unless the build defines `GGML_CUDA_FORCE_CUBLAS` (`mmq.cu:266-326`). On GB10, quantized decode therefore uses MMVQ, quantized prefill MMQ, and cuBLAS serves only float weights.

GB10 paths [Code-verified]. llama.cpp names the chip: `GGML_CUDA_CC_DGX_SPARK = 1210` (`common.cuh:61`). Four code paths use it, and they key on different things:
- MMVQ parameter table `MMVQ_PARAMETERS_GB10`: host check `ggml_cuda_highest_compiled_arch(cc) == 1210` (`mmvq.cu:140`), so it needs 121a code in the binary.
- L2 prefetch in MMVQ: `__CUDA_ARCH__ == 1210` (`mmvq.cu:12`), so it also needs 121a code.
- MUL_MAT_ID MMVQ batch cap (Q2_K at most 6): `cc == GGML_CUDA_CC_DGX_SPARK` on the runtime device (`mmvq.cu:348`), so it applies to any binary running on GB10.
- GQA-ratio-20 flash-attention ncols choice: `cc >= 1210` on the runtime device (`fattn.cu:369`), same.

### ExLlamaV3 in vLLM

Mechanism [Code-verified]. Upstream vLLM has no EXL3 quantization method at the pin or on main (no `exl3`/`exllamav3` anywhere in `vllm/`). EXL3 runs in vLLM only through community overlay kits, here the MiaAI-Lab GLM-5.3-Flash-EXL3 kit @ 71962cd, which adds an EXL3 linear method and a fused MoE. exllamav3 v0.0.43 maps every device with major ≥ 10 to `CC_BLACKWELL`, so GB10 shares B200's shape heuristics (`exllamav3_ext/quant/exl3_devctx.cu:32-45`). Dense EXL3 GEMM autotunes at runtime whenever neither a shape nor an SM count is forced, and caches the winner on disk under `EXLLAMAV3_TUNE_CACHE` or the XDG/HOME cache (`exl3_gemm.cu:209-255`; `coop_autotune.cu:76-111`). [Interpretation] The tune cache is one more JIT-style artifact to persist.

Stock fused-MoE constants at `c5d9c657` [Code-verified]: `MOE_TILESIZE_M 16`, `MOE_TILESIZE_K 32`, `MOE_SH_STAGES 3`, `MOE_FRAG_STAGES 3`, `MOE_SMS_PER_EXPERT 8`, `SMEM_MAX` 90 KiB; kernel instances K0-K8 × N {128, 256}, with no 32- or 64-row tiles and no `MOE_MAX_SMS_PER_EXPERT` (`exl3_moe_common.cuh:9-20`). Upstream `58d4d732` (2026-09-13, "two-stage coop kernel") and `6b84a21b` add `MOE_MAX_SMS_PER_EXPERT 32` and 32/64-row instances. `exl3_moe_max_concurrency = num_sms / MOE_SMS_PER_EXPERT` (`exl3_moe.cu:14-18`), and the kit overlay sizes the fused temps from it (`overlay/exl3.py:1315`); on GB10's 48 SMs that is 6 concurrent expert groups. [Interpretation] That cap bounds the stock decode kernel, and changing it means rebuilding the extension.

## 3. What is different on GB10 / SM121

- [Code-verified] GB10 passes every "at least 10.0" gate but fails every "family 10.x" and "exactly 12.0" gate. In vLLM this removes FlashInfer TRT-LLM MoE, both CuteDSL MoE variants, CuteDSL NVFP4 linear, DeepGEMM MXFP8 and TRT-LLM FP8 MoE from every auto list, and leaves FlashInfer CUTLASS NVFP4 MoE and linear (which use "at least" checks) as the W4A4 winners.
- [Code-verified] vLLM ranks FA2 first for non-MLA attention on major 12; major 10 ranks FlashInfer first (for causal attention). FA3 and FA4 are not available on 12.x.
- [Code-verified] The only sparse-MLA candidate in vLLM on major 12 is `FLASHINFER_MLA_SPARSE_SM120`. Issue #45317 (nightly 0.22.1rc1) shows the earlier state with no candidate, and a dense-MLA report there reached only `TRITON_MLA`, which then failed. [Community-measured]
- [Code-verified] FlashInfer's TRT-LLM attention on SM12x is XQA decode only, and it is the one SM12x-specific CUDA-graph rule in vLLM (UNIFORM_BATCH with XQA, UNIFORM_SINGLE_TOKEN_DECODE without). No trtllm-gen FMHA cubins are published for SM12x (TensorRT-LLM #11799; a comment on vLLM #49547 counts 0 SM120-tagged among 570,513 cubins). [Community-measured]
- [Code-verified] DeepGEMM is auto-eligible on GB10 in vLLM (`family(120)`, env defaults 1) and, at SGLang pins before 2026-09-18, was enabled on GB10 without the SM120 API probe and with the wrong scale format. [Community-measured] Its block-FP8 GEMM is silently wrong at K = 2560 on GB10 in a window of N and M (vLLM #54125).
- [Community-measured] 99 KiB (101,376 B) opt-in shared memory per block breaks tile configurations sized for 228 KiB parts: TensorRT-LLM's default CUTLASS MoE tactics (#12706) and its SM120 FP4 GEMM tiles on 1.3.0rc2 (#11368). CUTLASS issue #3144 and vLLM #45317 report the same 101,376-byte figure.
- [Code-verified] SGLang's QSA sparse decode excludes GB10 from the FlashInfer TRT-LLM route by design; the Triton varlen kernel is the GB10 path.
- [Code-verified] llama.cpp has a named GB10 constant and four GB10 paths; two need 121a code in the binary, two apply on any build running on GB10.
- [Code-verified] exllamav3 treats GB10 as generic Blackwell for shape heuristics; the kit's thin-fast MoE kernel is the one path gated on exactly (12, 1).
- [Code-verified] With 48 SMs (Red Hat AI Inference 3.5 DGX Spark guide, fetched 2026-09-23; vLLM #45317 logs `num_sms*occupancy=48`, which corroborates 48 only if occupancy is 1), exllamav3's 8-SMs-per-expert constant yields 6 concurrent expert groups.
- [Code-verified] TensorRT-LLM's SM121 fixes on main (CUTLASS MoE shared-memory filter, cuda-core FP8 fast path, MLA KV reuse) are absent from the playbook images; MLA chunked prefill still excludes SM121 on main.
- [Interpretation] "GB10 has no native FP4" is wrong as a hardware statement. The PTX ISA lists block-scaled FP4 MMA for 12.x; cuBLASLt FP4 reached 99.6 TFLOPS peak on a GB10 (TensorRT-LLM #11368); own logs show `FlashInferCutlassNvFp4LinearKernel` on the single-node Qwen 3.8 27B lane (vLLM 0.25.2) and the GLM NVFP4 two-node (487ecf187) lane; and the Marlin "no native FP4" line is a code-path message. The two Flash Next vLLM lanes log `MarlinNvFp4LinearKernel` for linear layers only because their linear checkpoint is W4A16, and `FLASHINFER_CUTLASS` for the W4A4 MoE. The failures people report are version-, tile-, gate- and model-specific.

## 5. Levers, ranked

1. **Keep FA2 as vLLM's non-MLA attention, or keep XQA available when FlashInfer is forced** — applies to: vLLM × dense and hybrid-attention models × any topology, most with speculative decoding. Gain: community +16% single stream (47.5 -> 55.2 tok/s, #49547) from avoiding the PIECEWISE graph downgrade; a later comment on the same thread saw no downgrade on v0.28.0 with `decode_backend=xqa, arch=sm121` on five two-node pairs. Cost: none if the default is kept. Risk: losing the `flashinfer_cubin` package silently brings the downgrade back. Smallest falsifying experiment: boot the lane once with `--attention-backend FLASHINFER` and once default, one variable per boot, and compare the logged `cudagraph_mode` and C1 decode at a fixed prompt.

2. **Dense FP8 weights through Marlin W8A16 for decode-bound lanes; BF16 for prefill-bound ones** — applies to: vLLM + EXL3 × GLM-class MLA/KDA models × TP2/TP3. Gain: own decode +7-14% at short depth, +1% at 120K (coding 27.1 -> 30.8, prose 29.4 -> 32.2) and 2.4 GiB smaller weights; cost: prefill −18 to −21% (BF16 is 22-26% faster; 1,420 -> 1,142 tok/s at ~95K). [Measured] Risk: Marlin alignment rules keep some merged projections BF16 at TP3. Smallest falsifying experiment: per-layer FP8 on/off for the KDA group only, same image, fixed decode fixture.

3. **Split large-M GEMMs off Marlin: BF16 above an M threshold, FP8 Marlin below** — applies to: vLLM + EXL3 × KDA or other large projections × TP3; generalizes to any weight-only path whose prefill GEMMs are compute-bound. Gain: +7.20% (~7.6K) and +7.93% (~95K) prefill, group-level with start-up changes; 2.17-2.25× on the component at M = 2,048. [Measured] Cost: a BF16 copy of the affected weights. Risk: memory against the KV floor. Smallest falsifying experiment: move the threshold from 512 to 256 and 1,024 with everything else frozen; if prefill does not move, the threshold is not the lever. [Proposed] The community "GB10 hybrid NVFP4" plugin (Marlin below an M threshold, CUTLASS above) is the same idea for NVFP4 and is untried.

4. **Cooperative decode MoE for EXL3, with a per-row dispatch policy** — applies to: EXL3 in vLLM × MoE models × TP3 (and the kit's two-node variant). Gain: kernel-time ratio 0.643 at 1 row, parity by 64 rows [Historical diagnostic]; inside a bundle, C1 coding +17.90% and prose +20.83% [Measured, bundle]; synthetic 1.35× (K3) and 1.94× (K2) at 1 row [Measured component]. Cost: a custom extension build that fails a whole-file hash gate on every clean rebuild. Risk: 39 of the policy's stock rows were never measured. Smallest falsifying experiment: policy all-stock vs current policy, same image, C1 and C8.

5. **Thin-fast stock MoE (`GLM53_EXL3_MOE_FAST=1`)** — applies to: EXL3 kit × K4/N256 routed experts × CC 12.1, documented TP2-only. Gain: maintainer medians +7.71% to +14.59% with a noise band of -3.54% to +4.62% [Community-measured]. Cost: an image rebuild. Risk: a second kit saw one run in four land 15-30% below stock (#227). Smallest falsifying experiment: 8 alternating boots FAST=0/1 on the two-node lane with a fixed decode fixture, reporting the distribution, not the median.

6. **Turn DeepGEMM off where the model's shapes hit the bad window** — applies to: vLLM (`VLLM_USE_DEEP_GEMM=0`) and SGLang pins before 2026-09-18 (`SGLANG_ENABLE_JIT_DEEPGEMM=0`) × block-FP8 models with K = 2560 or non-UE8M0 scales × any topology. Gain: correctness, not speed; the upstream attribute fix (`f8e0602713`) alone did not stop the crash on a checkpoint with FP32 block scales (#54125). [Community-measured] Cost: fallback to CUTLASS block-FP8, speed unmeasured locally. Risk: unknown exposure of DeepGEMM's grouped MoE kernel, which one own two-node lane logs for its FP8 MoE block. Smallest falsifying experiment: a numerical gate on the lane's actual DeepGEMM GEMM and MoE shapes against CUTLASS or Triton.

7. **Opt into B12X MoE** — applies to: vLLM × NVFP4 (`--moe-backend flashinfer_b12x`) or fork-local MXFP4 (`VLLM_USE_B12X_MOE`) × single node or TP2. Gain: the own DeepSeek V4 Flash TP2 lane runs fork-local `B12X_MXFP4` in production [Historical diagnostic]; upstream NVFP4 gain on GB10 has no usable A/B (the #47577 +10% at 8 prompts is SM120). Cost: none to try. Risk: vLLM keeps it off auto for open SM121 reports (TP garbage, Xid 31, start-up OOM). Smallest falsifying experiment: one idle-window boot with the flag on a single node, numerical and repeated-output gates first, speed second.

8. **TensorRT-LLM MoE backend to Triton on GB10** — applies to: TensorRT-LLM × NVFP4 MoE × single node. Gain: one report of roughly an order of magnitude on two Qwen MoE models, without version or ISL/OSL (#12706). [Community-measured, context missing] Cost: Triton JIT on the first calls. Risk: the root cause is fixed on main by #12704, so images from `v1.3.0rc23` on may not need it. Smallest falsifying experiment: `moe_config.backend: TRITON` vs `CUTLASS` in the playbook's rc13 image on one model at fixed ISL/OSL.

9. **Build llama.cpp and ds4 natively for 121a** — applies to: llama.cpp and Entrpi/ds4 × any GGUF model × single node. Gain: ds4 +10.8% on 12K cold prefill (306 -> 339) [Community-measured]; for llama.cpp the MMVQ table and the +4.81% L2 prefetch need 121a code [Community-measured]. Cost: a rebuild. Risk: low. Smallest falsifying experiment: `cuobjdump --list-elf` on the existing binary; if it already holds sm_121a code, the lever is spent.

10. **Persist tactic and JIT caches instead of re-tuning** — applies to: every FlashInfer, Triton, TileLang, CuTeDSL and exllamav3-autotune user × every topology. Gain: start-up 275.72 -> 126.89 s from ComputeCache plus lazy imports (n = 1) [Measured]; no repeatable C1 speed win from fresh autotune draws [Measured]. Cost: disk. Risk: a stale cache after an image change. Smallest falsifying experiment: two boots, cache mounted vs empty, compare time to API ready and the first-request latency.

## 6. Protocol

This is the protocol for changing any one backend choice (a `--*-backend` flag, a backend env var, a build arch) on a live lane. It follows the fleet rules on the entry page and the incidents in §4 and §7. See [Profiling protocol](14-profiling-protocol.md) for kernel attribution and [Quality and correctness gates](21-quality-and-correctness-gates.md) for the output gates.

Preconditions.
- Clean window: no client traffic. Check running and waiting requests and any client shim's in-flight count before each pass; discard a pass that overlaps traffic.
- No memory overcommit: at least 8 GiB `MemAvailable` on every node before a start, a 5 GiB warm floor while serving, and stop all benchmark traffic at 4 GiB `MemAvailable` on any node.
- One variable per boot. An A/B restart skips the image pull, so the backend under test is the only difference.
- Never restart a client gateway; engine restarts are the operator's step, a gateway restart is the operator's decision. Never `pkill -f` a pattern that also matches your own shell.
- All [entry-page](README.md) rules apply, in particular: greedy logprob probe after every relaunch; discard the first request and warm every shape; unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection line on every rank; ≥3 reps with a closing A/B/A; MemAvailable every 1-2 s and zero NV_ERR_NO_MEMORY/Xid; no reboot without per-node permission. For this page that means in particular the backend selection line on every rank, the same clock cap on every rank, a nonce with zero cached tokens, ≥3 reps, the first request discarded, and `MemAvailable` every 1-2 s.
- Record the baseline selection first: grep the current engine log for every backend line (vLLM `Using '...' backend out of potential backends`, `Selected ... backend`, `cudagraph_mode`, `use_trtllm_attention`/`decode_backend`; SGLang `server_info` fields `attention_backend`, `moe_runner_backend`, `fp8_gemm_runner_backend`, `sampling_backend`; llama.cpp build flags). Read the pinned source for the gate shape the change will hit (§2).

Change. Exactly one of: a backend flag, a backend env var, a KV dtype, a build arch for one binary. Never copy a MoE backend flag across quantization formats or models without re-gating: the same `FLASHINFER_CUTLASS` NVFP4 MoE that passes every gate on own Flash Next lanes is reported to corrupt one GLM NVFP4 build, and Marlin is reported to corrupt EXL3.

Run.
1. Boot and confirm dispatch: the new selection line must name the intended kernel. If the log shows a fallback (for example `EMULATION`, a BF16 emulation shape, `PIECEWISE` where `FULL_AND_PIECEWISE` was expected, or "Skipped N unsupported tactics"), record it and decide before measuring.
2. Warm every shape the lane will serve (sampler variants, chunk shapes, graph batch sizes), so no JIT compile happens during measurement or live serving.
3. Correctness first: a fixed-seed greedy reference comparison on a short prompt, then 4 repeated coding outputs at the lane's longest supported context, checked for token-0 or single-character loops. For a GEMM or MoE backend change, add a numerical gate on the lane's real shapes against a CUTLASS or Triton reference.
4. Speed: C1 coding and prose decode at a fixed prompt, C4/C8 aggregate, and cold prefill at 8K and the lane's long-context point, with the same repetition counts as the baseline packet.

Record (packet fields): engine, image digest and source commit; FlashInfer version and autotune cache key; the full before and after selection lines; `cudagraph_mode` and captured sizes; KV dtype; the one variable; correctness results (reference diff, repeated-output check, numerical gate error); decode and prefill numbers with repetition spread; minimum `MemAvailable` per node; start-up time; any JIT compile logged after warm-up.

Pass gate. Selection line names the intended kernel; zero corrupted outputs in the repeated-output check; numerical error within the reference's tolerance; decode and prefill at or above baseline beyond repetition spread, or a trade accepted in advance (as with dense FP8: decode up, prefill down); minimum `MemAvailable` at or above 5 GiB through the longest prefill.

Rollback. Revert the one flag or env var, restart with the pull skipped, confirm the selection lines match the baseline record, run one short decode and one cold 8K prefill, and compare within repetition spread before the lane serves again.

## 7. Anti-patterns and known-bad

- [Measured] + [Community-measured] + [Code-verified] Widening the FlashInfer TRT-LLM paged-decode guard from SM100 to SM121 for QSA sparse attention. Own evidence: 2 of 4 repeated coding outputs corrupted into token-0 loops (2026-08-27 Flash Next upstream recipe audit). SGLang PR #36845: 32/32 token id 0 at 120K-210K while HTTP stayed 200. Main carries a do-not-widen comment; use the Triton varlen kernel. History: #36649 widened with `is_sm121()` (merged, then superseded); #36556 (open) proposed `is_sm120_supported()`.
- [Historical diagnostic] Layering a newer kernel onto a base image that still carries an older BF16-only SM121 resolver: the stale resolver picked the wrong QSA kernel ahead of the FP8-capable one and the first production boot failed at graph warm-up. Assert and remove stale resolver blocks when layering images.
- [Code-verified] Setting `VLLM_NVFP4_GEMM_BACKEND`, `VLLM_USE_FLASHINFER_MOE_FP4`, `VLLM_FLASHINFER_MOE_BACKEND`, `VLLM_ATTENTION_BACKEND` or `VLLM_MXFP4_BACKEND` on a current vLLM: they do nothing, including where NVIDIA's own playbook sets them. Use `--moe-backend`, `--linear-backend`, `--attention-backend`.
- [Code-verified] Using `TRTLLM_MOE_BACKEND=TRITON` in TensorRT-LLM: the variable does not exist in the source. The selector is `moe_config.backend`.
- [Community-measured] Trusting DeepGEMM on GB10 by default: block-FP8 GEMM silently wrong at K = 2560 in an N/M window (vLLM #54125); the upstream attribute fix is not sufficient for checkpoints without E8M0 scales, where only `VLLM_USE_DEEP_GEMM=0` worked. SGLang pins before 2026-09-18 enabled DeepGEMM on GB10 with the wrong scale format; the PR #39482 author reproduced DeepGEMM's power-of-two scale assertion and CUDA error 719 on a DGX Spark in a small grouped FP8 × MXFP4 GEMM. DeepGEMM also generates `sm121_*` kernel names but ships only `sm120_*` headers, so a cache miss fails to compile (community DeepSeek V4 DSpark recipe CHANGELOG).
- [Interpretation] Reading the Marlin line "Your GPU does not have native support for FP4 computation" as a hardware fact. It prints whenever Marlin is chosen. Community sources that conclude "GB10 has no native FP4, so use Marlin W4A16" (vlaicu.io, exact text: "the GPU has no native FP4 compute, so dense layers run FLASHINFER_CUTLASS while MoE layers fall back to Marlin W4A16"; a SGLang fork README claiming all CUTLASS FP4 GEMM produces zeros/NaN on SM121; a community note on NGC 26.04 / vLLM 0.19) describe version- and tile-specific failures. Counter-evidence: own FlashInfer CUTLASS NVFP4 dispatch on two lanes, cuBLASLt FP4 at 99.6 TFLOPS peak, and post #15 in forum thread 365119, where a community image switched NVFP4 models back from Marlin to CUTLASS because of reported quality loss with the Marlin NVFP4 backend (the replier confirmed it). Post #6 there argues that dequantizing to BF16 costs bandwidth on a bandwidth-bound part.
- [Community-measured] Assuming "FlashInfer has no SM121 kernels, use triton". A community blog (sovgrid.org, dated 2026-03-20, no SGLang or FlashInfer version given) says so; own SGLang lanes run FlashInfer attention on GB10 with FlashInfer 0.6.17 and 0.6.18. The real gap it hit was narrow: FlashInfer #3297, a missing head_dim 512 template instance in FlashInfer 0.6.11 / 0.6.8.post1 with SGLang 0.5.11.
- [Interpretation] Copying a "use attention X on Spark" recipe across versions. The advice has flipped: an early SM121 fork said FA2 PTX was incompatible and FlashInfer was required; later notes said FlashInfer crashed and Triton was needed (vLLM #37754 with MTP = 2); current vLLM defaults to FA2 and forcing FlashInfer can cost the full decode graph unless XQA is available.
- [Code-verified] Building vLLM from source before 2026-07-28 with `TORCH_CUDA_ARCH_LIST` unset: a Fermi-era string rewrite turned `12.1` into `12.1(2.0)` and produced a "successful" build with `sm_75`-only cubins and `No compiled cutlass_scaled_mm ... capability: 121` (fixed by PR #49904, present in both pins).
- [Code-verified] Building ds4 without `make cuda-spark`: nvcc 13.0 emits compute_75 PTX that the driver JITs with Turing-era paths. [Interpretation] A llama.cpp binary with only `sm_120a` code loses the GB10 MMVQ table and L2 prefetch and would run from embedded PTX, since arch-specific cubins do not load across minor versions; unverified on hardware.
- [Community-measured] A KV dtype string routing to the wrong kernel: `nvfp4_ds_mla` sent decode to a slow BF16 path (~16× slower at 600K+ context, 1.0 vs 17.3 tok/s) until a hotfix (community DeepSeek V4 DSpark recipe, issue #22).
- [Community-measured] Upstream performance backports (adaptive top-k and a change without a CUDA-graph guard) caused silent token corruption under MTP + prefix caching + CUDA graphs on two DGX Sparks; `expandable_segments:True` produced NaN logits for prefills above 64 query tokens on one SGLang DeepSeek V4.1 build; FlashInfer's fused MoE finalize, picked by the autotuner for the 32-token bucket, made greedy output nondeterministic (`SGLANG_FLASHINFER_MOE_FUSED_FINALIZE=0` costs ~0.3 ms/step). All from the same community recipe family.
- [Historical diagnostic] JIT at serve time: unwarmed sampler and chunk shapes compile on the first live request, and in a multi-node lane that is a TP desync hazard. Persist every JIT cache and warm every shape.
- [Historical diagnostic] Citing public-head source as deployed state: research that read current FlashInfer sources concluded a native NoPE decode path was running; the installed FlashInfer 0.6.17 predates it by 278 commits. Quote the installed version.
- [Measured] Rejected on own lanes: batch 7,168 on the two-node GLM lane (+4% prefill for -640K context); grouped prefill tile variants (stock won every case); approximate INT8 GEMV (numerical gate failed); the experimental fused decoder (C8 -5.51%); the QSA launch-table retune (kernel 60.7 → 33.0 µs; end to end −2.5% to +2.4%, no repeatable gain); SGLang `--speculative-attention-mode decode` on Flash Next (coding 20.97 vs 62 tok/s; packet not re-opened for this page); NVFP4 KV on Flash Next (-29% decode per SGLang #36797 plus an open token-0 issue); the llama.cpp Q3 lane as a speed replacement (decode 11.72 vs 27.17 tok/s at ~495K).
- [Historical diagnostic] Expecting clean rebuild verification of a custom cooperative MoE binary: its whole-file hash gate fails on every clean rebuild (debug and path bytes), so rebuilds cannot be verified by hash.
- [Community-measured] Mixing up measurement scopes: bundle results (the cooperative MoE bundle, the KDA group) do not attribute gains to components, and single-run cells carry about ±2 tok/s noise.
