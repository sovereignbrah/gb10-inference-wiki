# Serving agent workloads: concurrency, scheduling, prefix reuse, TTFT budgets

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 128 GB unified memory), one to three nodes (node-1, node-2, node-3). A *pair* is TP2 on node-1 + node-2; the *triangle* is TP3/EP3 on all three. The agent client is a tool-using agent framework that reaches each engine through a thin metering proxy, which records per-request timing and token counts without content. Upstream code is quoted at vLLM `v0.30.0` (`ced6857`), SGLang `v0.5.20` (`94602c9`), llama.cpp `b11149` (`d2e5458`) and ExLlamaV3 `6b84a21`; the GLM-5.3-Flash EXL3 kit (MiaAI-Lab) at `0f49cfd`. The own lanes run forks and overlays, so a code line says what that tag does, not what a given lane runs.

Vocabulary used on this page. **Per-stream decode**: tokens per second of one request, first visible token to last. **Aggregate**: all active requests summed; never a single-stream claim. **Effective completion rate**: completion tokens divided by end-to-end seconds, which folds in queueing, prefill and reasoning. **Cn aggregate** in own harnesses is batch-wall aggregate (total completion tokens over batch wall time, queueing and prefill included) with fixed 512-token outputs unless a row says otherwise. **Newcomer**: a request that arrives while others are decoding. **Incumbent**: a request that is already decoding when a newcomer arrives. **Boot figure**: the vLLM line `GPU KV cache size: N tokens`, which is full-length concurrency times `max_model_len`, not a pool of reusable tokens.

## 1. What it is

A chat user sends one prompt and waits; an agent (a program that calls the model in a loop, runs tools, and feeds the results back) sends a long, mostly identical prompt every few seconds, often several agents at once. On the own fleet the median agent prompt is 30K to 130K tokens and the median answer is 100 to 360 tokens [Measured], [Historical diagnostic], so each turn is a small amount of new text on top of a large history the engine has already read. Serving that well is four decisions. Concurrency: how many requests the engine decodes together (the slot count), which trades each agent's speed for total throughput. Scheduling: when a newcomer's prompt is read (prefill, reading the prompt in chunks) while others are generating (decode, one token per step per request), which decides whether the newcomer waits seconds or minutes and whether the incumbents stall. Prefix reuse (skipping prompt text already read on an earlier turn): a hit turns a minute of prefill into about a second, and anything that changes the start of the prompt, such as a reasoning-effort line, a timestamp or a reordered tool list, throws the hit away. TTFT budgets (time to first token): how long a client should wait, and when a request should go to a different lane. On a GB10 these decisions weigh more than on a datacenter GPU because reading a prompt is slow (about 800 to 3,900 prompt tokens per second depending on model and lane [Measured], [Community-measured]), concurrent prefills do not speed each other up [Community-measured], a cold 95K-token prompt takes about a minute on the triangle [Measured], and the KV cache (per-token attention memory) shares the same 128 GB as the operating system, so the cache and the in-flight prefill both compete for the headroom that keeps a node alive. This page covers the agent workload model, the scheduler knobs of each engine, capacity per agent, prompt layouts that keep the prefix cache warm, lifecycle failures (timeouts, retries, cancellation), and routing between lane classes. Related pages: [Prefill optimization](04-prefill-optimization.md), [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md), [Memory on unified memory](11-memory-on-unified-memory.md), [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md), [Speculative decoding](02-speculative-decoding.md), [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md), [Quality and correctness gates](21-quality-and-correctness-gates.md), [Profiling protocol](14-profiling-protocol.md).

## 2. How each engine does it

### vLLM

- **Step order.** The V1 scheduler serves RUNNING requests first each step (their decode tokens and any in-progress prefill chunks), then admits WAITING requests into whatever is left of `max_num_batched_tokens` (`vllm/v1/core/sched/scheduler.py:609-667` for running, `854-866` for waiting @ `ced6857`). The waiting loop stops at `max_num_running_reqs = max_num_seqs` (`scheduler.py:124`, `864`). `long_prefill_token_threshold` (default 0 = off) caps how many tokens one prefilling request may take per step and also bounds block-aligned prefill ends (`vllm/config/scheduler.py:70-72`; `scheduler.py:470-480`). [Code-verified] Upstream therefore has no decode-protecting "skip" policy and no "fair" share; a waiting request gets only the leftover budget, so an in-progress long prefill with no threshold can delay newcomers for its whole duration. [Code-verified] The skip/fair policies measured in §4 are an overlay in the GLM EXL3 kit (see ExLlamaV3 in vLLM below), not upstream.
- **Admission.** `scheduler_reserve_full_isl` (default True) admits a request only if its whole prompt fits the KV cache, not just its first chunk; `watermark` (default 0.0) can hold back a fraction of blocks (`config/scheduler.py:172-183`). [Code-verified] A long cold newcomer therefore waits for pool room for its entire prompt. [Interpretation] `max_num_partial_prefills` and `max_long_partial_prefills` do not exist at this tag (no match in `config/scheduler.py` or `engine/arg_utils.py`); concurrent cold prefills are bounded only by the token budget and the per-request threshold. [Code-verified]
- **Priority.** Two policies: `fcfs` (default) and `priority` (lower value first, arrival time breaks ties); a request's `priority` must be 0 unless the server runs `--scheduling-policy priority` (`config/scheduler.py:141-147`; `entrypoints/openai/chat_completion/protocol.py:381-390`). Priority does not preempt for a slot: preemption happens only when a running request's KV allocation fails, and the victim is `max(running, key=(priority, arrival_time))` (`scheduler.py:745-760`; `v1/core/sched/request_queue.py:131-140`). [Code-verified] No GB10 measurement of the priority policy was found.
- **Load-shedding valves.** `--max-num-queued-reqs` (in-flight cap) and `--max-num-queued-tokens` (total prompt tokens in prefill) reject with HTTP 503, sized per the PR as target TTFT times prefill throughput; both default off (`config/scheduler.py:74-114`; PR #49445, merged 2026-08-31 as `dafbef1`). The token count uses the full `prompt_len` and does not subtract prefix-cache hits or chunked progress. [Code-verified]
- **Defaults when unset.** `engine/arg_utils.py:2719-2759` picks defaults by device memory: at least 160 GiB gives MNBT (max num batched tokens) 16,384 / `max_num_seqs` 1,024; at least 70 GiB and not an A100 gives 8,192 / 1,024 for the API server; anything else, including any exception while reading device memory (which sets it to 0), gives 2,048 / 256. The CUDA platform reads total memory through NVML (`platforms/cuda.py:833-836`). [Code-verified] Which branch GB10 takes is unverified on hardware: `nvidia-smi` reports memory as "Not Supported" on GB10, so if NVML's memory query raises, the fallback is 2,048 / 256; a platform class that reads torch `total_memory` instead would land in the 70 GiB branch. Recipes on this platform set both flags explicitly, which sidesteps the question. [Interpretation]
- **Prefix cache.** Only full blocks are cached; eviction is LRU over the free-block queue; `cache_salt` isolates tenants by salting the first block hash (`docs/design/prefix_caching.md` @ `ced6857`). For hybrid models, enabling prefix caching (the default) sets `mamba_cache_mode="align"`, which stores linear-attention state at the last token of each scheduler step and at block-size multiples; it falls back from `all` to `align` when unsupported and requires chunked prefill. `prefix_match_unit` controls matching granularity only, "not how often states are stored", and equals the hash block size; `prefix_cache_retention_interval=0` (default) keeps only semantic checkpoints (latest replay boundary and shared-prefix junctions); `enable_mamba_fine_grained_prefix_cache` is off by default (`config/cache.py:91-102`, `130`, `148-153`, `178-192`; `model_executor/models/config.py:622-651`). [Code-verified] A public issue claimed vLLM turns prefix caching off for hybrid models; at `v0.30.0` nothing in the hybrid path disables it. [Code-verified] See §8 for why that claim is not settled by measurement.
- **Observability.** `--kv-cache-metrics` (sampled) exports block lifetime, idle-before-evict and reuse-gap histograms; `vllm:num_requests_waiting_by_reason` splits capacity waits from deferred waits (`v1/metrics/loggers.py:518-529`, `915-959`; `engine/arg_utils.py:1540-1550`). [Code-verified] `usage.prompt_tokens_details.cached_tokens` is absent from responses unless the server runs `--enable-prompt-tokens-details`. [Measured] (2026-09-08 GLM 5.3 Flash pair E4 A/B)
- **Flags that matter for agents:** `--max-num-seqs`, `--max-num-batched-tokens`, `--long-prefill-token-threshold`, `--scheduling-policy`, `--max-num-queued-reqs`, `--max-num-queued-tokens`, `--enable-prefix-caching`, `--prefix-match-unit`, `--prefix-cache-retention-interval` (env `VLLM_PREFIX_CACHE_RETENTION_INTERVAL` in some kits), `--kv-cache-memory-bytes` (pins the pool), `--gpu-memory-utilization`, `--kv-cache-metrics`, `--enable-prompt-tokens-details`, and the CUDA-graph capture sizes in the compilation config (§4 shows capture sizes decide which concurrencies are fast).
- **GB10 guidance from the project.** The vLLM blog recommends `--max-num-seqs 4` for Nemotron-3-Super-120B-A12B NVFP4 on one Spark ("Above four concurrent decode streams the per-token bandwidth tax can outweigh continuous-batching gains, and time-to-first-token spikes"), explicit headroom through `--gpu-memory-utilization`, and caution on FP8 KV (vLLM blog 2026-06-01). [Community-measured] Contested by 8-slot measurements on smaller-active MoE models (§4, §8).

### SGLang

- **Policies.** `schedule_policy` defaults to `fcfs`; choices are `lpm`, `random`, `fcfs`, `dfs-weight`, `lof`, `priority`, `routing-key`, `hrrn` (`python/sglang/srt/arg_groups/fields/schedule.py:89-104` @ `94602c9`). The cache-aware policies are `lpm`, `dfs-weight` and `hrrn`; `lpm` and `hrrn` silently fall back to FCFS when more than 128 requests wait, `dfs-weight` does not fall back (`managers/schedule_policy.py:220-235`, `318-328`). [Code-verified]
- **Prefill first unless mixed.** `enable_mixed_chunk` is False by default; without it the scheduler "Run[s] prefill first if possible" and decodes only when no prefill batch forms (`managers/scheduler.py:3672-3681`; `schedule.py:191-194`). Mixed chunks are allowed with EAGLE, EAGLE3, DFLASH and DSPARK speculation but not ngram (`speculative/spec_info.py:139-150`). Other knobs: `chunked_prefill_size`, `max_prefill_tokens` (16,384), `prefill_max_requests`, `num_continuous_decode_steps` (default 1; the help text warns it "may also increase time-to-first-token"), `prefill_decode_interval` (`schedule.py:59-104`, `183-194`). [Code-verified] With defaults every decoder pauses for each chunk of a newcomer's prefill, the opposite trade from a decode-protecting policy. [Interpretation] That fits the own SGLang pair's concurrent tails of 1.6 to 9.0 tok/s with TTFT up to 60 s during overlap (2026-08-26 Flash Next TP2 operational monitoring), but no own A/B of `--enable-mixed-chunk` exists. [Interpretation]
- **Admission reservation.** For every running request the scheduler reserves decode room of `min(max_new_tokens - generated, 4096) × new_token_ratio`; the ratio starts at `0.7 × schedule_conservativeness` (capped at 1.0), decays over 600 steps to 0.14 of its initial value, and is re-estimated after retractions (`schedule_policy.py:79-81`, `708-716`, `1224-1231`; `managers/scheduler_components/new_token_ratio_tracker.py:13-48`; `environ.py:584-587`). [Code-verified] Agent clients that send large default `max_tokens` inflate this reservation (up to the 4,096 clip) and admit fewer newcomers; `schedule_conservativeness > 1` makes it stricter. [Interpretation]
- **DFlash admission delayer.** With DFlash-family speculation and `max_running_requests >= 8`, a min-free-slots delayer is enabled automatically: fresh prefill admissions wait until `min(4, max(2, (N+5)//6))` slots are free (2 at N=8, 3 at N=13 to 18), per rank, and it is skipped during an in-progress chunked prefill (`managers/min_free_slots_delayer.py:4-38`; `scheduler.py:1178-1190`, `3776-3789`). [Code-verified] Its newcomer-TTFT effect is unmeasured anywhere found.
- **Priority.** `--enable-priority-scheduling` schedules higher integers first by default, the opposite of vLLM, unless `--schedule-low-priority-values-first`; preemption needs a priority gap of at least `priority_scheduling_preemption_threshold` (default 10); `retraction_policy` is length or priority; `radix_eviction_policy=priority` aligns cache retention with admission (`schedule.py:105-140`; `docs/docs/advanced_features/radix_eviction_policy.mdx`). [Code-verified] No GB10 measurement found.
- **Prefix cache.** Radix tree with `lru` (default), `lfu`, `slru` (protected threshold default 2) and `priority` eviction; `--enable-session-radix-cache` makes eviction consume unreferenced entries before session-referenced ones; hierarchical host cache via `enable_hierarchical_cache` and `hicache_ratio` (`arg_groups/fields/memory.py:32-50`, `90-93`, `100-113`). [Code-verified] Hybrid sliding-window checkpoints follow chunk boundaries (§4, the 32,000-token shared-prefix row). An RFC for agent-aware whole-session eviction on StreamingSession was redesigned on a radix session cache and then auto-closed; the maintainer's objection was that StreamingSession "is difficult to work with and debug", while invisible KV pinning by idle sessions was the RFC author's own motivation (sglang #29099). [Community-measured]
- **Hybrid state slots.** On hybrid models with speculation each running request needs `1 + draft tokens` Mamba state slots, and the derived `max_mamba_cache_size` caps running requests below `max_running_requests`, logged only at info level (sglang #36889). [Community-measured] The own single-node hybrid Qwen lane saw 8 requested slots capped to 6 this way. [Measured] (2026-08-29 single-node Qwen k10 pool-cap changelog)
- **Memory heuristic.** When `mem_fraction_static` is not given, SGLang reserves, in MiB, about `512 + 1.5 × max(chunked_prefill_size, 2048)` plus parallelism and CUDA-graph terms (`max_bs × 2` and a TP×PP term), with a 10 GiB floor on devices above 60 GiB (so at least 10 GiB on GB10), and skips the estimate under post-capture KV sizing (`arg_groups/memory_hook.py:56-70`, `287-310`). The docstring's "GB" is a unit error; the code works in MiB. [Code-verified]
- **Routing.** The sgl-model-gateway offers `cache_aware` routing (a prefix tree of prompts with balance thresholds), `power_of_two`, round-robin, random and bucket policies, plus rate limiting, queuing, retries and per-worker circuit breakers (`sgl-model-gateway/README.md:25-33`, `736-741`). [Code-verified]
- **GB10 status.** A concurrency-dependent correctness defect with DFlash speculation on SM121 is open (§4, §7). Own lanes ran SGLang only with `fcfs` at 4, 5 and 8 slots; `lpm`, priority, mixed chunk and conservativeness were never measured on GB10 by anyone found.

### llama.cpp and forks

- **Slots and batching.** `-np` sets parallel slots (auto = 4 with unified KV); continuous batching is on by default; defaults `n_batch` 2,048 and `n_ubatch` 512. Each iteration first adds the sampled or drafted tokens of generating slots, then fills the batch with pending prompt tokens up to `n_batch`, so decode is never skipped and prompt chunks take what remains (`tools/server/server-context.cpp:3098-3125`; `tools/server/README.md:52-53`, `176-177` @ `d2e5458`). No priority, queue-policy or fair-share option appears in the server argument table. [Code-verified]
- **Context per slot.** Without unified KV each slot gets `n_ctx / n_seq_max`; `--kv-unified-per-slot N` caps per-slot context and, without `-c`, sizes the shared pool to `n_parallel × N` (`src/llama-context.cpp:291-305`; `tools/server/server.cpp:156-161`; `README.md:164`, `168`). [Code-verified]
- **Reuse.** A request takes the idle slot with the highest longest-common-prefix fraction above `--slot-prompt-similarity` (0.10); `--cache-ram` (default 8,192 MiB, which on GB10 comes out of the same memory) keeps evicted slot prompts in host RAM; `--ctx-checkpoints` stores up to 32 per slot at a minimum 8,192-token spacing for sliding-window and hybrid models; `--cache-reuse N` (default 0) enables KV shifting (`server-context.cpp:1547-1605`; `README.md:165-169`, `221-225`). [Code-verified] With more agents than slots, agents share slots and warm reuse depends on the host prompt cache. [Interpretation] `--reasoning-effort` is a server-level template control; a per-request effort change goes through request template kwargs, and where the template places the text decides cache safety as on the other engines. [Interpretation]
- **GB10 data.** `llama-batched-bench` on a DGX Spark shows flat prompt processing and rising generation throughput with batch size (§4). One 8-slot short-prompt ladder exists (§4). No long-context (50K+) concurrent agent-serving data for llama.cpp proper on GB10 was found. The only fork data is the own single-node ds4 CUDA fork, which plateaued at about 47 to 48 tok/s aggregate from C4 to C12 because its safe 1M launch admitted four KV banks. [Measured] (2026-08-22 single-node native ds4 engine v0.6.3 qualification)

### ExLlamaV3 in vLLM

- **Standalone ExLlamaV3** (`6b84a21`). The dynamic generator uses `max_chunk_size=2048`, documented as "can be lowered to trade off prompt speed for a shorter interruption to ongoing jobs when a new job is started"; `max_batch_size=256`, limited dynamically by cache space; the docstring warns that "speculative decoding with many parallel jobs is likely not advantageous" (`exllamav3/generator/generator.py:30-80`). Page eviction goes empty pages, then orphaned chains, then complete cached sequences by least-recently-used root, pruned tail-first so "the longest possible prefix survives"; recurrent-state checkpoints every 32,768 prompt tokens by default (`recurrent_checkpoint_interval_pp`), 4 GiB recurrent cache, optional CPU page tier; prefix hits stop at the last page with a stored recurrent state (`generator/pagetable.py:258-297`, `330-336`, `387-405`; `generator.py:40-44`; `cache/recurrent.py:21-39`). [Code-verified]
- **In vLLM (GLM-5.3-Flash EXL3 kit `0f49cfd`, vllm-exl3 plugin `78e1727`).** The vLLM V1 scheduler with kit overlays. `GLM53_MIXED_PREFILL_CHUNK` selects the mixed-prefill policy while a peer decodes: `fair` (default on the TP2, TP3 and TP4 launchers), `skip` ("starves prefills until decode ends"), `N>0` (cap mixed chunks) or `0`/`off` ("admits newcomers in ~1 s but collapses the incumbent 10–36× on TP=2") (`README.md:1396`). Fair v5 "allocates decodes first, charges only prefill that contends with a decoder, fits a fixed-plus-per-token step cost, runs the largest chunk that fits" the step budget. Its knobs: `GLM53_FAIR_PREFILL_CHUNK=256` (probe chunk), `GLM53_FAIR_PREFILL_SHARE=0.30`, `GLM53_FAIR_PREFILL_MAX_INTERVAL_MS=2000`, `GLM53_FAIR_PREFILL_MAX_STEP_MS=2000` ("the one knob for how long the incumbent may pause per mixed step"), `GLM53_FAIR_PREFILL_MAX_CHUNKS=1` (`README.md:1397-1401`; `.env.tp3.example:63-72`). [Code-verified]
- **Kit defaults relevant to agents.** `MAX_NUM_SEQS=4` and `MAX_NUM_BATCHED_TOKENS=7168` on TP2, with 2,048 called "the best measured balance" on a 16-sequence geometry and on TP4 (`README.md:202-205`, `1386-1387`, `1236`). `GLM53_KV_CAPACITY_LOG=1` logs, after the boot figure, the usable block ids, the ids one aligned cached segment costs across groups, and the resulting cached-conversation capacity; the README states the boot figure is "max_concurrency × max_model_len, **not** a pool size" (`README.md:1395`). `GLM53_APC_NO_STORE=1` honours a per-request no-store flag. `DEFAULT_MAX_NEW_TOKENS=65536` applies only when a request omits `max_tokens` and "does not reserve admission capacity … admission is chunk-based" (`README.md:1392-1394`). [Code-verified]
- **Drafter placement on TP3.** The DFlash2 drafter's 32 attention heads and 8 KV heads do not divide by 3, so the kit pads them to 36/9; the kit's TP3 example sets `DFLASH_DRAFT_TP=1` (`.env.tp3.example:73-75`), which the proposer does not read; the drafter runs on every rank on both the kit and the own triangle (see [Speculative decoding](02-speculative-decoding.md) §2; a per-rank shape dump is still owed). The own triangle also compacts the drafter KV.
- **Hybrid prefix granularity.** The cache page is aligned to the linear-attention state page (2,560 tokens on the own triangle, 3,584 on the own pair) with partial hits off, so every warm turn recomputes the trailing partial page (§4). The kit's TP3 example says to leave `PREFIX_MATCH_UNIT` empty: "512-token prefix-match is illegal on this hybrid stack (KDA align block is 64)" (`.env.tp3.example:50-52`). The own triangle already matches at a 64-token hash block, and match granularity does not add state checkpoints, so the warm-turn floor is set by where state is stored (the 2,560 page with partial hits off), not by the match unit. [Interpretation]
- **Single-node EXL3.** The single-Spark EXL3 K2 plugin recipe measured by a community harness ran with `max_num_seqs 1`, so concurrency only queued (§4).

### TensorRT-LLM (status)

KV reuse with prioritized LRU (priority 0 to 100 per token range with an optional duration), host offload, partial block reuse on by default, and KV cache events for routing; NVIDIA reports about 20% higher hit rates from priority eviction in internal benchmarks (TensorRT-LLM docs "KV Cache System" and NVIDIA technical blog 2025-01-16, both fetched 2026-09-23). [Community-measured] No GB10 agent-serving measurement was found. Per-token-range retention is the closest vendor analogue to the agent-aware retention ideas in §8.

## 3. What is different on GB10 / SM121

- [Community-measured] **Concurrent prefills do not batch.** Single Spark, vLLM, Qwen3-Coder-Next INT4, 8K distinct prompts: aggregate prefill 3,881 tok/s at 1 request vs 3,931 at 8 (+1.3%) while median latency rose 3.1 to 15.8 s (sergioamsilva). llama.cpp `llama-batched-bench`, gpt-oss-120B MXFP4, 4,096-token prompts: prompt processing flat at 2,401 to 2,414 tok/s for B = 1 to 32 while generation rose 55.2 to 262.2 tok/s. Two engines agree: on GB10 a second cold prompt only splits the same prefill rate, so cold newcomers queue in time even when slots are free.
- [Measured] **Cold prefill is measured in minutes at agent depths.** GLM 5.3 Flash triangle: 95K about 52 to 60 s, 524K about 343 s, about 1M 716 to 719 s cold; an 85K prompt 56.7 s cold vs 1.3 s cached (2026-09-16/17 combined-runtime qualification; 2026-09-23 V3.2 verification). A TTFT budget that ignores the cache state is meaningless.
- [Historical diagnostic] **On unified memory the KV pool is not the capacity limit; the per-request prefill working set is.** A DeepSeek V4.1 triangle wedged on a ~200K-token agent turn with the pool 25 to 28% full, because the indexer transient (proportional to chunk × prefix) plus allocator growth overran the headroom left at a 0.95 static fraction (2026-09-16 DeepSeek V4.1 TP3 wedge changelog). Capping the pool does not cap the request; cap context or chunk as well (see [Memory on unified memory](11-memory-on-unified-memory.md)).
- [Code-verified] **The vLLM boot figure is concurrency × max_model_len, not a pool.** The GLM kit README says so explicitly (`README.md:1395` @ `0f49cfd`). Every "KV pool" figure quoted from that line on this page is labelled a boot figure. The binding unit on hybrid kits is block ids per aligned cached segment plus a length-independent per-sequence floor (§4, kit occupancy row).
- [Measured] **Hybrid models set the reuse grain.** The own fleet's GLM, Qwen Flash Next and Qwen 27B models are hybrids (linear-attention layers plus attention). Their cache page is thousands of tokens (2,560 on the triangle, 3,584 on the pair), so each warm turn pays a trailing-page recompute, and resume points exist only where the scheduler stored a state (2026-08-30 GLM reasoning hardening and multi-turn evidence; 2026-09-16/17 combined-runtime qualification).
- [Community-measured] **Hybrid state slots cap concurrency silently on SGLang.** A pair running hybrid GLM-5.3-Flash NVFP4 with DFlash2 reported 8 running slots while the Mamba state cache admitted 2 (sglang #36889); an own single-node Qwen lane capped 8 to 6 [Measured].
- [Community-measured] **Speculative decoding interacts with concurrency on SM121.** On SGLang with DFlash2, Qwen3.8-27B NVFP4 on GB10, greedy: 0/100 wrong serially vs 7/100 at concurrency 8 on the base set, 111/304 on an expanded set of affected items, 0/304 without speculation (sglang #36548, open; GB10 data from a commenter, issue filed on an RTX Pro 6000). Throughput-only concurrency sweeps miss this (see [Quality and correctness gates](21-quality-and-correctness-gates.md) lever 4).
- [Community-measured] **Speculation gains shrink as concurrency rises.** EAGLE3 on gpt-oss-120B, single Spark: ±2% at every level from c=1 to c=256, acceptance 0.73 to 0.29 (Dendro Logic, "Four Iterations On"). On a four-Spark GLM-5.3-Flash EXL3 shape with 81K to 150K agentic prompts, DFlash2 k=3 beat k=7 at x1 and x4 (MiaAI-Lab issue #113).
- [Community-measured] **CUDA-graph capture sizes decide which concurrencies are fast.** Default captures pad c=5 to 8 and c=10 to 16; adding 5 and 10 raised c=5 from 81.1 to 118.7 and c=10 from 104.3 to 160.5 tok/s (Dendro Logic). The own first C4 batch on a new lane read 47.9 tok/s at 17.7 s TTFT from first-shape compile [Measured] (2026-09-14 GLM TP3 triangle qualification). See [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md).
- [Historical diagnostic] **vLLM notices a client abort only after the prefill finishes.** A runaway deep prefill could not be cancelled quickly on single-node vLLM lanes (2026-08-16 GB10 fleet serving bake-off). On GB10, where a deep prefill runs for minutes, this makes admission gating matter more than cancellation.
- [Code-verified] **Unset vLLM defaults on GB10 are unknown.** The default `max_num_seqs` / MNBT depend on an NVML memory query that GB10 reports as "Not Supported" (§2 vLLM). Always set both.
- [Code-verified] **SGLang's automatic memory reserve is at least 10 GiB on a 128 GB device** (§2 SGLang), before any agent-specific headroom. Budget it as part of the node's floor.

## 5. Levers, ranked

Ranked by measured gain on agent-shaped traffic, then by cost. Gains are bands from §4; "own" means measured on this fleet.

1. **Keep everything before the last user turn byte-stable** (reasoning-effort text before the latest user turn or appended to it; no timestamps, per-request headers or hashes at the head; deterministic JSON; no mid-session tool-list changes). Applies to: every engine × every model family × every topology, because prefix hashing is chained from token 0. Gain: a mode switch at 152K tokens 92.3 s -> 2.1 s own GLM [Measured]; 0 -> 8,960 cached, 12 to 14 s -> 0.4 to 0.7 s own DeepSeek V4.1 [Measured]; 0 -> 19,296 reused own Qwen Flash Next [Measured]; hit rate 0.06% -> 99.96% on a community coding-agent client [Community-measured]. Cost: a proxy or template change; at max effort the GLM pre-last-user placement thought ~6× longer on one fixture [Measured]. Risk: placement after the last user turn produced malformed output on GLM (9/20) [Measured]; an unconditional closed-thinking head line is an untrained shape [Historical diagnostic]; a proxy re-render must match the native template token for token. Smallest falsifying experiment: a low -> high -> low tier sequence on a ≥46K-token history, reading `cached_tokens` per request; the lever fails if the second and third requests do not reuse everything up to the final user turn.
2. **Decode-protecting fair mixed prefill instead of skip or off.** Applies to: vLLM + the GLM EXL3 kit overlay (TP2/TP3/TP4); the idea transfers to any engine with a prefill budget per step, but only this overlay implements it. Gain: 2K newcomer TTFT 130 -> 5.9 s, 30K 139 -> 109 s, C8 aggregate +12.6% own triangle [Measured]; 8.7 s and 110 s on the kit's triangle [Community-measured]. Cost: the incumbent runs ~30% slower while newcomer chunks run at 7,168-token chunks, ~4% over a whole 2K case, ~20% over a 30K case [Measured]; the kit measured 13 to 17% at the same share and step [Community-measured] (§8, C5). Risk: share 0.30 roughly doubles the incumbent penalty vs 0.20 [Community-measured]; a step budget the fitter cannot satisfy for the lane's chunk and slot geometry deadlocks it [Code-verified]; every fair-policy row on this page (own and kit) ran at the README's 1,000 ms without deadlock, and the failing geometry is not recorded here. Chunk and step sizing: [Prefill optimization](04-prefill-optimization.md). Smallest falsifying experiment: the overlap fixture (thinking essay + 2K and 30K newcomers at +10 s) under skip and fair on the same boot recipe; fair fails if newcomer TTFT does not fall below the essay's remaining time.
3. **Size slots to the offered concurrency, not to a platform constant.** Applies to: vLLM `--max-num-seqs`, SGLang `--max-running-requests`, llama.cpp `-np`, kit `MAX_NUM_SEQS`; strongest on MoE models with 3B to 18B active parameters. Gain: one factor 4 -> 8 slots, C8 aggregate +44% with C1 and C4 flat on own single-node Flash Next [Measured, 2 batches; re-qualify]; bundled 4 -> 8 on the GLM triangle C8 TTFT 10.6 -> 0.5 s [Measured] (bundle). When offered load exceeds slots the signature is flat aggregate plus TTFT p95 37 to 41 s [Measured]. Cost: per-stream decode falls (-17.5% at C8 in the GLM bundle [Measured]; community ladders fall to about 23 to 36% of solo at 8 to 16 streams [Community-measured]). Risk: on hybrid SGLang lanes the Mamba state cache may cap the real count silently [Community-measured]; each extra slot adds a CUDA-graph shape. Smallest falsifying experiment: one-factor slots 4 vs 8 at C1/C4/C8 with TTFT p50/p95 and per-stream decode recorded; fails if C8 aggregate does not rise or C1 falls outside the baseline band.
4. **Chunk budget sized to the incumbent's tolerable pause.** Applies to: vLLM MNBT/LPT, SGLang `chunked_prefill_size`, ExLlamaV3 `max_chunk_size`. Gain: incumbent worst gap 2.37 -> 1.02 s with newcomer TTFT unchanged, 7,168 -> 4,096 own triangle [Measured]; also changed the boot figure and turned a 524K repeat miss into a hit [Measured]. Cost: about -4% cold prefill per halving [Measured]. Risk: very large budgets hurt decode (MNBT 32,768 halved single-Spark generation, 74.3 -> 34.9 tok/s) [Community-measured]; on DeepSeek V4.1 SGLang a profile including chunk 256 (with 8 slots and a 2M pool, not isolated) halved cold prefill, and whether a separate isolated chunk-256 arm exists is unsettled; a larger chunk (1,024) wedged the lane near 200K [Measured], [Historical diagnostic]. Smallest falsifying experiment: overlap fixture at two chunk budgets on the same recipe; fails if the incumbent max gap does not scale with the chunk. Owner: [Prefill optimization](04-prefill-optimization.md).
5. **Two in-flight prefills where the engine exposes it.** Applies to: vLLM DSpark (DeepSeek V4 family) `DSPARK_MAX_INFLIGHT_PREFILLS`; no equivalent upstream vLLM knob at `v0.30.0`. Gain: 4 × 8K first-token spread -39%, aggregate +7.4%, no C1 loss, own pair [Measured]; mostly fairness, and a mixed soak also rose 69.1 → 91.6 tok/s (one arm). Qualified before the kit's admission-count fix; unconfirmed after it: only a post-fix cap-2 run exists, with no paired cap-1 arm ([Prefill optimization](04-prefill-optimization.md) §8), and the public kit's default flipped four times on same-topology A/Bs and now stays at 1, with 2 operator-qualified ([MiaAI-Lab recipes](18-case-study-miaai-lab-recipes.md) §7). Cost: memory for a second prefill working set. Risk: on GB10 concurrent prefills share one prefill rate [Interpretation]. Smallest falsifying experiment: 4 × 8K concurrent cold prompts at 1 vs 2 on the post-fix kit, three trials, fresh nonces.
6. **Pin the KV pool and cap tokens explicitly.** Applies to: every engine; `--kv-cache-memory-bytes`, SGLang `--max-total-tokens`, llama.cpp `-c`. Gain: capacity becomes a declared constant; host headroom +17 to +23 GiB with C1 to C5 unchanged, own Qwen lanes [Measured] (see [Memory on unified memory](11-memory-on-unified-memory.md) and [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md)); 37.8 GiB freed with decode unchanged on a community single-node lane [Community-measured]. Cost: none measured on throughput. Risk: a pin sized to resident sessions rather than measured occupancy evicts warm histories; lowering `max_model_len` is not the same lever on hybrid kits (§7). Smallest falsifying experiment: boot at the cap, run C1 to C5 and one long repeat; fails if any cell leaves the baseline band or host MemAvailable does not rise.
7. **Lifecycle hardening: verified cancellation, deadlines matched to cold-prefill anchors, no retry without cancel.** Applies to: every engine and client. Gain: removes duplicate generations (a retry storm doubled task time, ~29 vs ~14.5 min [Measured]) and orphan decodes (35 to 48 tok/s of wasted aggregate [Measured]). Cost: client configuration and a cancellation patch where the engine lacks it. Risk: raising a timeout alone hides the symptom. Smallest falsifying experiment: disconnect a streaming request mid-decode and mid-prefill; fails if the engine does not return to 0 running within seconds (SGLang after the backport: 4 to 7 s [Measured]; vLLM: only after prefill [Historical diagnostic]).
8. **Route by lane class.** Applies to: multi-lane fleets. Single-node lanes for short-context, decode-heavy, latency-sensitive turns while they hold warm; the TP3 lane for long cold contexts because it has the largest boot figure (3.94× concurrency at 1M) and, on the kit's hardware at share 0.20, the faster contended prefill (~268 vs ~179 tok/s) [Interpretation]; never two long cold sessions on one lane (8.3 -> 319 s [Measured]). Gain: avoids the minute-scale collisions in §4; not measured as a policy. Cost: a router or per-task lane choice. Risk: warm reuse is per lane, so rerouting a session mid-conversation pays a cold prefill. Smallest falsifying experiment: the same agent task on single-node vs TP3 lanes with cached-token stamping; the rule fails if the TP3 lane's per-turn wall time is not lower once the history exceeds ~100K.
9. **Raise hybrid state slots with speculation (SGLang).** Applies to: SGLang × hybrid (KDA/Mamba) models × DFlash-family speculation. Gain: c8 +70%, c12 +75% on a community pair [Community-measured]. Cost: ~6% single stream, more state memory (bf16 SSM state, fraction 0.90). Risk: fraction 0.90 on a 128 GB node crowds the floor; the DFlash concurrency correctness defect (§7) applies to the same stack. Smallest falsifying experiment: read the running count in the scheduler log at C8 before and after; fails if it already equals the requested slots. Owner: [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md).
10. **Capture CUDA graphs at the concurrencies the fleet actually sees.** Applies to: vLLM and SGLang with graph capture. Gain: c=5 +46%, c=10 +54% [Community-measured]. Cost: -18.7% prefill aggregate at c=256 [Community-measured]; capture time and memory. Risk: first-shape compile during a live batch (47.9 tok/s at 17.7 s TTFT [Measured]). Smallest falsifying experiment: C5 with and without a size-5 capture. Owner: [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md).
11. **Lower speculation depth for concurrent long-context agents.** Applies to: DFlash2 on GLM EXL3; EAGLE-family generally. Gain: k=3 over k=7 at x4 +27% on a four-Spark shape [Community-measured]; EAGLE3 net ±2% at c ≥ 1 on gpt-oss [Community-measured]. Cost: single-stream loss where acceptance is high. Risk: own DeepSeek V4.1 k=3 lost 11.0% on code in a same-day A/B [Measured]; this is per model. Smallest falsifying experiment: C1 and C4 at k=3 vs the lane's k with the same long agentic prompts. See [Speculative decoding](02-speculative-decoding.md).
12. **Untested or unmeasured on GB10** (all [Proposed]): prefix retention interval as an isolated arm (copied into recipes without an A/B); `mamba_partial_cache_hit` and state-checkpoint spacing to remove the flat trailing-page recompute; a page-aligned long-prefill threshold of 2,560 (untried; the 2026-09-20 scheduler receipt voided the page-grown-block premise, see [Prefill optimization](04-prefill-optimization.md) §4, so the predicted step-time gain is unsupported; it would also serialise concurrent cold prefills); internal KDA prefill checkpoints; SGLang `--enable-mixed-chunk`, `lpm`/`hrrn`, `schedule_conservativeness`, priority scheduling in either engine; the vLLM 503 valves (`--max-num-queued-tokens` overcounts cached prefixes by design, so it fits only cold-heavy traffic [Interpretation]); SGLang `cache_aware` gateway routing across lanes. Each needs the overlap fixture or the multi-session residency test from §6 before it is a lever.

## 6. Protocol

Use this to change or qualify any scheduling, concurrency or cache setting on a lane that serves agents. It builds on [Profiling protocol](14-profiling-protocol.md) and the memory rules in [Memory on unified memory](11-memory-on-unified-memory.md).

**Preconditions.**
- Fleet rules from the entry page: never overcommit memory (keep the warm floor free on every node, keep headroom before a start, raise a KV pin in bounded steps); one variable per boot; stop benchmark traffic when any node's MemAvailable drops below 4 GiB and preserve the engines; clean window with no outside requests (a contaminated pass is discarded, not averaged); restart-based A/Bs skip the image pull so arms stay identical; never restart an agent gateway to test an engine change; never `pkill -f` a pattern in your own command line.
- Record the lane state: image digest, recipe hash, slots, MNBT/LPT or chunk size, mixed-prefill policy and its knobs, KV pin and boot figure (labelled as boot figure), capacity log if the kit has one, `max_model_len`, speculation config, graph capture sizes.
- Confirm the meter is trustworthy: it parses the runtime's reasoning delta field (a meter that missed it reported late TTFT and inflated decode on reasoning turns [Historical diagnostic]); the proxy is aliased to its engine so aggregates are not double-counted; `cached_tokens` is present per request (vLLM needs `--enable-prompt-tokens-details`; SGLang `--enable-cache-report`).
- Confirm cancellation: disconnect one streaming request mid-decode; the engine must return to 0 running within seconds. If it does not, fix that first (§5 item 7).
- Confirm the client: its context limit equals the engine's (client limits that disagreed with the engine silently truncated or over-admitted [Historical diagnostic]); its request and first-token timeouts exceed the lane's cold-prefill anchor for the largest context it will send (§4 cold anchors); it does not retry after partial tool-call delivery without cancelling; auxiliary calls (titles, summaries) carry a token cap, a thinking control, streaming and cancellation, because they compete for the same slots.

**Fixtures** (fresh nonce at the head of every cold prompt so the cache cannot fake prefill):
- C1 / C4 / C8 at fixed 512-token outputs, at least 3 batches per cell, with a closing baseline arm (A/B/A), reporting aggregate, per-stream decode and TTFT p50/p95 side by side. Discard the first batch after a boot (first-shape compile).
- Overlap fixture: an incumbent thinking-on essay; a 2K and a 30K cold newcomer at +10 s. Record newcomer TTFT, incumbent decode during newcomer chunks, and incumbent maximum inter-chunk gap.
- Warm-turn fixture: a history at the lane's typical agent depth (median 30K to 130K here), then 3 to 4 appended turns with 2 to 5K new tokens each; record per-turn `cached_tokens`, uncached tokens, TTFT.
- Effort-switch fixture: low -> high -> low on a ≥46K history (if the lane exposes reasoning tiers).
- Residency fixture: N sessions with distinct cached prefixes interleaved, N = 1, 2, 4, 8 at 50K and at the lane's long-context target; record hit rate and TTFT p95 per N.
- Cold anchors: one cold prompt at 8K, 32K, 95K and the largest supported depth, n=1 each, recorded as budget inputs.
- Natural-EOS mixed soak at the target concurrency for at least 10 minutes, plus a fixed-seed greedy correctness set at that concurrency when speculation is on (a throughput sweep alone missed 7/100 wrong answers at c=8 on one SGLang DFlash stack [Community-measured]; see [Quality and correctness gates](21-quality-and-correctness-gates.md)).

**Change.** Exactly one of: policy, share, step budget, chunk budget, slot count, in-flight prefills, KV pin or token cap, retention setting, graph capture list, speculation depth, prompt-layout proxy. Bundles are allowed only for promotion after each component has its own arm, and are labelled as bundles.

**Record (packet fields).** Baseline and candidate recipe hashes; MemAvailable per node before, at peak and after; boot figure and capacity log; every fixture cell with n, spread and outside-traffic receipts; per-request `cached_tokens`; incumbent max gap; wall-time split per warm turn (queue, uncached prefill, decode) where the meter allows; running and waiting counts from the engine during C8 (to catch hidden slot caps); disconnect -> 0 running time; any error or NV memory message.

**Pass gate.** C1 per-stream decode inside the baseline band; C4 aggregate not lower than baseline beyond rep spread; the targeted metric improves beyond spread (for example newcomer TTFT, C8 TTFT p95, incumbent max gap); warm-turn reuse unchanged or better; residency at the lane's declared N stays at hit ≥ 0.99; correctness set unchanged; every node above the warm floor throughout and never below 4 GiB MemAvailable; correctness per [Quality and correctness gates](21-quality-and-correctness-gates.md). A quick probe of a few reps never promotes: on the own fleet uncontrolled quick probes produced headlines the frozen harness did not reproduce [Historical diagnostic].

**Rollback.** Keep the previous recipe as the lane's rollback target; restore it with the same one-variable boot. If a candidate wedges a node or drops MemAvailable below the stop line, stop traffic, keep the engines up for diagnosis, and restore only after the incident is logged. Client-side changes (timeouts, proxies) roll back separately from engine changes, and any gateway restart they need is handed to the owner.

## 7. Anti-patterns and known-bad

- [Measured] **Reasoning-effort or mode text at the head of the prompt.** Every switch re-prefills the whole history: ~84 s at median depth and 207 s worst on the GLM pair; 0 reused tokens on DeepSeek V4.1 native encoding and on the Qwen Flash Next template (§4). The same failure comes from DeepSeek's hoisting of trailing system messages to the front and from per-turn memory blocks injected into every user turn (~6 to 8K tokens each on another lane; a 42K prompt that reused 32.8K still prefilled 9.6K new tokens) [Historical diagnostic].
- [Measured] **Effort text after the last user turn on GLM.** Cache-unsafe on the next call and malformed output in 9/20 high-tier reps. Do not retry this placement.
- [Historical diagnostic] **Unconditional head line with a closed thinking block.** An untrained shape; upstream measured a quality loss with it and it was reverted.
- [Community-measured] **Per-request identifiers at the head of the system prompt.** A coding-agent client's changing billing hash cut hits to 0.06% until a proxy stripped it (jleighfields). Timestamps, unstable JSON key order and mid-session tool-list changes do the same (Manus, vendor guidance, hosted models).
- [Community-measured] **Assuming tool order is harmless.** On one single-Spark vLLM build, 31 tools with `write` last produced garbage at 33,254 tokens and were clean with `write` first; the author states the mechanism (uncached residual tripping a CUDA-graph shape defect) is unproven. Practical rule: after any image or flag change, replay a stored agent request body, not only synthetic prompts.
- [Measured] **Treating aggregate as speed.** C8 aggregate +61% came with -17.5% per-stream decode on the GLM triangle, and overlapped live requests ran at 25.77 vs 40.35 tok/s effective completion single-stream on the DeepSeek V4 pair. Report both, label both, and alias metering proxies to their engine so aggregates are not double-counted [Historical diagnostic].
- [Measured] **More offered load than slots.** C8 on 4 slots gave +3% aggregate and TTFT p95 37 to 41 s on two lanes; a community K2 single-node recipe at `max_num_seqs 1` gave flat 21.3 tok/s with TTFT 1.6 -> 36.8 s [Community-measured]. An image default below the offered load produced 134 s TTFT at 48 to 256 calls [Community-measured].
- [Measured] **Lowering `max_model_len` to buy concurrency on hybrid EXL3 kits.** No measurement shows it works: own pair 500K vs 896K left the boot figure at ~906 to 907K (with 2.2 GiB more KV memory at 500K) and 300K reuse unchanged; on a DCP4 kit the banner fell while implied concurrency rose only 6% [Community-measured]. The kit README asserts the hybrid floor "then shrinks the pool" without a receipt. Pin KV explicitly and size by measured occupancy. (On plain single-node vLLM with KV unpinned, KV is sized from free memory, so there the pin, not the context, is the lever [Community-measured].)
- [Historical diagnostic] **Sizing capacity by the pool and forgetting the request.** The DeepSeek V4.1 triangle wedged near 200K with the pool 25 to 28% full; a leftover-sized SGLang pool (1.64M) on one node left ~7 GiB free and ended in a reclaim wedge [Measured]; same-step memory changes have wedged nodes [Historical diagnostic]. One memory variable per boot; cap chunk or context as well as pool (see [Memory on unified memory](11-memory-on-unified-memory.md) and [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md)).
- [Measured] **Short client timeouts plus automatic retries against a long-prefill lane.** 300 s read timeout on a 317 s generation (task ~2× slower, overlap 4); 60 s timeout × 8 retries on a ~200K prefill that stalled 2 to 3 min per chunk [Historical diagnostic]; a 3-minute timeout at c=256 killed every request [Community-measured].
- [Measured] **Trusting a lane before cancellation is verified.** SGLang kept deleted requests decoding at 35 to 48 tok/s until a cancellation backport; vLLM saw aborts only after prefill [Historical diagnostic]. Kill the client process, not only a driver script, and gate deep prefills before admission.
- [Historical diagnostic] **Auxiliary calls on the same lane.** Background calls (titles, summaries) share slots with the foreground agent; uncapped ones kept decoding and made a stop look ineffective until they carried a token cap, a thinking control, streaming and cancellation.
- [Measured] **Two long sessions on one long-context lane.** Two ~275K sessions evicted each other (8.3 -> 319 s). Keep one long thread hot per lane, or measure residency first.
- [Measured] **Kit `skip` policy under agent load.** A 2K newcomer waited 130 s behind one essay; the kit reports 3 × 256K cold prefills serialized at 305 / 608 / 916 s TTFT on the pair and cold 150K prefills freezing co-running decodes on a DCP4 shape [Community-measured]. `off` is the other extreme: newcomers in ~1 s but the incumbent collapses 10 to 36× on TP2 [Community-measured].
- [Measured] **DeepSeek V4.1 SGLang "large" profile, then the "fast" profile.** 8 slots + 256 chunk + 2M pool fixed C8 TTFT but halved cold prefill; the 1,024-chunk replacement restored prefill and wedged near 200K. Neither was a one-variable change.
- [Measured] **Align-chunking correctness overlay kept by default.** Cost ~9 to 10% cold prefill at 95K on the triangle; dropped.
- [Measured] **Rejected levers on own lanes:** speculative attention mode "decode" (coding 62 -> 21 tok/s); MTP4 on single-node Flash Next (C4 -2.1%, C8 -6.8%); long-prefill threshold 0 on the DeepSeek V4 pair (headroom 4.0/4.7 GiB); hosted summary calls with reasoning off (endpoint refused).
- [Community-measured] **Large MNBT for "faster prefill".** 32,768 halved single-Spark generation (74.3 -> 34.9 tok/s); on TP4 GLM larger chunks did not prefill faster and hurt first-token latency (kit README quote of the four-Spark autoresearch).
- [Community-measured] **Concurrency sweeps without a correctness check when speculation is on.** 0/100 wrong serially vs 7/100 at c=8 (sglang #36548); gate it with [Quality and correctness gates](21-quality-and-correctness-gates.md) lever 4.
- [Community-measured] **Transferring short-prompt c=256 ladders to agent fleets.** The 695 to 1,042 tok/s aggregate figures used ~1.5K-token prompts; with 50K+ agent contexts, cached working set and prefill serialization bind first (Dendro Logic vs kit residency ladder).
- [Code-verified] **Using `--max-num-queued-tokens` as a TTFT valve for agent traffic.** It counts full prompt length, not the uncached remainder, so it rejects warm turns that need seconds of prefill.

## 8. Open questions

- **Per-turn split on the current triangle** (uncached new tokens vs cached prefix, fraction of fully cold turns, wall time split into queue / prefill / decode / tool). Settle by stamping per-request `cached_tokens` and timings in the metering proxy for a week of real traffic and joining them to agent-side tool timings.
- **Scheduler knobs never measured on GB10:** SGLang `lpm`/`hrrn` vs `fcfs`, `--enable-mixed-chunk`, `schedule_conservativeness`, the DFlash min-free-slots delayer, priority scheduling in either engine, and fair share 0.30 on its own. Settle with one-factor arms on the overlap fixture reporting newcomer TTFT and incumbent max gap.
- **A long cold newcomer (95K) arriving against 7 to 8 active decoders on the 8-slot triangle.** Modelled only: the own dossier gives > 55.7 s; arithmetic at the kit's ~268 tok/s contended rate gives ~5.9 min, but that rate is kit hardware at share 0.20 with one incumbent, and the lane runs 0.30 with 8 slots [Interpretation]. Settle with the overlap fixture scaled to 7 incumbents and a 95K newcomer.
- **Resident-session capacity on the triangle.** How many 64K / 128K / 256K histories stay warm (hit ≥ 0.99) as N rises. The boot figure bounds resident 128K histories at well below 3.94M/128K ≈ 30, because each sequence also pays the hybrid floor [Interpretation]. Settle with the residency fixture and the kit capacity log plus vLLM residency histograms enabled; the pair's ladder collapsed at 8 × 50K on an older stack.
- **Does lowering `max_model_len` change admitted concurrency on the triangle?** Refuted as a capacity lever on the pair and not shown on a DCP4 kit; untested at TP3. Settle with a one-variable boot at a lower ceiling (≥ 262K), reading the capacity log and running the residency fixture.
- **Which default branch vLLM picks on GB10 for `max_num_seqs` / MNBT when unset.** If NVML's memory query raises, the fallback is 2,048 / 256; a torch-memory platform class would give 8,192 / 1,024. Settle by booting a test instance with neither flag set and reading the resolved config.
- **Cause of the 524K and 900K exact-repeat misses at 7,168-token chunks.** Candidate mechanism: hybrid resume points exist only where the scheduler stored a state, and those move with the chunk budget and retention settings, as in the SGLang SWA case (sglang #36131) [Interpretation]. Settle with a 450K to 1M sweep in 50K steps reading hits and queried tokens per request at both chunk budgets.
- **Tool-schema churn on the own lanes.** Effect of adding, removing or reordering tools mid-session, and of non-deterministic JSON serialization, on hit rate. Settle with a prefix-drift sequence that appends real assistant, tool and result turns after a warm cache, then perturbs the tool list.
- **Does `mamba_partial_cache_hit` or denser state checkpoints remove the flat per-warm-turn trailing-page recompute (~6 s on the pair)?** The match unit is not the lever (the kit says leave `PREFIX_MATCH_UNIT` empty; the triangle already matches at 64 tokens). Settle with the warm-turn fixture before and after, reading uncached tokens per turn.
- **Per-lane TTFT budget and the client's effective timeouts and retries.** Configured values exist in files; the client's effective timeout and retry values are unverified, and an agent-shaped battery was designed but never run. Settle by reading the running client's resolved config and running the battery with lifecycle events logged.
- **Slot count on one Spark: 4 or 8+?** The vLLM blog recommends 4 for a 12B-active model; own lanes run 8 on 3B to 18B-active MoE with a stated per-stream cost. Settle per model with the one-factor slots arm; expect active parameters and output length to decide it [Interpretation].
- **FP8 KV under agent workloads.** The vLLM blog advises avoiding FP8 KV on Spark unless memory requires it; the own and kit GLM lanes run FP8 KV because the sparse-MLA path is FP8-only. No GB10 A/B on agent traffic exists. Settle with a same-image dtype A/B where BF16 KV is possible, on the warm-turn and correctness fixtures. See [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md).
- **Incumbent cost under fair scheduling: -30% own vs -13 to -17% kit, at the same share (0.20) and step (1,000 ms).** The arms differ in chunk budget (own 7,168/3,584) and hardware (the drafter runs on every rank on both, so placement does not explain it); the own 4,096-chunk rerun (incumbent 24.7 tok/s during the 30K newcomer, close to the kit's ~25.8) points at chunk budget [Interpretation]. Both sides are single runs. Settle with repeated overlap fixtures at 7,168 and 4,096 on one recipe.

Early-2026 community builds did see 0% hybrid hits before four fixes landed. Settle by reading per-request `cached_tokens` on a hybrid model at `v0.30.0` over a multi-turn agent session.

- **Agent-aware retention on GB10.** Papers report large gains from pinning KV across tool calls or workflow-aware eviction (Continuum: over 8× average job completion time on SWE-bench/BFCL/OpenHands traces; KVFlow up to 1.83× / 2.19×; Marconi up to 34.4× token hit rate for hybrids; Autellix 4 to 15× program throughput), all on datacenter GPUs or an Apple M4 Pro, none on GB10 [Community-measured].
