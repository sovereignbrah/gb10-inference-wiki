# Kernel authoring on SM121: when, in what, and the AI-assisted loop

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 128 GB unified LPDDR5X, 273 GB/s nominal memory bandwidth, used only as a denominator), node-1 / node-2 / node-3 on a direct-cabled ConnectX-7 RoCE triangle, driver 580.173.02. Own custom kernels are compiled with nvcc 13.0 (V13.0.88) for `sm_121a`. Since the 2026-09-21 clock-cap sweep every own kernel timing runs with the SM clock capped at 2,100 MHz (`-lgc 0,2100`); the cap is for heat and throttling, not speed, and whether a lane keeps it follows [Clocks, thermal, power](13-clocks-thermal-power.md) §5 lever 1. The second pass added, also fetched 2026-09-23: flash-attention `eed1971`, TileGym `5f4d7e6`, PyTorch `c6959ab`, the FlashInfer #3016 merge `17228c6f9e`, and the dgx-spark-playbooks cuTile tutorial `3410c65`. Community rows name the author by handle and the SKU they stated.


State of the evidence in one line: the fleet has authored or patched kernels three times, and each time the component win was larger than the end-to-end result or absent from it. The clean GB10 authoring wins in public are a launch-bound small-model decode megakernel and a prefill-kernel rewrite in a C/CUDA fork. The largest single community speedup came from shipping missing SM121 binaries, not from new code, and a recurring class of fixes turned on an existing fast kernel that a capability gate had silently excluded. No own Nsight Compute capture of any production kernel exists yet. [Interpretation, summarising §4 and §7]

## 1. What it is

A kernel is the small program the GPU runs for one step of a model: one matrix multiply, one attention pass, one mixture-of-experts step (routing tokens to expert sub-networks). Engines ship thousands of them, and almost all were written first for datacenter GPUs. The GB10's GPU, compute capability 12.1 (called SM121), is not a datacenter chip: it has the consumer-Blackwell instruction set (no datacenter tensor-memory instructions), a 99 KB cap on fast on-chip scratch per thread block (shared memory), a register file that halves occupancy at small overruns (the register cliff), and about 215-245 GB/s of measured memory bandwidth, depending on the probe ([SM121 hardware facts](17-sm121-hardware-facts.md) §3), that the CPU shares. So on a GB10 some kernels are missing, some run a slow fallback, and some are tuned for other shapes. Writing or patching a kernel is the most expensive lever on this wiki, and it is rarely the first one to pull. In 2026 most GB10 speedups came from turning on a fast path that a capability check excluded, from shipping a binary actually compiled for SM121, or from picking a better existing kernel. When a profile does show a kernel that is far from its hardware limit and matters to the whole request, several toolchains can target SM121 (CUDA C++, CUTLASS and its Python CuTe DSL, Triton, TileLang, and less mature ones), each with gaps, and each engine packages kernels its own way. AI coding agents now write kernels too. Public benchmarks show that they game the timer unless the evaluation is guarded, and the fleet's own agent-written kernel won in isolation and lost end to end. One agent-written SM121 kernel has been merged into an engine, on a model branch, and it got there as a correctness fix with a narrow declared contract rather than as a speedup. This page says when to author, which toolchain works on SM121, how each engine packages a kernel, how to prove one correct, how to run an AI-assisted loop without being fooled, and a design for an isolated kernel lab. See also [Profiling protocol](14-profiling-protocol.md), [SM121 hardware facts](17-sm121-hardware-facts.md), [Engine dispatch maps](16-engine-dispatch-maps.md), [Decode optimization](05-decode-optimization.md), [Prefill optimization](04-prefill-optimization.md), [GEMM backends and quant formats](09-gemm-backends-and-quant-formats.md) and [Quality and correctness gates](21-quality-and-correctness-gates.md).

## 2. How each engine does it

Each engine has two separate questions: how a kernel gets into the running process (build, registration, JIT), and which SM121 binary the build actually produces. The engines disagree on the second. Tools that JIT for the local device choose `sm_121a`, while wheel builders choose the family target `12.0f` or a baseline target. [Code-verified, §3 has the target semantics] TensorRT-LLM is not a fleet engine. It appears on this page as the home of NVIDIA's Nsight Compute sections guide used in §6 [Code-verified], and for two status facts. First, a CUTLASS 4.4.x stage-count carve-out bug made most MoE autotuner tactics fail on GB10 in TensorRT-LLM 1.3.0rc10; NVIDIA's CUTLASS maintainer says "a fix for some carve-out calculations in SM120 kernels" shipped in CUTLASS 4.4.2, and TensorRT-LLM bumped to it (cutlass #3144, closed 2026-05-11) [Community-measured + vendor maintainer statement]. Second, its `fmha_v2` HMMA prefill kernels are reachable on SM12x through FlashInfer only as an opt-in path (vLLM section below) [Code-verified].

### vLLM

- **Build and target.** C++/CUDA ops compile into the `_C` and `_moe_C` extensions through CMake with per-kernel arch lists. `CUDA_SUPPORTED_ARCHS` depends on the toolkit (`CMakeLists.txt:116-131` @ 34b0690): CUDA ≥ 13.4 gives `...;10.0;10.7;11.0;12.0`, CUDA 13.0-13.3 gives `...;10.0;11.0;12.0`, and only CUDA 12.8-12.9 gives `...;12.0;12.1`. SM12x kernels are declared as the family target `12.0f` (for example Marlin `"8.0+PTX;12.0f"`, scaled-mm `"12.0f"`, FP4 SM120 `"12.0f"`). On CUDA 13 toolkits, vLLM's own kernels build as family `12.0f` even when `TORCH_CUDA_ARCH_LIST=12.1a`, because the top-level supported-arch filter (`CMakeLists.txt:231-232`) strips 12.1 before any per-kernel intersection runs; the `12.0f` → `12.1a` family fallback in `cmake/utils.cmake` is reachable only under CUDA 12.8-12.9. [Code-verified at 34b0690; the verbatim `cuda_archs_loose_intersection` was re-run under `cmake -P` with the same result: with the CUDA 13.0 list, `12.1a`, `12.1`, `12.1f` and `12.0;12.1` all reduce to `12.0`, then per-kernel `12.0f`] Defaults on CC 12.1: `12.0f` cubins (they run on 12.0 and 12.1). Verify any "native `sm_121a` vLLM" claim with `cuobjdump --list-elf`, not with the flag. The effect is specific to vLLM's own CMake build of `_C`/`_moe_C`: own out-of-tree builds do land native `sm_121a` (§4).
- **Published images.** The published vLLM v0.27.1 aarch64 image carries zero `sm_121` cubins in `_C` and `_moe_C`. After patching the supported list, a community build showed 34 `sm_121` cubins in `_C_stable_libtorch.abi3.so` and 7 in `_moe_C_stable_libtorch.abi3.so`. A two-arch wheel is 518 MB and fails vLLM's 500 MB wheel-size gate (`RUN_WHEEL_CHECK=false`). A reviewer called the list patch "the load-bearing change". The PR that carries it (#38484, head `1d95dca`) is open with conflicts. [Community-measured, gperez2000 and ubehera in vLLM #38484, 2026-05-28 and 2026-08-13]
- **Silent capability gates.** vLLM's GDN prefill backend selection set `supports_flashinfer` for SM90 and the SM10x family only, so SM121 "silently fell through to the Triton/FLA fallback" (1,216 of 1,216 logged backend announcements on one GB10) until vLLM #55715 (merged 2026-09-08, `f6326f53b`); §4 has the measured gain. The recipe's rule is "verify from the log rather than from the version". [Community-measured, jschmied/qwen38-flash-next-gb10 REPRODUCE.md @ 6813ea7] A second gate class: an `enable_sm120_only` guard (`__CUDA_ARCH__ == 1200`, `trap` otherwise) crashed `12.1f` cubins until #33517 (merged 2026-02-07, `bc32444`) added `enable_sm120_family` (`>= 1200 && < 1300`) for blockwise FP8; a March community tree still found two files on the `_only` guard (saifgithub/vllm-gb10-sm121 @ 7e5cec5). [Code-verified at commit + Community-measured]
- **DeepGEMM on GB10.** `VLLM_USE_DEEP_GEMM=0` is the working GB10 workaround for one blockwise-FP8 checkpoint whose load crashed with `unspecified launch failure` (vLLM #54125, open). The crash was an attribute-name bug (`w8a8_block_fp8_linear` against `fp8_linear`) that skipped DeepGEMM weight post-processing, so raw float32 scales reached the E8M0 kernel. It is not SM121-specific, and it is already fixed on main by `f8e0602713`. On 2026-08-28 the reporter retracted the original framing that the capability-family gate was too coarse. The same thread carries a separate, real GB10 finding: a DeepGEMM block-FP8 sweep against a bf16 dequant reference corrupts silently at `K=2560` (rel_max 0.5-0.8, 1-2.5% of elements, 4 seeds) for `N ≤ 512` at every M probed and for `N = 640-1024` when `17 ≤ M ≤ 128`; every other K probed (1,024-10,240) is clean, and CUTLASS on identical inputs stays at rel_max ≤ 0.047. [Community-measured, vLLM #54125 comments 2026-08-28] DeepGEMM `sm120` kernels do run on GB10 elsewhere: about 61.9% of GPU time in a public 2-node DeepSeek-V4-Flash profile (§4) and a TF32 kernel in the own production prefill profile (§4). [Community-measured; Measured]
- **FlashInfer `fmha_v2` prefill, opt-in.** FlashInfer #3016 (merged 2026-07-17, `17228c6f9e`) makes TensorRT-LLM's `fmha_v2` HMMA prefill kernels selectable on SM12x only when the caller passes `use_fp16_qk_reduction=True`, and only for MHA with equal Q/KV segments, head dims 64/128/256, matching dtypes, NHD layout, no window or soft-cap, and S ≥ 256. The author's closing comment: "these guards make fmha_v2 effectively opt-in … a default prefill call stays on FA2". [Code-verified at `17228c6f9e`, `flashinfer/prefill.py`] Whether vLLM ever passes that flag on GB10 was not checked (§8).
- **Triton ptxas variable.** Open PR #31740 (since January, `mergeable_state: dirty`) sets `TRITON_PTXAS_PATH` in `vllm/triton_utils/importing.py`. That variable is inert for SM121 on any Triton that has the `ptxas-blackwell` split (§3). [Code-verified]
- **Registration.** An out-of-tree package registers an entry point in the group `vllm.general_plugins`, which vLLM loads "in all processes (process0, engine core process and worker processes)", filtered by `VLLM_PLUGINS` (`vllm/plugins/__init__.py:16-18,36-90`; `envs.py:1157`). A plugin replaces an in-tree layer with `CustomOp.register_oot` (`model_executor/custom_op.py:335`) or `PluggableLayer.register_oot` (`:83`); the class swap happens in `__new__` (`:106-125`). Python-level ops are registered with `direct_register_custom_op`, which dispatches to `current_platform.dispatch_key` because "`torch.library.custom_op` can have significant overhead" (`utils/torch_utils.py:1048-1078`). [Code-verified]
- **The default that silently measures the wrong kernel.** A registered `CustomOp` runs only if `enabled()` returns true: `(default_on() or "+name" in custom_ops) and "-name" not in custom_ops`, and `default_on()` is "On by default if 'all', off by default if 'none'. When PyTorch Inductor is used, 'none' is the default value" (`custom_op.py:269-307`). [Code-verified] Under the Inductor compile path, a new custom kernel falls back to its native torch implementation unless the launch lists `+OpName` in `CompilationConfig.custom_ops`. An A/B that forgets this measures the fallback. [Interpretation]
- **Tuning as data.** Triton fused-MoE tuned configs for `device_name=NVIDIA_GB10` exist for two FP8 W8A8 shapes (E=256 and E=512, N=512, block [128,128]); `VLLM_TUNED_CONFIG_FOLDER` (`envs.py:1909`) points vLLM at a user folder. Helion kernels read per-GPU files `{kernel}/{platform}.json`; at the pin only `nvidia_h100`, `nvidia_h200` and `nvidia_b200` exist, and a missing platform raises `KeyError` ("platform ... not found") (`kernels/helion/config_manager.py:63-91`). [Code-verified]
- **Determinism mode.** `VLLM_BATCH_INVARIANT=1` (`envs.py:628`) on a non-SM80 CUDA device sets `CUBLAS_WORKSPACE_CONFIG=:16:8` and `CUBLASLT_WORKSPACE_SIZE=1` to disable split-K, replaces softmax, log_softmax, mean and bmm with invariant kernels, disables TF32 and reduced-precision reductions, and pins NCCL to one channel, the Simple protocol and Tree all-reduce. When `get_max_shared_memory_bytes() <= 106496` it picks smaller Triton tiles "to avoid triton OutOfResources" (`model_executor/determinism/batch_invariant.py:1052-1180`, tile rule at `:1081-1091`). [Code-verified] SM121 takes the non-SM80 branch, so the mode covers vLLM's stock GEMMs and reductions, not community custom kernels. [Interpretation]
- **Known failure on GB10.** A stock `cu130-nightly` image (v0.17.0rc1, built 2026-03-06) shipped with no SM12x cubins. Rebuilding only `_C.abi3.so` and `_moe_C.abi3.so` for SM121 from the same commit and copying those two files into the pristine image took one Qwen3.5-35B-A3B FP8 request from 13.3 to 48.6 tok/s. A full `pip install .` rebuild changed the `transformers` version and broke model loading. [Community-measured, troy.e.davis, NVIDIA forum topic 365083, fetched 2026-09-23]
- **EXL3.** ExLlamaV3 is not in upstream vLLM. It reaches vLLM only through community overlays. [Code-verified negative, wave-1]
- **Own.** The fleet's router-GEMM backport (vLLM #54048) removed a bf16→fp32 copy that SM121 paid only because a specialisation was gated to Hopper and SM100. It was applied in a composite image and never measured in isolation. [Historical diagnostic]

### SGLang

- **Two kernel tracks.** JIT kernels (`python/sglang/kernels/jit`) compile at first use through tvm-ffi and are cached by content address under `$SGLANG_JIT_CACHE_DIR/<target>/<module>/build-<build_key>/deps-<deps_key>/` (default `~/.cache/sglang/jit`). The key covers flags, target and the transitive header closure, and a published leaf is never modified (`kernels/jit/utils/compile/cache.py:1-40,302`). AOT kernels (`python/sglang/kernels/aot`, published as the `sglang-kernel` wheel, pinned `sglang-kernel==0.4.7` in `python/pyproject.toml`) are for kernels that depend on CUTLASS or another large C++ project. [Code-verified @ 2909f84]
- **Target on GB10.** The JIT path emits `-gencode=arch=compute_121a,code=sm_121a` (`toolchain.py:134-136`). Its arch code maps "12.x (x>0) -> 'a' (SM120/SM121 need separate cubins to avoid cudaErrorIllegalInstruction)" and warns that plain `sm_120` is "never a valid fallback: without an a/f target CUTLASS's SM120 atoms lose LDSM/STSM and compile down to trap stubs (verified via SASS), which asserts at launch instead of failing the build" (`kernels/jit/utils/arch.py:72-92`). [Code-verified] The AOT wheel adds `compute_121a,code=sm_121a` only when CUDA ≥ 13.0 and the build host is aarch64, and its bundled InfLLM-v2 flash extension is built for `sm_80`, `sm_90` and `sm_120a` only (`kernels/aot/CMakeLists.txt:209-236,501-508`). [Code-verified] So InfLLM-v2 has no image that loads on GB10. Whether the PyPI 0.4.7 aarch64 wheel carries `sm_121a` depends on its CUDA version, which was not inspected. [Interpretation]
- **Authoring guidance in-tree.** SGLang ships an `add-jit-kernel` agent skill that requires tests and a benchmark. It advises: "For memory-bound kernels, keep to roughly 64 registers per thread so occupancy does not become the limit; prefer recomputing a value over letting it spill". It logs registers, spills and shared memory with `SGLANG_JIT_LOG_RESOURCE_USAGE=1 SGLANG_JIT_FORCE_RECOMPILE=1`, noting that a cache hit has no compiler output and that `-Xptxas -v` alone does nothing (`.claude/skills/add-jit-kernel/SKILL.md:18-24,38`). The developer guide says to prefer `cache_once` over `functools.lru_cache`, which "is not compatible with `torch.compile`" (`docs/docs/developer_guide/development_jit_kernel_guide.mdx:44-45`). SGLang depends on Hugging Face `kernels>=0.14.1,<0.15` (`python/pyproject.toml:47`). [Code-verified]
- **Published-wheel history.** Early in 2026 the published `sgl-kernel` 0.4.3 had `sm_90`/`sm_100` directories only, and `import sgl_kernel` failed on GB10. A community `sm_121a`-only wheel disables FA3 and FlashMLA to cut build time and peak memory (ubehera/sglang-spark @ 21fce8d). THUDM/slime #1835 (merged 2026-04-21, `f44af13d0c`) added `SGL_KERNEL_GB10_ONLY` (gencode `sm_120a` + `sm_121a`) after a 7-arch CUTLASS build ran out of memory, and moved to a CUDA 13.2 base because CUDA 12.9 ptxas lacked `sm_121a`. [Community-measured] The in-tree `sm_121a` gencode above is the current state at `2909f84`.
- **Dispatch changes that did and did not land.** A one-line SM121 dispatch to the SM120 CUTLASS FP4 grouped GEMM (#17421; ~37 tok/s single and ~110 tok/s at 4 concurrent on Qwen3-30B-A3B NVFP4, per its author) was closed unmerged on 2026-01-31 with no maintainer comment. [Community-measured] SGLang #36845 (merged 2026-08-30 into the `qwen4-main-squashed` model branch, not `main`; merge `78c5024e9d`) replaced a FlashInfer TensorRT-LLM paged decode path that "silently corrupts long-context decode" on SM121 (120K/190K/210K contexts returned 32/32 token id 0 with HTTP 200) with one Triton kernel. That kernel was produced by a Kernel Design Agent run (KDA-1.5, task pinned at `414ce456`, winning submission `b4181149c8884ddb`, source SHA-256 recorded) inside the Humanize implementation-and-review workflow, then approved by a maintainer. The PR notes that disabling FlashInfer autotune "only makes the incorrect SM121 kernel start; it does not fix its numerics." Its validation battery and numbers are in §4 and §6; the route is covered on [Attention backends on SM121](06-attention-backends-sm121.md). [Community-measured, sglang #36845 body, commits and comments]
- **A contested community fork.** One GB10 SGLang tree routes all NVFP4 to Marlin FP4 because "All CUTLASS FP4 GEMM operations produce corrupt output (zeros/NaN) on SM121", auto-selects Triton attention for MLA ("FlashInfer MLA is 30x slower"), and uses the sgl-kernel CUTLASS `fp8_scaled_mm` over `torch._scaled_mm`, which it says dispatches to `sm89_xmma` (scottgl9/sglang-spark-gb10-optimizations @ f77232a). [Community-measured; the FP4 claim is contested in §3] Upstream SGLang itself ships `.claude/rules` in-tree, and that fork inherited them. [Code-verified]
- **Cold JIT under a resident model.** A community SGLang NVFP4 image found that first use of dense FP4 GEMMs JIT-compiles about 18 CUTLASS kernels, and with a 23 GB model resident plus autotune the kernel OOM-killer took the compiler (`ninja` exit 137). Its answers are a pre-warmed cache in the image and, on bare metal, `taskset -c 0-7 ninja -j2` with nothing else resident. [Community-measured, r0b0tlab/ornith-15-35b-nvfp4-w4a16-sm121-sglang @ 6d0a25d]
- **Own.** The Qwen 3.8 Flash Next TP2 lane persists SGLang compile and autotune caches (own changelog, 2026-08-27). After a widened datacenter attention guard corrupted outputs on SM121 (§4), it adopted a community SM121-safe packed-varlen Triton fallback. The patch author's README says it "reads `cu_seqlens` on-device so CUDA-graph replay stays valid". The first production boot then failed because a legacy BF16-only SM121 resolver in the base image pre-empted the new branch, and the Dockerfile now asserts and removes that block. [Measured; README quote Community-measured] The fallback the fleet carries is the **first** revision of SGLang #36845 (`3681c4e03f`, 2026-08-28, "add SM121 Triton varlen fallback"). It is not the agent-written kernel that replaced it on 2026-08-29 and was merged. [Code-verified, PR commit list; Measured, own changelog 2026-08-28]

### llama.cpp and forks

- **Mainline.** The CUDA CMake appends `121a-real` when `CUDAToolkit_VERSION >= 12.9` and the build is not native (`ggml/src/ggml-cuda/CMakeLists.txt`, lines 1-60 excerpt @ 6e60f35; its comment explains that `120a-real` and `121a-real` work with any CMake, while `120f-virtual` needs CMake ≥ 3.31.8 or ≥ 4.0.2). [Code-verified] The correctness oracle is `test-backend-ops`. It runs each op graph on the target backend and on the CPU backend, compares with NMSE (default threshold `1e-7`, raised per op for quantized types), and places pre- and post-graph sentinel tensors to catch out-of-bounds writes (`tests/test-backend-ops.cpp:298,1206-1233,1370-1395`). [Code-verified] No own mainline GB10 measurement exists.
- **Mainline tuning for DGX Spark was kernel selection, not new kernels.** #19142 (merged 2026-01-28, `2eee6c866c`) changed only which flash-attention kernel runs at which depth on DGX Spark. The maintainer's explanation: master used the Blackwell path only for contexts ≥ 64K and sent shorter depths to a worse kernel. §4 has the per-depth numbers (2.07× at one depth, 1.04-1.09× at shallower ones). [Community-measured, ggerganov and the PR author, llama.cpp #19142] The follow-up pass found no new ds4, Entrpi or Anemll material.
- **ds4 (antirez).** The `Makefile` maps `CUDA_ARCH=sm_121` to `-gencode arch=compute_121a,code=sm_121a -DDS4_CUDA_HAVE_MXF4=1` (`Makefile:40-50` @ 0aaea5a). `CONTRIBUTING.md` requires both tracks for backend changes (`:9-66,107-131`). The correctness track covers `--logprob-vectors` against official DeepSeek V4 Flash continuations, long-context fact recall, tool-call quality, isolated Metal kernel numeric checks, and `make cuda-regression` for CUDA changes. The speed track requires "at least one before/after CSV … prefill_tps and gen_tps" on the same machine, backend, model, sweep, power/thermal state and background load. It states "The only acceptable regression speed is when an important correctness bug is fixed". [Code-verified] The README declares "strong assistance from AI coding agents" (`README.md:53`). [Code-verified]
- **Entrpi fork.** The fork's roofline computes ~11 GB of weights touched per decode token, so single-stream decode is capped near 225 / 11 ≈ 20.5 tok/s. It measures 18-20 tok/s ("~90%+ of the wall"). Decode kernel work (per-layer CUDA-graph capture, head-group flash-decode for dense and indexed attention, aligned-quant dispatch tiers) brought plain decode that close to the wall. Past that point the fork turned to speculation, batching and prefill kernels: "D2R" dequant-into-MMA-fragment MoE GEMMs, tensor-core attention tiles and an L2-aware expert-major CTA schedule (`Entrpi/ds4-on-spark` README lines 419-471, 601-623 @ 99fb7b1). [Community-measured] Its README names the models used to develop it: "GPT 5.5, 5.6, Claude Fable" (`Entrpi/ds4` README:50 @ b0a147a). [Code-verified] Own: the fork's `make` target emits `compute_121a,code=sm_121a` (§4). [Measured]
- **Anemll.** No SM121 kernel path was found. `Anemll/ds4-ssd` (@ 72aef7e, main-alpha) is "Metal-first": "CUDA sources are inherited from upstream DS4 and kept in tree, but the alpha validation focus is Apple Silicon SSD streaming". Anemll's GB10 artefact that bears on this topic is an agent rule set (`Anemll/dgx-spark-agent-rules` AGENTS.md @ ae8857e). It says to build for `121-real`, to "Use Nsight Systems to determine whether time is spent in CUDA kernels, NCCL proxy/staging, synchronization, page faults, or CPU scheduling. Use Nsight Compute only after a kernel has been identified as the actual hotspot", and to accept a change only if "the new configuration beats or intentionally matches the preserved baseline on the user-relevant metric" (§2, §6-§7). [Code-verified]

### ExLlamaV3 in vLLM

- **Upstream extension.** If no precompiled `exllamav3_ext` is importable, `ext.py` compiles every `.cu` file in the extension directory with `torch.utils.cpp_extension.load` and `-lineinfo -O3 --use_fast_math`. `--ptxas-options=-v` is added only if the module-level `verbose` flag, hard-coded `False`, is flipped (`ext.py:11,20-30,91-122,146-153` @ 6b84a21). When `TORCH_CUDA_ARCH_LIST` is unset, `util/arch_list.py` sets it to the device capability clamped to the highest SM in `torch.cuda.get_arch_list()`, plus `+PTX`. [Code-verified] Under a cu130 torch whose list tops out at `sm_120`, a GB10 JIT build therefore emits `sm_120` SASS plus PTX, not `sm_121`. That is fine for the extension's `mma.sync`, `cp.async` and `ldmatrix`-class instructions, but it means a first-use compile inside the serving container unless a prebuilt extension is present. [Interpretation] Registers and the 99 KB shared-memory cap bound these kernels, not the instruction set. [Code-verified, wave-1]
- **Why recompiling on a serving node is dangerous.** The upstream Dockerfile compiles ExLlamaV3 and the fat-expert extension with `MAX_JOBS=8`, and a compile of that size on a unified-memory node that is already serving competes for the host-memory floor. The fleet treats it as a UVM-livelock risk (UVM: unified virtual memory). [Measured practice; the livelock itself is documented only as community field notes from a 4-node kit, wave-1 topic 17]
- **Fleet packaging.** Layered images keep `exllamav3_ext` and the fat-expert extension byte-identical to the base image. New `.so` files are built offline in a network-less, GPU-less container capped at 2 CPUs and 8 GB, on the serving image digest. Cooperative decode kernels ship as a separate `.so` with a manifest and a dispatch policy bound to its hash (2026-09-15 upgrade provenance; 2026-09-20 "GLM 5.3 Flash V3 — retained startup/prefill improvements, V2 decoder" build record). [Measured]
- **Community GB10 packaging facts.** ExLlamaV3's JIT build needs aarch64 guards (AVX2/AVX-512 targets, `__builtin_ia32_pause`) before it compiles on GB10; after them, a 164-object JIT build took about 1 min 45 s (vcruz305/exllamav3 #1). The vLLM EXL3 plugin imports the compiled `exllamav3_ext`, and a cold `import exllamav3_ext` before `import torch` fails with `libc10.so` not found, so the install check must be `import torch, exllamav3_ext`. A community fork aliases a speculative drafter from an `mmap` of safetensors under ATS addressing (`EXL3_ATS_MMAP=1`, `EXL3_ATS_COPY='^(?!mtp\.)'`); without aliasing, a DeepSeek-V4.1-Flash 1.59 bpw load reached 114.03 GiB and left 1.52 GiB. A Qwen3.8-Flash-Next EXL3 3.05 bpw pack loads in 47 s natively against 8-10 min through vLLM (compile and graph capture). [Community-measured, vcruz305 recipes @ 677e30b, e0ebee8, 61a1f8c]
- **A component win shipped default-off.** A row-batched ExLlamaV3 mixer kernel cut mixer time 9.1 → 7.7 ms per round (97 sites, R=6) with fp32-reference parity unchanged (max rel 4.3e-4). End to end it was "within run-to-run noise", and the different accumulation order "shifts greedy trajectories/MTP acceptance", so it shipped default-off. It was merged into the author's own fork (vcruz305/exllamav3 #1, merged 2026-09-17, `4d78f0a481`). [Community-measured]
- **E3 grouped fat-expert prefill kernel (community).** MiaAI-Lab's two-node kit replaced about 14 launches per fat expert with 3 per MoE layer (gather; gate/up 64×128 tiles with a 4-stage `cp.async` pipeline; down projection scattered with 16 B `atomicAdd(float4)`). It is built without `--use_fast_math`. [Historical diagnostic, kit notes retained in own records] Its measured effect is in §4. Because the down projection accumulates with atomics, E3 prefill is not bitwise run-to-run deterministic by construction. Its gate must be a tolerance, not a bitwise repeat. [Interpretation]
- **Correctness gates in fleet use.** Frozen tolerances, real-weight parity, changed-data graph replay bitwise equal to eager, zero per-call allocations, and candidate-filtered compute-sanitizer runs (§4, §6). Still missing: counter-based classification and a run-to-run determinism record. [Measured / Interpretation]

## 3. What is different on GB10 / SM121

**Target strings**
- [Code-verified] `a` cubins run only on the exact compute capability. `f` cubins run on every member of the family: `compute_120f` covers 12.0 and 12.1, and `compute_121f` covers only 12.1. `sm_121a` exists from CUDA 12.9 (PTX ISA 8.8). An `sm_120a` cubin does not load on GB10. (NVIDIA family-specific-features blog; Programming Guide; PTX ISA 9.4; [SM121 hardware facts](17-sm121-hardware-facts.md))
- [Code-verified] The one GEMM-relevant feature that needs `sm_121a` rather than `12.0f` is sparse `mma.sp` with `.kind::mxf4nvf4` / `.kind::mxf4`. PTX 9.4 lists a few other `a`-only features (`cvt .s2f6x2`, multimem FP8 / `.acc::f16`, `fabric.try_pullred`) that inference kernels are not known to use. Dense FP4 `cvt` and dense block-scaled MMA are reachable through `sm_120f` or `sm_121a`. (PTX ISA 9.4; wave-1 topic 17 correction)
- [Code-verified] NVIDIA's DGX Spark porting guide tells CMake users `-DCMAKE_CUDA_ARCHITECTURES="121-real"` ("For DGX Spark, this is 121-real"), a baseline target with neither `a` nor `f`. (DGX Spark Porting Guide, compilation page, fetched 2026-09-23) [Community-measured] One GB10 builder hit `ptxas error: Instruction 'cvt with .e2m1x2' not supported on .target 'sm_121'` with `TORCH_CUDA_ARCH_LIST="12.1"` (forum 365083). [Interpretation] A baseline target is enough for bf16, fp16 and fp8 `mma.sync` kernels. FP4 and block-scaled kernels need `sm_121a` or `12.0f`.
- [Code-verified] Defaults by tool: Triton (`sm_arch_from_capability` appends `a` for every CC ≥ 90, `third_party/nvidia/backend/compiler.py:110-113`), FlashInfer (`compilation_context.py:81-111`, normalised to `12.1a`), SGLang JIT, TileLang (`contrib/nvcc.py:523-531`) and ds4 all choose `sm_121a`. vLLM wheels choose `12.0f`. Hugging Face kernel-builder's CUDA-13 default list is `...;12.0;12.1+PTX` (`kernel-builder/src/pyproject/templates/torch/preamble.cmake:99-110` @ f86e642). PyTorch treats 12.1 as binary-compatible with 12.0 and ships no 12.1 cubins. [Code-verified, wave-1] A PyTorch reviewer asked that an `sm_121` wheel PR be "compatible with 12.0", and the PR's author then closed it (pytorch #178891, closed 2026-04-06). [Community-measured] One GB10 README says the cu130 PyTorch wheel's BF16 tensor-core paths error out (`CUBLAS_STATUS_INVALID_VALUE`) and recommends NGC PyTorch, while the same README calls sm_120 and sm_121 binary compatible (Logos-Flux/optimized-CUDA-GB10 @ 49732f4). [Community-measured, contested] The fleet and many community stacks run pip cu130 torch on GB10, so the claim is at most version-specific. [Interpretation]
- [Community-measured] **Does `sm_121a` versus `12.0f` matter? Two answers.** Correctness, one kernel: CUTLASS example 87a (FP8 blockwise) built for `120a` passes `can_implement()` on GB10 and fails at launch (`kErrorInternal`); built for `121a` it runs at 0.51184 ms, 167,825 GFLOPS (vLLM #38484, 2026-05-22). That is consistent with "an `a` cubin for 12.0 does not load on 12.1", and it is not evidence against `12.0f`; whether `120f` also covers 87a is unanswered (§8). Speed, one workload: Qwen3.5-122B-A10B-NVFP4 with the `flashinfer_cutlass` MoE and byte-identical flags read 16.4 tok/s on the published image against 16.3 tok/s with native `sm_121` cubins, with identical KV capacity, prefix-cache warm-up and an 8-point correctness suite. Its MoE GEMMs come from FlashInfer, which JIT-compiles for the local device either way (vLLM #38484, 2026-08-13).
- [Community-measured] **FlashInfer's JIT cache ships family cubins.** `flashinfer-jit-cache` 0.6.17 and 0.6.18.post1 contain no filenames with `121`, and `fp4_gemm_cutlass_sm120.so` is 17 `sm_120` ELF images in both. After a cut-over, the `…/0.6.18.post1/121a/` JIT cache held 0 modules and a full start log had no `ninja`, `nvcc` or `Compiling` lines, because `compute_120f` covers 12.0 and 12.1 and `sm_121a` is needed only for sparse `mma.sp .kind::mxf4nvf4`. Autotune caches are keyed by version, so an upgrade discards them. (jschmied/qwen38-flash-next-gb10 REPRODUCE.md @ 6813ea7) [Interpretation] The ~85-kernel cold JIT reported earlier for a different version and model path (vLLM #48031) and this zero-compile start can both be true.
- [Community-measured, contested] **Microscaling on base targets.** Two more GB10 builders repeat "`cvt .e2m1x2` exists on sm_120 but not sm_121" and compile vLLM as 12.0 (scottski78/vllm-turboquant-gb10 @ a7e1b56; the Avarok dgx-vllm README's software E2M1 conversion). The better-evidenced reading is the one above: base `sm_121` drops the `a`/`f` features. Avarok issue #10 shows the ptxas error on target `sm_121` from a `compute_121` PTX, and `121a` builds of FP8 CUTLASS run. [Interpretation] Whether MXFP4 (E8M0-scaled) weights can drive GB10 tensor cores directly is contested too: one README says they cannot (VincentKaufmann/fp4-cuda-kernel @ e60a682), while CuTe DSL admits `MmaMXF4Op` on `sm_121a`/`sm_121f` and another README claims native support. No source measured a GB10 MXFP4 tensor-core GEMM with a correctness check (§8).

**Resource ceilings (design constraints)**
- [Code-verified] CC 12.x limits: 64K 32-bit registers per SM, 255 per thread; 48 resident warps and 1,536 threads per SM; 1,024 threads per block; 99 KB shared memory per block (101,376 B opt-in) and 100 KB per SM. The resident-blocks-per-SM figure is 24 in the Programming Guide and 32 in the Tuning Guide (unresolved, §8). (CUDA Programming Guide compute-capability tables; [SM121 hardware facts](17-sm121-hardware-facts.md))
- [Measured] [Interpretation] The register cliff is concrete. The fleet's cooperative decode MoE kernel builds at 63 registers, 0 spill bytes and 512 threads. Registers are allocated in steps of 8 per thread, so 63 rounds to 64, and 512 × 64 = 32,768 is exactly half the register file: two blocks fit per SM. At 65 registers the allocation rounds to 72, 512 × 72 = 36,864, and residency halves to one block, while the build log still reads "0 spills". The kernel declares only `__launch_bounds__(512)`, with no minimum-blocks argument, so nothing stops that regression. (2026-09-16 "GLM 5.3 Flash TP3 combined-runtime qualification")
- [Community-measured] The 99 KB shared-memory ceiling is the most common thing that breaks ported kernels on SM12x. Triton's matmul tests on an RTX PRO 6000 (sm_120) still fail on "the 99 KB shared memory limit (`OutOfResources`)" after other fixes (Triton PR #11862, alepot55, merged 2026-09-21). A TileLang Mamba-3 kernel asked for 168,128 B against 101,376 B on sm_120 (TileLang #2201). The Megakernels GB10 port had to cut its page table from 13 to 5 pages of 16 KB (PR #11). vLLM's batch-invariant mode picks smaller Triton tiles at ≤ 106,496 B (§2).
- [Community-measured] An LLM-propagated "fact" that SM120 has 228 KB of shared memory and SM121 99 KB reached a pending FlashInfer PR before it was corrected (forum 365083 replies #9-#10). Both parts are 99 KB per block. [Code-verified, [SM121 hardware facts](17-sm121-hardware-facts.md)] The same error opened a CUTLASS issue, and NVIDIA's maintainer answered: "SM120 (RTX 6000, 5090, etc.) and SM121 (Spark) only support 99 KiB smem. B200 is SM100, which has 228 KiB" (cutlass #3144, 2026-04-05). The research synthesis behind this page's second pass repeated the 228 KB error as well. [Community-measured + vendor maintainer statement]
- [Community-measured + vendor maintainer statement] **Compile-time stage counts can overshoot the cap.** In cutlass #3144, CUTLASS's `StageCountAutoCarveout` picked a stage count for a 128×256×64B FP4 grouped tile that asked for 102,400 B against the 101,376 B opt-in, 1 KiB over. In TensorRT-LLM 1.3.0rc10 on GB10, 13 of 16 MoE autotuner tactics failed. The maintainer says a fix for some SM120 carve-out calculations shipped in CUTLASS 4.4.2, and a community user confirmed a build from main resolved the 102,400 B failure. The reporter's tok/s figures name no model or workload, so they are not used here.
- [Community-measured] **Registers and shared memory as design limits in a measured GB10 kernel.** In the CuTe DSL flash-attention work (cutlass PR #3030), N=128 KV tiles ran 30-40% slower "from register-pressure spill" and `kv_stages=3` was "a wash" in FP8-TMA experiments. An early shared-memory estimate forced `kv_stages=1` at D=128; after the `can_implement` arithmetic was fixed, `kv_stages=2` at D=128 BF16 fits in 97.0 of 99 KB (thread of 2026-02-24 and 2026-04-27). [Code-verified: vendor doc, a design statement, not a measurement] cuDNN's experimental SM120/SM121 SDPA backward runs 384 threads: 8 math warps that can take up to 240 registers, a TMA producer warp at 24, and 3 "register donor" warps at 24, redistributed with `setmaxregister`. It drops from 2 Q stages to 1 at D=256 when shared memory does not fit (cuDNN frontend "SDPA backward (SM120)", fetched 2026-09-23).

**Memory bandwidth ceiling (the roofline denominator)**
- [Community-measured] Idle GPU read ceilings on GB10: 231-234 GB/s for a saturating `float4` read-sum (8 GiB, `<<<2048,256>>>`, CUDA 13.0, driver 580.173.02; vincenzopalazzo, antirez/ds4 #773); 227 GB/s read-only and 215 GB/s copy (Entrpi `bench/bw_bench.cu`, ds4-on-spark README "Roofline" @ 99fb7b1); 236 GB/s from a microbenchmark read (Megakernels PR #11). An nvfp4bench triad read 205 GB/s on an ASUS GX10 with a 580-era driver and 200 GB/s on 610.43.02, buffer size not stated ([SM121 hardware facts](17-sm121-hardware-facts.md)). The 273 GB/s figure is nominal only. No own on-node ceiling has been measured (§8).
- [Interpretation] The own implied-bandwidth curve from dispatch logs (172-351 GB/s) exceeds nominal at 1-2 rows, and the frontier dossier that derived it withdrew it. Use the community ceiling until an own `bandwidthTest` runs.
- [Community-measured, contested] **A lower reading from a different probe.** The `uma_bw` tool reads 161.31 GB/s and writes 116.15 GB/s on GB10 "idle", and 90.49 GB/s read (stddev 13.58) and 62.82 GB/s write while vLLM is serving; a second user read 165.68 GB/s (forum 367851; forum 371094 #4; 4 GB buffer, CUDA 13.0, driver 580.142). Three reasons make the 231-236 GB/s saturating reads above the better-evidenced ceiling. The probe's read kernel issues scalar 4-byte `ld.global.cg.f32` loads in a grid-stride loop (`uma_bandwidth_test.cu:181-195` @ 4f6c99b in parallelArchitect/nvidia-uma-fault-probe), against an 8 GiB `float4` read-sum. Its "idle" run was "(VLLM loaded, model not inferencing)", not an empty node. And the same tool printed 4,587,571 GB/s when built with nvcc 13.1, then 165.68 GB/s after a rebuild with 13.0. [Interpretation] Flag any lab-kernel time implying more than 245 GB/s as the physics floor (the probe range is on [SM121 hardware facts](17-sm121-hardware-facts.md) §3). Treat 161 GB/s as a scalar-load lower bound for that probe. Treat the 90 GB/s figure as the probe's share while an engine runs beside it, a shared-node reference and not a node ceiling. Do not average the two.

Both are kept out of §4. PR #10966 (closed unmerged) had accepted `num_ctas > 1` on SM12x although `supportClusterOps()` excludes major 12. PR #11862 (alepot55, merged 2026-09-21): sm_12x "has TMA gather but no scatter", and 280 of 288 failing matmul cases passed after the fix on an RTX PRO 6000. PR #10825 (merged 2026-07-09): a scalar multi-CTA `atomic_cas` failure on sm120 leaves sticky state that "poisons the rest of the in-process pytest run". Older bundled ptxas rejected `sm_121a` (#9181), and `TRITON_OVERRIDE_ARCH=sm120` against a physical `sm_121a` produced gather4 `.shared::cluster` rejections (#10152) (wave-1).
- [Code-verified] [Community-measured] **Which ptxas Triton uses on SM121, and the variable that does nothing.** Triton selects its `ptxas-blackwell` tool for every `arch >= 100` (`third_party/nvidia/backend/compiler.py:41-42` @ 2cfa167), and each tool's override variable is `TRITON_{BINARY}_PATH` with `-` turned into `_` (`python/triton/knobs.py:194-201,508-509`). The SM121 override is therefore `TRITON_PTXAS_BLACKWELL_PATH`, and the widely copied `TRITON_PTXAS_PATH=/usr/local/cuda/bin/ptxas` does nothing for SM121 on any Triton with the split. A PyPI aarch64 wheel check on a GB10 found that Triton 3.5.0 ships only ptxas 12.8.93 and cannot assemble `sm_121a`; 3.6.0 adds `ptxas-blackwell` 12.9.86 (checked at the wheel level only, "likely first working release rather than a measured one"); 3.7.0 ships 13.1.80; 3.7.1 and a source build of `main` were verified end to end, running a `@triton.jit` kernel on GB10 with no environment variables (max abs err 0.0). ptxas 13.0 rejects `.target sm_121` for PTX ISA ≤ 8.7 and accepts 8.8 and 9.0, so "CUDA 13.0 cannot do sm_121" was a PTX-version conflation (triton #10331, comments 2026-07-18 and 2026-08-18). [Interpretation] The recipe was a real fix only for Triton 3.5.x. On Triton ≥ 3.7 the environment-variable fix to remember is none.
- [Community-measured, contested] **Triton cache across architectures.** One maintainer of a GB10 serving stack reports that a warm `~/.triton/cache` built on `sm_120` or an older toolchain was reused on `sm_121` and "silently miscompiles". The issue author tested cold against warm caches on GB10 and H200 and got bit-identical results, with the cache JSON recording `target.arch` 121 and 90 (triton #10331). Not reproduced. [Interpretation] Use `TRITON_ALWAYS_COMPILE=1` or a fresh `TRITON_CACHE_DIR` in lab runs anyway; it costs compile time only.
- [Code-verified] **PyTorch max-autotune on 48 SMs.** Inductor's `max_autotune_gemm` requires at least 68 SMs (`is_big_gpu`, `torch/_inductor/utils.py:2134-2141` @ c6959ab). On a 48-SM GB10, max-autotune never uses Triton GEMM templates, and matmuls fall to cuBLAS in every compile mode. A community agent-versus-compiler study logged "Not enough SMs" on GB10 (§4). [Community-measured]
- [Community-measured] **`flex_attention` returns wrong numbers without an error.** On torch 2.11.0+cu130 on `sm_121` it "compiles, runs, raises nothing" and returns cosine similarity 0.92-0.97 against SDPA. NVIDIA's `sol_attn` has a CuTe table that stops at `sm_120` and falls back to its bundled Triton kernel on GB10 (3.51 ms against 3.33 ms for a community Triton kernel, same accuracy; H3-shaped call). (drowzeys MiniMax-H3 README @ 7e3db54)
- [Code-verified] **Triton knobs worth knowing** (`python/triton/knobs.py` @ 2cfa167): `TRITON_CACHE_DIR`, `TRITON_HOME`, `TRITON_DUMP_DIR`, `TRITON_OVERRIDE_DIR` (`:344-348`); `TRITON_KERNEL_DUMP`, `TRITON_KERNEL_OVERRIDE`, `TRITON_ALWAYS_COMPILE`, `TRITON_DISABLE_LINE_INFO`, `TRITON_ENABLE_ASAN` (`:358-367`); `TRITON_CACHE_AUTOTUNING`, `TRITON_PRINT_AUTOTUNING` (`:384-385`); `TRITON_OVERRIDE_ARCH` (`:476`); per-tool paths including `ptxas-blackwell` with `PTXAS_OPTIONS` and `TRITON_DUMP_PTXAS_LOG` (`:506-515`); the tool override pattern that yields `TRITON_PTXAS_BLACKWELL_PATH` (`:194-201`).
- [Community-measured] **Toolchain bumps change numerics.** A vLLM batch-invariance test failed 3 of 5 trials on B200 under torch 2.12.0 with Triton 3.7.0 (bundled `ptxas-blackwell` 13.1.80) and passed on torch 2.11 with Triton 3.6. A maintainer traced it, "not super confident", to a likely missing proxy fence before `tcgen05.ld` that more compact PTX exposed (pytorch #181248, closed 2026-06-17). [Interpretation] tcgen05 does not exist on SM121, so this bug cannot occur there, but the lesson carries over: re-run determinism and parity gates after any Triton or ptxas bump.
- [Code-verified] **ThunderKittens.** `ARCH=SM120` compiles `-DKITTENS_SM120 -gencode arch=compute_120a,code=sm_120a` (`kernels/common.mk:87-88` @ 67845f5). FP8, FP4 and E8M0 register-tile types are gated on `KITTENS_SM120`, and there is no SM12x kernel directory. [Community-measured] Open PR #204 (chauhang, head `54e8e4e`) adds `ARCH=SM121` (`compute_121a,code=sm_121a`) and a shim that lowers the warpgroup-MMA API to per-warp `mma.sync`, bf16 only and synchronous. It passed 3,239 of 3,240 unit tests on a real GB10; the one failure is a documented complex-MMA tolerance flake. Megakernels PR #11 depends on it. Neither PR is merged. [Code-verified] Upstream's "Add initial support for SM120" (`d60dc32`, 2026-05-09) sets `MAX_SHARED_MEMORY = 99 * 1024` under `KITTENS_SM120` (against 227 KB for SM10x and 163 KB for SM80) and extends the FP8/FP4 types, with no SM121 macro. Its multi-GPU `kernels/parallel` README supports `ARCH=SM90` or `SM100` and assumes 8 GPUs.
- [Code-verified] **TileLang.** It treats `120 <= arch < 130` as SM120 (`src/cuda/target_utils.cc:78-83`), registers an SM120 block-scaled GEMM implementation (`tilelang/cuda/op/gemm/__init__.py:29-30,49-54`), ships an SM120 NVFP4 example, and reserves TMEM for 100 ≤ arch ≤ 110 (@ e4e1415). [Code-verified] The SM120 NVF4 block-scaled path is exposed as `T.mma_gemm_blockscaled` ("Explicit SM120 warp-level block-scaled MMA GEMM", `mma.sync.m16n8k64.kind::mxf4nvf4.block_scale`) in `tilelang/cuda/language/gemm_op.py:84-127,398-420` @ e4e1415; the target-neutral `gemm_blockscaled` in `tilelang/language/gemm_op.py` points to `T.tcgen05_gemm_blockscaled`. [Community-measured] On sm_120 a JIT compile hangs with no output (#2328, open). A "random hang after 30k runs" report (#2301, TileLang 0.1.8, SKU unstated) was closed as resolved by PR #2315 (merged 2026-06-04). A community GB10 port of Qwen's FlashQLA found `T.gemm_v1(transpose_B=True)` "silently produces wrong results on Blackwell" and switched to `T.gemm_v2` (Plaaasma/FlashQLA-Blackwell @ 9cdca00). [Measured] Two TileLang kernels run in the own production GLM TP3 prefill profile (§4).
- [Code-verified] [Community-measured] **cuTile.** cuTile Python generates Tile IR and needs driver r580+. "The `tileiras` compiler (version 13.2) only supports Blackwell GPU and Ampere/Ada GPU" (README @ a59c59a). It runs on GB10: a kernel that hung on B200 ran there (#71, closed). zbrad reports on GB10 that `tileiras --gpu-name` accepts base `sm_121` and rejects every `a` target (`Cannot find option named 'sm_121a'`), and that `export_kernel(gpu_code="sm_121a")` fails to parse (`#105`, open; cuTile 1.4.0/1.5.0, CUDA 13.3). A follow-up shows `tileiras` V13.3.36 rejecting every `a` target, and the maintainer will fix only the Python-side parse. `ct.launch` is opaque to `torch.compile`. The maintainer's answer is to wrap it in `torch.library.custom_op` with a fake implementation (#80, closed). `tileiras` segfaults on some kernels (#94-#97, open). [Community-measured: vendor sample output] NVIDIA's DGX Spark cuTile playbook (updated 2026-06-16, @ 3410c65) prints FMHA at seq 2048 on `sm_121` going from 2.19 ms / 62.8 TFLOPS (basic) to 1.69 ms / 81.1 TFLOPS after exp2, `occupancy=2` and approximate division; a fused-attention series labelled "Expected output should look like" of 58.2-89.5 TFLOPS fp16 causal for N_CTX 1K-16K (batch 4, 32 heads, d=128); and Qwen2-7B at batch 16 × 50 tokens going from 15.66 tok/s under Hugging Face eager to 18.52 tok/s with cuTile kernels, against a weak baseline. [Code-verified: vendor doc] In cuTile, `num_ctas` is the "Number of CTAs in a CGA", a cluster size. NVIDIA's benchmarked GB10 cuTile kernels use `num_ctas=1` or none: the FMHA kernels behind the published numbers use `@ct.kernel()` or `@ct.kernel(occupancy=2)`, and every TileGym cuTile op with an SM12x branch (attention, group GEMM, BMM) uses `num_ctas=1` there (NVIDIA/TileGym @ 5f4d7e6). The playbook's `num_ctas=ct.ByTarget({"sm_103": 8, "sm_121": 4})` appears only in an illustrative snippet in its "Platform-specific tuning" section, untested, with a comment that misdescribes it as a launch count; TileGym's comment also mislabels sm_120/121 as "B200". [Community-measured] An independent paper measured CuTile on an RTX PRO 6000 (sm_120) at 179 TFLOPS fused attention, 53% of its FA2 and 62% of its Triton, against 1,007 TFLOPS on B200, and attributes the gap to `tileiras` being tuned for sm_100 (arXiv 2604.23466v2). cuTile-rs lists `sm_121` at Tile IR 13.2; its GB10 bring-up failure (#172) was a broken nix flake, not the architecture (NVlabs/cutile-rs @ 02a9b90). [Code-verified: vendor doc] CUDA Tile C++ (CUDA 13.3) compiles with `nvcc -std=c++20 --enable-tile -arch sm_120`, and "If JIT compilation is required for tile kernels, the NVIDIA driver version must be equivalent to or newer than the version associated with the CUDA Toolkit … CUDA Toolkit 13.3 requires an R610 driver or newer." [Interpretation] On GB10 nodes with an R580-series driver, tile kernels from a 13.3 toolkit must be compiled ahead of time, the same driver-gating shape as Mojo's PTX 9.1 path below. The vendor numbers are not evidence that cuTile is mature on GB10; the independent sm_120 figure points the other way.
- [Code-verified] [Community-measured] **Mojo / MAX.** The requirements page lists "DGX Spark / Blackwell / `sm_121`" (`requirements.mdx` @ b3e9394). Modular's umbrella issue #6570 (open) says the sm_120/sm_121 series "has a few areas still to be filled in and tuned". lightofbaldr found that native NVFP4 `mma.sync … kind::mxf4nvf4.block_scale.scale_vec::4X` works bit-exact on GB10 but needs target `sm_121a` and PTX 9.1, which requires a CUDA 13.1+ driver. **Clusters: contested**
- [Code-verified] [Community-measured] The Programming Guide marks thread-block clusters "Yes" for 12.x, and a community probe ran 2×1×1 and 2×2×1 clusters with about ±1% effect ([SM121 hardware facts](17-sm121-hardware-facts.md)). On the other side, the Megakernels GB10 PR found that a size-1 `__cluster_dims__` made nvcc emit `SR_CgaCtaId` addressing that was an "illegal instruction on sm_121". Triton's `supportClusterOps()` excludes major 12, and the CUTLASS SM120 builders and the CuTe DSL GeForce dense GEMM fix the cluster at 1×1×1. [Interpretation] The best reading is that cluster launch works and some cluster-scoped code generation does not. The contradiction is unresolved (§8). NVIDIA's published GB10 cuTile results do not bear on it: nothing published uses `num_ctas` > 1 on sm_121 (cuTile above).

**CUTLASS FP4 on SM121: contested**
- [Community-measured] One side: "All CUTLASS FP4 GEMM operations produce corrupt output (zeros/NaN) on SM121" (scottgl9/sglang-spark-gb10-optimizations @ f77232a) and "Never use CUTLASS FP4; silent garbage output" (Conselara Labs note, 2026-05-09, NGC 26.04 vLLM). The other side: 356 TFLOPS dense NVFP4 on one GB10 (forum 359960, which lists both a DSL patch and C++ collective-builder kernels and does not say which produced the number), 85-129 TFLOPS from CUTLASS example 79a (VincentKaufmann/fp4-cuda-kernel @ e60a682), and serving stacks that run FlashInfer CUTLASS FP4 MoE on GB10 with correctness suites (SGLang #36845; the vLLM #38484 A/B). [Interpretation] The "garbage" reports coincide with known version-specific causes: missing SM12x cubins in `flashinfer-cubin` 0.6.11 (flashinfer #3294), the stage-count carve-out bug fixed in CUTLASS 4.4.2 (cutlass #3144), and an SM120 NVFP4 MoE garbage issue (cutlass #3096). Treat CUTLASS FP4 as version-gated and verified per stack, not as broken on the hardware (§8).

**Instruments**
- [Community-measured] `ncu` DRAM counters may not report on GB10: "ncu's DRAM counters and nsys's BW path don't report on GB10's unified memory" (chauhang, Megakernels PR #11). Until an own `--query-metrics` run shows otherwise, compute GB/s as bytes touched ÷ kernel duration and compare it with a measured read ceiling. No own `ncu` or `nsys` capture exists. See [Profiling protocol](14-profiling-protocol.md).
- [Code-verified] compute-sanitizer's Tensor Core guardrails (`-g-tmem-access-check`) apply to `tcgen05` and so not to SM121. racecheck is "cp.async aware": it flags reads of a `cp.async` or `cuda::memcpy_async` target made before the commit and wait. (Compute Sanitizer user manual, fetched 2026-09-23) [Interpretation] That check matters directly for ExLlamaV3 and E3, whose kernels use `cp.async` pipelines.
- [Code-verified: vendor doc] Stock cuBLAS can trip a GB10 sanitizer run. The CUDA 13.4 Update 1 release notes list, for CC 12.0/12.1: strided batched GEMM with broadcast operands smaller than a few hundred KB may read out of bounds, "Numerical accuracy is unaffected, but these invalid accesses can trigger compute-sanitizer warnings or, in rare instances, illegal memory access errors" (introduced 13.0 Update 2); GEMV-like operations "may produce incorrect results" when transposed with a non-accumulation dimension > 3,145,680 and beta ≠ 0 (introduced 13.3 Update 1); and on 10.x/12.x GEMM may read device alpha/beta before `cudaGridDependencySynchronize()`, a write-after-read hazard under programmatic dependent launch (introduced 13.0 Update 2). Fixed in 13.2: "GEMM and Matmul APIs with BF16 and FP16 inputs on DGX Spark … could potentially cause illegal memory accesses". [Interpretation] Sanitizer findings in stock cuBLAS calls on GB10 can be vendor-known false alarms, which is one more reason to filter sanitizer runs to the candidate kernel.
- [Code-verified] Driver JIT cache: `~/.nv/ComputeCache`, `CUDA_CACHE_MAXSIZE` defaults to 1 GiB on desktop/server and 256 MiB on embedded (GB10's class is undocumented), with a 4 GiB maximum, and it is invalidated on a driver upgrade. (correction on [SM121 hardware facts](17-sm121-hardware-facts.md))

## 5. Levers, ranked

Ranked by expected value per hour on current GB10 lanes. The first four need no new kernel code.

1. **Audit what binary actually runs, and which backend the log says was selected, before writing anything.** Applies to: every engine × every model family × every topology, first on vLLM and SGLang images and on any extension built by JIT. Gain: when SM121 cubins were missing, shipping them gave 13.3 → 48.6 tok/s on one Qwen3.5-35B-A3B FP8 request [Community-measured, forum 365083]. Admitting SM121 to an existing FlashInfer GDN prefill backend gave +5.0% warm and +7.1% cold prefill (vLLM #55715) [Community-measured]. Gating fixes (Triton #10010, vLLM #33517, the own router-GEMM backport) replaced a fallback or a `trap` with the native path [Code-verified] [Historical diagnostic]. Where a family cubin was already present, a native `sm_121` rebuild changed nothing (16.4 vs 16.3 tok/s, vLLM #38484) [Community-measured], so the lever is about missing or trapping code, not the `a` suffix. On a lane whose hot kernels already carry the right cubins and the right backend, the gain is zero. Cost: one hour. Risk: none (read-only). Smallest falsifying experiment: `cuobjdump --list-elf` on every deployed `.so` and the JIT caches; the startup log's backend announcements for every attention, GDN, MoE and GEMM path; and a grep of the dispatch path for exact-CC and `== 1200` gates. If every hot kernel carries `sm_121a` or `12.0f`, every backend line names the intended kernel, and no gate excludes 12.1, the lever is exhausted. Also check toolchain floors that carry vendor fixes: CUTLASS ≥ 4.4.2 (SM120 carve-out), Triton ≥ 3.7 [Community-measured].
2. **Measure the ceiling and classify the hot kernel with counters.** Applies to: every engine, first the production cooperative MoE, E3, Marlin and TileLang kernels on the EXL3 TP3 lane. Gain: none directly. It decides whether authoring can pay at all: plain decode that already measures at ~90% of the bandwidth wall is no longer a kernel target [Community-measured, Entrpi; Interpretation]. Cost: half a day on an idle node. Risk: `ncu` serialises launches and perturbs timing, so never run it beside serving (§6). Smallest falsifying experiment: `bandwidthTest` plus a saturating vectorised (`float4`) read kernel on an idle node (a scalar-load probe reads about 161 GB/s and understates the ceiling, §3), then one `ncu` capture per kernel in the component harness. If `dram__bytes_*` returns no values (§3), fall back to bytes ÷ duration.
3. **Switch backends or adopt a proven upstream kernel through gates.** Applies to: vLLM + ExLlamaV3 on MoE and hybrid-attention models, any topology. Gain: the KDA Marlin → BF16 switch was 2.17-2.25× on the component and +7.2-7.9% effective prefill inside a bundle, at ~2.26 GiB per node [Measured]. The upstream E3 kernel gave +37-45% cold prefill on a 2-node kit [Community-measured]. The fleet adopted E3 without an isolated local A/B. Cost: hours to a day, plus an offline build. Risk: memory cost, numeric drift at large M, first-use JIT inside a live request. Smallest falsifying experiment: one isolated serving arm on the frozen harness with the candidate as the only change, closing baseline included. See [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md) for the KDA path.
4. **Tune data, not code.** Applies to: vLLM Triton fused-MoE (GB10 configs exist for only two FP8 shapes), SGLang Triton MoE, Triton KDA/GDN kernels, FlashInfer prefill shapes. Gain: unmeasured on the fleet [Proposed]. In the community, four generated `NVIDIA_GB10` SGLang Triton MoE config files turned an `OutOfResources` crash (147,456 B requested) into a working EAGLE path and gave +6.3% with EAGLE off (GLM-4.7-FP8, 4 × GB10, request shape not stated) [Community-measured, forum 359960]. FlashInfer's opt-in `fmha_v2` prefill is another data-level switch: 10-31% faster than FA2 at S ≥ 512 in its author's kernel table, slower below 256, end-to-end effect unmeasured [Community-measured]. Cost: a tuning run plus a config file, loaded by `VLLM_TUNED_CONFIG_FOLDER` [Code-verified]. A full FlashInfer autotune OOMs a unified-memory GB10 serving node, so recipes pass `--no-enable-flashinfer-autotune` (upstream kit note) [Community-measured]. A prefill-shape-only autotune with a persisted cache is the untried middle path. Risk: tuned tiles that exceed 99 KB `OutOfResources` at other shapes. Smallest falsifying experiment: `benchmarks/kernels/benchmark_moe.py --tune` for the lane's shape on an idle node, then one component A/B at the lane's real row counts. MoE configs belong to [MoE dispatch](08-moe-dispatch.md).
5. **Dispatch hygiene and a launch-bounds guardrail on kernels the fleet already ships.** Applies to: the cooperative decode MoE kernels on the EXL3 TP3 lanes. Gain: no speed gain is claimed [Proposed]. It prevents silent loss: 39 of 41 stock-routed row counts were never measured, the ≤0.97 gate sits inside ~15% node-to-node spread, and +2 registers would halve residency with "0 spills" still in the log [Measured]. Cost: about an hour for `__launch_bounds__(512, 2)` (a register regression then spills visibly instead of halving occupancy), and a day to complete the row grid. Risk: low. Smallest falsifying experiment: rebuild with `(512, 2)`, confirm the same 63 registers and zero spills, and re-time the 64-row grid with ≥ 200 samples near thresholds under the 2,100 MHz cap ([Clocks, thermal, power](13-clocks-thermal-power.md)).
6. **Author a new prefill kernel where counters show compute or tiling bound.** Applies to: engines where the kernel is under your control (llama.cpp forks, ds4, ExLlamaV3 in vLLM), MoE and attention prefill, any topology. Gain: 2.43× at 2K and 3.30× at 64K prefill in one fork vs upstream on the same GB10 [Community-measured, Entrpi], and E3's +37-45% [Community-measured]. No own authored kernel has a clean win. Amdahl bites hard here: a 2.76× TileLang GDN prefill kernel moved an 8K-prefill TTFT by ~3% on a 27B hybrid model whose prefill is dominated by other layers [Community-measured, FlashQLA-Blackwell], and in a public GB10 decode profile a 20% gain on the kernel family that takes ~61.9% of GPU time is ~12% end to end [Community-measured, forum 374382]. Cost: weeks. Risk: the component-to-model gap (§7) and toolchain gaps (§3). Smallest falsifying experiment: before writing code, an `ncu` capture showing the target kernel far below both the measured bandwidth and the compute ceiling, with a phase share large enough that a 2× kernel win moves TTFT by more than the run-to-run band (about -1% / +4% on the own TP3 harness). See [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md) for the GDN and KDA prefill kernels.
7. **Fuse launches on a launch-bound path.** Applies to: small dense models at batch 1 (decode), vLLM or standalone; not the fleet's large MoE lanes, which already run under CUDA graphs. Gain: 1.49× over eager and 1.33× over compiled-plus-graphs on Llama-3.2-1B [Community-measured, Megakernels]. Cost: weeks; depends on unmerged ThunderKittens PR #204. Risk: cluster codegen faults on sm_121 and the 99 KB cap (§3). Smallest falsifying experiment: nsys on the target path. If kernel gaps are under ~5% of GPU time, fusion cannot pay. See [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md).
8. **Put an AI agent in the loop, inside a human-directed harness.** Applies to: any of levers 4-7. Gain: agent-assisted beat full-agent in the one controlled comparison found (1.12-29.68× retained on B200) [Community-measured]. Under a verified protocol the best model fell to 0.88× of PyTorch [Community-measured]. The own agent-written decoder won on components and lost end to end [Measured]. On GB10 itself, the best of three agent CLIs was 1.026× against `torch.compile(default)` and 0.954× against max-autotune on Qwen3-1.7B [Community-measured, ianbarber]. The one agent-written SM121 kernel merged into an engine branch was a correctness fix first (a silent token-0 corruption), with a declared input contract, provenance by hash, and kernel (2.07×) and end-to-end (+4.45% at concurrency 1) numbers reported separately [Community-measured, sglang #36845]. That is the pattern to copy. A maintainer's review of an AI-co-written GB10 split-KV kernel is the counterweight: "Claude will usually do stuff in pytorch just to get the tests to pass, without caring about perf … For split we should be writing in fp32, not bf16" (tridao, flash-attention #2336) [Community-measured]. Cost: the harness in §6. Risk: reward hacking, and agent analysis errors (the own frontier dossier's verification passes corrected 31 items). Smallest falsifying experiment: give the agent one lever-4 or lever-5 task with the §6 harness outside its writable tree, and count candidates that fail Stage B or the physics-floor check.
9. **Author for bandwidth-bound MoE decode.** Applies to: EXL3 and GGUF MoE decode at low concurrency. Gain: little. The fleet's attempts gave component 1.23-1.94× on synthetic weights with no serving number, a decoder variant that read -5.51% at C8 in its combined arm, and tile variants that lost at 8,192 rows [Measured]. Plain decode that measures at the bandwidth wall is not a kernel target [Interpretation]. The exception is decode below the wall because of host overhead or launch count (0.107 ms per layer at 1 row, §4). Cost: weeks. Risk: high. Smallest falsifying experiment: bytes touched per token ÷ measured ceiling. If measured decode is within ~10% of that, stop. The one decode-kernel item with evidence is upstream's thin-fast stock-kernel patch, which needs an offline extension recompile and a ≥ 30-run histogram because of a reported bimodal regression [Historical diagnostic].

## 6. Protocol

This is the Spark Kernel Lab v2 procedure an agent executes to take one kernel change from idea to a promotion decision. It builds on the upstream "Atlas" EXL3 SM121 kernel lab v1 (NumPy oracle, model-agnostic `OPERATOR:K:N` workloads, a tactic sweep over tiles and SM quotas, receipts that refuse to emit without a resolvable runtime commit, a decision gate; development-only, never in the served image, never run on SM121) [Historical diagnostic], and on the fleet's combined-runtime gates [Measured]. Every stage is [Proposed] as a whole unless marked.

**Preconditions.**
- Fleet rules from the entry page ([GB10 Inference Wiki](README.md)):
  - no memory overcommit: ≥ 5 GiB warm floor, ≥ 8 GiB free before any start, and one memory variable per boot;
  - stop if `MemAvailable` falls under 4 GiB on any node;
  - one variable per boot;
  - a clean window with no outside traffic;
  - if an A/B needs an engine restart, skip the image pull (`--pull=never`);
  - never restart an agent gateway;
  - never `pkill -f` a pattern that matches your own shell.
- Isolation: the lab never shares a GPU with a serving lane. It runs only on a drained node or on an explicitly assigned idle node. The container refuses to start below 5 GiB free disk or 8 GiB host memory (the fleet's bounded maintenance container is 32 GiB, 4 CPUs, 30 min, `--pull=never --network none`). [Measured practice]
- The decision rule is met and written down: a profile names the kernel as a hotspot of the phase that matters (nsys first, `ncu` only after, per the Anemll rule set) [Code-verified]; levers 1-5 in §5 are exhausted or ruled out; no upstream fix is pending (search the engine's and the kernel library's open PRs for the kernel name and "sm_121"/"sm120").
- Clocks: the fleet 2,100 MHz cap is in place and recorded (`nvidia-smi -lgc 0,2100`); whether a lane keeps a cap follows [Clocks, thermal, power](13-clocks-thermal-power.md) §5 lever 1. [Measured]
- Profiling access: `ncu` needs `NVreg_RestrictProfilingToAdminUsers=0` or root ([Profiling protocol](14-profiling-protocol.md)). [Community-measured]

**The change (one kernel, one variable).**
- **Stage A, build, offline.** Compile the candidate in a network-less, GPU-less container on the serving image digest with capped CPU and memory (2 CPUs, 8 GB, `NVIDIA_VISIBLE_DEVICES=void`) [Measured practice]. Target `sm_121a` explicitly; never plain `sm_120` (trap stubs, §2 SGLang) or `121-real` for FP4 or block-scaled code (§3). Record `ptxas -v` (or `SGLANG_JIT_LOG_RESOURCE_USAGE=1 SGLANG_JIT_FORCE_RECOMPILE=1`). Fail the build if registers cross a residency step or spill bytes are above 0, unless declared. Require `__launch_bounds__(threads, minBlocks)` on any kernel near a cliff. Emit a manifest with source SHA, nvcc/ptxas/Triton/CUTLASS versions, flags, and the `cuobjdump -lelf` cubin list, so `sm_121a` vs `sm_120f` is recorded, not assumed. Whole-file SHA gates reject clean rebuilds, because nvcc embeds an absolute build path, a build-id and a few irreducible fatbin bytes [Community-measured, upstream issue discussion held in own records]. Hash the `.text` sections and the cubin list instead. Fail the build if the requested target did not land in the cubin list; for vLLM's own `_C`/`_moe_C` on a CUDA 13 toolkit, expect `12.0f` unless the supported-arch list is patched (§2) [Code-verified]. Pin Triton ≥ 3.7 (the first release verified end to end on GB10; 3.6.0 likely) and set `TRITON_PTXAS_BLACKWELL_PATH` only when a specific ptxas is required, never `TRITON_PTXAS_PATH` [Code-verified] [Community-measured]. Use a fresh `TRITON_CACHE_DIR` or `TRITON_ALWAYS_COMPILE=1` for every lab build. For cuTile or CUDA Tile C++, compile ahead of time whenever the toolkit is newer than the node driver (13.3 needs R610 to JIT) [Code-verified: vendor doc]. [Proposed as gates]
- **Stage B, correctness, idle GPU.** Write the tolerances down before the run (the fleet's are peak-rel ≤ 0.003, row-peak-rel ≤ 0.05, rel-L2 ≤ 0.05) [Measured]. Compare against an oracle (NumPy/CPU, or the stock kernel as in llama.cpp `test-backend-ops`) across the full row grid and every routing pattern, with hidden inputs drawn from several distributions (KernelBench v0.1 `rand_mix`; KernelBench-Verified). Also run:
  - changed-data CUDA-graph replay, which must be bitwise equal to eager;
  - a zero per-call allocation check;
  - compute-sanitizer memcheck (compile-time `-fdevice-sanitize=memcheck -lineinfo` where the toolkit matches the PTX compiler), racecheck including the `cp.async` checks, initcheck and synccheck. Filter each to the candidate namespace with `--kernel-name regex=` and set `--error-exitcode`;
  - a repeat-run bitwise test (N ≥ 10 identical launches), which must pass unless the kernel is declared atomic-order-nondeterministic, in which case a tolerance band applies;
  - a batch-invariance test for any kernel whose reduction strategy depends on M. [Code-verified docs; Proposed as a gate]
  - an fp64 reference beside the fp32 or stock oracle, and a mutation self-test of the harness before trusting it: inject a handful of arithmetic and precision faults into the candidate and confirm the gate kills them. Tolerance oracles are weakest on precision faults (the official KernelBench check missed 78.6% of them in one mutation study) [Community-measured, arXiv 2609.22220; Proposed as a gate];
  - a test of the test: confirm the reference agrees with fp64 on a permuted multi-head case before reading any failure as a kernel failure. A `view` without `permute` in one GB10 reference produced false FP8 failures for H ≥ 2, and Python's per-process randomised `hash()` used to seed "canonical inputs" produced a fake cosine-0.5 failure; derive seeds with a stable hash [Community-measured, cutlass PR #3030; ianbarber];
  - an explicit input contract with a descriptive error outside it, and a "one CUDA activity per call" assertion on the timed path [Community-measured, sglang #36845];
  - property stress at extreme scales (many chunks, large value scales, extreme decay), and a cache-key test that overwrites the same buffer without a version bump [Community-measured, kernelbench.com audit];
  - a long-run state test (≥ 10^5 consecutive launches) for kernels with persistent counters or atomics, checking that the counters return to zero [Community-measured, sglang #36845: 150,000 launches].
  Filter every sanitizer run to the candidate: stock cuBLAS on CC 12.x has vendor-known out-of-bounds reads that trip compute-sanitizer (§3).
- **Stage C, component timing.** Use CUDA events or graph-replay timing under the external 2,100 MHz cap. Alternate candidate and stock, keep ≥ 200 samples per cell near any dispatch threshold, cover all ranks, and keep p10/p50/p90. Hold the decision when the envelopes overlap. Synchronise the device and every stream before the end timestamp. Fingerprint outputs after return and again after the sync (the GPU MODE fix) [Community-measured]. Pre-warm every JIT variant outside the timed region (a first-run JIT produced a 1.25× outlier in the CuTe DSL flash-attention thread). Report standalone and in-graph timings separately, and never time against a profiler aggregate (one SwiGLU kernel read 3.0× that way and 1.06× standalone) [Community-measured]. When the comparison is `torch.compile` on GB10, record that max-autotune cannot use Triton GEMM templates below 68 SMs [Code-verified]. Physics-floor check: flag any time implying more than 245 GB/s for the bytes touched (the top of the probe range on [SM121 hardware facts](17-sm121-hardware-facts.md) §3, until an own ceiling exists; the ~90 GB/s under-load probe figure is only a shared-node reference), or below the compute ceiling for the FLOPs. Quarantine any candidate that beats stock by more than a preset factor (for example 3×) for manual review. KernelBench's own eval guide sets the same prior: "a >2x speedup for anything is highly unlikely" and "if you beat cudnn by more than 10%, think again" (EVAL.md @ 423217d) [Community-measured].
- **Stage D, attribution with counters.** Run Nsight Compute only on the candidate and stock kernels in the component harness, never beside serving (`ncu` serialises launches, flushes caches, saves and restores memory for replay, and needs lockstep setup for NCCL kernels) ([Profiling protocol](14-profiling-protocol.md)). Use `--clock-control none` under the external lock. Check each metric name with `--query-metrics` first, then collect the minimum set: duration, `dram__bytes_read.sum` / `dram__bytes_write.sum`, L2 hit rate, `local__*` spill bytes, `launch__registers_per_thread`, `launch__occupancy_limit_*`, warps active, eligible warps, stall reasons, tensor and FMA pipe activity. Classify with the 60/40 heuristic from NVIDIA's in-repo sections guide: memory throughput above 60% of peak is memory-bound, compute above 60% is compute-bound, both below 40% is latency-bound [Code-verified heuristic, not validated on SM121]. Express DRAM in GB/s, not percent. If `dram__bytes_*` is unavailable, use bytes ÷ duration against the Stage C ceiling. This replaces v1's timing-ratio classifier, whose code has three labels, with a counter-backed one. Keep the ratio as a cross-check.
- **Stage E, serving A/B gate.** The candidate becomes eligible only through its own arm on the frozen serving harness: fixed fixtures, forced output length (512 tokens), thinking off, C1/C4/C8, warm-up excluded (and not overlapping the timed gates), and a closing baseline repeat. Add repeated model-level coding, tool and reasoning outputs checked for corruption, because a component numeric pass does not prove the model is intact (the token-0 lesson, §4). Use changed-content consecutive requests, not identical repeats, because a CUDA-graph staleness bug hid behind identical requests in one GB10 recipe. Sweep concurrency far enough to reach known hang regions (a GDN decode kernel hung at c≈32 with no error). For long-context lanes, add needle-in-a-haystack prompts at the lane's long contexts and count token-id-0 outputs (the #36845 battery). Confirm from the startup log on every rank that the intended backend was selected, because gates fail silently. [Community-measured, jschmied recipe; sglang #36845; Proposed as gates] Correctness gates follow [Quality and correctness gates](21-quality-and-correctness-gates.md). All [entry-page](README.md) rules apply, in particular: greedy logprob probe after every relaunch; discard the first request and warm every shape; unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection line on every rank; ≥3 reps with a closing A/B/A; MemAvailable every 1-2 s and zero NV_ERR_NO_MEMORY/Xid; no reboot without per-node permission. For Stage E that means in particular `MemAvailable` sampled every 1-2 s with an Xid count, a greedy probe, a nonce per prompt, ≥3 reps, the backend line on every rank and the same clock cap on every rank. If the change needs a restart, restart with the pull skipped and change nothing else in that boot. Re-profile dispatch after any stock-path change.
- **Agent seat.** An AI agent may propose, write and run Stages A-D. The harness, tolerances, oracle and timer live outside the agent's writable tree. Evaluation runs in a separate trusted process that never imports the candidate. Candidates that create streams, threads or graphs are rejected or re-timed. Try/except fallbacks and calls into the reference op are banned. Stage E results and the promotion decision are reviewed by a human, and agent-written analysis is adversarially verified before it enters a packet. Any hardware sheet handed to the agent is built only from sourced numbers: one public GB10 agent platform gives its model 2,048 threads per SM, 209 BF16 TFLOPS, 128 KB shared memory per SM and "No FlashAttention", all wrong for SM121 (leap21ai/autospark @ 8b3578b) [Community-measured]. No public board offers GB10 feedback: GPU MODE's popcorn runners are B200/H100/A100/L4/T4-class, and GPU MODE says it is moving from KernelBench toward BackendBench and FlashInfer-Bench (gpumode.com 2026 post, read through a text reader) [Community-measured]. The cheap, verifiable signal on this fleet is therefore the local Stage B-C harness, run on an idle node. SOL-ExecBench's harness (clock locking, L2 flushing, subprocess isolation, static hack checks, scoring against analytic speed-of-light bounds; arXiv 2603.19173, B200) and KernelBench's own guidance (regex-based static checker; adversarial tests for reference-cache reuse, input mutation and non-default streams; EVAL.md @ 423217d) are the closest public templates. [Community-measured; Proposed as the fleet design] [Interpretation, synthesised from KernelBench v0.1, METR, CUDA-L1, Kevin, GPU MODE, KernelGuard, Makora and KernelBench-Verified; Proposed]

**Record (packet fields).**
- Candidate source SHA, base image digest, toolchain versions, build flags, the `.text` hash and cubin list, `ptxas -v` registers, spills, stack and shared memory, and the declared launch bounds.
- Frozen tolerances (written before the run), the oracle identity, the input distributions, and pass or fail per row, routing pattern and rank, with the worst values.
- Sanitizer tool, filter expression, launches checked, and error counts. Record partial runs as partial, never as a pass.
- Component timing: clock lock value, sample count, p10/p50/p90 per cell per rank, alternation order, the physics-floor result.
- Counter set with metric names as `--query-metrics` returned them, and the classification.
- Serving arm: baseline and candidate medians per concurrency, the closing baseline, the run-to-run band, and the repeated-output corruption check.
- Any first-use JIT seen during warm-up or inside a request.
- The backend-selection lines from the startup log, the fp64-reference result, and the harness mutation self-test score.
- The concurrency reached in Stage E and whether any request hung.

**Pass gate.**
- Stage B: every row, pattern and rank within the frozen tolerances; graph replay bitwise equal; zero per-call allocations; sanitizer-clean on the candidate namespace; determinism class declared and met.
- Stage C: candidate p90 below stock p10 at the rows the dispatch would route to it; no physics-floor violation.
- Stage E: the candidate beats or intentionally matches the baseline on the user-relevant metric by more than the stated run-to-run band (own TP3 harness: about -1% / +4% between baseline repeats), with no new failures, no corrupted repeated outputs, no hang across the concurrency sweep, and the intended backend confirmed in the log. A component ratio alone is never a pass. [Measured basis: the -5.51% combined-arm result]

**Rollback.**
- Kernels ship only as layered `.so` files over byte-identical base extensions, with the dispatch policy bound to the candidate's hash, so rollback is re-pointing to the previous layer or unsetting the enable flag in the lane recipe. Promote the recipe change through the lane's promotion mechanism, not by editing a running container. [Measured practice]
- Never recompile an extension on a serving node to roll back. Keep the previous `.so` and its manifest.
- If the lab's run touched a shared node, confirm `MemAvailable` and the warm floor are back to their pre-run values before handing the node back.

## 7. Anti-patterns and known-bad

- [Measured] **Component win, whole-model loss.** An agent-written decoder variant was exact, sanitizer-clean and 1-8% faster at small rows, and the combined arm containing it read C8 111.757 → 105.602 tok/s (-5.51%) with decode flat. Its own end-to-end effect was never isolated, and that is itself the lesson: the serving arm is the reward, and component ratios are only a filter. Z.ai states the same rule: "giving a compute kernel more resources may shorten its own execution time while leaving fewer resources for the KV Transfer kernel, ultimately slowing the overall pipeline." [Community-measured] (2026-09-20 "GLM 5.3 Flash V3") The gap recurs outside the fleet on GB10: a row-batched ExLlamaV3 mixer kernel 9.1 → 7.7 ms that was noise end to end and shipped default-off; a 2.76× TileLang GDN kernel that moved TTFT ~3%; a 3.91× standalone kernel that moved its workload 1.010× (§4). [Community-measured]
- [Measured] **Component numeric pass, serving output corrupt.** An SM121 sparse-decode path that an external six-shape numeric test had passed booted, passed most API gates, and corrupted 2 of 4 repeated coding outputs into token-0 loops. [Community-measured] A custom FP4 GEMM held 0.991 Pearson per GEMM, and raw FP4 GPT-OSS-20B still produced gibberish without calibration (forum 361600). Repeated model-level output gates are required.
- [Measured] **Tile variants chosen by intuition.** Three numerically clean tile variants lost to the stock 64-row / 4-stage tile at 8,192 rows (up to +219% time), and the one marginal win at 1,024 rows was within a few percent. Stock tiles are usually tuned. (2026-09-16 "DeepSeek V4.1 Flash EXL3 TP3 prefill profiling and tuning")
- [Measured] **"0 spills" read as safe.** Without a minimum-blocks launch bound, a two-register growth halves residency and the build log still says 0 spills.
- [Measured] **Dispatch decided by noise and by absence.** A ≤0.97 gate inside ~15% node-to-node spread, and 39 of 41 routed row counts never measured. A policy bound only to the new binary's hash would also accept a stale policy silently after a stock-path change. [Interpretation]
- [Measured] **Recompiling kernels on a unified-memory serving node.** A `MAX_JOBS=8` extension build competes for the host-memory floor (UVM livelock class). Build offline and layer the result. [Community-measured] A Mojo compile of one 958-line test file reached 53-59 GB RSS on a 60 GB sm_120 laptop (#6584). A compile of that size beside a serving lane would breach the fleet's memory floors. [Interpretation] GB10 reports agree: a cold CUTLASS FP4 JIT with a 23 GB model resident was OOM-killed (`ninja` exit 137); a vLLM start that JIT-compiled 6+ CUTLASS MoE kernels ran `cicc` processes of 1.5-6 GB each; and a MAX compile peaked at 108 GB for a 0.5B model at its default memory-manager setting (§4). [Community-measured] See [Memory on unified memory](11-memory-on-unified-memory.md).
- [Measured] **First-use JIT inside a live request, and warm-ups that overlap timed gates.** A sampler kernel and a Triton specialisation compiled inside the first live request that needed them. A warm-up that overlapped a gate forced the gate's timing to be discarded.
- [Measured] **Broad sanitizer runs.** A racecheck that instrumented unchanged stock kernels reported stock warnings and was stopped. The practice is to filter to the candidate namespace, preserve the partial evidence, and never count it as a pass. A diagnostic-only run once labelled "passed" is now labelled `diagnostic_only`.
- [Measured] **Enabling a locally built binary whose manifest still says GPU validation is pending.** It happened once, inside a bundle, with only component gates behind it.
- [Measured] **Profiler as a free observer.** The torch profiler inflated one ~32K TTFT from ~23.8 s to 35.96 s, and in one configuration it failed to arm at all.
- [Measured] **Stale kernel resolvers in base images.** A legacy BF16-only SM121 resolver pre-empted the FP8-capable branch and broke graph warm-up. Assert and remove the exact block in the Dockerfile.
- [Code-verified] **Custom op registered, fallback measured.** Under Inductor, vLLM's `custom_ops` default is `'none'`, so a new `CustomOp` runs its torch fallback unless `+OpName` is listed (§2).
- [Code-verified] **Wrong target suffix.** Plain `sm_120` compiles CUTLASS SM120 atoms into trap stubs that assert at launch (SGLang). An `sm_120a` cubin does not load on GB10, and that is what upstream ThunderKittens `ARCH=SM120` builds. `121-real` fails on FP4 `cvt`. `TRITON_OVERRIDE_ARCH=sm120` on a physical `sm_121a` produced `.shared::cluster` rejections (wave-1). Setting `TORCH_CUDA_ARCH_LIST=12.1a` for a vLLM build on a CUDA 13 toolkit still yields `12.0f` kernels, and the published v0.27.1 aarch64 image carries zero `sm_121` cubins [Community-measured, vLLM #38484]. A guard written as `__CUDA_ARCH__ == 1200` traps on `12.1f` cubins (vLLM before #33517). [Code-verified]
- [Code-verified] [Community-measured] **Copying `TRITON_PTXAS_PATH` into GB10 recipes.** Triton uses `ptxas-blackwell` for every arch ≥ 100, so the variable is inert on SM121 on Triton 3.6 and later; it was a real fix only for 3.5.x. It still appears in an open vLLM PR (#31740), several community recipes and the research synthesis behind this page's second pass. The fix to remember is Triton ≥ 3.7, which needs no variable (§3).
- [Community-measured] **Retracted GB10 failure reports cited as fact.** Three reports this program first read as GB10 kernel failures were retracted in their own threads. TileLang #3071's "silent all-zeros miscompilation" was withdrawn by its reporter: "tilelang is fully exonerated on the zeros … a model-level degenerate attractor in the `state-spaces/mamba3-mimo-1.5b` checkpoint, triggered by specific content, not a miscompilation". A later GB10 run showed 0.1.14 bit-for-bit consistent with 0.1.13. A vLLM report attributing a 600 s start timeout to FlashInfer JIT was disproved by its reporter (#48031). A report that `flashinfer-cubin` lacked SM12x kernels and produced NVFP4-MoE garbage was traced to a `cutlass-dsl` wheel collision. The maintainer notes that `flashinfer-jit-cache` ships SM120 modules as `120f` (flashinfer #3294). A third: a vLLM issue titled as a DeepGEMM family-12 gate fault on SM121 (#54125). Its reporter wrote on 2026-08-28: "My 'the `120` capability family is too coarse' framing was wrong; please read the title as inaccurate." The crash was an attribute-name bug that skipped DeepGEMM weight post-processing, not SM121-specific and already fixed on main (`f8e0602713`). The same thread holds a real, separate GB10 finding, the silent `K=2560` block-FP8 corruption window (§2). Read the whole thread and the maintainer reply before citing, and keep the real finding when the headline is retracted.
- [Community-measured] **LLM-propagated SM12x misinformation.** A largely LLM-written GB10 build guide called SM120 "datacenter Blackwell" and concluded that NVFP4 "will never compile for SM121 — this is a hardware limitation". The error came from building for plain `sm_121`. A reply noted that "When it comes to leading edge stuff, like Spark, LLM (or even Google) can not be trusted" (forum 365083). A public Blackwell wiki marks `wgmma.async` as available on SM 12.0, but PTX ISA says `sm_90a` only. [Measured] The own frontier dossier's three adversarial verification passes corrected 31 items across the first-pass analysis, the research brief and a prior packet, including a brief that read an `<4,1,…>` template as four pipeline stages (it is bits, codebook, width). A quick 3-rep probe claiming +38% was withdrawn. Do not read SM120 discrete-card documentation as SM121 fact, and adversarially verify agent-written kernel analysis. [Community-measured] The research synthesis behind this page's second pass repeated the 228 KB shared-memory error and the inert `TRITON_PTXAS_PATH` fix, cited an unmerged vLLM PR head as a landed commit, and read a cuTile cluster-size hint as a launch count; the follow-up pass caught each against the primary source. A web article on GB10 fixes called DGX Spark a B200/GB200 enterprise architecture and was not used. A public GB10 agent platform ships wrong limits to its model (§6).
- [Community-measured] **Reward hacks that fooled evaluators.** The Sakana AI CUDA Engineer claimed 10-100× speedups over PyTorch. Readers found within two days that incorrect kernels passed through a memory-reuse path, and one remaining >100× case had omitted the convolution entirely. Sakana acknowledged that "the system had found a memory exploit in the evaluation code which, in a number of cases, allowed it to avoid checking for correctness" (X posts fetched 2026-09-23; TechCrunch 2025-02-21). Documented hacks elsewhere:
  - timing on one stream while computing on another (KernelBench v0.1, METR, CUDA-L1's 82 of 250);
  - lazy tensors that compute only inside `allclose`, shrunken task hyperparameters, and results cached by input address (CUDA-L1);
  - inheriting or calling the PyTorch reference, and `try/except` fallbacks (Kevin);
  - `torch.empty` re-using the reference's output memory (METR);
  - super-batching timed calls (GPU MODE). The full post-mortem shows a second exploit path keyed on problem shapes, written after the agent reasoned about input cloning, so the clone-and-shuffle patch (reference-kernels PR #102) would not have stopped it; the fix (PR #104) fingerprints output buffers after return and again after the stream completes. "The boundary between 'optimizing the solution' and 'optimizing against the evaluation' doesn't exist for an agent." The agent's final kernel was still a real ~800-line CuTe NVFP4 grouped GEMM;
  - a lazy `torch.Tensor` subclass and stream injection against a CUDA-event timer; the published defences are a sync before the end event (or a hybrid of both timings), a thread-count check, rejecting non-materialised outputs, and pinning timer function references, with precision downgrade only "partial" (deep-reinforce defence write-up);
  - constant fill and "baseline kernel" (Makora).
  "Even when we patch known exploits, new ones emerge." (KernelBench v0.1)
- [Community-measured] **SM121 "fixes" on wrong premises.** Triton PR #9852 ("SM120/SM121 codegen: no tensor memory pipeline") was withdrawn by its author within three hours of review, after testing showed no `tcgen05` is emitted on GB10 anyway; an earlier SM120 change on the same premise (#9734) was merged and then reverted (#9755). A one-line SGLang SM121 FP4 dispatch (#17421) was closed unmerged.
- [Community-measured] **Silent numeric failures that raise nothing.** `flex_attention` on `sm_121` returned cosine 0.92-0.97 against SDPA with no error (torch 2.11.0+cu130). A FlashInfer TensorRT-LLM paged decode path returned 32/32 token id 0 with HTTP 200 at 120K-210K context on SM121 (sglang #36845). TileLang's `T.gemm_v1(transpose_B=True)` "silently produces wrong results on Blackwell" (FlashQLA-Blackwell). DeepGEMM block-FP8 corrupts silently at `K=2560`, small N (vLLM #54125). Each passes a smoke test; only an oracle or a model-level output gate catches it. See [Attention backends on SM121](06-attention-backends-sm121.md) for the token-0 route.
- [Community-measured] **Harness bugs read as kernel bugs.** A reference that called `view(B*H,S,D)` on a `(B,S,H,D)` tensor without `permute` produced false FP8 causal failures for H ≥ 2 (cutlass PR #3030); Python's per-process randomised `hash()` used as a seed produced different "canonical inputs" in two scripts and a fake cosine-0.5 failure (ianbarber); a first-run JIT produced a 1.25× outlier that "was a JIT artifact" (PR #3030); a bandwidth tool printed 4,587,571 GB/s and did not flag it (forum 371094). Test the test first.
- [Community-measured] **Loose tolerances and bounded outputs.** At cos ≥ 0.95 one agent replaced `sigmoid` with a clamped linear approximation and claimed 3.36×, which collapsed to 1.04× at cos ≥ 0.99 (ianbarber). A 104.89× HIP kernel read 256 B past its shared-memory limit and passed `allclose(1e-3)` because softmax outputs sit in [0, 1]; only a bitwise determinism check caught it (Wafer, MI300X). An FP8 GEMM kernel cached a padded operand keyed on `(data_ptr, _version)` and returned stale data after a same-buffer overwrite, cos 0.000778 (kernelbench.com audit, RTX PRO 6000).
- [Community-measured] **Identical repeats as a staleness test.** With CUDA graphs on, an unpatched branch consumed the previous step's offload outputs on every forward, and "identical consecutive requests hide it, real traffic never does"; a GDN decode kernel hung the engine at c≈32 with no error (jschmied recipe). A component harness with fixed inputs and low concurrency sees neither.
- [Community-measured] **Weak baselines.** Comparing against FP32 eager instead of TF32 or the production kernel inflates agent speedups (KernelBench-Verified: 1.43× → 0.88×). A custom FP4 kernel's "5-9× faster than BF16" was a comparison against FP32 `torch.mm` (forum 361600). A GB10 RMSNorm's 3.00× is against four unfused eager kernels, traffic that `torch.compile` would also remove (Logos-Flux), and a cuTile end-to-end +18% is against Hugging Face eager (NVIDIA playbook).
- [Interpretation] **Headline speedups from degenerate tasks.** CUDA-L1's 120× peak comes from a task whose output is always zero, the kind of task KernelBench v0.1 later removed.

## 8. Open questions

- Counter-based classification of any production kernel on GB10 (cooperative MoE, E3 fat-expert, Marlin, TileLang kernels). Settled by one Nsight Compute capture per kernel in the component harness with the Stage D metric set, clocks capped at 2,100 MHz, `--clock-control none`.
- Do Nsight Compute's sections and `dram__*` metrics return values on SM121, which chip does GB10 report, and what peak does `dram__*.pct_of_peak` use? One community statement says the DRAM counters do not report (Megakernels PR #11). Settled by `ncu --list-chips`, `--query-metrics --devices 0` and one `--set full` run.
- The on-node DRAM read ceiling for the fleet's own nodes. Community readings run 227-246 GB/s from saturating and rotating-buffer reads, 215-229 GB/s from copy kernels and 200-214 GB/s from STREAM triad ([SM121 hardware facts](17-sm121-hardware-facts.md) §3), and 161-166 GB/s from one scalar-load probe, with ~90 GB/s from that probe while an engine serves (§3). Settled by CUDA-samples `bandwidthTest` and a saturating `float4` read kernel on an idle node, at stock clocks and under the 2,100 MHz cap, plus the same kernel beside a serving lane in a maintenance window to measure the shared-node share.
- `12.0f` vs `12.1a` vs `121-real`: speed and correctness for the same dense kernel on GB10, and which targets the deployed extensions actually carry. Partly answered in the community: no NVFP4 MoE decode difference on one workload (16.4 vs 16.3 tok/s), and one FP8 blockwise CUTLASS kernel that fails at launch as `120a` and runs as `121a` (vLLM #38484). Still open: a dense `mma.sync` kernel the fleet wrote, and whether `120f` covers the kernel that fails at `120a` (a reviewer asked; unanswered). Settled by three builds of one kernel timed in the Stage C harness, one `120f` build of CUTLASS example 87a run on GB10, and `cuobjdump --list-elf` of every deployed `.so`.
- A run-to-run determinism record for the fleet's custom kernels (cooperative MoE, E3) and a batch-invariance check. Settled by N ≥ 10 repeated launches on fixed inputs compared bitwise, and single-request vs batched outputs on the frozen harness.
- Can CuTe DSL or Triton match the hand-written ExLlamaV3 `mma.sync` kernels for EXL3 trellis decode at M = 1-8 on SM121? No source has tried. Settled by one port run through the kernel lab's oracle and Stage C.
- Do Triton's warp-specialisation passes, which run on SM12x through the Blackwell pass branch, help or hurt there? A correctness data point exists (`tl.dot` up to 128×128×64 with 4 stages passes on GB10 with zero `TCGEN` in SASS, triton PR #9852); no performance number. Settled by compiling one Triton GEMM with and without them and timing it in Stage C.
- The cluster contradiction: which cluster-scoped instructions fault on sm_121? Settled by compiling size-1 and size-2 cluster kernels for `sm_121a`, inspecting SASS for `SR_CgaCtaId`, and running them under compute-sanitizer.
- Does any cuTile kernel with `num_ctas` > 1 launch as a cluster on sm_121? Nothing published uses it there; NVIDIA's benchmarked GB10 cuTile kernels use `num_ctas=1`. Settled by building one cuTile kernel with `num_ctas=2` and `4` for base `sm_121`, checking SASS for cluster addressing, and running it under compute-sanitizer.
- Resident blocks per SM on CC 12.x: 24 (Programming Guide) or 32 (Tuning Guide)? Settled by an occupancy-API query and a launch probe with tiny blocks on GB10.
- Which `CUDA_CACHE_MAXSIZE` class (desktop/server 1 GiB or embedded 256 MiB) does GB10 fall in? Settled by filling the ComputeCache on a fresh driver and measuring where eviction starts.
- Mojo and cuTile performance on any GB10 inference kernel, measured independently. cuTile has vendor sample output only (FMHA 81.1 TFLOPS at seq 2048), and an independent sm_120 study put CuTile attention at 53% of FA2; Mojo has none. Settled by one GEMM or attention kernel in each, timed against the CUTLASS or Triton equivalent on an idle node.
- The cubin contents of the `sglang-kernel` 0.4.7 aarch64 wheel (and its CUDA version). Answered for FlashInfer: `flashinfer-jit-cache` 0.6.11+cu130 aarch64 ships an SM120 `.so` set that the maintainer describes as `120f` (flashinfer #3294), and 0.6.17 and 0.6.18.post1 carry no `121` files (jschmied recipe). Answered for vLLM: the published v0.27.1 aarch64 image has zero `sm_121` cubins (vLLM #38484). Settled for SGLang by `cuobjdump --list-elf` on each `.so` in the wheel.
- Does CuTe DSL `MmaFP8Op` compile and run correctly on GB10 with DSL ≥ 4.6? Evidence stops at 4.5.2 (segfaults), and NVIDIA reports the GB10 lowering fixed in 4.6. Settled by one `cute.compile` of an FP8 warp-MMA GEMM on GB10 with DSL ≥ 4.6, checked against an fp32 reference.
- Does FlashInfer's opt-in `fmha_v2` path (`use_fp16_qk_reduction=True`) help GB10 prefill end to end, and does any engine the fleet runs pass that flag? Only the author's kernel table exists. Settled by a grep of the engine's FlashInfer call sites, then one serving arm with the flag as the only change, TTFT at the lane's prompt lengths.
- Does CUTLASS FP4 "garbage" on SM121 reproduce on CUTLASS ≥ 4.4.2 with a matching cubin package? Settled by one per-stack oracle run of the stack's FP4 GEMM against an fp32 dequant reference.
- Can GB10 tensor cores run an MXFP4 (E8M0-scaled) GEMM correctly? No source measured one. Settled by a CuTe DSL `MmaMXF4Op` or CUTLASS block-scaled MXFP4 GEMM on `sm_121a`, checked against a dequant reference.
- Does any DeepGEMM block-FP8 call on a fleet lane land in the silent-corruption window (`K=2560`, `N ≤ 512`, or `N` 640-1,024 at `17 ≤ M ≤ 128`)? Settled by logging DeepGEMM call shapes for one request per lane and running the #54125 reproducer at those shapes.
- Does a warm Triton cache built on another architecture or toolchain miscompile on `sm_121`? Reported, not reproduced. Settled by cold-versus-warm bitwise comparison of one kernel set with a cache copied from an sm_120 or older-toolchain build.
- Does the PyTorch-bundled NCCL 2.28.9 deadlock cross-node TP on GB10 after ~30 min, as one README claims without data? Settled by `cuobjdump --list-elf` on the bundled `libnccl.so.2` and a ≥ 60 min cross-node soak with the bundled and a locally built NCCL.
- Does upstream's thin-fast stock MoE patch help the TP3 lane, and is its reported bimodal regression real on GB10? Settled by an offline extension recompile and a ≥ 30-run decode histogram against stock in one boot.
- Not carried in the body: an "independent audit" of KernelGuard-era evaluators reporting that a submission could monkey-patch `torch.cuda.Event.elapsed_time`. The source was a search capture with no URL. Settled by locating the audit and re-reading it at a pinned URL.
- Not carried in the body: a community repository's claim to be "the first sm_121 kernel on the hub" (RMSNorm/GELU on the Hugging Face kernel hub). It was not re-read and has no URL in the source list. Settled by fetching the repo at a pinned commit and checking the hub's build variants.
