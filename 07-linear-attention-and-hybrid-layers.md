## 1. What it is

A hybrid model mixes ordinary attention layers, which look back over every earlier token, with "linear attention" layers (fixed-size memory, not growing history) that squeeze everything seen so far into a small running state and update it token by token. Kimi Delta Attention (KDA, used by GLM 5.3 Flash), Gated DeltaNet (GDN, used by the Qwen 3.8 family) and Mamba-2 (used by Nemotron-3) are three variants of the same idea. Because the state does not grow with the prompt, these layers make long contexts cheap in memory, but they bring their own kernels (GPU programs that do the math), and on a GB10 those kernels are where the surprises are. Most of them are written in Triton (a Python GPU compiler), tuned on datacenter Blackwell or Hopper cards with twice the on-chip scratch memory, and gated by compute-capability checks that sometimes include SM121 and sometimes quietly exclude it. Replacing a multi-kernel Triton chain with one hand-written CUDA kernel (FlashKDA for KDA, FlashInfer for GDN prefill) is the largest measured kernel win in this area on a GB10: roughly 2.5 to 4.5 times faster per layer and about 6-7% faster prompt processing end to end. The linear-attention layers also change how prompt caching works, because a cached prefix is only reusable where the engine saved a copy of the running state: that forces chunk boundaries, can split one prompt into two full-model passes, and has been the source of silent wrong-state bugs and of an own-lane overlay that cost 9-10% of cold prefill. Getting this layer right on a GB10 is therefore about three things: running the fast kernel the build actually contains, keeping the recurrent state correct across cache hits and speculative steps, and not letting an autotuner or a patch change behaviour without a log line to prove it. See also [Prefill optimization](04-prefill-optimization.md), [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md) and [SM121 hardware facts](17-sm121-hardware-facts.md).

## 2. How each engine does it

Shared kernel libraries (used by several engines; grades apply per line).
- Shared memory ceiling. CUDA compute capability 12.x allows at most 99 KB (101,376 bytes) of shared memory per thread block and 100 KB per SM, with carve-outs 0/8/16/32/64/100 KB; CC 9.0 and 10.x allow 227 KB per block. The guide lists 12.x as one column (CUDA Programming Guide v13.4.2, compute-capability tables 31-32). [Code-verified] (vendor specification, not an achieved figure) A GB10 prints the same limit in its own error text: `OutOfResources: shared memory, Required: 147456, Hardware limit: 101376` (SGLang issue #28019; GB10, SGLang 0.5.12 images, Gemma-4-26B-A4B FP8, first scheduler forward), 101,376 bytes in an NVIDIA forum thread on SM121 CUTLASS tuning (thread 359960), and `cudaDevAttrMaxSharedMemoryPerBlockOptin = 101376` read on a GB10 in CUTLASS issue #3144, where a CUTLASS maintainer corrects the issue title's 228 KiB for SM120: "SM120 (RTX 6000, 5090, etc.) and SM121 (Spark) only support 99 KiB smem". - FlashKDA (CUDA). Two kernels: K1 token-parallel with grid N x H x chunks, K2 the head-parallel recurrence with grid N x H; chunk 16; SM80 MMA with TMA copy atoms; recurrent state held in bf16 on chip between fp32 FMA updates; sigmoid via `tanh.approx.f32`, exponent via `ex2.approx.ftz` (docs/20260420-flashkda-v1-deep-dive.md:11-60 @ 7afb9f4). [Code-verified] Upstream `setup.py` lists `["90a", "100a", "103a", "120a"]` but its `auto` mode compiles `f"{major}{minor}a"` for the visible device, `121a` on a GB10, without checking the list (setup.py:19-51 @ 7afb9f4). [Code-verified] No upstream source says a native `sm_121a` build was tested. [Interpretation] MoonshotAI's own benchmark files (T = 8,192, D = 128, 30 warm-ups, 200 iterations, 5 repeats; BENCHMARK_H20.md and BENCHMARK_GB200.md @ 7afb9f4) put FlashKDA at 1.85-2.31x over FLA `chunk_kda` on H20 and 1.70-3.27x on GB200. [Interpretation] The only SM12x number for a FlashKDA-family kernel is a training kernel: MoonshotAI FlashKDA PR #28 (open, head 96c4273c) on an RTX 5090 (sm_120a, CUDA 12.8) runs its forward at 0.88x of FLA (6.14 vs 5.42 ms at T = 8,192, H = 96), "slightly slower by design" because it keeps Aqk/Akk for the backward pass, and forward plus backward at 1.06-1.10x. - Triton autotuner. During benchmarking, a config that exceeds shared memory does not fail the boot: `_bench` catches `OutOfResources`, `CompileTimeAssertionFailure` and `PTXASError` and scores it infinitely slow; the reason prints only when `knobs.autotuning.print` is on (`TRITON_PRINT_AUTOTUNING=1`) (python/triton/runtime/autotuner.py:151, 182-188 @ bcc4d53). [Code-verified] The catch only helps while two or more configs are being benchmarked. When pruning leaves exactly one config, the autotuner caches it without benchmarking (autotuner.py:247-250); a kernel with one config runs `self.configs[0]` directly (282-283); when every config fails, `min()` over infinite timings returns the first config, which then launches (185-188). Triton's documentation says `early_config_prune` "should return at least one config" (triton.autotune API page, fetched 2026-09-23). [Code-verified] So a config over 99 KB on a GB10 drops out only when two or more configs survive pruning; single-config, default-config and all-fail paths crash. ### vLLM

KDA (GLM 5.3 Flash).
- Prefill backend. `_resolve_kda_prefill_backend` picks FlashKDA automatically when the device is CUDA with `capability.major in (9, 10, 12)`, `head_dim == 128`, the model is bf16 and the gate is bounded (`lower_bound` set); otherwise the Triton `chunk_kda_with_fused_gate` chain (models/glm5next/common/kda.py:127-150). The major-12 test admits SM121. Flag: `--kda-prefill-backend {auto,triton,flashkda,flashinfer,fused}`, written into `additional_config`; the GLM resolver raises on `flashinfer` and `fused`. A `--kda-decode-backend` flag exists, but the GLM layer never reads it (engine/arg_utils.py:1819-1833, 2679-2693). [Code-verified] Default on CC 12.1: FlashKDA, if the build contains a FlashKDA binary SM121 can run.
- The Triton chain is about ten kernels by one count and about fifteen by another (a GB10 fork README; vLLM PR #55737); the difference is whether gate cumsum, l2norm, conv and output kernels are counted, and both agree FlashKDA replaces it with two CUDA kernels. [Interpretation] It imports vendored FLA `chunk_delta_h`, `solve_tril`, `cumsum` and `l2norm` (glm5next/nvidia/ops/third_party/kda/kernels.py:15). [Code-verified]
- FlashKDA build. vLLM fetches the fork at `b59532f1`; `FLASH_KDA_SRC_DIR` overrides the source. With CUDA 13.0 or newer it builds `9.0a`, `10.0f` and `12.0f`, and the family fallback maps a `12.0f` source onto a 12.1 target; with CUDA 12.9 it builds `9.0a`, `10.0a`, `10.3a` and `12.0a` (cmake/external_projects/flashkda.cmake:25-36; cmake/utils.cmake:414-457). [Code-verified] The only SM12x entry under CUDA 12.9 is the arch-specific `12.0a`, which SM121 cannot run, and a 12.1a-only target list gets no FlashKDA at all, so a CUDA 12.9 wheel runs the Triton chain on a GB10. [Interpretation]
- FlashKDA call. The workspace is sized at init from `max_num_batched_tokens` x local heads x `max_num_seqs`; q, k, v and g are copied with `.contiguous()` on every call because FlashKDA "hardcodes dense q/k/v/g strides" (kda.py:379-397). GLM passes `None, None` for FlashKDA's checkpoint arguments (kda.py:380-397). V-split is not a vLLM setting; it is inside every fork build at or after `053de1b7` (above). [Code-verified]
- Decode and speculative verify stay on Triton `fused_recurrent_kda_fwd` with a fixed launch: `BV = min(next_pow2(V), 8)` = 8, `num_warps = 1`, `num_stages = 3`, grid (NK, NV, N·HV), no autotune (kernels.py:36-63, 98). In a step that mixes prefill and speculative tokens, FlashKDA runs the prefill part into a workspace and the outputs are scattered back (PR #55737, merged b443c1cc). [Code-verified] One decode sequence at TP3 launches 1 x 16 x 22 = 352 one-warp programs on 48 SMs. [Interpretation] Every one of the 16 V tiles per head recomputes the q/k L2 norms and the per-channel gate in FP32 over the full K = 128 (fused_recurrent.py:90-189). [Code-verified] That is the redundancy a model developer's blog says its decode tile merge removed (it reported four repeated tiles and 1.71x, with no code, shape or hardware published), and it fits vLLM PR #57585's BV 8 -> 16 gain on H20; #57585 restricts the new launch to SM90, so GB10 keeps BV 8. [Interpretation]
- Grid limit. The GLM fused-recurrent kernel put N·HV in `gridDim.z` (capped at 65,535), so GLM at TP1 (64 heads) failed CUDA-graph capture at 1,024 sequences; open PR #56974 moves it to `gridDim.x`. At TP2 or TP3 this needs 2,048+ or 2,979+ sequences. [Code-verified] Not a GB10-lane limit at current capture sizes. [Interpretation]

GDN (Qwen 3.x, Qwen 3.8 Flash Next).
- Prefill. Since PR #55715 (merged f6326f53, 2026-09-08) vLLM routes GDN prefill on the SM12x family to FlashInfer's CuTe-DSL `chunk_gated_delta_rule` when `head_k_dim == 128` and the CUDA runtime is 13 or newer; before it, SM12x used Triton/FLA. The choice is logged as `Using FlashInfer GDN prefill kernel (requested=auto, head_k_dim=128)`. Flag: `--gdn-prefill-backend triton|flashinfer|cutedsl` (model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py:93-182; arg_utils.py:1812-1833). [Code-verified]
- Decode. Default `VLLM_GDN_DECODE_KERNEL=cuda` runs the fused CUDA `fused_gdn_decode_post_conv_mtp`. It needs CC >= 8.0, a BF16 model with K = V = 128, a non-interleaved layout, SiLU/sigmoid gating, a BF16 conv cache and a BF16 or FP32 recurrent state; Qwen3-Next's interleaved layout falls back to Triton with an info log (qwen_gdn_linear_attn.py:505-560; envs.py:131, 1210-1221). [Code-verified] A hand-written single-token CUDA GDN decode (vLLM PR #39563, closed) was slower than autotuned Triton FLA on SM120 and was withdrawn by its author; batch and shape were not stated. It is a different kernel from the fused default above. [Community-measured]
- Warm-up. The GDN layer runs one T = 64 pass during profiling so the Triton autotuner picks its configs then; "all kernels including `chunk_fwd_kernel_o` now use a fixed BT = chunk_size (64)" (qwen_gdn_linear_attn.py:1054-1093, comment at 1071-1073). [Code-verified] The warm-up exists because on non-SM90 parts profiling used to return early for GDN layers, so `solve_tril`, `chunk_scaled_dot_kkt`, `chunk_gated_delta_rule_fwd_h` and `chunk_fwd_o` first autotuned on the first real request, after the KV cache was allocated, and died with a CUDA out-of-memory error that `_bench` does not catch (issue #36598, RTX 5090). [Code-verified]

- Vendored FLA on a GB10 (second pass). The vendored copy classifies a GB10 as Hopper, `is_nvidia_hopper = is_nvidia and ("NVIDIA H" in name or capability[0] >= 9)` (utils.py:151-154), so GB10's `chunk_fwd_kernel_o` autotunes warps [2, 4] and BKV [32, 64] (chunk_o.py:21-22) and never tries 8 warps. [Code-verified] With TMA on, FLA `solve_tril` made the driver reserve about 22 MiB per SM that is never freed: +3,728 MiB against +0 MiB on an RTX 5090 (170 SMs), and a KV cache of 77,552 instead of 173,968 tokens on Qwen3.5-35B-A3B GPTQ-Int4 at utilization 0.95 and 131,072 context (issue #36973; PR #37088, unmerged). [Code-verified] Its reported decode TPOT of 64 -> 35 ms on a DGX Spark (Qwen3.5-35B-A3B NVFP4) bundles the TMA and tile changes, has no protocol, and cannot come from `chunk_o`, a prefill kernel. Cache boundaries.
- `_mamba_block_aligned_split` clips every prefill chunk in `align` mode so it ends where a recurrent state can be cached. Mandatory stops: the last block-aligned position (backed off one block under EAGLE-style block drop), the prompt's partial-tail hash boundary when `mamba_partial_cache_hit` is on, and a detected shared-prefix junction. Without internal checkpoints a prompt that fits the token budget but crosses a block boundary becomes two full-model forwards; PR #56960's example splits 1,159 tokens into 1,152 + 7 (v1/core/sched/scheduler.py:405-517). [Code-verified]
- Internal checkpoints (`use_internal_checkpoint`) remove the second pass when the KV spec advertises checkpoint blocks and the chunk reaches the end of prefill; FlashKDA's checkpoint alignment is 16 tokens (layers/mamba/kda_checkpoint.py:16-17; kimi_k3/nvidia/kda.py:741-749). Wired for Kimi-K3 (PR #52789, merged 9eb9d9d3; PR #53614, merged 144e79c8, adding partial prefix caching, EAGLE rewind and KV connectors); open for GLM 5.3 Flash (PR #56960, head 7565389f). Porting it needs a FlashKDA build at or after `ee0be888`. [Code-verified]
- `--prefix-match-unit` (= hash block size) lets hits land inside a physical recurrent block; it sets matching granularity, "not how often states are stored" (config/cache.py:91-102). `use_replayssm` (Mamba-2) and `use_kda_recoverssm` (Kimi-K3 only) trade decode work for state capacity (config/cache.py:203-216). [Code-verified]
- Other knobs: `mamba_cache_mode` {none, all, align} (align is the default with prefix caching), `mamba_block_size`, `enable_mamba_shared_prefix_checkpoint`. [Code-verified] The engine also resizes the attention block to match the recurrent page and logs the size it chose (see [Prefill optimization](04-prefill-optimization.md) §2; the own Qwen 3.8 Flash Next lane logged 3,200 tokens, §4).
- Retention and speculation (second pass). On main, `prefix_cache_retention_interval` defaults to 0, which keeps only semantic checkpoints (config/cache.py:160-166; engine/arg_utils.py:559-560; PR #52216, merged 017e9f44). The dense default for Mamba or hybrid models with EAGLE or MTP exists only on `releases/v0.29.0` (PR #55760, merged 0c766af7; PR #55861, merged 74c96922). Main carries two other fixes instead, PR #53945 (merged 263c4ff9; caches the Mamba state at the block-grid position) and PR #54713 (merged b28c3e15; retains both replay boundaries), and `disable_eagle_block_drop` turns off the trailing prefix-cache block drop (config/speculative.py:453; PR #53388, merged 481839ad). With plain MTP there is no draft KV group, so the coordinator's fallback flags every group as EAGLE (v1/core/kv_cache_coordinator.py:110); replay boundaries then collapse to 0 and nothing is inserted. [Code-verified] Lost first-repeat hits under speculation therefore have a two-stage history: sparse retention on 0.26-0.28 nightlies, fixed on main by #53945 and #54713 (issue #53504, closed as resolved on main; the reporter's 2x RTX 5090 retest hit about 36% on the first repeat, about 71% with `disable_eagle_block_drop`, ~3.1K prompt, n = 1); then, on a 2026-09-17 nightly, the coordinator fallback, which `disable_eagle_block_drop: true` bypasses. Both stages come from EAGLE's trailing-block drop. GB10 numbers for both are in §4. [Interpretation]
- Partial hits and where the align checkpoint lands. The coordinator shrinks a candidate hit until every group covers it, so a recurrent-state miss limits the full-attention hit (RFC #45702, closed; PR #46384, merged 481e481b). `enable_mamba_shared_prefix_checkpoint` (default off) needs align mode, EAGLE on the Mamba group and a `prefix_match_unit` smaller than the Mamba block (config/cache.py:199-204). [Code-verified] When the align checkpoint lands inside request-unique tokens (`floor((len - 1) / block) * block > shared_prefix_len`), hits fell from 52/64 to 0/64 and TTFT rose from 433 to 905 ms (issue #45238, open; Qwen3.5-4B, block 528, one GPU, concurrency 1, prompts of about 2,200 tokens); with the Marconi-style admission policy (PR #37898, merged dc66e01a) the unlucky case recovered to 40/64 at 658 ms. [Community-measured] (not GB10) A rule that non-final align chunks must end on a block boundary came from PR #47861, which closed unmerged. [Code-verified]
- `all` mode is deprecated on main (config/cache.py:341-350). [Code-verified] On an L40S (Qwen3.5-9B W4A16, mean input 2,000 tokens, 5 prefixes, 500 requests per level), stock `align` beat the faster of two open `all` implementations by 1.03 / 1.21 / 1.37x requests per second at concurrency 2 / 5 / 10, and both `all` PRs crashed with a shape mismatch at concurrency 2 and above (PR #26807 thread). [Community-measured] (not GB10) The GB10 `all`-mode datum is in §4.
- Exporting recurrent state off the GPU. LMCache's hybrid-model page (docs/source/mp/hybrid_models.rst @ 5f3c55f4) says: recurrent state is stored as an opaque page; `--separate-object-groups` is required; the chunk size must be the unified block size N or a multiple of it; `--max-num-batched-tokens` in [N, 2N) snapshots every block, while 2N or more snapshots only each step's last block and is allowed only with separate object groups; cached and fresh GDN outputs are "not bit-exact" because GDN backends do not support vLLM's batch-invariant mode; published N is 784 for Qwen3.6-27B and Qwen3.8-27B, 544 for Qwen3.5-0.8B, 944 for Kimi-Linear-48B on 2 GPUs and 768 for Kimi-K3 on 8. [Interpretation] (documentation text) N is model-specific: a GB10 TP2 Qwen3-Coder-Next boot logged "Setting attention block size to 544 tokens" (issue #33857, vLLM 0.16.0rc1), so read N from the boot log. [Community-measured] One field report on 2x RTX 3090 (TP2, Qwen3.8-27B AWQ INT4; vLLM 0.28.0 with PRs #54165 and #50885, LMCache 0.5.4rc5) restored a 20-28K prefix in 300-500 ms across restarts (uraniumchonk, vllm-hybrid-mamba-notes @ 405cf4e2). [Community-measured] (not GB10)
- A stale-state bug class. A new request given one token under an exhausted token budget was classified as decode and read a finished request's recurrent slot, giving confident gibberish on about one prompt in a thousand in a reinforcement-learning pipeline; the reporters made it reproduce by lowering `gpu_memory_utilization` from 0.9 to 0.2 and found it with a vLLM-against-transformers log-prob diff on identical token sequences; PR #32118 (merged 8fb2c135) fixed it (AI21 engineering blog, 2026-01-29, fetched 2026-09-23). [Community-measured]

KDA or GDN prefill goes to its vendored FLA Triton `chunk_kda` / `chunk_gated_delta_rule` when `seqlen >= num_v_heads` and no history is needed, looping one sequence at a time from Python; everything else goes to its CUDA recurrent kernel `ext.cuda_recurrent_gated_delta_rule`, with a channel-wise variant for KDA (modules/gated_delta_net_fn/gated_delta_rule.py:100-225). Its vendored FLA keeps the Blackwell 2-warp `fwd_h` guard and the shared-memory-gated stages (vendor/fla/chunk_delta_h.py:15-45; utils.py:51). It has no FlashKDA path, and no FLA config-pinning layer: plain `triton.autotune` with `cache_results=True`, relying on Triton's disk cache (vendor/fla/utils.py:29-31). [Code-verified] No SM121 measurement of the native path was found.
- Second pass: no new source for ExLlamaV3; the follow-up search found none either.

## 3. What is different on GB10 / SM121

- [Code-verified] 99 KB of shared memory per block, against 227 KB on Hopper and datacenter Blackwell (vendor specification); GB10 error text prints `Hardware limit: 101376` [Community-measured]. FLA's tile heuristics fall to their small-tile lists on a GB10. A Triton config over the limit drops out only when several configs are benchmarked; a pinned, default or sole surviving config launches and crashes (§2). [Interpretation] No source lists which linear-attention configs actually drop out on `sm_121a` (§8).
- [Interpretation] 48 SMs changes FlashKDA's parallelism. K2 launches N x H CTAs: 22 for one sequence at TP3 and 32 at TP2, fewer than the SM count. The fork's automatic V-split (`2·H·N <= num_SMs`) fires for single-sequence prefill at TP3 and never at TP2. The own lane's `b5d11010` build predates it.
- [Code-verified] Arch-specific binaries do not transfer from 12.0 to 12.1. A GB10 runs FlashKDA only from a CUDA 13 family (`12.0f`) build; vLLM's CUDA 12.9 build list has only `12.0a`. The own lane's installed extension carries `sm_90a`, `sm_100` and `sm_120` cubins and no PTX, and runs on SM121 through the family target (§4).
- [Community-measured] One GB10 report (CUDA 13.0, vLLM PR #38957 comment) links `12.0f`-only cubins to CUTLASS `can_implement()` failures in scaled-mm, MoE-data and MLA kernels; a maintainer disputed that this is a feature gate and asked for a retest that never came, so it is unresolved. FlashInfer's CUDA 13 AArch64 jit-cache wheels likewise ship SM120 family cubins, not native SM121a ones (v0.6.18 release notes, documentation text). [Interpretation]
- [Code-verified] vLLM's vendored FLA treats a GB10 as Hopper (`capability[0] >= 9`): `chunk_o` autotunes 2 and 4 warps only, and the TMA path stays off unless `FLA_USE_TMA=1`. With TMA on, SM12x loses about 22 MiB of driver memory per SM that is never freed [Community-measured, RTX 5090]; the only GB10 figure (+1,077 MiB) is stated without a log.
- [Community-measured] Triton toolchain: 3.5.x needs a CUDA 13 `ptxas` for `sm_121a`; 3.6 and newer compile sm_121 with no environment variables, and `TRITON_PTXAS_PATH` does nothing for Blackwell targets there. `TRITON_OVERRIDE_ARCH=sm120` on a GB10 splits the IR and `ptxas` targets and fails.
- [Code-verified] Several fast paths stop at 12.0 or require tcgen05: FlashInfer's SM120 KDA prefill (exactly 12.0), FlashInfer's CuTe/Cake KDA prefill (10.0 and 10.3), FlashInfer `SSDCombined` for Mamba-2 (majors 10 and 11), FLA's FlashQLA GDN backend (exactly 12.0), SGLang's CuTe-DSL and nvidia_kda KDA backends (SM100) and ptx_kda (SM103). FlashInfer's fused GDN decode registry (cc 120 rows only, exact match) and the CUDA KDA/GDN projects cuLA and INT21 (SM90 and SM10x only) also exclude a GB10. On a GB10 the remaining fast paths are FlashKDA (KDA prefill, vLLM and SGLang), FlashInfer GDN prefill (vLLM since f6326f53, with FlashInfer's #3960 sm_121a compile fix) and vLLM's fused CUDA GDN decode; outside the engines, a community TileLang port of FlashQLA and the llama.cpp-dgx chunked kernel also run on a GB10 [Community-measured].
- [Code-verified] Engines disagree on the SM12x GDN prefill default: vLLM admits the SM12x family (CUDA >= 13, head_k_dim 128); SGLang does not (majors 9 and 10 only), and its open SM120 PR requires an fp32 state pool.
- [Interpretation] The Blackwell `tl.dot` recurrence race is unproven on SM12x either way. FLA's guards cover major 12, every reproduction is on sm_100, sm_103, B300 or GB300, the linked Triton compiler bug sits in a TMEM-hoisting pass that targets tcgen05 hardware SM12x lacks, vLLM's vendored FLA still offers the racy w4/s2 and w4/s3 configs, and SGLang pins BV 32 / w4 / s2, which FLA #945 marks racy on sm_103. At the SASS level a GB10 check found Triton's `tcgen05` PTX lowered to HMMA with no TCGEN instructions (Triton PR #9852) [Community-measured], so the hardware the bug is tied to is absent while the IR passes still run; mamba_ssm's Mamba-3 SISO `num_stages == 1` gate for majors 10 and 12 is a second precautionary SM12x gate with no SM12x repro.
- [Community-measured] A community GB10 recipe reports that vLLM enables PDL (programmatic dependent launch) for CC >= 9, SM121 included, in the Triton kernels that carry KDA state, and gates it off on SM12x (tonyd2wild GLM 5.3 Flash NVFP4 recipe); one SM120 x86 report found KDA chunk-state return numerically broken (closed without resolution).
- [Community-measured] DeepGEMM is admitted on sm_121; the #54125 `profile_run` crash was a skipped UE8M0 repack fixed upstream (`f8e0602713`); FP32-scale mis-selection and a K = 2560 silent-corruption window remain (see [GEMM backends](09-gemm-backends-and-quant-formats.md) §7). The TF32 mHC pre-norm GEMM variant runs without a fault on the own GLM TP3 lane [Historical diagnostic]; no source checks that GEMM's precision.
- [Measured] Unified memory: on one GB10, prefill CUDA-graph capture of the Triton GDN kernel at a 32,768-token chunk with a 0.90 memory fraction hit OOM inside `chunk_gated_delta_rule` (830 MB free). Linear-attention graph capture allocates outside the static pool. [Interpretation]
- [Community-measured] Long-run stability is not settled on GB10 hybrids. vLLM issue #37431 began as a Mamba-2 illegal-instruction report (vLLM 0.17.2rc1, Triton 3.6.0) and is now the main GB10 thread for long-run Mamba-2 and GDN crashes and wedges; the async illegal-instruction symptom narrowed by 0.22.1 but the thread is open, TP1 and TP2 GB10 reports on a GDN hybrid show wedges 9-72 h apart that piecewise graphs and `cudagraph_mode: NONE` did not fix, and one py-spy capture places a hang inside the Triton/FLA GDN chunked-prefill kernel on a 13-token tail resuming a prefix-cache state.
- [Interpretation] The FLOP share of the linear-attention layers is a poor guide to their time on a GB10: KDA is about 33% of GLM prefill FLOPs by roofline but 3-6% of profiled kernel time (§4), because its chunk math is small matrices next to the MoE and projection GEMMs. Kernel speedups shrink the same way end to end: a 2.76x TileLang GDN prefill kernel moved Qwen3.6-27B TTFT by about 3% at 8K, and a 9.5x chunked GDN kernel left llama.cpp prefill at parity with GDN at 1-2% of the total [Community-measured]; set against the ~9% GDN share at 32K implied by vLLM PR #55715, the GDN time share grows with context length [Interpretation]. On SM120 a chunked GDN op ran at about 1% of tensor peak, latency- and occupancy-bound [Community-measured].
- [Community-measured] Hybrid prefix caching with MTP on a GB10 loses first-repeat hits by default on recent vLLM nightlies, first through sparse retention and then through the coordinator treating every group as EAGLE; one flag (`disable_eagle_block_drop: true`) restored 50.1% hits and cut TTFT from 3.9 to 1.6 s (§4). Cached and fresh greedy outputs diverged on 6 of 6 prompts in one GB10 test, which the tester put down to batch-shape numerics, and LMCache documents GDN output as not bit-exact, so hit counters and score-level checks, not token equality, are the gate. [Interpretation]

## 5. Levers, ranked

1. **Run the fused CUDA KDA prefill kernel (FlashKDA) on KDA models, and prove it is running** — applies to: vLLM (auto on major 12 with a CUDA 13 `12.0f` build) and vLLM + EXL3 x GLM 5.3 Flash (Kimi-class KDA in principle) x TP2/TP3; SGLang only for batches whose sequences are all 64-2,048 tokens. Gain: kernel 3.33x at 2,048 tokens dense, 2.55x at production shape with copies charged, +6.5% sustained prefill and -5.1% TTFT at 7K end to end on a GB10 TP3 fork [Community-measured]; the own lane's profile shows 0.714 ms per 2,048-token layer call, matching the fork's 0.673 ms dense figure, and the whole KDA family at about 3% of summed kernel time against about 6% for the Triton chain on the upstream TP2 profile [Historical diagnostic] [Community-measured]; datacenter reference -7.9% to -13.2% TTFT on 4 x GB300 TP4 and 183 -> 49 µs per layer at 8 x 2,048 on a GB300 micro-benchmark [Community-measured]. Contested (C3): the fork's matched single-flag boots are the better evidence for the kernel's effect; the own bundle (-8.92% at 7.6K, +3.47% at 95K) cannot attribute anything to FlashKDA; do not average. SGLang's 64-2,048 window is a head-count- and batch-dependent crossover taken from datacenter tables (PR #29472: 1.24-1.27x at 2,048 on H20-3e and B200, 0.73x at B = 1, H = 16, 8K on H20), never measured on a GB10 with the stock package SGLang calls; the GB10 fork ratios (3.31x at 4K, 3.52x at 8K, 22 heads) suggest the cap leaves speed unused there [Interpretation] (§8). Cost: a CUDA 13 build (a CUDA 12.9 wheel silently runs Triton on a GB10); one shared workspace of 109.57 MiB at 4,096 tokens, 8 sequences and 22 heads (61.45 MiB at 2,048 tokens and 8 sequences on the fork) plus transient q/k/v copies up to 66 MiB. Risk: a patch that silently does nothing (§7); workspace capacity is not checked in the pinned C++ wrapper, so oversized token or sequence counts must be rejected before launch, and `lower_bound=None` passed when `safe_gate` is off [Code-verified]; NaN on extreme gates before fork commit `3b225bf2` (§7). Smallest falsifying experiment: two boots one flag apart (`--kda-prefill-backend triton` vs `flashkda`), backend log line confirmed on every rank (dispatch lines: [Engine dispatch maps](16-engine-dispatch-maps.md)), 24 fresh ~7K prompts and a 95K cold x 5; the lever fails if sustained prefill does not beat Triton by more than the run spread.
2. **Upgrade the FlashKDA build to the fork tag vLLM main fetches (`b59532f1`)** — applies to: vLLM lanes on fork builds older than `053de1b7` x GLM 5.3 Flash x TP3 most (the automatic V-split targets exactly 22 heads, 48 SMs, one sequence); TP2 gets the fixes but never the split. Gain on a GB10: unknown [Proposed]. Evidence for the parts: V-split 1.216-1.263x (B300) and 1.266-1.358x (H100) at 12 heads with the split forced, 0.835-0.947x at 96 heads [Community-measured, not GB10]; the proxy-fence fix removes an empty-varlen-sequence path where "stale smem could be written to final_state" and the inverse fix removes a NaN on a synthetic T = 16,384, gate -12, beta 8 input at +0.72% to +1.99% kernel time on unstated hardware [Code-verified]; checkpoint export (+4.37% kernel time for one checkpoint, +5.17% for two over 0.078 ms, GB300, shape unstated) is the prerequisite for lever 6 [Community-measured]. Cost: rebuild plus the ABI change (the own lane's 14-argument ABI has no checkpoint arguments). Risk: V-split cannot be toggled at runtime; an A/B needs two builds or a patched `use_vsplit` heuristic. Smallest falsifying experiment: the fork's `bench_fwd` protocol (CUDA graphs, L2 scrub, 30 warm-ups, 200 iterations, 6 repeats, alternating order) on an idle GB10 at 22 and 32 heads, N = 1, 2, 4, 8, 512-8,192 tokens, old vs new build, with bitwise output-and-state parity; the lever fails for speed if N = 1 at 22 heads is not faster beyond the repeat spread (it still carries the correctness fixes).
3. **Route GDN prefill to FlashInfer on Qwen-family hybrids** — applies to: vLLM builds at or after f6326f53 with CUDA >= 13 and `head_k_dim` 128 (automatic); SGLang only through an explicit `--linear-attn-prefill-backend` choice or PR #36357, and even then only with an fp32 state pool, so bf16-state lanes stay on Triton. Gain: kernel 3.83x-4.52x from 1,024 to 8,192 tokens and TTFT -7.2% (c1) / -7.4% (c4) at 32K on one GB10 [Community-measured]; +8.7% prefill throughput on an SM120 RTX PRO 5000 with a bf16 pool the PR's own gate rejects [Community-measured, not GB10]. Kernel gains shrink with shorter prompts: a community TileLang GDN port measured 2.76x at kernel level on a GB10 but about 3% of TTFT at 8K on Qwen3.6-27B [Community-measured], against -7.2% at 32K for the FlashInfer path, so the lever pays mostly on long prompts [Interpretation]. The port is an option only for vLLM builds older than #55715, and it patches that older selector. Cost: ~4.2 s of JIT on the first sight of each new prefill shape (measured on SM120); the SGLang state-dtype conflict (issue #36532, confirmed on SM120 by issue #36701); a FlashInfer build that contains #3960 (merged 3caf5d2b), the sm_121a CuTe-DSL compile fix. Risk: numerics (final-state max abs up to 0.00477 against Triton); JIT during serving. Smallest falsifying experiment: both arms in one process on one node as in PR #55715, then two boots with `--gdn-prefill-backend triton` vs `flashinfer` at ISL 32,768 x 3 with the log line checked; the lever fails if TTFT does not drop by more than the A-B-A TTFT spread (0.3-0.4% on a GB10 pair).
4. **Large-M BF16 GEMM for the weight-only-quantized KDA input projection** — applies to: vLLM + EXL3/Marlin GLM 5.3 Flash lanes x TP2/TP3 (no upstream vLLM switch). Gain: +7.20% at 7.6K and +7.93% at 95K as a group, component 2.17-2.25x at M = 2,048 [Measured]; TTFT -11.4% at 16K and -12.3% at 100K on a TP2 port [Community-measured]. Cost: +2.264 GiB per rank (TP3), +3.26 GiB per rank (TP2). Risk: numerics (rel-RMSE <= 0.004), boundary choice: M > 512 is the only qualified value, and an analytic one-point crossover sits near M 129 [Interpretation]. Smallest falsifying experiment: boundary sweep at M = 64, 128, 256, 512, 1,024, 2,048 on the lane's per-rank N, then 5 matched cold samples at 7.6K and 95K for the best boundary. See [GEMM backends and quant formats](09-gemm-backends-and-quant-formats.md).
5. **Restore hybrid prefix-cache hits under speculation (second pass)** — applies to: vLLM GDN and KDA hybrids with MTP or EAGLE-style drafting and prefix caching in `align` mode, any topology; builds from the 0.26-0.28 nightlies onward. Gain: on 2 GB10 at TP2 (Qwen3.8-Flash-Next NVFP4, MTP 3, 19,839-token prompt) the first repeat went from 8.2 s with no hit to 2.6 s with `--prefix-cache-retention-interval 3200` and 1.6 s with `disable_eagle_block_drop`; on a 2026-09-17 nightly, `disable_eagle_block_drop: true` took hits from 0 to 50.1% and TTFT from 3.9 to 1.6 s on a 4,137-token repeat [Community-measured]. Which switch applies depends on the build: sparse retention bites on builds with PR #52216 but without #53945 and #54713; the coordinator fallback bites on current nightlies under plain MTP [Code-verified]; the v0.29.0 release branch sets dense retention by default for these models (#55760, #55861). Cost: one flag; dense retention stores more recurrent checkpoints, and the trailing-block drop exists for EAGLE-style drafters, so its effect on draft acceptance after a hit, measured in neither report, belongs in the A/B [Interpretation]. Risk: cached and fresh greedy outputs diverged on 6 of 6 prompts in the GB10 test (batch-shape numerics per the tester), so this must be gated on scores, not token equality; lanes that run their own hybrid prefix-hit overlays may already hit, so read the counter before changing anything. Prefix caching is on [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md); drafters on [Speculative decoding](02-speculative-decoding.md). Smallest falsifying experiment: on the lane's own engine build, three boots (default, retention = block size, `disable_eagle_block_drop: true`), the same long prompt sent twice per boot, `prefix_cache_hits_total` and TTFT on the first repeat, plus a score-level comparison of cached against cache-off output; the lever fails if the default already hits.
6. **Remove the doubled forward at recurrent-state boundaries: internal KDA prefill checkpoints** — applies to: vLLM hybrids with prefix caching in `align` mode x GLM 5.3 Flash (open PR #56960), Kimi-K3 (merged) x any topology. Gain on a GB10: unknown [Proposed]; Kimi-K3 TP8 TTFT -9.4 / -25.5 / -20.7% at concurrency 1 / 4 / 16 (guidellm 8K/1K) and, with partial hits, recomputed tokens per incremental request -49.8% and incremental P50 TTFT -25.6% with cold TTFT -0.44% [Community-measured, not GB10]; on GLM TP4 cached-token counts were identical and "we save one step" [Community-measured]. The own TP2 follow-up turns paid ~6 s instead of ~0.6 s for the trailing partial page [Measured]. Cost: a FlashKDA build at or after `ee0be888`, cache-manager, hashing, eviction and speculative-rollback work (multi-week). Risk: state-checkpoint correctness (§7 lists silent wrong-state bugs in this exact area). Smallest falsifying experiment: first count prefill steps per request against ceil(len / LPT) over the frozen prefill manifest (no traffic change), then the multi-turn follow-up fixture before and after; the lever fails if follow-up TTFT does not approach the exact-hit ~0.6 s.
7. **Re-measure every hybrid cache-boundary overlay per TP geometry, and keep the one that pays** — applies to: vLLM + EXL3 GLM lanes (TP2 page 3,584, TP3 page 2,560). Gain: removing the align-chunking overlay restored 9-10% cold prefill at 95K on TP3 [Measured]; the same overlay was reported +0.34% on TP2 [Community-measured]. The upstream `tail_boundary` stop cannot explain the TP3 cost because the lane runs with partial hits off [Code-verified]; the cost must come from the overlay's own stops, which is unmeasured [Interpretation]. Cost: the overlay's correctness benefit (checkpoint alignment for prefix-cache resumes) is given up, and it was never measured. Risk: a silent wrong-state resume. Smallest falsifying experiment: overlay off vs on in the same session, frozen manifest at 7.6K and 95K x 5, plus exact-repeat and prefix-resume outputs compared with a cache-off run.
8. **Size recurrent-state pools explicitly and pick the state dtype** — applies to: SGLang GDN and KDA hybrids with speculation (5 slots per request with `extra_buffer`), vLLM Qwen Flash Next. Gain: +75% aggregate at c8/c12 on a two-GB10 GLM NVFP4 pair from 10 -> 40 slots with bf16 state [Community-measured]; own pools silently capped 5 -> 2, 10 -> 8, 8 -> 6 requests [Measured]; bf16 SSM cache +6.8% C1 / +8.5% C8 on one GB10 for Qwen 3.8 Flash Next and float32 3% slower than bf16 on Qwen 3.8 27B [Community-measured]. Cost: memory (153.9 MB fp32 or 78.4 MB bf16 per slot for Qwen 3.8 27B; the K16 draft block doubled the intermediate allocation to ~7.88 GB) [Measured]; about -6% single stream from lower acceptance at higher concurrency [Community-measured]. Risk: a swapless GB10 wedged when the KV and state pools left 6.9 GiB free [Measured] (memory: [Memory on unified memory](11-memory-on-unified-memory.md); slot counts and concurrency: [Serving agent workloads](22-serving-agent-workloads.md)); bf16 state blocks SGLang's SM120 FlashInfer GDN prefill path (lever 3). Second pass: SGLang's `compute-mamba-ratio` skill gives the sizing rule, r* = (S + D) x token_equiv x dcp_size / L with L the average context per request, or pin `--max-mamba-cache-size` = target concurrency x S [Code-verified]; a single-GB10 Qwen 3.8 Flash Next recipe needs 110.11 MB per request and fails at `--mem-fraction-static 0.72` [Community-measured]; on that recipe, bf16 SSM state (41.3 tok/s) sat inside the baseline range (41.1-43.2) at one stream under SGLang [Community-measured]. That does not contradict the vLLM +6.8% C1 / +8.5% C8 figure (different engine, concurrency and measurement); keep both, and expect the dtype to matter through capacity and concurrency more than single-stream speed [Interpretation]. Smallest falsifying experiment: boot with `--max-mamba-cache-size` = requests x slots, grep the capped `max_running_requests`, run C1/C4/C8 x 3 in bf16 and fp32; the lever fails if the capped value does not rise or C8 does not beat the spread.
9. **Chunk size on GDN hybrids** — applies to: SGLang x Qwen 3.8 27B x one node (measured); any GDN hybrid in principle. Gain: 8,192 -> 2,048 cut cold TTFT 20% at 30K and 16% at 94K, decode flat [Measured, screen]. Cost: 5-stream aggregate -5% to -8% [Measured]. Risk: a larger chunk plus prefill graphs OOMs inside the Triton GDN kernel on unified memory (§7). Smallest falsifying experiment: a repeated combined comparison at 2,048 / 4,096 / 8,192, cold 30K and 94K x 3 and C5 x 3, one arm per boot. See [Prefill optimization](04-prefill-optimization.md).
10. **Pin linear-attention autotune results instead of redrawing them** — applies to: vLLM (preserve `TRITON_CACHE_DIR`; `TRITON_CACHE_AUTOTUNING=1` is the default), SGLang (`SGLANG_GDN_CHUNK_H_*`), upstream FLA (`FLA_CACHE_MODE` + JSON), ExLlamaV3 native (Triton `cache_results`). Gain: reproducibility and correctness rather than speed: redraws on the own Qwen lane changed 20-23 of 36 entries with no repeatable single-stream win [Measured]; a tuned Triton launch table halved a sparse-attention micro-kernel at 8 rows but moved serving by nothing measurable at 1-5 streams [Measured]. Cost: a warm-up at production shapes (vLLM's GDN warm-up runs at T = 64, and autotune keys omit T). Risk: autotuning an in-place state kernel on the live pool corrupts it silently (SGLang's source comment) [Code-verified]. Pinning makes the single-config path the live one: Triton caches a sole surviving config without benchmarking, so a pinned config that does not fit crashes instead of dropping out; check each config's shared-memory estimate against 101,376 bytes before pinning [Code-verified]. Device-named configs: SGLang PR #28077 (closed unmerged) measured a Gemma-4 FP8 MoE config tuned on an RTX PRO 6000 Max-Q at 1.02 / 1.12 / 1.04x over the clamped default at M = 64 / 256 / 2,048, bit-identical, on Triton 3.6.0; the device name in the filename keeps an SM120 file from applying to "NVIDIA GB10" [Community-measured, not GB10]. Do not adopt vLLM PR #37700's head on a GB10 untested: it would re-add the 8-warp BK = BV = 128 `chunk_o` config FLA removed on majors 10 and 12 for correctness, and its speed claim has no protocol (§8). Smallest falsifying experiment: boot twice with `TRITON_PRINT_AUTOTUNING=1` from boot and a wiped cache, diff the chosen configs per kernel; if they never differ, pinning buys nothing on that lane.
11. **Decode-side KDA kernel launch and tile work** — applies to: vLLM `fused_recurrent_kda` (BV 8, 1 warp, 3 stages on every non-SM90 part) x GLM 5.3 Flash x speculative decode. Cost: a kernel patch on the lane image. Risk: state correctness under speculation. Smallest falsifying experiment: an off-lane micro-benchmark of `fused_recurrent_kda` at 22 heads, N = 1-8, T = 1 and T = k + 1, BV 8 vs 16, bitwise output and state; the lever fails if no BV beats 8 on a GB10.
12. **Mixed-batch KDA copy removal (the vLLM #56159 technique) and FlashKDA q/k/v copy removal** — applies to: vLLM GLM lanes with fair mixed prefill (mixed speculative and non-speculative steps are routine). ## 6. Protocol

This is the protocol for swapping, upgrading or re-tuning a linear-attention kernel, or changing a hybrid cache-boundary rule, on a GB10 lane. It follows the fleet rules on the entry page and the incidents in §4 and §7. See [Profiling protocol](14-profiling-protocol.md) for kernel attribution and [Quality and correctness gates](21-quality-and-correctness-gates.md) for output gates.

Preconditions.
- All index rules apply (see [the entry page](README.md)), in particular: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor measured after the longest qualified prefill, and traffic stopped below 4 GiB; a greedy logprob probe after every relaunch; discard the first request and warm every serving shape before timing; a unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection or configuration line read on every rank; at least 3 repetitions with a closing baseline (A/B/A); MemAvailable sampled every 1-2 s with zero NV_ERR_NO_MEMORY or Xid lines; no reboot or power cycle without per-node permission; correctness gates from [Quality and correctness gates](21-quality-and-correctness-gates.md) before any speed number. For this page: check for a rank latched at a low clock (see [Clocks, thermal, and power](13-clocks-thermal-power.md)) and warm every prefill shape, since first-sight JIT and autotune distort the first pass.
- No memory overcommit: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor while serving, KV pin raises of no more than 1.5 GiB per boot, and memory freed by one change never spent in the same boot. Stop all benchmark traffic at 4 GiB MemAvailable on any node. Swap is not headroom. Keep at least 15 GiB of cushion when sizing KV plus recurrent-state pools on a swapless node (§7).
- Clean window: no outside traffic; poll running requests before each pass and discard any pass that overlaps outside traffic.
- One variable per boot. A restart for an A/B skips the image pull, so the only difference is the variable under test. A FlashKDA upgrade is one variable (the build), even though it carries several commits; say so in the packet.
- Never restart a client gateway; restarting the lane's engine is the operator's step, and a gateway restart is the operator's decision. Never `pkill -f` a pattern that also matches your own shell.
- Toolchain receipt (second pass): Triton version (3.6 or newer compiles sm_121 with no `ptxas` variables; on 3.5.x use the CUDA 13 `ptxas` recipe), `TRITON_OVERRIDE_ARCH` unset, `FLA_USE_TMA` unset, one Triton cache directory per SKU and per arm. After any toolchain change, force one recompile (`TRITON_ALWAYS_COMPILE=1`) before trusting a persisted autotune cache, because a cross-architecture stale-cache miscompile has been claimed and not ruled out (§8).
- Build receipt: engine commit; FlashKDA tag and whether it is at or after `053de1b7` (automatic V-split), `3b225bf2` (inverse fix), `ee0be888` (checkpoint export); CUDA version of the build (13 or newer for a `12.0f` family binary); FlashInfer and Triton versions; the linear-attention PRs present (vLLM #55715, #55737, #56960, #54163, #55601, #51508, #56531; SGLang #36357, #32024); the prefix-cache retention and block-drop fixes present (vLLM #52216, #53945, #54713, #53388, or the v0.29.0 branch defaults #55760 and #55861); whether the FlashInfer build contains #3960.
- Engine-init receipt, read, never derived: block size, hash block size, partial-cache-hit flag, long-prefill threshold, token budget, `mamba_cache_mode`, the "Setting attention block size" line, the resolved `prefix_cache_retention_interval` and `disable_eagle_block_drop` values, state-pool size and the capped `max_running_requests` (SGLang). A source-derived step sequence was wrong once (§7).

Change. Exactly one of: prefill or decode backend (`--kda-prefill-backend`, `--gdn-prefill-backend`, `VLLM_GDN_DECODE_KERNEL`, `--linear-attn-*-backend`, `FLA_FLASH_KDA`), a kernel build, a launch or autotune config, the state dtype, the state-pool size, a cache-boundary overlay, the chunk size, a prefix-cache retention or block-drop setting.

Run.
1. Off-lane parity, before anything touches a serving engine. A model-free test at production shapes: strided q/k/v, varlen batches including an empty sequence, 22 and 32 heads, bf16 inputs, FP32 state, the model's `lower_bound` (-5 on GLM 5.3 Flash), lengths from 1 to 16,384, and the synthetic T = 16,384, gate -12, beta 8 input. Clone every input so the reference cannot mutate the fixture. Compare output and final recurrent state, bitwise where the PR claims bitwise, otherwise at a tolerance fixed in advance. Never relax a tolerance to pass. Compare against the incumbent kernel numerically, never by shape alone: a transposed recurrent-state layout passes shape checks when K = V = 128, and a TileLang `gemm_v1(transpose_B=True)` ran about 50% off in magnitude on SM120/121 without an error. Add the adversarial gates of arXiv:2608.12700 (NaN and Inf propagation, run-to-run determinism, shape changes, fp16 against fp32 accumulation; several are tolerance-free), which found 39.5% of 2,638 harness-accepted generated kernels broken [Community-measured]. For state-slot bugs that surface once in a thousand requests, add a log-prob diff against a reference implementation on identical token sequences, including a run at deliberately low memory utilization to force slot reuse.
2. Micro-benchmark on an idle node or during a scheduled lane pause: CUDA graphs, L2 scrub, 30 warm-ups, 200 iterations, 6 repeats, alternating arm order, at 512 / 1,024 / 2,048 / 4,096 / 8,192 tokens and N = 1, 2, 4, 8, with any layout copies the serving path needs charged to the kernel. For a V-split question this is two builds (or a patched heuristic): there is no runtime flag.
3. Autotune capture: boot with `TRITON_PRINT_AUTOTUNING=1` set from boot (vLLM's JIT monitor turns printing on only after warm-up) and save the chosen config per kernel; keep one Triton cache directory per arm; run serving arms with `--jit-monitor-mode error` so any compile or autotune during serving fails the arm. Never run a multi-config autotune of an in-place state kernel against the live state pool. Before pinning, or for any kernel with a single or default config, estimate each config's shared memory and prune anything over 101,376 bytes before benchmarking (the vLLM PR #43047 pattern); a sole surviving or default config is launched without benchmarking and crashes.
4. Boot one arm per flag and confirm the backend on every rank from the log: vLLM "Using FlashInfer GDN prefill kernel (requested=..., head_k_dim=...)", FLA `[FLA Backend] kda.chunk_kda -> flash_kda`, SGLang "Defaulting SM... GDN prefill backend", or the patch's own per-process line. A boot with no such line is a boot where the change did not run.
5. Serving A-B-A through the frozen harness with a same-session restore: cold-nonce prompts at 7.6K and 95K (or 8K, 32K and 100K) x 5 with 8-token output; exact repeats; a prefix-resume case; hybrid-hit outputs compared with a cache-off run; short decode fixtures x 3. Read TTFT and effective prefill for the few-percent decision; decode needs a larger effect (§4: 6-7% A-B-A spread on a GB10 pair). For hybrid prefix caching, read the engine's hit counter (`prefix_cache_hits_total` in vLLM) on every exact repeat and judge cached-versus-fresh output with a score-level check, since GDN outputs are not bit-exact across batch shapes.
6. For cache-boundary changes, also log prefill steps per request against ceil(len / LPT) over the manifest, and re-run the whole arm on every TP geometry the lane uses.
7. Watch memory at 1 s resolution on every node through the longest prompt; record the NVIDIA allocation-error and Xid counts.

Record (packet fields): build and engine-init receipts; the one variable and its two values; topology, heads per rank, slots; parity results (cases, max abs, output and state); micro-benchmark per length and N with spread; chosen autotune configs per kernel and whether any JIT event fired in serving; per depth prompt tokens, TTFT, effective prefill, repetition spread (n and range), cached tokens and hit-counter deltas on repeat; follow-up TTFT; short-decode tok/s; KV and state-pool capacity; minimum MemAvailable per node; Xid and allocation-error counts; discarded passes and why. Profiler runs are recorded separately and never scored.

Pass gate. Parity passes at the fixed tolerance, including state. Micro-benchmark wins beyond its repeat spread at the lane's shapes. Serving prefill at or above baseline beyond the noise floor (±2% for whole-context prefill within one boot on the own harness, per the [Prefill optimization](04-prefill-optimization.md) protocol; 0.3-0.4% TTFT spread across restarts on a GB10 pair), decode within repetition spread, every exact repeat and resume hit where the baseline hit with outputs equal to cache-off, no JIT event in serving, zero Xid and allocation errors, minimum MemAvailable at or above the 5 GiB warm floor, capacity change recorded and accepted. Every arm reports its n and range; a difference inside the baseline range is no difference, and a gain derived by dividing by a noisy acceptance figure is not a gain (a single-GB10 recipe retracted a "+17%" for exactly that reason).

Rollback. Revert the one variable (backend flag, env var, build or overlay), restart with the pull skipped, confirm from the backend log line on every rank that the old path runs, and run one cold 8K plus its exact repeat; both must match the baseline within repetition spread before the lane serves again.

## 7. Anti-patterns and known-bad

- [Measured] A parity "failure" that was a fixture bug: the reference mutated an input and the test reused it. Clone and reset inputs before diagnosing a kernel; compare output and recurrent state; never relax tolerances (2026-09-16 combined-runtime qualification).
- [Measured] A kernel patch that silently does nothing still boots healthy: an installer that dry-runs without its in-place flag, or with the wrong root, leaves the Triton chain running. Require the per-process backend line on every rank in both arms. A patch that skips any file already containing its marker makes a partially edited file look complete; validate structure after patching, not the marker (2026-09-16 compatibility review; the fork's README reports 18 minutes of downtime from a separate gate bug).
- [Measured] Bundles hide regressions. E3 -> E4 lost about 10% prefill that only a single-factor BF16 arm attributed to FP8 KDA and dense projections; the combined bundle's -8.92% at 7.6K is still unattributed, and FlashKDA's own effect on the lane was never isolated (2026-09-08 E4 A/B; 2026-09-16 combined-runtime qualification).
- [Measured] A hybrid cache-boundary overlay reported +0.34% on two nodes cost 9-10% at 95K on three. Do not transfer TP2 results to TP3; the recurrent page differs (3,584 vs 2,560) (2026-09-23 V3.2 verification).
- [Measured] A source-derived step sequence was wrong: a predicted 2,048/512 alternation did not occur because the scheduler resolved block and hash size 64. Take the engine-init receipt first (2026-09-20 startup and prefill optimization).
- [Measured] A quick 3-rep probe claimed +38% decode and was withdrawn; the frozen rerun showed no change. Compare only inside a frozen harness (2026-09-23 V3.2 verification).
- [Measured] Triton GDN prefill-graph capture OOM on unified memory at a 32,768 chunk and 0.90 memory fraction; the later "8K chunks beat 32K" conclusion stands (2026-08-19 Qwen 3.8 27B campaign).
- [Measured] Recurrent-state pools silently cap concurrency under speculation, and an oversized KV plus state pool left 6.9 GiB free and wedged a swapless node until a cold power cycle; grep the capped request count and keep >= 15 GiB cushion (2026-08-19 to 2026-08-29 Qwen 3.8 27B packets and changelog).
- [Measured] Autotune redraws and micro-kernel launch tables as speed levers: redraws changed 20-23 of 36 entries without a repeatable win; a table that halved a micro-kernel moved serving by nothing measurable (2026-09-08 Qwen 3.8 27B screen; 2026-09-05 Qwen 3.8 Flash Next qualification).
- [Code-verified] Multi-config Triton autotuning of an in-place state kernel corrupts the state pool and produces silently wrong output on the first request (SGLang's comment); `restore_value` cloning OOMs at production scale. vLLM's and FLA's `chunk_delta_h` still autotune several configs and avoid corruption only by writing final state to a separate buffer or warming on dummy tensors; no source checks each call site.
- [Code-verified] Expecting FlashInfer KDA prefill, FlashInfer `SSDCombined`, FlashInfer's fused GDN decode registry, FLA FlashQLA, SGLang's CuTe-DSL / nvidia_kda / ptx_kda backends, cuLA or the INT21 KDA kernels on a GB10: each is gated to 12.0 exactly (or cc 120 exactly), to majors 10-11, or to SM90/SM100/SM103. The topic's "FlashInfer ssd_combined" is not an SM121 kernel, and FlashInfer's April audit row calling it supported on major >= 10 is wrong against the code.
- [Code-verified] A CUDA 12.9 vLLM build of FlashKDA (`12.0a` only) runs the Triton chain on a GB10 without saying so beyond the backend choice; `support_deep_gemm()` admits SM121: DeepGEMM is admitted on sm_121; the #54125 `profile_run` crash was a skipped UE8M0 repack fixed upstream (`f8e0602713`); FP32-scale mis-selection and a K = 2560 silent-corruption window remain (see [GEMM backends](09-gemm-backends-and-quant-formats.md) §7). [Community-measured]
- [Community-measured] Silent recurrent-state corruption classes under speculation on hybrids: a stale zero-accept row indexing slot -1 reads the neighbouring row (vLLM PR #51508; needs speculation plus async scheduling); a row switching between the non-speculative and speculative slot conventions drops accepted tokens from GDN, KDA or Mamba-2 state (PR #56531; ngram-style proposers only, not MTP, EAGLE or always-drafting DFlash); a hybrid state seed using the wrong block size restores the wrong state on short hits (PR #55601; TP1). Each produces plausible output, so only output-and-state comparisons catch them. [Interpretation]
- [Community-measured] (see [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md) and [Speculative decoding](02-speculative-decoding.md)) Speculative decoding on a hybrid-GDN model zeroing prefix-cache hits (vLLM issue #54360, 0 of 442,227 hits in one kit report; second pass: on a 2026-09-17 nightly the cause is the coordinator flagging every group as EAGLE under plain MTP, and `disable_eagle_block_drop: true` restored hits, §4, lever 5); DFlash/DSpark never writing target blocks so prompts under two recurrent blocks never materialize a reusable state (vLLM PR #54163); extra KDA state copies starving the fourth sequence at 7-slot drafts (sfxnz GLM 5.3 Flash NVFP4 vLLM recipe); a hybrid KDA step not ending on a 3,584-token page boundary vetoing the hit, and a 1,024 budget that "could silently prevent KDA checkpoint-aligned cache hits" (Reederey87 GLM 5.3 Flash EXL3 recipe).
- [Community-measured] An int32 overflow in vLLM's vendored FLA chunk kernel caused an illegal access beyond ~131K tokens (vcruz305 GLM 5.3 Flash EXL3 recipe, commit list only).
- [Community-measured] vLLM #37431: the Mamba-2 async illegal-instruction symptom was declared obsolete on 0.22.1 synthetic cells, yet a production long-prompt workload still hit Xid 43 in ~25 minutes, and later GDN-hybrid wedges were not fixed by piecewise or disabled graphs. Synthetic clean runs do not clear a GB10 hybrid lane.
- [Interpretation] Reading KDA's ~33% share of prefill FLOPs as its time share. On GB10 it is 3-6% of profiled kernel time (§4); plan KDA work by profile, not roofline.
- [Interpretation] Quoting datacenter FlashKDA or V-split speedups (GB300 -7.9% to -13.2% TTFT; H100/B300 1.2-1.36x forced split) or H20 decode-kernel gains as GB10 numbers. None was taken on a GB10.
- [Interpretation] GDN readout overflow (vLLM PR #54146: an fp32 readout stored into an fp16 output overflowed to inf and NaN over long low-decay contexts; analysed and validated on AMD MI50, not an NVIDIA repro) is an fp16-path risk; GB10 lanes that run bf16 activations share fp32's exponent range and are not exposed to this particular overflow.
- [Community-measured] Trusting the Triton autotuner to discard a config that does not fit (second pass). It does so only while benchmarking two or more configs; SGLang's default fused-MoE config crashed the first forward pass on a GB10 (issue #28019), and GLM-4.7-FP8 on four GB10s crashed with its default config once EAGLE was on (forum thread 359960). Prune by estimate before benchmarking.
- [Community-measured] Turning on the TMA path of the vendored FLA (`FLA_USE_TMA=1`) on SM12x: the driver reserves about 22 MiB per SM that is never freed (+3,728 MiB and less than half the KV cache on an RTX 5090, issue #36973); the GB10 figure (+1,077 MiB) is stated without a log. Leave it unset.
- [Community-measured] Accepting a kernel port because it compiles, launches and passes shape checks. In the FlashQLA-Blackwell port, TileLang `T.gemm_v1(transpose_B=True)` ran on SM120/121 about 50% off in magnitude, and a `(B, H, K, V)` state against vLLM's `(B, H, V, K)` passed the shape check at K = V = 128 and produced "structured gibberish" (docs/BLACKWELL_FIXES.md @ 9cdca002).
- [Community-measured] Blaming the kernel before checking the reference. vLLM PR #36414's SM120 wrong-output claim against FLA's Triton GDN kernels was withdrawn: its own fallback lacked the 1/sqrt(K) query scale. On an RTX 5090, a 170 W prefill "ceiling" first blamed on FLA GDN was the FFN GEMM path; switching INT4 AutoRound/Marlin weights to NVFP4 moved prefill from about 1,100 to 5,300 tok/s on a 47K prompt (devnen, SM120_GDN_CEILING.md @ 8e40de26). Kernel speedups also vanish end to end when GDN is a small share: 2.76x -> ~3% TTFT at 8K and 9.5x -> parity on GB10 27B hybrids (§4).
- [Community-measured] Reporting a gain that sits inside the baseline range. A single-GB10 SGLang recipe retracted a "+17%" that came from dividing by a noisy acceptance figure; bf16 SSM state, ReplaySSM speculation and TF32 matmul all landed inside the 41.1-43.2 tok/s baseline range at n = 10 (§4).
- [Community-measured] Rare, memory-pressure-dependent state corruption slips past smoke tests: a Mamba stale-slot bug produced confident gibberish on about one prompt in a thousand and only reproduced on demand after `gpu_memory_utilization` was lowered to 0.2 (AI21 blog; fixed by vLLM PR #32118).
- [Community-measured] Setting `TRITON_OVERRIDE_ARCH=sm120` on a GB10: the IR targets 120 while `ptxas` targets `sm_121a`, and kernels using `.tile::gather4` fail to assemble (Triton issue #10152). On Triton 3.6 and newer, `TRITON_PTXAS_PATH` is also a no-op for Blackwell targets, so recipes that rely on it are stale.
- [Code-verified] Quoting vLLM PR #55760's dense retention default as main behaviour: it and #55861 merged only to `releases/v0.29.0`; main defaults to sparse retention and relies on #53945, #54713 and `disable_eagle_block_drop`.
- [Community-measured] Using `all`-mode prefix caching for GDN hybrids: it is deprecated on main, both open `all` implementations crashed at concurrency 2 and above on an L40S and lost to `align` by 1.03-1.37x RPS, and the only GB10 `all` datum (83.4% hits) is offline-only, with 0% hits under `vllm serve` on the same image (PR #26807).
- [Community-measured] Claims that did not survive the second pass, kept so they are not repeated: that Triton emits `global_scratch` for FLA kernels on SM >= 10 even with TMA off (retracted by the Triton PR #10002 author: the image predated vLLM #38981, so TMA was active; the non-TMA path needs no scratch); that vLLM uses FlashInfer GDN prefill only on capability 9.0 (stale since PR #55715); that vLLM issue #33857 was a GDN autotuner out-of-memory error (it was a Ray-executor allocator error on a GB10 TP2 run, reported fixed by a later, unidentified commit); that FlashInfer PR #3731 fixed the GB10 GDN path (it closed unmerged; #3960 is the fix).
