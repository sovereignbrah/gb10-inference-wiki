# MoE dispatch on GB10: fused MoE backends, routing, EP vs TP

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, `sm_121` / arch-specific `sm_121a`, 48 SMs, 128 GB unified LPDDR5X), one to three nodes (node-1, node-2, node-3) joined by direct-cabled ConnectX-7 RoCE with no GPUDirect RDMA. Own measurements are cited by evidence-packet date and title; community results carry their author, link and protocol. Code lines are quoted at these pins (all fetched 2026-09-23): vLLM main `8b660ce96bc2` and the own-lane vLLM pin `487ecf187d3d` (a bring-up branch that left main on 2026-08-13), SGLang `f2a1366584e1`, FlashInfer `e838a8585bdc`, ExLlamaV3 master `6b84a21b6f1e` (own EXL3 lanes run `c5d9c657`, v0.0.43, 2026-06-14), llama.cpp `d2e54583c745`, DeepGEMM upstream `78b69000794d`, the vLLM-vendored DeepGEMM fork `e1f418c2a4f2`, DeepGEMM nv_dev `8b1392b978f5` (vendored by the own-lane pin), the two-node GLM 5.3 Flash EXL3 serving kit (MiaAI-Lab) `71962cd19e51`, DeepEP `a56d6156febc`, DeepSeek EPLB `d52c72d5b2f2`, antirez/ds4 `0aaea5a238fb`, Entrpi/ds4-on-spark `99fb7b170528`. A code line says what upstream does now, not what a given lane runs.

Reading rule for every capability gate on this page. A gate is one of four shapes: "at least X" (`has_device_capability(100)`) admits GB10; "same major" (`is_device_capability_family(120)`, SGLang `is_sm120_supported()`) admits GB10; "exactly 12.0" (`is_sm120()`, `== (12, 0)`) excludes GB10; "family 10.x" (`is_device_capability_family(100)`) excludes GB10. Most GB10 MoE surprises are one of these four shapes. See [Engine dispatch maps](16-engine-dispatch-maps.md) for the same rule applied to every kernel family.

## 1. What it is

A mixture-of-experts model (only a few sub-networks run per token) replaces each feed-forward block with many small "experts" and a router that sends every token to a handful of them, for example 8 of 288. Serving it fast takes three steps per layer: route (score the experts and pick the top few), dispatch (group tokens by expert, so each expert's weights are read once for all the tokens that chose it), and run the expert matrix multiplications in one fused kernel (one GPU program doing several steps). On a GB10 almost all of decode time is spent reading expert weights out of 128 GB of shared memory at a few hundred GB/s, so what decides speed is how many times each expert's bytes are read, how many tiny kernels and host round trips the routing step adds, and whether the engine's chosen MoE kernel even runs correctly on this chip. That last point is the GB10 trap: most engines pick their MoE kernel from a priority list that was written for datacenter Blackwell (compute capability 10.x), and GB10 (12.1) either falls through to an older or weight-only kernel, lands on a kernel with open correctness bugs, or fails because GB10 has less than half the on-chip scratch memory the kernel was tiled for. With two or three GB10 boxes, "expert parallelism" (each box holds a different subset of experts) sounds like the datacenter recipe, but without NVLink or GPUDirect RDMA there is no fast all-to-all exchange; in practice the engines keep every token on every box and add one all-reduce per MoE layer, so expert parallelism on GB10 buys memory for the KV cache, not speed. The biggest measured wins are dispatch-shape work in the EXL3 engines: a cooperative decode kernel that reads each expert once per 8 routed rows instead of once per 16, a leaner thin-row kernel, and a grouped kernel for prefill. See also [Decode optimization](05-decode-optimization.md), [Inter-Spark communication](03-inter-spark-communication.md) and [SM121 hardware facts](17-sm121-hardware-facts.md).

## 2. How each engine does it

Shared kernel libraries (used by several engines; grades apply per line).
- Shared memory. GB10 reports `shared_memory_per_block_optin` 101,376 B and `shared_memory_per_multiprocessor` 102,400 B over 48 SMs (SGLang PR #25665 device dump, Triton 3.6.0). NVIDIA/cutlass#3144 claimed SM120 has 228 KiB and SM121 99 KiB; a CUTLASS contributor answered on the same issue that "SM120 (RTX 6000, 5090, etc.) and SM121 (Spark) only support 99 KiB smem" and that a carve-out fix is in CUTLASS 4.4.2; SGLang PR #28038 measured the same 101,376 B on an RTX PRO 6000. The 228 KiB figure belongs to SM100. [Community-measured] Treat SM120 and SM121 as having the same budget; MoE tiles sized for SM100 fail on both. [Interpretation]
- FlashInfer CuTe-DSL fused MoE. `cute_dsl_fused_moe_nvfp4` is `@supported_compute_capability([100, 103, 107])` (flashinfer/fused_moe/cute_dsl/fused_moe.py:1382). The CuTe-DSL MoE that targets GB10 is b12x: `b12x_fused_moe` is `@supported_compute_capability([120, 121])` and raises below CUDA 13 (b12x_moe.py:56, 161). [Code-verified]
- FlashInfer b12x dispatcher. Routed pairs (tokens x top-k) pick a tier: "direct micro" (≤ 32 pairs and N ≤ 512, commented "Measured on GB10, pending other GPUs"), "micro" (≤ 20 pairs single top-k, ≤ 40 multi top-k, ≤ 8 tokens), "static" (≤ 640 pairs MXFP4, ≤ 1,024 NVFP4, a 32-row virtual-expert split into a tile-64 kernel), else "dynamic" (prefill); micro, static and dynamic each have a max-active-cluster ladder keyed on routed rows (cute_dsl/blackwell_sm12x/moe_dispatch.py:75-127). [Code-verified] This is the same small/medium/large split as the EXL3 cooperative / fused / grouped tiers. [Interpretation]
- FlashInfer CUTLASS fused MoE. Both `"120"` and `"121"` dispatch to a separately built SM120 CUTLASS fused-MoE module (flashinfer/fused_moe/core.py:650-651; split out in FlashInfer PR #1817). [Code-verified]
- FlashInfer MoE-EP. The `moe_ep` runtime bootstraps NVSHMEM (flashinfer/moe_ep/core/runtime/bootstrap.py:1, 140-167). [Code-verified] FlashInfer 0.7.0 release notes (2026-09-22): RTX PRO 6000 and DGX Spark "gain an MXFP8 MegaMoE backend with functional correctness validated and performance tuning ongoing" (flashinfer.ai/releases, fetched 2026-09-23). [Community-measured] On GB10 that means single-node use; see the EP subsection. [Interpretation]

[Code-verified] [Community-measured]
- DeepGEMM. Upstream main lists "NVIDIA SM90 or SM100 architecture GPU" (README.md:28 @ `78b69000794d`) and its grouped entry points dispatch `arch_major == 9` (float scales) or `10` (int scales), else `DG_HOST_UNREACHABLE` (csrc/apis/gemm.hpp:185-245). [Code-verified] DeepGEMM PR #324 (merged into nv_dev 2026-06-24) added M-grouped and K-grouped kernels for sm120 and sm121; all its numbers are RTX PRO 6000. [Community-measured]
- TensorRT-LLM (status only). Default CUTLASS MoE tactics mostly fail the SMEM budget on GB10 and the documented workaround is `TRTLLM_MOE_BACKEND=TRITON` (TensorRT-LLM#12706; NVIDIA/cutlass#3144 counts 13 of 16 tactics failing); the numbers in #12706 carry no prompt or output length. ### vLLM

Backend selection (the "oracle"). Each quant scheme has a priority list; the first backend whose device, scheme, activation and parallel predicates all pass wins, and the choice is logged as `Using '<X>' NvFp4 MoE backend out of potential backends: [...]`. [Code-verified]
- NVFP4. Auto order `FLASHINFER_TRTLLM, FLASHINFER_CUTEDSL, FLASHINFER_CUTEDSL_BATCHED, FLASHINFER_CUTLASS, VLLM_CUTLASS, MARLIN, HUMMING, EMULATION`. The comment above the list reads "FLASHINFER_B12X is intentionally excluded from auto-selection until the upstream CUTLASS SM121 MMA op guard is resolved; use moe_backend="flashinfer_b12x" to opt in explicitly"; the native `B12X` backend (PR #52018, merged 2026-08-21) is also absent. Same list and comment at the lane pin (oracle/nvfp4.py:176-199). Overrides: `--moe-backend {b12x, cutlass, flashinfer_trtllm, flashinfer_cutlass, flashinfer_cutedsl, flashinfer_b12x, marlin, humming, emulation}` (oracle/nvfp4.py:155-175). [Code-verified]
- Why NVFP4 lands on FlashInfer CUTLASS on GB10. CuteDSL and TRT-LLM-gen experts (NVFP4, FP8, BF16, MXFP4) require `is_device_capability_family(100)` (experts/flashinfer_cutedsl_moe.py:78-81; flashinfer_cutedsl_batched_moe.py:67-70; trtllm_nvfp4_moe.py:209-212 and siblings). `FlashInferExperts` accepts `family(120)` as a device; it admits NVFP4 and MXFP4 x MXFP8 through `has_device_capability(100)` and BF16 plus static-scale per-tensor FP8 through `has_device_capability(90)`, both at-least tests GB10 passes; it rejects block FP8 and W-MXFP4-A16 (exact 9.0). Activations: SiLU, GELU-tanh, ReLU2 (no-mul), SwiGLU-OAI and SwiGLU-OAI-uninterleave (experts/flashinfer_cutlass_moe.py:128-190). [Code-verified]
- vLLM's own CUTLASS grouped NVFP4 (`VLLM_CUTLASS`, `CutlassExpertsFp4`) admits families 100, 110 and 120 (experts/cutlass_moe.py:703-710). The SM12x kernel is a CUTLASS `Sm120` ptr-array grouped GEMM with a cooperative mainloop, compiled only with `ENABLE_NVFP4_SM120`; runtime gate `120 <= version < 130` (csrc/libtorch_stable/quantization/fp4/nvfp4_blockwise_moe_kernel.cu:419-490, 635-655); CMake builds `12.0f` with CUDA ≥ 13, else `12.0a;12.1a` (CMakeLists.txt:991-1012). [Code-verified] Published builds that lack the SM121 FP4 kernels fall back to Marlin (issue #50925, open; PR #38484 to add 12.1 to published targets, open). [Community-measured]
- B12X, both flavours, reject expert parallelism. Native `B12xExperts` needs `family(120)` plus the optional `b12x` package and a parallel predicate of `not use_ep and ep_size == 1 and not use_all2all_kernels and not enable_eplb`; `supports_expert_map()` returns False (b12x.py:457-515). `FlashInferB12xExperts` needs `family(120)` and `not use_ep` (experts/flashinfer_b12x_moe.py:165-202). [Code-verified] Main also has `VLLM_B12X_MOE_FP4_FORCE_A16`. [Code-verified]
- FP8. Order AITER, FLASHINFER_TRTLLM, FLASHINFER_CUTLASS, DEEPGEMM, VLLM_CUTLASS, TRITON, ... (oracle/fp8.py:75-140, 440-530). `cutlass_group_gemm_supported()` returns False for capability ≥ 110 (_custom_ops.py:851-858; issue #43507 open), although CUTLASS itself gained an SM120 ptr-array TMA collective for tensor/token-scaled FP8 grouped GEMM in PR #3280 (2026-06-13, closing NVIDIA/cutlass#3263) and vLLM main bundles CUTLASS v4.7.1. [Code-verified]
- BF16. Order FLASHINFER_TRTLLM, FLASHINFER_CUTLASS, TRITON, BATCHED_TRITON; FlashInfer CUTLASS moves behind Triton only when `dp_size > 1` or the activation is SwiGLU-OAI; the Hopper-only demotion does not apply (oracle/unquantized.py:63-94; same demotions at the lane pin). [Code-verified]
- Resolution summary on GB10 [Code-verified]: W4A4 NVFP4 → FlashInfer CUTLASS (or VLLM_CUTLASS on a source build without FlashInfer's fused MoE); W4A16 NVFP4 → Marlin; block FP8 → DeepGEMM through the vendored SM12x fork with UE8M0 scales, Triton if DeepGEMM is off; per-tensor FP8 → FlashInfer CUTLASS with static scales, Triton with dynamic scales; BF16 → FlashInfer CUTLASS. B12X is opt-in only. Own boot logs agree for NVFP4 and block FP8 (§4). Triton `fused_moe` and per-device config JSONs.
- File name `E={E},N={N},device_name={device}{,dtype=...}{,block_shape=[bn,bk]}.json`; the device string is `get_device_name()` with whitespace and `/` replaced by `_`, so a GB10 is `NVIDIA_GB10`; N is `w2.shape[2]`, the per-rank intermediate after TP sharding, doubled for `int4_w4a16`. Lookup: `VLLM_TUNED_CONFIG_FOLDER` first, then the in-package `configs/`. A miss logs "Using default MoE config. Performance might be sub-optimal! Config file not found at ..." and falls to `get_default_config()`; a hit takes the key nearest to M (`min(keys, key=lambda x: abs(x - M))`), no interpolation; `VLLM_BATCH_INVARIANT` forces the default (fused_moe.py:1093-1167, 1419-1447; utils/platform_utils.py:69-74). [Code-verified]
- GB10 files in the tree: vLLM main carries two, `E=256,N=512` and `E=512,N=512`, both `dtype=fp8_w8a8,block_shape=[128,128]` (block FP8), added by PR #52502 (commit `7ea4b40954`, merged 2026-08-17; Triton 3.5.0; 13 of 18 keys are `16x128x128`, 4 warps, 3-4 stages). v0.28.0 (published 2026-08-26) is the first release that contains them; v0.27.0 does not; the own-lane pin has none. Open or unmerged GB10 JSON PRs: #45949 ("didn't capture A/B"), #52192 (`E=512,N=2688`), #31740 (large SM121 bring-up, needs rebase). [Code-verified]
- Defaults fit the budget. Using the "(stages − 1) x (A tile + B tile)" rule that Triton's `Required:` message matches: BF16 at M > 512 (`128x128x64`, 3 stages) and per-tensor FP8 at M > 512 (`128x128x128`, 3 stages) each need about 65,536 B; block FP8 at M > 64 (`64x128x128`, 3 stages) needs 49,152 B; all fit 101,376 B (fused_moe.py:1296-1416). [Interpretation, arithmetic on Code-verified defaults]
- Tuning: `benchmarks/kernels/benchmark_moe.py --tune` runs one Ray worker per GPU over 1,920 candidates (`BLOCK_M {16..256} x BLOCK_N {32..256} x BLOCK_K {64,128,256} x GROUP_M {1,16,32,64} x warps {4,8} x stages {2..5}`), skips candidates that raise `OutOfResources`, sweeps 18 batch sizes 1-4,096, and writes the file under the `get_config_file_name()` name (benchmark_moe.py:364-406, 522-535, 640-660, 925-950). [Code-verified]
- Where a missing GB10 JSON matters: only on TRITON, which on GB10 means dynamic-scale per-tensor FP8, block FP8 with DeepGEMM off (for example the `VLLM_USE_DEEP_GEMM=0` workaround in issue #54125), BF16 with DP > 1, or SwiGLU-OAI. [Code-verified]

Routing and sorting.
- `moe_align_block_size` is device-side. Buffers use the static bound `topk_ids.numel() + num_experts * (block_size - 1)` (rounded under `pad_sorted_ids`, and capped at `numel * block_size` only when `numel < num_experts`); `num_tokens_post_pad` is a one-element device tensor (moe_align_block_size.py:137-169). The kernel is a single-block counting sort: shared-memory per-expert atomics, a CUB `BlockScan` over 1,024 threads, then per-expert fills, with a small-batch variant and an `expert_map` path that drops non-local experts in kernel (csrc/libtorch_stable/moe/moe_align_sum_kernels.cu:140-230, 232-310). [Code-verified]
- The Triton launch avoids a host sync by over-provisioning: each program reads `num_tokens_post_padded` and returns when `pid_m * BLOCK_SIZE_M >= num_tokens_post_padded` (fused_moe.py:142-158). When `A.size(0) < BLOCK_SIZE_M` the grid is clamped to `M * top_k * BLOCK_SIZE_M` rows (fused_moe.py:820-837). [Code-verified] So for decode batches below BLOCK_M the grid is about M x top_k M-blocks with few idle; at M ≥ BLOCK_M the grid is `numel + E x (BLOCK_M − 1)` padded rows and many blocks exit early (M = 16, top-8, E = 256, BLOCK_M 16: 248 launched against at most 128 active). [Interpretation, arithmetic]
- Top-k. `topk_softmax` and `topk_sigmoid` are fused CUDA ops (router/fused_topk_router.py:26-69); DeepSeek-style `grouped_topk` guards only its programmatic-dependent-launch waits with `__CUDA_ARCH__ >= 900` (grouped_topk_kernels.cu:525-528); the FP32 router GEMM builds for SM90+ (CMakeLists.txt:764-776). PR #54048 (merged 2026-08-30, `b5707bf994`) extended the cuBLAS `out_dtype` FP32 router-GEMM tier from "Hopper or SM100" to family 120; before it GB10 used a standalone copy that bf16-rounded router logits before grouped top-k. The lane pin predates it. [Code-verified]
- Kernel-only benchmarks exist (`benchmarks/kernels/benchmark_moe_align_block_size.py`, `benchmark_router_gemm.py`); no GB10 result was found. [Code-verified]

Expert parallelism.
- With DP = 1, TP + EP runs no all-to-all at all: `use_all2all_kernels = use_ep and (dp_size > 1 or pcp_size > 1 or is_sequence_parallel)` (fused_moe/config.py:1028-1031; lane pin 1056-1059), and sequence-parallel MoE itself requires `data_parallel_size > 1` (config/parallel.py:719-735). Without all-to-all kernels no dispatcher is built (all2all_utils.py:188-190); tokens stay replicated across the TP group, each rank runs its local experts, and the layer's all-reduce combines them (prepare_finalize/no_dp_ep.py:40, class `MoEPrepareAndFinalizeNoDPEPModular`). [Code-verified] On a 2-3 node GB10 cluster at DP = 1, `--all2all-backend` is inert and the per-layer traffic is one all-reduce of the hidden states, the same as TP-sliced experts. [Interpretation]
- `--all2all-backend` values on main: `deepep_high_throughput`, `deepep_low_latency`, `deepep_v2`, `mori_*`, `moonep`, `nixl_ep`, `allgather_reducescatter` (default), `flashinfer_all2allv`, `flashinfer_nvlink_two_sided`, `flashinfer_nvlink_one_sided`; `pplx` and `naive` were removed and map, with a warning, to `allgather_reducescatter` (config/parallel.py:44-58, 202, 507-513). [Code-verified]
- Padding. Without EPLB a non-divisible expert count is spread unevenly, the first `E mod ep` ranks getting one extra (expert_map_manager.py:60-80). With EPLB, vLLM raises "EPLB currently only supports even distribution of experts across ranks" unless `(num_experts + num_redundant_experts) % ep_size == 0` (layer.py:70-82, 255-265). [Code-verified] So 256 experts on EP3 need 2, 5, 8, ... redundant experts; 288 divide by 3 with none. [Interpretation, arithmetic]
- EPLB. `--enable-eplb` with `EPLBConfig` defaults `window_size` 1000, `step_interval` 3000, `num_redundant_experts` 0, `log_balancedness` off (with `log_balancedness_interval`), `use_async` on, `policy` "default" (config/parallel.py:61-110). DeepSeek EPLB packs expert groups onto nodes hierarchically only when `num_groups % num_nodes == 0`, else balances globally (eplb.py:92, 150-156 @ `d52c72d5b2f2`). [Code-verified] On GB10 a node is one GPU, so the hierarchical tier buys nothing; redundant replicas can still even out per-rank rows. [Interpretation]

Known-bad on GB10 (details in §7): Marlin NVFP4 MoE illegal-memory-access in long serving (#54666); SwiGLU-OAI alpha/beta dropped on the NVFP4-Marlin path (forum thread 376979); B12X EP rejection and open SM120 faults (#47365, #50189, #49031); DeepGEMM dense block-FP8 corruption reported in a comment on #54125 (dense GEMM, not the grouped path).

Lane pin vs main, for MoE: no GB10 Triton JSONs; no native `B12X` backend (only `FLASHINFER_B12X`); no #54048 router fix; DeepGEMM nv_dev instead of the vLLM fork; FlashInfer 0.6.17 and cutlass-dsl 4.6.2; `VLLM_TEST_FORCE_FP8_MARLIN` still honoured. [Code-verified]

### llama.cpp and forks

- llama.cpp CUDA. Each `MUL_MAT_ID` node picks MMVQ, then MMQ with device-side expert bucketing, then MMF, then a host-synchronized fallback (ggml/src/ggml-cuda/ggml-cuda.cu:1910-1952). For `MUL_MAT_ID` the MMVQ cap is `get_mmvq_mmid_max_batch()`, which returns `MMVQ_MAX_BATCH_SIZE` (8) for every quant type on NVIDIA Volta and on compute capability ≥ Ada, so MMVQ handles MoE up to 8 tokens for every type on GB10; the GB10-tuned Q2_K cap of 6 lives in `ggml_cuda_should_use_mmvq()` and governs dense `MUL_MAT` only (mmvq.cu:285-296, 318-356). [Code-verified]
- GB10-only code is `GGML_CUDA_CC_DGX_SPARK = 1210`: an MMVQ L2-prefetch path and parameter table compiled only when `__CUDA_ARCH__ == 1210` (common.cuh:61; mmvq.cu:5-20, 117, 140), so it needs a build whose target is exactly `sm_121`. The Blackwell MMQ config with native FP4 tiles applies when the highest compiled arch is ≥ 1200 and < 1300 (common.cuh:376-379). [Code-verified]
- Routing stays on the device. A fused top-k MoE kernel covers softmax or sigmoid → top-k → get_rows with optional bias, normalization and delayed softmax, for expert counts that are a power of two up to 512 or exactly 288 or 576 (topk-moe.cu:398-407), fired inside graph fusion (ggml-cuda.cu:3470-3522); `mm_ids_helper` builds per-expert bounds on the device for MMQ (mmid.cu:1-40); the only host-synced path (`cudaMemcpyAsync` of ids plus `cudaStreamSynchronize`) runs when MMVQ, MMQ and MMF all decline, and asserts it is not reached during CUDA-graph capture (ggml-cuda.cu:1881-1906). [Code-verified] PR #27621 (merged 2026-08-31) extended the MoE GLU fusion and top-k router fusion from 1 token to speculative widths 2-8 (§4). [Community-measured]
- No expert parallelism. Split modes are `none, layer, row, tensor` (include/llama.h:198-203); multi-node is RPC. [Code-verified]
- ds4 (antirez) `0aaea5a238fb`. Single-GPU CUDA, Spark included, runs concurrent rows as an "ordered fallback" rather than native batching (docs/SERVER.md:79). Two-node "tensor parallelism" for DeepSeek-V4.1 Flash Q2 is a 50/50 routed-expert split, one GPU per rank, over RDMA or TCP; the transport "stages CUDA results through host memory; this is RoCE, not GPUDirect" (docs/DISTRIBUTED.md:100-135). Decode batching starts at five ready sessions because "smaller groups run in order, which is faster at those sizes" (DISTRIBUTED.md:133). [Code-verified] Numbers in §4. [Community-measured]

[Community-measured]

### ExLlamaV3 in vLLM

ExLlamaV3 uses no vendor MoE backend; the EXL3 quantized experts run ExLlamaV3's own kernels, and the vLLM serving kits wrap them in an overlay.
- Upstream tiers (block_sparse_mlp.py:24-44, 985-992 @ `6b84a21b6f1e`) [Code-verified]:
  - a two-stage cooperative decode kernel `exl3_moe_coop` for 1-8 token rows (`MAX_BSZN = 8`), added by commit `58d4d7322a1b` (2026-09-13, "MoE: Replace bszN and bsz1 paths with two-stage coop kernel"): stage A is gate/up with the input rotation, stage B is down, for 1-8 bit weights;
  - the fused `exl3_moe` kernel with 16/32/64-row tiles up to `EXL3_MOE_FUSED_ROWS` (default 128) or 256 when wide tiles apply;
  - a batched reconstruct tier; a per-expert reconstruct loop.
- Cooperative kernel details. Each block handles up to `ROWS = 8` slots of one expert (exl3_moe_coop_kernel.cuh:40). Two tile geometries: narrow (32 columns per block, k split 16 ways) and wide (128 columns, 4 x 4 warps). `moe_coop_pick_wide` returns wide always below Blackwell (Ampere, Ada and Hopper), and on Blackwell only when `kslices >= 256` (k ≥ 4,096) or `kslices >= 128` with ≥ 32 slots (exl3_moe_coop.cu:80-104). `DevCtx::get_cc` maps every major ≥ 10 to `CC_BLACKWELL`, so GB10 is "Blackwell" here (exl3_devctx.cu:32-44). `EXL3_MOE_COOP_WIDE=0|1` forces one geometry for both stages; `EXL3_MOE_COOP_KSPLIT=n` is "measured as neutral to harmful on every GPU here" (doc/env_vars.md:396-406). [Code-verified] For a GLM-shaped layer (hidden 4,096) stage A auto-picks wide; stage B (k = local intermediate, 1,024 at TP2 or 2,048 at EP3) auto-picks narrow unless slots ≥ 32 at k = 2,048: the kits' "geometry 2" (A wide, B narrow). [Interpretation]
- Host syncs. Upstream routing groups assignments with `argsort`, counts with `torch.bincount` and reads counts back with `.tolist()`, a per-layer device-to-host sync; it now skips the readback when `num_tokens * top_k <= fused_rows` ("the readback (a CPU sync per layer, ~33% idle at MTP verify shapes) is skipped and everything is fused"; block_sparse_mlp.py:1093-1105). The ~33% is a maintainer statement, not a GB10 measurement. [Code-verified]
- Concurrency. `exl3_moe_max_concurrency = num_sms / MOE_SMS_PER_EXPERT` = 48 / 8 = 6 on a GB10 (exl3_moe.cu:15-18; exl3_moe_common.cuh:10), which matches the own boot line `concurrency=6`. [Code-verified] [Measured, log] Other knobs: `EXL3_MOE_FUSED_ROWS_WIDE`, `EXL3_MOE_MTILE`, `EXL3_MOE_BATCH_RECON`, `EXL3_MOE_FUSED_DET` (default 1, deterministic slot-and-gather). [Code-verified]
- The vLLM kit overlay (`overlay/exl3.py:1444-1560` @ `71962cd19e51`) [Code-verified]:
  - thin path: tokens ≤ `EXL3_TEMP_ROWS_FUSED` (the allocated temp cap) run one fused `exl3_moe` launch, "a single graph-safe launch"; it replaces `torch.bincount` with a device `scatter_add_` ("torch.bincount can host-stage and break CUDA graphs") and passes `num_active = -1` ("max-concurrency grid, no .item() host sync");
  - grouped E3 path: tokens above the cap with `EXL3_FAT_GROUPED=1` and effective tier `grouped` run thin experts in `exl3_moe` and fat experts in three grouped launches "driven by device-side tables. No host sync, so this branch is CUDA-graph capturable";
  - otherwise the older E1/E2 or sorted fat tiers, which copy counts to host (E1 overlaps the copy with the thin launch on a side stream; the sorted path calls `counts.tolist()`).
- Two-node cooperative decode. The kit ships cooperative MoE as an opt-in overlay (`EXL3_OVERLAY_HOST` plus the extension; `GLM53_COOPERATIVE_MOE=1` alone does not deploy the binary): a GLM-shaped build of `58d4d732` (hidden 4,096, local intermediate 1,024 at TP2, top-k 8, 4-bit MCG) whose `call_eligible` requires 1-32 rows and top-k 8, so prefill never takes it. It forces geometry 1 (both stages wide) because auto geometry 2 launches `rows*topk*(H/32)` down blocks (8,192 at 8 rows vs 2,048 wide) (docs/cooperative-moe.md; docs/cooperative-moe-handoff.md). [Code-verified] Correctness: 18/18 cases within 0.3% of reference peak, not bit-exact (6,473,169 raw differing elements retained). [Community-measured]
- Three-node (TP3/EP3) cooperative decode. The TP3 extension targets `sm_121a`, 4-bit MCG, hidden 4,096, local intermediate 2,048, top-k 8, ≤ 96 local experts and SwiGLU limit 10; native ABI 2 builds separate 32-row and 64-row translation units (256/512 routed slots); the adapter shares scratch per device and rejects micro-batching and dual-batch overlap; unsupported shapes and activation limits fall back to stock EXL3. `select_policy.py` reduces nine rank x geometry profile logs (three EP ranks x geometries 0/1/2) into a per-row policy: geometry 2 at rows 2, 3, 4, 5, 10, 18, 24; geometry 1 at rows 1, 6, 7, 8, 9, 12, 15, 16, 20, 25, 30, 32, 35, 40, 48, 56; stock otherwise; 64 rows "did not meet the conservative 3% worst-case gain threshold and therefore use stock" (extensions/cooperative_moe/tp3/README.md:1-65). [Code-verified] The own production policy is exactly this grid (§4). [Measured]
- Thin-fast path. `GLM53_EXL3_MOE_FAST=1` (default 0; kit PR #217, merged 2026-09-18 as `ca29e28`) adds two 4-bit / N256 variants of the stock thin `exl3_moe` kernel with a 1-stage register pipeline instead of 3 and 8-stage shared-memory staging instead of 3; stock geometry is unchanged (K32 tiles, N256, eight blocks per expert). A second variant skips the duplicate up-lane input Hadamard when the gate and up SUH pointer tables are the same allocation, aliased only after an all-expert `torch.equal`. Dispatch requires 4-bit, `hidden % 256 == intermediate % 256 == 0`, the flag literally `1`, and SM121, and fails closed at load if the image lacks the patch; "The TP3 launcher keeps unsetting it"; "Composition with the cooperative-MoE path is untested" (docs/sm121-perf-paths.md:13-160). Author-reported SASS: fast 127 registers / 16 B frame / 6 spill stores / 0 spill loads vs stock 128 / 88 B / 37 / 39. [Code-verified] [Community-measured]
- Hazards recorded in kit docs and own evidence: a hash-gated cooperative binary that no clean rebuild reproduces; one lock buffer per device, so two EXL3 MoE kernels on different streams deadlock; component wins that did not survive the whole engine; thin-fast bimodality (§7). [Measured] [Community-measured]

## 3. What is different on GB10 / SM121

- [Code-verified] The fastest datacenter MoE kernels are closed to GB10 by "family 10.x" gates: FlashInfer CuteDSL fused MoE (non-b12x) and every TRT-LLM-gen fused MoE (NVFP4, FP8, BF16, MXFP4). vLLM, SGLang and FlashInfer all exclude GB10 from them. NVFP4 MoE therefore lands on FlashInfer's separate SM120 CUTLASS module.
- [Code-verified] The one CuTe-DSL MoE built for SM12x (b12x) is opt-in only in vLLM and rejects expert parallelism and EPLB by design. The exclusion comment's stated reason (the CuTe-DSL SM121 MMA guard) is fixed in the pinned cutlass-dsl; the open correctness bugs are the live reason (§7). [Community-measured]
- [Community-measured] SM120 and SM121 have the same 99 KiB per-block shared memory (101,376 B opt-in), not 228 KiB; SM100-sized MoE tiles fail with `OutOfResources` (Triton), "Failed to initialize cutlass TMA WS grouped gemm" (CUTLASS/TRT-LLM), or silently drop out of an autotuner's candidate list. K = 128 block-scaled grouped tiles need more than the budget.
- [Code-verified] CUTLASS grouped FP8 MoE is gated off at cc ≥ 110 in vLLM even though CUTLASS 4.7.1 now has an SM12x tensor/token-scaled FP8 ptr-array collective; per-tensor FP8 MoE with dynamic scales runs Triton.
- [Code-verified] DeepGEMM grouped MoE runs on GB10 only through the vLLM fork or nv_dev, and only with UE8M0 int scales; SGLang enabled UE8M0 for SM121 on 2026-09-18. No GB10 accuracy check of the grouped kernels exists (§8).
- [Code-verified] Published vLLM builds that lack `12.1a` FP4 kernels send NVFP4 MoE to Marlin weight-only FP4, which has an open long-serving fault on SM121 (#54666). The fix (#38484) is open.
- [Code-verified] At most two GB10 Triton `fused_moe` JSONs exist in vLLM (block FP8, `E=256/512,N=512`, from v0.28.0) and one in SGLang (per-tensor FP8, `E=128,N=768`, from v0.5.15). A tune takes hours on a GB10 (§4), and the stock vLLM tuner "cannot complete" `E=512,N=2688` past M = 8 on unified memory (vLLM PR #52192 body). [Community-measured]
- [Community-measured] No GPUDirect RDMA: memory from `cudaMalloc` on the iGPU "cannot be coherently accessed by the CPU complex nor by I/O peripherals like PCI Express devices. Hence the GPUDirect RDMA technology is not supported", so nvidia-peermem, dma-buf and GDRCopy do not work; RDMA applications should use `cudaHostAlloc` + `ibv_reg_mr` (NVIDIA staff, developer forum thread 352051 post 2, fetched 2026-09-23).
- [Code-verified] DeepEP requires "Hopper (SM90) GPUs, or other architectures with SM90 PTX ISA support", "NVLink for intranode communication" and "RDMA network for internode communication"; V2 moved the live EP path to the NCCL Gin backend with NVSHMEM kept for legacy methods, "0 SM RDMA low-latency EP is no longer supported", and it is "fully tested with InfiniBand networks. However, it is theoretically compatible with ... RoCE" (DeepEP README.md:9-84, 373 @ `a56d6156febc`). [Interpretation] With no GPUDirect RDMA and one GPU per node, DeepEP, NVSHMEM/IBGDA and FlashInfer MegaMoE have no supported multi-node transport on GB10; no source ran any of them across two or more GB10 nodes. That is a negative search result, not proof of impossibility.
- [Code-verified] Expert parallelism at DP = 1 in vLLM and with `moe_a2a_backend none` in SGLang adds no all-to-all: every rank sees every token and the layer ends in one all-reduce. On GB10, EP changes where expert weights live (memory, divisibility, KV capacity), not the communication pattern.
- [Code-verified] A GB10 node is one GPU, so hierarchical (node-group) EPLB placement buys nothing; only redundant replicas can rebalance per-rank rows.
- [Code-verified] ExLlamaV3 classes GB10 as Blackwell, so its cooperative kernel auto-picks the wide tile only for long-k stages; with 48 SMs and 8 SMs per expert, the stock fused kernel runs at most 6 experts concurrently.
- [Code-verified] llama.cpp has a GB10-only MMVQ prefetch and parameter table that exists only in a build whose target is exactly `sm_121`.
- [Measured] Decode on a three-node EXL3 MoE lane barely moved with GPU clock (C1 means 36.0 / 33.7 / 33.9 / 34.25 tok/s at stock, 2,200, 2,100 and 1,900 MHz, first requests excluded in every arm: −4.9% to −6.4%, inside the stock rep spread 33.9-38.2, n=5) while 250K prefill fell 3-9% (2026-09-21 GPU clock-cap sweep, GLM 5.3 Flash EXL3 TP3). [Interpretation] MoE decode on GB10 is bound by expert bytes, not SM clock; dispatch work that cuts bytes or host overhead is what moves it. See [Clocks, thermal, and power](13-clocks-thermal-power.md).

## 5. Levers, ranked

1. **Cooperative decode MoE kernel, selected per row count from measurements** — applies to: vLLM + EXL3 and native ExLlamaV3 x GLM 5.3 Flash, DeepSeek V4.1 Flash and Qwen 3.8 Flash Next shapes x 1, 2 and 3 nodes (upstream ExLlamaV3 at or after `58d4d7322a1b` has it built in; own lanes on `c5d9c657` need the kit extension). Gain: component 0.52-0.97 time ratio for 1-56 rows and none at 64 on the own TP3 layer, with most of the 1-row win being host overhead (0.107 ms per layer) [Measured]; external TP2 matched A/B/A +7.3% structured x1, +9.3% x2 [Community-measured]; DeepSeek-shaped +25% to +35% on a weaker 2/3-bit stock kernel [Community-measured]; the own TP3 +17.9% / +20.8% is a multi-change bundle (component list in §4) with no attribution [Measured, bundle]. Contested: the external matched A/B/A is better evidence of the kernel's serving effect, but at local intermediate 1,024, not 2,048; do not transfer the number to TP3. Cost: a native extension per shape (graph-safe launches: [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md)), a profile-and-select pass over three ranks and three geometries, a per-row policy file bound to the binary hash. Risk: the binary is hash-gated and not reproducible from a clean rebuild; any stock-path change silently invalidates the policy; the policy's 3% margin is finer than the 15% inter-rank spread (§7). Smallest falsifying experiment: one boot with every row forced to stock (the "all but cooperative" arm) against the current policy, C1 and C8, 5 exact-body repeats each; the lever fails if the policy arm does not beat all-stock beyond repeat spread.
2. **Thin-fast stock kernel (`GLM53_EXL3_MOE_FAST=1`)** — applies to: vLLM + EXL3 x 4-bit GLM-shaped experts (hidden and intermediate multiples of 256) x SM121, TP2 in practice (the public TP3 launcher unsets it). Gain: layer latency 8-17% faster; TP2 median decode +7.7% to +14.6% (maintainer, noise up to 4.6%) and +4.6% to +7.9% (independent), register-cut template +2.5% to +12% on a second kit [Community-measured]. Cost: an offline `exllamav3_ext` rebuild. Risk: a slow mode, one run in four 15-30% below stock with cause unknown (§7); untested together with the cooperative kernel; the sealed numerical study was inconclusive because its absolute KL gate fails stock-vs-stock. Smallest falsifying experiment: A/B/A with at least 8 runs per arm, full distribution reported, GPU clocks and per-step fallback counters sampled during every run; the lever fails if the p25 of the fast arm is below the p25 of stock.
3. **Grouped fat-expert prefill (E3) with the chunk budget as its dial** — applies to: vLLM + EXL3 x GLM 5.3 Flash and DeepSeek V4.1 Flash x 2-3 nodes. Gain: +37% to +45% cold prefill vs E2 [Community-measured]; own chunk ladder about 4% prefill per halving of the budget, trading KV capacity (2.58M -> 3.37M tokens from 7,168 to 2,048) [Measured]; Entrpi's expert-major schedule 2.43x-3.30x in the llama.cpp lineage [Community-measured]. Cost: none beyond the kernel (chunk budget: [Prefill optimization](04-prefill-optimization.md)); the thin/fat cutoff must equal the decode verification shape (slots x (draft + 1) = 64 at 8 slots) or decode rows fall into the prefill branch. Risk: the grouped tile is already at its measured optimum (stock 64-row/4-stage won every case [Measured]); do not tile-tune. Smallest falsifying experiment: E3 on vs off in one boot pair at a fixed chunk budget, cold 8K/100K x 5.
4. **Make the fast vendor backend the one that runs, and prove it from the log** — applies to: vLLM and SGLang x NVFP4, MXFP4 and FP8 MoE models x all topologies. Gain: stability first — auto Marlin faulted where explicit b12x ran 26 minutes clean; a source build with SM12x FP4 kernels ran VLLM_CUTLASS where the published build fell to Marlin [Community-measured]. Speed gain unknown: no same-model backend A/B with a stated protocol exists on GB10 [Proposed]. Formats and dense GEMM backends: [GEMM backends and quant formats](09-gemm-backends-and-quant-formats.md). Cost: a source build (or a release after #38484), one boot per backend. Risk: b12x has open faults on SM120 (#47365, #50189, #49031) and on 8 x GB10 (FlashInfer#3383); it rejects EP. Smallest falsifying experiment: same model, same boot flags, `--moe-backend flashinfer_cutlass` vs `marlin` vs `b12x` (EP off), C1/C8 decode and cold prefill, backend line captured from every rank.
5. **Measure the routing histogram before any EP, EPLB or row-size decision** — applies to: every multi-node MoE lane. Gain: none directly; it decides levers 6-8 [Proposed]. Own evidence says uniform-routing models are wrong here: real prefill routing was "much more concentrated" than uniform, and a uniform byte model predicted above-nominal bandwidth at small rows [Measured]. Cost: SGLang `--expert-distribution-recorder-mode stat` or vLLM `log_balancedness`; the own EXL3 lane needs a preallocated device ring buffer drained per request, since the existing per-layer telemetry adds a host sync per layer. Risk: an instrument that syncs per layer perturbs what it measures (§7). Smallest falsifying experiment: one request mix recorded with the ring buffer on vs off; the instrument fails if decode moves beyond repeat spread.
6. **Use EP on GB10 for capacity and legality, not speed** — applies to: vLLM and SGLang x large MoE (256-512 experts) x 3-4 nodes; EXL3 TP3 already uses whole experts per rank. Gain (KV and memory budget: [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md), [Memory on unified memory](11-memory-on-unified-memory.md)): KV pool 1.61M -> 4.91M tokens at equal decode speed (~86 vs ~85 tok/s) on 3 GB10 [Community-measured]; required to load at all when TP slicing drops the intermediate below the NVFP4 kernel minimum [Community-measured]. Speed: the only EP-on/off speed comparison (-3.4% at EP = 4) is confounded [Community-measured]. Cost: divisibility padding (256 experts on EP3 need 2, 5, 8, ... redundant experts with EPLB). Risk: EP disables b12x; FlashInfer CUTLASS was 0/12 stable at EP = 4 on SGLang 0.5.10 [Community-measured]. Smallest falsifying experiment: same model and backend, `--enable-expert-parallel` on vs off, one boot each, record KV pool and C1/C8; the capacity claim fails if the pool does not grow.
7. **EPLB with redundant experts** — applies to: vLLM (`--enable-eplb`) and SGLang x EP lanes on 2-3 nodes; not reachable from the EXL3 quant method. Gain: unknown on GB10; no balancedness figure and no on/off tok/s exist [Proposed]. Cost: redundant expert memory; the vLLM draft model is not a `MixtureOfExperts` and crashed the EPLB controller on `expert_load_view != None` until an identity dummy was mounted [Community-measured]. Risk: rebalancing moves expert weights over a link measured at ~18 GB/s all-to-all bus bandwidth [Interpretation]. Smallest falsifying experiment: EPLB on vs off with `log_balancedness` on, same mix, C8; fails if max/mean per-rank rows do not drop.
8. **Tuned Triton `fused_moe` JSON for GB10** — applies to: vLLM and SGLang only when the MoE lands on TRITON (dynamic-scale per-tensor FP8, block FP8 with DeepGEMM off, BF16 with DP > 1, SwiGLU-OAI); no own lane today. Gain: kernel +2.3% to +5.2% per decode key but serve-level wash (vLLM #52192); a +11.6% 8K TTFT regression in another test (DocAI); no clean serving-level win exists in any source [Community-measured]. Cost: 3-6 hours of tuning per shape; the stock tuner cannot finish large shapes on unified memory. Risk: nearest-key snapping puts a decode tile on prefill M (-2.35% pp2048 until large-M rows were pinned). Smallest falsifying experiment: paired A/B with and without the file (large-M keys pinned to the default), 8K prefill c4 and decode c1, three seeds.
9. **Keep router logits in FP32 (vLLM #54048)** — applies to: vLLM x DeepSeek/GLM-style grouped top-k x all topologies; in main since 2026-08-30, backported into an own composite. Gain: precision (bf16-rounded logits before grouped top-k removed); no speed number [Code-verified]. Cost: none measured. Risk: none recorded. Smallest falsifying experiment: flip the backport's ablation switch, compare top-k expert choices on a fixed prompt set; fails if choices are identical.
10. **Fused MoE finalize off for determinism (SGLang)** — applies to: SGLang x FlashInfer MXFP4/NVFP4 MoE. Gain: deterministic greedy output (atomic-BF16 finalize drifted ~1 nat) at about 0.3 ms per step [Community-measured]. Cost: that step time. Risk: the launcher default is on, so a lane loses it on any restart that drops the setting. Smallest falsifying experiment: 0 vs 1, 20 greedy repeats of one prompt, count distinct outputs.

## 6. Protocol

This is the protocol for changing a MoE backend, kernel, dispatch policy, parallel layout or chunk budget on a GB10 lane. It follows the fleet rules on the entry page ([GB10 Inference Wiki](README.md)) and the incidents in §4 and §7. See [Profiling protocol](14-profiling-protocol.md) for kernel attribution, [Quality and correctness gates](21-quality-and-correctness-gates.md) for output gates, and [Inter-Spark communication](03-inter-spark-communication.md) for the fabric.

Preconditions.
- All index rules apply (see [the entry page](README.md)), in particular: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor measured after the longest qualified prefill, and traffic stopped below 4 GiB; a greedy logprob probe after every relaunch; discard the first request and warm every serving shape before timing; a unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection or configuration line read on every rank; at least 3 repetitions with a closing baseline (A/B/A); MemAvailable sampled every 1-2 s with zero NV_ERR_NO_MEMORY or Xid lines; no reboot or power cycle without per-node permission; correctness gates from [Quality and correctness gates](21-quality-and-correctness-gates.md) before any speed number. For this page: one memory variable per boot (a backend repack or redundant experts counts as one).
- No memory overcommit: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor while serving, KV pin raises of no more than 1.5 GiB per boot, and memory freed by one change never spent in the same boot. Stop all benchmark traffic at 4 GiB MemAvailable on any node. Redundant experts, a second backend's weight repack, and Marlin's repack all cost memory: size them before the boot.
- Clean window: no outside traffic; poll running requests before each pass and discard any pass that overlaps outside traffic.
- One variable per boot. A restart for an A/B skips the image pull, so the only difference is the variable under test.
- Never restart a client gateway; restarting the lane's engine is the operator's step, and a gateway restart is the operator's decision. Never `pkill -f` a pattern that also matches your own shell.
- Build receipt: engine commit; FlashInfer, cutlass-dsl, Triton and DeepGEMM versions (vendored fork or nv_dev); whether the build contains SM121 FP4 kernels (`12.1a` or a CUDA 13 `12.0f` family build); for EXL3, the ExLlamaV3 commit, the cooperative binary hash and the policy file hash.
- Boot receipt, read on every rank, never derived: vLLM `Using '<X>' ... MoE backend out of potential backends: [...]`, the prepare/finalize class (`MoEPrepareAndFinalizeNoDPEPModular` means no all-to-all), `Expert parallelism is enabled ... Local/global`, any "Using default MoE config" or "GPU does not have native FP4" warning, FlashInfer autotuner skipped-tactic lines; SGLang server info (`moe_runner_backend`, `ep_size`, `moe_a2a_backend`, `enable_eplb`, redundant experts, fused-finalize setting); EXL3 `experts_local=... fused_moe=... concurrency=...`, `effective_tier=...`, the printed row policy. A boot with no such line is a boot where the change did not run.

Change. Exactly one of: `--moe-backend` / `--moe-runner-backend`; a DeepGEMM switch (`VLLM_USE_DEEP_GEMM`, `VLLM_MOE_USE_DEEP_GEMM`); a Triton config folder; the cooperative kernel on/off, geometry or policy; `GLM53_EXL3_MOE_FAST`; E3 on/off; `EXL3_TEMP_ROWS_FUSED`; the chunk budget; EP on/off; EPLB on/off or the redundant-expert count; the fused-finalize setting.

Run.
1. Off-lane parity at production shapes before anything touches a serving engine: real weights, rows 1 to 64, uniform and concentrated routing, every EP rank's expert range; compare at the raw FP32 boundary, not after BF16 rounding; tolerance fixed in advance and never loosened (narrow the dispatch envelope instead); `compute-sanitizer` memcheck and a racecheck filtered to the candidate kernel.
2. Component timing: CUDA-graph replay, clocks locked or sampled, at least 25 samples per cell and at least 200 near any selection threshold, both routing patterns, all ranks; select with p10/p90 envelopes and hold when envelopes overlap, not with a median ratio against a 3% margin.
3. For a per-row policy, profile every capture size the engine uses (not a subset; capture lists are on [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md)) and re-profile after any change to the stock path or the binary.
4. Serving A-B-A through the frozen harness with a same-session restore: C1 and C8 decode, 5 exact-body repeats per arm (8+ for thin-fast, with the full distribution), cold prefill at 8K and 100K x 5, a routing-concentrated fixture.
5. For EP, EPLB or backend changes also record the KV pool size from the boot log, per-rank routed rows (histogram), and the all-reduce count per step.
6. Watch memory at 1 s resolution on every node through the longest prompt; record Xid and allocation-error counts.

Record (packet fields): build and boot receipts per rank; the one variable and its two values; topology, local experts per rank, local intermediate, slots and draft width; parity results (cases, max abs, raw differing elements, sanitizer counts); component medians with p10/p90 per row and rank; serving per-run values, medians and spread; KV pool; minimum MemAvailable per node; discarded passes and why. Component and profiler runs are recorded separately and never scored as serving numbers.

Pass gate. Parity passes at the fixed tolerance with zero sanitizer errors in the candidate. The component win holds outside the envelope on every rank. Serving C1 and C8 at or above baseline beyond repeat spread with no run below the baseline's minimum (thin-fast: p25 at or above stock p25), prefill within spread, backend line as intended on every rank, zero Xid and allocation errors, minimum MemAvailable at or above the 5 GiB warm floor. A bundle that passes is recorded as a bundle; a lever's share is claimed only from a one-variable arm.

Rollback. Revert the one variable (flag, env var, backend, policy file or binary), restart with the pull skipped, confirm from the boot receipt on every rank that the old path runs, and run one C1 fixture and one cold 8K; both must match the baseline within repetition spread before the lane serves again. For a cooperative binary change, restore the previous binary and its matching policy file together.

## 7. Anti-patterns and known-bad

- [Measured] Quoting a bundle gain as one lever's gain. The +17.9% / +20.8% single-stream result bundles several changes (list and count caveat in §4); the "all but cooperative" arm was never run (2026-09-16 GLM 5.3 Flash EXL3 TP3 combined runtime qualification).
- [Measured] Trusting component ratios as serving speedups. A decoder change 7.5% faster at 1 row and ~1% at 8-56 rows in components shipped in a group that measured C8 -5.5% in the whole engine; it was reverted (2026-09-20 GLM 5.3 Flash V3: retained startup and prefill improvements).
- [Measured] Selecting kernels with a margin finer than the noise. The policy uses a 3% worst-case threshold while identical shapes differ by up to ~15% across ranks; the rows-64 "regression" is a worst-of-six tie; 39 of the 64 policy rows were never profiled and default to stock.
- [Measured] Sizing EP, EPLB or row-size levers on a uniform-routing model. Real prefill routing was much more concentrated than uniform, and a uniform byte model implied up to 351 GB/s per rank at 1-2 rows, above the nominal 273 GB/s; the "percent of DRAM ceiling" claims built on it were withdrawn. No percent-of-ceiling claim without `dram__bytes_read.sum`.
- [Community-measured] Host syncs and multi-launch tiling in the MoE path. Row tiling (8 full-grid launches per layer, each with a host `.item()`) lost 18-61% cold prefill, and one large 1,024-row launch without extra syncs still lost 13-24%, so the host-sync share is not isolated (GLM kit docs/improve-prefill.md). Keep counts on the device (`scatter_add_`, `num_active = -1`, device-side tables).
- [Measured] Telemetry that perturbs what it measures: the EXL3 fat-expert log costs one host sync per MoE layer and buckets at 128 rows, not the live 64.
- [Measured] A hash-gated kernel binary no clean rebuild can reproduce (nvcc embeds the build path, build id and a few bytes of fatbin variance); the policy binds only to the binary hash, so a stale policy on an unchanged binary is accepted silently.
- [Community-measured] Overlapping EXL3 MoE kernels on multiple streams: ExLlamaV3 keeps one lock buffer per device, so two EXL3 kernels on different streams deadlock; the cooperative adapter rejects micro-batching and dual-batch overlap for the same reason.
- [Measured] Relaxing a tolerance to pass: a non-production activation limit failed the frozen tolerance (peak-relative 0.00310 vs 0.003); the dispatch envelope was narrowed instead. Comparing post-BF16 output hid differences; the comparison moved to the raw FP32 boundary.
- [Community-measured] Thin-fast has a slow mode: medians improve 5-8% but about one run in four lands 15-30% below stock on a second kit, with identical acceptance and no preemptions (kit issue #227, open). A median-only A/B hides it.
- [Community-measured] Marlin NVFP4 MoE on SM121: auto-selected Marlin died with an illegal memory access in long serving, also with `VLLM_MARLIN_USE_ATOMIC_ADD=0` (vLLM #54666, open); the NVFP4-Marlin path drops SwiGLU-OAI alpha/beta, giving garbage MiniMax-M3 output until patched (NVIDIA forum thread 376979). Contested: a 2026-05 note says `VLLM_MARLIN_USE_ATOMIC_ADD=1` is required against a race (conselara.dev, no protocol); #54666 is the better evidence (a stated run with counts), and at the lane pin the flag is a performance choice. Unresolved.
- [Code-verified] Forcing Marlin as a workaround with no control arm: two own NVFP4 lanes were run on `--moe-backend marlin` for vLLM #50925 with no non-Marlin arm, so the "prefill tax" noted in their changelogs is unmeasured.
- [Community-measured] b12x at EP > 1 on `sm_121a`: a spec-validator mismatch, then `cudaErrorIllegalAddress`; plain TP = 8 hit `cudaErrorInvalidValue` in `launch_sm120_moe` (FlashInfer#3383, open, on flashinfer 0.6.11); on SM120, empty or garbage output under TP or PP (#47365) and an Xid 31 MMU fault under concurrent chunked prefill (#50189); W4A16 repack keeps both weight copies and OOMs at startup (#49031). The field report of `ValueError: Mxfp4 MoE backend 'B12X' does not support ... ep_size=2 ... use_ep=True` (habr.com article 1050470) is the designed rejection, not a bug.
- [Community-measured] FlashInfer CUTLASS NVFP4 MoE at EP = 4 on SGLang 0.5.10: 0/12 stable, `cudaErrorIllegalInstruction`; eager `cutlass_moe_fp4` rows collapsed onto one token (forum thread 366325).
- [Community-measured] Other closed FlashInfer SM12x MoE defects, useful when reading old reports: #3294 (GB10 garbage traced to a cutlass-dsl wheel collision), #3031 (pure FP8 MoE redirected to Sm89 tiles, some with zero occupancy), #3119 (a single valid FP8 x FP4 tile on SM120), #4049 (SM120 gemm1 autotune then illegal instruction; workaround `skip_ops`), #3359 (b12x `TypeError` from a dropped `max_active_clusters`), #3683 / PR #3744 (b12x lacked `gelu_tanh` and needed intermediate size a multiple of 128).
- [Community-measured] The K = 64 SM120 grouped-tile patch (FlashInfer PR #2786, closed unmerged): its GB10 figure (19.6 tok/s with MTP 3 on Qwen3.5-122B-A10B-NVFP4) was withdrawn by its poster as a log-metric artefact in favour of 14.31 tok/s with MTP off (llama-benchy tg256, no unpatched control), and the thread's 55 -> 282 tok/s headline (4 x RTX PRO 6000) was withdrawn by its author, who could reproduce only 2.5-6%, "probably within" noise (forum thread 363493).
- [Community-measured] A tuned Triton JSON is not a free win: an 11.6% 8K-prefill TTFT regression (DocAI), a serve-level wash behind a +3.5% kernel win (vLLM #52192). BTankut's +6.3% (16.77 vs 15.77 tok/s, 4 x GB10, GLM-4.7-FP8, SGLang v0.5.4.post2) comes from a repo whose A/B script, result files and results page disagree on engine, TP and EAGLE state, so its protocol is unknown. Avarok's "+65.7% vs default" gives no method; a combined MoE + dense-GEMM tune (pp2048 4,677 ± 2,150 -> 7,406 ± 19 tok/s) cannot be attributed to the MoE file.
- [Code-verified] Symlinking another GPU's tables to `NVIDIA_GB10` names (rdoiron/mimo-mods-for-dgx-spark symlinks RTX PRO 6000 Server Edition JSONs) gives tiles tuned for a different SM count, with no benchmark.
- [Community-measured] TensorRT-LLM CUTLASS MoE on GB10: 13 of 16 default tactics fail, and the survivor was reported at 4.8 tok/s against 40.0 with `TRTLLM_MOE_BACKEND=TRITON` (Qwen3-30B-A3B-NVFP4, TensorRT-LLM#12706, protocol not stated); the ungate PR was closed unmerged.
- [Code-verified] Expecting an all-to-all speedup from `--all2all-backend` or `--moe-a2a-backend` at DP = 1: the setting is inert (vLLM) or unused (`none`, SGLang), and DeepEP is present in some images but unreachable from the EXL3 quant method.
- [Community-measured] Reading the FlyCockpit "TP=3 without EP is slower" line alone: that arm was Socket transport with MTP 0; with the same Mesh fabric and MTP 5, no-EP matched EP on speed and lost on KV capacity.
- [Measured] Approximate INT8 single-token expert GEMV: rejected on numerics (~0.7-0.8% rel-L2 against a tight gate) (2026-09-16 DeepSeek V4.1 Flash EXL3 TP3 component gates).
- [Measured] Tile-tuning the grouped prefill kernel: every variant lost to stock 64-row / 4-stage, by up to 219% (2026-09-16 DeepSeek V4.1 Flash EXL3 TP3 prefill tuning).
- [Measured] Acting on a scheduler model without the engine's own log: a predicted 2,048 / 512 prefill half-step, the premise of a proposed "halve expert-weight passes" lever, did not occur in the live engine (2026-09-20 GLM 5.3 Flash V3 packet). Take the engine-init line before sizing a chunk lever (see [Prefill optimization](04-prefill-optimization.md)).

- How long do `topk_softmax`, `grouped_topk`, `moe_align_block_size` and the Triton early-exit launch take on GB10? — vLLM's `benchmark_moe_align_block_size.py` and `benchmark_router_gemm.py` on one node at decode M = 1-64 and chunk M = 2,048-8,192, for 96 / 256 / 288 / 512 experts.

EP vs TP
- EP vs TP-sliced experts on the same backend and model across 2-3 GB10 nodes — a one-flag `--enable-expert-parallel` A/B with identical backend, recording C1/C8 and KV pool (the queued Flash Next EP isolation arm is the cheapest instance).

- What does EPLB do on GB10? — EPLB on vs off with balancedness logging, same mix, C8.
- Why did EP = 4 lose 3-7% in the four-node SGLang matrix: communication, whole-expert imbalance or the runner change? — the same matrix with one MoE runner fixed across EP settings.

Cooperative and thin-fast

- Does thin-fast help the own TP3 lane, does it compose with the cooperative kernel, and what causes #227's slow mode? — a TP3 build with the patch, A/B/A with 8+ runs, per-step fallback counters and clocks sampled during every run.
- Does a 16-row cooperative run (`ROWS` 8 -> 16), a persistent grid (about 84% no-op CTAs estimated at 64 rows), or `MOE_SMS_PER_EXPERT` 4/16 pay on GB10? — an ncu stall breakdown of the cooperative kernel at 32-64 rows first, then one binary per change.

All-experts-per-chunk economics
- What is GB10's effective L2 behaviour and the real bytes read per MoE kernel? — ncu `dram__bytes_read.sum` and `lts__t_sector_hit_rate` on the stock fused, cooperative and grouped kernels at 1, 8, 64 and 2,048 rows; no source or own packet has an ncu byte count on a MoE kernel.
