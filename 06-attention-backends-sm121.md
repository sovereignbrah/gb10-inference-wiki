# Attention backends on SM121

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 48 SMs as reported by torch, 128 GB unified memory), one to three nodes (node-1, node-2, node-3), direct-cabled ConnectX-7 RoCE between nodes. Own measurements are cited by evidence-packet date and title. Code is quoted at these pins: vLLM `487ecf187` (2026-08-25, the base the own GLM lanes self-report) and vLLM `v0.30.0` = `ced6857a` (2026-09-22); SGLang `79fec592a8fd` (2026-09-23); FlashInfer tags v0.6.15 = `8eccd0c1`, v0.6.17 = `a0a6b019`, v0.6.18 = `69ff11fc`, v0.6.18.post1 = `8bc3b578`, v0.7.0rc1 = `07869c61` (2026-09-10), v0.7.0 = `4d75a33f` (tagged 2026-09-21T23:52Z, release notes 2026-09-22), head `5c586da4` (2026-09-23); Dao-AILab flash-attention `6a3ecb9b`; the vLLM flash-attention forks JaredforReal `2b84100f` (pinned by vLLM 487ecf187) and vllm-project `506341a1` (pinned by v0.30.0); llama.cpp `d2e54583c745`; ExLlamaV3 `6b84a21b6f1e`; DeepGEMM `8b1392b9` (deepseek-ai, pinned by vLLM 487ecf187) and `e1f418c2` (vllm-project fork, pinned by v0.30.0). A code line says what that pin does; it is not proof of what a given lane runs. FlashInfer releases are cut from release branches that cherry-pick fixes, so every "absent from tag X" statement on this page rests on a file-content check at the tag, never on commit ancestry alone.

## 1. What it is

Attention is the step where each new token looks back over every earlier token in the conversation, and on a long prompt it is the part of the model whose cost grows with context. An "attention backend" is the specific GPU program (kernel) an inference engine picks to do that step, and engines ship several: FlashAttention (a family of fused attention kernels) in generations 2, 3 and 4, FlashInfer (a kernel library built for serving), Triton kernels (Python-compiled GPU code), and special kernels for sparse attention (reads only selected past tokens) and MLA (compressed-KV attention, DeepSeek style). The GB10 is a consumer-class Blackwell chip, compute capability 12.1, and it lacks the Hopper and datacenter-Blackwell instructions (wgmma, tcgen05, tensor memory) that the newest and fastest attention kernels are written for, so FlashAttention 3 and the datacenter FlashAttention 4 never run on it. What does run is older-style warp-level kernels, some of which were validated only on the sibling SM120 chip (RTX PRO 6000 class) and some of which silently produce garbage when their guard is widened to SM121. Which backend the engine picks decides three things on a GB10: whether long-context output is correct at all, whether CUDA graphs (recorded GPU launch sequences) can be captured under speculative decoding, and only then raw speed; on the MoE models these lanes serve, attention is a small share of decode time, so the measured speed swings from a backend change are usually a few percent unless the change also flips the graph mode or the KV-cache format. The practical work is therefore to know which backend each engine auto-selects on 12.1, prove it from the engine's log line, pin the FlashInfer version it depends on, and refuse any backend or guard change that has not passed a long-context correctness gate. See also [SM121 hardware facts](17-sm121-hardware-facts.md), [Engine dispatch maps](16-engine-dispatch-maps.md), [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md) and [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md).

## 2. How each engine does it

Shared kernel libraries (used by several engines; grades apply per line).
- FlashInfer JIT arch. `_normalize_cuda_arch` maps CC 12.0 to `120f` and any other 12.x (GB10 included) to `<minor>a`, i.e. `compute_121a`/`sm_121a`, and raises `RuntimeError("SM 12.x requires CUDA >= 12.9")` below CUDA 12.9 instead of falling back; the docstring gives the reason as avoiding SM120 code on SM121 "which can cause cudaErrorIllegalInstruction". `FLASHINFER_CUDA_ARCH_LIST` overrides detection and keeps a user-supplied `a`/`f` suffix. The function is identical at v0.6.15, v0.6.17 and v0.7.0 (flashinfer/compilation_context.py:34-59 @ 8eccd0c1; :61-101 @ a0a6b019; same @ 4d75a33f). [Code-verified]
- FlashInfer caches and version checks. The JIT workspace is `FLASHINFER_CACHE_DIR/<flashinfer version>/<arch>`, `121a` on a GB10; mismatched `flashinfer-cubin` or `flashinfer-jit-cache` versions raise at import unless `FLASHINFER_DISABLE_VERSION_CHECK` is set (flashinfer/jit/env.py:58-62, 92-102, 127-137, 148-157 @ a0a6b019). vLLM builds its FlashInfer autotune cache as `VLLM_CACHE_ROOT/flashinfer_autotune_cache/<version>/<arch>` from the same workspace (vllm/model_executor/warmup/flashinfer_autotune_cache.py:24-41 @ 487ecf187), so an autotune path such as `.../0.6.17/121a` is a code-backed receipt of the installed Python package version. [Code-verified]
- FlashInfer wheels. Release CI builds `12.0f`, which covers CC 12.0 and 12.1; only sparse `mma.sp` mxf4 needs `sm_121a` (FlashInfer issue #3170 audit, correction note 2026-06-12). The v0.6.18 release notes say CUDA 13 AArch64 jit-cache wheels "drop native SM121a cubins (DGX Spark keeps running via SM120 family cubins)" and that single-request FA2 modules are no longer prebuilt and always JIT (PRs #4757, #4760). From v0.7.0 `flashinfer-jit-cache` is a shim over per-arch provider wheels (PR #4514, merged 2026-09-10); the cu130 index lists `flashinfer_jit_cache_sm121a-0.7.0+cu130` and `sm120f` aarch64 wheels. PyPI's `flashinfer-cubin` stops at 0.6.13; matching cubin wheels come from flashinfer.ai/whl (all fetched 2026-09-23). [Code-verified] (vendor release notes and indexes)
- FlashInfer SM12x gates. fa3 only on SM90; XQA decode on majors {9, 10, 12}; XQA-MLA on major 12; trtllm-gen on major 10 only; maintainers have "no plans to generate SM120 TRTLLM FMHA cubins" (#3170 body and 2026-08-17 comment). [Code-verified]

[Code-verified]

### vLLM

Mechanism. `_get_backend_priorities()` returns, for any non-MLA device with major not 10 (GB10 included): FLASH_ATTN > FLASHINFER > TRITON_ATTN > FLEX_ATTENTION > TURBOQUANT (vllm/platforms/cuda.py:184-199 @ 487ecf187; :166-177 @ v0.30.0, which adds an SM90-only TRITON_FLASH_ATTN prefix). For MLA on major 12 it returns TRITON_MLA > FLASHINFER_MLA_SPARSE_SM120 (:130-133 @ 487ecf187; :132-135 @ v0.30.0). Candidates are filtered by each backend's `validate_configuration`; the highest valid one wins and is logged as `Using <X> attention backend out of potential backends: [...]` (:533). An explicit `--attention-backend` that is invalid raises `ValueError("Selected backend … is not valid …")`, otherwise logs `Using <X> backend.` (:464-473); there is no silent fallback from an explicit choice. [Code-verified]

Flags and environment. `--attention-backend` and `--attention-config` (PR #26315). `VLLM_ATTENTION_BACKEND` and `VLLM_FLASH_ATTN_VERSION` were removed by PR #32812 (merged 2026-01-22, `6437ff1f`) and appear nowhere in vllm/envs.py at 487ecf187 or v0.30.0: setting them does nothing. [Code-verified] Other knobs that matter here, named in the cited recipes and issues rather than read at the pin: `VLLM_ENGINE_READY_TIMEOUT_S` (cold JIT), `VLLM_USE_FLASHINFER_SAMPLER`, `--no-enable-flashinfer-autotune`, `--kv-cache-dtype`, `--block-size`. [Community-measured]

FlashAttention. `get_flash_attn_version` picks FA3 on major 9, FA4 on major 10 and FA2 otherwise (v1/attention/backends/fa_utils.py:93-101 @ 487ecf187); `_is_fa4_supported` rejects any major other than 10 in both forks vLLM builds from (flash_attn_interface.py:57-63 @ 2b84100f and @ 506341a1); vLLM PR #47218, which would add SM12x, is open. The bundled FA2 is compiled for `FA2_ARCHS "8.0+PTX"` (fork CMakeLists.txt:140 at both pins) and vLLM's loose arch intersection maps a 12.1 target to 8.0 plus PTX (cmake/utils.cmake @ 487ecf187), so FA2 on a GB10 is sm_80 PTX JIT-compiled by the driver on first load; vLLM #47397 shows an nvcc 13.3 build failing under driver 580.159.03 with `cudaErrorUnsupportedPtxVersion`, only for models routed to FLASH_ATTN. FLASH_ATTN rejects quantized KV on SM12x: `flash_attn_supports_kv_cache_dtype` is true only for FA3 on family 90 or FA4 on family 100 (fa_utils.py:226-246; flash_attn.py:186-193). Log line: `Using FlashAttention version 2` (flash_attn.py:868). [Code-verified]

FlashInfer. Prefill uses FlashInfer's native FA2 path; TRTLLM prefill is off on SM12x. `supports_trtllm_attention()` returns decode-only for family 120, meaning XQA. Decode is XQA for FP8 KV, for speculative decoding, and for BF16 batches of at most 256 tokens in auto mode; native otherwise (vllm/utils/flashinfer.py:375-426, 453-540 @ 487ecf187). XQA needs `has_nvidia_artifactory()`: the `flashinfer-cubin` package installed, or the NVIDIA artifactory answering an HTTP GET within 5 s; an offline node without the cubin wheel silently loses XQA. SM12x XQA with ragged spec-decode masks and UNIFORM_BATCH graphs came from vLLM #49718 (merged 2026-08-11, pins FlashInfer 0.6.16.post1). The native decode path declares UNIFORM_SINGLE_TOKEN_DECODE graph support, so spec decode on it drops to PIECEWISE graphs (#49547); a head-ratio misdeclaration drops a draft model's graphs to NONE (#55581). Log line: `FlashInfer resolved query dtypes: … decode_backend=xqa|flashinfer-native … arch=sm121` (v1/attention/backends/flashinfer.py:887-911). [Code-verified]

Sparse and dense MLA. `FLASHINFER_MLA_SPARSE_SM120` requires `kv_cache_dtype == "fp8_ds_mla"` (v1/attention/backends/mla/flashinfer_mla_sparse_sm120.py:66-70 @ 487ecf187): 656 B rows for GLM_NSA/DSV3.2, 584 B for DSV4. In upstream vLLM, `FLASHINFER_MLA_SPARSE_SM90` accepts major 9 only (flashinfer_mla_sparse_sm90.py:123-124 @ 487ecf187; :106-107 @ v0.30.0); one community build's gate table shows it widened to (9, 12) and then rejecting `fp8_ds_mla` at init (vLLM #37754 comment, 2026-09-01). FLASHMLA_SPARSE and FLASHMLA are major 9/10 only; TRITON_MLA has no sparse path. The SM120 sparse path arrived with vLLM #43477 (merged 2026-06-22); before it, #45317 had "no valid attention backend" for sparse MLA on SM121. [Code-verified] On v0.27.0 GLM-5.2 on four GB10 crashed at startup because `FlashInferMLASparseSM120Impl` lacked `masked_mha_available` (vLLM #51920). [Community-measured]

Indexer and top-k (DeepSeek V3.2/V4, GLM DSA). Varlen paged MQA logits require family 100; `use_fp4_indexer_cache` asserts family 100 ("sm_120 (consumer Blackwell)… not supported"); outside SM100 the FP8 paged-MQA-logits kernel supports `next_n` in {1, 2}, so the indexer flattens when speculation is deeper (v1/attention/backends/mla/indexer.py:649-740 @ 487ecf187). Top-k: FilteredTopK runs only with at least 128 KiB of opt-in shared memory per block (csrc/libtorch_stable/topk.cu:38), which a GB10 never has, and very long rows that would oversubscribe the persistent cooperative launch raise an error (:137-145); vLLM #54110 (merged 2026-09-05, in v0.30.0) falls back to `top_k_per_row_decode` on low-SMEM devices instead. vLLM #51538 (merged 2026-08-15, `97388c44`) clamps negative indexer context lengths for padded decode slots under MTP and hardens `persistent_topk`; a content check shows neither hunk at 487ecf187, while v0.28.0 contains it. [Code-verified]

New in v0.30.0. An opt-in `B12X` causal paged-attention backend for SM12x (PR #52017, merged 2026-09-01): `supports_compute_capability` accepts (12, 0) and (12, 1) (v1/attention/backends/b12x.py:212-215 @ v0.30.0), install with `pip install vllm[b12x]`, absent from the auto priority list; the PR's benchmarks are on RTX PRO 6000 only. [Code-verified]

### SGLang

Mechanism. `get_default_attn_backend` returns `flashinfer` for MHA on a CUDA device that is neither Hopper nor SM100 (`triton` when the model has attention sinks or FlashInfer is missing) and `triton` for MLA (srt/arg_groups/model_override_base.py:247-320 @ 79fec592). `is_sm120_supported` means major 12 on CUDA at least 12.8 and so includes GB10; exact `is_sm120()` and `is_sm121()` exist separately (srt/utils/common.py:290-336), and `platform.is_sm120` maps to the family helper (runtime_context:1762). Log line when unspecified: `Attention backend not specified. Use <X> backend by default.` (overrides.py:1066-1069). [Code-verified]

Flags. `--attention-backend`, the phase split `--prefill-attention-backend` / `--decode-attention-backend`, `--speculative-draft-attention-backend`, and for DSA models `--dsa-prefill-backend` / `--dsa-decode-backend` (logged as `Set DSA backends … prefill=…, decode=…`, overrides.py:636-640, 684-688). `trtllm_mha` is accepted for prefill and decode on the SM90, SM100 and SM120 families at this pin; SM120-family FMHAv2 prefill is refused with `fp8_e4m3` KV or skip-softmax, and prefill context parallelism needs SM100 (srt/arg_groups/attention_hook.py:129-168). ### llama.cpp and forks

Mechanism. `-fa/--flash-attn` takes on, off or auto, and auto is the default (`flash_attn_type = LLAMA_FLASH_ATTN_TYPE_AUTO`, common/common.h:499 @ d2e54583). Auto keeps FA on only if the FA op lands on the layer's own device, otherwise disables it (src/llama-context.cpp:520-558); FA is enabled automatically for tensor split mode and for a quantized V cache, where an explicit disable is an error. Log lines: `flash_attn = auto|enabled|disabled` (:313) and the probe's "enabled" or "not supported, set to disabled". [Code-verified]

Kernels on CC 12.1. The CUDA FA path goes through `turing_mma_available`, which selects the `mma.sync` MMA_F16 kernel or the vec kernel for small batches (ggml/src/ggml-cuda/fattn.cu:632-664); these are warp-level MMA kernels, not an FA2 or FA4 library. A DGX-Spark-specific tile choice exists for DKQ 576 / DV 512 at GQA 20 (GLM 4.7 Flash MLA) when `cc >= GGML_CUDA_CC_DGX_SPARK` (1210) (fattn.cu:369-375; common.cuh:61; PR #19142, merged 2026-01-28). Upstream also has a CUDA lightning-indexer op (PR #25545, merged 2026-07-15). [Code-verified]

Forks and status. The Entrpi ds4 fork is built `sm_121a` on the own fleet, but its attention kernels were not characterised; the phuongncn GX10 fork runs DeepSeek V4 with `-fa on`. llama.cpp #28132 (open) reports deterministic character-level corruption for DeepSeek-V4-Flash on a native `-DCMAKE_CUDA_ARCHITECTURES=121` build, independent of quant, on two GX10 over an RPC tensor split; the reporter suspects the DSA indexer, MLA or MoE paths. No controlled `-fa on` against `-fa off` A/B on a GB10 exists in any source found; published Spark tables force `-fa 1`. [Community-measured] [Code-verified]

Defaults on CC 12.1. FA auto, which resolves to on for a single-GPU node with the FA op on-device and is forced on by a quantized V cache. [Code-verified]

### ExLlamaV3 in vLLM

EXL3 in vLLM. [Code-verified] (own read of the installed adapter) DeepSeek V4.1 EXL3 at three nodes pads attention heads 64 to 96 so each rank holds 32, the smallest count the SM120 sparse-MLA kernels instantiate. ## 3. What is different on GB10 / SM121

- [Code-verified] No wgmma, no tcgen05, no tensor memory. FA3 (wgmma, SM90), datacenter FA4 (tcgen05, SM100) and trtllm-gen FMHA/MLA cubins (SM100/103) cannot run, and no engine auto-selects them on 12.1 (§2). What runs is warp-level MMA: FlashAttention 2, FlashInfer FA2 templates and XQA, the SGLang SM12x `fa4` family, the upstream `FlashAttentionForwardSm120` port, Triton, and llama.cpp's MMA_F16 kernels.
- [Code-verified] vLLM's FA2 on a GB10 is sm_80 PTX JIT-compiled by the driver; there is no native sm_121 SASS in the bundled library, so a toolchain newer than the driver can break every FLASH_ATTN path at load (vLLM #47397).
- [Code-verified] Two arch spellings coexist. FlashInfer JIT on a GB10 builds `sm_121a` (and needs CUDA at least 12.9); FlashInfer release wheels ship `120f` family code, and from v0.6.18 the aarch64 cu130 jit-cache carries no native 121a cubins until the v0.7.0 per-arch provider wheels. DeepGEMM's `get_arch()` gives `120f` or `121a` depending on family support. A `121a` directory with modules in the version-keyed cache means local JIT happened; an empty one with no `ninja`/`nvcc` lines at start means only prebuilt `120f` modules ran (community wheel inspection, jschmied REPRODUCE.md @ 6813ea7f).
- [Code-verified] Shared memory per block is 99 KB (101,376 B opt-in). This single ceiling explains several SM121 exclusions: vLLM FilteredTopK needs 128 KiB, so GB10 always takes the persistent or per-row top-k path; FlashInfer's FP8 FA2-MLA branch forces a Hopper tile needing 117,312 B, so relaxing its SM90 gate fails at `cudaFuncSetAttribute` (community kit root cause, tonyd2wild GLM NVFP4 kit @ 9fea48c1); SGLang's tilelang DSA kernel wants 169,984 B.
- [Community-measured] The GB10 has 48 SMs (torch `multi_processor_count` in FlashInfer #3170 comments; SGLang #32991's GB10 table; tonyd2wild DSv4.1 RESULTS). The #3170 audit text says 84; treat that as a documentation error. SM-count heuristics (split-KV, top-k CTA groups) should use 48.
- [Measured] [Community-measured] SM120 validation does not transfer to SM121. The trtllm-gen QSA sparse-decode route that is correct on exact SM120 silently corrupts long-context output when widened to SM121. Three counts from different instruments on the same mechanism, not one number: sglang #36845's body reports 32/32 outputs token id 0 at 120K, 190K and 210K with HTTP 200; sglang #36806 reports 1/4 runs at 120K rising to 4/4 at 210K; the own audit saw 2 of 4 repeated coding outputs become token-0 / "!" loops. Guards must stay exact-SM120 until a SM121 long-context gate passes.
- [Code-verified] SM120 sparse-MLA kernels are shape-bound: page 64 only, a fixed head grid {8, 16, 32, 64, 128} before v0.7.0rc1, and fixed top-k sets. Models whose per-rank head count is off-grid are padded (GLM 22 to 32 heads and 512 to 576 query width; DeepSeek V4.1 64 to 96 heads at three nodes), and geometry mismatches block boot rather than degrade (DeepGEMM paged MQA accepts `block_kv` 32 or 64 while indexer backends advertise 128, vLLM #56461; a DSv4.1 top-k of 1152 from padded SWA rows, vLLM #56837, fix verified on SM120).
- [Measured] Attention page geometry interacts with speculation depth (see [Speculative decoding](02-speculative-decoding.md)): a QSA ring of 12 rows must divide the attention block size vLLM chose, so MTP5 at a 1,616-token page could not boot and MTP6 at 1,632 could ("2026-08-31 Flash Next vLLM MTP depth A/B").
- [Code-verified] Quantized KV narrows the backend set. FLASH_ATTN rejects FP8 KV on SM12x, so any FP8-KV dense model lands on FlashInfer; SM120 sparse MLA requires `fp8_ds_mla`; vLLM's fp4 indexer cache is gated to SM100 even though DeepGEMM ships SM120 fp4 MQA-logits headers.
- [Historical diagnostic] Indexer workspaces live in the same unified pool as the KV pin. Indexer transients scale with chunk x prefix: an own three-node DeepSeek V4.1 lane wedged all nodes on a ~200K prompt, and a community Flash Next ladder wedged two nodes at 393,216 tokens; raising the KV pin by an amount freed from the indexer workspace starved a node. See [Memory on unified memory](11-memory-on-unified-memory.md).
- [Historical diagnostic] The live GLM three-node engine corroborates the 656 B sparse-MLA row: its boot log's hybrid page of 1,679,360 B equals 2,560 x 656 exactly.

## 5. Levers, ranked

Ranked by expected value on the own lanes, with correctness levers first because a wrong backend on SM121 produces fluent garbage, not a crash. No lever below has an own attention-only speed A/B; gains are bands from the rows in §4.

1. **Keep sparse-decode guards at exact SM120 and run the SM121 Triton fallback** — applies to: SGLang and vLLM x QSA (Qwen 3.8 Flash Next) and any trtllm-gen/XQA sparse decode x all topologies. Gain: correctness (own 2/4 corrupted outputs with the widened guard; community 32/32 token id 0 at 120K-210K in sglang #36845 and 1/4 rising to 4/4 from 120K to 210K in sglang #36806) plus a faster correct kernel: 2.07x kernel and +4.45% / +4.00% end to end at c=1 / c=4 over the previous Triton kernel [Measured] [Community-measured]. Cost: none beyond carrying the #36845 kernel. Risk: a later rebase or an open PR (#36556) re-widens the gate; a stale resolver in an older base image shadows the FP8-capable kernel (§7). Smallest falsifying experiment: widen the gate on a sidecar, run 4 repeated coding prompts plus 120K / 190K / 210K needles x 4; any token-0 output keeps the rejection.
2. **Upgrade FlashInfer 0.6.17 -> 0.6.18.post1 on sparse-MLA lanes (the smallest step carrying the #4732 barrier-race fix)** — applies to: vLLM + EXL3 GLM 5.3 Flash (TP2/TP3), vLLM DeepSeek V4 lanes on 0.6.15, TensorRT-LLM DSA via #16224. Gain: removes a known prefill-kernel hang (5/5 runs hung -> 0/150,000 iterations in the PR soak) [Community-measured]; speed unknown [Proposed]. The own lanes on 0.6.17 recorded no wedge through 95K and longer prefills, so this is risk reduction, not a fix for an observed fault [Historical diagnostic]. Cost: aarch64 cu130 wheels run `120f` code (no native `121a` prebuilt), single-request FA2 always JITs, cutlass-dsl and NCCL pin skew against the engine (§6), a new `121a` JIT cache. Risk: new version, new tactics; the separate forum mbarrier livelock is not tied to any merged fix, so the upgrade does not close it. Smallest falsifying experiment: model-free soak of `sparse_mla_sm120` prefill at the lane's padded shape (32 heads, top-k 2048, 256 tokens) for 30,000 iterations on both versions, then a frozen-harness A-B-A including 95K cold prefills; a hang on 0.6.18.post1 or a decode or prefill loss beyond spread falsifies.
3. **FlashInfer at or after v0.7.0rc1 for native GLM NoPE and runtime-H decode (drop the 22 -> 32 head and 512 -> 576 query padding)** — applies to: vLLM + EXL3 GLM 5.3 Flash x TP3 (22 heads per rank; TP2 already sits on the 32-head grid). Gain: unknown on a GB10 [Proposed]; the runtime-H kernel is stated 0.9-2.5% slower than dedicated-head instantiations, and GLM FP8 prefill is still instantiated only at 8 / 16 / 32 / 64 / 128 heads, so prefill padding remains [Code-verified]. Cost: FlashInfer upgrade across every attention path plus an adapter rewrite; #5142 reports the #4802 cpb calibration failing on the head rank during startup on a two-Spark TP2 pair and falling back to a heuristic [Community-measured]. Risk: distinct, less-tuned kernel needing its own correctness gate; the NoPE calibration grid is (32, 2176) and (64, 2176) only. Smallest falsifying experiment: off-lane decode micro-benchmark at 22 heads (runtime-H, native 512 query) against 32 heads (padded) at the lane's top-k and batch sizes, then per-layer nsys on one serving arm.
4. **Compact 528 B NoPE rows (post-v0.7.0 main, PR #5075, plus an engine-side cache change)** — applies to: vLLM GLM 5.3 Flash lanes; the #5075 NaN-safe gathers also apply to DeepSeek V4 dual-cache prefill (#5095, SM120). Gain: about +15% logical KV tokens on the three-node GLM pool, because only the 11 MLA layers shrink [Interpretation] (the PR's 19.5% is per-token row arithmetic [Code-verified]); correctness for masked candidates [Code-verified]. Cost: not in any release as of 2026-09-23; engine cache ABI change; hybrid page re-tiering. Risk: a stride mismatch between writer and reader gives silent wrong output. KV row bytes and pool sizing are on [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md). Smallest falsifying experiment: log the KV pool before and after on one boot pair with everything else fixed, then greedy parity at 8K and 95K against the 656 B build.
5. **Keep FULL_AND_PIECEWISE CUDA graphs under speculation by choosing the draft/dense backend that supports them** — applies to: vLLM x dense and draft attention x all topologies. Gain: +16% single stream when FLASHINFER's spec-decode downgrade to PIECEWISE was the difference (Qwen3.5-122B, older build) [Community-measured]; +1.75% C1 aggregate / +4.45% per-stream / -1.9% C8 for graphs vs eager on a GLM EXL3 TP3 draft, inside a ±4% boot band [Community-measured]. Cost: activation reservation 1.66 -> 2.62 GiB, -3.85% KV pool on that TP3 lane. Risk: a backend that "wins" by graph mode loses the win when the graph path changes upstream (#49718 added UNIFORM_BATCH XQA). Smallest falsifying experiment: same lane, one flag, record the logged `cudagraph_mode` in both arms, frozen harness at C1 and C8. See [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md).
6. **XQA-family decode for dense GQA with FP8 KV (SGLang `--decode-attention-backend trtllm_mha`; vLLM auto)** — applies to: SGLang x Qwen 3.8 dense-attention layers (Flash Next full-attention layers, 27B) x single node; vLLM already auto-selects XQA for FP8 KV and spec decode. Gain: +32% code decode with MTP (final median 41.5, n=5) and +36% without speculation (n not stated) on one GB10 [Community-measured]. Cost: none on current SGLang; FMHAv2 prefill with fp8_e4m3 KV is refused, so prefill stays on flashinfer. Risk: this is dense XQA; it must not be confused with sparse trtllm-gen decode (lever 1). XQA in vLLM silently disappears without the cubin wheel or artifactory access. Smallest falsifying experiment: one own SGLang lane, decode backend flashinfer vs trtllm_mha, frozen harness plus 120K needles x 4, backend line read from the log.
7. **Top-k fallback and padded-row clamp on DSA/DSV4 lanes (vLLM #54110 and #51538, or capture every graph size)** — applies to: vLLM DeepSeek V4/V4.1 and GLM DSA x MTP + CUDA graphs. Gain: `top_k_per_row_decode` 1.6-3.6x faster than `persistent_topk` in micro-benchmarks at 6 and 48 rows [Community-measured]; removes a deterministic padded-graph hang (3,364/3,364 probes clean with full capture sizes) [Community-measured]. Cost: a vLLM rebase or backport; full capture sizes cost capture time and graph memory. Risk: 487ecf187 lacks both patches (content check); whether the own overlays backport them is unknown (§8). Graph capture and padded replay are on [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md). Smallest falsifying experiment: grep the installed build for the #51538 clamp and the #54110 fallback; if absent, a padded-batch replay (6 real rows into an 8-row graph, MTP) for 1 hour.
8. **SGLang SM12x `fa4` for MHA prefill or draft attention** — applies to: SGLang builds containing `889c2f31` x dense MHA and DFlash draft x all topologies. Gain: kernel-level 3.61x prefill and 1.214x paged decode over SGLang Triton [Community-measured]; end-to-end unknown on any own lane [Proposed]. Cost: opt-in flag. Risk: Dao-AILab CuTe FA4 shapes fail to compile on SM121 (packed QSA varlen, flash-attention #2453), so an engine that resolves `fa4` to the CuTe path instead of SGLang's own kernel breaks; the own `fa4` lane never logged which kernel ran. Smallest falsifying experiment: boot the flag with a profile or kernel-name log proving `flash_attention_v4_sm120` ran, then flashinfer vs fa4 draft attention on the frozen harness.
9. **NVFP4 KV for sparse MLA (density)** — applies to: vLLM GLM EXL3 (community 288 B/token latent) and DeepSeek V4 (FlashInfer #4955, 384 B/token, `kv_cache_format="nvfp4"`, from v0.7.0). Gain (KV dtype and row bytes: [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md)): pool density about 2.3x with 0.36 ms/layer decode cost and byte-identical probes (workload unstated) [Community-measured]; #4955 medians are SM120, not GB10. Cost: gather-dequant kernel per layer. Risk: NVFP4 KV on the QSA path regressed single-stream decode about 29% on a GB10 and produced token-0 failures (sglang #36797) [Community-measured]; a KV dtype routed to the wrong kernel cost ~16x decode at 600K+ (DeepSeek V4, §7). Smallest falsifying experiment: KV pool and C1/C8 decode at 8K and 262K plus greedy parity against fp8_ds_mla on one lane.
10. **vLLM `B12X` paged attention (v0.30.0, opt-in)** — applies to: vLLM v0.30.0+ x dense causal attention x SM12x. Gain: unknown on a GB10; PR benchmarks are RTX PRO 6000 only [Proposed]. Cost: extra package. Risk: new backend, no GB10 correctness evidence. Smallest falsifying experiment: one dense-attention lane, FLASH_ATTN vs B12X, same graph mode, frozen harness plus needles.
11. **GB10-tuned QSA Triton launch table** — applies to: vLLM Qwen 3.8 Flash Next x 8 or more concurrent decodes. Gain: none at 1-5 streams [Measured]; roughly 2% of the decode step at 8 concurrent rows [Interpretation]. Cost: an overlay to carry. Risk: none observed. Smallest falsifying experiment: C8 frozen-harness A/B; otherwise leave it dropped. The larger QSA cost is the MQA scorer plus top-k at 131K and above (0.3-0.65 ms per step at 8 rows), which the table cannot move [Measured].

## 6. Protocol

This is the protocol for changing an attention backend, a FlashInfer version, or a sparse-attention guard on a GB10 lane. It follows the fleet rules on the entry page and the incidents in §4 and §7. See [Profiling protocol](14-profiling-protocol.md) for kernel attribution and [Quality and correctness gates](21-quality-and-correctness-gates.md) for output gates.

Preconditions.
- All index rules apply (see [the entry page](README.md)), in particular: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor measured after the longest qualified prefill, and traffic stopped below 4 GiB; a greedy logprob probe after every relaunch; discard the first request and warm every serving shape before timing; a unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection or configuration line read on every rank; at least 3 repetitions with a closing baseline (A/B/A); MemAvailable sampled every 1-2 s with zero NV_ERR_NO_MEMORY or Xid lines; no reboot or power cycle without per-node permission; correctness gates from [Quality and correctness gates](21-quality-and-correctness-gates.md) before any speed number. For this page: discard the first request after a backend or FlashInfer change (first use JIT-compiles).
- No memory overcommit: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor while serving, KV pin raises of no more than 1.5 GiB per boot, and one memory variable per boot; memory freed by a change (an indexer workspace, a smaller KV row) is taken as host headroom at the original pin, never spent in the same boot. Stop all benchmark traffic at 4 GiB MemAvailable on any node.
- Clean window: no outside traffic; poll running requests before each pass and discard any pass that overlaps outside traffic.
- One variable per boot. A restart for an A/B skips the image pull, so the only difference is the variable under test. A FlashInfer upgrade is one variable even though it carries many commits; say so in the packet.
- Never restart a client gateway. Restarting the lane's engine is the operator's step; a gateway restart is the operator's decision.
- Build receipt, read, not inferred: engine commit; `flashinfer show-config` (prints flashinfer, flashinfer-cubin and flashinfer-jit-cache versions and module status; flashinfer/__main__.py:346 @ v0.6.17) or `flashinfer collect-env --json`; the autotune and JIT cache paths (`<version>/<arch>`); `cuobjdump --list-elf` of the `sparse_mla_sm120` module (`sm_121a` vs `sm_120` family); for sparse MLA, a grep of the installed `_sparse_mla_sm120.py` for the model types it supports (`GLM53_NOPE` present or not) and of `prefill_kernel.cuh` for the #4732 alt-barrier helpers; for vLLM DSA lanes, a grep for the #51538 clamp and the #54110 fallback. Never cite public-head source as the installed build.
- Caches persisted and backed up before the change: FlashInfer JIT and autotune caches, `VLLM_CACHE_ROOT/deep_gemm` (the DeepSeek V4 image runs indexer kernels from persisted cubins; a miss fails at first use), Triton cache.

Pinning FlashInfer in an image.
1. Install `flashinfer-python`, `flashinfer-cubin` and `flashinfer-jit-cache` at one version; the jit-cache carries the `+cu130` local tag and `jit/env.py` enforces the match. Cubin wheels come from flashinfer.ai/whl (PyPI stops at 0.6.13), jit-cache from flashinfer.ai/whl/cu130, and from v0.7.0 the arch provider wheel (`flashinfer-jit-cache-sm121a` or `-sm120f`) as well as the shim. [Code-verified]
2. Do not float `FLASHINFER_REF=main` against an engine commit that pins `nvidia-cutlass-dsl`: 0.6.18 pinned 4.7.0 against vLLM's 4.5.2 and the resolver failed (forum topic 375595 p.2). After any nightly install, audit transitive pins: one GB10 kit saw a FlashInfer nightly downgrade `nvidia-nccl-cu13` to 2.29.7 and skew cutlass-dsl (tonyd2wild GLM NVFP4 kit item 3). [Community-measured]
3. Pin the engine tree by SHA, never a branch: a force-pushed branch booted, captured graphs and emitted one repeated token (tonyd2wild DSv4.1 RECIPE @ d45538f6). Floating "current" prebuilt tags (for example eugr's `prebuilt-flashinfer-current`, 0.7.0-c6ec2cce-d20260921 on 2026-09-21) are not pins; record the resolved version. [Community-measured]
4. Cap runtime JIT so it cannot take the host down (`MAX_JOBS=2 FLASHINFER_NVCC_THREADS=1`), set `VLLM_USE_FLASHINFER_SAMPLER=0` if a first-request sampler JIT is not wanted, and raise `VLLM_ENGINE_READY_TIMEOUT_S` for a cold `121a` cache (1800 s worked where 600 s failed, vLLM #48031). After a header-only FlashInfer fix, delete stale `.o`/`.so` in the JIT cache before the A/B (PR #4732 note). [Community-measured]
5. Remove stale resolver or dispatch blocks when layering an image on an older base; assert the intended kernel is the one the resolver returns (§7). [Measured]

Change. Exactly one of: `--attention-backend` / `--attention-config` (vLLM), `--prefill-attention-backend` / `--decode-attention-backend` / `--speculative-draft-attention-backend` / `--dsa-*-backend` (SGLang), `-fa` (llama.cpp), a KV cache dtype, the FlashInfer version, a sparse-attention guard, a launch or autotune table. Never set `VLLM_ATTENTION_BACKEND` or `VLLM_FLASH_ATTN_VERSION`; they no longer exist (PR #32812).

Run.
1. Boot one arm and confirm the backend on every rank from the log, never from the flag: vLLM `Using <X> attention backend out of potential backends: [...]` (auto) or `Using <X> backend.` (explicit), `Using FlashAttention version 2`, `FlashInfer resolved query dtypes: … decode_backend=… arch=sm121`, and the CUDA-graph line `CUDAGraphMode.FULL_AND_PIECEWISE is not supported with spec-decode for attention backend …; setting cudagraph_mode=…`; SGLang `Attention backend not specified. Use <X> backend by default.` and `Set DSA backends … prefill=…, decode=…`; llama.cpp `flash_attn = …` plus the probe line. A boot with no such line is a boot where the change did not run. Record the resolved graph mode: a backend A/B that changes graph mode is a graph-mode A/B (§4, vLLM #49547).
2. For a new kernel or guard, run an off-lane parity test first at the lane's shapes (padded head count, top-k, page size, batch rows 1-64 and above 64, since 64 rows is the decode/prefill boundary in `sparse_mla_sm120`), then a kernel micro-benchmark on an idle node. Report the kernel figure and the serving figure separately: 2.07x at the kernel was +4.45% end to end (sglang #36845).
3. Serving A-B-A through the frozen harness with a same-session restore: C1 and the lane's working concurrency, short decode fixtures x 3, cold-nonce prefill at 8K and 95K x 5.
4. Long-context correctness gate before any speed claim: needles at 120K or more with n of at least 4 per point, 4 repeated coding outputs, a greedy reference capture compared token for token, and a garble gate. Short benchmarks never reach the corrupting sparse kernels (§4 own A1; sglang #36845; tonyd2wild DSv4.1 RECIPE).
5. For speculative lanes, capture CUDA graphs at the exact row counts the lane uses (or every size up to `max_num_seqs x (k+1)`) and treat a replay stall with GPUs pinned near 96% utilisation and idle host workers as a padded-graph hang, not a slow kernel (FlashInfer #5015; see [CUDA graphs and launch overhead](01-cuda-graphs-and-launch-overhead.md)).
6. For FlashInfer + MTP changes, soak 600 s at the lane's depth and concurrency with async scheduling recorded as a variable (vLLM #37754).
7. Watch MemAvailable at 1 s resolution on every node through the longest prompt; record Xid and allocation-error counts.

Record (packet fields): build receipt above; the one variable and its two values; the backend and graph-mode log lines per rank; topology, per-rank heads (and padding), KV dtype and row bytes, page size, top-k; parity cases and max abs error; micro-benchmark per shape with spread; frozen-harness C1 / Cn decode, prefill at each depth with repetition spread; needle and repeated-output results; KV pool tokens; minimum MemAvailable per node; Xid and allocation-error counts; discarded passes and why.

Pass gate. Every rank logs the intended backend; the long-context gate passes with zero token-0, empty or garbled outputs and greedy parity with the reference; decode and prefill at or above baseline beyond the frozen harness's repetition spread (quick probes do not count, §7); no hang in soak; zero Xid and allocation errors; minimum MemAvailable at or above the 5 GiB warm floor; KV pool change recorded and accepted.

Rollback. Revert the one variable (flag, guard, overlay, or the three-package FlashInfer pin) through the lane's recipe promote/previous mechanism [Interpretation]; restart with the pull skipped; the FlashInfer JIT and autotune caches are keyed by version and arch, so the previous version's `<old-version>/121a` cache is reused if it was kept [Code-verified]; confirm from the backend log line on every rank that the old path runs, and run one cold 8K plus a 120K needle before the lane serves again. No upstream engine documents an attention-backend rollback beyond these pins.

## 7. Anti-patterns and known-bad

- [Measured] Widening a trtllm-gen / FlashInfer sparse-decode guard from SM100/SM120 to SM121 because it boots and passes short API gates: own 2 of 4 coding outputs became token-0 / "!" loops ("2026-08-27 Flash Next dual-node upstream recipe audit"); community 32/32 token id 0 at 120K-210K with HTTP 200, and the circulating "SM121 QSA guard fix" was retracted upstream by #36806 [Community-measured].
- [Measured] Layering a new image on an older base that still carries a BF16-only SM121 resolver: it shadowed the FP8-capable Triton QSA kernel and the first production boot failed at graph warmup. Assert and remove stale resolver blocks.
- [Historical diagnostic] Citing public-head source as the installed build: one first-pass claim that native GLM NoPE was compiled into the running engine was wrong by 278 commits; only a few Python files had been read from the container. Grep the installed files.
- [Historical diagnostic] Trusting a docstring over the code path: the GLM adapter's docstring says prefill keeps 22 heads, but the code pads every call because a 22-head prefill killed the engine.
- [Code-verified] Selecting a vLLM backend through `VLLM_ATTENTION_BACKEND` or `VLLM_FLASH_ATTN_VERSION`: both were removed in January 2026 (PR #32812), which explains a community TP2 sweep where FLASH_ATTN stayed selected on an FP8 checkpoint with `VLLM_ATTENTION_BACKEND=FLASHINFER` visible in the process environment. Read the "out of potential backends" line.
- [Community-measured] Reading a backend A/B that changed CUDA-graph mode as a kernel result: vLLM #49547's +16% for FLASH_ATTN over FLASHINFER is entirely the PIECEWISE downgrade under spec decode.
- [Community-measured] Confounded "attention A/Bs" that are not backend comparisons: GLM-4.7-Flash TRITON_MLA 41.6 / 33.1 / 26.0 vs FLASHINFER + FP8 KV 40.2 / 27.3 / 18.8 tok/s (vLLM 0.14) ran the FP8 arm with MLA disabled (`VLLM_MLA_DISABLE=1`), so it is MLA-on vs MLA-off plus a KV dtype change (seanGSISG @ d4f5c41e); SGLang 0.5.9 flashinfer ~52 vs 0.5.10 triton 77.4 tok/s changed the engine version (forum topic 365555); a MiniMax M2.7 matrix changed the MoE FP4 path (topic 366324, post 13); TensorRT-LLM #12706's 4.8 -> 40.0 tok/s compares MoE backends; a Mistral-Small-4 12-15 vs 35-41 tok/s gap is a speculation delta.
- [Community-measured] TRITON_ATTN for the GLM DFlash2 draft (drafters: [Speculative decoding](02-speculative-decoding.md)): the mask is causal inside the draft block on that image and later-position acceptance collapses; the kit reports structured decode dropping to about 29 tok/s at 0.31 acceptance against 65.1 tok/s at 0.959 (baseline median of 5 x 400 tokens; the TRITON_ATTN run's date and protocol are not stated) (MiaAI-Lab README @ 71962cd1). The own recipes prohibit it.
- [Community-measured] Using FlashInfer's non-tensor-core batch decode wrapper at GQA 16 or more: illegal memory access (FlashInfer #2849, 0.6.6 on a GB10). The maintainer states it affects all SM architectures, not only SM121, and points to cudnn or trtllm-XQA decode or `use_tensor_cores=True`; the fix PR #2895 was never merged.
- [Community-measured] Relaxing FlashInfer's SM90 gate on FP8 FA2-MLA KV and stopping at "invalid argument": the fp8 branch forces a Hopper tile (117,312 B > 101,376 B). One kit caps the tile and runs FP8 FA2-MLA in production (rel-err ~0.005); unpatched, the path is unusable.
- [Community-measured] Assuming "FA4" means the same kernel everywhere: Dao-AILab CuTe FA4 fails to compile on SM121 for QSA's packed varlen shape ("expects coord and shape of view are weakly congruent", sglang #36845; flash-attention #2453 open) and for a video DiT packed shape, while SGLang's `fa4` on SM12x is its own kernel family (§2). Log which one ran.
- [Community-measured] Baking an indexer or top-k shortcut into a captured CUDA graph: vLLM #50004's adaptive top-k and #49486's short-context indexer skip, replayed against longer prefixes, silently corrupted tokens under MTP + prefix caching + graphs on two DGX Sparks (upstream #51318, #52492). Any shortcut must be barred during stream capture.
- [Community-measured] Routing a KV dtype to the wrong kernel: DeepSeek V4 `nvfp4_ds_mla` fell to the BF16-KV path, about 16x slower decode at 600K+ (1.0 vs 17.3 tok/s); fixed by routing to the FP8-KV path. Confirm the kernel, not the dtype string (KV dtypes: [KV cache and prefix caching](10-kv-cache-and-prefix-caching.md)).
- [Historical diagnostic] Spending freed indexer workspace on a bigger KV pin in the same boot: right-sizing the GLM indexer workspace together with a +4.0 GiB KV pin raise starved node-1 (SSH banner timeouts, swap thrash). Indexer transients also scale with chunk x prefix and wedged an own three-node DeepSeek V4.1 lane on a ~200K prompt.
- [Measured] Quick probes as evidence: a 3-rep probe claimed +38% decode that the frozen harness did not reproduce ("2026-09-23 GLM TP3 V3.2 verification").
- [Community-measured] Scout and folklore claims that do not survive the source: FlashInfer #3294's "cubin 0.6.11 has no sm_120/121, so garbage tokens" was withdrawn in-thread (the jit-cache kernels are `120f`, "the cuobjdump showing sm120 is just the display format"; the garbage was a cutlass-dsl wheel collision plus a MoE bug); FlashInfer PR #3275 limits sm110 builds and is not the "12.1a aarch64 wheel" change (that was #3907, closed unmerged); vLLM #50707's "FA2 cannot do non-causal DFlash draft attention on SM121" was self-corrected by its reporter (mixed sliding and full drafter layers in one KV group); "FlashInfer MLA is ~30x slower on SM121" (scottgl9 fork README) and "FP8 + FlashInfer crashes on SM121, use TRITON_ATTN" (conselara notes) have no methodology, kernel name or version.
- [Community-measured] "FlashInfer 0.6.17 NaNs on 64-256-row batches" read as a sparse-MLA fault: the kit's bisect probe exercises the dense FA2 MLA wrapper (`BatchMLAPagedAttentionWrapper(..., backend="fa2")`, H=32), not `sparse_mla_sm120`, so it does not contradict clean 0.6.17 runs on FLASHINFER_MLA_SPARSE_SM120 lanes (tonyd2wild GLM NVFP4 kit @ 9fea48c1) [Interpretation].
- [Code-verified] Using a community Blackwell GPU wiki's instruction matrix: it marks `wgmma.async` available on SM 12.0, but the PTX ISA restricts wgmma to sm_90a.
