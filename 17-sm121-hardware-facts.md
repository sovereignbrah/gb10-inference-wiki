# SM121 hardware facts card: what a GB10 actually is

Hardware for every own row: three ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 128 GB unified LPDDR5x), node-1, node-2 and node-3, driver 580.173.02, ASUS firmware v0104, direct-attach 200 Gb/s RoCE between nodes. No own device-query, `bandwidthTest`, STREAM or Nsight Compute capture exists; every resource limit and instruction-family statement below is read from NVIDIA documents or source code, not measured on these nodes. Code is quoted at these pins: vLLM `34b0690`, SGLang `2909f84`, llama.cpp `6e60f35`, ExLlamaV3 `6b84a21`, antirez/ds4 `0aaea5a`, CUTLASS `0b55a2f`, FlashInfer `06aa49c`, Triton `2cfa167`. NVIDIA documents are the versions fetched 2026-09-23 (CUDA Programming Guide compute-capabilities appendix, Blackwell Tuning Guide, PTX ISA 9.4). The own lanes run older builds, so a code line says what upstream does now, not what a given lane runs.

## 1. What it is

A GB10 is a small NVIDIA chip that puts an Arm CPU and a Blackwell-generation GPU on one package and gives both the same 128 GB of memory. It is not a shrunken datacenter Blackwell. Its GPU reports compute capability 12.1 (the version number kernels are compiled for), the same family as RTX 50-series cards and not the B200 family, so it lacks the datacenter features many fast kernels were written for: no tensor memory (TMEM, a datacenter on-chip buffer), no `tcgen05` or `wgmma` matrix instructions, and only 99 KB of shared memory (fast per-block scratchpad) per thread block. What it does have is 48 SMs (the GPU's compute clusters), the older warp-level `mma.sync` tensor-core instructions extended with FP8 and block-scaled FP4 formats, and a memory system that NVIDIA rates at 273 GB/s but that community tests reach at about 200-246 GB/s idle, depending on the probe (§3), and much less while a model is running. That memory is shared with Linux, so the free memory an engine can use is what the kernel calls `MemAvailable`, not what the GPU driver reports, and running out usually freezes the machine instead of raising a clean error. The toolchain matters as much as the silicon: a kernel built for the wrong target (`sm_120a` instead of `sm_121a` or the `12.0f` family) either refuses to load or silently loses a feature, and CUDA 12.9 or newer is required to target the chip at all. This card collects what is documented, what has been measured and by whom, and what is still unknown, so the other pages can cite one place. See [Memory management on a unified-memory GB10](11-memory-on-unified-memory.md), [Clocks, thermal, and power on GX10 / DGX Spark](13-clocks-thermal-power.md), [Engine dispatch maps](16-engine-dispatch-maps.md) and [Kernel authoring on SM121](15-kernel-authoring-sm121.md).

## 2. How each engine does it

### vLLM

Build targets (`CMakeLists.txt` and `cmake/utils.cmake` @ 34b0690).
- CUDA 13.0 and newer: the top-level `CUDA_SUPPORTED_ARCHS` lists (`:116-120` for CUDA ≥ 13.4, `:121-126` for ≥ 13.0) are `7.5;8.0;8.6;8.7;8.9;9.0;10.0;11.0;12.0`, with no 12.1; the comment says the build relies on family targets. Per-kernel lists use `12.0f` (Marlin `:615`, scaled_mm c3x `:818`, SM12x NVFP4 `:992`, Marlin MoE `:1315`). [Code-verified]
- A `TORCH_CUDA_ARCH_LIST=12.1a` request does not produce `12.1a` cubins on CUDA 13.x. `CMakeLists.txt:227-233` first intersects the requested arches with `CUDA_SUPPORTED_ARCHS`, which reduces 12.1a to 12.0, so SM12x kernels build as `12.0f`. The family fallback in `utils.cmake:410-440` (a `12.0f` source matching a `12.1a` target and emitting `12.1a`) only fires if 12.1a survives that filter, which it does not on CUDA ≥ 13.0. [Code-verified: the pinned cmake functions were executed in isolation, not a full build] This matches the "after" log in PR #49904 ("CUDA supported target architectures: 12.0", then "12.0f") and the empirical report in PR #38957 (open, head `35e38d0`) that a CUDA 13.0 GB10 build asked for `12.1a` got `12.0f`-only cubins. Confirming it on a built `_C*.so` with `cuobjdump --list-elf` is still [Proposed].
- CUDA 12.8-12.9: the supported list includes 12.1 (`:127-129`) and kernels use `12.0a;12.1a`. [Code-verified]
- PyTorch's vendored `select_compute_arch.cmake` rewrites `2.1` to `2.1(2.0)`, which turned `12.1` into `arch=compute_20,code=sm_121`; with `TORCH_CUDA_ARCH_LIST` unset a GB10 build produced only `sm_75` cubins and crashed in `profile_run` (CUDA 13.0.88, torch 2.11.0+cu130). PR #49904 (merged, `74587939`) makes `extract_unique_cuda_archs_ascending` prefer `code=sm_*` over `arch=compute_*` (`utils.cmake:264-266`). [Code-verified]

Runtime memory. `vllm/utils/mem_utils.py:138-151` replaces the `cudaMemGetInfo` free figure with `psutil.virtual_memory().available` (Linux `MemAvailable`) when `current_platform.is_integrated_gpu()` is true, which reads `torch.cuda.get_device_properties().is_integrated` (`platforms/cuda.py:728-729`); on GB10 this path is the default. `release_device_memory_under_pressure` (`mem_utils.py:45-78`) empties the caching allocator when available memory falls below 20% of total. `gpu_memory_utilization` is applied to total memory and is overshot during start-up profiling on GB10 (vllm#46307, open; §4); PR #49760 (open) proposes capping the integrated-GPU budget at available memory minus a host reserve. [Code-verified] + [Community-measured]

Kernel gates on CC 12.1.
- FP8 CUTLASS scaled-MM dispatch uses `enable_sm120_family` (`__CUDA_ARCH__` from 1200 to below 1300; `csrc/libtorch_stable/cutlass_extensions/common.hpp:128-134`). `enable_sm120_only` (`== 1200`, `:114-118`) is still defined but referenced nowhere else in the tree, so the community-reported trap where it faulted every FP8 GEMM on real `sm_121f` cubins (saifgithub/vllm-gb10-sm121 @ 7e5cec5) is not reachable at this pin. [Code-verified]
- `FLASHINFER_B12X` NVFP4 MoE is "intentionally excluded from auto-selection until the upstream CUTLASS SM121 MMA op guard is resolved" (`model_executor/layers/fused_moe/oracle/nvfp4.py:191-193`). [Code-verified]
- DeepGEMM is live on GB10: `support_deep_gemm()` in `platforms/cuda.py:719-725` includes family 120, and `utils/deep_gemm.py:85` selects UE8M0 scales for it. [Code-verified] DeepGEMM is admitted on sm_121; the #54125 `profile_run` crash was a skipped UE8M0 repack fixed upstream (`f8e0602713`); FP32-scale mis-selection and a K = 2560 silent-corruption window remain (see [GEMM backends and quantization formats on SM121](09-gemm-backends-and-quant-formats.md) §7). PR #54600 (open) reports unmodified DeepGEMM passing all 984 warmup kernels at about 27 tok/s and that excluding sm_121 breaks `profile_run`. [Community-measured]
- Attention on SM121 per the community table in PR #31740 (unmerged): TRITON_ATTN and TRITON_MLA work, FlashInfer attention covers SM75-SM121, FlashInfer MLA and CUTLASS MLA are SM100-only, FlashMLA Sparse is SM90/SM100. Sparse MLA had no legal backend on a 4x GB10 nightly (vllm#45317, open). [Community-measured] See [Attention backends on SM121](06-attention-backends-sm121.md).
- EXL3: upstream vLLM has no EXL3 kernel; the only hit in the tree is a documentation mention, and the `exllama` path under `model_executor/kernels/linear/mixed_precision/` is the legacy GPTQ kernel. [Code-verified negative]

### SGLang

- Arch helpers in `python/sglang/srt/utils/common.py` @ 2909f84: `is_sm120_supported` checks major 12 with CUDA ≥ 12.8, so it includes GB10 (`:293-296`); `is_sm120()` is exactly (12, 0) and excludes GB10 (`:322-325`); `is_sm121()` is exactly (12, 1) (`:328-332`). A guard written with `is_sm120()` silently skips GB10. [Code-verified]
- Free memory: `get_available_gpu_memory` uses `psutil.virtual_memory().available` when `props.is_integrated` (`:445-450`), so `MemAvailable` is the budget on GB10 by default. [Code-verified]
- DeepGEMM: `layers/deep_gemm_wrapper/configurer.py:38-59` accepts `sm_version in (120, 121)` and probes for the SM120 APIs added in DeepGEMM PR #324. An earlier `sm_version == 120` check missed GB10; SGLang PR #34018 (open) re-enables the FP8 `wo_a` path and measures about −4.2 ms per decode step for that PR alone (bs=1, 2x DGX Spark TP=2, DeepSeek-V4-Flash-0731 + DSpark). The −10.1% (70.31 → 63.19 ms) in the same PR includes a separate MHC-default change. [Code-verified] + [Community-measured]
- Memory fraction: in one community recipe `--mem-fraction-static 0.76` left 21.30 GB free after graph capture and 0.80 crashed at 3 concurrent requests, because FlashInfer FP8 autotune and CUDA-graph capture allocate outside the tracked pool; the same recipe relays that the SGLang cookbook rejects 0.85 on DGX OS because of earlyoom (hasso5703/dgx-spark-qwen38 `docs/gb10-memory.md` @ 54bb2c3). [Community-measured]
- Known-bad defaults: Hopper-sized extend-attention blocks need 106,496 B against the 101,376 B limit (PR #17908, closed unmerged). A dated tracking issue (sglang#11658, closed 2026-01-17) reported FP8 CUTLASS kernels failing to dispatch on `sm_121a` and falling back to legacy FP8; a later comment there traces one garbage-output case to a fused `qkv_proj` load bug instead. Re-check at the lane's pin. [Community-measured]

### llama.cpp and forks

- Mainline llama.cpp @ 6e60f35. Without `GGML_NATIVE`, CUDA ≥ 12.8 adds `120a-real` and CUDA ≥ 12.9 adds `121a-real`; the comment says `120f-virtual` "would in principle work" but trips CMake's arch-validation regex unless CMake is ≥ 3.31.8 below 4.0, or ≥ 4.0.2 (`ggml/src/ggml-cuda/CMakeLists.txt:40-55`). `common.cuh:60-61` defines `GGML_CUDA_CC_BLACKWELL 1200` and `GGML_CUDA_CC_DGX_SPARK 1210`; `BLACKWELL_MMA_AVAILABLE` covers 1200 up to below 1300 (`:296-298`) and gates NVFP4 sub-block scales. [Code-verified]
- Memory reporting: `ggml_backend_cuda_device_get_memory` reports `MemAvailable` from `/proc/meminfo` when the CUDA device property `integrated` is set or `GGML_CUDA_ENABLE_UNIFIED_MEMORY` is set (`ggml-cuda.cu` around `:5057-5070`), but the backend's own `integrated` flag is forced false at `:307`, "temporarily disabled due to issues with corrupted output (e.g. #15034)", so integrated-GPU buffer shortcuts are off on GB10. `sharedMemPerBlockOptin` is read unchecked (`:341, :348`); a community PR adding a sanity check after a bad readout on an RTX 5090 (#22338) was closed unmerged. [Code-verified]
- antirez/ds4 @ 0aaea5a: `make cuda-spark` builds with `CUDA_ARCH=sm_121`, which the Makefile maps to `-gencode arch=compute_121a,code=sm_121a -DDS4_CUDA_HAVE_MXF4=1` (`Makefile:43-46, 299-300`). [Code-verified] A local build of the Entrpi fork emitted `compute_121a,code=sm_121a` (2026-08-22 Entrpi ds4 v0.6.3 single-node qualification). [Measured] Entrpi/ds4 @ b0a147a7fb carries the same mapping (`Makefile:44-45, 172-173`). [Code-verified]
- Anemll/dspark-vllm-gx10 @ 081fda9754 is a vLLM port, not a llama.cpp fork; it builds with `--build-arg torch_cuda_arch_list=12.1a` (`scripts/build-image.sh:36`). Given the vLLM arch filter above, whether that yields `12.1a` or `12.0f` cubins depends on the vendored tree's `CUDA_SUPPORTED_ARCHS`. [Code-verified] build flag; outcome open (§8).
- No own mainline llama.cpp measurement on GB10 exists.

### ExLlamaV3 in vLLM

- Upstream ExLlamaV3 @ 6b84a21 uses only baseline instructions: `mma.sync.aligned.m16n8k16` f16 → f32/f16, `mma.sync m8n8k4`, `cp.async.cg` with `.L2::cache_hint`, and `ldmatrix m8n8.x4` (`exllamav3/exllamav3_ext/ptx.cuh:36-198`); `det_gemm.cuh` also uses `mma.sync m16n8k32 s8` (baseline sm_80). A whole-extension scan finds no `kind::`, `cp.async.bulk`, `wgmma`, `tcgen05` or cluster usage. [Code-verified]
- `util/arch_list.py` sets `TORCH_CUDA_ARCH_LIST`, only when it is unset, to the device capability clamped to the highest arch in `torch.cuda.get_arch_list()` with suffixes stripped, plus `+PTX`. [Code-verified] On a cu130 torch whose list tops out at `sm_120`, a GB10 JIT build therefore targets `12.0+PTX`, a baseline target, which is enough for these instructions. [Interpretation]
- EXL3 inside vLLM exists only in community GLM and DeepSeek kits. The own cooperative MoE kernel builds at 512 threads, 63 registers, 0 spills, 24,576 B dynamic plus 48 B static shared memory, 2 resident blocks per SM by arithmetic (2026-09-20 GLM 5.3 Flash TP3 frontier dossier v2, ptxas output, not an occupancy capture). [Code-verified] With 48 warps per SM a 512-thread block caps at 3 per SM by warps, registers bind at 2, and the 24-versus-32 blocks question below does not affect it. [Interpretation] The binding limits on SM121 for this family are registers and the 99 KB shared-memory ceiling, not instruction features. [Interpretation]

## 3. What is different on GB10 / SM121

Identity and resource limits.
- [Code-verified] GB10 is compute capability 12.1. An NVIDIA moderator stated it on the developer forum (topic 342864), and NVIDIA's CUDA GPU table lists "12.1 NVIDIA GB10 (DGX Spark)" while RTX 50-series and RTX PRO Blackwell parts are 12.0.
- [Code-verified] Programming Guide Tables 30/31 have one "12.x" column shared by 12.0 and 12.1: 64 K 32-bit registers per SM and per block, 255 per thread, 24 resident blocks per SM, 48 resident warps, 1,536 resident threads, 1,024 threads per block, 100 KB shared memory per SM, 99 KB per block, 32 banks, 64 KB constant memory, FP32:FP64 non-tensor throughput 64:1. The 24/48/1,536 set is the same as CC 11.0; 9.0 and 10.x have 32/64/2,048.
- [Code-verified] Table 32: the 12.x unified L1/shared cache is 128 KB with shared-memory carveouts of 0, 8, 16, 32, 64 or 100 KB. Allocations over 48 KB per block need dynamic shared memory and an explicit opt-in; PTX ISA 9.4 §5.1.7 caps static shared memory at 48 KB per CTA except on arch-specific targets, where `sm_120a`/`sm_121a` get 100 KB against 228 KB for `sm_90a`, `sm_100a/103a/107a` and `sm_110a`.
- [Code-verified] CUTLASS @ 0b55a2f: `sm120_smem_capacity_bytes = 101376` (`include/cutlass/arch/arch.h:47`); `struct Sm120` (`:118-121`) declares `kMinComputeCapability = 120` and `kSharedMemoryCapacityBytes` with no TMEM member, and there is no `struct Sm121`, so SM121 code builds against `Sm120`.
- [Community-measured] The opt-in readout on a GB10 is 101,376 B; a CUTLASS MoE grouped FP4 tile needing 102,400 B failed and 13 of 16 autotuner tactics failed (cutlass#3144, closed; NVIDIA staff say the fix is in CUTLASS 4.4.2).
- [Interpretation] The Blackwell Tuning Guide §1.4.1.1 says 32 blocks per SM for 10.0 and 12.0 and "128KB" shared memory per SM for 12.0; the 128 KB is the unified-cache size, so that paragraph mixes quantities, and 24 is the better-supported value. It has not been read from a GB10. The difference matters only for single-warp CTAs (32 threads or fewer): 24 of 48 warps (50%) versus 32 of 48 (67%). A 64-thread CTA gets 24 CTAs (48 warps) under either limit.

Instruction families.
- [Code-verified] Absent: `tcgen05.*` and TMEM (PTX ISA 9.4 lists `tcgen05.alloc` for `sm_100a`, `sm_101a` (renamed `sm_110a`) and the `sm_100f`/`sm_110f` families only; CuTe enables `CUTE_ARCH_TCGEN05_*` only for SM100/101/103/107/110; an NVIDIA employee on forum 359598: "sm12x don't have tcgen05"). Absent: `wgmma.mma_async` (§9.7.17.5.2, "Requires sm_90a").
- [Code-verified] Present at baseline: `mma.sync` m16n8k16 f16/bf16 → f32 (sm_80+), FP8 `.e4m3/.e5m2` mma (sm_89+), `cp.async` (sm_80+), `ldmatrix` (sm_75+), `stmatrix` (sm_90+). `ldmatrix .m16n16/.m8n16` with `.b8`, `stmatrix .m16n8` and `setmaxnreg` need `sm_120a` or the `sm_120f` family (PTX 8.8+).
- [Code-verified] Present at family level: dense block-scaled MMA. For dense `mma`, `.kind`, `.block_scale`, `.scale_vec_size` and the `.e3m2/.e2m3/.e2m1` types "require sm_120a and are supported on sm_120f or higher in the same family from PTX ISA version 8.8", so a `compute_120f` cubin can carry dense `kind::mxf4nvf4` (NVFP4) and `kind::mxf8f6f4`. CuTe enables the F8F6F4, MXF8F6F4, MXF4NVF4 2X-UE8M0 and 4X-UE4M3 MMA atoms for SM120/120A/121/121A with nvcc ≥ 12.8; the 4X-UE8M0 atom needs CUDA 13.1+ (`include/cute/arch/config.hpp:158-176`).
- [Code-verified] Arch-specific only: sparse FP4. For `mma.sp`, `.kind::mxf4nvf4` and `.kind::mxf4` are listed for `sm_120a` and `sm_121a` only, not the `sm_120f` family. Because an `a` cubin runs only on its exact CC, 2:4-sparse NVFP4/MXFP4 on GB10 needs a native `sm_121a` build. This is the one GEMM-relevant instruction-level reason to prefer `sm_121a` over `12.0f`. PTX 9.4 lists a few other `sm_120a`/`sm_121a`-only features (`cvt .s2f6x2`, multimem FP8 types and `.acc::f16`, and `fabric.try_pullred` reductions) that current inference kernels are not known to use. `.rs` rounding is `sm_100a/103a/107a` only, which explains TensorRT-LLM#14575's "Feature '.rs' not supported on .target 'sm_121a'". FlashInfer's own SM121 audit (flashinfer#3170) reached the same dense/sparse split after correcting an earlier claim.
- [Code-verified] Programming Guide Table 33: 12.x tensor cores take TF32, BF16, FP16, FP8, FP6, FP4 and INT8, and not FP64 or INT4. Table 29 marks 12.x "Yes" for thread-block clusters, distributed shared memory, the TMA unit, 128-bit atomics and float2/float4 `atomicAdd`; DPX is "Multiple Instr." (emulated) on 11.0 and 12.x.
- [Code-verified] TMA exists at the sm_90 level (`cp.async.bulk.tensor` "Requires sm_90 or higher"); CuTe enables `CUTE_ARCH_TMA_SM90_ENABLED` for SM120A/121A and SM120F/121F and `CUTE_ARCH_TMA_SM120_ENABLED` for SM120/121. On `sm_120a` the `.shared::cluster.global` direction does not support sub-byte types or `.swizzle_atomicity` (PTX ISA 9.4, `cp.async.bulk.tensor` restriction notes under §9.7.10.28).
- [Code-verified] `tile::gather4` into CTA-local shared memory (`.shared::cta`) is legal from sm_100 up, so it works on SM12x; gather4 into `.shared::cluster` needs `sm_100a`/`sm_100f`, `tile::scatter4` is `sm_100a`/`sm_110a` and their families only, and `cp.async.bulk.prefetch.tensor` with gather4 is `sm_100a`/`sm_101a` and families only. Triton PR #8498 (merged, `4d85824a`) enabled `cp.async.bulk.tensor.2d.tile::gather4.shared` on sm_120/121 and noted "All other TMA features except for cluster-related ones are supported on sm_120"; triton#10152 shows ptxas rejecting gather4 into `.shared::cluster` on `sm_121a` with `TRITON_OVERRIDE_ARCH=sm120` set.
- [Code-verified] Clusters and DSMEM exist (`barrier.cluster` and `mapa` need sm_90+). A forum user's `__cluster_dims__` failure on GB10 came from compiling without `-arch`; an NVIDIA moderator compiled and ran the Programming Guide cluster sample with `-arch=sm_120` (forum 357593). Only the portable cluster size of 8 is documented. CUTLASS SM120 collectives fix the cluster shape at 1x1x1.
- [Code-verified] Multicast (`.multicast::cluster` on `cp.async.bulk(.tensor)`) needs only sm_90+, but PTX advises it for `sm_90a`, `sm_100f/100a`, `sm_103f/103a`, `sm_110f/110a`, and the PTX ISA 8.2 change notes say it "may have substantially reduced performance on other targets". Community posts that call it absent on SM121 overstate this; no SM12x measurement exists.
- [Community-measured, contested; single-probe evidence] Tensor-core ceiling. Two register-resident probes disagree: mmapeak (forum 351993, clock not stated) reads BF16 ≈213 and FP8 ≈214 TFLOPS; a hand-PTX probe (getpoppy) reads BF16 123.3 / FP8 246.5 / NVFP4 493, an exact 1:2:4 ladder that matches nvfp4bench's `mxf8f6f4` 243-256 and the 500 TFLOPS FP4 figure (§4). Until an own probe settles it, assume neither 'FP8 = BF16 rate' nor 'FP8 = 2x BF16'.

Memory system.
- [Code-verified: vendor nominal] 128 GB LPDDR5x unified memory, 256-bit interface, "16 channels (256 bit) LPDDR5X 8533", 273 GB/s; 6,144 CUDA cores; 2 copy engines; GB10 SoC TDP 140 W inside a 240 W supply (DGX Spark hardware page). These are nominal, never achieved figures.
- [Community-measured] 48 SMs: nvfp4bench headers on the ASUS GX10, HP ZGX Nano and a Founders Edition; a CUDA 13.0 `deviceQuery` printed "(048) Multiprocessors, (128) CUDA Cores/MP" (kubesimplify @ b74c3c2); Chips and Cheese states 48 SMs. 6,144 / 128 = 48. Own packets only infer 48 from a log line.
- [Community-measured] L2 is 24 MB (nvfp4bench "L2 cache: 24.0 MB" on three SKUs; `deviceQuery` 25,165,824 bytes). Chips and Cheese's latency sweep shows the 24 MB L2; the 16 MB system-level cache is invisible in that sweep, and they judge it non-exclusive with the L2, so its capacity is not additive.
- [Community-measured, contested; each figure is a single-author probe] Achieved DRAM bandwidth from the GPU, idle, depends on the probe: saturating read 227-235; NNNtrance rotating-buffer read 238.6-245.9; copy 215-229; STREAM triad 200-214; decode ruler 230-245 GB/s ([Decode optimization](05-decode-optimization.md) §3). This bullet is the wiki's single statement of the ruler; other pages cite it. Nobody has published a sustained 273 GB/s. Under a running model the residual copy bandwidth falls to roughly 40-50% of idle (§4). CPU-side STREAM is about 116-121 GB/s. See [Decode optimization on GB10: the bytes model](05-decode-optimization.md).
- [Community-measured, contested] Coherence. NVIDIA's DGX Spark datasheet and a partner datasheet say NVLink-C2C delivers a "CPU+GPU coherent memory model"; the hardware page does not use the words. NVIDIA's own forum FAQ (347344, moderator) says `cudaMalloc` memory "cannot be coherently accessed by the CPU complex nor by I/O peripherals", so GPUDirect RDMA is unsupported and verbs buffers should come from `cudaHostAlloc` plus `ib_reg_mr`. For engineering the FAQ is the more specific statement.

Clocks.
- [Community-measured, contested] Clock attributes are labels, not achieved clocks: nvfp4bench reports "Max SM clock 3.00 GHz" on all SKUs, a `deviceQuery` capture reports 2,418 MHz, Chips and Cheese says "up to 2.55 GHz", and the nvfp4bench author observed about 2.6 GHz under load on one unit. [Measured] On the own nodes the median graphics clock under load was 2,392-2,411 MHz stock (advertised maximum 3,003 MHz) and 2,080 MHz with a 2100 MHz cap (2026-09-21 GPU clock-cap sweep, GLM 5.3 Flash EXL3 TP3).
- [Community-measured, contested] The memory-clock attribute returns 0 and `nvidia-smi` shows N/A for it on driver 580.142 (uma_bw author, forum 367851), while a `deviceQuery` capture prints 8,533 MHz. `nvidia-smi` memory-usage columns read "Not Supported" per NVIDIA's own known-issues text, and `nvmlDeviceGetMemoryInfo` can report a total close to `MemTotal`, which is not allocatable capacity (forum 366877).

Interconnect. See [Inter-Spark communication over DAC](03-inter-spark-communication.md).
- [Code-verified: vendor doc] "The NIC connects independently to the two external QSFP ports, and it connects to the SoC through two independent PCIe Gen 5 x4 links." Each QSFP port appears as two Ethernet interfaces and two RoCE devices (for example `rocep1s0f0` and `roceP2p1s0f0`); the port is capped at 200 Gb/s; NVIDIA lists approved 400 mm QSFP112 DACs (spark-clustering page).
- [Interpretation] One PCIe Gen5 x4 link carries about 126 Gb/s raw per direction (32 GT/s x 4 x 128/130), so a single RoCE controller cannot reach the 200 Gb/s port rate. That fits the own 108.8-109.0 Gb/s single-controller RDMA smoke results (§4) and is why the second controller of each port matters.

Toolchain.
- [Code-verified] CUDA 12.9 is the floor. PTX ISA 8.8 (CUDA 12.9, driver r575) introduced `sm_121`, `sm_121f` and `sm_121a`; `sm_120`/`sm_120a` came with PTX 8.7 (CUDA 12.8). CUDA 13.0 = r580, 13.1 = r590, 13.2 = r595. Below 12.9: FlashInfer raises "SM 12.1+ requires CUDA >= 12.9" instead of falling back (`flashinfer/compilation_context.py:81-110`); every CUTLASS SM121 macro is undefined (`include/cutlass/arch/config.h:227-247` requires nvcc ≥ 12.9, while SM120 needs ≥ 12.8 at `:155-174`), so a pre-12.9 build for GB10 can ship only `sm_120` baseline code or PTX; llama.cpp adds `121a-real` only at CUDA ≥ 12.9.
- [Code-verified] Suffix semantics (Programming Guide §5.1.2 and Table 28; NVIDIA family-features blog): an `a` cubin runs only on the exact CC it was built for; an `f` cubin runs on every family member of equal or higher minor; a baseline cubin runs on the same major at an equal or higher minor. `compute_120f` covers 12.0 and 12.1; `compute_121f` covers 12.1 only ("Some families only contain a single member when they are created. They may be expanded in the future"). [Interpretation] On GB10 an `sm_120` baseline cubin loads, an `sm_120a` cubin does not, `12.0f` does, and nothing from 10.x does, so the real choice is `12.0f` or `12.1a`. No NVIDIA sentence says "sm_120a fails on GB10" by name.
- [Community-measured] The `-arch=sm_121a` shorthand "and some CMake paths" can silently drop the trailing `a`, producing plain `sm_121` without block-scaled FP4; use `-gencode=arch=compute_121a,code=sm_121a` (nvfp4bench author, forum 373618).
- [Code-verified] FlashInfer @ 06aa49c keeps the minor and appends `a` for SM 12.1+ (`compute_121a`); `jit/core.py:169-171` hardcodes `sm120a`, `sm120f` and `sm121a` flag sets; `is_sm121a_supported` checks `torch.version.cuda` ≥ 12.9, not nvcc (`utils.py:683-701`). Per flashinfer#3170 (open) release wheels build `120f` with no `121a` cubins, and JIT on SM121 produces `121a`.
- [Code-verified] PyTorch treats 12.1 as binary-compatible with 12.0: commit `36acaaae` maps expected 121 to 120, and PR #178891 (adding `12.1+PTX` to aarch64 CUDA 13 wheels) was closed with "We do not need to compile PyTorch for 12.1 as it is compatible with 12.0." [Measured] torch 2.9.1 and 2.10.0 (+cu130) warn "cuda capability 12.1 ... (8.0) - (12.0)" on GB10 and renders in a co-resident container were unaffected (2026-08-18 co-resident container staging log).
- [Code-verified] Triton @ 2cfa167 appends `a` for every capability ≥ 90, so GB10 compiles to `sm_121a` (`third_party/nvidia/backend/compiler.py:110-113`), and uses a separate `ptxas-blackwell` (bundled 13.4.59; the other bundled `ptxas` is 12.9.86) for arch ≥ 100 (`:40-41`), overridden by `TRITON_PTXAS_BLACKWELL_PATH`. Older Triton builds bundled a ptxas too old for `sm_121` (version not stated) and failed with "Value 'sm_121a' is not defined for option 'gpu-name'" (triton#9181, closed); the widely posted `TRITON_PTXAS_PATH=/usr/local/cuda/bin/ptxas` workaround, including an NVIDIA moderator reply for TensorRT-LLM 1.3.0rc5 containers (forum 366006), does not govern arch ≥ 100 at the current pin. [Interpretation]
- [Code-verified: vendor doc] Driver JIT cache: `~/.nv/ComputeCache` by default; `CUDA_CACHE_MAXSIZE` defaults to 1 GiB on desktop/server and 256 MiB on embedded platforms (which class GB10 falls in is not documented), maximum 4 GiB; the cache is invalidated when the driver is upgraded. Minor-version compatibility for 13.x needs a ≥ 580 driver and does not run PTX-only applications. The forward-compatibility matrix lists `cuda-compat-13-1` through `13-4` as compatible with 580+ drivers and `12-9` as not, but the same document limits forward compatibility to data-center GPUs, NGC-Ready RTX SKUs and Jetson, so GB10 is not listed. [Community-measured] On driver 580.173.02 a CUDA 13.2 NGC container reported "compatibility mode is UNAVAILABLE" after the same container had started in forward-compat mode on 580.159.03, while a CUDA 13.1 container ran (forum 379168); the published matrix does not explain this.
- [Community-measured] `%clock64` is reported broken on GB10 under CUDA 13.1 and returning 0 under CUDA 13.2 (driver 580.142); the author times kernels with CUDA 13.0 (parallelArchitect/gb10-uma-diagnostics @ 520b7925c2). Single source.

Unified memory. See [Memory management on a unified-memory GB10](11-memory-on-unified-memory.md).
- [Code-verified: vendor doc] DGX Spark known issue: `cudaMemGetInfo` "does not account for memory that could potentially be reclaimed from SWAP", so it can under-report allocatable memory; NVIDIA's sample estimator reads `MemAvailable`, `SwapFree` and the HugePages fields.
- [Measured] Linux sees 121.63 GiB on the own ASUS GX10 nodes; idle `MemAvailable` is 114-116 GiB with only a desktop session resident; about 12 GiB sits outside an engine's accounting (desktop session including the login greeter, kernel, Docker, page-cache floor). [Community-measured] `MemTotal` varies by SKU and firmware: MSI and Founders units show about 121.7 GiB; a Gigabyte owner went from 119 to 121 GiB after a firmware update; an ASUS GX10 owner reports 119 before and 121 after a BIOS update; an Acer unit stayed at 119 GiB fully updated (forum 363849). If physical memory is 128 GiB, the gap to 121.63 GiB is about 6.4 GiB, larger than the 2 GB display carveout, and no vendor page itemizes the rest.
- [Code-verified: vendor doc] The July 2026 DGX Spark release notes say the included driver "enhances Out-of-Memory (OOM) handling" with "user feedback" under memory pressure, and that "Display Reserved Memory can now be toggled between 2GB (default) and 4GB through the system BIOS". No before/after numbers are given, the notes apply to the Founders Edition first, "GB10-based partner systems may not receive updates at the same time", and the NVIDIA UEFI pages do not name the menu item.
- [Measured] + [Community-measured] Driver allocations fail fast instead of waiting for reclaim: a 2-node GB10 KV ladder found `NV_ERR_NO_MEMORY` at `mem_desc.c:1359` above the engine's own suggested KV size (tonyd2wild, §4), and with a 16 GB runtime swapfile at `vm.swappiness=0` an own 131K cold prefill logged 104 nonfatal `NV_ERR_NO_MEMORY` while swap stayed at 0 MiB (2026-09-15 DS V4.1 Flash TP3 fast-profile k5 swap scorecard). This does not contradict the vendor note, which is about `cudaMemGetInfo` not counting swap-reclaimable pages; nobody has tested swappiness above 0 against driver-pinned allocations.
- [Measured] + [Community-measured] `docker --memory` does not bound CUDA allocations: one SGLang run at fraction 0.76 under a 100g cgroup showed only 7.15 GiB as container RSS (hasso5703 @ 54bb2c3), and an own global OOM killed a co-resident container, the one with the largest RSS, 2.5 min before the candidate's memcg limit fired (2026-08-18 co-resident container staging log).
- [Interpretation] Exhaustion usually shows up as a freeze rather than a CUDA error, because the NVRM failure sits below the CUDA runtime and the Linux OOM killer cannot reclaim driver-pinned memory. Evidence: a DGX Spark that went unresponsive instead of throwing CUDA OOM (forum 353752, physical reboot); an ASUS GX10 hard power-off under vLLM whose journal shows two `NV_ERR_NO_MEMORY` lines first, with the cause contested between power delivery (the owner started an RMA) and memory exhaustion (forum 370007); and the own incidents in §7.
- [Community-measured] The display reserve is CUDA-allocatable on headless boxes: reload `nvidia_drm` with `modeset=1 fbdev=0`, allocate a DRM dumb buffer, map it and register it with `cuMemHostRegister(DEVICEMAP|IOMEMORY)`; the recipe puts 1.75 GB of KV there, keeps 250 MB free, needs the BIOS setting at 2 GB, and "measures slightly slower" (emihuang, forum 383583; coolbho3k `display_kv.py` @ 878e0ee). 2,032 MiB is the largest buffer that allocates (MiaAI-Lab GLM kit PR #234, open). No source measured this on an ASUS GX10.
- [Community-measured] Driver 590.48.01 did not release UMA memory after a CUDA process exited while 580.126.09 did; an NVIDIA moderator replied in February 2026 that "we do not support new drivers past version 580.126.09" (forum 359969). That is a point-in-time support statement, not a codegen limit.

## 5. Levers, ranked

This card is mostly facts, so its levers are the ones that follow directly from a hardware or toolchain fact. Speed levers for specific kernels live on the engine and kernel pages.

1. **Budget memory by `MemAvailable`, keep the engine's automatic KV sizing, and hold floors.** Applies to: every engine x every model family x every topology on GB10. Gain: stability, not speed; the own KV-raise-plus-workspace change with 4.4 GiB host-available made a node unreachable until a power cycle, and five explicit-KV 900K launches died at multimodal warm-up, while auto KV at utilization 0.84 booted (2026-08-28 GLM TP2 stabilization) [Measured]; a community ladder shows explicit KV above the engine's suggestion failing 5 of 5 [Community-measured]. Cost: a few GiB of KV. Risk: over-conservative floors waste context. Smallest falsifying experiment: on one lane, raise KV by 1.5 GiB in one boot and sample `MemAvailable` every 2 s through the lane's longest supported prefill; the lever is wrong if the minimum stays above 5 GiB with zero `NV_ERR_NO_MEMORY` at a KV size the rule forbids. See [Memory management on a unified-memory GB10](11-memory-on-unified-memory.md).
2. **Know which arch each deployed kernel carries (`12.0f` or `12.1a`), and build `12.1a` only where a feature needs it.** Applies to: vLLM and SGLang source builds on CUDA 13.x, FlashInfer JIT, ds4, custom CUTLASS; any model using 2:4-sparse FP4. Gain: availability and correctness, not a measured speed-up; at vLLM 34b0690 on CUDA 13.x a `12.1a` request yields `12.0f` [Code-verified]; the only GEMM-relevant `sm_121a`-only feature is sparse FP4 MMA [Code-verified]; no `12.0f`-versus-`12.1a` A/B of the same dense kernel exists. Cost: one `cuobjdump --list-elf` per shared object. Risk: forcing `12.1a` through a patched arch filter may miss upstream fixes. Smallest falsifying experiment: build one dense NVFP4 GEMM twice (`12.0f`, `12.1a`) at the same commit and run the same shape 100 times each; if the medians differ beyond run spread, the "no dense difference" assumption is wrong.
3. **Size kernel configs to SM12x limits (101,376 B per block, 48 warps per SM).** Applies to: Triton and CUTLASS kernels in vLLM and SGLang whose defaults were tuned for Hopper or SM100 (FLA ops, extend attention, MoE Triton configs, CUTLASS FP4 tiles). Gain: "fails or falls back" → works; 13 of 16 CUTLASS tactics failed 1 KiB over the limit (cutlass#3144) [Community-measured]. PR #37700's 64 → 35 ms bundles TMA and tile changes, has no protocol, and would restore a config FLA removed for correctness (see [Linear attention](07-linear-attention-and-hybrid-layers.md)); do not adopt its 8-warp FLA tiles on GB10 untested. Cost: autotune time or a patched config. Risk: unmerged patches drift. Smallest falsifying experiment: on the affected lane, log the selected config and its shared-memory request at boot; if no selected kernel requests more than 101,376 B, the lever does not apply there. See [GEMM backends and quantization formats on SM121](09-gemm-backends-and-quant-formats.md).
4. **Drive both RoCE controllers of each QSFP port.** Applies to: every TP2/TP3 lane on direct-attach cables, NCCL over RoCE. Gain: unknown on this fleet; one controller measured 108.8-109.0 Gb/s RDMA write (smoke) against a 200 Gb/s port, and one PCIe Gen5 x4 link tops out near 126 Gb/s raw [Measured] + [Interpretation]; the two-controller selector is applied on some lanes but never measured here. Cost: a second IPv4 subnet, GID preflight, a re-qualification. Risk: a stale GID index kills a rank about 60 s into load. Smallest falsifying experiment: one NCCL all-reduce battery at 4 KiB, 1 MiB and 64 MiB with one versus two controllers, same boot; if the two-controller bus bandwidth is within spread of one, drop it. See [Inter-Spark communication over DAC](03-inter-spark-communication.md).
5. **Clock cap: follow [Clocks, thermal, and power on GX10 / DGX Spark](13-clocks-thermal-power.md) §5 lever 1.** Cap for heat and throttling, not speed. Expect 3-6% on cold prefill; single-stream decode was 5-6% lower by mean, inside spread, on the own TP3 lane. Qualify per lane with 13's A/B/A rule before keeping the cap. Applies to: every engine (host-level); measured here on the vLLM EXL3 GLM TP3 lane. Gain: peak temperature −10 °C and zero throttle time at 2100 [Measured]. Cost: prefill −4.9% at 250K; C1 decode means 5-6% lower, inside rep spread (own TP3, n=5); community controlled runs ±2% [Measured] + [Community-measured]. The TP2 −6.8% (n=3) and the TP3 −5.8% (n=5) are the same size; neither lane settles transfer. Risk: a lane-specific decode loss. Smallest falsifying experiment: 13's interleaved A/B with its pass rule (TTFT-weighted cost ≤3%, peak down ≥5 °C, throttle seconds down).
6. **Keep the driver JIT cache persistent and large.** Applies to: any containerized engine that JIT-compiles PTX (FlashInfer, Triton, PTX fallbacks). Gain: part of a start-up bundle that cut container-to-API from 275.72 s to 126.89 s on warm caches, not isolated [Measured]; the default `CUDA_CACHE_MAXSIZE` is 1 GiB (desktop/server) or 256 MiB (embedded), up to 4 GiB [Code-verified]. Cost: a volume mount and disk. Risk: a stale Triton cache produced garbled text in two GB10 reports (vllm#41871) [Community-measured]; the driver cache is invalidated on driver upgrades. Smallest falsifying experiment: two cold restarts with the cache volume and two without, pull skipped, same image; if container-to-API differs by less than run spread, the cache is not the cause.
7. **Align host memory sysctls across TP ranks before comparing headroom.** Applies to: every multi-node lane. Gain: boot versus no boot; a 4 GiB `min_free_kbytes` on one node cut its reported availability from 110.93 to 97.96 GiB and the TP3 boot exited until aligned [Measured]. Cost: none. Risk: lowering reserves reduces the kernel's own emergency headroom. Smallest falsifying experiment: record `vm.min_free_kbytes` and `vm.watermark_scale_factor` on all ranks at every boot; a boot that succeeds with them misaligned and equal headroom falsifies the need. See [Memory management on a unified-memory GB10](11-memory-on-unified-memory.md).
8. **Put part of the KV cache in the reclaimed display reserve.** [Proposed] Applies to: headless nodes only, any engine with a pluggable KV allocator (community port exists for a vLLM EXL3 kit). Gain: capacity, about 1.75 GiB per node; the reclaimed pool is slower (162/114 versus 235/196 GB/s read/write in one probe) [Community-measured]. Cost: an `nvidia_drm modeset=1 fbdev=0` host change and a kit patch. Risk: kills any local display, AGPL-derived code, unmeasured on ASUS GX10. Smallest falsifying experiment: on one headless node, allocate the largest DRM dumb buffer and register it; if it fails or reads below 100 GB/s, drop it.

## 6. Protocol

This is the protocol for capturing the missing hardware facts on the own nodes and for any change that depends on them (a build-arch change, a memory floor, a clock cap). It follows the fleet rules on the entry page and the incidents in §4 and §7. See [Profiling protocol](14-profiling-protocol.md) for kernel attribution.

Preconditions.
- Clean window: no client traffic. Check running and waiting requests and any client shim's in-flight count before each pass; discard a pass that overlaps traffic.
- No memory overcommit: at least 8 GiB `MemAvailable` on every node before a start, a 5 GiB warm floor while serving, and stop all benchmark traffic at 4 GiB `MemAvailable` on any node. Swap is not headroom; it does not rescue driver-pinned allocations. KV raises no more than 1.5 GiB per boot.
- One variable per boot. A restart for an A/B skips the image pull, so the variable under test is the only difference.
- Never restart a client gateway; the engine restart is the operator's step, a gateway restart is the operator's decision. Never `pkill -f` a pattern that also matches your own shell.
- All [entry-page](README.md) rules apply, in particular: greedy logprob probe after every relaunch; discard the first request and warm every shape; unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection line on every rank; ≥3 reps with a closing A/B/A; MemAvailable every 1-2 s and zero NV_ERR_NO_MEMORY/Xid; no reboot without per-node permission. For this page that means in particular an A/B/A with ≥3 reps per arm for any clock-cap or build-arch decision, and a greedy logprob probe after any build-arch change.
- Record the platform first: driver version, firmware version, CUDA toolkit inside the container, `MemTotal`, and `vm.min_free_kbytes` / `vm.watermark_scale_factor` on every rank (they must match across ranks). Time microbenchmarks with a CUDA 13.0 toolchain until the `%clock64` report on 13.1/13.2 is resolved.

Change. Exactly one of: a device-fact capture (no serving change), a build-arch change for one shared object, a memory floor or KV size, a clock cap, a NIC-controller selection.

Run.
1. Device facts, once per node, engine stopped: `cudaGetDeviceProperties` fields `multiProcessorCount`, `l2CacheSize`, `sharedMemPerBlockOptin`, `maxBlocksPerMultiProcessor`, `clockRate`, `memoryClockRate`; `cudaOccupancyMaxActiveBlocksPerMultiprocessor` for an empty 32-thread kernel (settles 24 versus 32 blocks).
2. Arch census: `cuobjdump --list-elf` on every engine shared object and on FlashInfer's JIT cache; record `sm_120`/`sm_121`, `a`/`f`.
3. Idle bandwidth: CUDA-samples `bandwidthTest` (H2D, D2H, D2D) plus a STREAM-style copy/triad kernel and a saturating `float4` read at 8 GiB, `<<<2048,256>>>`, 5 runs after 2 warm-ups; report median and spread.
4. Loaded bandwidth: the same kernels at 128 MB (above the 24 MB L2) while the lane decodes one fixed prompt, and the decode tok/s with and without the probe.
5. Memory watch for any memory-touching change: `/proc/meminfo` every 2 s (`MemAvailable`, `MemFree`, `Cached`, `SwapFree`) on every rank, plus a `dmesg` count of `NV_ERR_NO_MEMORY` and `oom-kill` lines, through boot, warm-up and the lane's longest supported prefill.
6. Clocks: `clocks.gr`, temperature, power and throttle-reason counters per arm at 1 s.

Record (packet fields): node, driver, firmware, toolkit, image commit; the device-property dump; the arch census; bandwidth medians, spreads, buffer sizes, launch shape and whether a model was loaded; decode tok/s during the loaded probe; minimum `MemAvailable` and `MemFree` per rank; `NV_ERR_NO_MEMORY` and `oom-kill` counts split into start-up and serving; clock median and throttle seconds per arm; discarded passes and why.

Pass gate. For a capture: every field present on every node, bandwidth spread within 3% across the 5 runs. For a change: zero serving-time `NV_ERR_NO_MEMORY`, zero `oom-kill`, minimum `MemAvailable` at or above 5 GiB on every rank through the longest supported prefill, and decode and prefill within repetition spread of baseline unless a trade was accepted in advance. Start-up-only NVRM lines with clean serving afterwards are not by themselves a failure (§4); any during prefill are.

Rollback. Revert the one variable, restart with the pull skipped, confirm the configuration line and the platform record match the baseline, run one short decode and one cold 8K prefill, and compare within repetition spread before the lane serves again. For a clock cap, `nvidia-smi -rgc` restores stock clocks.

## 7. Anti-patterns and known-bad

- [Measured] Reading `MemFree` as available inference memory. Page cache fills the gap: minimum `MemFree` 0.76 GiB while minimum `MemAvailable` was 13.86 GiB (2026-09-05 Qwen 3.8 Flash Next single-node qualification).
- [Measured] Treating swap as headroom for GPU memory. None of three swap setups tried on the own nodes (swap off, a low-swappiness host-only valve with model cgroups barred from swap, runtime swap at swappiness 0) protected driver-pinned allocations; at swappiness 0, 104 `NV_ERR_NO_MEMORY` fired with swap at 0 MiB (2026-09-15 k5 swap scorecard).
- [Historical diagnostic] Two memory changes in one boot. A KV-cache raise plus a workspace change, with 4.4 GiB host-available and no swap, made a node unreachable until a power cycle; the kernel starved the SSH daemon, not the engine, and recovery needed a physical reboot.
- [Historical diagnostic] Capping only the KV pool. A ~200K-token prefill on a TP3 lane with about 1.4 GiB left per rank wedged all three nodes while the KV pool was 25-28% full; the Linux OOM killer repeatedly killed a small desktop process and never the driver-pinned engine, and the tensor-parallel group stalled together. Cap request length or chunk size as well (see [Prefill optimization](04-prefill-optimization.md)).
- [Historical diagnostic] Trusting `docker --memory` to isolate GPU memory on GB10; a global OOM killed a co-resident container first (§4).
- [Historical diagnostic] Stopping the display manager to reclaim memory; it kills the headless remote-desktop session. Drop the page cache instead.
- [Historical diagnostic] A stale fixed RoCE GID index after a reboot kills a rank about 60 s into load (index 3 became all-zero on one node). Preflight per-rank GIDs.
- [Historical diagnostic] A base image that carried a legacy SM121-only attention resolver broke CUDA-graph warm-up by selecting the wrong fallback; assert its removal in the image build.
- [Measured] Treating start-up NVRM `NV_ERR_NO_MEMORY` lines as failure (72-172 per rank with clean serving afterwards), or treating the same line during prefill as harmless (the 131K prefill warnings preceded the 200K wedge).
- [Interpretation] Transferring "decode is free under a clock cap" across lanes, or reading one lane as proof it does not transfer: −6.8% decode at 2200 on a DeepSeek V4 Flash TP2 lane (n=3) and C1 means −5.8% at 2100 on a GLM TP3 lane (n=5, inside rep spread) are the same size; neither lane settles transfer. Lane, engine, firmware and rep counts differ. See [Clocks, thermal, and power](13-clocks-thermal-power.md) §5 lever 1.
- [Code-verified] Assuming `TORCH_CUDA_ARCH_LIST=12.1a` gives `12.1a` cubins in a vLLM CUDA 13.x source build; at 34b0690 the supported-arch filter turns it into `12.0f` (§2).
- [Code-verified] Assuming `sm_120a` code (for example a wheel built only for RTX 50-series `a` targets) runs on GB10. An `a` cubin runs only on its exact CC; use `sm_120` baseline, `12.0f` or `12.1a`.
- [Community-measured] Writing `-arch=sm_121a` and trusting the `a` survived; the shorthand and some CMake paths drop it (forum 373618). Use the explicit `-gencode` form and check with `cuobjdump`.
- [Code-verified] Guarding GB10 with `is_sm120()` or `== 1200` checks. SGLang's `is_sm120()` is exactly (12, 0), and an earlier DeepGEMM check `sm_version == 120` skipped GB10 (SGLang PR #34018).
- [Code-verified] Expecting `tcgen05`, TMEM, `wgmma`, 2-SM MMA, `tile::scatter4`, gather4 into `.shared::cluster`, or a `cutlass::arch::Sm121` tag on GB10. None exist on SM12x.
- [Community-measured] Hopper-sized shared-memory tiles: SGLang extend attention asked for 106,496 B (PR #17908), a Triton MoE config asked for 147,456 B (forum 359960), and TensorRT-LLM routed `mSm == 120 || mSm == 121` onto FP4 tiles needing more than 99 KiB (TensorRT-LLM#11368, closed). The limit is 101,376 B.
- [Community-measured] Using `TRITON_PTXAS_PATH` as the fix for "sm_121a is not defined" on current Triton. It fixed older containers; at 2cfa167 arch ≥ 100 uses `ptxas-blackwell` and `TRITON_PTXAS_BLACKWELL_PATH`.
- [Community-measured] Citing the Blackwell GPU community wiki for SM121: it does not mention SM121, its `wgmma` cells for SM12.0 are wrong (PTX: "Requires sm_90a"), and its L2 figures (about 16 MB and 96 MB) disagree with the 24 MB readouts.
- [Code-verified] Reading 32 resident blocks per SM from a naive parse of the CUDA Programming Guide table; with colspans expanded the 12.x value is 24 (the Tuning Guide's 32 is the documented conflict in §3).
- [Historical diagnostic] Using profile-log "implied bandwidth" above nominal (125-129% of 273 GB/s) as a DRAM ceiling; it refutes the read-once accounting, not the DRAM limit.
- [Community-measured] Bigger thread-block clusters for GEMM: +1.1% at 2x1x1 and −0.8% at 2x2x1 in the one GB10 sweep (forum 367851).
- [Code-verified] Relying on llama.cpp's integrated-GPU shortcuts on GB10: the backend forces its `integrated` flag false because of corrupted output (#15034).
- [Community-measured] Reusing another fleet's `MemAvailable` stop threshold: one 2-node EXL3 pair served normally at 1.1-2.4 GiB available with zero OOM kills, while a 4-node fleet kept 10.3 GiB after a 1M-token request (MiaAI-Lab DS V4.1 #19). Thresholds are per stack.
- [Community-measured] `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` is stack-specific: it is the default in one vLLM GB10 stack (spark-vllm-docker commit `20fd867`), was blamed for an OOM at load on that stack (forum 369076, "once you remove it, everything works normally"), and one SGLang DeepSeek V4.1 TP3 recipe forbids it because prefills over 64 query tokens returned NaN logits. No own A/B.
- Retracted, do not cite: "wrong-family prebuilt cubins (flashinfer-cubin 0.6.11) booted and produced garbage". In flashinfer#3294 the maintainer explained `flashinfer-cubin` holds only closed-source kernels while `flashinfer-jit-cache` ships `sm120f` kernels expected to work on 12.1; the reporter conceded the inspection was wrong and the garbage traced at least partly to a cutlass-dsl wheel collision. Also retracted: vllm#48031's attribution of a ~599 s start-up abort to `VLLM_ENGINE_READY_TIMEOUT_S` (the reporter disproved it; cause unknown), and triton#9852's diagnosis that SM12x was being routed into SM100 tensor-memory pipelines (the author withdrew it and reported `sm_121a` valid and the Blackwell codegen path working on SM121, Triton 3.5.1, CUDA 13.1). Also retracted: "DeepGEMM faults on sm_121" from vllm#54125; the `profile_run` crash was a skipped UE8M0 repack fixed upstream (`f8e0602713`), and the live risks are FP32-scale mis-selection and silent block-FP8 corruption at K = 2560 (see [GEMM backends](09-gemm-backends-and-quant-formats.md) §7).

## 8. Open questions

Open questions:
- Is `maxBlocksPerMultiProcessor` 24 or 32 on a GB10? — one `cudaDeviceGetAttribute(cudaDevAttrMaxBlocksPerMultiprocessor)` read, or `cudaOccupancyMaxActiveBlocksPerMultiprocessor` for an empty 32-thread kernel (§6 step 1).
- What are the empty-kernel launch latency and per-node CUDA-graph replay overhead on GB10? — a back-to-back null-kernel launch loop plus an Nsight Systems trace on CUDA 13.0. See [CUDA graphs and launch overhead on GB10](01-cuda-graphs-and-launch-overhead.md).
- What do the own nodes achieve in `bandwidthTest` and STREAM-style copy/triad, idle and during decode? — §6 steps 3-4; no public or own CUDA-samples `bandwidthTest` log exists.
- Which driver or attribute path gives a memory clock of 0 versus 8,533 MHz, and a max SM clock of 3.00 GHz versus 2,418 MHz? — the same `cudaGetDeviceProperties` dump on driver 580.142, 580.173.02 and 610.x.
- Does a `12.1a` build of the same dense kernel differ from `12.0f` in speed or output on GB10, and which arch do the deployed shared objects carry? — the two-build A/B in §5 lever 2 plus a `cuobjdump --list-elf` census.
- Does multicast TMA or DSMEM give any benefit on SM12x? — a CUTLASS or hand-written GEMM with and without `.multicast::cluster` at a fixed tile, same boot.
- Does the July 2026 driver OOM-handling change prevent freezes or only add a message, and does ASUS firmware expose the 2/4 GB display-reserve toggle? — a controlled over-allocation on a sacrificial node with the new driver (physical access required) and a firmware menu inspection; not on a serving node.
- Does the display-reserve CUDA allocation work on an ASUS GX10, and at what bandwidth? — §5 lever 8's falsifying experiment.
- Can the UVM livelock be reproduced? Field notes from a 4-node TP=4 kit describe engine steps stalling with the GPU at about 96% utilization and 12-20 W while `/health` stays 200, prevented by `vm.swappiness=0` plus a swap cycle before every start, detected by frozen token counters for 10 one-minute ticks, and cleared in about 18 min by `docker kill`, a swap cycle and a trivial CUDA probe; the suspected trigger is a ~236K-token prefill touching pages swapped out days earlier. [Community-measured, not reproduced] — a long-idle node with swap on, then a ~236K prefill, with the token-counter detector running.
- Why do ranks die silently 60-90 s after load when a multi-node kit uses the InstantTensor direct-I/O loader? The deaths happened at every KV size tried, including 4.14 GiB, which is stable on the standard loader, so allocation size is not the cause (tonyd2wild KV ladder). — the same boot with the standard loader and with InstantTensor, same KV, `dmesg` and NCCL logs captured.
- What cubins does the Anemll vLLM port's `torch_cuda_arch_list=12.1a` build actually produce? — `cuobjdump --list-elf` of its image, read against its vendored `CUDA_SUPPORTED_ARCHS`.
- Why did a CUDA 13.2 container fail forward-compat on driver 580.173.02 after starting on 580.159.03, when the published matrix marks 13-2 compatible with 580+ but does not list GB10 as a forward-compat platform? — the same container on both drivers with `CUDA_VERSION` and the compat-library load log captured.
- Is DeepGEMM numerically safe on GB10 at a given engine pin? The vllm#54125 fault was retracted (§7); FP32-scale mis-selection and the K = 2560 silent-corruption window remain. — `VLLM_USE_DEEP_GEMM=1` versus 0 at the lane's pin, same boot, `profile_run` log and a short correctness fixture that includes a K = 2560 shape.
- Which FP4 path is numerically correct on SM121? One community repo says all CUTLASS FP4 GEMMs produce zeros or NaN on SM121 (scottgl9/sglang-spark-gb10-optimizations @ f77232a48f); another says vLLM's Marlin FP4 MoE is silently wrong (lmxxf/Consumer-DeepGEMM @ a933c92e7b). Neither was cross-checked. — a fixed-input GEMM against a BF16 reference through each path on one node.
- How does the 2100 MHz cap behave on a real-traffic day, and on lanes other than GLM TP3? — §5 lever 5's decode A/B and one day of traffic with throttle counters.
- Is the copy-engine count 2 (NVIDIA spec) or 1 (one `deviceQuery` capture, kubesimplify)? — `asyncEngineCount` in the §6 device dump.
