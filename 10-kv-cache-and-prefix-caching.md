# KV cache and prefix caching on GB10

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 128 GB unified LPDDR5X), one to three nodes (node-1, node-2, node-3). A pair is node-1 (head) + node-2 over a direct 200 Gb RoCE link; the three-node GLM lane uses node-1 as head, the three-node DeepSeek V4.1 SGLang lane used node-3. Upstream code is quoted at vLLM `8b660ce96bc2`, SGLang `f2a1366584e1`, llama.cpp `d2e54583c745` (all main or master on 2026-09-23) and ExLlamaV3 `6b84a21b6f1e` (2026-09-20). The own lanes run forks (a GLM-5.3 vLLM fork at `487ecf187`, a DeepSeek-V4 DSpark image on vLLM 0.25.2, an SGLang build at `da64c5c` that is not an upstream commit), so a code line says what upstream does now, not what a given lane runs. Vocabulary used below: a *record* is what one attention kernel reads per token per layer; *allocator bytes* are pool bytes divided by pool tokens, which include other cache groups and padding; the *hit grain* is the smallest unit of prefix reuse; `cached_tokens` is the per-request count of prompt tokens served from cache.

## 1. What it is

Every token a model has read leaves a small record in the KV cache (per-token attention memory), and generating each new token means reading those records back. Two consequences follow. First, the storage format decides how many tokens fit and how fast each step reads them: an FP8 (8-bit float) record takes half the room of BF16 (16-bit), a 4-bit FP4 record half again, but the GPU has to dequantize (unpack to full precision) it before use, and on GB10 the attention kernels mostly do that unpacking in software rather than computing in the small format. Second, a cache can be kept after a request ends, so the next request that starts with the same text skips recomputing it; this is prefix caching (reusing earlier prompt work). Engines find the reusable start by fingerprinting pages (fixed blocks of consecutive tokens) in a hash chain (each fingerprint includes the previous one), so one changed token near the start invalidates everything after it. On a GB10, reading a long prompt is slow (roughly 800 to 2,000 prompt tokens per second on the own lanes [Measured]), and agent sessions resend long, mostly identical prompts every turn, so a hit or a miss decides whether a turn starts in about a second or after minutes: one own 300K-token follow-up went from 345.5 s to 10.0 s to first token once reuse worked [Measured]. Hybrid models add a third piece, a fixed-size running summary per layer (linear-attention state) that can only be restored at saved checkpoints; that makes pages thousands of tokens long and makes some hits vanish outright. And because the 128 GB is shared by the CPU, the operating system and the GPU, every gigabyte given to the cache comes out of the headroom that keeps the node alive. This page covers the formats and which kernels they select, paging and hashing, hybrid caches, pool sizing, and moving KV between nodes. Related pages: [Memory management on a unified-memory GB10](11-memory-on-unified-memory.md), [Attention backends on SM121](06-attention-backends-sm121.md), [Linear attention and hybrid layers on SM121](07-linear-attention-and-hybrid-layers.md), [Speculative decoding on GB10](02-speculative-decoding.md), [Serving agent workloads](22-serving-agent-workloads.md), [Inter-Spark communication](03-inter-spark-communication.md).

## 2. How each engine does it

### vLLM

- **The KV dtype picks the attention backend on SM12x.** For non-MLA models the SM12x priority list is FLASH_ATTN, FLASHINFER, TRITON_ATTN, FLEX_ATTENTION, TURBOQUANT (`vllm/platforms/cuda.py:166-179`). FlashAttention routes a quantized KV cache to `fa_utils.py:282-308`, which accepts FP8 only for FA3 on SM90 or FA4 on the SM100 family (`flash_attn.py:384-391`), so an FP8 KV request on GB10 drops FLASH_ATTN and lands on FlashInfer (capability 8.0 to 12.1, `flashinfer.py:510-518`) or Triton. [Code-verified]
- **Dense NVFP4 KV is refused on GB10.** FlashInfer reports `nvfp4` / `nvfp4_4over6` support only on the SM100 family with the trtllm-gen path (`flashinfer.py:494-503`), and the metadata builder raises "requires the SM100 trtllm-gen FlashInfer path" (`flashinfer.py:773-792`). The open SM120 PRs (#44851, #46329) and feature request #49011 are not merged. [Code-verified]
- **B12X backend.** A paged-attention backend for exactly (12,0) and (12,1) accepts `fp8` / `fp8_e4m3` as its only quantized KV dtype, BF16 queries, pages of 64 or 128 (preferred 128) (`b12x.py:47-56`, `210-215`, `230`). It is in no automatic priority list and must be selected explicitly. [Code-verified]
- **MLA on SM12x.** Priority is TRITON_MLA, then FLASHINFER_MLA_SPARSE_SM120 (`cuda.py:132-136`). The SM120 sparse backend accepts `auto`, `fp8`, `fp8_e4m3`, `fp8_ds_mla` with kernel block sizes 64 or 256 and does not list `nvfp4_ds_mla`; `FLASHMLA_SPARSE` rejects `nvfp4_ds_mla` off SM100 (`flashmla_sparse.py:218-222`); the DeepSeek V4.1 mega-attention backend is SM100 only (`models/deepseek_v41/sparse_mla.py:235-256`). `fp8` is an alias for `fp8_ds_mla` on the sparse MLA backends. [Code-verified]
- **Stock MLA record sizes** (`flashmla_sparse.py:74-120`; `mla_attention.py:1359`; `models/deepseek_v41/common/ops/cache_utils.py:35-52`): DeepSeek V3.2-geometry `fp8_ds_mla` 656 B per token per layer (512 B FP8 NoPE + 16 B of four FP32 scales + 128 B BF16 RoPE); DeepSeek V4 584 B (448 FP8 NoPE + 128 BF16 RoPE + 8 UE8M0 scales); DeepSeek V4.1 528 B (all 512 dims FP8); SM100-only `nvfp4_ds_mla` 352 B for V3.2 geometry; and an SM100-only V4.1 NVFP4 compressed record of 288 B (512 E2M1 values + 32 E4M3 scales) read only by the mega-attention kernel. [Code-verified] The same string `nvfp4_ds_mla` therefore means three things across builds: a 584 B envelope in the DSpark ports (llama.cpp and forks, below), 352 B for V3.2 geometry and 288 B for V4.1 on SM100. [Code-verified]
- **NoPE models (GLM-5.3-Flash, `qk_rope_head_dim = 0`).** The stock `fp8_ds_mla` writer accepts `pe_dim == 64 || pe_dim == 0` and zeroes the reserved RoPE tail for NoPE rows, keeping the 656 B row (`csrc/libtorch_stable/cache_kernels.cu:552-561`, `943-944`). [Code-verified] So a NoPE row carries 128 B of zeros; the own GLM lane's page logs as 2,560 tokens x 656 B = 1,679,360 B [Measured] (2026-09-20 GLM 5.3 Flash TP3 frontier dossier v2). A community draft issue reporting the old `pe_dim must be 64` assert on 2x GB10 (tonyd2wild, `9fea48c`) is superseded at HEAD.
- **FP8 KV is storage plus in-kernel dequant, not FP8 attention math.** On the Qwen QSA sparse path an FP8 dot does compile on sm_120 (Triton 3.7.1), but QK in FP8 ran 0.53-1.07x end-to-end with 6-10x the maximum error, so the merged kernel (PR #55557) keeps Q in BF16 and upcasts K to the query dtype and V to FP16. [Community-measured] (vLLM PR #55557 author thread, SM120) An FP8 two-stage wide prefill tile asked for 106,496 B of shared memory against a 101,376 B limit and lost a pipeline stage (PR #54846, open, SM120). [Community-measured] The optional FP8 QSA indexer cache (#54890, merged) has no SM12x gate at HEAD (`qwen4_exp/nvidia/indexer_qsa.py:148-155`) and its microbenchmarks are on GB300 only. [Code-verified]
- **Hashing and paging.** Each full block is hashed as `hash(parent_hash, token_ids_of_block, extra_keys)` starting from `NONE_HASH` at token 0 (`v1/core/kv_cache_utils.py:649-679`); prefix caching is on by default with `sha256` (xxhash and CBOR variants optional) (`config/cache.py:43-60`); `DEFAULT_BLOCK_SIZE` is 16 (`cache.py:71`). Only full blocks are cached, so reuse ends at the block that contains the first differing token. `--prefix-match-unit` makes the hit grain finer than the physical block when every group's block size is divisible by it (`cache.py:91-102`). Hybrid models raise the block to fit the linear-attention page and pad the Mamba page to the attention page (`mamba_page_size_padded`). [Code-verified]
- **Hybrid caches.** `mamba_cache_mode`: `align` (the default with prefix caching) stores linear state only for the last token of a scheduler step that lands on a block boundary; `all` stores every block; the hybrid coordinator needs every KV group to hit, so one missing state checkpoint vetoes matched attention blocks. `--enable-mamba-shared-prefix-checkpoint` adds a checkpoint at the shared-prefix junction, only with `align`, speculative decoding on the Mamba group, a match unit smaller than the Mamba block, and no multi-module MTP (`cache.py:190-205`; `docs/features/automatic_prefix_caching.md:16-38`). `prefix_cache_retention_interval` defaults to 0 (keep only semantic checkpoints: latest replay boundary and shared-prefix junctions) for sliding-window and Mamba groups; `None` retains densely (`cache.py:160-166`; PRs #52216, #45845, #43447, merged). Internal prefill checkpoints for FlashKDA (PR #52789, merged 2026-08-22, `9eb9d9d`) replace the doubled full-model forward at a checkpoint boundary with one forward and a split FlashKDA call, and PR #53614 (merged 2026-09-06) extends them to speculative decoding, partial prefix hits and KV-connector restores; `layers/mamba/kda_checkpoint.py:17` sets a FlashKDA checkpoint alignment of 16. [Code-verified] Under speculation, `disable_eagle_block_drop` (PR #53388, merged 2026-09-01) restores first-repeat hits under MTP (see [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md) §4).
- **Capacity and the boot line.** `requested = ceil(total_memory x gpu_memory_utilization)`; `available_kv = requested - non_kv (weights + profiled activation peak + non-torch) - cudagraph_estimate` (the last only with `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS`); start-up refuses if free memory is below `requested`, and on integrated GPUs "free" is `psutil.virtual_memory().available`, which includes reclaimable page cache (`v1/worker/gpu_worker.py:581-603`, `660-682`; `v1/worker/utils.py:533-552`; `utils/mem_utils.py:143-151`). `--kv-cache-memory-bytes` (`arg_utils.py:1307`) skips profiling and pins the pool. Boot lines: `Available KV cache memory: X GiB`, then `GPU KV cache size: N tokens, Maximum concurrency for L tokens per request: C x`, where N = int(C x L), a group-aware figure, not a prefix-cache capacity (`kv_cache_utils.py:2412-2440`). Default utilization at HEAD is 0.92 (`cache.py:103`). [Code-verified]
- **Transfer.** Under tensor parallelism an MLA model has one KV head, so every rank stores the full latent; the vLLM docs state TP8 on DeepSeek-R1 duplicates the KV cache 8x. Decode context parallel (`-dcp`, 1 to tp/H) shards KV along the token dimension with an interleave, paid for by per-layer AllGather + ReduceScatter or an all-to-all of partial outputs plus LSE (2 instead of 3 NCCL calls per MLA layer) (`docs/serving/context_parallel_deployment.md:30-52`; `config/parallel.py:359-385`; method in arXiv 2507.07120 as cited there). KV connectors (NIXL, Mooncake, LMCache, native offloading; `KVOffloadingBackend = native | lmcache`, `cache.py:63`) exist upstream. [Code-verified]
- **Flags and env vars seen on GB10 lanes:** `--kv-cache-dtype`, `--kv-cache-memory-bytes`, `--gpu-memory-utilization`, `--block-size`, `--prefix-match-unit`, `--mamba-cache-mode`, `--enable-mamba-shared-prefix-checkpoint`, `--prefix-cache-retention-interval` (env `VLLM_PREFIX_CACHE_RETENTION_INTERVAL` in some kits), `--enable-prompt-tokens-details` (needed for `cached_tokens` in responses), `-dcp`.

### SGLang

- **KV dtypes and gates.** `--kv-cache-dtype` accepts `auto`, `fp8_e5m2`, `fp8_e4m3`, `mxfp8`, `bf16`/`bfloat16`, `nvfp4`, `fp4_mx_block16` (`arg_groups/fields/model.py:189-212`). `nvfp4` requires `is_sm100` or `is_sm120`; `is_sm120` maps to `is_sm120_supported`, which matches compute-capability major 12 with CUDA 12.8 or newer, so GB10 passes (`arg_groups/kv_cache_hook.py:111-137`; `utils/common.py:293-297`; `runtime_context.py:1760-1762`). `mxfp8` requires `is_blackwell`, which covers majors 10, 11 and 12 (`utils/common.py:286-292`), so it also passes the gate on GB10; only the error text says "SM100+". Whether its FA4 MXFP8 attention path runs on SM121 is untested. FP4 KV is refused with `--enable-unified-memory` (a hybrid-pool option, not a statement about UMA hardware) (`fields/memory.py:79-86`). [Code-verified]
- **NVFP4 KV path off SM100.** Prefill dequantizes cached prefix entries into an FP8 E4M3 workspace served by FlashInfer; decode runs `trtllm_mha` with the XQA implementation (SM90/SM120), which reads the legacy linear NVFP4 scale layout; native NVFP4 prefill is SM100 only (`kv_cache_hook.py:33-96`; `layers/attention/trtllm_mha_backend.py:1-12`, `238-252`). [Code-verified] The SGLang team's write-up measured this path on SM120, not GB10 (row in §4).
- **SM121 sparse-attention decode.** HEAD routes SM121 to a dedicated Triton QSA varlen decode kernel (BF16, D = 256, 12:1 GQA; `layers/attention/qwen_sparse_attn_backend.py:45-75`; SM121 probe at `utils/common.py:324-335`). This came from PR #36845 (merged 2026-08-30): on SM121 the TRT-LLM sparse decode, enabled a few days earlier by #36649, returned token id 0 at 120K, 190K and 210K context, so SM121 was excluded. [Code-verified] Open PR #36556 argues for re-enabling TRT-LLM sparse decode on SM120/SM121; its 4.70e-4 max-abs-diff match on GB10 is a short-shape test and does not cover long context. [Community-measured]
- **FP8 scales.** When a checkpoint ships no KV scales, or the key path does not match, SGLang uses 1.0 and says so in a single log line ("Defaulting to scaling factors of 1.0"). On one own build all 32 calibrated scale tensors (16 k_scale + 16 v_scale) of a checkpoint were dropped this way. [Measured] (2026-08-19 Qwen 3.8 27B single-node campaign audit)
- **Paging.** `page_size` is 1 on CUDA (token-granular radix tree) unless a backend or model override forces more (`arg_groups/overrides.py:1288-1311`); DeepSeek V4/V4.1 is forced to 256 (NPU 128) (`model_overrides/deepseek_v4.py:51-63`). [Code-verified] The HiCache design doc states that larger pages cut metadata and I/O cost but lower the hit rate when only part of a page matches (docs.sglang.io, fetched 2026-09-23; vendor documentation, no measurement). `--enable-cache-report` (default off) returns cached tokens per request (`fields/serving.py:185-188`). [Code-verified]
- **Hybrid caches.** The unified radix cache (PR #21206, merged 2026-04-13) keeps one token-keyed tree and lets FULL, SWA and MAMBA components vote on the reusable boundary: FULL reuses the whole path; SWA needs a contiguous trailing window (older slots may be tombstones); MAMBA needs an exact checkpoint, copied before mutation. Mamba checkpoints align to `mamba_track_interval`, which must be a multiple of `page_size` and at least the draft-token count; chunked prefill smaller than the Mamba chunk skips checkpoints with a warning (`arg_groups/mamba_hook.py:95-139`). [Code-verified] Other knobs: `--max-mamba-cache-size` (state slots), `--mamba-ssm-dtype` (unset can resolve to FP32, see §4), `--mamba-radix-cache-strategy` `extra_buffer` / `no_buffer` (the latter needs page 1).
- **Capacity.** `mem_fraction_static` covers weights plus KV; `--max-total-tokens` caps the pool. The DeepSeek V4 configurator sizes tokens as `available_bytes / bytes_per_full_token`, a blended coefficient (SWA ratio x SWA bytes + compressed-attention layers at 1/4 and 1/128 of KV bytes + indexer at 1/4, the 1/4 assuming a shrink factor of 1), inflated by (target + draft layers) / target layers under speculation (`model_executor/pool_configurator.py:1150-1165`, `1273-1302`, `1400-1412`). [Code-verified] The own DeepSeek V4.1 lane's 1,670.75 B/token/rank is this blended figure, which is why it sits far below 528 B times the layer count. [Interpretation]
- **Transfer.** PD disaggregation with Mooncake and NIXL backends and HiCache L2/L3 exist upstream. No GB10 PD run was found.

### llama.cpp and forks

- **llama.cpp mainline.** KV types are f32, f16, bf16, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1; there is no FP8 or NVFP4 KV. A quantized V cache needs flash attention (auto-enabled, else an error), and the quant block must divide the head dim (`common/arg.cpp:304-314`; `src/llama-context.cpp:3781-3812`). GB10 is special-cased as `GGML_CUDA_CC_DGX_SPARK 1210` (`ggml/src/ggml-cuda/common.cuh:61`) in flash-attention kernel selection for the 576/512 MLA shape at GQA ratio 20 (`fattn.cu:369`) and in MMVQ. [Code-verified]
- **Prefix reuse.** The server reuses the longest common token prefix per slot (`--cache-prompt`, default on), can shift matching chunks (`--cache-reuse N`, default 0), keeps a host-RAM prompt cache (`--cache-ram`, default 8,192 MiB, which on GB10 comes out of the same memory), and for sliding-window or recurrent models stores up to 32 context checkpoints per slot at a minimum 8,192-token spacing (`common/common.h:626-632`; `common/arg.cpp:1686-1728`, `3568-3586`). The grain is one token. [Code-verified]
- **ds4 (DeepSeek V4 Flash only) and its forks.** antirez/ds4 keeps FP8 as the runtime KV format, matches the live token prefix first and then rendered-text prefixes persisted on disk, with boundary trim and align controls (docs/SERVER.md at `0aaea5a`). [Community-measured] The Entrpi fork (ds4-on-spark, v0.6.5 pinned at `99fb7b1`) adds per-sequence KV banks, continuous batching, fork-by-copy fan-out and a memory governor with a 4 GiB system-free floor (`--mem-floor-gb`, default 4). The CUDA fork by tylerwagler, since renamed Pulsar, stores the ratio-4 indexer cache MXFP4-packed by default (`PULSAR_IDX_FP4`, README at `3b7d0a5`). [Community-measured] `--cuda-tensor-parallel` must not be used on a single node; two-node network TP in upstream ds4 rebuilds saved token prefixes on both ranks on load. [Community-measured]
- **Anemll DSpark port (a vLLM fork, listed here because the lanes that use it are ds4-lineage DeepSeek V4 deployments).** Built on the vLLM v0.25.1 tag with FlashInfer `0472b9b3`, it adds `nvfp4_ds_mla` as a first-class DeepSeek V4 KV format but stores a "tested 584-byte packed sparse-MLA token envelope for both MLA and sliding-window cache groups", block size 256, through a FlashInfer SM120/121 sparse-MLA bridge (Anemll/dspark-vllm-gx10 README at `081fda9`). [Community-measured] That the name only selects kernel dispatch, not a 4-bit record, is an inference. [Interpretation] Independently, a vLLM 0.27.1 GB10 lane notes that an earlier runtime routed `nvfp4_ds_mla` to the same FP8 DS-MLA record and that 0.27.1 treats the name as an alias; no packed DeepSeek V4 writer and reader exist at that tag (nepenth deepseek-v4-flash-gb10 docs/NVFP4_DS_MLA.md at `e82bab4`). [Community-measured] The upstream DSpark recipe's design doc states `nvfp4_ds_mla` and `fp8_ds_mla` are byte-identical 584 B rows (MiaAI-Lab DeepSeek-v4-Flash-DSpark-2x recipe, docs item8-fp4-kv-design, written against Anemll image 0.1.1 / FlashInfer 0.6.15). [Community-measured]

### ExLlamaV3 in vLLM

- **Native ExLlamaV3.** Quantized KV is 2 to 8 bits per element in 32-element groups (`CacheLayer_quant`, `exllamav3/cache/quant.py:13-45`), paged at `PAGE_SIZE = 256` (`constants.py:2`); there is no FP8 or NVFP4 dtype. Pages are hashed with blake2b chained over the previous page hash (`generator/pagetable.py:23-42`). Recurrent models stash state checkpoints in host memory (`RecurrentCache`, default 4 GiB LRU with stranded-first eviction, `cache/recurrent.py:1-40`) and cap KV prefix reuse at the last page that has a stored recurrent state (`pagetable.py:255-290`); on GB10 host and device memory are the same pool. [Code-verified]
- **GB10 forks.** A MiaAI-Lab ExLlamaV3 fork advertises NVFP4 (E2M1 + block-16 E4M3, about 4.5 bits per element) and FP8 KV with online dequant in Triton paged attention, "measured lossless at generation level, ~3.5x more context per GB than fp16" (README at `63b32f0`). There is no protocol or table behind the claim; it is an unqualified project claim.
- **EXL3 inside vLLM** (own GLM 5.3 and DeepSeek V4.1 lanes; community GLM and DeepSeek V4 kits). ExLlamaV3 supplies weights and kernels only; KV dtype, page layout and prefix caching are vLLM's, so every vLLM item above applies, subject to the fork version. [Interpretation] (consistent with the Reederey87 GLM kit architecture doc at `8e443d6`: EXL3 weights, KV `fp8` mapped to packed `fp8_ds_mla` through FLASHINFER_MLA_SPARSE_SM120) GB10-specific overlays seen in community kits: a fine-grained APC exemption for the indexer tail, per-group retention, per-request no-store, compact 528 B NoPE rows, DCP2, and an NVFP4 latent gather (rows in §4 and §5).

### TensorRT-LLM (status)

- The TensorRT-LLM quantization page marks FP8 KV "Y" for Blackwell sm120 and NVFP4 KV for sm100/103 only, has no SM121 row, requires an offline ModelOpt checkpoint for NVFP4 KV and "only supports FP8 weight/activation quantization when NVFP4 KV cache is enabled" (nvidia.github.io, fetched 2026-09-23). FP8 KV on SM121 is therefore unknown, not unsupported. On one GB10, `trtllm-serve` 1.3.0rc7 refused Qwen3-Next hybrids ("mamba hybrid cache requires block reuse to be disabled") (NVIDIA forum 363540), and 1.3.0rc17 `quantize.py` could not place tensors because NVML free memory is unsupported on GB10 (TensorRT-LLM issue #15021, closed). [Community-measured] No TensorRT-LLM KV-dtype speed A/B on GB10 was found.

## 3. What is different on GB10 / SM121

- [Code-verified] No FP8 attention math on the stock SM12x paths. FlashAttention's FP8 KV gates are SM90 and SM100 only, so FP8 KV on GB10 switches the backend (to FlashInfer, Triton or the opt-in B12X) and becomes storage plus in-kernel dequant; the merged QSA kernel upcasts K and V because QK in FP8 did not pay on SM120 [Community-measured].
- [Code-verified] Dense NVFP4 KV is refused by stock vLLM on GB10 and accepted by SGLang, which prefills through an FP8 workspace and decodes through XQA. The only GB10 speed reports for NVFP4 KV (single stream, 2x GB10, derivative images) are slower than FP8 [Community-measured]; the capacity-bound gains are measured on SM120 only.
- [Code-verified] The SM120 sparse MLA backend used on GB10 takes FP8 records (`fp8_ds_mla`), not `nvfp4_ds_mla`; real packed FP4 MLA records on GB10 exist only in forks (416 B DeepSeek V4, 288 B GLM-5.3, 368 B GLM-5.2) [Community-measured].
- [Community-measured] Shared memory per block limits tile shapes on SM12x: an FP8 two-stage wide prefill tile needed 106,496 B against 101,376 B and lost a pipeline stage (PR #54846, measured on SM120; the single-node GX10 FP8 QSA patch halved `block_n` for the same reason, per its author).
- [Code-verified] Free memory is MemAvailable, not device free memory: vLLM and SGLang size the pool from `psutil` available on integrated GPUs, which counts page cache the driver cannot hand out instantly. A pin that the budget accepts can still fail in the driver (`NV_ERR_NO_MEMORY`) [Community-measured]. The whole topic of headroom is on [Memory management on a unified-memory GB10](11-memory-on-unified-memory.md).
- [Community-measured] The default utilization preallocates most of the node: on one Spark at the then-default 0.9, a 19 GB model got 89 GB of KV (117 GB process); utilization 0.2 gave 4 GB (NVIDIA forum 364886). HEAD's default is 0.92 [Code-verified].
- [Measured] Hybrid pages on GB10 are thousands of tokens long, so hit grains are coarse: 3,584 tokens on the GLM TP2 lane, 2,560 on the TP3 lane (every observed TP3 hit is an exact multiple of 2,560), 256-token blocks on the DeepSeek V4 vLLM pair. Community GB10 grains: 3,584 on a GLM TP2 kit; 1,568 / 1,600 / 1,648 on a hybrid Qwen 27B at speculative depth K = 0 / 3 / 7 (vLLM issue #53670); 3,184 on a single-node Qwen Flash Next under FP8 KV [Community-measured]. The page is set by the linear-attention state size and speculation depth, not by `--block-size`. [Interpretation]
- [Measured] On multi-node lanes an MLA latent is replicated on every rank (own DeepSeek V4.1 SGLang TP3: "do not multiply by three"), so adding nodes adds bandwidth and weight room but not KV tokens unless DCP shards the cache.
- [Code-verified] SGLang carries an SM121-only QSA decode kernel because the TRT-LLM sparse decode silently corrupted long-context decode on GB10 (token id 0 at 120K to 210K).
- [Community-measured] FlashInfer's non-tensor-core paged decode wrapper crashed on SM121 at GQA ratio 16 or more (ratio 8 was fine); the maintainer says it affects every SM on that path (fix #2895), `use_tensor_cores=True` avoids it, and Triton attention bypasses it (FlashInfer issue #2849, closed).
- [Community-measured] KV transfer infrastructure built for discrete GPUs stumbles on unified memory: NIXL failed at backend init on two GB10 nodes (`NIXL_ERR_BACKEND`, UCX registration of UMA memory suspected; `UCX_TLS=tcp` did not help), and LMCache's L1 can only be given about 4-6 GB on a GB10 (NVIDIA dgx-spark-playbooks issue #82; NVIDIA forum 375308).
- [Community-measured] Headless GB10 firmware reserves about 2 GB for display that becomes CUDA-allocatable after a driver modeset change and has been used for KV (NVIDIA forum 383583). A probe with a main-memory control (MiaAI-Lab GLM PR #234, open, `cd504b6`) measured that region at 162 GB/s read / 114 GB/s write against 235 / 196 GB/s for `cudaMalloc` memory, about 69% [Community-measured]; see [Memory on unified memory](11-memory-on-unified-memory.md). An earlier ~160 vs 250-260 GB/s claim came without a method.
- **Bytes per token on GB10, by family** (record = code; allocator = measured pool bytes / pool tokens):
  - MLA with GLM NoPE via zero pad: 656 B record [Code-verified]; own GLM TP2 about 0.72 GiB per 100K tokens [Measured] (2026-08-28 GLM 5.3 Flash EXL3 TP2 500K stabilization qualification).
  - MLA, DeepSeek V4: 584 B record [Code-verified]; about 6,800-10,300 B per logical token per rank across four 2x GB10 boots on mixed stacks (7,327 / 10,303 / 6,822 / 7,231 B, the last own) [Community-measured], [Measured]; the spread depends on stack, drafter and slots.
  - MLA, DeepSeek V4.1: 528 B record [Code-verified]; SGLang blended 1,670.75 B/token/rank plus a fixed ~0.30 GB sliding-window pool [Measured] (2026-09-13 DeepSeek V4.1 Flash SGLang TP3 qualification); 16 GiB/rank for about 4.57M tokens on a 4x GB10 vLLM fork, with about 3.2 KB per token on its disk tier [Community-measured] (nacyot vllm-ds4f-gb10, `5be09c5`).
  - Dense GQA, no own row: Qwen3-4B (36 layers x 8 KV heads x 128) is 73,728 B per token at FP8 and 41,472 B at NVFP4 by config arithmetic [Interpretation]; one Spark SGLang boot held 1,371,456 FP8 and 2,309,504 NVFP4 tokens [Community-measured] (NVIDIA forum 377425), which by config arithmetic is about 94.2 and 89.2 GiB; the same post's RTX PRO 6000 boot logged about 43.5 KB per NVFP4 token against 41,472 B from config, so config arithmetic under-counts by about 5% [Interpretation]. The 1.68x token ratio against a 1.78x byte ratio fits the NVFP4 FP8 prefill workspace [Interpretation].
  - Hybrids (few full-attention layers): Nemotron-3-Nano f16 KV 768 MiB at 131,072 context (about 6 KB per token) [Community-measured] (Memoriant, `ecd3353`); Qwen3.8-Flash-Next 24 KB fp16 and 12 KB 8-bit per token in ExLlamaV3 (12 of 48 layers full attention) [Community-measured] (vcruz305, `e0ebee8`); Qwen 3.8 27B 43,008 B per token at FP8 (target 32,768 + drafter 10,240) plus a flat 1.58 GB of Mamba state [Measured] (2026-08-19 Qwen 3.8 27B single-node DFlash2 campaign audit). Allocator ratios on hybrids include recurrent state and are not layout constants.

## 5. Levers, ranked

Ranked by evidence strength times the TTFT or capacity recovered on the model families this fleet runs. Prefix-cache levers come first because a miss on a long agent prompt costs minutes, while a capacity lever costs a few percent.

1. **Put everything that varies per request after every stable byte.** Applies to: every engine x every model family x every topology. Gain: at 152K tokens, 92.3 s -> 2.1 s per reasoning-tier change; about 84-157 s per toggle on real traffic [Measured] + [Interpretation]; 0 -> 98.5-98.8% cached across effort switches with a stable-history encoder [Measured]; community (not GB10) 0.3% -> 87% hits by moving volatile fields to the tail [Community-measured]. Cost: a template change or a small proxy that renders and tokenizes. Risk: correctness, not just cache: tail placement produced malformed High-tier answers in 10 of 22 reps (other pages quote 9 of 20 from the same 2026-09-11 packet; possibly two runs of the probe, and which count is right is unresolved), and pre-placement at max tier thought 6x longer on one fixture [Measured]; a proxy that forwards token ids must fall back on media-bearing histories. Smallest falsifying experiment: the 16,579-token three-call sequence (low -> high -> low) with a system prompt and tools present, head vs candidate placement; the candidate passes if every call after the first caches the full stable prefix to the page grain.
2. **Fix hybrid and drafter cache accounting before tuning anything else.** Applies to: vLLM (and EXL3 in vLLM) x hybrid or MLA models with a separate drafter (GLM-5.3, Qwen hybrids with DFlash) x any topology. Gain: pool +81% at equal memory and prefix reuse from a 7K ceiling to 97.7% at 300K [Measured]; compact drafter KV +31% pool at the same pin [Measured]. Cost: a kit or fork update. Risk: these are fork patches; an upstream rebase can re-open the bug. Smallest falsifying experiment: two interleaved sessions of about 10K tokens plus one 2,540-token interloper; a correct cache keeps the first session's hits.
3. **Choose the prefill chunk against the page-id budget, not only against prefill speed.** Applies to: vLLM hybrid MLA lanes with a sparse-indexer tail group (GLM-5.3) and sliding-window groups (DeepSeek V4.1 EXL3). Gain: 7,168 -> 4,096 gave +16% pool, turned a 524K exact-repeat miss into a 3.2 s hit, at about -4% cold prefill per halving, decode unchanged [Measured]; 1,024 vs 8,192 on DeepSeek V4.1 EXL3 held 13% more token-equivalents [Measured]. Cost: a few percent of prefill (chunk sizing: [Prefill optimization](04-prefill-optimization.md)). Risk: 900K and 1M repeats at 4,096 are not re-run. Smallest falsifying experiment: cold then exact repeat at 524K, 900K and 1M at chunk C and C/2, same pull; record cached tokens and the logged pool.
4. **Set hybrid prefix-cache retention deliberately (interval 0 or per-group).** Applies to: vLLM hybrid lanes (KDA/GDN/Mamba + sliding window) x any topology. Gain: on a GB10 GLM kit, round-2 hits 0% -> 95-98% under concurrent agentic load; per-group retention recovered subagent forks (0% -> 37-49%) but cost hits at the pool edge (75.0% -> 49.9% at 4x200K) [Community-measured]. Cost: none at boot. Risk: a PR comment reports 0% Mamba hits with EAGLE under the new default [Community-measured]; the own lanes carry interval 0 from a community integration without an A/B. Smallest falsifying experiment: two 68K sessions, round 2 after a third 68K session, interval 0 vs dense, one boot each.
5. **Refine the hit grain on hybrids** (`--prefix-match-unit`; exempting a small indexer-tail group from alignment). Applies to: vLLM hybrid lanes whose page is thousands of tokens. Gain: grain 3,584 -> 64, a 6.5K follow-up reused 6,464 instead of 3,584 tokens, TTFT ~4.1 -> ~1.0 s, at -2.7% structured decode [Community-measured]. Cost: small decode tax. Risk: the upstream path needs a match unit that divides every group's block size, and it interacts with speculation and checkpoints (§2). Smallest falsifying experiment: a 6.5K first turn plus a short follow-up, grain on vs off; record `cached_tokens` and decode on a fixed fixture.
6. **FP8 KV on non-MLA and hybrid models.** Applies to: vLLM and SGLang x GQA and hybrid families x any topology. Gain: x1.70 pool with cold prefill flat, tool and long-context gates at parity [Community-measured, matched 2x GB10]; x1.9 on a single node with an earlier kernel [Community-measured]. Cost: -6.6% single-stream decode at 8K and -7% to -11% concurrent with MTP; the drop comes with lower acceptance (0.725 -> 0.630), and that the kernel is not the cause is the commenter's explanation [Interpretation]. Risk: scales silently at 1.0 when absent or mis-keyed (logged once); one hybrid report of repetition with uncalibrated scales (§7); FP8-KV quality gates are on [Quality and correctness gates](21-quality-and-correctness-gates.md). Smallest falsifying experiment: same image and checkpoint, dtype-only change, C1 decode with MTP on and off plus a 131K cold prefill; if MTP-off decode also drops, the kernel is part of the cost.
7. **Declare the pool size instead of letting it fill leftovers.** Applies to: SGLang (`--max-total-tokens`) and vLLM (utilization or explicit bytes) x any model x any topology. Gain: headroom, not speed: 6.7 -> 29 GiB available on one node [Measured]; pool size did not move cold TTFT (28.8 -> 29.1 s for a 5.4x pool cut, 9x more free memory) [Measured]; one GB10 operator lost 18% throughput at 32 streams by uncapping a pool that peaked at 67% use [Community-measured]. Cost: logical capacity that was mostly unused. Risk: an explicit vLLM byte pin removes the profiler margin and can fail in the driver even when the budget accepts it (§7). Smallest falsifying experiment: one boot with the cap at the measured peak live-token count plus 10%; warm available should rise by at least the pool bytes removed.
8. **Match speculation depth to the prefix and pool you need.** Applies to: vLLM hybrids with EAGLE, MTP or DFlash drafters. Gain or loss: one speculative block of reachable prefix is dropped per hit (69.4% -> 42.5-43.3% hit rate, TTFT 0.66 -> 1.93-2.04 s on one GB10) [Community-measured]; pool falls with depth (877,909 at K = 1 to 490,739 at K = 4) [Community-measured]; KDA state reserves 2 + k blocks per slot (about 514 MB at k = 7 vs 114 MB at 2) [Measured] + [Interpretation]. Cost: decode speed from speculation. Risk: the trade-off moves with each upstream fix to the last-block drop (#48375 open); `disable_eagle_block_drop` (PR #53388, merged 2026-09-01) restores first-repeat hits under MTP (hits 0 -> 50.1%, TTFT 3.9 -> 1.6 s on one nightly, see [Linear attention and hybrid layers](07-linear-attention-and-hybrid-layers.md) §4) [Community-measured]. Smallest falsifying experiment: the 7.3K-seed, 6-turn session at k = 0, 3, 7 on one lane; record hit rate, TTFT and decode.
9. **Internal FlashKDA prefill checkpoints (upstream #52789 / #53614).** Applies to: vLLM KDA hybrids (GLM-5.3, Kimi-class) x any topology. Gain on GB10: none measured; on Kimi-K3 TP8, TTFT -9.4% to -25.5% and incremental P50 TTFT -25.6% with partial hits [Community-measured, not GB10]. Cost: a rebase or port plus a FlashKDA build with the checkpoint tail (multi-week for a forked lane). Risk: kernel ABI and fork drift. [Proposed] for GB10 lanes. Smallest falsifying experiment: cold prefill at 8K and a partial-hit follow-up, old path vs new, same checkpoint.
10. **Offload long sessions to host or disk instead of re-prefilling.** Applies to: vLLM MLA lanes on 2-4 nodes with multi-hundred-K sessions. Gain: 493K restored in 7.8 s vs 392 s cold on 4x GB10 [Community-measured]; LMCache 32K restore 0.344 s vs ~102 s [Community-measured]. Cost: host staging comes out of the GPU's share of unified memory; L1 can only be 4-6 GB. Risk: LMCache restore failures under warm L1, one divergent restore at temp 0, a ranks 1-3 deadlock under MLA/TP, a documented dead-server hang; the own lanes rejected LMCache on these grounds without a run [Historical diagnostic]. [Proposed] for the own lanes. Smallest falsifying experiment: one 131K session evicted by a second session, then restored; compare restore TTFT and a greedy output checksum against recompute.
11. **Smaller MLA records** (native 528 B NoPE rows for GLM instead of 656 B zero-padded; packed FP4 latents of 416 B for DeepSeek V4 or 288 B for GLM). Applies to: vLLM MLA lanes on GB10. Gain: native NoPE sized at about +15% logical tokens from the same pool [Interpretation]; the 416 B DeepSeek branch held about 6% more tokens per GiB than a 584 B lane in unmatched boots (the record is 28.8% smaller; the rest of the pool is other groups) [Community-measured]; a GLM 288 B fork reports about 2.3x pool density (no matched boot). Cost: a FlashInfer upgrade (native NoPE) or an out-of-tree writer and reader (FP4). Risk: alignment re-tiering under `mamba_cache_mode=align`; FP4 quality unmeasured at long context on GB10. [Proposed] for the own lanes. Smallest falsifying experiment: same image, same pin, record size only; compare logged pool tokens and a 250K retrieval gate.
12. **Dense NVFP4 KV (SGLang).** Applies to: SGLang x GQA and hybrid families x capacity-bound serving. Gain: none on GB10 at single stream (44.0 vs 56.8-58.6 tok/s FP8) [Community-measured]; +37-78% peak-batch decode under capacity-bound load on SM120 [Community-measured, not GB10]. Cost: single-stream decode; prefill through an FP8 workspace. Risk: accuracy -0.31 to -1.01 pp on SM120 benches; GB10 capacity-bound regime unmeasured. Smallest falsifying experiment: same image, FP8 vs NVFP4 KV, at a concurrency that saturates the FP8 pool at 160K context; compare aggregate decode and the pool.
13. **Quantized KV in llama.cpp and native ExLlamaV3.** Applies to: single-node GGUF and EXL3 lanes. Gain or loss is kernel-specific: ExLlamaV3 8-bit was faster than fp16 at every depth (+7 tok/s at 240K) [Community-measured]; llama.cpp q8_0 lost 34% decode at ~110K while prompt speed held [Community-measured]. Cost: none at boot. Risk: generalizing either result to the other engine. Smallest falsifying experiment: same model depth sweep (4K, 32K, 110K), fp16 vs 8-bit, in the engine you serve with.
14. **Shard MLA KV across ranks with decode context parallel.** Applies to: vLLM MLA lanes at TP2 or TP3. Gain: none measured on GB10; community recipes report 4.6-4.7M logical tokens at a 1M ceiling with 528 B NoPE rows plus DCP2 [Community-measured, no DCP on/off A/B]. Cost: per-layer collectives over the RoCE link. Risk: decode slowdown from collectives that may exceed the capacity gain. [Proposed]. Smallest falsifying experiment: DCP1 vs DCP2 on one lane, same pin; record pool tokens, decode at 8K and 262K, and per-rail RDMA counters.

## 6. Protocol

This is the protocol an agent runs for any change that touches the KV cache or prefix reuse: a KV dtype, a block or match unit, a retention setting, a chunk size, a drafter setting, a pool size, a template or proxy change, an offload connector. It is grounded in the incidents in §4 and §7. See also [Profiling protocol](14-profiling-protocol.md) and [Memory management on a unified-memory GB10](11-memory-on-unified-memory.md).

**Preconditions (fleet rules, all mandatory).**
- All index rules apply (see [the entry page](README.md)), in particular: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor measured after the longest qualified prefill, and traffic stopped below 4 GiB; a greedy logprob probe after every relaunch; discard the first request and warm every serving shape before timing; a unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection or configuration line read on every rank; at least 3 repetitions with a closing baseline (A/B/A); MemAvailable sampled every 1-2 s with zero NV_ERR_NO_MEMORY or Xid lines; no reboot or power cycle without per-node permission; correctness gates from [Quality and correctness gates](21-quality-and-correctness-gates.md) before any speed number. For this page: warm every serving shape, read the KV and backend configuration line on every rank, and run the quality gates before any speed or capacity number.
- No memory overcommit: at least 8 GiB MemAvailable on every rank before a start, and a warm floor of at least 5 GiB on every rank after the longest qualified prefill.
- One variable per boot. KV pin raises are at most 1.5 GiB per boot. A change that frees memory and a change that spends it are two boots.
- Stop traffic when MemAvailable falls below 4 GiB on any rank; preserve the engines.
- Clean window: no co-tenant GPU work, builds or other benchmarks; the lane's owner has agreed to the downtime.
- Restart A/Bs with the image and recipe pull skipped, so both arms run identical bits.
- Never restart a serving gateway or front-end as part of the experiment; if the change needs one, stop and hand that step to the operator.
- Turn on per-request cache reporting before measuring: vLLM `--enable-prompt-tokens-details`, SGLang `--enable-cache-report`. Without them clients show zero cache reads while caching works.

**The change.** Exactly one variable. For a template or proxy change the engine does not restart; for anything else it does.

**Measure prefix reuse this way.**
1. Cold baseline with a unique nonce at the head of the prompt, so nothing is reused by accident.
2. Same-prompt, same-settings repeat: this is the reuse ceiling for the lane (the Flash Next lane's ceiling was 77.3% of a 25K prompt, not 100%). Every other arm is judged against this control, not against 100% and not against rendered-text overlap.
3. The arm under test, with a real system prompt and the full tools schema present on every turn. A harness that drops the tools block on turn 2 measures its own bug (380.8 s "miss").
4. For hybrid caches, a cold/repeat depth sweep across the served range (for example 8K, 32K, 131K, 250K, 524K, 750K, 900K, 1M): exact repeats can miss at particular depths while neighbours hit.
5. An interleaved two-session test (two long sessions alternating, plus one mid-size interloper), because single-chain probes hid the 7K ceiling.
6. Check that every cached count is a multiple of the lane's page or match unit; a count off the grain means you are reading the wrong counter.

**Measure a KV dtype or record change this way.** Same image, same checkpoint, dtype or record only. Read the boot line for the pool (vLLM `Available KV cache memory` and `GPU KV cache size`, SGLang budget line) and for scale loading ("Defaulting to scaling factors of 1.0" means uncalibrated). Run C1 decode with speculation on and off, a 32K and a 131K cold prefill, a capacity-saturating concurrency, and a long-context retrieval gate. Run a logprob sanity probe first; a KV-quality test on a model with a broken lm_head cannot see KV effects.

**Record (packet fields).** Engine, version and pin; the one-line diff; KV dtype, record bytes, page or block size, match unit, retention setting, chunk (MNBT and long-prefill threshold), speculation depth, slots; the boot lines verbatim; pool tokens and GiB per rank; scale-loading line; per-request prompt tokens, `cached_tokens` and TTFT for every arm; the control arm's ceiling; hit grain check; per-rank MemAvailable minimum during the run; decode tok/s and acceptance; cold prefill tok/s; trials per arm.

**Pass gate.**
- Prefix changes: every arm after the first reaches the control's ceiling to the page grain, with tools and system prompt present, and output quality holds on the fixed fixtures (the tail placement that was cache-safe failed here).
- Dtype and record changes: pool gain as predicted by bytes; cold prefill within 5% of baseline; decode change stated with and without speculation; retrieval and tool gates at parity.
- Hybrid cache changes: no new miss in the depth sweep; interleaved sessions retain at least 99% of the control on the second visit (the TP3 lane's measured bar).
- Memory: warm floor at least 5 GiB on every rank, no `NV_ERR_NO_MEMORY` during the gated workload.
- A correctness overlay passes only with a single-factor A/B that shows its benefit; the Mamba-align overlay cost 9-10% prefill and never showed one.

**Rollback.** Revert the one changed line or template, boot if the engine was restarted, and confirm the control arm's ceiling and the pool are back to the recorded baseline. For template or proxy changes, keep a canary that asserts the placement in both the host file and the running container; an upstream template revert once re-broke the cache and the canary, checking the old contract, stayed red until noticed.

## 7. Anti-patterns and known-bad

- [Measured] Reading the headline pool as prefix-cache capacity. `GPU KV cache size` is max concurrency x max_model_len summed over groups; `num_gpu_blocks` x block size under-counted a pool that later ran a 436K prefill; cumulative hit counters hide round-2 cliffs; rendered common-prefix percent overstates engine reuse (99.9% rendered vs 77.3% engine on Flash Next). Use per-request `cached_tokens` against a same-prompt control. A GB10 GLM kit reports the same: hit counters move only in multiples of 3,584 and sub-page prompts register 0 forever [Community-measured].
- [Measured] Per-request content at the head of the prompt. A reasoning toggle at about token 2 cost 84-157 s per toggle on real traffic [Measured] + [Interpretation]; a proxy that inserted the directive as a message rendered after the tools block shared only 22 characters between the two shapes; its "95.3% retention" came from a probe with no system message or tools.
- [Measured] Cache-safe is not correct. Tail placement kept the cache and produced malformed High-tier answers in 10 of 22 reps (other pages quote 9 of 20 from the same 2026-09-11 packet; possibly two runs of the probe, and which count is right is unresolved); a "frozen head + tail hint" variant leaked the hint into output and was removed.
- [Measured] Cache-measurement harnesses that change the prefix: turn 2 without the tools schema forced a 380.8 s re-prefill; an unsupported 90% hit threshold failed a correct candidate.
- [Measured] (quality gates: [Quality and correctness gates](21-quality-and-correctness-gates.md)) FP8 KV scales can be dropped with a single log line (key-path mismatch, 32 tensors, scale 1.0), and several production checkpoints ship no KV scales. Check the boot log.
- [Measured] Sizing an SGLang pool from leftovers: a 1.64M-token pool for a lane addressing 262,144 tokens left ~6.9 GiB and the node needed a power cycle. A declared cap freed 22 GiB.
- [Measured] The KV pool was not the binding memory in the worst incident: three nodes wedged on a ~200K prefix with the pool 25-28% used [Historical diagnostic]. Budget the prefill working set separately.
- [Measured] Spending freed memory in the same boot: an indexer-workspace rightsize and a KV pin raise together wedged a node until a power cycle; five 900K launches with an explicit vLLM KV byte pin died at warmup because the pin removed the profiler margin.
- [Community-measured] A KV pin the budget accepts can still fail in the driver: 5.5-7.5 GiB pins died with `NV_ERR_NO_MEMORY` while page cache from the weight load was unreclaimed; the direct-I/O loader that let 7.5 GiB allocate was followed by silent rank deaths 60-90 s after load in all four TP2 boots (tonyd2wild ladder). A direct-I/O loader also kept 4.43 GiB resident that would otherwise be KV (MiaAI-Lab kit issue #204).
- [Measured] Hybrid caches can miss exact repeats at particular depths: GLM TP3 at chunk 7,168 missed at 524K and 900K (338.9 s and 623.1 s) while 250K, 750K and 1M hit. Map the band before trusting long-session reuse.
- [Measured] A cache-correctness overlay can tax prefill: the Mamba-align chunking overlay cost 9-10% cold prefill at 95K with no measured benefit.
- [Measured] Radix-off "stability" profiles kill prefix reuse; the own Flash Next lane did not adopt one.
- [Measured] Two ~275K sessions could not both stay cached on the TP2 GLM lane (97.7% -> 0%, 8.3 -> 319 s) [Historical diagnostic]; the TP3 runtime later kept interleaved 131K and 524K sessions at 99.6%.
- [Community-measured] Hybrid prefix hits crash in stock vLLM paths on GB10: concurrent donors died in `precopy_mamba_align_fused_kernel` (#54199, retracted as a duplicate of #53142, still open), and varied-length prompts over a shared prefix crashed until #48375 and a #53142 fix, both open at HEAD (#54173).
- [Community-measured] The hybrid align checkpoint veto: one missing state checkpoint zeroes matched attention hits (0/64 before upstream #37898; 40/64 after, not GB10). TensorRT-LLM 1.3.0rc7 refused hybrid caches with block reuse on at all.
- [Code-verified] `nvfp4_ds_mla` is not 4-bit storage in the DSpark ports: the envelope is 584 B, the same as `fp8_ds_mla`; the own DeepSeek V4 pool under that label is FP8-record capacity. Stock vLLM uses the same string for 352 B and 288 B records on SM100 only.
- [Code-verified] "NVFP4 KV SM120 path upstreamed into vLLM" (hikarioyama README) is contradicted by HEAD: dense `nvfp4` KV raises off SM100 trtllm-gen, and the SM120 PRs are open. That repository's SM120 agentic A/B (34/89 vs 32/89, McNemar p = 0.815, 2x RTX PRO 6000) found no accuracy loss [Community-measured].
- [Community-measured] NVFP4 KV at single stream on GB10 is slower than FP8 (44.0 vs 56.8-58.6 tok/s, 2x GB10, derivative image). Do not carry the SM120 capacity-bound gain to a GB10 single-user lane.
- [Community-measured] "On ~273 GB/s LPDDR5X dequant never pays" is contradicted: ExLlamaV3 8-bit KV was faster than fp16 on one GB10 while llama.cpp q8_0 was slower [Interpretation: kernel-dependent].
- [Interpretation] "1M context: KV 96 GB at FP16 -> 1.7 GB at q4_0 (56x)" (thupalo README) uses an all-layer FP16 baseline for a hybrid model. The q4_0 size is plausible (Memoriant's 216 MiB at 131K scales to about 1.69 GiB at 1M); the real reduction from q4_0 is about 3.5x.
- [Community-measured] Retracted llama.cpp claims (q4_0 larger than f16, a 92% prefill collapse) came from RSS, which does not see GB10 unified allocations, and from failed requests (Memoriant v1; corrected in v3).
- [Interpretation] "Utilization 0.4 means 40% for weights and 60% for KV and the OS" (X post, MichaelGannotti) misreads the parameter: utilization caps the whole instance, weights included (§2 vLLM).
- [Community-measured] Uncalibrated FP8 KV quality is contested, not settled (gate it per [Quality and correctness gates](21-quality-and-correctness-gates.md)): one GB10 report saw repetition after ~500 tokens on a Qwen3.5 hybrid with `--kv-cache-dtype fp8 --calculate-kv-scales` and no scales file, fixed by BF16 KV (ai-muninn, 2026-03-21); against it, scale-1.0 FP8 KV recalled a ~21K needle at 64K context on GLM-4.7 (NVIDIA forum 375690) and the matched 2x GB10 A/B held tool and RULER gates at parity. The repetition report changed two flags on one model [Interpretation].
- [Community-measured] NIXL did not initialize on two GB10 nodes (`NIXL_ERR_BACKEND`, `UCX_TLS=tcp` no help); stock exo clustering of a Mac and a Spark runs CPU-only on Linux and did not reproduce GPU prefill (corti.com).
- [Community-measured] FlashInfer's non-tensor-core paged decode wrapper crashed on SM121 at GQA ratio 16 or more (fixed upstream, #2895).

## 8. Open questions

- Does NVFP4 KV pay on GB10 when the pool, not the kernel, is the limit? — Same SGLang image, FP8 vs NVFP4 KV, concurrency that saturates the FP8 pool at 160K context; aggregate decode and pool per arm.
- What do FP8 and NVFP4 dequant cost in isolation on SM121? — Kernel microbenchmark of the attention decode and prefill paths at 8K and 262K, BF16 vs FP8 vs NVFP4 KV, same shapes.
- Does FP8 KV cost prefill on current builds? The matched 2x GB10 A/B was flat; an earlier single-node patch lost 30% at 32K. — Single-node, merged kernel, dtype-only, 32K and 131K cold prefill.
- Is the -9% decode under FP8 KV entirely through speculative acceptance? — The same A/B with MTP off.
- Does a true packed FP4 MLA record keep quality and speed on GB10? — Same image and pin, 584 B vs 416 B (DeepSeek V4) or 656 B vs 288 B (GLM), with a 250K retrieval gate and C1 decode.
- Is the own DeepSeek V4 pair's alternating warm TTFT (0.42 / 5.37 s) the short-tail trap measured on a 4x GB10 fork (tails under 65 tokens past the last 256-token block drop the whole hit)? [Interpretation] — Vary the tail past the last full block (10, 64, 65, 200 tokens) on the own image and read `cached_tokens`.
- What page size does the own SGLang DeepSeek V4.1 build use? Upstream forces 256; the own build is not an upstream commit; observed hits (32,768 and 131,072) fit several sizes. — Boot log or server info on that build.
- What is the own Flash Next vLLM hybrid block size, and why does the same-prompt ceiling sit at 77.3%? — Boot log `block_size`, then a repeat at prompt lengths that straddle page boundaries.
- Do 900K and 1M exact repeats hit on GLM TP3 at chunk 4,096, and where exactly is the miss band? — Cold/repeat sweep 450K-1M at 4,096.
- Does retention interval 0 help or hurt the own hybrid lanes? It was carried in without an A/B. — Interval 0 vs dense on the two-session round-2 test and a subagent-fork shape.
- What do the doubled forward at a checkpoint boundary and its removal (#52789 / #53614) cost on GB10? — Cold prefill at 8K and a partial-hit follow-up, old path vs new, same checkpoint.
- How much memory does KDA state under speculation take, measured rather than computed? — Pool and MemAvailable at k = 0 vs k = 7, one boot each.
- Does the Mamba-align chunking overlay buy any resume benefit for its 9-10% prefill cost? — Resume-from-cache fixture with the overlay on vs off.
- How many bytes per token does a dense all-layer GQA model take on GB10, with GiB and tokens from the same boot? — One boot of a dense GQA model at FP8 and NVFP4 with both lines captured.
- What does DCP2 cost in collective traffic and decode on GB10, and what does it buy in pool? — DCP1 vs DCP2 on one MLA lane with per-rail RDMA counters.
- Can two GB10 nodes do phase-disaggregated serving with live KV handoff? — A two-node NixlConnector attempt with `UCX_TLS=tcp` and host buffers; if NIXL still fails, a plain TCP connector baseline.
- Do LMCache restores stay correct and available at scale on GB10? — Restore under warm L1 with eviction, greedy checksum vs recompute, 50 restores.
- What did the Spark-plus-Mac P/D repo actually transfer? Its 2.599 s for 32,000 tokens implies about 3.2 GB/s if KV were BF16, above a 10 GbE line rate. [Interpretation] — Per-transfer byte counts from the repo's logs, or a re-run with transfer size logged.
- How fast is the display-reserve region when used as KV? — Read bandwidth microbenchmark on that region vs main memory, then decode at a context that lands KV there.
- Does SGLang's `mxfp8` KV path run on SM121? It passes the startup gate. — One boot with `mxfp8` and a short decode and retrieval check.
- Does the FP8 QSA indexer cache (#54890) work and pay on GB10? — Indexer cache FP8 vs BF16 on a QSA model, prefill and decode at 131K.
- Is uncalibrated FP8 KV safe on hybrid models? — Same hybrid, BF16 vs FP8 at scale 1.0 vs FP8 with calibrated scales, a 2K-token free-generation repetition check and a long retrieval gate.
- Does TensorRT-LLM support FP8 KV on SM121? The matrix has no SM121 row. — One `trtllm-serve` boot with FP8 KV on a dense model.
- Is the MiaAI-Lab ExLlamaV3 fork's "lossless, ~3.5x context per GB" claim reproducible? — Its NVFP4 and FP8 KV vs fp16 on one model, with perplexity and a retrieval gate.
