# CUDA graphs and launch overhead on GB10

Hardware for every own row: ASUS Ascent GX10 (NVIDIA GB10, compute capability 12.1, 48 SMs, 128 GB unified LPDDR5X), one GPU per node, one to three nodes (node-1, node-2, node-3) over a direct RoCE fabric. Code lines are quoted at these pins: vLLM `34b069080d9f`, SGLang `2909f84e3b2f` (plus historical `49420741746c`), llama.cpp `6e60f35608ec`, antirez/ds4 `0aaea5a238fb`, ExLlamaV3 `6b84a21b6f1e`, PyTorch `9535d6b09f62`. Own lanes run older forks, so a code line says what upstream does at the pin, not what a given lane runs.

## 1. What it is

Every word a model writes needs one full pass through all of its layers, and the engine issues that pass to the GPU as hundreds to a few thousand separate small jobs called kernels (GPU work orders). Handing each job over costs the CPU a few microseconds; NVIDIA estimates 1-5 µs per kernel, and nobody has yet published the figure for GB10. A CUDA graph (a recorded, replayable job list) records the whole list once and replays it with a single call, so the CPU cost nearly vanishes. The catch is that a graph only fits the exact batch shape it was recorded with. Engines therefore record a fixed menu of sizes (buckets) at boot, and any step whose size is not on the menu runs the slow way, called eager (one launch per kernel). Speculative decoding (draft several tokens, verify together) multiplies the sizes, because each request checks 1 + k tokens per step. On a GB10 a warmed decode step is mostly limited by memory bandwidth, so graphs pay off where the CPU is the bottleneck: Python-heavy engines, steps that fall off the menu, and multi-node steps. They pay little where the step is already graphed and memory-bound; one GB10 measurement found the GPU 99.9% busy. Graphs also cost boot time (on this fleet mostly first-use compilation, not the recording itself), memory from the same shared 128 GB pool that keeps the node alive, and a set of failure modes (hangs, crashes, wrong output) when recording interacts with cross-node communication or with kernels that were never written to be recorded. Related pages: [Speculative decoding](02-speculative-decoding.md), [Memory on unified memory](11-memory-on-unified-memory.md), [Profiling protocol](14-profiling-protocol.md), [Inter-node communication](03-inter-spark-communication.md), [Engine dispatch maps](16-engine-dispatch-maps.md).

## 2. How each engine does it

### vLLM

Mechanism. Five modes: `NONE`, `PIECEWISE` (graphs between attention calls, attention eager), `FULL` (whole step), `FULL_DECODE_ONLY` (whole step for uniform decode batches, everything else eager) and `FULL_AND_PIECEWISE` (full for uniform decode, piecewise for prefill and mixed batches). Defaults by optimization level: -O0 `NONE`, -O1 `PIECEWISE`, -O2 and -O3 `FULL_AND_PIECEWISE` (`vllm/config/vllm.py` 253-340). [Code-verified]

- `--enforce-eager` sets the mode to `NONE` and empties the capture list, and at this pin it also sets compilation mode `NONE` and disables JIT kernel warmup ("equivalent to -cc.mode=none -cc.cudagraph_mode=none and --kernel_config.enable_jit_warmup=False", `vllm.py` 1668-1677, 1902-1909). A vLLM "eager vs graphs" pair taken with compile on is therefore a compile-plus-graphs bundle, not a graphs measurement. [Code-verified]
- Compile coupling. With compilation mode `NONE` (`mode:0`) and breakable graphs off, any mode that needs piecewise compilation is downgraded: `FULL_AND_PIECEWISE` becomes `FULL_DECODE_ONLY`, `PIECEWISE` becomes `NONE` (`vllm.py` 1083-1103; `vllm/config/compilation.py` 80-85). [Code-verified]
- Spec decode and attention backends. Each attention backend declares a graph-support level: FlashAttention 3 and Triton attention `ALWAYS`, FlashAttention 2 `UNIFORM_BATCH`, FlashInfer `UNIFORM_SINGLE_TOKEN_DECODE` (`UNIFORM_BATCH` only on its TRT-LLM path) (docs.vllm.ai design/cuda_graphs, fetched 2026-09-23); what FlashInfer declares on SM121 is pin-dependent (§3). With spec decode on, full decode graphs need a backend at `UNIFORM_BATCH` or better; if none qualifies and attention is not a splitting op (compile mode 0, breakable off), the resolver sets `cudagraph_mode=NONE` for the whole model, not `PIECEWISE` (`compilation.py` 1443-1461). Without spec decode, or with FlashAttention or Triton attention, mode 0 keeps `FULL_DECODE_ONLY`. [Code-verified]
- Breakable graphs (stream capture that breaks at attention and KV ops, no torch.compile) are switched on automatically when `VLLM_USE_BREAKABLE_CUDAGRAPH` is unset, for a fixed architecture list that includes DeepSeek V3.2, V4 and V4.1, GLM-5-Next (GLM 5.3 Flash) and GlmMoeDsa; turning them on forces compilation mode `NONE` (`vllm.py` 78-125, 771-846; `vllm/envs.py` 766-769; `vllm/compilation/breakable_cudagraph.py` 1-22). Opt out with `VLLM_USE_BREAKABLE_CUDAGRAPH=0`. [Code-verified]
- Default sizes on CC 12.1. The capture ceiling is `1024 if is_device_capability_family(100) else 512`, so GB10 gets 512; the effective ceiling is `min(max_num_seqs x uniform_decode_query_len x 2, 512)`, clamped to `max_num_batched_tokens`. Default grid: `[1, 2, 4]`, then 8 to 248 in steps of 8, then steps of 16, plus `max_num_batched_tokens` if it fits (`vllm.py` 2387-2397, 2479-2533). [Code-verified]
- Spec decode sizes. `uniform_decode_query_len = 1 + num_speculative_tokens` for every method (`vllm.py` 677-697). The default path scales a request-count grid by the query length rather than stretching the token grid (the source comment gives 581 sizes vs about 100 at 512 sequences and 16 drafts), and dynamic speculative decoding gets one request-count grid per tier (2398-2478). An explicit `cudagraph_capture_sizes` list is used verbatim. [Code-verified]
- Truncation. If only a scalar `max_cudagraph_capture_size` is given, it is truncated to the largest grid entry at or below it and startup logs `Truncating max_cudagraph_capture_size to N`; if both a scalar and a list are given and disagree, startup raises (`vllm.py` 2540-2571). [Code-verified]
- Dispatch. A batch whose unpadded token count exceeds `max_cudagraph_capture_size` runs `NONE` (eager); otherwise the dispatcher tries `FULL`, then `PIECEWISE`, else `NONE`. Uniform spec-decode batches need an exact multiple of the query length (`vllm/v1/cudagraph_dispatcher.py` 270-320). [Code-verified]
- Dynamic spec decode. With `num_speculative_tokens_per_batch_size` set and the V2 model runner off, `FULL_AND_PIECEWISE` is forced down to `PIECEWISE` with the warning "Use VLLM_USE_V2_MODEL_RUNNER=1 if you want to use full CUDA graphs" (`vllm.py` 1045-1062). [Code-verified]
- Memory. Before capture, a profiler captures the first two descriptors per mode and estimates graph memory as the maximum over modes of the first-capture delta plus the sum over modes of (N - 1) x max(second-capture delta, 1 MiB) (`vllm/v1/worker/gpu_model_runner.py` 6660-6749). Profiling runs whenever the mode is not `NONE`; `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS` (default 1) only decides whether the estimate is subtracted from the KV budget; the whole step is skipped when `--kv-cache-memory-bytes` is set (`gpu_worker.py` 581-603, 620-665; `envs.py` 2136-2141). After capture, the log line "Graph capturing finished in N secs, took X GiB" is the free-memory difference from `torch.accelerator.get_memory_info()` across the whole capture (`gpu_model_runner.py` 6830-6855). [Code-verified]
- Observability. `--cudagraph-metrics` (default off) records `(unpadded tokens, padded tokens, paddings, runtime mode)` per step and logs counts per interval (`vllm/config/observability.py` 67-70; `vllm/compilation/cuda_graph.py` 33-60; `gpu_model_runner.py` 4014-4021; `vllm/engine/arg_utils.py` 1579-1582). `--enable-layerwise-nvtx-tracing` adds per-layer ranges (`arg_utils.py` 1584-1586). [Code-verified]
- Flags and env vars: `--enforce-eager`, `-cc.cudagraph_mode`, `-cc.cudagraph_capture_sizes`, `-cc.max_cudagraph_capture_size`, `-O0..-O3`, `VLLM_USE_BREAKABLE_CUDAGRAPH`, `VLLM_USE_V2_MODEL_RUNNER`, `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS`, `--cudagraph-metrics`, `--enable-layerwise-nvtx-tracing`.

### SGLang

Mechanism. Two phases, each with its own graph backend: decode defaults to `full`; prefill defaults to `breakable` on CUDA and `tc_piecewise` (torch.compile) elsewhere; `full` prefill is opt-in per architecture (`model_executor/cuda_graph_config.py` 38-47, 121-131, 154-162). [Code-verified]

- Default decode ceiling on CC 12.1. `max_bs` comes from device-memory tiers: 60-90 GiB and 90-160 GiB both give 256 at TP < 4 and 512 at TP >= 4, with chunked prefill 8192 (`arg_groups/memory_hook.py` 88-170). [Code-verified] GB10 reports about 121.6 GiB total (vLLM #44740 log), so an uncapped GB10 decode list runs to 256 at TP1-TP3. [Interpretation]
- Bucket lists (`arg_groups/cuda_graph_hook.py` 622-674). Non-spec decode: `[1, 2, 4, 8, 12]`, 16-256 step 8, 272-511 step 16, then step 32. Spec decode: 1-8, 10-32 step 2, 40-64 step 4, 72-256 step 8, and up. `--disable-cuda-graph-padding` captures every size from 1 to `max_bs`. Prefill token buckets: 4-32 step 4, 48-256 step 16, and up to a prefill `max_bs` whose default is the chunked-prefill size for non-MLA backends and 2048 for MLA backends (`memory_hook.py` 224-231). [Code-verified]
- Legacy flags map onto the phase config: `--disable-cuda-graph` (both phases), `--disable-prefill-cuda-graph`, `--cuda-graph-max-bs-decode`, `--cuda-graph-bs-decode` (`cuda_graph_hook.py` 59-90). [Code-verified]
- Breakable prefill graphs are switched off automatically for KDA hybrid linear attention (GLM 5.3 Flash; "supports explicit BCG opt-in, but stays off by default"), DeepSeek V4 ("c4 indexer scratch is pinned in the capture pool and OOMs"), context parallel, decode context parallel, two-batch overlap, unvalidated all-to-all backends and non-allowlisted multimodal models; pipeline parallel is opt-in (`cuda_graph_hook.py` 114-145, 278-350). [Code-verified]
- Spec decode. Target verify is the decode runner itself with `speculative_num_draft_tokens` tokens per request; draft, draft-extend and MTP-draft steps get their own runners (LMSYS blog 2026-08-17; historical sglang `49420741746c` `cuda_graph_runner.py` 115-142, 186-201). The documented out-of-memory levers are `--cuda-graph-max-bs-decode 4` ("or even 2") and a smaller draft tree (docs.sglang.io speculative_decoding, fetched 2026-09-23). [Code-verified]
- Observability: the Prometheus counter `sglang:cuda_graph_passes_total{mode=...}` (one GB10 snapshot showed 282 decode-graph passes and 12 eager prefill passes, NVIDIA forum 383859) and `--debug-cuda-graph`. [Community-measured]
- Flags and env vars: `--disable-cuda-graph`, `--disable-prefill-cuda-graph`, `--disable-decode-cuda-graph`, `--cuda-graph-backend-{decode,prefill}`, `--cuda-graph-max-bs-{decode,prefill}`, `--cuda-graph-bs-{decode,prefill}`, `--disable-cuda-graph-padding`, `--debug-cuda-graph`, `SGLANG_USE_BREAKABLE_CUDA_GRAPH`.

### llama.cpp and forks

llama.cpp. CUDA graphs are compiled in by default for llama.cpp builds (`GGML_CUDA_GRAPHS_DEFAULT ON` in the top-level `CMakeLists.txt` 169-170; ggml-only builds default OFF, `ggml/CMakeLists.txt` 117-118, 209). At run time they are disabled only below Volta or when `GGML_CUDA_DISABLE_GRAPHS` is set; there is no SM121 gate (`ggml/src/ggml-cuda/common.cuh` 1297-1300; `ggml-cuda.cu` 4404-4418). [Code-verified]

- Policy. One graph per ggml compute graph, keyed by its first node pointer; a graph is captured only after two consecutive calls with no node-property change, re-instantiated through `cudaGraphExecUpdate` when properties change, and a sweep every 5 s evicts graphs unused for 10 s. A compute graph containing a MoE `MUL_MAT_ID` that takes the synchronizing fallback is not graphed at all. There is no static bucket list (`ggml-cuda.cu` 1878-1905, 2557-2664, 4425-4475; `common.cuh` 1477-1494). `GGML_CUDA_GRAPH_OPT=1` enables an optional graph-optimize pass that runs only with graphs on (`ggml-cuda.cu` 4597-4620). [Code-verified]
- Default on CC 12.1: the backend sets `cudaDeviceScheduleSpin` when the compute capability is 12.1 (`ggml-cuda.cu` 362-369), added by PR #16585 because the default schedule made every `cudaStreamSynchronize` slow on GB10. [Code-verified]
- ds4 (antirez) and its Entrpi fork. Per-layer "decode island" graphs: island 0 runs pre-norm through the QKV projection, island 1 attention output through FFN or MoE, island 2 exists for V4.1 tensor parallel; up to 64 layers x 3 islands x 4 variants. First sight runs eager, the second captures, later calls replay; any failure marks that entry dead and the island stays eager. Single GPU only (`enabled && g_n_gpus == 1`); `DS4_CUDA_DECODE_GRAPHS=0` disables. The source credits the design to Entrpi/ds4 commits abe26575, 2200c675 and 9caaa508 (`ds4_cuda.cu` 897-983). [Code-verified]
- A GB10 ds4 DSpark fork found graph executables accumulating across speculative variants because the per-variant LRU had no global limit (the author: "not a CUDA driver leak"); the fix is a global segmented LRU with a default of 24 live executables, validated over 6,954 DSpark cycles with 7 live executables (NVIDIA forum 376830 post 44). [Community-measured]
- Anemll lineage. The Anemll image is a vLLM DSpark fork, not a llama.cpp fork; its DeepSeek V4 path auto-enables breakable graphs when the env var is absent (vLLM section above). No other Anemll-specific graph code was read.

### ExLlamaV3 in vLLM

Inside vLLM, EXL3 is a quantization plugin and graph policy is vLLM's (above). [Code-verified]

- Native ExLlamaV3 captures per-module graphs with thread-local capture mode and patches kernel-node parameters on replay, including Triton driver-API nodes (`exllamav3_ext/graph.cu` 30-45, `graph.cuh` 80-139). EXL3 linear layers refuse graph capture above batch 1 (`TORCH_CHECK(!graph || graph->disabled, "BC_LinearEXL3 invoked with graph and bsz > 1")`, `libtorch/linear.cpp` 34-43); gated-delta-net layers keep a separate batch-N graph keyed on state-buffer geometry and fall back to eager on a geometry change (`libtorch/gated_delta_net.cpp` 345-372). No SM121-specific gating. [Code-verified]
- GB10 recipe practice (MiaAI-Lab GLM-5.3-Flash-EXL3 recipe @ `71962cd`). The launcher generates `{1,2,4,8,16,24,32}` plus every `n x (k+1)` for `n <= MAX_NUM_SEQS` and `k+1` in the adaptive set plus `DFLASH_TOKENS+1`, but only when `SPEC_METHOD=dflash` and `GLM53_ADAPTIVE_K` is `ema`, `on` or `1`; otherwise the stock list is `1 2 4 8 16 24 32` (DFlash) or `1 2 3 4 6 8 12` (MTP) (`start.sh` 298-326). The recipe exposes `CG_ESTIMATE=0` (default 1) to drop vLLM's graph-memory deduction, stating "estimate is 2.43 GiB while the captured graphs actually consume -0.19 GiB" (`start.sh` 177-181). [Code-verified]
- MiaAI-Lab DeepSeek-v4.1-Flash-EXL3 recipe @ `6f7d159`: capture sizes `1 2 3 4 6 8 12 18 24` (6 included for k3 x 2 sequences); every EXL3 GEMM shape is autotuned before capture (26 shapes x 5 row buckets, about 3 s) because an un-tuned shape raises "operation not permitted when stream is capturing"; auxiliary streams are disabled because two EXL3 kernels on different streams deadlock on the shared lock buffer. [Code-verified]
- The MiaAI-Lab ExLlamaV3 fork (@ `63b32f0`) adds `tools/cudagraph_probe.py` to graph the whole target-verify forward (parity plus speed); no GB10 result is published. [Code-verified]

## 3. What is different on GB10 / SM121

- [Code-verified] Capture ceiling. vLLM's default ceiling is 1024 only for compute-capability family 100 (B200, GB200, GB300); GB10 gets 512. SGLang puts GB10 (about 121.6 GiB) in the tier with decode `max_bs` 256 at TP < 4.
- [Code-verified] FlashInfer's graph-support level on SM121 is pin-dependent: at vLLM `34b0690` FlashInfer on SM121 declares only `UNIFORM_SINGLE_TOKEN_DECODE`, so with spec decode on and compile mode 0 a FlashInfer-only model downgrades to `NONE` and loses full decode graphs entirely (`compilation.py` 1443-1461); at vLLM `711fc55` it declares `UNIFORM_BATCH` when trtllm/XQA serves the head layout, and the downgrade is to `PIECEWISE`. Read the lane's own pin; see [Attention backends](06-attention-backends-sm121.md).
- [Code-verified] vLLM's all-reduce plus RMSNorm fusion needs compute family 100 or SM90 and never enables on SM121; attention-quant fusion, sequence parallelism and GEMM-communication fusion are off. The fusions that can fire on CUDA are norm+quant (when the RMSNorm/FP8-quant custom op is active), act+quant (the same, or any NVFP4 model), and at -O2 and above rope + KV-cache + MLA-cat fusion when the KV update is not split out (`vllm.py` 132-247, 253-340).
- [Code-verified] Inductor refuses max-autotune GEMM below 68 SMs (`torch/_inductor/utils.py` 2159-2185); GB10 has 48, so `max_autotune_gemm` never engages without overriding `is_big_gpu`. MegaCpp forces it with `TORCHINDUCTOR_MAX_AUTOTUNE_GEMM=1` plus the override, without before/after numbers. [Community-measured]
- [Community-measured] Unified memory breaks graph-memory accounting. `cudaMemGetInfo` reported 78 GiB free while `psutil` reported 115 GiB available on one GB10 (vLLM #46932, one reading). vLLM's estimator went negative on GB10 (vLLM #44740). [Measured] Own boots log 0.16 GiB on one rank and 3.48 GiB on another for the same capture list (2026-09-20 startup and prefill optimization, GLM 5.3 Flash EXL3 TP3).
- [Measured] Capture time here is dominated by first-use kernel compilation: 110 s on a first boot vs 40-43 s later with the same list, and 48-50 s falling to 17-19 s once a persistent compute cache was mounted (2026-09-14, 2026-09-16 and 2026-09-20 GLM 5.3 Flash EXL3 TP3 packets). The cause is [Interpretation].
- [Community-measured] Cross-node collectives are host-staged on GB10 (no GPUDirect RDMA), and PyTorch's default `capture_error_mode="global"` is invalidated by NCCL proxy threads; capture with `thread_local` mode at all seven capture sites was needed for stable cross-node capture (vLLM #46253). [Measured] Own TP3 preflights passed NCCL collectives from 4 KiB to 16 MiB under 5 graph replays on all three ranks only with `NCCL_CUMEM_ENABLE=1` and an explicit per-rank ring (2026-09-13/14 TP3 preflights).
- [Community-measured] The 101,376-byte per-block shared-memory limit blocks kernels before graphs matter: default SGLang MoE tiles requesting 147,456 bytes crash at startup with EAGLE on (NVIDIA forum 359960); a `persistent_topk` kernel wanting 128 KB blocked GLM-5.3-Flash capture until skipped on SM12x (NVIDIA forum 381543).
- [Community-measured] Compile toolchain traps on `sm_121a`: Triton's bundled CUDA 12.8 `ptxas` rejects it (triton #8539, #9181; fix `TRITON_PTXAS_PATH` pointed at the CUDA 13 `ptxas`; vLLM PR #32704 automates it, still open); PyTorch's CMake rewrites an unset `12.1` arch into `12.1(2.0)` and builds kernel-less extensions (PyTorch PR #174065 closed unmerged; vLLM PR #49904 merged 2026-07-28 works around it).
- [Code-verified] llama.cpp sets `cudaDeviceScheduleSpin` on CC 12.1 only. [Community-measured] The measured effect on DGX Spark was tg32 +19% (gpt-oss 120B) and +46% (gpt-oss 20B), against a baseline that had just gained extra stream syncs (llama.cpp PR #16585). Whether vLLM or SGLang would benefit from the same flag on GB10 is open (§8).
- [Community-measured] With graphs on, a GB10 decode step can be almost entirely GPU-bound: DeepSeek V4 C=1 decode measured 99.9% GPU-busy with a host gap of about 0.1% (vLLM #51522, breakable graphs). No empty-kernel launch time has been published for GB10 (§8).

## 5. Levers, ranked

Ranking rule: evidence of a GB10 gain first, then cost and risk. The pattern across §4 is consistent: the GB10 gain from graphs is concentrated where the host issues the step (Python engines, eager fallbacks, uncaptured buckets) and shrinks to noise when decode is bandwidth-bound and already graphed [Interpretation].

1. **Capture every reachable decode shape, and prove it from the boot log.** Applies to: vLLM (all forks, EXL3 inside vLLM) and SGLang x any model with spec decode x any topology. Size the list as every `n x (1 + k)` for `n` up to the slot count and every k the scheduler can pick, with the ceiling rounded up to a multiple of 8 so the top shape survives the default grid. Gain: 0 at concurrencies that were already captured; at a concurrency whose step fell off the list, -12% (C6 aggregate, MiaAI-Lab, median of 3) to 5.27x aggregate with a 26 s vs 0.84 s TTFT (vLLM #54933, 5 trials), and +36% at c=12 (0xSero) [Community-measured]. Cost: more capture time (43 -> 52 s per rank for 15 -> 25 sizes) and resident graph memory, which ranges from about 0.2 to about 2.4 GB depending on shape count and model [Measured; Community-measured]. Risk: low; the failure is silent, which is the reason for the boot-log check. Smallest falsifying experiment: one boot at the current list and one with the top `slots x (1+k)` shape removed, C6 (or the top concurrency) aggregate median of 3; no difference falsifies the lever for that lane.
2. **Regular graphs instead of breakable graphs where the model allows.** Applies to: vLLM DeepSeek V4/V4.1 and other architectures on the breakable auto-list x TP1-TP2 (TP3 unknown). Gain: +28.6% C1 and +13.1% C2 aggregate on 2x GB10 DeepSeek V4 Flash, corroborated at ~30% C1 by a second author [Community-measured]; no own A/B. Cost: none at run time; set `VLLM_USE_BREAKABLE_CUDAGRAPH=0` explicitly. Risk: medium on multi-node: regular graphs around host-staged collectives need thread-local capture (vLLM #46253), and one DeepSeek V4 pair saw replay hangs with both graph types. Smallest falsifying experiment: one boot per arm on the same image, C1 and C2 at a fixed 512-token decode, three trials each.
3. **Keep full decode graphs from being silently downgraded.** Applies to: vLLM x spec-decode models x any topology. Check three things: the attention backend declares `UNIFORM_BATCH` or better when spec decode is on (pin-dependent: at `34b0690` FlashInfer on SM121 declares only `UNIFORM_SINGLE_TOKEN_DECODE`, downgrade to `NONE`; at `711fc55` it declares `UNIFORM_BATCH` when trtllm/XQA serves the head layout, downgrade to `PIECEWISE`; read the lane's own pin, see [Attention backends](06-attention-backends-sm121.md)); a drafter's attention group does not fail FlashInfer's head-ratio check (vLLM #55581 found a padded target with 22 query heads per rank against a 3-KV-head drafter set the whole model to `NONE`); dynamic spec decode needs `VLLM_USE_V2_MODEL_RUNNER=1` for full graphs. Gain: up to +16% single stream in the one GB10 case where a backend swap kept full graphs (vLLM #49547; kernel and graph mode changed together) [Community-measured]. Cost: none. Risk: low; a different attention backend can change quality, so rerun correctness gates. Smallest falsifying experiment: boot twice, differing only in backend, confirm the logged mode differs, measure C1 decode.
4. **Persistent JIT / compute cache across boots.** Applies to: every engine x every model x every topology (startup only). Gain: graph-capture phase 48-50 s -> 17-19 s and container-to-API 275.7 -> 126.9 s in a change group that also made an import lazy [Measured]; a recipe author reports DFlash2 capture 30 s -> 0 s from the same change on a 2-node kit [Community-measured, one kit]. No serving-speed gain is implied. Cost: a writable cache volume per node. Risk: low, but a stale Triton cache once produced silently garbled output on GB10 (vLLM #41871), so pair it with a correctness gate after any engine or driver upgrade. Smallest falsifying experiment: two consecutive boots with and without the mount, capture seconds from the boot log.
5. **Warm every serving shape before timing or before users arrive.** Applies to: every engine x every model x every topology. Gain: removes first-shape compile outliers such as a C4 batch at 47.9 tok/s with 17.7 s TTFT and a 10.5 s vs 4.7 s first 8K prefill [Measured]. Cost: tens of seconds after ready. Risk: low, as long as warmup does not overlap timed gates. Smallest falsifying experiment: two timed passes after boot, first without warmup, second with; compare the first-pass maximum TTFT.
6. **Cut small kernels inside the step (fused norm/quant/rope, cooperative MoE, fused sampler, fewer index ops).** Applies to: vLLM and SGLang x MoE and hybrid models x TP1-TP3. Gain band: unknown on GB10 serving. Evidence: ~2,000 small kernels take ~10 ms (~12%) of an 82 ms DeepSeek V4.1 TP3 step [Community-measured]; a stock MoE layer costs 0.107 ms more than a cooperative one in graph replay (cooperative MoE: [MoE dispatch](08-moe-dispatch.md)) [Historical diagnostic], an estimated 4.5 ms per step [Interpretation]; removing 6 `index_select` + 2 `index_copy_` per layer on mixed spec steps gave +5.2-7.7% end to end on Kimi-K3 TP8, not GB10 (vLLM PR #56159) [Community-measured]; a fused Markov argmax on an older vLLM DSpark tree gave C4 +5-14% and was C1-neutral [Community-measured] (a different knob from `DSPARK_ENABLE_REPLICATE_MARKOV`, which measured no C1 gain and C6 122 vs 148 tok/s; the §4 capture-ceiling row pairs the same 122 with 139, and whether the two comparisons are different runs is unresolved). Counter-evidence: on bandwidth-bound single-GPU ds4 decode, -61 launches per token and ~300 launches moved into graphs were both flat [Community-measured]. Cost: kernel work, days ([Kernel authoring on SM121](15-kernel-authoring-sm121.md)). Risk: correctness; the default vLLM norm/act-quant fusions produced token salad on DeepSeek V4 Flash on 2x GB10 (vLLM #50773). Smallest falsifying experiment: torch-profiler per rank for 40 steps before and after, kernels per step and wall step time; no wall-time change falsifies it.
7. **Prefill graphs (SGLang breakable prefill, vLLM piecewise or breakable prefill).** Applies to: SGLang and vLLM x models not on SGLang's auto-disable list x TP1-TP2. Gain: prefill-only 1.45-1.93x on 4x GB300 [Community-measured, not GB10]; no GB10 number exists (prefill levers: [Prefill optimization](04-prefill-optimization.md)). Cost: resident graph memory (42 shapes on a 78-layer MoE added 2.4 GB on GB300) and boot time. Risk: high on GB10 memory ([Memory on unified memory](11-memory-on-unified-memory.md)): an own prefill-graph capture at mem-fraction 0.90 with an oversized pool ran out of memory (2026-08-19 Qwen 3.8 27B FP8 DFlash2) [Measured]. [Proposed] Smallest falsifying experiment: one boot with prefill graphs on at a pool pinned 10% smaller, cold 8K and 32K TTFT, post-capture MemAvailable.
8. **torch.compile / Inductor on vLLM lanes (compile mode above 0).** Applies to: vLLM x models that carry `@support_torch_compile` x TP1. Gain: +3% for 13 GB more memory on one GB10 Nemotron-3-Nano NVFP4 (compile and graphs bundled, NVIDIA forum 364886) [Community-measured]; +5-8% from Inductor RoPE + KV-write fusion on GB200, not GB10 (SGLang #21855) [Community-measured]; "fusion upside ~0" at 99.9% GPU-busy (vLLM #51522) [Community-measured]. Cost: minutes of compile at boot, inductor compile workers of ~0.5-0.6 GiB each outside the static pool [Measured]. Risk: high (see §7: garbled output, failed cached restarts, capture breaks, compile-wrapper dependencies). Smallest falsifying experiment: -O0 vs -O2 at an identical `FULL_DECODE_ONLY` capture set, C1 decode and the Inductor fused-kernel list from the log.
9. **llama.cpp and ds4: leave graphs on and the spin schedule in place.** Applies to: llama.cpp and ds4 forks x any GGUF model x single node. Gain: no published graphs-on vs graphs-off llama.cpp number on GB10 (the "~5-10% generation speed" in one GB10 recipe is stated, not measured); the spin schedule's +19% / +46% tg32 is against a baseline with extra syncs [Community-measured]. Cost: none. Risk: RPC splits with graphs crashed (llama.cpp #25791) and leaked to OOM before an upstream fix (#20315). Smallest falsifying experiment: `GGML_CUDA_DISABLE_GRAPHS=1` vs default, llama-bench tg128 at depth 0 and 32K, five repetitions each.

## 6. Protocol

Preconditions (fleet rules; see [the entry page](README.md)):
- All index rules apply (see [the entry page](README.md)), in particular: at least 8 GiB MemAvailable on every node before a start, a 5 GiB warm floor measured after the longest qualified prefill, and traffic stopped below 4 GiB; a greedy logprob probe after every relaunch; discard the first request and warm every serving shape before timing; a unique nonce at token 0 with zero cached tokens asserted from the usage block; every rank at the same clock cap with no latched rank; the selection or configuration line read on every rank; at least 3 repetitions with a closing baseline (A/B/A); MemAvailable sampled every 1-2 s with zero NV_ERR_NO_MEMORY or Xid lines; no reboot or power cycle without per-node permission; correctness gates from [Quality and correctness gates](21-quality-and-correctness-gates.md) before any speed number.
- No memory overcommit. Keep the warm floor free on every node, keep headroom before a start, raise a KV pin in bounded steps, and change one memory variable per boot. Graphs, inductor compile workers and activation peaks all live outside the static pool; reject any configuration with less than 15 GiB MemAvailable after capture (the rule adopted after a post-capture wedge, 2026-08-29 K10 pool-cap changelog) [Measured].
- One variable per boot. A capture-list change, a graph-mode change, a compile-mode change and a k-set change are four separate boots. A k-set change also changes the captured shapes and the kernel geometry per shape, so re-profile kernel dispatch for the new k-set or drop the arm (2026-09-20 GLM 5.3 Flash TP3 frontier dossier) [Code-verified].
- Restart A/Bs skip the image pull so both arms run the same image.
- Stop benchmark traffic when any node's MemAvailable drops below 4 GiB; do not kill the engine.
- Clean window: no outside requests during a measured arm; a contaminated baseline pass is discarded, not averaged.
- Never restart an agent gateway to test an engine change; make the change, verify, and hand the restart decision to the operator.
- Never `pkill -f` a pattern that appears in your own command line; use pid files.
- On vLLM, the "graphs off" arm is `-cc.cudagraph_mode=NONE` with the same compilation mode as the "on" arm, not `--enforce-eager`, which also turns off torch.compile and JIT warmup [Code-verified].

Change. Exactly one of: the capture list or ceiling; the graph mode (`FULL_AND_PIECEWISE`, `FULL_DECODE_ONLY`, `PIECEWISE`, `NONE`, regular vs breakable); the attention backend (only to restore full decode graphs); a compile or cache setting; SGLang decode or prefill graph flags. For a capture-list change, compute the reachable decode row counts first: every `n x (1 + k)` for `n` in 1..slots and every k in the scheduler's set, and set the ceiling to the largest, rounded up to a multiple of 8.

Record (packet fields):
- Boot log lines: resolved `cudagraph_mode` and compilation mode; the exact capture list; "Capturing CUDA graphs (FULL): N/N" and "(PIECEWISE): N/N" counts; the absence of any `Truncating max_cudagraph_capture_size` line; capture seconds; the "took X GiB" line (recorded, never quoted as graph cost); for SGLang, per-runner capture time and `mem usage`, and the `cuda graph: True/False` flags on decode and prefill steps.
- MemAvailable on every node before start, after capture, and after the run.
- Bucket coverage during the run: vLLM `--cudagraph-metrics` histogram of `(unpadded, padded, mode)`, or SGLang `sglang:cuda_graph_passes_total{mode=...}`; the fraction of decode steps that ran eager.
- Speed: C1 decode tok/s and every concurrency up to the slot count, median of 3, fixed output length, warmed; TTFT per concurrency; per-stream and aggregate separately.
- For a launch-overhead claim: torch-profiler per worker (nsys cannot see vLLM's spawned EngineCore process, NVIDIA forum 363238) for 40 decode steps in both arms; kernels per step, kernel-time sum, wall step time, gap fraction. Graph replays appear as one launch unless graph-node tracing is on [Interpretation].
- Image digest, engine commit, driver version, clock cap (see [Clocks, thermal, and power](13-clocks-thermal-power.md)), config hashes.

Pass gate:
- Every reachable decode shape is captured (full count N/N matches the computed list) and no truncation line appears.
- Bucket histogram shows no eager decode steps at the concurrencies the lane serves.
- Correctness gates ([Quality and correctness gates](21-quality-and-correctness-gates.md)) pass after warmup and outside the timed window: a long loop-detection generation and a long-context multi-marker retrieval. Graphs have produced silent corruption that eager did not (SGLang #37111), and eager has collapsed where graphs did not (NVIDIA forum 366325), so neither arm is exempt.
- Speed: the change beats the baseline by more than the lane's boot-to-boot band at the concurrency it targets, and loses nothing outside that band elsewhere (the one isolated GB10 TP3 A/B had a ±4% band, vLLM #55581).
- MemAvailable after capture at or above the fleet floor above; no node below 4 GiB during the run.

Rollback. Restore the previous recipe (capture list, mode, env) through the lane's promotion mechanism, boot with the pull skipped, confirm the old capture counts in the boot log, and rerun the quick suite once. If a node wedged, do not reboot without the owner's per-instance permission.

## 7. Anti-patterns and known-bad

Measurement and configuration traps:
- [Measured] Quoting vLLM's "took X GiB" line as graph memory. On unified memory it is a free-memory difference that absorbs other allocations and page-cache movement: 0.16 vs 3.48 GiB on two ranks of one boot for the same list (2026-09-20 startup and prefill optimization). The meaning is [Interpretation].
- [Community-measured] Trusting vLLM's pre-capture estimator on GB10. It estimated -35.69 GiB and sized the KV pool at 72.44 GiB at utilization 0.55, and ran out of memory at 0.8 (vLLM #44740, 0.22.1rc1, Qwen3.6-35B NVFP4, MTP 3); a second reporter on 0.26.0 saw -20.50 GiB and 90.6 GiB KV while the post-capture line said 0.73 GiB. On an RTX PRO 6000 (SM120, not GB10) a 4.2 GiB "graph" charge was about 96% warmup transient, with real full graphs at 14-26 MiB each (vLLM #50780).
- [Community-measured] Setting only a scalar capture ceiling that is not a grid entry. 42 at 6 seqs x k6 truncates to 40 with a startup warning, and the 42-token C6 step then runs eager (vLLM #54933; -12% C6 in the MiaAI-Lab A/B). [Historical diagnostic] An earlier "no C6 lift" A/B on the same fork lineage had the shape uncaptured in both arms, so its verdict was void.
- [Community-measured] Letting a fork pick the graph mode by omission: the Anemll-lineage DeepSeek V4 path auto-enables slower breakable graphs when `VLLM_USE_BREAKABLE_CUDAGRAPH` is absent. Set it explicitly.
- [Code-verified] Using `--enforce-eager` as the "graphs off" arm on vLLM; it also disables compile and JIT warmup. Several published GB10 "eager vs graphs" numbers are compile-plus-graphs bundles for this reason: NVIDIA forum 362368 and 364886, vLLM #46253, NVIDIA forum 381543, and two vendor-image notes without protocol (Avarok, Conselara).
- [Measured] Changing the speculation k-set as if it were one variable: it changes the captured shapes and the per-shape kernel geometry together (2026-09-20 GLM 5.3 Flash TP3 frontier dossier, code-verified at the lane's pinned commit).
- [Measured] Timing first-shape compiles (a C4 batch at 47.9 tok/s / 17.7 s TTFT; 2026-09-14 triangle qualification), and letting warmup overlap correctness gates (gate timing declared not a performance result; 2026-09-20 startup and prefill optimization).
- [Community-measured] Assuming eager is the safe baseline. SGLang decode graphs corrupted Qwen3.8-Flash-Next output while eager passed (SGLang #37111; the eager control later crashed separately and the deployment profile was withdrawn); SGLang eager collapsed onto "!" on the `cutlass_moe_fp4` path while graph rows were stable (NVIDIA forum 366325, 4x GB10 Qwen3.5-397B NVFP4, 8 of 8 eager rows).

Memory pressure (see [Memory on unified memory](11-memory-on-unified-memory.md)):
- [Measured] Prefill-graph capture at mem-fraction 0.90 with an oversized pool: out of memory inside `chunk_gated_delta_rule` (2026-08-19 Qwen 3.8 27B FP8 DFlash2). Keep prefill graphs off or the pool smaller.
- [Measured] Too little post-capture headroom: about 2 GiB of graphs plus a ~74 GiB pool left ~6.9 GiB for the OS, inductor workers and activations, and a node's userspace wedged (2026-08-29 K10 pool-cap changelog). Pinning the pool by token count raised free memory from 6.7 to 29 GiB.
- [Community-measured] mem-fraction 0.95 blocked graph capture on a DeepSeek V4 GB10 recipe and hard-rebooted one GB10 during draft-graph capture (as filed in own packets, no protocol); utilization 0.87/0.88 froze a node on a MiMo DFlash 2x GB10 recipe (HeNryous); earlyoom killed graph capture at large KV pins. SGLang disables breakable prefill graphs for DeepSeek V4 because the indexer scratch pinned in the capture pool runs out of memory (`cuda_graph_hook.py` 114-145) [Code-verified].

Compile and fusion:
- [Community-measured] vLLM's default `fuse_norm_quant` / `fuse_act_quant` produced token salad on DeepSeek V4 Flash 0731 on 2x GB10 (vLLM #50773, 0.26.0, greedy). Setting both false removed the salad; the output still did not follow the instruction (a separate issue), and a GB10 commenter disputes whether the group-quant patterns should fire on SM12x at all.
- [Community-measured] torch.compile for DeepSeek V4 on 2x GB10: a prototype compiled in ~6.5 s per rank and captured, but a cached restart failed in replay (Xid 31, segfault) and a later cold fixed-KV run also failed after capture (vLLM #53455); an opt-in compile "garbled output on dual-GB10" (r0b0tlab). DeepSeek V4 lacks `@support_torch_compile`, and adding it fails Dynamo on inline deep_gemm/TileLang bindings (vLLM #51522).
- [Community-measured] SGLang `--enable-torch-compile` breaks graph capture for Qwen3.8-Flash-Next on 2x GB10 (SGLang #36796); an April 2026 SGLang nightly's piecewise capture failed in Dynamo on `_thread.allocate_lock` (SGLang #23386, fixed on main).
- [Measured] vLLM's GPU n-gram proposer requires a torch.compile wrapper and fails at load on a compile-mode-0 recipe (2026-09-11 Qwen 3.8 Flash-Next MTP/lookup screen).
- [Community-measured] Stale Triton kernel cache produced silently garbled output on GB10 until wiped (vLLM #41871, closed stale). FP8 CUTLASS wrappers compiled with an SM120-only guard surfaced as launch failures during Inductor warmup (saifgithub/vllm-gb10-sm121; NVIDIA forum 363514).

Cross-node capture:
- [Community-measured] Breakable capture of a fused all-reduce + RMSNorm across 2x GB10 died at `capture_end()` with an illegal memory access; the root cause was PyTorch's global capture-error mode invalidated by NCCL proxy threads, plus rank phase drift during capture (vLLM #46253). The eager-break-collectives PR #46372 did not fix capture on the MiniMax-M3 expert-parallel model (#46372 comments). Later, after the thread-local and barrier fixes, `capture_sizes=[1]` worked while `[2,4,8]` still crashed (#46253). On the same model, breakable graphs were net-neutral at 14.6 tok/s either way.
- [Community-measured] A rank that captures different graphs from its peers hangs NCCL after piecewise capture (MiaAI-Lab GLM-5.3-Flash-EXL3 README); TRT-LLM 1.1.0rc3 hung at "generation only CUDA graph warmup" across two GB10s and ignored `cuda_graph_config: null` in YAML (NVIDIA forum 366127).
- [Community-measured] All-reduce inside graphs is contested: 18.2 µs eager vs 45.6 µs inside a graph for a 4 KiB all-reduce at 97 all-reduces per token on 2x GB10 TP2, but the same author later credited the eager split with only "+8%", a second operator got "!!!" output with the splitting-op trick, and the headline run included speculative decoding (NVIDIA forum 362009).

Shape- and kernel-specific faults:
- [Community-measured] vLLM `FULL_AND_PIECEWISE` + chunked prefill hung after ~6 requests on DeepSeek V4 Flash 2x GB10, and `PIECEWISE` ran 200+ requests at 4.99 tok/s (eager 4.5) for one reporter; a later TP8 GLM-5.1-NVFP4 reproduction on 8x GB10 wedged under every graph mode including eager (vLLM #40969). SGLang NEXTN invalid-probability asserts first seen with full decode graphs were later reproduced fully eager (SGLang #37052). Graphs are not required for either failure.
- [Community-measured] Bucket trimming as a crash workaround does not transfer across models: capture sizes `[2,4]` ran ~47 tok/s with MTP on Qwen3.5-122B NVFP4, but on Qwen3.6-35B-A3B NVFP4 `PIECEWISE` turned a hang into an Xid 13 crash and `[1,2,4]` still soft-locked (vLLM #37431).
- [Community-measured] Kernels that allocate or exceed SMEM inside capture: SM121 sparse-MLA decode called `torch.full` inside full capture (CosmicRaisins/glm-5.2-gb10 #2); `persistent_topk` wanted 128 KB SMEM (NVIDIA forum 381543); the PyTorch-fallback sampler's `scatter_` failed under capture with n-gram spec decode (vLLM #42745, closed); deep_gemm MoE asserted at capture on `sm_121` (SGLang #39226); a Triton `load_binary` inside decode-graph replay after ~24 h stable cascaded into memory exhaustion and a driver lockup (SGLang #40948, one GB10, one incident).
- [Community-measured] Spec-decode capture bugs: `PIECEWISE` skipped the spec capture-size alignment so partial-acceptance steps hit `cudaErrorIllegalAddress` (vLLM PR #46324, open, reproduced on GB10 with DFlash k=15); DFlash/DSpark depth missing from the compile-cache key so depths 1 and 15 shared one startup plan (vLLM PR #53292); dynamic spec decode + MTP failed full speculator capture on H100 (vLLM #48494).
- [Community-measured] llama.cpp RPC splits crashed in `ggml_backend_cuda_graph_compute` on 2x GB10 (llama.cpp #25791). An RPC server accumulated graphs at 0.76-9.8 MB per token until out of memory, avoided with `GGML_CUDA_DISABLE_GRAPHS=1`, and fixed upstream (reporter confirmed no repro on b8954; llama.cpp #20315).
- [Community-measured] Capturing a weight-bound MoE FFN in a graph measured -15% on one GB10 (Poppy blog, CUDA-event medians, shape not stated); treat as an anecdote.

Uncorroborated claims (keep, do not act on):
- A "confirmed CUDAGraph deadlock" on driver 590.x (Conselara; repeated in NVIDIA forum 362368) has no vendor bug or independent reproduction; NVIDIA forum 359969 documents a different 590 regression.
- A driver change cutting decode 38 -> 11 tok/s on 2x GB10 was attributed by its author to "launch overhead or graph efficiency" without measurement, and the same driver change also reordered RoCE GIDs and forced an NCCL TCP fallback (r0b0tlab benchmark repo).
- "`GRAPH_CAP` must equal `MAX_NUM_SEQS`" or boot hangs (NVIDIA forum 372268 post 239): no mechanism, internally inconsistent ("128/128, or 32/64"), and other GB10 DeepSeek V4 recipes run capture 48 at 6 seqs.

- Whether a boot hang tied to `GRAPH_CAP != MAX_NUM_SEQS` exists at all (NVIDIA forum 372268 post 239). Measure: boot a DeepSeek V4 GB10 recipe at capture 48 and 6 seqs, then at the claimed matching values.
